## Developer workflow

Use pnpm and a compatible Node version; the verification TypeScript scripts use Node 24 directly. Package.json declares Node ≥22.12 for the project. FFmpeg/ffprobe are development tools, not recipient dependencies.

| Command | Purpose |
| --- | --- |
| `pnpm install` | Install dependencies |
| `pnpm dev` | electron-vite hot reload; capture permission identity may belong to the launching terminal/editor |
| `pnpm start` | Build and launch development Electron.app through macOS open; suitable for audio experiments |
| `pnpm start:app` | Build, self-sign, verify, and open RecordStuff.app; prints each phase's duration and records the bundle's runtime inputs |
| `pnpm open:app` | Verify and open the existing development bundle when its recorded runtime inputs still match; does not rebuild it |
| `pnpm check` | Typecheck, all Vitest tests, and production build |
| `pnpm icons` | Generate PNG/ICO assets, the DMG background pair, and native ICNS on macOS |
| `pnpm log` | Follow the current macOS log |
| `pnpm dist:mac` | Build/verify a self-signed app, then create a DMG next to it in dist/ |
| `pnpm diagnose:cadence` | Record the test material through an isolated capture-host fixture and compare the track's delivered frame timestamps and counters with the file's pts, to locate a frame-rate deficit ([details](#frame-cadence-diagnostic)); macOS only, not a pass/fail check |
| `pnpm acceptance:updates` | Build an isolated signed copy; exercise production update handlers/model/settings, process restarts and two real shortcut recordings; retain reports and recordings, then clean up the owned app |
| `pnpm acceptance:settings` | Against the built artifacts: load `out/preload/settings.js` and `out/renderer/settings.html` in a real Electron window, judge the shipped CSP, the sandboxed preload boundary and a real IPC round trip; report and screenshot under docs/verification/measurements. Needs `pnpm build`, no tray and no installed app |
| `pnpm acceptance:regression` | One command runs check (including build), settings fixture and shortcut integration, including repeated open/close/tray-route reopen. Isolated preferences/processes; per-runner reports; stops at the first failure. Does not start/quit the user’s RecordStuff or record. |
| `pnpm acceptance:recipe` | Run a verification recipe phase by phase with one build of identical inputs and write a timing report ([details](#verification-recipes-and-timing)) |
| `pnpm acceptance` | Against the running app with its real settings, countdown included: open the material fullscreen, start/stop a recording with the global shortcut through System Events, report preparation, countdown ticks, `record → started` and the first chunk separately, crop the digit region from the first frames, verify the integrity tier (test-material mode), then cancel a second attempt with a second press; write a report under docs/verification/measurements (gitignored, local) |
| `pnpm acceptance:playback` | Play one saved recording in QuickTime Player through its AppleScript dictionary and judge duration, size, real-time playback, seeking, a picture that follows the seek and playback to the end; a report under docs/verification/measurements, with screenshots only when it does not pass ([details](#playback-check)) |
| `pnpm acceptance:notification` | Against the app in /Applications (optionally `--install` the dist bundle for the run): record, press the "Saved …" banner through Accessibility, judge whether Finder is frontmost and shows the file, several clicks per Finder state, English by default; report under docs/verification/measurements |

Main, preload, and renderer are separate electron-vite entries. Only out files, package metadata, and selected resources enter the app. Tests, measurement tools, and documentation are not runtime dependencies. The app has no FFmpeg subprocess.

## Assets and generated output

- `build/` contains committed packaging assets: `icon.png`, the native macOS `icon.icns`, and the DMG background `background.png` with its `background@2x.png` Retina pair (540×380 points). The builder uses this directory as `buildResources`, explicitly selects the ICNS for macOS, and merges the background pair into a multi-resolution TIFF with `tiffutil`. Keep these files; regenerate artwork with `pnpm icons`. All artwork is generated from code, so the repository has no hand-drawn binaries.
- `resources/` contains runtime tray icons, macOS entitlements, and the bilingual installation/update/removal guide (`INSTALL.md`, `INSTALL.zh-TW.md`). The guide is documentation linked from GitHub releases and the README; the packaging filter copies only PNG/ICO files, so it is not shipped inside the App or the DMG.
- `out/` is generated by `pnpm build`; `dist/` is the single output directory for `pnpm start:app` (App bundle under `dist/mac-arm64/`) and `pnpm dist:mac` (the same bundle plus the DMG). Both are ignored by Git and can be regenerated. Keep any installer you still need before clearing `dist/`; `pnpm open:app` requires an existing bundle built from the current runtime inputs. Locally built DMGs are for checking packaging; released DMGs are always built by CI from the tag.
- `node_modules/` holds installed development dependencies and can be restored with `pnpm install`.

All sources in `scripts/fixtures/` use TypeScript and participate in `pnpm typecheck`. Standalone entries are compiled on demand by [build-fixture.mts](../../scripts/lib/build-fixture.mts), using Vite's TypeScript transform: settings-panel, recording-lifecycle, history-quit, quit-dialog, frame-cadence and release-record-network emit ESM (`.mjs`), while shortcut-failure emits CommonJS (`.cjs`) because it intercepts CommonJS loading before requiring the production app. frame-cadence-renderer is the one renderer-side fixture: it emits a classic script (IIFE) that a `file://` page loads under the capture host's CSP, and `tsconfig.web.json` checks it against DOM types while `tsconfig.node.json` excludes it. Generated entries are kept in each acceptance report directory or disposable test directory; they are not maintained source files or shipped app code. The update-acceptance fixture continues to build with the disposable app source copy. Existing acceptance commands need no separate fixture build step. Compilation removes types; `pnpm typecheck` checks them. Renderer scripts passed as strings to `executeJavaScript` are still runtime code, not TypeScript-checked DOM code.

Quality options and error codes are each defined once as constant lists; their TypeScript types are derived from those lists, and the tray reuses the quality lists. Typechecking also rejects unused locals and parameters. Settings v1 migration remains supported to preserve existing output-folder preferences.

`pnpm signing:create` preserves existing matching Keychain certificates or creates an encrypted identity archive with explicit output/password inputs; see [identity setup](signing.md). It does not import keys or configure trust.

## Current signing and packaging

See [macOS signing identities and self-signing](signing.md) for identity design, certificate creation/backup, troubleshooting, and planned CI provisioning.

[Start-app](../../scripts/start-app.mjs) resolves exactly one valid signing identity, default `RecordStuff Dev`. RECORDSTUFF_SIGN_IDENTITY may specify an exact name or SHA-1. It rejects missing/ambiguous identities, duplicate certificate names, invalid dates, non-self-signed certificates, or a mismatched final signature. SHA-1 identifies the public signing certificate here; release-file integrity uses SHA-256.

The script checks for a running RecordStuff/project Electron process before rebuilding. It removes Apple/CSC release variables from child environments, disables identity auto-discovery, forces signing, sets notarization false, and passes publish never. It does not reset permissions, import keys, notarize, or publish.

Verification performs strict deep codesign checks, inspects nested app/framework certificates without following symlinks, checks identifiers/runtime flags, and matches the outer designated requirement. Only after this succeeds does it package the existing verified app into a DMG.

The [base configuration](../../electron-builder.yml) defines the installer UI: a 540×380 Finder window with the generated arrow background, 128-point icons, and exactly two entries, the App at x=130 and the `/Applications` link at x=410, both centered at y=190. The [local configuration](../../electron-builder.local.yml) extends it and disables notarization/timestamps and DMG signing/update metadata. It must not add `dmg.contents`: `extends` concatenates arrays, and the release gate rejects any root entry other than `Applications`, `RecordStuff.app` and the hidden Finder layout files. Help is intentionally not bundled in any format; installation, update and removal guidance is online. Output is `RecordStuff-<version>-<arch>-selfsigned.dmg`; arm64 and x64 are architecture-specific, not universal. Only arm64 has been verified.

`pnpm dist:mac` produces the same DMG that CI builds and publishes on a tag push (it replaced the former `dist:mac:local` alias and the separate `dist/dev`/`dist/local` folders). The base configuration disables notarization. No `dist:win` script or Windows packaging target is configured.

Self-signing is not Apple approval. Recipients may need Open Anyway for an unnotarized app; managed Macs may restrict that option. Use the ordinary per-app workflow in the [installation guide](../../resources/INSTALL.md), not global security changes. The same guide documents manual update (quit, download, replace at the same Applications path; identity and settings retained) and removal (quit, move the App to Trash; recordings, `~/Library/Application Support/recordstuff` and `~/Library/Logs/recordstuff` remain unless the user deletes them). There is no uninstaller, background service or automatic permission reset. See [Apple](https://support.apple.com/102445).

## Verification tools

```bash
pnpm probe -- /absolute/path/recording.mp4
pnpm verify -- /absolute/path/recording.mp4 --screen 1920x1080 --sync --out
pnpm verify -- /absolute/path/any-desktop-recording.mp4 --screen 1920x1080   # integrity only
pnpm acceptance -- --seconds 10        # unattended shortcut acceptance of the running app
pnpm acceptance -- --skip-cancel --countdown-sound   # the same with the countdown tick on for the round (plan 046)
pnpm acceptance:playback -- /absolute/path/recording.mp4   # the playback case in QuickTime Player; about 20 s
pnpm acceptance:settings                           # settings page + preload in a real Electron window; includes the screenshot matrix
pnpm acceptance:notification -- --install --clicks 2  # short notification smoke check
pnpm acceptance:notification -- --install          # saved-notification click → Finder in front; ~1 min; built app swapped into /Applications for the run
pnpm acceptance:notification -- --install --full   # all three Finder states, English; ~3 min (estimate)
pnpm matrix -- quick
pnpm matrix -- all
pnpm matrix -- long
pnpm matrix -- fps,long                                  # several matrices in one round: one build, one material launch
pnpm matrix -- fps,quick --repeat 2                      # repeats interleave; the summary groups them per case
pnpm diagnose:cadence                                    # frame cadence at 30 and 60 fps, two runs each
pnpm diagnose:cadence -- --request 30:30.6,60:62.4       # compare a candidate frame-rate request
pnpm measure:finalization -- --dir /Volumes/test/rs --seconds 15 --repeat 10   # stop-to-ready and its phases into an isolated folder
pnpm bench:publication -- --dir /Volumes/test/rs --sizes 64m,2g                 # publication cost by file size; no recording
pnpm measure:cpu                                         # CPU budget on the quit bundle: idle, one 30 fps recording, idle after it, Settings open; ~15 min
pnpm measure:cpu -- --fps 60 --repeat 3                  # the baseline round: both frame rates three times each; ~25 min
```

Verify accepts multiple files, an optional log path, source dimensions, `--moving` (the content moved continuously), sync detection (implies `--moving`), Markdown/JSON output, and an explicit JSON destination. It requires channel energy, and with `--sync` the flash/beep markers too; it exits 1 when a check failed, required evidence is incomplete or a file cannot be read, 2 when a required tool is missing (blocked) and 0 otherwise ([verdicts](#measurement-pipeline-and-thresholds)). The default evidence directory is docs/verification/measurements; it is gitignored, so raw runs stay local and only interpreted conclusions go into the verification record. It reads every retained file (the active log and `.1`–`.3`, oldest first) and pairs a recording with its session by identity (plan 029): the run and session ids of the [session records](desktop.md#logs), looked up by the file's full path, falling back to its name only when a single session in the log names a file of that name (a copied file). One record logged twice is one outcome; different outcomes for one session are a conflict. A failure that kept no file claims no path, because a same-second retry may reuse its temporary name. Launches from builds before session records use a conservative legacy association: an outcome is accepted only when nothing else could own it (a `file finalized` line, the one session still recording, or the one unresolved failure whose text matches), so two unresolved failures are never assigned by which printed first. Otherwise the report says the metadata is ambiguous, conflicting or unknown, and no check against the requested settings is judged; media measurements stay independent of the metadata. `pnpm acceptance` and `pnpm matrix` fail a case whose metadata is not matched to its own session. A replay of the 244 retained logs available on 2026-09-25 gave the same association as the old order-based reading for all 628 files it had paired; no retained log contained the reversed-cleanup interleaving that reading got wrong.

### Test material

`scripts/test-material.html` is the one fixed page every measurement records: scrolling small text (sharpness), thin red/blue lines and coloured text (chroma edges), a square moving every frame (frame timing), a top-right box that flashes white for 100 ms once a second, and a soft 660 Hz tone (120 ms, about −26 dBFS, alternating left/right) on the same audio clock. Flash and tone are the sync markers: `verify --sync` finds them with ffmpeg blackdetect on the box and silencedetect (−35 dB, 0.4 s) on the audio, so the page must otherwise stay silent and nothing else may play on the machine. Because the audio is sparse, the AAC bitrate of these recordings is reported, not judged (`--test-material`). Opened by hand, the page starts on a click (browser autoplay policy); `pnpm matrix` and `pnpm acceptance` open it in a fresh-profile Chrome app-mode fullscreen window on the primary display with autoplay allowed and `?auto=1`, so no click is needed. Acceptance reports record the page's SHA-256 so results can be tied to a material version. Version history: until 2026-09-19 the tone was a 1 kHz, 60 ms beep at 0.5; on 2026-09-20 it became the softer 660 Hz tone above, and the first run with it detected 20 flashes and 19 beeps in 20 s with a 79 ms flash/beep offset, inside the historical 45–80 ms latency, so earlier sync results stay comparable. On 2026-09-29 the gain dropped from 0.3 (about −10 dBFS) to 0.15 (SHA-256 `4064e63e…`; 10 flashes with 10 beeps in 10 s at a 65 ms offset, channel RMS −33.2 against −27.3 dBFS), and on 2026-09-30 to 0.05, about −26 dBFS and 9 dB above silencedetect's threshold, to stay quiet beside whoever runs a round. Capture takes the page's digital level, before the system output volume, so the volume setting does not narrow that margin. Its first acceptance run matched 10 flashes with 10 beeps in 10 s at a 61 ms offset with channel RMS −42.8 dBFS. The same file with only its audio attenuated offline still matched all 10 pairs down to −6 dB (63 and 65 ms), lost two beeps and read 101 ms at −9 dB while `verify` still passed, and failed at −12 dB: this level keeps 6 dB of clean margin and is the quietest one that does, so do not lower it further. The tone now crosses the detector threshold about 3.6 ms into its attack (0.6 ms at 0.3), which adds a few milliseconds to the flash/beep offset, far below a frame: offsets and drift stay comparable, while audio levels (channel RMS) of earlier versions are higher and are no baseline for this one. Current SHA-256: `e98bf1fc63d2e7f0662a6d3dca62f21bdf3afa9debff6b4e64455b46a20a70bb`.

Matrix is macOS-only developer automation. It launches the test material in a Chrome app-mode fullscreen window on the primary display unless --no-open-material is supplied, samples the app's process tree with the [shared CPU sampler](#cpu-budget), and drives an unpackaged app through RECORDSTUFF_AUTORECORD. Keep source display/audio stable during the run. Packaged builds ignore this variable. Autorecord quits immediately after saving, so on macOS that quit cancels the pending saved notification; a banner is not part of autorecord completion. The internal automatic-recording parser accepts durations in (0,3600], validated quality overrides merged over defaults, not user settings, an optional `countdown` (0, 3, 5 or 10) and an optional absolute `outputDir` that replaces the stored folder in memory for that run. Autorecord counts down 0 seconds unless its configuration names a countdown, so the matrix and audio-quality runs keep their timing; the stored countdown is never used there. Every case requires channel energy and the sync markers (plan 030): the matrix checks for ffmpeg, ffprobe and the Command Line Tools' clang before it builds or records anything and exits 2 (blocked) without them. A case passes only when none of its checks failed, was blocked or is incomplete; such cases are listed with each unmet check and its reason at the end of the run and in the measurements file, and the run exits 1.

One invocation is one desktop round (plan 042): it builds `out/` once, opens the material once and runs the named matrices in order. Names are comma-separated (several arguments are joined), and a name listed twice runs twice, so `fps,fps,long` records fps twice and long once. `--repeat N` (1–10) repeats the whole list, so a case's repeats interleave with the other cases rather than always running first or warmest; `--dry-run` prints the order. An unknown or empty name, an unknown option or a `--repeat` outside 1–10 prints the usage and exits 2. Cases run back to back: the next one launches as soon as the previous file is verified, and that verification is the rest between recordings. Each case prints and appends a timing line (launch to recording, recording, stop to saved, quit, and each verification tool), and the measurements file gets a Timing table with the round's preflight, build, material and wall time. A case that runs more than once is titled "run k of n", and a Repeats table lists every run's verdict with the minimum, median and maximum of the average frame rate, median interval, drops, CPU average and 95th percentile, encoder CPU, flash/beep offset, drift and video bitrate; the case passes only when every run passed. A case the round never reached, because it stopped when ffmpeg or ffprobe went missing, counts as a blocked run. Exit codes are unchanged, except that a round whose cleanup left a process running exits 1. SIGINT or SIGTERM stops the build's whole process group, sends SIGTERM to the running case's app, whose normal quit stops and saves a recording in progress (within 5 seconds of a launch it first waits for the app to appear; anything still running after 30 seconds is killed), waits for the material's launch to finish and closes the material browser, ends the desktop round, confirms the processes exited and exits 130 or 143 without writing measurements; it names the interrupted case's saved file, which was not verified. Only processes of this checkout's Electron.app and the material's private profile are stopped, never an installed RecordStuff. A SIGTERM that arrives while ffprobe or ffmpeg is running takes effect when that tool finishes (seconds), before the next case starts or any measurement is written; Ctrl-C also stops the tool itself.

Verification dominates a case's overhead, and within it the two ffprobe passes (the full-decode frame count and the frame timestamps) take most of the time: on the M1 Pro reference machine 4.6 of 5.4 seconds for a 30-second 30 fps file, 12.4 of 13.9 at 60 fps and 22.9 of 27.0 for long. The three ffmpeg passes (astats, blackdetect, silencedetect) take under a second, or 4 seconds for long, so they remain separate runs.

| Matrix | Cases |
| --- | --- |
| quick | Three 15-second recordings: 1440p Standard/High and Source Standard |
| levels | Three 30-second 1080p recordings: Economy/Standard/High |
| fps | Source Standard at 30 and 60 fps, 15 seconds each |
| long | 180-second 1080p Standard/30 fps drift regression |

The historical ten-minute baseline has already been recorded. Long now uses three minutes by user decision; quick and fps use 15 seconds since plan 042, which still holds about 14 flash/beep pairs against the minimum of 3. On the reference machine a round costs about 8 seconds of preflight, build and material, plus per case the recording, about 2.5 seconds of launch and quit, and its verification (about 3 seconds for a 15-second 30 fps case, 7 at 60 fps, 27 for long): fps alone takes about a minute, quick about 1.2 minutes, long 3.6 and all about 6 (estimated from the plan 042 phase timings). [Raw evidence](../verification/README.md) retains the older run's duration and verdicts.

### Frame-cadence diagnostic

`pnpm diagnose:cadence` (plan 041) locates a frame-rate deficit; it judges nothing and ships with nothing. Each run records the test material (Chrome kiosk, as in the matrix, unless `--no-open-material`) through the isolated [frame-cadence fixture](../../scripts/fixtures/frame-cadence.ts): the production main-side capture host, the built capture-host preload and the real renderer host, answered like the app answers display-media requests (primary screen plus loopback). It is launched with `open -a` on the development Electron.app so that app's screen-recording grant applies; quit RecordStuff and the development app first. A [renderer wrapper](../../scripts/fixtures/frame-cadence-renderer.ts) only observes: it timestamps every frame the video track delivers before MediaRecorder (`MediaStreamTrackProcessor`), samples `track.stats` and `getSettings().frameRate` once a second and marks the recorder's start and stop. The runner compares those timestamps, the delivered/discarded counters (from the first sample after the recorder started, which leaves out the start-up burst) and the file's pts over the recording, samples Electron CPU, and names the layer the distributions point at: `source-floor` (frames reach the track late, none discarded), `track-limiter` (the track discards more than 1%), `recorder-timestamps` (on time at the track, late in the file) or `on-time`, using 1% of the period for the median. A tap that saw fewer than 99% of the file's frames is `undetermined`, because a stalled observer would look like a slow source. Duplicate frames are not counted; `ffmpeg -vf mpdecimate` on the retained file shows them. Interval percentiles are the shared nearest-rank ones of [stats.mts](../../scripts/lib/stats.mts) and the median the midpoint median, so p95 means the same as in `measure:cpu` and `measure:finalization`. Reports written before 2026-09-29 (plan 053) interpolated p05 and p95 linearly; their medians are unchanged, but their p05/p95 are not directly comparable with later ones.

Options: `--rates 30,60`, `--runs 2` (runs alternate rates), `--seconds 30`, `--load N` (N busy processes during each recording), `--request 30:X,60:Y` (replace the frame-rate constraint with `{ ideal, max }` at those rates in both `getDisplayMedia` and `applyConstraints`), `--ideal-only` (`{ ideal }` alone), `--label`. Without `--request` it measures the product's own request. Evidence goes to `docs/verification/measurements/<timestamp>-frame-cadence/` (`summary.md`, `summary.json`, and per run `recording.mp4`, `result.json`, `fixture.log`). It exits 0 when every run produced its evidence and a classification, 1 when one did not or cleanup left a process behind, and 2 when ffprobe is missing or the desktop locked. SIGINT or SIGTERM stops the round's own fixture, busy processes and material browser, confirms they exited, and exits 130 or 143 without a summary. Sync, channel energy, bitrate and drops stay with `pnpm matrix`.

### Finalization measurement

`pnpm measure:finalization` (plan 037) measures how long a stop keeps the next recording waiting, and where that time goes; it judges nothing and ships with nothing. One invocation is one desktop round: it builds once, opens the test material (Chrome kiosk, unless `--no-open-material`) and records `--repeat` takes (default 5) of `--seconds` (default 15) through the development app with `RECORDSTUFF_AUTORECORD`, `--quality` (default standard) and `--fps` (default 60) at source resolution, into `--dir`, an absolute folder given as autorecord's `outputDir`, so settings.json is never written. Quit RecordStuff and the development app first. Stop-to-ready is the app log's `state → stopping` to `state → idle`, the moment a toggle starts a new recording again; its phases come from the recorder's `finalize timing` line (host handoff, queued writes, flush, close, publication with its method, cleanup, and the interruption sentinel's completion checkpoint) plus the UI settle from `file finalized` to idle. The checkpoint (`checkpoint N ms`, plan 053) reads the session's sentinel and rewrites it atomically with fsync in userData, so a slow userData volume shows there; a session whose latest sentinel write failed skips it and logs `checkpoint ? ms`, and lines logged before the field existed still parse, without it. Each take's file needs a video and an audio stream, no decode errors and, unless the take stopped early for low disk, a duration within 2 seconds of the requested one. `--verify quick` (default) fully decodes the first saved take with ffprobe and, for the rest, reads streams and duration and decodes only the first and last second; `--verify full` decodes every take. The window decode uses ffprobe because `ffmpeg -f null` reports the repeated timestamps of static screen content as errors although every frame decodes. The file is then deleted unless `--keep`, so a round never accumulates recordings on the volume. Point `--dir` at an isolated folder or disk image for slow, small or foreign file systems; never fill the system disk. Evidence goes to `docs/verification/measurements/<timestamp>-finalization-<label>/` (`summary.md` with nearest-rank distributions per phase, `summary.json`). It exits 0 when every take saved and verified, 1 when one did not, outlived its bound (the report says whether the app then quit on SIGTERM or had to be killed) or cleanup left a process behind, 2 when ffprobe is missing, the app is already running or the desktop locked, and 130 or 143 after SIGINT or SIGTERM, which wait up to 5 seconds for a launch still in flight, quit the round's app normally and close the material without a summary.

### Publication benchmark

`pnpm bench:publication` (after plan 037) answers how a save's publication grows with file size on one volume, without recording, a desktop, screen permission or `out/`. It bundles [the benchmark](../../scripts/fixtures/publication-bench.ts) with the production FileWriter and runs it under Electron's own Node (`ELECTRON_RUN_AS_NODE`), so publication uses the app's libuv. For each `--sizes` entry (default `64m,2g`) and `--repeat` round (default 3) it writes the file in 4 MiB chunks into `--dir`, calls `finish`, which links where the volume allows and copies otherwise, and reports publication, flush, close and cleanup times, the method with the link's error code, and the write rate; the file is deleted unless `--keep`. The writes run far faster than a recording's, so most of the file is still unflushed at `finish` and the flush phase is larger than after a real take: judge publication, and take flush from `pnpm measure:finalization`. It refuses to start unless the volume has twice the largest size plus 1 GiB free, because a copy briefly holds two copies; with `--keep` every kept file counts too. Evidence goes to `docs/verification/measurements/<timestamp>-publication-<label>/` (`summary.md`, `summary.json`). It exits 0 when every file published, 1 when one failed, 2 on bad arguments or too little space, and 130 or 143 after SIGINT or SIGTERM, which stop the benchmark and remove its own files.

### CPU budget

`pnpm measure:cpu` (plan 049) keeps RecordStuff's CPU small while it waits in the menu bar and normal while it records, on the packaged app; `pnpm matrix` judges recording CPU with the same sampler. CPU is a percentage of one core, as Activity Monitor shows it (the reference M1 Pro has ten cores, so the whole machine is 1000%). Wake-ups are idle plus interrupt wake-ups per second, Activity Monitor's Idle Wake Ups. What may run while idle is listed in the [design overview](design-overview.md#waiting-in-the-menu-bar).

**Sampler.** [cpu-sampler.c](../../scripts/lib/cpu-sampler.c), after Cap's per-process sampler, is compiled with `clang` from the Command Line Tools into the run's folder; without them the measurement is blocked (exit 2), never skipped. Once a second, on a fixed schedule, it lists every process, keeps the app's main process and all its descendants, resolved again at every sample, plus every process named VTEncoderXPCService, and prints each one's `proc_pid_rusage` counters: CPU time in nanoseconds, idle and interrupt wake-ups, energy and resident memory. `ps` is not used: it reports CPU time in hundredths of a second, too coarse for an idle second in which 0.2% is 2 ms, and its `%cpu` is a decaying average that flattens peaks and carries start-up into later samples. [cpu-sampler.mts](../../scripts/lib/cpu-sampler.mts) turns the counters into per-second figures and reports the average, the 95th percentile (nearest rank) and the maximum, per process and in total. A window counts only the one-second intervals lying wholly inside it, so CPU spent before its start never leaks in, and an interval in which the app's set of processes changed is discarded and listed, except where a start or end is expected. A window whose judged intervals cover less than 80% of it, or a sampler that exited before it was stopped, fails: missing samples never pass as zero CPU. VTEncoderXPCService, the system's hardware encoder, is reported apart and never counted as the app; it is a shared system service (four idle instances on the reference Mac), so its CPU is judged, not its presence. Energy is macOS's own per-process estimate, so it is reported, not judged.

**Scenarios.** Build the bundle with `pnpm start:app` and quit it, then run `pnpm measure:cpu`. It refuses to start while any RecordStuff runs. With the app quit it writes the countdown Off, the recorded display to the primary one (where the material opens) and the quality Standard, Source, 30 fps into settings.json, launches `dist/mac-arm64/RecordStuff.app` and waits for `ready;`, the granted permission, `recording history: loaded` and the launch update check's outcome or its `updates: launch check skipped` line, so startup work is over before anything is judged:

- **A. Idle after launch,** Settings closed: `--minutes` (default 5) after a 60-second warm-up.
- **R. Recording:** a 60-second recording started and stopped with the recording shortcut over the moving test material (Chrome kiosk on the primary display), judged over seconds 5 to 55 with VTEncoderXPCService followed. `--repeat N` (odd, 1–9, so the median is one run's own figure) records N times and judges the median run. `--fps 60` then quits the app, writes 60 fps and relaunches for a second set.
- **B. Idle after the recording:** from 30 seconds after the last save, `--minutes`, with the idle thresholds.
- **C. Settings open behind another app:** opened with its shortcut, confirmed by the app's `settings shortcut: … pressed` line and a running Settings renderer, Finder brought to the front, measured for 3 minutes after 10 seconds of settling, then closed.

**Process roles.** Every idle scenario also checks the app's processes by Chromium role, read from their command lines (`--type` and `--utility-sub-type`), because the three helpers share one name. The idle contract, `IDLE_ROLES` in cpu-sampler.mts: the main, GPU and network-service processes once each, and besides them only what the [design overview](design-overview.md#waiting-in-the-menu-bar) explains. That is at most one pre-warmed renderer after launch (A), which the first window takes; at most Chromium's audio service after a recording (B), which the first system-audio capture starts and which stays until the app quits; and exactly one renderer, the Settings page, while Settings is open (C), so a Settings window that never opened fails instead of measuring closed idle. With Settings closed no renderer may remain after a recording, so a capture host or countdown overlay left behind fails even though the pre-warmed renderer is gone; any other role fails too. Five seconds after every save the roles are snapshotted, and every snapshot of a launch, and B's roles, must equal the first: what a recording starts once is expected, what it adds each time is a leak, the way a leak detector such as [fuite](https://github.com/nolanlawson/fuite) counts growth per repetition instead of comparing with a cold start. The report also gives the app's memory at each snapshot, reported, not judged.

`--skip-recording` leaves out R and B, `--skip-settings` leaves out C, and `--out` names the report folder. The report, `report.md` and `report.json` under `docs/verification/measurements/<time>-cpu/` (gitignored), gives each scenario's checks against the budget, its judged and discarded intervals, CPU, wake-ups, energy and memory in total and per process, the saved files, and the machine, macOS, Electron, displays, power source and bundle time. Afterwards the runner quits the app normally (after an interruption it first waits up to 10 seconds for an app whose launch it had already requested), confirms it exited, closes the material browser and confirms that it exited too, and, once no RecordStuff process remains, sets `countdown`, `display` and `quality` back to their values before the run, keeping anything else the app saved meanwhile; the original file is kept beside the report as `settings-before.json`. The recordings stay in the output folder. Like the other desktop runners it declares user activity and holds a display and idle-sleep assertion for its lifetime. It exits 0 when every judged check passed, 1 when one failed, the run failed or cleanup was incomplete, 2 when blocked (no Command Line Tools, a locked screen), and 130 or 143 after SIGINT or SIGTERM, which settle a recording in progress (the shortcut is sent only while that recording is counting down or recording and no stop was sent yet, so it never starts a new one), close the material, quit the app and restore the settings, then write a partial report marked INTERRUPTED.

**Budget.** Initial targets from plan 049, confirmed by the [2026-09-28 baseline](../verification/history-2026-09.md#plan-049-cpu-baseline--2026-09-28) on the reference M1 Pro; `CPU_BUDGET` in cpu-sampler.mts holds them.

| State | Threshold | Why |
| --- | --- | --- |
| Idle, Settings closed (A, and B after a recording) | Average ≤0.2%, 95th percentile of one-second samples ≤1%, ≤5 wake-ups per second in total | There is nothing to do: the only periodic work is the 5-second permission poll. Apple's [energy guide](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/Timers.html) asks apps to respond to events instead of polling |
| After a recording (B) | The idle thresholds from 30 seconds after saving, the idle contract's roles with no renderer, and the same roles after every recording; VTEncoderXPCService below 0.1% is a warning, since the service is shared | A timer, renderer or encoder left behind shows up here; comparing with the state right after launch would not, since the first recording takes the pre-warmed renderer and starts the audio service once |
| Settings open behind another app (C) | Average ≤0.5% | One idle renderer with no running animation |
| Recording at 30 fps (R and the matrix) | Average ≤30%; until the baseline confirmed it, the former 40% ceiling applied | Capture and H.264 encoding run in hardware; the app's own share is the Chromium media pipeline, AAC, IPC and file writes |
| Recording at 60 fps | Average ≤40% | Twice the frames, not twice the fixed costs |
| Hardware encoder while recording | Reported, not judged | Absent while the app's own CPU is high suggests a software-encoding fallback, which in Cap's benchmark cost tens of times the hardware path per frame |
| Against the baseline | A recording more than 25% above this machine's baseline for the same case is a warning, even under its threshold | A regression can hide under a generous ceiling; CPU drifts between rounds, so it is not a failure |

Baselines live in [cpu-baselines.json](../../scripts/lib/cpu-baselines.json), keyed by `sysctl hw.model`: each recording figure is the median average of three repetitions, entered by hand from a baseline round together with its verification history entry. A machine without an entry is judged only against the thresholds. Another machine, or an Electron upgrade, takes a new baseline before its results are compared. A baseline that fails a target is a finding to investigate, not a reason to loosen the target without written evidence and the maintainer's agreement.

**Matrix.** Each `pnpm matrix` case follows the development Electron.app's main process and its descendants with the same sampler, starting within a second of launch, and judges them over the case's recording from its third second to the stop request (a case without those log lines falls back to the third second after launch until exit, where the capture host's start and end are expected). A case whose sampler never found the app, exited early or covered less than 80% of that window fails as CPU evidence incomplete. Its CPU check reports the average, 95th percentile, peak and VTEncoderXPCService, fails above the frame rate's threshold, and notes a baseline regression (also printed on the console) and a missing encoder. The 17%, 21% and 23% figures recorded before plan 049 came from `ps`'s decaying average over whole cases and are not comparable.

### Selecting acceptance coverage

Choose required checks and exclusions using the [shared testing policy](../testing.md). Use the [shared acceptance cases and report](../acceptance.md) for native/recording work. This guide owns command mechanics and thresholds, not a separate test-selection policy.

The update fixture is instrumented and matrix uses autorecord; neither replaces acceptance of the normal built app. Notification acceptance retains its installed-app path and distinct Finder-state coverage. An unchanged file and verification scope can reuse media evidence; different artifacts or UI actions cannot. Shared material arguments and bounded log waits live in `scripts/lib/acceptance.mts` and `scripts/lib/acceptance-runtime.mts`; each runner retains its own app lifecycle and verdicts. Log positions are rotation-aware cursors from `scripts/lib/log-reader.mts` (plan 029), shared by waiting and cleanup: a cursor is a file's identity (device, inode, birth time) plus a byte offset, so reading since it follows that file into whichever archive now holds it and then reads every newer file, each line once. It tolerates the moment between a rotation's rename and the next append, holds back an unterminated last line, and reports an explicit evidence gap when retention deleted or truncation erased the cursor's history, instead of waiting out the timeout. The cursor also keeps the 64 bytes before its offset, which an append-only log never changes, so a file truncated and regrown past the offset between two reads is a gap too, not a silent skip. The `start:` line of a second launch refused by the single-instance lock is not a process start, so it neither hides the running app's state nor splits its log. The hotkey runner requires the app's run id, binds its waits to the session named by this run's capture record, and takes the file from that session's terminal record. Runners that start a real recording never absorb the countdown into a latency threshold (plan 040): `pnpm acceptance` uses the real settings and reports each phase from the app log (press → `prepared`, each `state → countdown (n)` from the first, the overlay's dismissal, `record` after the anchor, `record → started`, `started → first chunk`); the notification runner seeds `countdown: 0` with the language and restores the user's value; the update fixture sets 0 in its isolated userData; autorecord uses 0. A cancelled countdown settles an interrupted recording on its `cancelled:` line, and a cleanup that finds a countdown presses the key once to cancel it.

With a countdown, `pnpm acceptance` converts the logged overlay placement (window and display bounds, in points) into frame pixels and saves crops of that region from the first 15 frames and from the 15 frames two seconds later, selected by timestamp, to `digit-crops/`. Over the test material the region lies inside the black marker, which flashes white once per second, so each early crop is compared with the later one of the same flash phase: frames bright in either (the flash, where a white digit cannot show) are skipped, and the round fails when a judged frame's mean luma difference exceeds 3 levels or no frame could be judged. Without the material the crops are saved but not judged. The cancel case then presses the shortcut, waits for `state → countdown`, presses again, and requires a `toggle` cancel, no remaining temporary or final file, no failure, notification, `record` or recording line, and idle; `--skip-cancel` omits it and a countdown of Off makes it not applicable. The report says whether the session's countdown ticked, from the `prepared` line's `sound on`/`sound off` (plan 046). When it ticked, the runner mixes the first 500 ms of the recording's audio and the 500 ms from 2 s on to mono and measures the loudest 50 ms Hann-windowed frame (25 ms hop) at the tick's pitches, 523 and 784.5 Hz, with Goertzel. The material's 660 Hz tone leaks about −58 dBFS into those bins in both windows alike, while a tick measures about −28 dBFS at full scale, so the round fails when the first window is more than 6 dB above the later one and above −70 dBFS, or when a beep onset in the first 500 ms has no flash beside it. Capture can begin inside a material beep: the file then starts with silence and the beep at full level, and that abrupt onset reaches both tick pitches at about −41 dBFS, which the same beep 2 s later, with its 10 ms attack, does not. The runner therefore looks for that truncated onset: the first window's first sample at half its peak, with nothing above a tenth of the peak from 25 ms to 1 ms before it (room for an AAC frame's pre-echo) and nothing above −70 dBFS earlier. When it finds one, it silences both windows up to it and fades both in over 20 ms from it before measuring them: the repeated beep gets the same gentle onset in both, which keeps the later window near −67 dBFS at the tick's pitches, so a tick whose tail the file starts inside still stands out instead of hiding under the onset's energy. A sound that rises through its own attack, a file that starts with sound and a window with nothing above −70 dBFS are compared as recorded, so no sound that could reach the floor is discarded. The report gives the onset (plan 054). What this cannot see is the faint tail of a tick that began about 60 ms or more before capture, at −28 dBFS, when capture also began inside a beep. `--countdown-sound` turns the stored switch on for the round: already on (a missing field reads as on) changes nothing; off makes the runner check everything that can refuse the round first (the output folder, a locked desktop), then quit the idle app, set only that key and relaunch the same bundle. The key is set back only once no RecordStuff process remains, after the final quit or, when setup fails after the relaunch, after quitting the app it launched, because a running app would write the round's value back on its next save; if the app cannot be confirmed gone, the run fails and says the key was not restored ([stored-override.mts](../../scripts/lib/stored-override.mts)). It refuses a stored countdown of Off. The notification runner and the update fixture seed a countdown of 0, autorecord never ticks, and the controlled build starts from defaults, so no other runner hears it. Before its stop key, `pnpm acceptance` looks for its session's `saved` or `failed` record since the capture record; a session that already ended is reported and fails the run without the key, which an idle app would take as a new start (plan 054). Hotkey and notification runners share interrupted-recording settlement, which waits for saving and never toggles stop twice after a successful stop command; runner evidence logs mark a lost history in place of its lines.

### Notification acceptance

The verdict now requires a `clicked` event matching the observed banner body (falling back to this save's expected localized body when absent) and a successful reveal request matching its full path. These are separate diagnostics: missing reveal evidence alone is no longer labeled an undelivered callback. Old builds without click logging cannot pass this stricter runner; historical reports retain their original conclusions.

Notification timing diagnostics include `tracksStoppedAt` (renderer wall-clock milliseconds after stopping tracks), main-process `host stopped` and `file finalized`, plus `saved scheduled`, `saved cancelled`, and `saved request failed`. The JS timestamp does not prove OS readiness. Correlate these with the existing request/show/click logs, AX observations and narrowly filtered macOS logs when available. No system-log access is required by the app. The saved request delay is 500 ms on macOS; the runner still searches for only 5 s after save. Historical Plan 017 completion criteria and results are retained in the [verification history](../verification/history-2026-09.md#saved-notification-timing--2026-09-20); they are not the default gate for every change.

Each case also writes `<language>-<finder>-<click>-diagnostics.json`: timestamped search attempts, bounded Accessibility traversal text/errors, and app notification lifecycle events. A non-passing case gets an additional observation-only snapshot (up to 5 s, so failed cases may take longer). The app logs show-requested/shown/clicked/closed/failed separately; a shown event alone is not proof that the script found a visible banner. These local files can contain notification text and are not committed.

`pnpm acceptance:notification` checks whether clicking the saved notification selects the file and brings Finder forward. Each case records for 2 s, searches for that save's banner for at most 5 s, samples the frontmost app for 3 s, then reads Finder's selection and Accessibility row. Missing banners are recorded as not run; the script does not make extra recordings to retry. A group needs at least two passing clicks and no failed clicks; not-run counts remain visible.

The default is five clicks with Finder closed, in English (roughly one minute). `--full` covers three Finder states × five clicks in English (15 cases, roughly three minutes estimated from prior case timings; actual time depends on Accessibility). It changes only Finder coverage, not the language. Localized notification text is unit-tested; use `--languages zh-TW` for native Traditional Chinese checks, or `--full --languages en,zh-TW` to explicitly request both languages (30 cases). Every case prints its start, progress and elapsed time. Use `--clicks 2` for a shorter smoke check; values below two are rejected. Other options: `--finder closed,behind,minimized`, `--languages en,zh-TW`, `--seconds`, `--front <app>`, `--keep-recordings`, `--out`.

The installed bundle reproduced a focus race that local dist runs did not: macOS activated RecordStuff after the notification callback. Consequently the script tests `/Applications/RecordStuff.app`. `--install` temporarily copies the signed `dist/mac-arm64/RecordStuff.app` there, then restores the verified previous app; successful restoration removes the backup, failed restoration preserves it and reports its path. Raw reports stay under `docs/verification/measurements`.

Run on a dedicated desktop: close Finder windows first, leave the desktop alone during the run, and grant the terminal Accessibility plus Automation access to Finder and TextEdit. Existing Finder windows cause preflight to stop without closing them. A fresh temporary TextEdit file is opened for each case; only that file is closed, not other documents. Finder windows are tracked by their IDs after setup or a matching reveal. Unknown windows, including a reveal interrupted before its ID was observed, are left open and reported for manual cleanup. After closing the test document, TextEdit quits if no other documents remain; otherwise it stays running to preserve those documents. This avoids a general-purpose window snapshot/restore system. The notification verdict checks the session-wide frontmost application and Finder selection, not the monitor containing the windows. Test windows on a secondary monitor are valid for that verdict; RecordStuff still records the primary monitor, so those windows need not appear in the recording. Placement on a particular monitor or Space is not asserted.

Ctrl-C or SIGTERM cancels commands and waits. Commands have a 10 s timeout (process lookup 5 s, app copies 60 s); shortcut delivery and Finder window creation finish within their 5 s command limit before cancellation takes effect. Cleanup uses an independent 120 s budget, gives the current recording up to 30 s to settle, and sends stop at most once. It never reads a previous recording as evidence that the current one stopped. If recording settlement cannot be established, it leaves the app running and preserves the backup instead of quitting or replacing it. Settings are restored only after the app stops; the app stays closed even if it was running before the test. Incomplete runs, cancellation and cleanup failures fail the report. These bounds cover asynchronous operations, not an unresponsive filesystem or OS.

Not covered: tray menu reveal, other Spaces and Notification Center list clicks after the banner disappears. Historical timings, failures and later completion evidence are preserved in the [notification history](../verification/history-2026-09.md#finder-foreground-after-a-notification-click--2026-09-20); do not treat an older failure status as the current result.

### Playback check

`pnpm acceptance:playback -- <file>` covers the [playback case](../acceptance.md#recording-smoke-and-native-cases) for a saved file without a person or Computer Use at the player. It opens the file with `open -a "QuickTime Player"` and drives the player through AppleScript: QuickTime's duration within 0.5 s of ffprobe's and the same dimensions; at least 75% of 2 s of wall time played from the start; seeks to 25%, 25% again and 75% landing within 0.25 s; the front window's picture changing between the two positions by a mean of at least 1 gray level and more than four times the change between the two views of the same position; and playback from 1.5 s before the end stopping at the end. The audio track, QuickTime's mute and the system output volume are reported, not judged. `report.md` and `result.json` go to a new directory under docs/verification/measurements; the screenshots of each step feed the picture check and are kept there only when the round does not pass. Exit codes are 0 pass, 1 fail (including incomplete cleanup) and 2 blocked: not macOS, no ffmpeg/ffprobe, a locked session, or QuickTime Player already running, which the check refuses so that it only ever closes what it opened. It closes its document, quits the player and confirms the process exited. Its first run, on the 10.27 s smoke recording of 2026-10-01, measured a mean change of 29.42 between positions against 1.18 for the repeat, the controls overlay fading in between.

Screenshots need Screen Recording permission for the terminal; without it they show no QuickTime window, and the picture check fails with that hint. Not covered: clicking the player's own controls, other players, and whether the audio sounds right, which needs a listener.

## Measurement pipeline and thresholds

For a from-scratch explanation of the pipeline, the test material, each metric and why some settings measure better than others, see the learning article [Measuring screen-recording quality](../learning/measuring-screen-recording-quality.html) (Traditional Chinese). This section remains the reference for the current commands and thresholds.

Media-tools runs ffprobe/ffmpeg; verify.mts parses and judges pure data; verify-recording.mts pairs files with logs and saves results; CLI/matrix orchestrate. For long files, frame timestamps are sampled in separate head/tail intervals so the unobserved middle is not counted as dropped frames. The test page supplies moving content plus flash/beep markers on an audio clock.

Checks are in two tiers. **Integrity** checks hold for any content and are what a release acceptance needs: they ask whether the file is what the session produced. **Performance** checks are only meaningful when the recorded picture moved continuously, because screen capture emits no frames while the picture is still; they are judged only with `--moving` or `--sync` (the test material page, as `pnpm matrix` uses) and otherwise reported as n/a with the measured value still shown.

| Tier | Metric | Current project threshold |
| --- | --- | --- |
| Integrity | Output dimensions | Match capture report; satisfy cap and source aspect when known |
| Integrity | Duration | Requested matrix duration, else the log session length (`state → recording` to `state → stopping`), ±2 s |
| Integrity | Audio/video duration difference | Absolute difference <100 ms |
| Integrity | Audio minus video start offset (container) | Strictly between −45 and +125 ms |
| Integrity | Audio format | 48 kHz, two channels (stream metadata) |
| Integrity | Channel energy | Both channels measured by ffmpeg astats, each RMS above −60 dBFS. A silent, missing or invalid channel fails, as does an astats run that exited nonzero or reported fewer channels than the stream |
| Integrity | Video bitrate | At least 70% of the requested target; more is a larger file, not a failure |
| Integrity | Audio bitrate | At least 50% of the requested target; AAC follows content. With `--test-material` (implied by `--sync`, set by `pnpm acceptance`) it is reported, not judged: the page's sparse beeps encode far below any request, and dense-audio bitrate belongs to the [audio-quality diagnostics](audio-quality.md) |
| Integrity | Decode | No ffprobe full-frame decode errors; interactive playback remains a separate check |
| Performance | Average fps | Requested ±2 fps. The median frame interval and the nominal period are printed beside it (reporting only), so a cadence that is slow on every frame is told apart from drops |
| Performance | Dropped frames | <2% |
| Performance | Audio minus video offset (flash/beep) | Strictly between −45 and +125 ms, from at least 3 matched flash/beep pairs. It fails when a flash or beep more than 1 s from either end of the file has no partner (the page's own start, up to two flashes before its first beep, excepted): the remaining pairs would still give a median, but a beep lost near the detector threshold read 101 ms against 65 ms |
| Performance | End-to-end drift | Absolute drift <100 ms. A recording of at least 120 s (requested or measured) needs at least 3 matched pairs in each of its first and last 60 s; a shorter one has no drift to judge |
| Performance | CPU | Average of the app's process tree over the recording from its third second: ≤30% at 30 fps, ≤40% at 60 fps; 95th percentile, peak and VTEncoderXPCService reported; more than 25% above this machine's baseline is a warning (matrix only; [CPU budget](#cpu-budget)) |

Bitrate is a floor rather than a target because Chromium's encoder overshoots the request at 60 fps by 1.5–2× while still producing the intended quality; only a starved stream indicates a problem. These are the project's current constants in THRESHOLDS, not a guarantee for arbitrary content. A beep-heavy source has low AAC bitrate, and dual-mono passes the two-channel energy check without proving stereo separation.

Each check is pass, fail, blocked, incomplete or n/a (plan 030), and the caller states which evidence it requires: the matrix requires channel energy and the markers, `pnpm verify` energy and with `--sync` the markers, `pnpm acceptance` energy, and the update acceptance both. Required evidence that a missing tool prevents is **blocked**. Required markers that were measured but are too few, or a long file without both edge windows, are **incomplete**, with the reason: no flashes (the material was not on the recorded display), no beeps (silent or masked system audio) or too few pairs. The coverage rule uses the existing constants, `MIN_SYNC_PAIRS` (3) and the 60-second edge window; neither one pair nor a sync request alone is evidence. A tool that exited nonzero or printed incomplete output makes its check **fail**; its partial output is never used. Evidence a report did not require stays **n/a** with its reason and never passes. The format check is measured independently, so 48 kHz stereo can pass while energy is blocked. The aggregate is fail if any check failed, else blocked, else incomplete, else pass if any check passed, else n/a; processes exit 1 for fail or incomplete, 2 for blocked and 0 otherwise. The JSON measurement records each piece of evidence as `measured` with its value, or `not-requested`, `unavailable` or `error` with a reason. Channel RMS uses numbers for finite dBFS values and the strings `"-Infinity"` (digital silence), `"Infinity"` or `"NaN"` (invalid measurements) for non-finite values, preserving their meaning across JSON round trips. Legacy `null` levels are invalid, never evidence of audible audio. Reports written before this change carry the older combined audio check and three verdicts; they remain historical.

English is the default for new diagnostic output and measurement reports. Historical raw results retain the language and labels they had when recorded; the English verification summary explains their meaning. Do not rewrite measured values or old failures to resemble a new passing run.

## Audio fidelity regression

Read [Audio Quality: What We Measure and Why](audio-quality.md) for fixture v2, mathematics, threshold rationale, regression cases, and limitations.

```bash
pnpm audio:quality -- record /tmp/audio-run-001
pnpm audio:quality -- record /tmp/audio-repeat-001 --repeat 3
pnpm audio:quality -- fixture /tmp/audio-reference-v2.wav
pnpm audio:quality -- verify /absolute/path/recording-of-v2.mp4
```

`record` builds and drives the actual development app for 16 seconds, playing 12.1 seconds of diagnostic tones with macOS `afplay` once capture starts. Quit this project's development app first. Screen/system-audio grants and FFmpeg/ffprobe are required. Keep output device/volume fixed and pause other audio; the tool does not change settings. It records the primary screen and plays audible sound. `--repeat` accepts 1–10 runs; default 1. This requires a desktop session, not headless CI.

Use a new directory with an existing parent. Each run retains `reference.wav`, `capture.log`, and `report.json`; multiple runs use `run-1`, `run-2`, etc. MP4 files remain in the app's configured output directory, referenced by reports. The root contains `summary.json` and before/after environment snapshots with versions, source/fixture hashes, device inventory, and volume when available. Repeated summaries include min/median/max and missing counts, never hide a failed run, and become invalid if endpoint device/volume snapshots changed. A partial summary remains `incomplete` until the batch and its environment checks finish; errors also produce `error.json`.

`fixture` writes a new WAV without overwriting a file. `verify` prints JSON; direct Node invocation avoids pnpm's banner when redirecting stdout. Only v2 diagnostic recordings are valid inputs, not arbitrary music/speech or v1 recordings. Decode is limited to the first 60 seconds; format is checked without resampling or upmixing. Owned capture children time out after 60 seconds; external decode/tool operations also have bounded timeouts.

Exit status is 0 for pass, 1 for measured failure, 2 for invalid measurement or execution/input error. Marker/PCM ambiguity suppresses unsupported frequency measurements. New gates include frequency fitting, a simultaneous pilot, terminal marker, per-component overlapping dropout windows, and local clipping/gap checks. All thresholds and guard regions are explained in the design chapter; none are calibrated product-wide guarantees.

`pnpm test` runs clean/degraded PCM and repeat-summary tests. With FFmpeg/ffprobe installed it also tests real AAC, low-pass, mono/44.1 kHz, and CLI contracts. The integration case is explicitly skipped without those tools. These controls validate the detector; real `record` runs validate the local app/OS path. Keep historical [evidence](../verification/README.md) unchanged when fixture or analyzer versions change.

Release v0.1.0 completed browser-download/install verification on the available Mac; Gatekeeper required per-app Open Anyway approval. See [release evidence](../verification/releases/0.1.0.md). Self-signing does not remove that first-launch barrier. Developer ID signing and Apple notarization are the separate distribution route if the scope is reconsidered.

After installing dependencies in a clean environment, run `node node_modules/electron/install.js` to install Electron 44 runtime (the package has no postinstall). CI includes this step; see [release automation](releases.md).

## Keyboard-layout shortcut check

```bash
pnpm acceptance:shortcut-layout
```

Plan 043 registers global shortcuts by physical key by disabling Chromium's `LayoutAwareGlobalHotkeys` ([recording shortcut](desktop.md#recording-shortcut)). An Electron upgrade that renames or drops the feature would silently bring back layout lookup, and a digit shortcut would move to the keypad under Zhuyin. This check catches that without any manual input-source switching. Run it with RecordStuff closed, on macOS. The terminal needs System Events Accessibility access, and at least one keyboard input source whose number row types no digits, such as Zhuyin, must already be enabled. Like `acceptance:shortcut`, the script builds first; the runner invoked directly stops as blocked when `out/` is missing. It records nothing, needs no capture permission and takes about 10 seconds, build included.

- **Other RecordStuff processes.** The runner refuses as blocked while one runs: the packaged app, or an Electron development or fixture process started with this checkout. It would own the same shortcuts.
- **Choosing a source.** It reads the current input source and keyboard layout, then tries enabled, selectable keyboard sources, the current one first. It stops at the first whose layout types no digit on the number row while keypad 7 still types 7: that is the layout under which a layout-aware digit shortcut moves to the keypad. `-- --source <id>` tries only that source; a source that is not enabled is blocked before anything changes. The runner never adds or enables sources and never changes keyboard settings.
- **Activating an input method.** An input method applies its own layout only when a text field activates it. Selected from a background process, it keeps typing with the previous layout, and the check would pass with the bug present. For an input method, the runner therefore opens a small window of its own with a focused text field, waits up to 8 seconds for the layout to report the change, and closes the window. This briefly takes focus. A layout that does not change in time is blocked.
- **The app under test.** An Electron fixture loads the built `out/main/index.js` behind the [shortcut-failure](../../scripts/fixtures/shortcut-failure.ts) boundary pattern: isolated userData and logs, and a saved recording shortcut of `CommandOrControl+Control+Alt+Shift+7`. Registration reaches the real `globalShortcut`, but a press is recorded instead of calling the production toggle, so nothing records and no permission prompt appears.
- **Keys.** System Events sends three key codes. The Settings shortcut ⌘⌥, (key code 43) is a delivery control and must fire. Number-row 7 (key code 26) must fire. Keypad 7 (key code 89) must not fire within 1.5 seconds. A combination that nothing registered goes to the frontmost app.
- **Restore.** The original input source is restored and confirmed on success, failure, timeout, SIGINT and SIGTERM; an unconfirmed restore is a cleanup failure. Selecting a source is the same as choosing it from the input menu, so macOS's list of recently used sources can change. An input method keeps the layout it applied until its next use; that state belongs to the method and is not restored.

`-- --drill-layout-aware` is a negative control outside the default run. The fixture removes production's `disable-features` value before app ready, so Chromium's layout-aware lookup is on as it was before plan 043. The number-row key must then fail and the keypad fires; the run exits 1 and still restores the input source. The report states whether the drill detected the lookup.

Reports go to `docs/verification/measurements/<timestamp>-shortcut-layout/`, with a `-drill` suffix for the drill. `report.md` and `report.json` list the original, tried, in-use and restored sources with their layouts and number-row characters, the accelerator and registrations, each key result and the cleanup. `electron.log` and `check/app.log` keep the process output.

Exit codes:

- 0: pass.
- 1: fail, including an interrupted run and any cleanup failure.
- 2: blocked. Causes: not macOS, missing `out/`, another RecordStuff process, a locked screen, no System Events access, no qualifying enabled source, a refused registration, or an input source that changed during the check.

Synthetic key codes do not prove physical keys; 043's maintainer-reported press remains the hardware evidence.

## Acceptance cleanup

Complete app acceptance rounds save test recordings, restore settings, close test UI, quit the tested app and confirm exit, on success, failure and cancellation. Cleanup failure fails acceptance. Preserve evidence and do not reset permissions. During development, stopping recordings and quitting/restarting/rebuilding RecordStuff as needed is authorized without additional confirmation. Quitting resets process state, not stored preferences.

Desktop runners (`acceptance`, `acceptance:settings`, `acceptance:shortcut` and the regression that runs them, `acceptance:shortcut-layout`, `acceptance:settings-shortcut`, `acceptance:quit-dialog`, `acceptance:notification`, `acceptance:updates` with capture, `acceptance:playback`, `matrix`, `measure:cpu` and `audio:quality -- record`) share [desktop-session.mts](../../scripts/lib/desktop-session.mts): `caffeinate -u` wakes an idle-slept display, `ioreg`'s `CGSSessionScreenIsLocked` refuses a locked session before anything is launched or keyed, `caffeinate -d -i -w <runner pid>` keeps the display awake until the runner exits, and a lock seen during the round (polled every 2 seconds and at the end) turns the result into BLOCKED with exit code 2 and a `Desktop:` line in the report. Isolated lifecycle fixtures do not need the display and do not hold it.

Settings acceptance also treats a window another app deactivated as blocked (plan 057). The page draws no focus line while its window is inactive, and on macOS `BrowserWindow.focus()` does not take activation back from another app, so before each case that needs an active window (the focus-line and focus-border matrix, shortcut capture, which a blur cancels, focus that the page returns only to a focused document after a result action or a failed link's Retry, and the screenshots taken with them) the fixture reads `BrowserWindow.isFocused()`, `isVisible()` and the page's `data-window`, asks for activation the way `SettingsWindow` does (`app.focus({ steal: true })`, then `window.focus()`) when the window is not active, and reads them again when the case is judged. Each interaction starts its own check, so a blur in one does not decide the next; a case whose window was not active at either point, or blurred in between, is `NOT RUN` in the console, `report.md` and `results.json`, with the reason and the frontmost app from `lsappinfo`; a case that ran on an active window keeps its pass or fail. When `capturePage()` throws, the fixture still writes the cases recorded so far and adds `failure.json` naming the screenshot and the window's state at that moment. The round then exits 2 (blocked) when only not-run cases or a capture on an inactive or hidden window stopped it after the fixture had shown its window; any judged failure, another stop, or a fixture exit or process cleanup that disagrees with the results exits 1. The classification lives in [settings-activation.mts](../../scripts/lib/settings-activation.mts) and its unit tests.

Runners share process matching and the launch environment (plan 052). [processes.mts](../../scripts/lib/processes.mts) builds every `pgrep`/`pkill` pattern: `recordStuffPattern` for a RecordStuff bundle and `electronPattern` for a checkout's development Electron.app escape the path and anchor it, so a checkout under `~/Code (2026)/` matches itself and no sibling or argument that mentions it, and `pgrepPids` throws on a spawn error or any status but 0 and 1 (1 is "none"). A process-group probe treats only `ESRCH` as gone; `EPERM` means the group still exists, and a failed signal is reported as a cleanup error. A `pgrep` failure therefore blocks the round instead of reading as "nothing is running": in preflight the runner stops before it launches anything, and in cleanup the round exits 1 (`CLEANUP FAILED` after an interrupt), because nothing then proves its processes exited. Every runner that launches Electron or the app starts from `scrubbedEnv()` in [runner-env.mts](../../scripts/lib/runner-env.mts), which removes `ELECTRON_RUN_AS_NODE`, `ELECTRON_RENDERER_URL`, `RECORDSTUFF_AUTORECORD` and `NODE_OPTIONS` (a VS Code JavaScript Debug Terminal sets the last), and adds only what it owns, such as the autorecord request, fault points or `PATH`; a unit test fails when a runner deletes one of these keys itself or copies `process.env`. `matrix`, `measure:finalization` and `diagnose:cadence` build asynchronously in the build's own process group, so a Ctrl-C or SIGTERM during the build reaches only the runner, whose handler stops the whole group and exits 130 or 143 after cleanup. `matrix`, `measure:finalization` and `diagnose:cadence`, like `acceptance`, `measure:cpu` and `acceptance:updates`, open the material in a private Chrome profile created for the round with `mkdtemp`; cleanup waits for that browser to exit, then removes the profile, and reports a profile it could not remove as incomplete cleanup.

`pnpm acceptance` leaves the accepted app closed and reports the final cleanup verdict in `report.md`; it refuses to quit a replaced process or an app not confirmed idle. Notification acceptance restores the bundle and settings but keeps the app closed. Settings acceptance supervises its own process group and writes `cleanup.json`, including timeout and interruption outcomes. Isolated runners clean only their own processes. Unit checks do not close unrelated apps. The settings-shortcut entry step leaves its panel open for native inspection; the complete Computer Use round owns final shutdown. Start the app before the next recording round; use `pnpm start:app` to rebuild changed code.

The shortcut runner writes `input-diagnostics.json` before sending start and on failure: exact AppleScript, app PID, sender process, System Events UI status, frontmost app and any Secure Input owner reported by IORegistry. No reported owner is not proof that Secure Input was off. Diagnostic queries are read-only, bounded, and do not grant permissions. `events.log` and the current run’s `app-session.log` survive failed runs as well. An osascript success is not delivery proof: only the registered app callback counts. Do not blindly resend a toggle shortcut after timeout; it could stop a recording whose callback arrived late. When delivery fails, compare a physical press and the generated script against the same bundle and input context before attributing the failure to the app.

### Verification recipes and timing

```bash
pnpm acceptance:recipe -- --list
pnpm acceptance:recipe -- shortcut-registration
```

A recipe is the leaf commands of the composite checks one kind of change needs ([testing policy](../testing.md#select-once-validate-once)), run in order with one build of identical inputs. `check` is `pnpm check`; `settings` is `pnpm acceptance:regression`; `shortcut-registration` adds the keyboard-layout runner without the second `pnpm build` that `pnpm acceptance:shortcut-layout` starts with; `recording` runs typecheck, tests, `pnpm start:app`, whose `electron-vite build` is check's build, and `pnpm acceptance`. `pnpm acceptance` can follow `start:app` directly because it waits up to 30 seconds for the log's latest session to be the running pid's own, by its run id, and idle; before plan 061 it could judge the previous app's session. Playback stays a separate `pnpm acceptance:playback -- <file>` on the saved recording. `-- --dry-run` prints a recipe's commands without running them. A unit test keeps each recipe's runners equal to the package scripts it replaces.

Each phase runs in its own process group with the console attached and stops the recipe when it does not pass, as `&&` does; later phases are reported as not run. Exit code 2 from a desktop runner is blocked; from typecheck, tests or a build it is a failure. SIGINT or SIGTERM sends SIGTERM to the running phase and waits up to 60 seconds for its own cleanup before killing its group, so a runner still quits the app and restores what it changed; the recipe then exits 130 or 143, or 1 when that cleanup was incomplete. A phase that runs longer than an hour is stopped and fails, as does one whose group outlived it or needed SIGKILL to clean up, even after exit 0. `recording` owns the bundle `pnpm start:app` opens: when it ends before `pnpm acceptance` quit the app (a failure, a blocked runner or an interrupt), it asks the bundle to quit normally, which saves a recording in progress, and waits up to 30 seconds for every process of the bundle, helpers included, to exit; it never kills the app, and a process it cannot confirm gone fails the run. An app already running when the recipe started is not its to quit. Otherwise the recipe adds no desktop interaction of its own, so each runner keeps its handoff, lock and cleanup rules.

The report goes to `docs/verification/measurements/<timestamp>-recipe-<name>/` (`--out <new directory>` chooses another and refuses an existing one). `report.json` and `report.md` record the wall time, each phase's start offset and duration from the monotonic clock, its outcome, exit code and cleanup, and the time outside phases (identity hashing and the app cleanup; writing the report is not timed). A child that knows its own boundaries appends them to the file named by `RECORDSTUFF_TIMING_FILE`; `pnpm start:app` reports preflight (process check and signing identity), build, package, verify, and open or the DMG this way, and they appear inside their phase without being added to the totals again. The report also records the revision, a digest of the uncommitted changes including untracked files, the runtime-input digest, the `out/` and `app.asar` digests before and after, and Node, pnpm, Electron and OS versions. When sources, tests or configuration change during the run, an otherwise passing run is **invalid** and exits 1, because its evidence belongs to no single revision. Agent orchestration gaps and desktop-readiness waits happen outside the process and are reported as unknown, not as zero.

**Bundle reuse.** After a successful build and signature verification, `pnpm start:app` writes `dist/mac-arm64/RecordStuff.app.inputs.json` beside the bundle, outside its signature and the DMG. It holds a digest per runtime input — `src/` without `*.test.ts`, `build/`, `resources/` without Markdown, `package.json`, the lockfile, the electron-builder, electron-vite and app TypeScript configurations, and the installed Electron, electron-builder, electron-vite and Vite versions — and the digest of `app.asar`. Symlinks are followed, so the digest covers what they point to. A copied acceptance workspace whose sources import from `scripts/`, as `acceptance:updates` and `acceptance:controlled` instrument theirs, counts `scripts/` too. The inputs are read before the build; when they changed by the time verification finished, no record is written. A rebuild removes the old record first, so a failed rebuild leaves none. `pnpm open:app` refuses, before verifying the signature, a bundle with no record, an unreadable record, a changed `app.asar` or changed inputs, naming up to five changed files; rebuild with `pnpm start:app`. Editing only tests, scripts, documentation, plans or the website therefore keeps the verified bundle reusable, and any source or configuration change forces a rebuild.

### Guided deferred-quit notice

Run `pnpm acceptance:quit-dialog -- --language zh-TW`, then repeat with `--language en`. This launches a separate Electron test process, from a signed copy described below, with isolated userData and synthetic bytes; it never records, changes real preferences, fills storage or replaces the installed app. It shares the production `createQuitFeedback`, Recorder, FileWriter and quit coordinator; a plain Electron `Notification` stands in for the tray's, which the fixture does not create. A held publication and an accelerated 100 ms shutdown deadline defer the quit about three seconds after launch, and the deferred-quit notification appears (plan 055; the command keeps its name from the dialog it replaced). Observe the banner and its complete text; nothing needs an answer. The fixture logs `Notification.isSupported()` with the request, so a refused banner can be told from an unsupported system. For the next 8 seconds a 1 s timer measures how late main runs, and the round fails if any tick is 500 ms late or more; the fixture then checks that the publication is still held, releases it, verifies exact bytes and retries normal quit. The `.mp4` fixture output contains synthetic bytes and is not a playable recording.

The fixture runs only from a fully signed Electron.app (plan 062): macOS refuses notifications (`UNErrorDomain` error 1) from the linker/ad-hoc-signed Electron in `node_modules`, while an A/B/A comparison on 2026-10-01 delivered both languages once the same copy carried a complete RecordStuff Dev signature. Each round runs `node scripts/start-app.mjs --fixture-app <temporary>/Electron.app <report>/signature.json` under its own supervised process group with a 60-second bound: it copies this checkout's Electron.app with `ditto` into a unique temporary directory, signs the copy with `codesign --force --deep --timestamp=none`, using the identity `pnpm start:app` selects (RecordStuff Dev or `RECORDSTUFF_SIGN_IDENTITY`, with the same validity, self-signed and ambiguity checks), and verifies it with the same `verifyBundle`: `codesign --verify --deep --strict`, the selected certificate on the outer app and every nested app/framework, no ad-hoc signature, the identifier `com.github.Electron` and the designated requirement `identifier "com.github.Electron" and certificate leaf = H"<sha1>"`. The copy keeps Electron's identifier, whose notification permission the comparison used, and has no hardened runtime or entitlements. A missing, ambiguous, expired or inaccessible identity, a keychain that needs a person (`errSecInternalComponent` and similar) or a timeout while the keychain is consulted is **blocked** (exit 2); any other signing or verification failure, or an interruption, **fails** (exit 1). Neither launches the fixture. `node_modules`, `dist/`, installed apps, preferences, certificates and trust are never changed. The setup runs with `TMPDIR` inside the same temporary directory, so a killed verification leaves no certificate scratch elsewhere. The copy is removed once its process groups have exited; it is retained, and cleanup fails, when that cannot be confirmed. Evidence torn by a killed process reads as missing, and a runner error still removes the copy under the same condition and writes a failing `report.json`.

The report keeps five layers apart: the signed fixture app (with provenance: commit, dirty state and `workingTreeIdentity` content, Electron version, lockfile and fixture hashes, bundle path and identifier, certificate name, SHA-1 and expiry, designated requirement and setup phase times), the lifecycle (one deferral and one notice, timers, exact bytes, normal exit), the notification's delivery event, the visual banner and cleanup. The fixture appends `requested`, `shown` and `failed` events to `notification.jsonl` as they happen, so delivery is judged even when the lifecycle later fails. Only a `shown` event within 8 seconds of the request passes delivery; an explicit authorization denial (`UNErrorDomain` error 1, “not allowed”) is blocked, any other error or no event in the window fails, and a failure outranks a show. The runner never judges the visual layer: it stays **not run** with the reason that an observer must record it. A failure in any layer makes the round fail (exit 1) and outranks blocked results, including a lock; otherwise a blocked layer, a layer that could not run or a lock makes it blocked (exit 2). Exit 0 is automated evidence for the signed app, lifecycle, delivery event and cleanup; complete native acceptance also needs the visual observation.

`--help` does not launch anything; malformed options fail before launch. Ctrl+C cancels only the isolated process groups, during signing as well as after launch; repeated cancellation signals do not bypass supervisor cleanup. This runner requests immediate SIGKILL of its own disposable synthetic process group on cancellation/timeout; other runners retain the default graceful SIGTERM path. A 40-second supervisor deadline bounds unattended runs; interruption/timeout and forced cleanup are failures, never passes. The explicit synthetic-only SIGKILL path avoids that misleading prompt and is always recorded as forced cleanup and failure; it never applies to the normal RecordStuff app. Logs (`setup.log`, `electron.log`), `signature.json`, `notification.jsonl` and `report.json`/`report.md` are retained under `docs/verification/measurements/<timestamp>-quit-dialog-<language>/`. ## Controlled acceptance build

Plan 035's native acceptance needed failure states that real faults cannot produce on demand: a pending result that normally lasts milliseconds, an unknown outcome after a close failure, slow or failing history storage, and seeded history. `pnpm acceptance:controlled` builds a clearly labeled signed copy of the app for them. Like the update fixture, it copies the source into a new run directory under `docs/verification/measurements/<timestamp>-controlled/`, instruments only that copy behind anchor checks ([controlled-acceptance.mts](../../scripts/lib/controlled-acceptance.mts)) and runs the copy's `pnpm start:app`. The bundle identifier and signing identity, and with them the screen-recording grant and notification permission, stay those of the development app. Tray, Settings, Recorder, FileWriter, failure history, notifications and the quit flow are the production code, and normal builds have no command channel. The copy differs in three ways:

- **Isolated data.** userData, logs and the default output folder live in the run directory. The maintainer's settings, failure history and `~/Movies/RecordStuff` are never read or written. The build starts with default preferences (English, notifications on, 3-second countdown with its tick, ⌘⇧1).
- **Label.** Every tray tooltip starts with `[Controlled acceptance build]`, and a `controlled:` log line names the run directory. Evidence from this build is controlled-state evidence: it shows native presentation and interaction, not a real disk or capture fault.
- **Fault points** ([controlled-faults.ts](../../scripts/fixtures/controlled-faults.ts)), all off until armed:
  - `cleanup=hold` holds each failure's settled result before it reaches the history, so the pending result (processing, Got it disabled, no reveal) stays on screen, quit is deferred and a session's interruption sentinel, when it has one, stays until `release cleanup`. The file work behind it has already finished.
  - `write=eio|enospc` fails the next write to a recording file that already holds data, once, through the production FileWriter: output_write_failed or disk_full, with the partial kept.
  - `close=fail` fails the next close of a recording file, once, after the descriptor really closed. The writer cannot confirm preservation, so the result is unknown; armed before a normal stop, the stop itself fails that way.
  - `history-save=hold|fail` holds saves until `release history-save`, or rejects them as an I/O error that every automatic retry meets again until the fault is off.
  - `--hold-history-load` on `launch` or `reopen` holds that launch's history load until `release history-load`; the command channel answers from launch on.
  - `throw` raises one synthetic uncaught exception from a timer on the next tick, outside any promise, so it reaches the production uncaught-exception handler as a real programming fault would (plan 056). Sent during a recording, it shows whether writes, the stall guard and the stop continue and when the error box appears; the `events.jsonl` line records the state and `mediaPending` when it was scheduled. It is not a fault mode: nothing stays armed.

```bash
pnpm acceptance:controlled -- launch [--seed none|v1|retention] [--hold-history-load]   # new run: build, sign, open
pnpm acceptance:controlled -- fault cleanup=hold write=enospc     # also close=fail, history-save=hold|fail, <name>=off
pnpm acceptance:controlled -- release cleanup                     # or history-save, history-load
pnpm acceptance:controlled -- status                              # state, faults, holds and each failure-history row
pnpm acceptance:controlled -- throw                               # one synthetic uncaught exception on the next tick
pnpm acceptance:controlled -- quit                                # production quit: saves a recording, may ask about reminders
pnpm acceptance:controlled -- reopen [--hold-history-load]        # the same bundle and data
pnpm acceptance:controlled -- clean                               # after exit: remove the workspace, keep the evidence
pnpm acceptance:controlled -- selftest
```

`quit` leaves armed faults and holds in place, so it can exercise a deferred or questioned exit; turn faults off and release holds first for a plain exit. An interrupted or failed `launch` or `reopen` waits up to 15 seconds for a bundle that `open` already started: a ready app quits normally, and one that never reported ready is named for the user to quit. Commands other than `launch` and `selftest` act on the newest guided run unless `--dir <run>` names one. `--seed v1` writes one unread legacy `recording-result.json` whose synthetic partial exists, for migration. `--seed retention` writes twenty reviewed records between two unread ones, so acknowledging the old unread record exercises the limit of 20 most recently reviewed records. Seeded files hold synthetic bytes, never a playable recording. `launch` and `reopen` refuse while any RecordStuff runs, because an isolated userData does not share the single-instance lock. Exit 0 means success, 1 failure, and 2 blocked or a usage error. Arm and release events are appended to `events.jsonl` and the run's app log.

The maintainer performs every native action; the runner only builds, seeds, arms, releases, reports and quits. `selftest` is the one exception and proves the tool, not the product. In a separate run with notifications and the recording shortcut off, it makes the isolated output folder unwritable and holds the cleanup of the resulting start failure while rejecting its save. It checks the pending and unsaved rows, releases, retries, holds an acknowledgement's save, quits, relaunches with a held history load and quits again, calling the recorder's toggle and the production action handler directly. It records nothing, so the write and close faults rest on their unit tests with the real FileWriter and Recorder. A failed or interrupted self-test turns every fault off and releases every hold before quitting. Its `report.md` lists each step, and the workspace is removed once the app has exited.

### Audit tool bounds and evidence

Media subprocesses default to a 900,000 ms timeout with SIGKILL; RECORDSTUFF_MEDIA_TIMEOUT_MS accepts a positive integer override. A successful version probe must exit zero. Measurement Markdown and JSON are atomically replaced using a .md.pending journal; the next append replays an interrupted pair before adding new evidence. This is crash recovery for a serialized writer, not simultaneous-reader or multi-writer transactions.

Stable release tags share the updater's numeric grammar and reject leading zeros. Asset HEAD checks follow redirects and require a successful final response. Website links resolve relative to each source page, including queries and escaped fragments. Reveal styling is activated only after the observer is installed, so a missing JavaScript bundle leaves content visible.
