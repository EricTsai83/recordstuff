## Developer workflow

Use pnpm and a compatible Node version; the verification TypeScript scripts use Node 24 directly. Package.json declares Node ≥22.18 for the project, the first Node 22 that runs the TypeScript runners (`pnpm test:scope`, the acceptance rounds) without a flag. FFmpeg/ffprobe are development tools, not recipient dependencies.

Main, preload, and renderer are separate electron-vite entries. Only out files, package metadata, and selected resources enter the app. Tests, measurement tools, and documentation are not runtime dependencies. The app has no FFmpeg subprocess.

## Assets and generated output

- `build/` contains committed packaging assets: `icon.png`, the native macOS `icon.icns`, the Windows `icon.ico` (16–256 px entries for the executable, installer and shortcut), and the DMG background `background.png` with its `background@2x.png` Retina pair (540×380 points). The builder uses this directory as `buildResources`, explicitly selects the ICNS for macOS, and merges the background pair into a multi-resolution TIFF with `tiffutil`. Keep these files; regenerate artwork with `pnpm icons`. All artwork is generated from code, so the repository has no hand-drawn binaries.
- `resources/` contains runtime tray icons, macOS entitlements, and the bilingual installation/update/removal guide (`INSTALL.md`, `INSTALL.zh-TW.md`). The guide is documentation linked from GitHub releases and the README; the packaging filter copies only PNG/ICO files, so it is not shipped inside the App or the DMG.
- `out/` is generated by `pnpm build`; `dist/` is the single output directory for `pnpm start:app` (App bundle under `dist/mac-arm64/`), `pnpm dist:mac` (the same bundle plus the DMG) and `pnpm dist:win` (`RecordStuff-<version>-x64-unsigned-setup.exe`). Both are ignored by Git and can be regenerated. Keep any installer you still need before clearing `dist/`; `pnpm open:app` requires an existing bundle built from the current runtime inputs. Locally built DMGs are for checking packaging; released DMGs and Windows installers are always built by CI from the tag.
- `node_modules/` holds installed development dependencies and can be restored with `pnpm install`.

All sources in `scripts/fixtures/` use TypeScript and participate in `pnpm typecheck`. Standalone entries are compiled on demand by [build-fixture.mts](../../scripts/lib/runner/build-fixture.mts), using Vite's TypeScript transform: settings-native, player-panel, recording-lifecycle, history-quit, quit-dialog and release-record-network emit ESM (`.mjs`), while shortcut-failure emits CommonJS (`.cjs`) because it intercepts CommonJS loading before requiring the production app. Generated entries are kept in each acceptance report directory or disposable test directory; they are not maintained source files or shipped app code. The update-acceptance fixture continues to build with the disposable app source copy. Existing acceptance commands need no separate fixture build step. Compilation removes types; `pnpm typecheck` checks them. Renderer scripts passed as strings to `executeJavaScript` are still runtime code, not TypeScript-checked DOM code.

Quality options and error codes are each defined once as constant lists; their TypeScript types are derived from those lists, and the tray reuses the quality lists. Typechecking also rejects unused locals and parameters. Older settings are backed up and reset to current defaults at startup; only the current format is supported.

`pnpm signing:create` preserves existing matching Keychain certificates or creates an encrypted identity archive with explicit output/password inputs; see [identity setup](signing.md). It does not import keys or configure trust.

## Current signing and packaging

See [macOS signing identities and self-signing](signing.md) for identity design, certificate creation/backup, troubleshooting, and planned CI provisioning.

[Start-app](../../scripts/start-app.mjs) resolves exactly one valid signing identity, default `RecordStuff Dev`. RECORDSTUFF_SIGN_IDENTITY may specify an exact name or SHA-1. It rejects missing/ambiguous identities, duplicate certificate names, invalid dates, non-self-signed certificates, or a mismatched final signature. SHA-1 identifies the public signing certificate here; release-file integrity uses SHA-256.

The script checks for a running RecordStuff/project Electron process before rebuilding. It removes Apple/CSC release variables from child environments, disables identity auto-discovery, forces signing, sets notarization false, and passes publish never. It does not reset permissions, import keys, notarize, or publish.

Verification performs strict deep codesign checks, inspects nested app/framework certificates and the native capture engine's (plan 076) without following symlinks, checks identifiers/runtime flags, and matches the outer designated requirement. Only after this succeeds does it package the existing verified app into a DMG.

The [base configuration](../../electron-builder.yml) defines the installer UI: a 540×380 Finder window with the generated arrow background, 128-point icons, and exactly two entries, the App at x=130 and the `/Applications` link at x=410, both centered at y=190. The [local configuration](../../electron-builder.local.yml) extends it and disables notarization/timestamps and DMG signing/update metadata. It must not add `dmg.contents`: `extends` concatenates arrays, and the release gate rejects any root entry other than `Applications`, `RecordStuff.app` and the hidden Finder layout files. Help is intentionally not bundled in any format; installation, update and removal guidance is online. Output is `RecordStuff-<version>-<arch>-selfsigned.dmg`; arm64 and x64 are architecture-specific, not universal. Only arm64 has been verified.

`pnpm dist:mac` produces the same DMG that CI builds and publishes on a tag push (it replaced the former `dist:mac:local` alias and the separate `dist/dev`/`dist/local` folders). The base configuration disables notarization.

Self-signing is not Apple approval. Recipients may need Open Anyway for an unnotarized app; managed Macs may restrict that option. Use the ordinary per-app workflow in the [installation guide](../../resources/INSTALL.md), not global security changes. The same guide documents manual update (quit, download, replace at the same Applications path; identity and settings retained) and removal (quit, move the App to Trash; recordings, `~/Library/Application Support/recordstuff` and `~/Library/Logs/recordstuff` remain unless the user deletes them). There is no macOS uninstaller, background service or automatic permission reset. See [Apple](https://support.apple.com/102445).

### Windows packaging and CI

By the maintainer's decision of 2026-10-03 ([design decisions](decisions.md)), the base configuration also has `win` and `nsis` sections: an x64 NSIS target with `build/icon.ico`, the artifact name `RecordStuff-<version>-<arch>-unsigned-setup.exe`, a per-user one-click installer (`oneClick: true`, `perMachine: false`, no admin prompt) whose Start-menu shortcut carries the appId `com.ericts.record` as AppUserModelID for Windows toasts, `deleteAppDataOnUninstall: false`, so the uninstaller in Settings → Apps keeps recordings, settings and logs, and `differentialPackage: false`, since without an updater no blockmap is needed. `files` and `extraResources` stay shared, so the Windows install carries the same `app.asar` inputs and the tray ICOs. `pnpm dist:win` is a plain electron-builder call without the macOS signing path; `start-app.mjs` still refuses any host but macOS arm64/x64 and points to it. No maintainer machine runs Windows, so these were built and checked only on GitHub's runners and never on Windows hardware.

[check.yml](../../.github/workflows/check.yml) runs every check on every push to main and every pull request that changes more than documentation or the website, on `macos-15` and `windows-2025`, the runner images the release builds use, split across runners so the slowest part sets the time (2026-10-09; about 17 minutes in two jobs before, about 5 after): `check` runs `pnpm check` and then `pnpm test:ui:drills` on that build, per platform; `ui` runs the background suite in four groups by kind of test per platform (`layout`, `states`, `settings` and `app` in [ui-groups.mts](../../scripts/lib/runner/ui-groups.mts), each `pnpm test:ui` on its specs, one worker each, as on a developer machine; a job's name says which kind of test failed, every background spec is in exactly one group, which a unit test enforces, and four keep macOS within the five runners a free account runs at once; the groups take about 2.5–3.5 minutes each); and `windows-installer` runs `pnpm dist:win`, then `node scripts/release.mts windows-smoke dist`, the same silent install, inspection and uninstall gates as the release ([release contract](releases.md#release-contract)), and uploads the installer as the `windows-installer` artifact for 7 days; it is a build artifact, not a release. `workflow_dispatch` runs every job on any branch, so a work branch can be checked on Windows before it reaches main. [.gitattributes](../../.gitattributes) sets `* text=auto eol=lf`, so a Windows checkout keeps the LF endings that byte comparisons of READMEs and fixtures expect; tests whose expectations differ by platform (path separators, `chmod` fixtures, POSIX-only tools) are platform-aware rather than skipped on both. Every build there except the background suite's makes plan 076's native capture engine with the runner's Rust (`RECORDSTUFF_SKIP_NATIVE=1` skips it in the `ui` shards, which never record), and the `check`, `windows-installer` and `native-windows` jobs keep Cargo's output with `Swatinem/rust-cache`; the release builds use no cache. The installer smoke also loads the installed engine.

## Verification tools

```bash
pnpm probe -- /absolute/path/recording.mp4
pnpm verify -- /absolute/path/recording.mp4 --screen 1920x1080 --sync --out
pnpm verify -- /absolute/path/any-desktop-recording.mp4 --screen 1920x1080   # integrity only
pnpm acceptance -- --seconds 10        # unattended shortcut acceptance of the running app
pnpm acceptance -- --skip-cancel --countdown-sound   # the same with the countdown tick on for the round (plan 046)
pnpm acceptance:playback -- /absolute/path/recording.mp4   # the playback case in QuickTime Player; about 20 s
pnpm test:ui                                       # the background suite: no window, focus, key or sound reaches the desktop
pnpm acceptance:recipe -- native-ui                # the native Settings, shortcut and player cases; a desktop round
pnpm acceptance:notification -- --install --clicks 2  # short notification smoke check
pnpm acceptance:notification -- --install          # saved-notification click → Settings on Recordings in front; ~1 min; built app swapped into /Applications for the run
pnpm acceptance:notification -- --install --full   # all three Finder states, English; ~3 min (estimate)
pnpm matrix -- quick
pnpm matrix -- all
pnpm matrix -- long
pnpm matrix -- fps,long                                  # several matrices in one round: one build, one material launch
pnpm matrix -- fps,quick --repeat 2                      # repeats interleave; the summary groups them per case
pnpm measure:finalization -- --dir /Volumes/test/rs --seconds 15 --repeat 10   # stop-to-ready and its phases into an isolated folder
pnpm bench:publication -- --dir /Volumes/test/rs --sizes 64m,2g                 # publication cost by file size; no recording
pnpm measure:cpu                                         # CPU budget on the quit bundle: idle, one 30 fps recording, idle after it, Settings open; ~15 min
pnpm measure:cpu -- --fps 60 --repeat 3                  # the baseline round: both frame rates three times each; ~25 min
pnpm measure:cpu -- --camera preview=0 --skip-settings --skip-playback --studio --fps 60 --minutes 2   # the camera: R, S (Studio showing the recording) and L (Live preview); plan 075
pnpm measure:cpu -- --skip-settings --skip-playback --fps 60 --minutes 1 --diagnostics   # each recording's pipeline figures (plan 083); a run without --diagnostics beside it gives their cost
pnpm diagnose:pipeline -- --last 3                       # the last sessions' pipeline figures from the app's log (plan 083)
pnpm measure:cpu -- --skip-settings --skip-playback --studio --studio-rate standard --studio-stall 15,30 --diagnostics --minutes 1   # the Studio's page stalled 30 s, 15 s into each port (plan 084; --studio-memory instead: the no-stall control); its CPU is no baseline
pnpm measure:cpu -- --skip-settings --skip-playback --fps 60 --minutes 1 --repeat 3 --profile --audio off   # one cause isolated: no sound (or --capture-interval frame); plan 091
pnpm diagnose:profile -- docs/verification/measurements/<run>   # the capture process's profiled CPU by cause, thread and library (plan 091)
pnpm measure:thumbnails                                  # Recordings thumbnails over hundreds of real videos in the hidden view host: limits and cache compared; needs out/; ~2 min
```

Verify accepts multiple files, an optional log path, source dimensions, `--moving` (the content moved continuously), sync detection (implies `--moving`), Markdown/JSON output, and an explicit JSON destination. It requires channel energy, and with `--sync` the flash/beep markers too; it exits 1 when a check failed, required evidence is incomplete or a file cannot be read, 2 when a required tool is missing (blocked) and 0 otherwise ([verdicts](#measurement-pipeline-and-thresholds)). The default evidence directory is docs/verification/measurements; it is gitignored, so raw runs stay local and only interpreted conclusions go into the verification record. It reads every retained file (the active log and `.1`–`.3`, oldest first) and pairs a recording with its session by identity (plan 029): the run and session ids of the [session records](desktop.md#logs), looked up by the file's full path, falling back to its name only when a single session in the log names a file of that name (a copied file). One record logged twice is one outcome; different outcomes for one session are a conflict. A failure that kept no file claims no path, because a same-second retry may reuse its temporary name. Launches from builds before session records use a conservative legacy association: an outcome is accepted only when nothing else could own it (a `file finalized` line, the one session still recording, or the one unresolved failure whose text matches), so two unresolved failures are never assigned by which printed first. Otherwise the report says the metadata is ambiguous, conflicting or unknown, and no check against the requested settings is judged; media measurements stay independent of the metadata. `pnpm acceptance` and `pnpm matrix` fail a case whose metadata is not matched to its own session. A replay of the 244 retained logs available on 2026-09-25 gave the same association as the old order-based reading for all 628 files it had paired; no retained log contained the reversed-cleanup interleaving that reading got wrong.

### Test material

`scripts/test-material.html` is the one fixed page every measurement records: scrolling small text (sharpness), thin red/blue lines and coloured text (chroma edges), a square moving every frame (frame timing), a top-right box that flashes white for 100 ms once a second, and a soft 660 Hz tone (120 ms, about −26 dBFS, alternating left/right) on the same audio clock. Flash and tone are the sync markers: `verify --sync` finds them with ffmpeg blackdetect on the box and silencedetect (−35 dB, 0.4 s) on the audio, so the page must otherwise stay silent and nothing else may play on the machine. Because the audio is sparse, the AAC bitrate of these recordings is reported, not judged (`--test-material`). Opened by hand, the page starts on a click (browser autoplay policy); `pnpm matrix` and `pnpm acceptance` open it in a fresh-profile Chrome app-mode fullscreen window on the primary display with autoplay allowed and `?auto=1`, so no click is needed. Acceptance reports record the page's SHA-256 so results can be tied to a material version. Version history: until 2026-09-19 the tone was a 1 kHz, 60 ms beep at 0.5; on 2026-09-20 it became the softer 660 Hz tone above, and the first run with it detected 20 flashes and 19 beeps in 20 s with a 79 ms flash/beep offset, inside the historical 45–80 ms latency, so earlier sync results stay comparable. On 2026-09-29 the gain dropped from 0.3 (about −10 dBFS) to 0.15 (SHA-256 `4064e63e…`; 10 flashes with 10 beeps in 10 s at a 65 ms offset, channel RMS −33.2 against −27.3 dBFS), and on 2026-09-30 to 0.05, about −26 dBFS and 9 dB above silencedetect's threshold, to stay quiet beside whoever runs a round. Capture takes the page's digital level, before the system output volume, so the volume setting does not narrow that margin. Its first acceptance run matched 10 flashes with 10 beeps in 10 s at a 61 ms offset with channel RMS −42.8 dBFS. The same file with only its audio attenuated offline still matched all 10 pairs down to −6 dB (63 and 65 ms), lost two beeps and read 101 ms at −9 dB while `verify` still passed, and failed at −12 dB: this level keeps 6 dB of clean margin and is the quietest one that does, so do not lower it further. The tone now crosses the detector threshold about 3.6 ms into its attack (0.6 ms at 0.3), which adds a few milliseconds to the flash/beep offset, far below a frame: offsets and drift stay comparable, while audio levels (channel RMS) of earlier versions are higher and are no baseline for this one. Current SHA-256: `e98bf1fc63d2e7f0662a6d3dca62f21bdf3afa9debff6b4e64455b46a20a70bb`.

Matrix is macOS-only developer automation. It launches the test material in a Chrome app-mode fullscreen window on the primary display unless --no-open-material is supplied, samples the app's process tree with the [shared CPU sampler](#cpu-budget), and drives an unpackaged app through RECORDSTUFF_AUTORECORD. Keep source display/audio stable during the run. Packaged builds ignore this variable. Autorecord quits immediately after saving, so on macOS that quit cancels the pending saved notification; a banner is not part of autorecord completion. The internal automatic-recording parser accepts durations in (0,3600], validated quality overrides merged over defaults, not user settings, an optional `countdown` (0, 3, 5 or 10) and an optional absolute `outputDir` that replaces the stored folder in memory for that run. Autorecord counts down 0 seconds unless its configuration names a countdown, so the matrix and audio-quality runs keep their timing; the stored countdown is never used there. Every case requires channel energy and the sync markers (plan 030): the matrix checks for ffmpeg, ffprobe and the Command Line Tools' clang before it builds or records anything and exits 2 (blocked) without them. A case passes only when none of its checks failed, was blocked or is incomplete; such cases are listed with each unmet check and its reason at the end of the run and in the measurements file, and the run exits 1.

One invocation is one desktop round (plan 042): it builds `out/` once, opens the material once and runs the named matrices in order. Names are comma-separated (several arguments are joined), and a name listed twice runs twice, so `fps,fps,long` records fps twice and long once. `--repeat N` (1–10) repeats the whole list, so a case's repeats interleave with the other cases rather than always running first or warmest; `--dry-run` prints the order. An unknown or empty name, an unknown option or a `--repeat` outside 1–10 prints the usage and exits 2. Cases run back to back: the next one launches as soon as the previous file is verified, and that verification is the rest between recordings. Each case prints and appends a timing line (launch to recording, recording, stop to saved, quit, and each verification tool), and the measurements file gets a Timing table with the round's preflight, build, material and wall time. A case that runs more than once is titled "run k of n", and a Repeats table lists every run's verdict with the minimum, median and maximum of the average frame rate, median interval, drops, CPU average and 95th percentile, encoder CPU, flash/beep offset, drift and video bitrate; the case passes only when every run passed. A case the round never reached, because it stopped when ffmpeg or ffprobe went missing, counts as a blocked run. Exit codes are unchanged, except that a round whose cleanup left a process running exits 1. SIGINT or SIGTERM stops the build's whole process group, sends SIGTERM to the running case's app, whose normal quit stops and saves a recording in progress (within 5 seconds of a launch it first waits for the app to appear; anything still running after 30 seconds is killed), waits for the material's launch to finish and closes the material browser, ends the desktop round, confirms the processes exited and exits 130 or 143 without writing measurements; it names the interrupted case's saved file, which was not verified. Only processes of this checkout's Electron.app and the material's private profile are stopped, never an installed RecordStuff. A SIGTERM that arrives while ffprobe or ffmpeg is running takes effect when that tool finishes (seconds), before the next case starts or any measurement is written; Ctrl-C also stops the tool itself.

Verification dominates a case's overhead, and within it the two ffprobe passes (the full-decode frame count and the frame timestamps) take most of the time: on the M1 Pro reference machine 4.6 of 5.4 seconds for a 30-second 30 fps file, 12.4 of 13.9 at 60 fps and 22.9 of 27.0 for long. The three ffmpeg passes (astats, blackdetect, silencedetect) take under a second, or 4 seconds for long, so they remain separate runs.

### Per-frame log

`pnpm diagnose:cadence` (plan 041) was removed with the hidden capture renderer on 2026-10-16, since it measured only that renderer's capture host. The native engine's counterpart (plan 078, a development switch at the maintainer's choice) is a per-frame log: with `RECORDSTUFF_FRAME_LOG=<folder>` in the app's environment, each recording writes `<file name>.frames.jsonl` there, one line for every frame capture delivered while recording (`picture`, `idle`, `blank`) and every frame the core encoded on its own (`first`, `skipped`, `due`, `refresh`, `stop`), with its time after the start, whether the pacer kept it and the pacer's next slot ([frame_log.rs](../../native/capture/src/core/frame_log.rs)). The prepared warnings name the file. `pnpm diagnose:frames -- <file>… [--fps 30]` reads it and prints the kept frames' gap histogram and, for every gap of one and a half intervals or more and every one of half an interval or less, the deliveries around it and the pacer's decisions. Nothing ships that sets the switch, and the runners pass it through, so `RECORDSTUFF_FRAME_LOG=/tmp/frames pnpm matrix -- quick` logs a matrix round. It found the skipped refreshes behind the last 50 ms gaps ([frame pacing](recording.md#frame-pacing)). It answers where a gap comes from; `pnpm matrix` stays the measure of how many there are.

### Camera age

The engine logs at each stop of a recording that composed the camera how old the camera's picture was in the frames it was composed into (plan 075 step 8, [camera.rs](../../native/capture/src/core/camera.rs) `CameraAges`): `camera: the camera's picture 113.9 ms older than its frame on average (87.7 to 138.7 ms) in 1005 frame(s)`, each composed frame's host time less the capture time of the camera frame in it, negative when the camera's frame is newer. It stands in for a flash shown to the camera and found in the file. That line is the 2026-10-18 round's, with an iPhone's Continuity Camera, whose wireless link is in the figure. On Windows camera frames are stamped when they arrive, so the figure there leaves out the time the camera and Media Foundation hold a picture.

### Pipeline figures

Plan 083 measures where a session's time goes, stage by stage, with a development switch as the per-frame log is: with `RECORDSTUFF_DIAGNOSTICS=1` in the app's environment each capture session keeps bounded figures ([diagnostics.rs](../../native/capture/src/core/diagnostics.rs)), and without it no stage is timed. A stage is a fixed array of 128 counters (a quarter of an octave of microseconds each, so a percentile read from them is within about 12.5%) with its count, sum and maximum, whatever the recording's length; nothing per frame is written anywhere, and every figure is taken on one clock inside one process.

| Figure | What it times | Notes |
| --- | --- | --- |
| `capture_callback` | The core taking a captured picture: the video lock, the pacer and, when the picture is kept, its submission | ScreenCaptureKit stamps a frame about 10 ms ahead of the host clock (the stop's `frames stamped … ahead` line), so the delivery's own latency cannot be read on that clock |
| `encode_submit` | Handing a frame to the encoder | On macOS it includes composing the camera, when one is composed |
| `compose` | Composing the camera into a recording's frame on the GPU, waited for | macOS |
| `encode_latency` | A frame's submission to its encoded sample | Paired by the frame's time, at most 64 waiting: `in_flight_high` the most waiting, `unmatched_samples` samples whose submission was not remembered, `encoder_dropped` frames VideoToolbox answered without a sample |
| `write_wait`, `write` | Media handed to the writer until it is taken; muxing and writing it | `writer_pending_high` and `writer_backlog_high_bytes` are the queue's high-water marks; its 64 MiB bound fails the recording |
| `preview_compose`, `preview_encode` | The preview's picture (macOS); its submission to its chunk | `preview_chunks` made; `preview_gate_sent` and `preview_gate_dropped`, the chunks napi's gate of two in flight passed or dropped before the JavaScript thread |

The capture host reads them (`NativeCapture.diagnostics()`, cumulative from the session's start) every 5 s while the session runs and once more when it ends, and logs each as a `capture host: diagnostics: {"kind":"engine",…}` line with the session, `running` or how it ended (`finished`, `writeError`, `cancelled`, `failed`), and its own counts: the preview chunks forwarded to the Studio and their bytes, those given while no page held a port, and, from plan 084, those its bounded delivery held back (`previewHeld`), the key frames it asked of the engine (`previewKeyRequests`) and the most chunks and bytes outstanding at once (`previewOutstandingHigh`, `previewOutstandingBytesHigh`; see the [recording design](recording.md#camera)). While the Studio shows the preview, the host asks the page on the Studio's port, and the page reports every 5 s and once more as it lets the port go (`{"kind":"page",…}`; [preview-diagnostics.ts](../../src/renderer/lib/preview-diagnostics.ts)): chunks received, drawn, never received (a gap in their numbers) and received but not decoded; the most chunks waiting to be drawn and in the decoder's own queue at once (`pendingHigh`, `decodingHigh`, plan 084) and the most of its JavaScript heap in use when a chunk came (`heapHigh`, bytes; under the switch main starts Chromium with `--enable-precise-memory-info`, without which the figure comes in coarse, cached steps); decoder restarts for a codec or after an error; the port's delay, from the capture process's `Date.now()` at the send to the page's at the receipt, two processes on one wall clock in whole milliseconds, which a clock step would disturb; and decoding with drawing into the canvas, which is not yet the screen showing it; and a stalled page's catching up (`recover`, plan 084), from the first chunk it received more than a second after it was sent to the first frame it drew within a second of its sending. No picture, device name or typed text is kept.

A second development switch, `RECORDSTUFF_STUDIO_STALL=<at>,<for>` in seconds ([studio-stall.ts](../../src/shared/studio-stall.ts), plan 084), makes a page that draws nothing reproducible: once the Studio's page has held a port for `at` seconds, the capture host asks it on the port to hold its main thread for `for` (at most 120), as a stalled renderer or a long garbage collection would, reading the clock only every 100,000 turns so the hold itself allocates next to nothing (a first version read it every turn and its own garbage grew the renderer by about 30 MB, plan 084's record); main, the capture process and the recorded apps go on, and without the switch nothing is ever asked. `pnpm measure:cpu -- --studio --studio-stall <at>,<for>` launches the bundle with it and notes, for each S recording, the capture process's and each renderer's memory just before the stall and the most it reached after; `--studio-memory` notes the same at 15 s without a stall, as its control. The page's busy thread costs a core while it lasts, so such a run's CPU figures are no baseline.

A session's last line is its whole: main ends a Live preview by ending the capture process, which then logs no outcome, so its figures are those of its last 5-second snapshot. `pnpm diagnose:pipeline -- [<log>…] [--session <id>]… [--last N] [--json <file>]` reads the app's log, by default its archive and current file, and prints each session's stages (count, mean, p50, p95, maximum) and counts; [pipeline-report.mts](../../scripts/lib/verification/pipeline-report.mts) merges histograms by adding their buckets, so runs combine without their samples, and writes the report as `recordstuff.pipeline-diagnostics/1`, refusing figures of another schema. `pnpm measure:cpu -- --diagnostics` launches the bundle with the switch and adds the figures per recording and per scenario to its report, failing a recording or Live preview whose engine line never came, and refuses to run without `--diagnostics` while launchd holds the switch; `RECORDSTUFF_DIAGNOSTICS=1 pnpm matrix -- quick` passes it to the development app. The switch's cost and the baseline it gave are under [Pipeline baseline](#pipeline-baseline).

Before, every chunk made during the stall was posted and queued (the page's `pending` and the decoder's queue reached the counts above, the port's delay 30 s), and the page drew all of them after the stall. After, the host held what was beyond the limit (147–447 a stall), asked once for a key frame and the page drew a current picture within two preview ticks plus decoding (the gate: 408 / 208 / 141 ms at 5 / 10 / 15 a second); the page never had more than 3 chunks pending. The renderer columns differ in their stall: the before rows and a first after round held the page with a loop that read the clock every turn and whose own garbage added about 30 MB (after with it: +48 to +52 MB; the same loop with the preview Off: +0); the after rows above use the loop that reads it every 100,000 turns. The capture process grew 7–10 MB in a stall before and after. A recording made through a stall passed `pnpm verify --sync` (0 frames dropped, A/V −19 ms).

### Finalization measurement

`pnpm measure:finalization` (plan 037) measures how long a stop keeps the next recording waiting, and where that time goes; it judges nothing and ships with nothing. One invocation is one desktop round: it builds once, opens the test material (Chrome kiosk, unless `--no-open-material`) and records `--repeat` takes (default 5) of `--seconds` (default 15) through the development app with `RECORDSTUFF_AUTORECORD`, `--quality` (default standard) and `--fps` (default 60) at source resolution, into `--dir`, an absolute folder given as autorecord's `outputDir`, so settings.json is never written. Quit RecordStuff and the development app first. Stop-to-ready is the app log's `state → stopping` to `state → idle`, the moment a toggle starts a new recording again; stop-to-saved is `state → stopping` to `file finalized`; both are paired with their stop whichever of idle and the save comes first, since saves run in the background (2026-10-09) and idle usually comes before the save; the phases come from the recorder's `finalize timing` line (the host's stop, the drain after it, the engine's finalize to plain MP4, close, publication with its method, cleanup, and the interruption sentinel's completion checkpoint; its flush field is kept for the line's shape and reads 0, since the engine syncs its own file) plus the UI settle from `file finalized` to idle when idle came after the save. The checkpoint (`checkpoint N ms`, plan 053) reads the session's sentinel and rewrites it atomically with fsync in userData, so a slow userData volume shows there; a session whose latest sentinel write failed skips it and logs `checkpoint ? ms`, and lines logged before the field existed still parse, without it. Each take's file needs a video and an audio stream, no decode errors and, unless the take stopped early for low disk, a duration within 2 seconds of the requested one. `--verify quick` (default) fully decodes the first saved take with ffprobe and, for the rest, reads streams and duration and decodes only the first and last second; `--verify full` decodes every take. The window decode uses ffprobe because `ffmpeg -f null` reports the repeated timestamps of static screen content as errors although every frame decodes. The file is then deleted unless `--keep`, so a round never accumulates recordings on the volume. `--label` names the report folder and `--no-build` reuses the current `out/`. Point `--dir` at an isolated folder or disk image for slow, small or foreign file systems; never fill the system disk. Evidence goes to `docs/verification/measurements/<timestamp>-finalization-<label>/` (`summary.md` with nearest-rank distributions per phase, `summary.json`). It exits 0 when every take saved and verified, 1 when one did not, outlived its bound (the report says whether the app then quit on SIGTERM or had to be killed) or cleanup left a process behind, 2 when ffprobe is missing, the app is already running or the desktop locked, and 130 or 143 after SIGINT or SIGTERM, which wait up to 5 seconds for a launch still in flight, quit the round's app normally and close the material without a summary.

### Publication benchmark

`pnpm bench:publication` (after plan 037) answers how a save's publication grows with file size on one volume, without recording, a desktop, screen permission or `out/`. It bundles [the benchmark](../../scripts/fixtures/publication-bench.ts) with the production EngineFileWriter and runs it under Electron's own Node (`ELECTRON_RUN_AS_NODE`), so publication uses the app's libuv. For each `--sizes` entry (default `64m,2g`) and `--repeat` round (default 3) it reserves the file with EngineFileWriter, writes it in 4 MiB chunks into `--dir` and syncs it as the native engine writes its file, then calls `finish`, which links where the volume allows and copies otherwise, and reports publication, close and cleanup times and the whole `finish`, the method with the link's error code, and the write rate; the file is deleted unless `--keep`. Since the file is synced before `finish`, as the engine's is, `finish` holds publication and its bookkeeping only; the engine's own finalize and the wait for it are a recording's, measured by `pnpm measure:finalization`. It refuses to start unless the volume has twice the largest size plus 1 GiB free, because a copy briefly holds two copies; with `--keep` every kept file counts too. Evidence goes to `docs/verification/measurements/<timestamp>-publication-<label>/` (`summary.md`, `summary.json`). It exits 0 when every file published, 1 when one failed, 2 on bad arguments or too little space, and 130 or 143 after SIGINT or SIGTERM, which stop the benchmark and remove its own files.

### Export benchmark

`pnpm bench:export -- --dir <absolute folder>` ([runner](../../scripts/bench-export.mts), [fixture](../../scripts/fixtures/export-bench.ts); plan 085) measures the export's gates without recording. It makes synthetic sources in the engine's own file layout with the engine's encoders (`cargo test … bench_sources`, so Rust and VideoToolbox are needed): `64m` and `2g` of 1080p30 at about 12 Mbps and `2h60`, two hours at 60 fps, the most samples. The gates: the key-frame remux at least half the copy's rate, cancel within 1 s at p95; the worker's peak against 64 MiB is reported both absolute and over the worker at rest. Evidence goes to `docs/verification/measurements/<timestamp>-export-<label>/`.

`pnpm bench:editable [-- --pair direct|mix] [--seconds 60] [--repeat 3] [--label name] [--app-r 12.2]` ([runner](../../scripts/bench-editable.mts), [judging](../../scripts/lib/verification/editable-bench.mts), [recordings](../../native/capture/src/mac/editable_bench.rs); plan 087, step 1) measures what the editable recording prototype costs over today's recording without a desktop: no screen, camera or microphone is opened and nothing on the screen is recorded, so the machine can be used meanwhile (a heavy load still moves the figures). The modes alternate, `--repeat` recordings each (odd), and the shared CPU sampler follows each recording's process and VTEncoderXPCService from the recording's fifth second to five before its end. A recording whose file is fragmented, whose camera was told lost, whose tracks are not the mode's, whose video tracks hold fewer than 95% of 30 pictures a second or whose tracks' lengths differ by more than 0.1 s is unusable and fails the run. The estimate is not the app's measurement: only a recording of the packaged app confirms it, which 087's closure requires. A run under heavy load is no evidence: the first, at a load average of 25–29, read +4.11 points, and rounds on a quiet machine still move by about two points, so judge the median of five.

### CPU budget

`pnpm measure:cpu` (plan 049) keeps RecordStuff's CPU small while it waits in the menu bar and normal while it records, on the packaged app; `pnpm matrix` judges recording CPU with the same sampler. CPU is a percentage of one core, as Activity Monitor shows it (the reference M1 Pro has ten cores, so the whole machine is 1000%). Wake-ups are idle plus interrupt wake-ups per second, Activity Monitor's Idle Wake Ups. What may run while idle is listed in the [design overview](design-overview.md#waiting-in-the-menu-bar).

**Sampler.** [cpu-sampler.c](../../scripts/lib/verification/cpu-sampler.c), after Cap's per-process sampler, is compiled with `clang` from the Command Line Tools into the run's folder; without them the measurement is blocked (exit 2), never skipped. Once a second, on a fixed schedule, it lists every process, keeps the app's main process and all its descendants, resolved again at every sample, plus every process named VTEncoderXPCService, and prints each one's `proc_pid_rusage` counters: CPU time in nanoseconds, idle and interrupt wake-ups, energy and resident memory. `ps` is not used: it reports CPU time in hundredths of a second, too coarse for an idle second in which 0.2% is 2 ms, and its `%cpu` is a decaying average that flattens peaks and carries start-up into later samples. [cpu-sampler.mts](../../scripts/lib/verification/cpu-sampler.mts) turns the counters into per-second figures and reports the average, the 95th percentile (nearest rank) and the maximum, per process and in total. A window counts only the one-second intervals lying wholly inside it, so CPU spent before its start never leaks in, and an interval in which the app's set of processes changed is discarded and listed, except where a start or end is expected. A window whose judged intervals cover less than 80% of it, or a sampler that exited before it was stopped, fails: missing samples never pass as zero CPU. VTEncoderXPCService, the system's hardware encoder, is reported apart and never counted as the app; it is a shared system service (four idle instances on the reference Mac), so its CPU is judged, not its presence. Energy is macOS's own per-process estimate, so it is reported, not judged.

**Scenarios.** Build the bundle with `pnpm start:app` and quit it, then run `pnpm measure:cpu`. It refuses to start while any RecordStuff or this checkout's development Electron.app runs. With the app quit it writes the countdown Off, the recorded display to the primary one (where the material opens) and the quality Standard, Source, 30 fps into settings.json, launches `dist/mac-arm64/RecordStuff.app` and waits for `ready;`, the granted permission, `recording history: loaded` and the launch update check's outcome or its `updates: launch check skipped` line, so startup work is over before anything is judged:

- **A. Idle after launch,** Settings closed: `--minutes` (default 5) after a 60-second warm-up.
- **R. Recording:** a 60-second recording started and stopped with the recording shortcut over the moving test material (Chrome kiosk on the primary display), judged over seconds 5 to 55 with VTEncoderXPCService followed. `--repeat N` (odd, 1–9, so the median is one run's own figure) records N times and judges the median run. `--fps 60` then quits the app, writes 60 fps and relaunches for a second set.
- **B. Idle after the recording:** from 30 seconds after the last save, `--minutes`, with the idle thresholds.
- **C. Settings open behind another app:** opened with its shortcut, confirmed by the app's `settings shortcut: … pressed` line, a running Settings renderer and its window in the Accessibility tree (a launch without recordings still has its pre-warmed renderer; on macOS the full-screen page waiting loaded beside Settings is a second renderer), Finder brought to the front, the pointer moved onto the menu bar so no card's hover preview plays (where the steps before left it decided C before, 2026-10-15), measured for 3 minutes after 10 seconds of settling, then closed. The pointer's place, the window's frame and a screenshot with the pointer are kept at both ends. `--hover-card` rests the pointer on the first card instead: a preview played there behind Finder (33.6% on 2026-10-15) until Settings stopped previewing while it lacks the focus, and the option checks that it stays stopped.
- **P. Playback** (plan 072): the last 30 fps recording of R, reached as a person does: from Finder, the tray menu's Show last recording, whose `show last recording:` line must name that file, focuses its card's Play button, read by its element id through Chromium's accessibility tree, which is turned off again before the window, and Return plays it in the Settings player. Judged over 50 seconds after 5 seconds of settling, per role from the process tree: the app in total, its GPU process and its renderers. A GPU process or renderer under 0.5% means nothing played and fails. The file must have been saved as a plain MP4 (its `finalize timing` line). The hardware decoder, VTDecoderXPCService, is not followed: it adds about 2% outside the app. Escape closes the player and ⌘W the window, each only while Settings is focused in front. Without a recording in this launch P is skipped.

**Process roles.** Every idle scenario also checks the app's processes by Chromium role, read from their command lines (`--type` and `--utility-sub-type`), because the three helpers share one name. The idle contract, `IDLE_ROLES` in cpu-sampler.mts, is the native engine's (plan 076): the main, GPU and network-service processes once each, and besides them only what the [design overview](design-overview.md#waiting-in-the-menu-bar) explains. No renderer runs after launch (A), since nothing uses the default session before a window opens, and none after a recording (B): capture starts neither Chromium's audio service nor a lasting process, since the capture `utilityProcess` (`utility:node`) ends once its file is finished, so a countdown overlay left behind fails, and any other role fails too. While Settings is open (C) its renderer must exist, so a Settings window that never opened fails instead of measuring closed idle; a second renderer, the full-screen page waiting hidden, Chromium's audio service and, with the microphone on, Settings' microphone monitor (`utility:node`, plan 079) are allowed. Five seconds after every save the roles are snapshotted, and every snapshot of a launch, and B's roles, must equal the first: what a recording starts once is expected, what it adds each time is a leak, the way a leak detector such as [fuite](https://github.com/nolanlawson/fuite) counts growth per repetition instead of comparing with a cold start. The report also gives the app's memory at each snapshot, reported, not judged.

`--skip-recording` leaves out R, B and P, `--skip-settings` leaves out C, `--skip-playback` leaves out P, `--hover-card` measures C with the pointer on a card, `--camera` and `--studio` add the camera and the Recording Studio (below), `--profile` samples the app's processes (below), `--diagnostics` adds the [pipeline figures](#pipeline-figures), `--material still` records static text (`scripts/still-material.html`, a still screen whose capture delivers few pictures) instead of the moving material, and `--out` names the report folder. Without `--camera` the round seeds the Camera switch off, so no recording or Studio of it opens a camera. The report, `report.md` and `report.json` under `docs/verification/measurements/<time>-cpu/` (gitignored), gives each scenario's checks against the budget, its judged and discarded intervals, CPU, wake-ups, energy and memory in total and per process, the saved files, and the machine, macOS, Electron, displays, power source and bundle time. Afterwards the runner quits the app normally (after an interruption it first waits up to 10 seconds for an app whose launch it had already requested), confirms it exited, closes the material browser and confirms that it exited too, and, once no RecordStuff process remains, sets `countdown`, `display` and `quality` back to their values before the run, keeping anything else the app saved meanwhile; the original file is kept beside the report as `settings-before.json`. The recordings stay in the output folder. Like the other desktop runners it declares user activity and holds a display and idle-sleep assertion for its lifetime. It exits 0 when every judged check passed, 1 when one failed, the run failed or cleanup was incomplete, 2 when blocked (no Command Line Tools, no Accessibility access, a locked screen), and 130 or 143 after SIGINT or SIGTERM, which settle a recording in progress (the shortcut is sent only while that recording is counting down or recording and no stop was sent yet, so it never starts a new one), close the material, quit the app and restore the settings, then write a partial report marked INTERRUPTED.

**Budget.** Initial targets from plan 049, confirmed by the [2026-09-28 baseline](../verification/history-2026-09.md#plan-049-cpu-baseline--2026-09-28) on the reference M1 Pro through the former Chromium path and met with more margin by the native engine (plan 076 step 7, 2026-10-16: 10.4% at 30 fps and 14.0% at 60 fps); `CPU_BUDGET` in cpu-sampler.mts holds them.

| State | Threshold | Why |
| --- | --- | --- |
| Idle, Settings closed (A, and B after a recording) | Average ≤0.2%, 95th percentile of one-second samples ≤1%, ≤5 wake-ups per second in total | There is nothing to do: the only periodic work is the 5-second permission poll. Apple's [energy guide](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/Timers.html) asks apps to respond to events instead of polling |

Each limit sits between the fix and the regression it guards |
| Against the baseline | A recording more than 25% above this machine's baseline for the same case is a warning, even under its threshold | A regression can hide under a generous ceiling; CPU drifts between rounds, so it is not a failure |

**Playback costs** (plan 072). Two things made the in-app player expensive. A fragmented MP4 has no index, so Chromium's demuxer reads every `moof` through a range request of the `recordstuff-media:` protocol and the renderer then holds thousands of disjoint buffered ranges; its cost grows faster than the file's length, while the same file read from `file://` stays cheap. Recordings are saved as plain MP4 (by the hidden renderer's `FragmentIndex` until it was removed on 2026-10-16, by the native engine's muxer since); files already saved fragmented by earlier versions keep the cost and are not repaired. And a `backdrop-filter` is redrawn with every video frame even when nothing behind it changes, so the player's backdrop only darkens and the page under it is blurred with `filter` instead (`#root` in ui.css), which Chromium draws once. Both decode video in VideoToolbox.

Baselines live in [cpu-baselines.json](../../scripts/lib/verification/cpu-baselines.json), keyed by `sysctl hw.model`: each recording figure is the median average of three repetitions, entered by hand from a baseline round together with its verification history entry. Since plan 076 removed the hidden renderer (2026-10-16) the file keeps only the native engine's `measure:cpu recording 30` and `60` figures; the matrix has no baseline yet. A machine or case without an entry is judged only against the thresholds. Another machine, or an Electron upgrade, takes a new baseline before its results are compared. A baseline that fails a target is a finding to investigate, not a reason to loosen the target without written evidence and the maintainer's agreement.

**Matrix.** Each `pnpm matrix` case follows the development Electron.app's main process and its descendants with the same sampler, starting within a second of launch, and judges them over the case's recording from its third second to the stop request (a case without those log lines falls back to the third second after launch until exit, where the capture process's start and end are expected). A case whose sampler never found the app, exited early or covered less than 80% of that window fails as CPU evidence incomplete. Its CPU check reports the average, 95th percentile, peak and VTEncoderXPCService, fails above the frame rate's threshold, and notes a baseline regression when this machine has a matrix baseline (also printed on the console) and a missing encoder. The 17%, 21% and 23% figures recorded before plan 049 came from `ps`'s decaying average over whole cases and are not comparable.

`--profile` (plan 081) also writes 10 s of macOS `sample` of main, the GPU process, every renderer and the capture process beside the report (`profile-NN-<scenario>-<role>-<pid>.txt`), from 25 s into each recording and 20 s into each Live preview, to attribute a process's share by thread: the H.264 decoder's `Media` thread, a renderer's main and compositor threads, the GPU process's `VizCompositorThread` and `CVDisplayLink`. Electron's framework is stripped, so its symbols are only the nearest exported ones; the thread split is what holds. The sampling perturbs the window it falls in (about 0.3 points in plan 081's runs), which the figures then include.

`pnpm diagnose:profile -- <run>… [--role utility-node] [--json <file>]` (plan 091) reads those files and, per window (`R30`, `R60`, `S30`, …), merges one role's graphs, by default the capture process's, and shares its on-CPU samples by cause (AAC encoding, picture and sound delivery, the video encoder's submission, the system's media queues, Node and Chromium's threads, …), by thread or dispatch queue and by the library of the innermost frame ([sample-profile.mts](../../scripts/lib/verification/sample-profile.mts)); each share is scaled to milliseconds a second by that process's average CPU in the same recording. `sample` records every thread's stack whether it runs or waits, so a sample whose innermost frame is a kernel wait is counted off the CPU; that estimate overweights short, frequent callbacks: in plan 091 it gave AAC encoding about 29 ms a second, where turning the sound off saved 17 and a benchmark of the encoder measured 2.4–5.3. Read its shares as where to look, and measure a cause by switching it off. The estimate needs the system's wait frames to be named, which held in the capture process; in main and Chromium's other processes, whose Electron frames are stripped, waits inside them are counted as running (main's profiles gave hundreds of times its measured CPU), so use their thread split only. A share is scaled only by the one recording its process lived in, so main, the GPU process and a Live preview's profiles are left unscaled. Two such switches, development only and passed with `open --env`: `--audio off` records without sound (`RECORDSTUFF_CAPTURE_AUDIO=off`; the file keeps a silent AAC track, still encoded) and `--capture-interval frame` asks ScreenCaptureKit for the frame interval instead of a quarter of it (`RECORDSTUFF_CAPTURE_INTERVAL=frame`, [pacing.rs](../../native/capture/src/pacing.rs), macOS); `scrubbedEnv` removes both and the runner refuses to start while launchd holds either. A report made under them says so and is not a baseline.

**Camera and the Recording Studio** (plan 075). `--camera <value>` launches the bundle with `RECORDSTUFF_CAMERA_PROTOTYPE=<value>` (step 2's development switch; `1`, or `width=…,height=…,rounding=…,x=…,y=…,mirror=…,device=…,preview=0`) and seeds the Camera switch on in settings.json, with `cameraDevice` when the value names `device=<id>`, so every recording composes the camera at the stored layout; `camera` and `cameraDevice` are restored with the other seeded keys. It needs `--skip-settings --skip-playback` and leaves B out, since the prototype's preview page, open unless the value has `preview=0`, is a renderer the idle contract does not allow. `--studio` (with `--camera`, not with `--skip-recording`) adds two scenarios at each rate, before R and over the same moving material:

- **S. Recording with the Recording Studio showing it:** the Studio opened from the tray's Open Recording Studio… before the material's full screen hides the menu bar, then the same recordings with the Studio showing the engine's preview and the meters. Judged against R's median at the same rate (D18: at most 8 points more, reported rather than judged when the Studio window is not on another display than the material, which the report names) and against the camera's recording budget plus 8 (28% at 30 fps, 33% at 60).
- **L. ### Selecting acceptance coverage

Choose required checks and exclusions using the [shared testing policy](../testing.md). Use the [shared acceptance cases and report](../acceptance.md) for native/recording work. This guide owns command mechanics and thresholds, not a separate test-selection policy.

The update fixture is instrumented and matrix uses autorecord; neither replaces acceptance of the normal built app. Notification acceptance retains its installed-app path and distinct Finder-state coverage. An unchanged file and verification scope can reuse media evidence; different artifacts or UI actions cannot. Shared material arguments and bounded log waits live in `scripts/lib/acceptance/acceptance.mts` and `scripts/lib/acceptance/acceptance-runtime.mts`; each runner retains its own app lifecycle and verdicts. Log positions are rotation-aware cursors from `scripts/lib/runner/log-reader.mts` (plan 029), shared by waiting and cleanup: a cursor is a file's identity (device, inode, birth time) plus a byte offset, so reading since it follows that file into whichever archive now holds it and then reads every newer file, each line once. It tolerates the moment between a rotation's rename and the next append, holds back an unterminated last line, and reports an explicit evidence gap when retention deleted or truncation erased the cursor's history, instead of waiting out the timeout. The cursor also keeps the 64 bytes before its offset, which an append-only log never changes, so a file truncated and regrown past the offset between two reads is a gap too, not a silent skip. The `start:` line of a second launch refused by the single-instance lock is not a process start, so it neither hides the running app's state nor splits its log. The hotkey runner requires the app's run id, binds its waits to the session named by this run's capture record, and takes the file from that session's terminal record. Runners that start a real recording never absorb the countdown into a latency threshold (plan 040): `pnpm acceptance` uses the real settings and reports each phase from the app log (press → `prepared`, each `state → countdown (n)` from the first, the overlay's dismissal, `record` after the anchor, `record → started`, `started → first engine progress`); the notification runner seeds `countdown: 0` with the language and restores the user's value; the update fixture sets 0 in its isolated userData; autorecord uses 0. A cancelled countdown settles an interrupted recording on its `cancelled:` line, and a cleanup that finds a countdown presses the key once to cancel it.

With a countdown, `pnpm acceptance` converts the logged overlay placement (window and display bounds, in points) into frame pixels and saves crops of that region from the first 15 frames and from the 15 frames two seconds later, selected by timestamp, to `digit-crops/`. Over the test material the region lies inside the black marker, which flashes white once per second, so each early crop is compared with the later one of the same flash phase: frames bright in either (the flash, where a white digit cannot show) are skipped, and the round fails when a judged frame's mean luma difference exceeds 3 levels or no frame could be judged. Without the material the crops are saved but not judged. The cancel case then presses the shortcut, waits for `state → countdown`, presses again, and requires a `toggle` cancel, no remaining temporary or final file, no failure, notification, `record` or recording line, and idle; `--skip-cancel` omits it and a countdown of Off makes it not applicable. The report says whether the session's countdown ticked, from the `prepared` line's `sound on`/`sound off` (plan 046). When it ticked, the runner mixes the first 500 ms of the recording's audio and the 500 ms from 2 s on to mono and measures the loudest 50 ms Hann-windowed frame (25 ms hop) at the tick's pitches, 523 and 784.5 Hz, with Goertzel. The material's 660 Hz tone leaks about −58 dBFS into those bins in both windows alike, while a tick measures about −28 dBFS at full scale, so the round fails when the first window is more than 6 dB above the later one and above −70 dBFS, or when a beep onset in the first 500 ms has no flash beside it. Capture can begin inside a material beep: the file then starts with silence and the beep at full level, and that abrupt onset reaches both tick pitches at about −41 dBFS, which the same beep 2 s later, with its 10 ms attack, does not. The runner therefore looks for that truncated onset: the first window's first sample at half its peak, with nothing above a tenth of the peak from 25 ms to 1 ms before it (room for an AAC frame's pre-echo) and nothing above −70 dBFS earlier. When it finds one, it silences both windows up to it and fades both in over 20 ms from it before measuring them: the repeated beep gets the same gentle onset in both, which keeps the later window near −67 dBFS at the tick's pitches, so a tick whose tail the file starts inside still stands out instead of hiding under the onset's energy. A sound that rises through its own attack, a file that starts with sound and a window with nothing above −70 dBFS are compared as recorded, so no sound that could reach the floor is discarded. The report gives the onset (plan 054). What this cannot see is the faint tail of a tick that began about 60 ms or more before capture, at −28 dBFS, when capture also began inside a beep. `--countdown-sound` turns the stored switch on for the round: already on (a missing field reads as on) changes nothing; off makes the runner check everything that can refuse the round first (the output folder, a locked desktop), then quit the idle app, set only that key and relaunch the same bundle. The key is set back only once no RecordStuff process remains, after the final quit or, when setup fails after the relaunch, after quitting the app it launched, because a running app would write the round's value back on its next save; if the app cannot be confirmed gone, the run fails and says the key was not restored ([stored-override.mts](../../scripts/lib/acceptance/stored-override.mts)). It refuses a stored countdown of Off. The notification runner and the update fixture seed a countdown of 0, autorecord never ticks, and the controlled build starts from defaults, so no other runner hears it. Before its stop key, `pnpm acceptance` looks for its session's `saved` or `failed` record since the capture record; a session that already ended is reported and fails the run without the key, which an idle app would take as a new start (plan 054). Hotkey and notification runners share interrupted-recording settlement, which waits for saving and never toggles stop twice after a successful stop command; runner evidence logs mark a lost history in place of its lines.

### Notification acceptance

The verdict requires a `clicked` event matching the observed banner body (falling back to this save's expected localized body when absent) and, since 2026-10-04, the app's `show last recording: Recordings with <path>` line for the full saved path, where it once required a reveal request. These are separate diagnostics: missing reveal evidence alone is no longer labeled an undelivered callback. Old builds without click logging cannot pass this stricter runner; historical reports retain their original conclusions.

Notification timing diagnostics include `tracksStoppedAt` (the capture process's wall-clock milliseconds when it reported its tracks stopped), main-process `host stopped` and `file finalized`, plus `saved scheduled`, `saved cancelled`, and `saved request failed`. The JS timestamp does not prove OS readiness. Correlate these with the existing request/show/click logs, AX observations and narrowly filtered macOS logs when available. No system-log access is required by the app. The saved request delay is 500 ms on macOS; the runner still searches for only 5 s after save. Historical Plan 017 completion criteria and results are retained in the [verification history](../verification/history-2026-09.md#saved-notification-timing--2026-09-20); they are not the default gate for every change.

Each case also writes `<language>-<finder>-<click>-diagnostics.json`: timestamped search attempts, bounded Accessibility traversal text/errors, and app notification lifecycle events. A non-passing case gets an additional observation-only snapshot (up to 5 s, so failed cases may take longer). The app logs show-requested/shown/clicked/closed/failed separately; a shown event alone is not proof that the script found a visible banner. These local files can contain notification text and are not committed.

`pnpm acceptance:notification` checks whether clicking the saved notification opens Settings on Recordings in front (2026-10-04; before that, whether it selected the file and brought Finder forward). Each case records for 2 s, searches for that save's banner for at most 5 s, samples the frontmost app for 3 s, then reads RecordStuff's front window and, once Chromium's accessibility tree is on (it is built asynchronously, so the focus is polled for up to 2.5 s), the focused element, which must be a recording card's "Play …" button; when it is the focused Settings window with RecordStuff in front, closes it with ⌘W so the next click opens it afresh. The Finder states remain as variations of the desktop the click lands on. Missing banners are recorded as not run; the script does not make extra recordings to retry. A group needs at least two passing clicks and no failed clicks; not-run counts remain visible.

The default is five clicks with Finder closed, in English (roughly one minute). `--full` covers three Finder states × five clicks in English (15 cases, roughly three minutes estimated from prior case timings; actual time depends on Accessibility). It changes only Finder coverage, not the language. Localized notification text is unit-tested; use `--languages zh-TW` for native Traditional Chinese checks, or `--full --languages en,zh-TW` to explicitly request both languages (30 cases). Every case prints its start, progress and elapsed time. Use `--clicks 2` for a shorter smoke check; values below two are rejected. Other options: `--finder closed,behind,minimized`, `--languages en,zh-TW`, `--seconds`, `--front <app>`, `--keep-recordings`, `--out`.

The installed bundle reproduced a focus race that local dist runs did not: macOS activated RecordStuff after the notification callback. Consequently the script tests `/Applications/RecordStuff.app`. `--install` temporarily copies the signed `dist/mac-arm64/RecordStuff.app` there, then restores the verified previous app; successful restoration removes the backup, failed restoration preserves it and reports its path. Raw reports stay under `docs/verification/measurements`.

Run on a dedicated desktop: close Finder windows first, leave the desktop alone during the run, and grant the terminal Accessibility plus Automation access to Finder and TextEdit. Existing Finder windows cause preflight to stop without closing them. A fresh temporary TextEdit file is opened for each case; only that file is closed, not other documents. Finder windows are tracked by their IDs after setup or a matching reveal. Unknown windows, including a reveal interrupted before its ID was observed, are left open and reported for manual cleanup. After closing the test document, TextEdit quits if no other documents remain; otherwise it stays running to preserve those documents. This avoids a general-purpose window snapshot/restore system. The notification verdict checks the session-wide frontmost application and Finder selection, not the monitor containing the windows. Test windows on a secondary monitor are valid for that verdict; RecordStuff still records the primary monitor, so those windows need not appear in the recording. Placement on a particular monitor or Space is not asserted.

Ctrl-C or SIGTERM cancels commands and waits. Commands have a 10 s timeout (process lookup 5 s, app copies 60 s); shortcut delivery and Finder window creation finish within their 5 s command limit before cancellation takes effect. Cleanup uses an independent 120 s budget, gives the current recording up to 30 s to settle, and sends stop at most once. It never reads a previous recording as evidence that the current one stopped. If recording settlement cannot be established, it leaves the app running and preserves the backup instead of quitting or replacing it. Settings are restored only after the app stops; the app stays closed even if it was running before the test. Incomplete runs, cancellation and cleanup failures fail the report. These bounds cover asynchronous operations, not an unresponsive filesystem or OS.

Not covered: other Spaces and Notification Center list clicks after the banner disappears. Historical timings, failures and later completion evidence are preserved in the [notification history](../verification/history-2026-09.md#finder-foreground-after-a-notification-click--2026-09-20); do not treat an older failure status as the current result.

### Playback check

`pnpm acceptance:playback -- <file>` covers the [playback case](../acceptance.md#recording-smoke-and-native-cases) for a saved file without a person or Computer Use at the player. It opens the file with `open -a "QuickTime Player"` and drives the player through AppleScript: QuickTime's duration within 0.5 s of ffprobe's and the same dimensions; at least 75% of 2 s of wall time played from the start; seeks to 25%, 25% again and 75% landing within 0.25 s; the front window's picture changing between the two positions by a mean of at least 1 gray level and more than four times the change between the two views of the same position; and playback from 1.5 s before the end stopping at the end. The audio track, QuickTime's mute and the system output volume are reported, not judged. `report.md` and `result.json` go to a new directory under docs/verification/measurements; the screenshots of each step feed the picture check and are kept there only when the round does not pass. Exit codes are 0 pass, 1 fail (including incomplete cleanup) and 2 blocked: not macOS, no ffmpeg/ffprobe, a locked session, or QuickTime Player already running, which the check refuses so that it only ever closes what it opened. It closes its document, quits the player and confirms the process exited. Its first run, on the 10.27 s smoke recording of 2026-10-01, measured a mean change of 29.42 between positions against 1.18 for the repeat, the controls overlay fading in between.

Screenshots need Screen Recording permission for the terminal; without it they show no QuickTime window, and the picture check fails with that hint. Not covered: clicking the player's own controls, other players, and whether the audio sounds right, which needs a listener.

## Measurement pipeline and thresholds

For a from-scratch explanation of the pipeline, the test material, each metric and why some settings measure better than others, see the learning article [Measuring screen-recording quality](../learning/measuring-screen-recording-quality.html) (Traditional Chinese). This section remains the reference for the current commands and thresholds.

Media-tools runs ffprobe/ffmpeg; verify.mts parses and judges pure data; verify-recording.mts pairs files with logs and saves results; CLI/matrix orchestrate. For long files, frame timestamps are sampled in separate head/tail intervals so the unobserved middle is not counted as dropped frames. The test page supplies moving content plus flash/beep markers on an audio clock.

Checks are in two tiers. **Integrity** checks hold for any content and are what a release acceptance needs: they ask whether the file is what the session produced. **Performance** checks are only meaningful when the recorded picture moved continuously, because screen capture emits no frames while the picture is still; they are judged only with `--moving` or `--sync` (the test material page, as `pnpm matrix` uses) and otherwise reported as n/a with the measured value still shown.

| Tier | Metric | Current project threshold |
| --- | --- | --- |
| Integrity | Output dimensions | Match capture report; satisfy cap and source aspect when known |
| Integrity | Duration | Requested matrix duration, else the log session length (`state → recording` to `state → stopping`), ±2 s |
| Integrity | Audio/video duration difference | Absolute difference <100 ms |
| Integrity | Audio minus video start offset (container) | Strictly between −45 and +125 ms |
| Integrity | Audio format | 48 kHz, two channels (stream metadata) |
| Integrity | Channel energy | Both channels measured by ffmpeg astats, each RMS above −60 dBFS. A silent, missing or invalid channel fails, as does an astats run that exited nonzero or reported fewer channels than the stream |
| Integrity | Video bitrate | At least 70% of the requested target; more is a larger file, not a failure |
| Integrity | Audio bitrate | At least 50% of the requested target; AAC follows content. With `--test-material` (implied by `--sync`, set by `pnpm acceptance`) it is reported, not judged: the page's sparse beeps encode far below any request, and dense-audio bitrate belongs to the [audio-quality diagnostics](audio-quality.md) |
| Integrity | Decode | No ffprobe full-frame decode errors; interactive playback remains a separate check |
| Performance | Average fps | Requested ±2 fps. The median frame interval and the nominal period are printed beside it (reporting only), so a cadence that is slow on every frame is told apart from drops |
| Performance | Dropped frames | <2% |
| Performance | Audio minus video offset (flash/beep) | Strictly between −45 and +125 ms, from at least 3 matched flash/beep pairs. It fails when a flash or beep more than 1 s from either end of the file has no partner (the page's own start, up to two flashes before its first beep, excepted): the remaining pairs would still give a median, but a beep lost near the detector threshold read 101 ms against 65 ms |
| Performance | End-to-end drift | Absolute drift <100 ms. A recording of at least 120 s (requested or measured) needs at least 3 matched pairs in each of its first and last 60 s; a shorter one has no drift to judge |
| Performance | CPU | Average of the app's process tree over the recording from its third second: ≤30% at 30 fps, ≤40% at 60 fps; 95th percentile, peak and VTEncoderXPCService reported; more than 25% above this machine's baseline is a warning (matrix only; [CPU budget](#cpu-budget)) |

Bitrate is a floor rather than a target because an encoder may exceed the request while still producing the intended quality (the former Chromium path overshot it by 1.5–2× at 60 fps); only a starved stream indicates a problem. These are the project's current constants in THRESHOLDS, not a guarantee for arbitrary content. A beep-heavy source has low AAC bitrate, and dual-mono passes the two-channel energy check without proving stereo separation.

Each check is pass, fail, blocked, incomplete or n/a (plan 030), and the caller states which evidence it requires: the matrix requires channel energy and the markers, `pnpm verify` energy and with `--sync` the markers, `pnpm acceptance` energy, and the update acceptance both. Required evidence that a missing tool prevents is **blocked**. Required markers that were measured but are too few, or a long file without both edge windows, are **incomplete**, with the reason: no flashes (the material was not on the recorded display), no beeps (silent or masked system audio) or too few pairs. The coverage rule uses the existing constants, `MIN_SYNC_PAIRS` (3) and the 60-second edge window; neither one pair nor a sync request alone is evidence. A tool that exited nonzero or printed incomplete output makes its check **fail**; its partial output is never used. Evidence a report did not require stays **n/a** with its reason and never passes. The format check is measured independently, so 48 kHz stereo can pass while energy is blocked. The aggregate is fail if any check failed, else blocked, else incomplete, else pass if any check passed, else n/a; processes exit 1 for fail or incomplete, 2 for blocked and 0 otherwise. The JSON measurement records each piece of evidence as `measured` with its value, or `not-requested`, `unavailable` or `error` with a reason. Channel RMS uses numbers for finite dBFS values and the strings `"-Infinity"` (digital silence), `"Infinity"` or `"NaN"` (invalid measurements) for non-finite values, preserving their meaning across JSON round trips. Legacy `null` levels are invalid, never evidence of audible audio. Reports written before this change carry the older combined audio check and three verdicts; they remain historical.

English is the default for new diagnostic output and measurement reports. Historical raw results retain the language and labels they had when recorded; the English verification summary explains their meaning. Do not rewrite measured values or old failures to resemble a new passing run.

## Audio fidelity regression

Read [Audio Quality: What We Measure and Why](audio-quality.md) for fixture v2, mathematics, threshold rationale, regression cases, and limitations.

```bash
pnpm audio:quality -- record /tmp/audio-run-001
pnpm audio:quality -- record /tmp/audio-repeat-001 --repeat 3
pnpm audio:quality -- fixture /tmp/audio-reference-v2.wav
pnpm audio:quality -- verify /absolute/path/recording-of-v2.mp4
```

`record` builds and drives the actual development app for 16 seconds, playing 12.1 seconds of diagnostic tones with macOS `afplay` once capture starts. Quit this project's development app first. Screen/system-audio grants and FFmpeg/ffprobe are required. Keep output device/volume fixed and pause other audio; the tool does not change settings. It records the primary screen and plays audible sound. `--repeat` accepts 1–10 runs; default 1. This requires a desktop session, not headless CI.

`record` cannot record the microphone: the development Electron has no microphone usage description, so macOS refuses it without a prompt and a start with the microphone on fails as `microphone_unavailable`. Microphone fidelity runs record the fixture with the packaged app from `pnpm start:app` (its shortcut, `afplay` playing the fixture) and measure the file with `verify`; plan 074's runs are in [audio quality §18](audio-quality.md#18-microphone-results--2026-10-16) and plan 078's, on CoreAudio's HAL, in [§19](audio-quality.md#19-microphone-results-on-coreaudios-hal--2026-10-17). Mute the output, keep the room quiet and do not speak during a run: the analyzer expects the fixture alone, and speech in the start marker's gap makes a run invalid.

Use a new directory with an existing parent. Each run retains `reference.wav`, `capture.log`, and `report.json`; multiple runs use `run-1`, `run-2`, etc. MP4 files remain in the app's configured output directory, referenced by reports. The root contains `summary.json` and before/after environment snapshots with versions, source/fixture hashes, device inventory, and volume when available. Repeated summaries include min/median/max and missing counts, never hide a failed run, and become invalid if endpoint device/volume snapshots changed. A partial summary remains `incomplete` until the batch and its environment checks finish; errors also produce `error.json`.

`fixture` writes a new WAV without overwriting a file. `verify` prints JSON; direct Node invocation avoids pnpm's banner when redirecting stdout. Only v2 diagnostic recordings are valid inputs, not arbitrary music/speech or v1 recordings. Decode is limited to the first 60 seconds; format is checked without resampling or upmixing. Owned capture children time out after 60 seconds; external decode/tool operations also have bounded timeouts.

Exit status is 0 for pass, 1 for measured failure, 2 for invalid measurement or execution/input error. Marker/PCM ambiguity suppresses unsupported frequency measurements. New gates include frequency fitting, a simultaneous pilot, terminal marker, per-component overlapping dropout windows, and local clipping/gap checks. All thresholds and guard regions are explained in the design chapter; none are calibrated product-wide guarantees.

`pnpm test` runs clean/degraded PCM and repeat-summary tests. With FFmpeg/ffprobe installed it also tests real AAC, low-pass, mono/44.1 kHz, and CLI contracts. The integration case is explicitly skipped without those tools. These controls validate the detector; real `record` runs validate the local app/OS path. Keep historical [evidence](../verification/README.md) unchanged when fixture or analyzer versions change.

Release v0.1.0 completed browser-download/install verification on the available Mac; Gatekeeper required per-app Open Anyway approval. See [release evidence](../verification/releases/0.1.0.md). Self-signing does not remove that first-launch barrier. Developer ID signing and Apple notarization are the separate distribution route if the scope is reconsidered.

After installing dependencies in a clean environment, run `node node_modules/electron/install.js` to install Electron 44 runtime (the package has no postinstall). CI's Windows jobs and the release builds include this step; see [release automation](releases.md).

### Echo-removal bench

Plan 096's measurement tools ([plan](../../plans/096-speaker-echo-removal.md)): material made by the tool, a simulated room, and an analyzer that judges a canceller's output against the answer known in advance. Developer tooling only; nothing ships with the app.

```bash
pnpm echo:bench -- material /tmp/echo-096-a [--seed 96] [--voices say|synthetic]
pnpm echo:bench -- baseline /tmp/echo-096-a
pnpm echo:bench -- analyze /tmp/echo-096-a/medium-clean-speech /path/to/output.wav
pnpm echo:bench -- aac /tmp/echo-096-a /tmp/echo-096-a-aac
pnpm echo:bench -- run /tmp/echo-096-a-aac c1 [--two-pass]
pnpm echo:bench -- compare /tmp/echo-096-a-aac c3 [none]
```

`material` writes stage A's takes to a new directory, one per condition: three rooms (small, medium, reverberant; a synthetic room response with early reflections and a decaying tail behind a 35–45 ms device delay), a clean and a soft-clipping laptop speaker (high-passed at 150 Hz), speech and music at the far end, plus a volume step (+6 dB on the speakers at 28 s, the reference unchanged), fixture v2's tones and headphones (no echo). The near voice is −26 dBFS RMS, the echo 6 dB below it, the microphone's noise floor −70 dBFS. Each condition holds `mic.wav` (mono), `reference.wav` (stereo, what the system track would hold), `ideal.wav` (the microphone without the echo), `echo.wav` and `take.json` (condition, seed, the script, events, device delay and environment). The script is 34 s: silence, far end only (1–9 s), silence, near end only (10–15 s), double-talk (15–25 s), far end only (25–33 s), silence. Voices come from macOS `say` (Meijia and Eddy in Mandarin (Taiwan) for the near end, Samantha and Reed in English for the far end; their sound depends on the macOS release, which `take.json` records); `--voices synthetic`, the default elsewhere, uses a speech-like synthetic signal (a gliding sawtooth through three formants with fricative bursts), which stands in for a voice's spectrum and rhythm only. Music is synthesized (panned sawtooth chords, bass, kick, snare and hi-hats above 7 kHz). Everything else is deterministic from the seed.

`analyze` reads a canceller's output (mono, or stereo read as its mean, at 48 kHz) for one condition and prints a JSON report; `baseline` analyzes the raw microphone (no canceller) and the ideal output (a perfect one) for every condition and writes `baseline.json`, the analyzer's floor and ceiling on that material, exiting 1 if a perfect canceller fails or no canceller passes where there is echo. The analyzer first aligns the output with the input by cross-correlation over the voiced stretches (±50 ms, reported as `lagSamples`), then measures 20 ms frames (Hann window, 1024-point FFT) over 125 Hz–16 kHz and in five bands (125 Hz–1 kHz, 1–4, 4–8, 8–12, 12–16 kHz):

- **ERLE** in far-end-only frames 10 dB over the input's noise floor (measured in the silent stretches and taken off both sides, so the floor does not cap the reading): median and 5th percentile, from 2 s after the first far-end sound and after each volume change; and **convergence**, the time after which every 100 ms window to the end of that far-end stretch stays above 15 dB.
- **Without echo** (near end only): the change, output − input, against the input, and the level difference.
- **The voice in double-talk**, in frames where the ideal is 15 dB over its floor: per frame and band, the output is fitted as g·ideal + h·echo (complex least squares, the input's echo being input − ideal), so residual echo correlated with the input's echo is not read as voice; the loss is −20·log10 of g's real part, capped at 60 dB. Median, 95th percentile, and the fraction of frames down more than 10 dB.
- **The raw echo against the voice** (G0), each where it is alone.

The gates judge the output as it is, aligned by the lag only, as D1 froze them. Beside them, never judged, `phaseNormalized` gives the voice figures again with a fixed phase per frequency taken out of the output, read over the near-end-only stretch from bins within 60 dB of the loudest and with coherence of at least 0.5 (others left as they are): a canceller's band-split filters shift phase by a constant amount, and AEC3 read 0.7 dB of "change" at 8–12 kHz on a voice it had no echo to remove from. Only the phase is normalized; a lost level still reads as one.

The report applies the plan's gates as the maintainer froze them on 2026-10-29 (`"gates": "frozen 2026-10-29"`): G1a–G1c on ERLE and convergence where the input has echo, G2 without echo, G3 in the full band and in every band with at least 20 voiced frames (a voice cut above 4 kHz barely moves the full band's figure). Checks that do not apply (no echo in that band) are `null` and do not count. Exit 0 when every applicable check passed, 1 when one failed, 2 for invalid input or a usage error.

`aac` copies a material directory with each condition's microphone and reference through macOS's AAC encoder (`aac_at`, 256 kbps, the encoder family the app's tracks use) and back, lined up again with the originals by cross-correlation; the ideal stays lossless (plan 096's D3: candidates are judged on AAC, as the app's files hold them). Stage B material is already AAC. `run` builds the offline bench in `native/echo-bench` (its own package, not the shipped engine's: it builds WebRTC's audio processing module from source with meson and ninja, `brew install meson ninja`; on macOS it names the SDK's libc++ headers, since a partial leftover in the Command Line Tools' own include directory hid them on the reference Mac), processes every condition with the candidate (`c1`: WebRTC AEC3 with its defaults; `c2`: AEC3 with a suppressor more transparent while the near end talks; `c3`: the offline canceller of our own, below; `none`: unchanged; `--two-pass`: the take processed twice and the second pass kept), analyzes each output and writes `run-<candidate>.json` with each condition's verdict and failed checks, the slowest real-time factor on one thread and the largest peak memory (`/usr/bin/time -l`). Only echo cancellation runs: no high-pass filter, noise suppression or gain control. AEC3 delays its output by 431 samples (9 ms) and adds comfort noise at about −96 dBFS where it suppresses; the bench's `cargo test` checks determinism, length, silence staying below −80 dBFS, a microphone without reference keeping its level, and its WAV handling.

`c3` (`native/echo-bench/src/c3.rs`, pure Rust with `rustfft`) works offline on the whole take: it returns the microphone bit for bit wherever the system track was silent within the echo's reach (its delay plus 300 ms); finds the bulk delay by a softened phase-transform cross-correlation (β 0.7, 150 Hz–8 kHz, the peak by magnitude, from the loudest channel over at most 30 s from where the system track first has sound); learns the room with one partitioned frequency-domain adaptive filter per channel of the system track (overlap-save, 512-sample blocks, 24 partitions, a step of 0.2 normalized per bin with a floor of a hundredth of the mean power, each later partition learning at 0.8 of the one before so a quasi-periodic far end does not ring); runs the take three times (learn everywhere and find the near end; learn where there is none and find it again; learn likewise and keep the output), the near end being error well above the residual its leak predicts and not coherent with the estimate, runs of a single block dropped; and suppresses only where no near end is heard, down to the room's noise (its power smoothed over about 70 ms, tracked down at once and up about 3 dB a second, never from a frame where the microphone is digitally silent; at most 40 dB), learning nowhere the microphone is digitally silent, at most 9 dB within about 530 ms of a voice, never leaving a bin louder than the microphone had it. Its state is about 0.4 MB for a stereo reference; this bench holds whole takes (about 250 MB peak for 34 s), so an integration would stream the passes. Built without AEC3 (`--no-default-features --features c3` against `--no-default-features`), it adds about 455 KB to the stripped binary (AEC3 about 580 KB).

`compare` reads a candidate's and a baseline's reports (`none`, the microphone unprocessed, by default) and writes `compare-<candidate>.md` and `.json`: the conditions passed and the medians of echo removed, change without echo, the voice's loss (median and 95th percentile) and the share of voice frames down more than 10 dB, then each condition before → after with its verdict.

`pnpm test:scope -- tooling-analysis` runs the analyzer's own controls (`scripts/lib/audio/echo-analyze.test.ts`), on synthetic voices so they run anywhere: a known fraction of echo removed reads within 0.5 dB of its ERLE (20 and 30 dB); a pass-through reads 0 dB ERLE and an unchanged voice; a canceller that outputs silence fails every voice check; a perfect canceller passes everything, also 100 samples late; a canceller that leaves the echo for 3 s after a volume step fails G1c for that step only, while one weak final frame does not fail it (convergence is judged on complete 100 ms windows); ERLE stays finite on noiseless material; a voice with 5% of its frames 12 dB down, or low-passed at 4 kHz, fails G3; and a perfect output through a first-order all-pass fails G2 (the gate judges the waveform) while its normalized figures read it unchanged, and the same 3 dB quieter reads as a loss there too.

### Real-speaker echo round

Plan 096 step 2, stage B on the Mac's own speakers and microphone with no canceller (`scripts/echo-record.mts`; its pure parts, with tests, in `scripts/lib/audio/echo-stage-b.mts`). A desktop round: it needs the [handoff](../testing.md#confirm-desktop-handoff-before-testing), plays sound and takes the speakers, the microphone and the primary display for about 20 minutes with three runs.

```bash
pnpm echo:record -- /tmp/echo-096-b [--runs 1..5] [--speakers-on-jack]
pnpm echo:bench -- baseline /tmp/echo-096-b/conditions
```

Before it: set the output to speakers (a headphone output blocks the round, since it makes no echo; speakers plugged into the headphone jack are named as headphones by macOS, and `--speakers-on-jack` says so for a built-in jack output, as the report notes) and the input to the microphone under test; the round uses the system default input, clearing `microphoneDevice` for its duration. It blocks (2) without macOS, the bundle, FFmpeg, Chrome or a settings file, while RecordStuff or this project's Electron runs, on a locked screen, or when the directory exists. It saves Editable recordings, the microphone on, the camera off, no countdown and the primary display over the user's settings, opens a guided page served on 127.0.0.1 full screen on the primary display (the only window the recordings show; `page.html` keeps it), launches the bundle and records, started and stopped by the registered shortcut:

1. **The voice take.** The page counts down 5 s and shows six sentences (Mandarin (Taiwan) and English) for 20 s; nothing plays. The maintainer reads them at their normal level and distance. Its microphone track from half a second in, 15 s of it (the script's near-end and double-talk stretches), is the near voice of every condition and G0's reference, at this microphone and this person's real level (the maintainer's choice of 2026-10-29: a voice played by the speakers would set G0 by the material's level alone). A reading not 15 dB over the quiet before it is asked for once more, then blocks.
2. **The echo takes**, each run: speech (`say`, English) and synthesized music at output volumes 50% and 100%, placed by stage A's script; music at 50% stepped to 100% at 28 s; music at 50% muted from 3 to 6 s; speech muted throughout (no echo). The page asks for quiet. Each take records about 40 s.

Each take's own system and microphone tracks are decoded (plan 098's layout, from the file's description); the material is found in the system track by normalized cross-correlation within the first 6 s, and both tracks are cut there, since they share the session's clock. A system track too quiet to correlate (score under 0.5, as when the output is muted and capture follows it) is placed by the runner's own timing instead, as `take.json` says. Each echo take plus the read voice becomes a condition in stage A's format under `conditions/` (the microphone is the echo take's plus the voice, the ideal the voice, the reference the system track), so `echo:bench`'s `analyze` and `baseline` read it. A volume step's size is read from the microphone either side of it.

`summary.json` and `report.md` give G0 per take (the echo against the read voice, median and worst run; G0 passes when a primary take's median, the speakers at 50% or 100%, is within 30 dB of the voice; a take whose echo never rises 10 dB over the microphone's floor counts as below the floor, a G0 failure rather than a missing measurement), whether the system's sound is captured before or after the output volume (the reference's level at 50% against 100%, from system tracks matching the material only: within 1.5 dB is before, 3 dB lower is after, otherwise unclear or unavailable), and the muted stretch's reference and microphone levels (D2). A recording that ends early fails the round without another shortcut, which would start a new one. Afterwards, also after a failure or an interrupt, `afplay` is stopped, a recording in progress stopped, the output volume and mute and the settings file restored, the app quit and the page closed once its launch has finished; the recordings stay in the output folder. Exit 0 when G0 passes, 1 when it fails or cleanup is incomplete, 2 blocked, 130/143 interrupted.

### Update acceptance

Run `pnpm acceptance:updates` with RecordStuff closed, on macOS arm64, using Node 24, the existing local signing identity, Chrome, ffmpeg/ffprobe and System Events Accessibility access. Unanswered, it stays over the centre of the material during both recordings and closes when the fixture exits. The runner itself never answers it; the round's executor may press Allow under the maintainer-authorized [exception](../acceptance.md#additional-cases-by-impact). It takes over the primary display for two short recordings; stop other audio and avoid interacting with the desktop during capture. It never quits an existing RecordStuff process, modifies the installed app, disconnects the network or writes the real user settings.

The runner copies source/build resources into a unique report workspace, instruments only that copy, and runs `pnpm start:app`. Production update handlers, the real AppTray context, SettingsStore, Recorder, native capture host and shutdown path remain in use. The build-only fixture substitutes deterministic HTTP responses and a clock, stores settings/logs/recordings under the report directory, and intercepts `shell.openExternal` to assert the requested URL. There is no test command channel in normal builds. Anchor checks stop preparation if production wiring changes instead of silently testing a stale substitute.

Default cases cover checking/overlap, current/newer versions, a launch that announces a newer version once (the update notification is intercepted like the saved one, and a manual result counts as told), GitHub fallback, failure followed by recovery, language/preference across process restarts, launch checks disabled when due, the 24-hour limit including failed attempts, delayed requests during capture and results withheld until saving, and quitting during a pending check. `--full` also exercises older versions, invalid/prerelease/incompatible feeds and real bounded timeout cancellation; those boundary cases already have unit coverage and need not run in every smoke check. Reports identify the mode and selected feed scenarios. The real-capture phase uses the existing System Events shortcut mechanism, fixed Chrome test material, media integrity checks and flash/beep guards. Both modes retain two recordings of about ten seconds each: one checks a deferred request, the other a deferred result. Missing permission/tools or contaminated material cannot count as a successful capture.

Recorder-state snapshots are judged by one contract, `assertLockContract` in [update-acceptance.mts](../../scripts/lib/acceptance/update-acceptance.mts). Only recording shows REC and one enabled Stop; starting shows `…` like saving, and neither offers Stop. Starting, recording and saving lock the screen, quality, resolution cap, frame rate, shortcut, notification, launch-check and update-action groups, the output folder's Change… and the tray's output-folder change; language, appearance, the About links and the output folder's Show in Finder stay usable, each choice included. A settled recorder (idle or needsPermission) unlocks every group; choices it disables for their own reasons, such as a check already running, are outside this contract. The tray never carries update actions. The expected behavior comes from `BUSY_SETTINGS_POLICY`, not from the model's current flags: a settings group missing from it, or a listed group the panel no longer offers, fails until it is classified. The real run applies the contract to the recording snapshots and the idle snapshots around them. Starting, saving and permission states are covered by unit tests against real `settingsView`/`trayModel` snapshots, because the runner cannot pause in those transient states.

`--logic-only` explicitly omits real capture. `--require-native-ui` makes missing native UI evidence a required gap (exit 2); the default scope reports it separately. Handler/model assertions are **not** native Tray clicks, browser visual confirmation, playback listening, first permission grant or public-build upgrade acceptance. The current computer-use windowless Tray limitation remains documented; this runner does not simulate a mouse click by claiming an action-handler invocation was one.

Reports live under `docs/verification/measurements/<timestamp>-updates-*/`; `--out <new-directory>` chooses a new directory and refuses an existing one. `report.json`/`report.md` include every required case, including ones not run after an earlier failure; requests/responses, events, build/signing output, source/artifact hashes and recording verification are retained. Exit 0 means every required case in the stated scope passed, 1 means a failure, and 2 means blocked/incomplete. SIGINT/SIGTERM request cleanup: the owned fixture quits through the production shutdown path to stop/save a recording, and only the unique material-browser profile is closed. A fixture that cannot be safely stopped is left intact and reported as a cleanup failure; it is never replaced with a global kill. Source workspace is removed only after the app exits; recordings and evidence remain.

The isolated fixture also intercepts saved notifications and records the event so the first recording’s banner cannot obscure the second recording’s material; notification delivery is outside this acceptance scope. Media analysis judges frame timing and flash/beep offset and requires at least five matched pairs; short clips do not judge long-run drift. Channel energy and the markers are required evidence, so a blocked or incomplete check fails the case as a failed one does. An existing `--out` directory is preserved and rejected with a clear message and exit 2, without writing a report there.

## Background UI suite

`pnpm test:ui` (plan 066) runs the routine renderer and Electron integration checks without the desktop: no window appears, nothing takes focus, no key or pointer event reaches the system, no global shortcut is registered, no sound plays, no notification is delivered, nothing opens in Finder or a browser, and nothing is captured. The maintainer can keep working while it runs. It replaced the desktop rounds of the former `acceptance:settings` and `acceptance:shortcut` fixtures and most of `acceptance:player`; every former case has a ledger ID and a destination in [the migration ledger](../verification/playwright-migration-066.md).

- **Hosts.** [global-setup.ts](../../tests/ui/global-setup.ts) refuses a run without `out/`, the test clips or the Electron runtime (blocked, exit 2), compiles three Electron hosts once and records the `out/` digest. The app host ([app-host.ts](../../tests/ui/hosts/app-host.ts)) loads the built `out/main/index.js` with a seeded, isolated userData, logs and videos tree: production `SettingsWindow`, actions, `AppShortcuts`, `AppTray`, `VideoFullScreen`, settings.json and pages. The view host ([view-host.ts](../../tests/ui/hosts/view-host.ts)) serves the production page and preload with the real `settingsView`, `RecordingResults` and `RecordingsLibrary` but its own IPC handlers, as the former settings fixture did; its `components` mode is the synthetic view of the component checks. The countdown host ([countdown-host.ts](../../tests/ui/hosts/countdown-host.ts)) drives the production `CountdownOverlay` and countdown page. Tests reach a host's main process through `globalThis.__recordstuff`; no test IPC reaches a page and nothing ships.
- **Boundary.** [boundary.ts](../../tests/ui/hosts/boundary.ts) is what production receives for `require("electron")`. Every `BrowserWindow` is created hidden, offscreen (`webPreferences.offscreen`), muted and unthrottled; `show`, `showInactive`, `focus`, `blur`, `minimize`, `restore`, `setFullScreen`, `setSimpleFullScreen` and `setVisibleOnAllWorkspaces` are recorded and answered from a virtual window state (focus moves between windows and emits `focus`/`blur` as the OS would). `app.focus`, `app.dock.show` and `setMenu`, the tray, notifications, global shortcuts (a registration adapter whose refusals a test chooses and whose callbacks a test calls), dialogs (scripted answers; an error box fails the test), `shell` (the Trash moves the file into the test's own folder), `desktopCapturer`, `systemPreferences` and `powerSaveBlocker` are adapters that record each request. IPC, storage, the media protocol, pages and preloads stay production's.
- **Evidence kinds.** Three scopes, kept apart in names and reports: logic (Vitest), background UI and integration (this suite: page input, DOM focus, rendering, real IPC, production main and storage, real muted decoding of the checked-in clips in tests/ui/media) and desktop/capture (the native runners and recording rounds). An adapter call says production asked for something (show, focus, cover the display, notify, register); it is never evidence that the OS did it. DOM focus here is the page's own: Playwright keeps the document focused, so a case that needs the window to be active in the OS is a native case.
- **Input.** Playwright's mouse and keyboard are Chromium input events through CDP. Keys main intercepts before the page (`before-input-event`: zoom, the Escape filter after full screen) are not reached by CDP and are sent with Electron's `sendInputEvent` instead ([helpers.ts](../../tests/ui/helpers.ts) `mainKey`); a key Playwright's layout does not name (F20) goes through CDP's `Input.dispatchKeyEvent`. `evaluate` sets up state, injects precise faults (a held settings.json rename, a refused registration, a delayed history save) and reads results; it never replaces a click or key under test.
- **Containment.** After every test, on any outcome, the fixture ([fixtures.ts](../../tests/ui/fixtures.ts)) audits the boundary: a window not made through it, a page rendering onscreen or unmuted, a request to unmute (refused at once), or a call that reached the real `globalShortcut`, `shell`, `desktopCapturer`, `dialog`, `Notification`, `app.focus`, the Dock or a tray's methods fails the test. Electron's `Tray` constructor cannot be replaced, so a real tray made anyway is caught by its first use. Each violation is appended to the launch's folder as it happens, so one is still reported when the app quit itself or hung. On macOS a [window-server probe](../../tests/ui/desktop-probe.ts) samples about once a second, read-only, whether any window of the launch's main process is on screen and whether it became the frontmost app; either fails the test, as does a probe that could not sample. An offscreen window's own `isVisible()` follows its page and says nothing about the screen, so it is not used. Samples cannot see a window that appeared and went between two of them; the adapter log is the complete record of requests. Windows CI has the boundary's guards only.
- **Cleanup.** Teardown closes the app normally (production's quit, with a held test write released first), then confirms from the process table, rescanned until it ends, that every process of the launch is gone: its main process's descendants and this checkout's Electron run with its unique temporary folder, such as the local-data cleanup worker; another program that merely names the folder (a `tail -f` of its log) is never adopted. A process table or audit that could not be read fails the test too. A close that times out or a tree that needed SIGKILL fails the test, and a folder whose processes could not be confirmed gone is kept for diagnosis. Only the launch's own processes are ever signalled. `pnpm test:ui:drills` ([drills.spec.ts](../../tests/ui/drills.spec.ts)) proves this: a launch that fails before the app is up, an assertion failure, a timeout (in a child run), a renderer crash, a hung main (forced cleanup reported as a failure), a containment violation, bypasses of the real dialog, notification, activation and unmute paths, a violation before the app quits itself, a foreign process naming the folder (left alone) and SIGINT to the runner (macOS/Linux) each fail where they must and leave no process of the launch.
- **Close timings (plan 078 step 5).** Every launch's teardown appends its phases to `test-results/ui-close-timings.jsonl`: the boundary audit, the normal close and the wait for every process to end, and the host's quit steps (`before-quit`, `will-quit`, `quit`, the main process's exit, which the hosts write to the launch's log) in ms after the close began. `node scripts/ui-close-timings.mts` prints the spread of the normal closes and the slowest launches with each phase, and check.yml runs it after every UI group; the file is in the failure artifact. The Windows shards' intermittent close timeouts were traced with it on 2026-10-17: in every close, slow ones included, main had quit and exited 70–100 ms after the close began, while Playwright's close, which resolves only when every process holding the launch's output has ended, took up to 7.7 s, because Chromium's helpers sometimes lingered on the Windows runner after main had gone. ## Scripted native acceptance

By the maintainer's decision of 2026-10-02 ([acceptance cases](../acceptance.md#additional-cases-by-impact)), committed runners operate RecordStuff's own tray menu, Settings window and menu items, so these native cases no longer wait for a person or for Computer Use, which cannot reach the tray-only process. [native-ax.mts](../../scripts/lib/runner/native-ax.mts) holds one JavaScript for Automation helper that calls the Accessibility C API through the ObjC bridge and posts CoreGraphics events. It reads a menu in about 0.1 s; the same read through System Events took 29 s. Every read names its target by pid. An AXError -25211 (no Accessibility access for the terminal) is **blocked**; runners never change the privacy list.

[tray-driver.mts](../../scripts/lib/acceptance/tray-driver.mts) finds the status item under the app's `AXExtrasMenuBar` and opens its menu with a CoreGraphics right-click; `AXPress`, the item's only action, is a left click and would start a recording. On macOS 26 status items are drawn in Control Center's windows, one per display. AX reports one copy's frame even when the front app's menus crowd that copy off a narrow menu bar: on 2026-10-02 the `REC` item vanished from a 1080 pt portrait display while AX still reported it there, and clicks reached nothing. The driver therefore clicks the reported frame only while a Control Center window there is on screen, and otherwise the on-screen window that the primary menu bar names after the bundle identifier (`com.ericts.record`); with neither, it fails. A right-click that opens nothing within 3 s is repeated, at most three times and only while no menu is open, because one click in a recording reached nothing while the next ones opened the menu; the report lists every click and how its point was found. Menu items are chosen by `AXPress` on the item or by arrow keys and Return, and closed with Escape. Separators are untitled disabled items; a shortcut is `AXMenuItemCmdChar` with its modifier bits (1 Shift, 2 Option, 4 Control, 8 no Command). Each UI state is bounded at 30 s and every wait honours cancellation.

The click moves the real pointer. Events posted to the process instead (`CGEventPostToPid` to RecordStuff or Control Center, with or without the window number and a moved event) left the pointer alone but never opened the menu on macOS 26.6.2 (2026-10-02): Control Center hit-tests a click at the pointer. A round therefore needs the desktop handoff, and input from a person during it can still close a menu or change a selection; nothing detects that yet.

## Keyboard-layout shortcut check

```bash
pnpm acceptance:shortcut-layout
```

Plan 043 registers global shortcuts by physical key by disabling Chromium's `LayoutAwareGlobalHotkeys` ([recording shortcut](desktop.md#recording-shortcut)). An Electron upgrade that renames or drops the feature would silently bring back layout lookup, and a digit shortcut would move to the keypad under Zhuyin. This check catches that without any manual input-source switching. Run it with RecordStuff closed, on macOS. The terminal needs System Events Accessibility access, and at least one keyboard input source whose number row types no digits, such as Zhuyin, must already be enabled. Like `acceptance:shortcut-native`, the script builds first; the runner invoked directly stops as blocked when `out/` is missing. It records nothing, needs no capture permission and takes about 10 seconds, build included.

- **Other RecordStuff processes.** The runner refuses as blocked while one runs: the packaged app, or an Electron development or fixture process started with this checkout. It would own the same shortcuts.
- **Choosing a source.** It reads the current input source and keyboard layout, then tries enabled, selectable keyboard sources, the current one first. It stops at the first whose layout types no digit on the number row while keypad 7 still types 7: that is the layout under which a layout-aware digit shortcut moves to the keypad. `-- --source <id>` tries only that source; a source that is not enabled is blocked before anything changes. The runner never adds or enables sources and never changes keyboard settings.
- **Activating an input method.** An input method applies its own layout only when a text field activates it. Selected from a background process, it keeps typing with the previous layout, and the check would pass with the bug present. For an input method, the runner therefore opens a small window of its own with a focused text field, waits up to 8 seconds for the layout to report the change, and closes the window. This briefly takes focus. A layout that does not change in time is blocked.
- **The app under test.** An Electron fixture loads the built `out/main/index.js` behind the [shortcut-failure](../../scripts/fixtures/shortcut-failure.ts) boundary pattern: isolated userData and logs, and a saved recording shortcut of `CommandOrControl+Control+Alt+Shift+7`. Registration reaches the real `globalShortcut`, but a press is recorded instead of calling the production toggle, so nothing records and no permission prompt appears.
- **Keys.** System Events sends three key codes. The Settings shortcut ⌥⌘, (key code 43) is a delivery control and must fire. Number-row 7 (key code 26) must fire. Keypad 7 (key code 89) must not fire within 1.5 seconds. A combination that nothing registered goes to the frontmost app.
- **Restore.** The original input source is restored and confirmed on success, failure, timeout, SIGINT and SIGTERM; an unconfirmed restore is a cleanup failure. Selecting a source is the same as choosing it from the input menu, so macOS's list of recently used sources can change. An input method keeps the layout it applied until its next use; that state belongs to the method and is not restored.

`-- --drill-layout-aware` is a negative control outside the default run. The fixture removes production's `disable-features` value before app ready, so Chromium's layout-aware lookup is on as it was before plan 043. The number-row key must then fail and the keypad fires; the run exits 1 and still restores the input source. The report states whether the drill detected the lookup.

Reports go to `docs/verification/measurements/<timestamp>-shortcut-layout/`, with a `-drill` suffix for the drill. `report.md` and `report.json` list the original, tried, in-use and restored sources with their layouts and number-row characters, the accelerator and registrations, each key result and the cleanup. `electron.log` and `check/app.log` keep the process output.

Exit codes:

- 0: pass.
- 1: fail, including any cleanup failure, even when the run was also interrupted or the screen locked.
- 130 or 143: interrupted by SIGINT or SIGTERM with the input source restored and nothing left.
- 2: blocked. Causes: not macOS, missing `out/`, another RecordStuff process, a locked screen (even when a key also failed), no System Events access, no qualifying enabled source, a refused registration, or an input source that changed during the check.

Synthetic key codes do not prove physical keys; 043's maintainer-reported press remains the hardware evidence.

## Acceptance cleanup

Complete app acceptance rounds save test recordings, restore settings, close test UI, quit the tested app and confirm exit, on success, failure and cancellation. Cleanup failure fails acceptance. Preserve evidence and do not reset permissions. During development, stopping recordings and quitting/restarting/rebuilding RecordStuff as needed is authorized without additional confirmation. Quitting resets process state, not stored preferences.

Desktop runners (`acceptance`, `acceptance:settings-native`, `acceptance:shortcut-native`, `acceptance:shortcut-layout`, `acceptance:settings-shortcut`, `acceptance:tray`, `acceptance:quit-dialog`, `acceptance:notification`, `acceptance:updates` with capture, `acceptance:playback`, `acceptance:player`, `acceptance:window-drag`, `matrix`, `measure:finalization`, `measure:cpu` and `audio:quality -- record`) share [desktop-session.mts](../../scripts/lib/runner/desktop-session.mts): `caffeinate -u` wakes an idle-slept display, `ioreg`'s `CGSSessionScreenIsLocked` refuses a locked session before anything is launched or keyed, `caffeinate -d -i -w <runner pid>` keeps the display awake until the runner exits, and a lock seen during the round (polled every 2 seconds and at the end) turns the result into BLOCKED with exit code 2 and a `Desktop:` line in the report. Every desktop runner ends in the same order ([round-exit.mts](../../scripts/lib/runner/round-exit.mts), 2026-10-05): anything the round owned left running or unrestored fails it (1) even when the session also locked or the round was interrupted, since the next round must not start over it; an interruption (Ctrl-C or SIGTERM) that left nothing exits 130 or 143, the first signal deciding; a lock is blocked (2) even when a case also failed, since the lock may be why; then a failed case is 1; and a missing prerequisite or a case that could not run is blocked (2) only when nothing failed, so it never hides a real failure. Isolated lifecycle fixtures do not need the display and do not hold it.

Native Settings acceptance (`acceptance:settings-native`) also treats a window another app deactivated as blocked (plan 057). The page draws no focus line while its window is inactive, and on macOS `BrowserWindow.focus()` does not take activation back from another app, so before each case that needs an active window (since plan 066 the focus border on a window another one deactivated and a day rollover while it is in front; the focus-line and focus-border matrix, shortcut capture and returned focus run in the background suite, where the page's document keeps focus) the fixture reads `BrowserWindow.isFocused()`, `isVisible()` and the page's `data-window`, asks for activation the way `SettingsWindow` does (`app.focus({ steal: true })`, then `window.focus()`) when the window is not active, and reads them again when the case is judged. Each interaction starts its own check, so a blur in one does not decide the next; a case whose window was not active at either point, or blurred in between, is `NOT RUN` in the console, `report.md` and `results.json`, with the reason and the frontmost app from `lsappinfo`; a case that ran on an active window keeps its pass or fail. When `capturePage()` throws, the fixture still writes the cases recorded so far and adds `failure.json` naming the screenshot and the window's state at that moment. The round then exits 2 (blocked) when only not-run cases or a capture on an inactive or hidden window stopped it after the fixture had shown its window; any judged failure, another stop, or a fixture exit or process cleanup that disagrees with the results exits 1. The classification lives in [settings-activation.mts](../../scripts/lib/acceptance/settings-activation.mts) and its unit tests.

Runners share process matching and the launch environment (plan 052). [processes.mts](../../scripts/lib/runner/processes.mts) builds every `pgrep`/`pkill` pattern: `recordStuffPattern` for a RecordStuff bundle and `electronPattern` for a checkout's development Electron.app escape the path and anchor it, so a checkout under `~/Code (2026)/` matches itself and no sibling or argument that mentions it, and `pgrepPids` throws on a spawn error or any status but 0 and 1 (1 is "none"). A process-group probe treats only `ESRCH` as gone; `EPERM` means the group still exists, and a failed signal is reported as a cleanup error. A `pgrep` failure therefore blocks the round instead of reading as "nothing is running": in preflight the runner stops before it launches anything, and in cleanup the round exits 1 (`CLEANUP FAILED` after an interrupt), because nothing then proves its processes exited. Every runner that launches Electron or the app starts from `scrubbedEnv()` in [runner-env.mts](../../scripts/lib/runner/runner-env.mts), which removes `ELECTRON_RUN_AS_NODE`, `ELECTRON_RENDERER_URL`, `RECORDSTUFF_AUTORECORD` and `NODE_OPTIONS` (a VS Code JavaScript Debug Terminal sets the last), and adds only what it owns, such as the autorecord request, fault points or `PATH`; a unit test fails when a runner deletes one of these keys itself or copies `process.env`. `matrix` and `measure:finalization` build asynchronously in the build's own process group, so a Ctrl-C or SIGTERM during the build reaches only the runner, whose handler stops the whole group and exits 130 or 143 after cleanup. `matrix` and `measure:finalization`, like `acceptance`, `measure:cpu` and `acceptance:updates`, open the material in a private Chrome profile created for the round with `mkdtemp`; cleanup waits for that browser to exit, then removes the profile, and reports a profile it could not remove as incomplete cleanup.

**Capture engine (plan 076).** The native engine is the only one since 2026-10-16: the runners take no engine option and the app no engine switch. `scrubbedEnv()` also removes the app's development capture switches (`RECORDSTUFF_CAPTURE_SOURCE`, `RECORDSTUFF_CAPTURE_AUDIO`, and the old engine switch so a stale shell value never reaches the app; [capture-engine.mts](../../scripts/lib/runner/capture-engine.mts)), which would otherwise change the recorded area or its sound without a trace. `measure:cpu` starts the bundle with `open`, which hands it launchd's environment instead, so it is blocked while launchd holds any of these switches (`launchctl getenv`). CPU baselines are the native engine's only ([CPU budget](#cpu-budget)). `audio:quality` fingerprints the recording engine's sources (the native host process, every Rust source and `Cargo.lock`), and its build may take 10 minutes, since it compiles the engine. `pnpm acceptance`'s start timeline adds the native engine's process ready, display chosen, probe and prepare times, and names its first progress report, which comes on a one-second tick, as such. `measure:finalization` pairs each stop with its save whichever comes first (saves run in the background since 2026-10-09, so idle usually precedes them; before this it found no sample) and adds stop→saved, finalize and the engine's finish.

`pnpm acceptance` leaves the accepted app closed and reports the final cleanup verdict in `report.md`; it refuses to quit a replaced process or an app not confirmed idle. Notification acceptance restores the bundle and settings but keeps the app closed. Native Settings acceptance supervises its own process group and writes `cleanup.json`, including timeout and interruption outcomes; the background suite confirms every launch's process tree is gone after each test. Isolated runners clean only their own processes. Unit checks do not close unrelated apps. The settings-shortcut entry step leaves its panel open for native inspection, unless `--quit` ends it with ⌘Q; otherwise the complete round owns final shutdown. Tray acceptance leaves the app closed, as `pnpm acceptance` does. Start the app before the next recording round; use `pnpm start:app` to rebuild changed code.

The shortcut runner writes `input-diagnostics.json` before sending start and on failure: exact AppleScript, app PID, sender process, System Events UI status, frontmost app and any Secure Input owner reported by IORegistry. No reported owner is not proof that Secure Input was off. Diagnostic queries are read-only, bounded, and do not grant permissions. `events.log` and the current run’s `app-session.log` survive failed runs as well. An osascript success is not delivery proof: only the registered app callback counts. Do not blindly resend a toggle shortcut after timeout; it could stop a recording whose callback arrived late. When delivery fails, compare a physical press and the generated script against the same bundle and input context before attributing the failure to the app.

### Focused test scopes

`pnpm test:scope` ([test-scope.mts](../../scripts/test-scope.mts), plan 070) runs one task's checks from the scope catalog in [test-scopes.mts](../../scripts/lib/runner/test-scopes.mts). ### Verification recipes and timing

```bash
pnpm acceptance:recipe -- --list
pnpm acceptance:recipe -- shortcut-registration
```

A recipe is the leaf commands of the composite checks one kind of change needs ([testing policy](../testing.md#select-once-validate-once)), run in order with one build of identical inputs. `check` is `pnpm check`; `settings` is `pnpm acceptance:regression`, check and the background suite, with no desktop phase; `shortcut-registration` adds `acceptance:shortcut-native` and the keyboard-layout runner without the second `pnpm build` that `pnpm acceptance:shortcut-native` and `pnpm acceptance:shortcut-layout` each start with; `native-ui` builds once and runs `acceptance:settings-native`, `acceptance:shortcut-native` and `acceptance:player`, the native counterparts of the background suite, in one desktop round; `recording` runs typecheck, tests, the native engine's Rust tests, `pnpm start:app`, whose `electron-vite build` is check's build, and `pnpm acceptance`. `pnpm acceptance` can follow `start:app` directly because it waits up to 30 seconds for the log's latest session to be the running pid's own, by its run id, and idle; before plan 061 it could judge the previous app's session. Playback stays a separate `pnpm acceptance:playback -- <file>` on the saved recording. `-- --dry-run` prints a recipe's commands without running them. A unit test keeps each recipe's runners equal to the package scripts it replaces.

Each phase runs in its own process group with the console attached and stops the recipe when it does not pass, as `&&` does; later phases are reported as not run. Exit code 2 from a desktop runner or from the background suite (a missing build or clip) is blocked; from typecheck, tests or a build it is a failure. SIGINT or SIGTERM sends SIGTERM to the running phase and waits up to 60 seconds for its own cleanup before killing its group, so a runner still quits the app and restores what it changed; the recipe then exits 130 or 143, or 1 when that cleanup was incomplete. A phase that runs longer than an hour is stopped and fails, as does one whose group outlived it or needed SIGKILL to clean up, even after exit 0. `recording` owns the bundle `pnpm start:app` opens: when it ends before `pnpm acceptance` quit the app (a failure, a blocked runner or an interrupt), it asks the bundle to quit normally, which saves a recording in progress, and waits up to 30 seconds for every process of the bundle, helpers included, to exit; it never kills the app, and a process it cannot confirm gone fails the run. An app already running when the recipe started is not its to quit. Otherwise the recipe adds no desktop interaction of its own, so each runner keeps its handoff, lock and cleanup rules.

The report goes to `docs/verification/measurements/<timestamp>-recipe-<name>/` (`--out <new directory>` chooses another and refuses an existing one). `report.json` and `report.md` record the wall time, each phase's start offset and duration from the monotonic clock, its outcome, exit code and cleanup, and the time outside phases (identity hashing and the app cleanup; writing the report is not timed). A child that knows its own boundaries appends them to the file named by `RECORDSTUFF_TIMING_FILE`; `pnpm start:app` reports preflight (process check and signing identity), build, package, verify, and open or the DMG this way, and they appear inside their phase without being added to the totals again. The report also records the revision, a digest of the uncommitted changes including untracked files, the runtime-input digest, the `out/` and `app.asar` digests before and after, and Node, pnpm, Electron and OS versions. When sources, tests or configuration change during the run, an otherwise passing run is **invalid** and exits 1, because its evidence belongs to no single revision. Agent orchestration gaps and desktop-readiness waits happen outside the process and are reported as unknown, not as zero.

**Bundle reuse.** After a successful build and signature verification, `pnpm start:app` writes `dist/mac-arm64/RecordStuff.app.inputs.json` beside the bundle, outside its signature and the DMG. It holds a digest per runtime input — `src/` without `*.test.ts`, `build/`, `resources/` without Markdown, `package.json`, the lockfile, the electron-builder, electron-vite and app TypeScript configurations, and the installed Electron, electron-builder, electron-vite and Vite versions — and the digest of `app.asar`. Symlinks are followed, so the digest covers what they point to. A copied acceptance workspace whose sources import from `scripts/`, as `acceptance:updates` and `acceptance:controlled` instrument theirs, counts `scripts/` too. The inputs are read before the build; when they changed by the time verification finished, no record is written. A rebuild removes the old record first, so a failed rebuild leaves none. `pnpm open:app` refuses, before verifying the signature, a bundle with no record, an unreadable record, a changed `app.asar` or changed inputs, naming up to five changed files; rebuild with `pnpm start:app`. Editing only tests, scripts, documentation, plans or the website therefore keeps the verified bundle reusable, and any source or configuration change forces a rebuild.

### Guided deferred-quit notice

Run `pnpm acceptance:quit-dialog -- --language zh-TW`, then repeat with `--language en`. The copy is removed once its process groups have exited; it is retained, and cleanup fails, when that cannot be confirmed. Evidence torn by a killed process reads as missing, and a runner error still removes the copy under the same condition and writes a failing `report.json`.

## Controlled acceptance build

Plan 035's native acceptance needed failure states that real faults cannot produce on demand: a pending result that normally lasts milliseconds, an unknown outcome after a close failure, slow or failing history storage, and seeded history. `pnpm acceptance:controlled` builds a clearly labeled signed copy of the app for them. Like the update fixture, it copies the source into a new run directory under `docs/verification/measurements/<timestamp>-controlled/`, instruments only that copy behind anchor checks ([controlled-acceptance.mts](../../scripts/lib/acceptance/controlled-acceptance.mts)) and runs the copy's `pnpm start:app`. The bundle identifier and signing identity, and with them the screen-recording grant and notification permission, stay those of the development app. Tray, Settings, Recorder, EngineFileWriter, failure history, notifications and the quit flow are the production code, and normal builds have no command channel. The copy differs in three ways:

The build records through the native engine, the only one since 2026-10-16, and injects only its faults: the write fault turns the engine's next progress report after media arrived into its write error (`disk_full` for `enospc`, `output_write_failed` for `eio`), and the close fault fails the engine's finished file once as a failed close would, through EngineFileWriter's outcome, so the file stays under its temporary name. The engine's own error mapping in Rust is not exercised; its unit tests cover it.

- **Isolated data.** userData, logs and the default output folder live in the run directory. The maintainer's settings, failure history and `~/Movies/RecordStuff` are never read or written. The build starts with default preferences (English, notifications on, 3-second countdown with its tick, ⇧⌘1).
- **Label.** Every tray tooltip starts with `[Controlled acceptance build]`, and a `controlled:` log line names the run directory. Evidence from this build is controlled-state evidence: it shows native presentation and interaction, not a real disk or capture fault.
- **Fault points** ([controlled-faults.ts](../../scripts/fixtures/controlled-faults.ts)), all off until armed:
  - `cleanup=hold` holds each failure's settled result before it reaches the history, so the pending result (processing, Got it disabled, no reveal) stays on screen, quit is deferred and a session's interruption sentinel, when it has one, stays until `release cleanup`. The file work behind it has already finished.
  - `write=eio|enospc` fails the engine's next progress report after media arrived, once, as its write error (above): output_write_failed or disk_full, with the partial kept.
  - `close=fail` fails the engine's next finished file, once, through EngineFileWriter's outcome, as a failed close would. The writer cannot confirm preservation, so the result is unknown; armed before a normal stop, the stop itself fails that way.
  - `history-save=hold|fail` holds saves until `release history-save`, or rejects them as an I/O error that every automatic retry meets again until the fault is off.
  - `prepare=hold` (plan 065) holds each `prepared` reply of the capture host in main until `release prepare`: the host holds its stream and waits for `record`, and the Recorder stays starting, so a start lasts as long as a check needs. A reply released after its attempt was cancelled reaches the Recorder as a stale session's, which stops it again.
  - `--hold-history-load` on `launch` or `reopen` holds that launch's history load until `release history-load`; the command channel answers from launch on.
  - `throw` raises one synthetic uncaught exception from a timer on the next tick, outside any promise, so it reaches the production uncaught-exception handler as a real programming fault would (plan 056). Sent during a recording, it shows whether writes, the stall guard and the stop continue and when the error box appears; the `events.jsonl` line records the state and `mediaPending` when it was scheduled. It is not a fault mode: nothing stays armed.

```bash
pnpm acceptance:controlled -- launch [--seed none|partial|retention] [--hold-history-load]   # new run: build, sign, open
pnpm acceptance:controlled -- fault cleanup=hold write=enospc     # also close=fail, history-save=hold|fail, prepare=hold, <name>=off
pnpm acceptance:controlled -- release cleanup                     # or history-save, history-load, prepare
pnpm acceptance:controlled -- status                              # state, faults, holds and each failure-history row
pnpm acceptance:controlled -- throw                               # one synthetic uncaught exception on the next tick
pnpm acceptance:controlled -- quit                                # production quit: saves a recording, may ask about reminders
pnpm acceptance:controlled -- reopen [--hold-history-load]        # the same bundle and data
pnpm acceptance:controlled -- clean                               # after exit: remove the workspace, keep the evidence
pnpm acceptance:controlled -- selftest
```

`quit` leaves armed faults and holds in place, so it can exercise a deferred or questioned exit; turn faults off and release holds first for a plain exit. An interrupted or failed `launch` or `reopen` waits up to 15 seconds for a bundle that `open` already started: a ready app quits normally, and one that never reported ready is named for the user to quit. Commands other than `launch` and `selftest` act on the newest guided run unless `--dir <run>` names one. `--seed partial` writes one unread current-format history record whose synthetic partial exists. `--seed retention` writes twenty reviewed records between two unread ones, so acknowledging the old unread record exercises the limit of 20 most recently reviewed records. Seeded files hold synthetic bytes, never a playable recording. `launch` and `reopen` refuse while any RecordStuff runs, because an isolated userData does not share the single-instance lock. Exit 0 means success, 1 failure, and 2 blocked or a usage error; a `launch` or `reopen` interrupted by Ctrl-C or SIGTERM exits 130 or 143 once nothing of it is left running. Arm and release events are appended to `events.jsonl` and the run's app log.

The maintainer performs every native action; the runner only builds, seeds, arms, releases, reports and quits. `selftest` is the one exception within this runner and proves the tool, not the product; [`pnpm acceptance:tray -- --long-start`](#tray-acceptance) drives a launched controlled build's real status item and shortcut under the 2026-10-02 permission for committed runners. In a separate run with notifications and the recording shortcut off, it makes the isolated output folder unwritable and holds the cleanup of the resulting start failure while rejecting its save. It checks the pending and unsaved rows, releases, retries, holds an acknowledgement's save, quits, relaunches with a held history load and quits again, calling the recorder's toggle and the production action handler directly. It records nothing, so the write and close faults rest on their unit tests with the real EngineFileWriter and Recorder. A failed or interrupted self-test turns every fault off and releases every hold before quitting. Its `report.md` lists each step, and the workspace is removed once the app has exited.

### Audit tool bounds and evidence

Media subprocesses default to a 900,000 ms timeout with SIGKILL; RECORDSTUFF_MEDIA_TIMEOUT_MS accepts a positive integer override; any other value is a usage error (exit 2) that each runner and `pnpm verify` report before they launch, record or measure anything. A successful version probe must exit zero. Measurement Markdown and JSON are atomically replaced using a .md.pending journal; the next append replays an interrupted pair before adding new evidence. This is crash recovery for a serialized writer, not simultaneous-reader or multi-writer transactions.

Stable release tags share the updater's numeric grammar and reject leading zeros. Asset HEAD checks follow redirects and require a successful final response. Website links resolve relative to each source page, including queries and escaped fragments. Reveal styling is activated only after the observer is installed, so a missing JavaScript bundle leaves content visible.
