# 070 — 縮小測試 scope，加快程式迭代

[English](070-focused-test-scope.md) | [繁體中文](070-focused-test-scope.zh-TW.md)

狀態：已規劃，尚未開始實作。建立：2026-10-08。優先順序：下一項。硬性相依：無。依[計畫索引](README.zh-TW.md)按順序執行。

## 目標與邊界

每次修改只執行能抓出受影響行為與依賴回歸的最小檢查集合，減少本機「修改—驗證」循環中的無關工作，同時保留有意義的斷言及完整 CI／發布覆蓋。成功代表無關案例減少、回饋時間可量測地縮短，而非單純減少斷言。

本計畫落實已加入[測試政策](../docs/zh-TW/testing.md)的低風險選擇規則。修改範圍是測試選取、開發指令、配方說明與案例粒度。不改產品行為、不刪除必要的原生／擷取證據、不增加桌面並行、不弱化清理、不用另一套設計代替正式 UI，也不引入 monorepo、遠端測試服務或自動依賴圖選取器。

## 現況與證據

- `pnpm check` 包含根目錄所有型別檢查、所有 Vitest 測試與正式建置。Vitest 已能指定檔案，`pnpm test:ui` 已能選 Playwright 檔案／標題，但方便的設定配方仍把完整 check 與所有背景 UI spec 綁在一起。
- `tests/ui/settings-matrix.spec.ts` 提供十二個語言／主題／尺寸案例，每個內部再跑十種狀態及播放器／選單互動，難以只選單一分頁或狀態。其他 spec 也有一次包住多種行為的案例。
- UI global setup 即使只跑局部案例，也要求整套 `out/` 頁面／preload 並編譯三個 host。這是共用初始化成本，與多跑無關測試是不同問題。
- 2026-10-06 三份通過的設定配方紀錄約為：型別 1 秒、單元測試 26–27 秒、建置 2–3 秒、背景 UI 210–215 秒。這是歷史本機量測，不是目前保證。來源：`docs/verification/measurements/2026-10-06T07-51-06-837Z-recipe-settings/report.json`、`2026-10-06T10-20-38-990Z-recipe-settings/report.json`、`2026-10-06T11-06-09-720Z-recipe-settings/report.json`。這些 ignored 檔案只作補充證據，計畫不依賴它們才能理解。
- 規劃開始時，計畫索引寫著以 `pnpm check` 作為所有 App 修改的最終基準，配方說明也引導邏輯／設定修改跑廣泛檢查。登記本計畫時已修正索引，配方說明仍需與低風險流程對齊。

## Scope 選擇契約

從本次任務的 diff、受影響呼叫端及共用依賴選擇 scope，不把工作樹原有的無關修改算進本次任務。這種區分不代表能沿用過期產物：真正執行的內容仍須對應目前相關 runtime 輸入。

每項檢查都要回答具體的回歸問題。缺少覆蓋時補相關測試或明列限制，不以無關完整套件代替。共用修改取受影響使用端 scope 的聯集；只有具體跨領域風險、影響無法充分界定或使用者明確要求，才擴大到完整套件。人工選擇為準，不只依路徑判斷影響。

以下是選擇範例，不是撰寫計畫時應執行的指令：

- 顯示文案：語意、雙語／placeholder 一致性；具型別 key／placeholder／呼叫改動加型別檢查，可能換行時看受影響畫面。不跑無關邏輯、播放器、擷取或全主題矩陣。
- 單一設定分頁的局部間距：該分頁相關視覺狀態／尺寸。需要新的渲染證據時建置一次；不預設跑其他分頁互動或完整矩陣。
- 獨立 helper：相關模組測試與 TypeScript 檢查，沒有整合理由就不跑 UI／建置。
- 設定持久化或 IPC：受影響的正式 main 整合案例與 model 測試；只有 OS 啟用／視窗框／焦點改動才加原生案例。
- 共用 primitive／token：受影響使用端與代表狀態；共用影響需要時才跑完整視覺範圍。
- 錄影、原生快捷鍵送達、權限、簽章、執行期依賴：保留政策中的對應高風險檢查。聚焦背景通過不能證明擷取或 OS 效果。

## 實作順序

### 1. 盤點可選單位與代表任務

- [ ] 用一份小型、可審查的 scope 清單，對應現有單元／UI／原生群組的行為與依賴。先涵蓋設定錄影偏好、一般、媒體庫、失敗／疑難排解、主題／排版、播放器、倒數及快捷鍵整合。沿用檔名與穩定案例 ID，不複製測試內容、不另做測試框架。
- [ ] 分開視覺渲染、互動、持久化／IPC 與真正 OS 行為，記錄目前混合的案例及需要 scope 聯集的共用使用端。
- [ ] 選五種代表修改：文案、單分頁間距、獨立 helper、單一持久化路徑、共用 token。實作前先列預期包含／排除案例。有既有耗時就沿用，不為測試選取修改重跑原生／錄影基準。

交付：scope 定義、預期選取結果及待拆案例的斷言／ID 覆蓋清單。

### 2. 提供可看見選取結果的聚焦入口

- [ ] 新增最小的 `pnpm test:scope` 入口（提案，尚不可用），接受明確具名 scope 或測試檔，將支援的篩選傳給既有 Vitest／Playwright runner。可組合 scope，檢查不重複；既有完整套件指令不變。
- [ ] 提供 list／dry-run，執行前列出確切檔案／案例、檢查、必要產物、是否建置及排除範圍；dry-run 不建置、不啟動 Electron。內部可用 filter，但不能依賴易變的標題敘述選取。
- [ ] 未知 scope、filter 沒匹配或非預期的零案例須拒絕，不回報成功、不默默退回完整套件。保留 runner exit code 及受阻／清理結果。
- [ ] 所選案例需要正式 `out/` 時最多建置一次；純單元檢查不建置。只有相關輸入能證明未變時才沿用產物，否則重建。不要求新增跨任務的通過快取。
- [ ] 適用時沿用現有 typecheck project，不發明會漏掉 import／共用契約的單檔 TypeScript 檢查。先量成本，再決定是否值得細拆型別檢查。

交付：可預期的本機入口；廣泛配方仍明確是廣泛範圍。個別任務直接使用既有指令更簡單時，仍可使用。

### 3. 只拆阻礙有效選取的案例

- [ ] 重構設定視覺矩陣，使分頁／狀態、語言、主題及尺寸可獨立選取；播放器／選單行為移到獨立案例。共用 helper／資料，不複製斷言。
- [ ] 其他打包案例只在代表任務需要更窄選取時拆分。不把每個斷言都拆成案例、不增加不必要的 Electron 啟動；狀態連續性本身就是受測行為時，相關步驟維持在一起。
- [ ] 保留每項既有有意義斷言、ledger ID、正式頁面／樣式／preload 路徑及完整套件維度。比對拆分前後覆蓋清單，測試數量改變不代表覆蓋保留。
- [ ] 盡量保留既有審核 snapshot 的覆蓋與 baseline 名稱。重整案例不默默更新 baseline，視覺差異須檢視；完整執行仍跑保留的整個矩陣。
- [ ] 每個實際案例保留隔離與清理，不為數字好看而並行使用桌面，或讓原本獨立的案例共用可變狀態。

交付：一般分頁的局部修改可不跑媒體庫／播放器／倒數，完整執行仍保留這些覆蓋。

### 4. 對齊政策、配方與入口

- [ ] 同步 `AGENTS.md`、雙語測試指南、雙語貢獻指南、工具文件及計畫索引，移除互相矛盾的一律 App 基準。範例保持簡短：受影響行為 → 最小檢查 → 擴大條件。
- [ ] 更新配方 purpose，說明 `settings`、`check`、`acceptance:regression` 是廣泛組合，不是每次局部修改的預設。不默默縮減 CI 或維護者依賴的既有指令。
- [ ] 每次任務只需簡短選取說明與結果，不為小修改建立永久報告。所選檢查通過就停止；後續修改只重跑失效的檢查。
- [ ] 維持目前 CI 與發布閘門。局部結果須寫明 scope，不回報為完整回歸證據。

交付：指示、指令及 agent 預設行為一致採用最小相關範圍。

### 5. 驗證 scope 並量測改善

- [ ] 驗證有意義的 selector 行為：聯集／去重、未知與空 scope、filter 傳遞、是否需要建置、子程序失敗傳遞、dry-run 沒副作用。跑受影響工具測試與型別檢查；fixture／host／teardown 改動另依政策跑既有 drills。
- [ ] 對五種代表任務檢視所選檔案／案例，確認指定無關群組沒有出現。在相符的最終輸入上執行有用的代表聚焦回合，分別記錄 wall time、初始化／建置時間及執行案例。這是選取驗證，不是假造產品修改再追加錄影。
- [ ] UI 拆分全部完成後，在同一份最終建置上跑一次完整背景套件，確認覆蓋移轉與清理。影響分類要求時跑完整根目錄檢查，不重複組合指令已涵蓋的階段；中間修改跑相關案例，不每一步都完整回歸。
- [ ] 在相同原始碼、產物與環境比較局部與完整耗時，沿用最終完整移轉驗證作比較。代表性的局部視覺修改以 wall time 至少減少 50% 為目標；未達時回報實測與剩餘成本，不反覆量到結果好看。純單元 scope 不啟動 Electron，純文案靜態檢視不啟動測試 runner。
- [ ] 只有 global setup／host 編譯實際主導聚焦耗時時才優化，這是計畫內的條件式後續工作，不是提供可用選取的前置。修改時驗證 fixture 邊界及清理 drills，不犧牲產物新鮮度或必要正式輸入來省初始化。

## 完成條件與驗證限制

入口及文件符合選擇契約、代表任務排除無關案例、拆分覆蓋有對照、最終移轉檢查通過，且耗時／限制有紀錄後才完成。不能只為達成時間目標而漏掉相關斷言；缺工具／權限是受阻，不是不適用。

本工作通常不需簽章封裝、真實桌面回合、錄影、音訊／矩陣或發布，因為沒有規劃修改擷取或 OS 輸入路徑。實作若碰到這些邊界，重新分類，只補對應受影響案例，遵循準備交接及原生驗收 skill。背景 Electron 檢查仍是背景證據。

這次僅撰寫計畫：檢查相對連結／錨點、現有及提案指令區分、雙語一致性與 `git diff --check`；不跑測試、建置、不啟動 App、不錄影。

結案時把耐久指令／選擇契約寫入工具及測試文件，將覆蓋移轉與耗時證據寫入雙語驗證紀錄，更新雙語索引，再依 repository 完成規則移除計畫檔。沒有使用者要求，不 commit、push 或發布。
