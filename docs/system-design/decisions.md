# Design Decisions

[English](decisions.md) | [繁體中文](../zh-TW/system-design/decisions.md)

These are adopted decisions, not a future-work checklist. Current code and measured results supersede assumptions from old execution plans.

| Decision | Rationale | Tradeoff or reconsideration trigger |
| --- | --- | --- |
| Electron and TypeScript | Implement desktop lifecycle, native UI, and Chromium capture with one language | Electron resource cost; consider native capture only after measuring a concrete limitation |
| Bundle identifier is the reverse of a domain the maintainer controls (`com.ericts.record`; [why](signing.md#bundle-identifier)) | Identifiers have no registry, so an owned domain is the only uniqueness guarantee; the identifier is the app's identity for TCC grants, notifications and the signature | Chosen once and kept: changing it makes macOS treat the app as new and users must re-allow screen recording |
| Built-in getDisplayMedia and MediaRecorder | Avoid custom audio devices and native sidecars | Limited codec/timestamp control; explicit EC/NS/AGC false restored local spectral fidelity and stereo, so remeasure on engine/platform changes |
| Hidden capture renderer | DOM media APIs belong in a renderer; visible UI can remain native | Requires port readiness, session IDs, ordering, and heartbeat |
| Main owns state and media writer | UI and capture must not independently claim success | Main coordinates cleanup and file completion |
| H.264/AAC MP4 | Verified QuickTime playback and hardware encoding | Fragmented MP4; no universal repair guarantee or format fallback |
| Native Tray/Menu/Notification | A one-button recorder does not need a UI framework | OS controls notifications and foreground ordering |
| Scripted native input on RecordStuff's own UI, by committed runners only (maintainer decision 2026-10-02, plan 063; [tooling](tooling.md#scripted-native-acceptance)) | Computer Use cannot reach the tray-only process, so tray cases waited for the maintainer or were blocked; CoreGraphics clicks and keys with Accessibility reads reached every state in the 048 and 035 rounds, and a runner repeats them and compares the native menu with the production model's log line | Scripted input proves delivery and state, never appearance, which stays an observation of its screenshots. A click moves the real pointer (posting to the process did not open the menu on macOS 26), so rounds still need the desktop handoff and a person's input can disturb them undetected; an isolated macOS session or VM is the step that would remove that. Recheck the status-item lookup after each macOS update, since Control Center hosts the item |
| Recording failure history in its own Settings tab, not a separate window (plan 047; [design](desktop.md#recording-failure-results)) | Failures above the preferences made every Settings open start with a long block of reasons; Cap keeps history and diagnostics as pages of its one Settings window and links the tray straight to them. Failures and preferences are used together (guidance leads to the Recording tab), and a second window would need its own lifecycle, preload, sender authorization, size persistence, close shortcut, crash and focus handling | Revisit a separate window only if the history grows beyond failures into, for example, a library of saved recordings, a separate product decision. Error text only in a tooltip, a recordings library and a log upload were not adopted |
| Pre-recording countdown, 3 s by default (plan 040; [design](recording.md#countdown)) | Capture began about 0.3 s after the click, so the first frames showed the pointer leaving the menu bar and there is no editor to trim them. Capture is prepared before the count and `MediaRecorder.start()` is the gate at zero, as Cap prepares its pipeline and gates frames; Off, 3, 5 and 10 s follow Cap's choices, and the default applies to existing users | Only a 28%-white digit at the top-right, no box, ring, text, full-screen dimming or content protection: `getDisplayMedia` has no per-window exclusion, so the overlay leaves 300 ms before capture instead. An optional tick with each digit (plan 046) is on by default by the maintainer's choice, also for existing users, and switchable in Settings; it ends 860 ms before capture, so time separation keeps it out of the recording. There is still no start sound at zero, because RecordStuff records system audio and whether `restrictOwnAudio` excludes the app's own sounds is unverified. The digit fades on bright photos; in 035's N32 the maintainer judged it readable and transparent enough over a bright photo, a white document and a dark editor, so the alpha stays. Its size scales with the recorded display, 14% of the shorter side clamped to 56–216 pt (plan 045), because a fixed 56 pt was about 5% of a 1080 pt screen and read as too small; a size setting and a centred digit were not adopted. Any click, the shortcut, the menu or Quit cancels, and a cancel is not a failure |
| Publish by exclusive hard link; no overlapping finalization (plan 037; [design](recording.md#file-completion-and-failure)) | Measured stop-to-ready was the publication copy: libuv never clones on macOS, so saving a 2 GB recording copied for 1.3–1.9 s and a low-disk early stop failed for lack of room. A link takes constant time, needs no space and, like the copy, never replaces a name; with it no separable wait was left, so a second lifecycle for overlapping saves was not built | Volumes without hard links (exFAT, some network volumes) still copy: a 2 GB save waited 2.2–3.1 s on an exFAT image and the copy needs the file's size free, which overlap would not fix, and on a slow drive the copy would contend with the next recording's writes. Accepted by the maintainer (2026-09-27). If such output folders prove common, first remove the copy there (for example reserve the final name exclusively, then rename over the reservation, after measuring it on that file system) rather than overlap; reconsider overlap only if a measured representative case again spends over 0.5 s after the file is closed |
| CPU budget measured from outside the app (plan 049; [budget](tooling.md#cpu-budget)) | Idle had no measurement and the matrix read `ps`'s decaying `%cpu`, too coarse for an idle second and blind to system helpers. As in Cap's harness, a small helper reads `proc_pid_rusage` for the app's process tree, reports VTEncoderXPCService apart and discards windows whose process set changed; unlike Cap, the thresholds fail a run | No monitoring timer in the shipped app, which would itself wake the idle app. Thresholds hold for the reference M1 Pro; another machine or an Electron upgrade takes a new baseline first. The 5-second permission poll stays until a measurement shows it matters; the page-less renderer Electron pre-warms with the default session (about 65 MB until the first window) and Chromium's audio service kept after the first capture (about 49 MB, 0.3 wake-ups per second) are accepted by the maintainer (2026-09-28), since memory is reported, not budgeted; the idle contract names them by role and the post-recording check counts growth per recording rather than the difference from launch |
| Keep awake during a session; stop and save on sleep (plan 050; [design](recording.md#file-completion-and-failure)) | Nothing kept the Mac awake, so idle display or system sleep could end a long recording without input, and a sleep the user asked for ended it as capture_failed 146 ms after `suspend` with its banner lost (035's N31). A `prevent-display-sleep` blocker covers the session; a sleep that cannot be refused becomes a normal stop with a note, and notifications wait for waking. Cap ([static review](https://github.com/CapSoftware/Cap/tree/20c224073bece3fbebed8acb631bd2df97cd6f40)) holds no blocker and rebuilds its capture into the same recording after a system stop | The display stays on for as long as a recording runs, with no setting. The same file is not continued after waking, because `MediaRecorder` cannot swap tracks; reconsider if users need recordings that span a sleep. A forced display sleep or a screen lock without system sleep is not handled and still fails the recording; the maintainer accepted that on 2026-09-28 |
| Global shortcuts register by physical key (`LayoutAwareGlobalHotkeys` disabled on macOS; [why](desktop.md#recording-shortcut)) | The editor records physical keys and refuses the keypad; Chromium's layout-aware lookup moved the default ⇧⌘1 to the keypad under Zhuyin | On non-QWERTY Latin layouts a letter shortcut is the US position, not the keycap letter. On every Electron upgrade, run `pnpm acceptance:shortcut-layout` ([check](tooling.md#keyboard-layout-shortcut-check)): if its Chromium renamed or dropped the feature, registration silently returns to layout lookup |
| Handwritten guards and one repository | Small protocol/state surface stays readable and testable | No protocol negotiation; independently shipped peers would need a stronger contract |
| Copy media buffers | An Electron 44 ArrayBuffer-transfer probe hung main | Extra copy and no bounded backpressure |
| Measure actual frame size | getSettings once caused an incorrect 1080×606 output from a 1080p display | Additional startup measurement and explicit fallback warnings |
| Align timeslice and keyframe interval | Low-motion Retina recordings exceeded the first-chunk deadline with timeslice alone | Nominal 1-second settings are not delivery guarantees |
| Retain quality coefficients | 30 fps outputs were near target; 60 fps remained useful despite excess bitrate | Larger 60 fps files; distinguish requests, track reports, and measured output |
| Remove audio-quality selector | Different requests produced about 160 kbps AAC on this setup | Fixed 256 kbps request does not promise that bitrate or stereo separation |
| Do not compensate inherent A/V latency | Measured latency/drift met the project's accepted limits | Remeasure after capture-engine changes |
| Fixed self-signing identity and DMG | Recipients can install without developer tools or certificates | No Apple notarization; first-launch exception may be needed; TCC behavior is not universally guaranteed |
| DMG holds only the App and Applications link | The drag-to-Applications window is the installer convention users already know; bundled documents added clutter and ambiguity | Help, update and removal guidance must stay reachable online and linked from every release; the release gate fails on any extra visible file |
| Tag is the release and the version; verification precedes tagging | One maintainer and one Mac cannot support nightly channels, an in-pipeline manual acceptance gate only repeated checks already done during development, and a version stored in the repository before tagging was one more thing to get wrong | CI proves build, signature, layout and byte identity but not capture; a bad release is fixed by a new version, never by overwriting; the record job commits to main as a bot |
| Manual update, no updater; Trash removal on macOS, the per-user uninstaller on Windows (Windows part: maintainer decision 2026-10-03) | Same identity and path keep settings and permissions across replacements; a one-button recorder gains little from background update machinery. On Windows, an entry in Settings → Apps is how users expect to remove an installed app, and the per-user installer registers it | Users must download new versions themselves on both platforms; user data is never deleted automatically. The macOS rule is unchanged. The Windows uninstaller removes the app, its Start-menu shortcut and its registration and keeps recordings, settings and logs (`deleteAppDataOnUninstall: false`). Revisit an updater only through the deferred update assessment |
| Windows x64 published with macOS by the same tag, checked by CI only, without Windows hardware (maintainer decision 2026-10-03, plan 064, [closure](../verification/history-2026-10.md#plan-064-closure--2026-10-03); [release contract](releases.md#release-contract)) | The maintainer has no Windows machine but wants Windows users served by the same flow as the Mac; GitHub's Windows runners can build, install, inspect and uninstall an installer, though not record. A per-user one-click NSIS installer (`oneClick`, `perMachine: false`, no admin prompt) is the common practice for an Electron app released on GitHub (T3 Code, pingdotgg/t3code, ships one beside its DMG), and its Start-menu shortcut carries the appId `com.ericts.record` as the AppUserModelID Windows toasts need | Hardware verification remains macOS only. Windows evidence is CI only: `pnpm check` on `windows-2025` and, before and after publication, the silent per-user install, registration, version, architecture, signature state, tray icons, shortcut and silent uninstall; capture, system audio, notifications and the tray are unverified on Windows (035's N17 tray matrix stays open), the Windows wording (system tray, the computer going to sleep, the default playback device, Ctrl-only shortcut messages and reserved keys) has never been seen on Windows, and the app enforces no Windows version floor: Electron 44 itself supports Windows 10 and newer, below which the app cannot start to check, and without hardware no narrower floor can be set. Unsigned, as the asset name says, so SmartScreen warns; integrity rests on SHA256SUMS, `release-win32-x64.json` and a GitHub build-provenance attestation. A Windows failure fails the whole tag before publication. x64 only: Windows on Arm and Linux have no build. Record hardware evidence when a Windows machine becomes available; reconsider signing if SmartScreen or user reports make the unsigned installer impractical |
| English source and optional Traditional Chinese | GitHub documentation and diagnostics use a common source language; users may choose Chinese UI | Catalog and paired documentation must be maintained together |
| Separate design from plans | Execution logs are poor long-term specifications | Keep behavior/evidence in docs and unfinished work in plans |
| Raw measurement runs stay local | Per-run reports, logs and probes are machine-specific and would multiply with every contributor; only the interpreted conclusion is durable | `docs/verification/measurements/` is gitignored; the verification record and release records must carry enough numbers to stand without the raw files; history before `acc6342` still holds the early raw runs |
| [Known-fixture audio diagnostics](audio-quality.md) | Simultaneous pilot, frequency fitting, and continuity windows distinguish spectral loss, gain, and clock error | Invalid measurements cannot support quality claims; retain repeated failures, never learn a bad baseline automatically; not a substitute for listening or long-duration verification |

## Evolution boundaries

Builds use electron-vite and electron-builder. Follow stable dependency releases and rerun relevant checks and media verification when upgrading; an old measurement is not proof about a new engine.

There is no speculative Effect, schema framework, monorepo, React, Rust, or full PlatformRecorder layer. A future UI renderer should remain outside the media byte path. If Chromium proves inadequate, evaluate a replacement host while preserving Recorder's contract. Recording libraries, editing, shortcuts, automatic updating, Windows hardware verification and support for platforms beyond macOS and Windows x64 are not prerequisites for the current downloadable build.

Third-party comparisons and native-engine candidates from historical planning are not current dependencies or commitments. Reevaluate their APIs and suitability if an actual need arises.

2026-10-06: Updates and ordinary uninstall continue to retain user data. An explicit, confirmed “Clear local app data and quit” exit path removes app-owned data while retaining recordings and the output folder. Old settings migrate at startup; newer schemas refuse overwrite. Migration support and removal policy are independent: cleanup does not replace upgrade support. See [desktop design](desktop.md#local-app-data-cleanup).
