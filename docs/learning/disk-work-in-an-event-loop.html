事件迴圈裡的磁碟工作：三個可遷移的設計模式

一個只有一條 JavaScript 執行緒的桌面程序，既要即時回應使用者，又要把資料安全地寫到磁碟、在當機後交代得清楚，還要限制同時進行的工作量。本文以一個選單列錄影 App 從「停止錄影」到「檔案發布」的流程為貫穿範例，說明三個彼此相扣的設計模式：先用非同步 I/O 而不是執行緒、在建立資源之前先寫下意圖、以及用 promise 鏈做有上限的並行。每個模式都寫明它成立的前提，以及不該使用它的情況。

這篇文章要回答的問題

把場景抽象化之後，問題其實很一般。一個以事件迴圈為核心的程序，例如 Electron 的 main process、一個 Node.js 服務、或任何單執行緒的執行環境，同時負責兩種工作：回應互動（選單、快捷鍵、行程間通訊），以及把狀態寫到磁碟。磁碟的延遲不受你控制，程序可能在任何時刻被殺掉，而且會有多個長時間操作想同時進行。於是有三個問題會反覆出現：

  1. 寫磁碟時，怎麼不卡住互動，又不引入不必要的執行緒？
  2. 程序死掉之後，怎麼知道有哪些東西寫了一半？
  3. 多個長操作重疊時，怎麼讓它們有限度地並行而不失控？

這三個問題各有一個小而穩定的答案。它們不是三個孤立的技巧，而是同一組前提底下互相支撐的決定：第一個模式決定 I/O 在哪裡執行，第二個決定當機後誰來交代，第三個決定並行的邊界，而第三個模式一旦引入，就反過來要求第二個模式的紀錄必須以「每個操作一份」的形式存在。

貫穿範例：一段錄影的停止與發布

範例來自 RecordStuff，一個在 macOS 選單列運作的螢幕錄影 App，用 Electron 寫成，沒有主視窗。它的 main process 擁有全部狀態與所有檔案寫入；一個隱藏的 capture renderer 用瀏覽器的 MediaRecorder 產生編碼好的影片分片，透過 MessagePort 送回 main。main process 只有一條 JavaScript 執行緒，這條執行緒同時負責 tray 圖示、右鍵選單、全域快捷鍵，以及底下這三種磁碟工作。

磁碟工作內容特性
媒體分片大約每秒一段編碼資料，依序 append 到暫存檔 <stamp>.recording.mp4，每 5 秒 fsync 一次串流、持續、量大；已經是非同步寫入
失敗歷史一個小 JSON，記錄失敗過的錄影與使用者是否已確認；寫入採「寫暫存檔、fsync、rename」的原子替換小、偶發、必須耐久；目前用同步呼叫
發布停止後 sync、close，把暫存檔以獨占方式複製成 <stamp>.mp4，再刪除暫存檔一次性、可能很慢（大檔、外接碟）；決定使用者何時看得到成品

接下來的討論都用同一個情境：

  1. 使用者停止錄影 A。writer 排空剩餘分片、fsync、close，然後開始發布。
  2. 發布途中某個寫入失敗，App 必須在 userData 記一筆失敗歷史，提醒使用者這段錄影有問題。
  3. 使用者立刻按下快捷鍵想開始錄 B。
  4. 此時電腦被強制關機。

模式一回答步驟 2：記那筆失敗歷史時，UI 能不能不卡住。模式二回答步驟 4 之後：重新啟動時，App 怎麼知道 A 和 B 都沒有正常結束。模式三回答步驟 3：B 能不能在 A 發布完成之前開始，以及如果可以，誰在管 A 的收尾。

模式一：先用非同步 I/O，量測之後才考慮執行緒

成立的前提

  • 只有一條執行緒負責互動。任何在這條執行緒上阻塞的呼叫，都直接變成使用者感受得到的停頓。
  • 磁碟延遲沒有上限。userData 可能位於慢速外接碟、網路磁碟，或正被備份程式掃描的位置。
  • 這項工作是 I/O 重、CPU 輕：資料很小，序列化很快，等待幾乎都花在磁碟上。

天真做法與它們的症狀

第一種做法是同步呼叫：openSync、writeFileSync、fsyncSync、renameSync 依序執行。其中 fsync 是真正把資料推到儲存裝置的呼叫，在慢碟上可能花數百毫秒到數秒。這段時間裡 tray 點不動、快捷鍵沒有反應，使用者看到的是 App 凍結。

第二種做法是把同步呼叫包進 Promise，以為這樣就非同步了：

TypeScript// 看起來非同步，實際上完全一樣阻塞
function saveHistory(content: string): Promise<void> {
  return new Promise((resolve) => {
    fs.writeFileSync(file, content); // executor 立即在同一條執行緒同步執行
    resolve();
  });
}

Promise 的 executor 會立刻在呼叫它的執行緒上同步執行，裡面的 writeFileSync 照樣阻塞到底。這是很常見的誤解，值得單獨點名。

第三種做法是直接上 worker_threads。它確實能解決阻塞，但代價是一整套機制：建置要多一個 entry，打包後要驗證 worker 檔案真的存在且能啟動；主執行緒與 worker 之間要設計訊息協定與快照傳輸；worker 崩潰、逾時、重複啟動都要處理；測試要模擬 worker 失敗。當工作本身只是「寫一個小 JSON」時，這些機制的維護成本會超過它解決的問題。RecordStuff 的計畫草稿一開始就是這樣寫的，結果規格裡多出好幾條專門處理 worker 打包、崩潰與終止的條款，全都與原本要解決的凍結無關。

模型：分開 CPU 工作與 I/O 工作

把一次寫入拆成兩半。CPU 工作是序列化與驗證；I/O 工作是 open、write、fsync、rename。I/O 交給 Node 的 fs.promises：這些呼叫會被送進 libuv 的執行緒池，主執行緒只登記回呼，然後繼續跑事件迴圈。CPU 工作留在主執行緒，但要有上限，而且要量測：拿最大允許的輸入去測序列化時間，對照一個畫面更新週期（約 16 毫秒）；低於這個預算，就不需要執行緒。

RecordStuff 的 atomic-file.ts 已經同時提供同步與非同步兩個版本，非同步版本節錄如下：

TypeScriptexport async function writeFileAtomic(
  file: string, content: string,
): Promise<void> {
  const temporary = `${file}.tmp`;
  await fs.promises.mkdir(path.dirname(file), { recursive: true });
  const handle = await fs.promises.open(temporary, "w");
  try {
    await handle.writeFile(content, "utf8");
    await handle.sync();      // 真正等磁碟，但等待發生在 libuv 執行緒池
    await handle.close();
    await fs.promises.rename(temporary, file);
  } catch (error) {
    await handle.close().catch(() => undefined);
    await fs.promises.unlink(temporary).catch(() => undefined);
    throw error;
  }
}

每一個 await 之間，主執行緒都是空閒的，可以處理 tray 點擊或快捷鍵。同時順序仍然被保證：rename 一定在 sync 之後，所以讀者看到的檔案不是舊內容就是完整的新內容，不會是半截。

每個機制對應的問題

  • fs.promises 對應阻塞。等待搬到執行緒池，主執行緒不再為磁碟停下來。
  • 序列化留在主執行緒對應複雜度。不必把資料搬到另一個執行緒，不必設計協定，不必處理另一個執行緒的生命週期。
  • 量測門檻對應「以後資料變大怎麼辦」。門檻寫下來，資料成長到觸發門檻時才升級到 worker，而不是預先付費。
  • 資料上限對應量測的可信度。失敗歷史有明確上限：全部未確認的紀錄加最近確認的 20 筆，每筆細節最多 64 KiB，讀取時超過 32 MiB 直接拒絕。沒有上限，「序列化夠快」就是一句無法驗證的話。

為什麼在這個前提下它是最佳預設

同步 fsfs.promisesworker_threads
主執行緒阻塞整段 I/O 期間無無
額外機制無無建置 entry、訊息協定、生命週期、崩潰處理
CPU 重工作阻塞仍然阻塞隔離
適合程序即將結束、必須在退出前完成的最後一次寫入I/O 重、CPU 輕的常態寫入量測證明 CPU 工作超過畫面預算，或需要與崩潰隔離

fs.promises 優化的是「用最少的新機制消除阻塞」。它接受的代價是 CPU 工作仍在主執行緒，所以必須靠上限與量測來守住這個代價。相較之下 worker 優化的是隔離，代價是整套生命週期；在工作只有幾百 KB 的 JSON 時，這個代價買不到任何使用者感受得到的東西。

邊界：什麼時候不該用

  • 關機路徑。程序退出時，事件迴圈可能不再等待尚未完成的 promise。如果某次寫入一定要在退出前完成，同步版本反而正確，這正是 writeFileAtomicSync 被保留並註明「用於 App 關閉期間也必須完成的寫入」的原因。正常退出時更好的做法是「有限時間等待非同步寫入完成，逾時就留在 App 並如實顯示還有什麼沒存」，而不是回頭用同步呼叫硬撐。
  • CPU 重的工作。解析大檔、影像編碼、壓縮。fs.promises 對這些沒有幫助，量測會直接告訴你該升級。
  • 需要崩潰隔離。如果某個原生模組可能讓整個程序當掉，worker 或子程序才有意義，而且那時隔離才是你真正要買的東西。

模式二：先寫意圖，再建立資源

成立的前提

  • 一個長時間操作會在磁碟上留下產物，例如暫存檔。
  • 程序可能在沒有任何通知的情況下死亡：強制結束、kill -9、斷電、核心崩潰。
  • 重新啟動後沒有人記得這個產物存在，而且不能靠掃描輸出資料夾來找：那是使用者的資料夾，裡面有其他檔案，可能在外接碟上，掃描既慢又會誤判。
  • 使用者需要被告知，而不是被自動修復：「上次沒有正常結束、這個檔案可能不完整、它在這裡」。

天真做法與它們的症狀

只在正常的終止事件記錄結果。當機時終止事件永遠不會到，暫存檔就靜靜留在資料夾裡，使用者以為那段錄影消失了。

啟動時掃描 *.recording.mp4。這會碰使用者的資料夾；遇到手動複製的檔案或其他 App 的同名檔會誤報；外接碟不在時什麼都判斷不了；而且每次啟動都要付掃描成本。

模型：意圖先落地，資源才存在

在建立資源之前，先把「我要做這件事」寫到一個私有位置，內容是操作 id、開始時間、資源路徑。每一種終止結果，成功與失敗都算，都刪除這筆紀錄。下次啟動時，任何還留著的紀錄就代表一個沒有結束的操作；把它轉成一筆使用者看得到的報告，然後刪除。

四個容易做錯的細節

  1. 順序：意圖在資源之前。如果先建暫存檔再寫意圖，中間那個瞬間當機就會留下一個沒有任何紀錄指名的檔案。反過來，意圖寫了但資源還沒建就當機，啟動時的報告會發現檔案不存在，標成「不明」。後者是可接受的假警報，前者是靜默的資料遺失。
  2. 輔助證據不能阻擋主要工作。意圖寫入失敗只記一次 log，錄影照常開始。這個紀錄存在的目的是多一層交代；如果它失敗反而讓使用者錄不了，就本末倒置了。
  3. 每個操作一份，用 id 當檔名。兩個操作同時進行時（模式三會讓這件事發生），A 刪自己的檔、B 寫自己的檔，不需要對同一個檔案做讀改寫，也不需要鎖。在只有一個操作的今天，這個決定看起來多餘；但它讓後來加入並行時不必改格式、不必寫升級程式。
  4. 確定只有你一個活著。留下的紀錄有可能屬於另一個還活著的同程式實例。RecordStuff 用 app.requestSingleInstanceLock() 保證第二個實例根本啟動不了，所以殘留紀錄一定屬於已死的程序。沒有這個保證時，紀錄要帶 pid，啟動時要先確認那個程序不在了。

這個模式的親戚，以及邊界

資料庫的 write-ahead log、工作佇列的 claimed 或 leased 標記、安裝程式的 pending-operation 檔案，形狀都相同：先寫意圖，再做有副作用的事，完成後清除。你在別的系統看到「先記一筆再動手」，通常就是這個模式。

不需要它的情況：

  • 產物只在你私有的暫存目錄裡，掃描便宜又不會誤判。直接掃描就好。
  • 操作是冪等且可重跑的。下次啟動直接重做，不用報告。
  • 你真正需要的是自動復原，例如把半截的 MP4 修好。這個模式只提供「知道發生了」；復原是另一個問題，需要另一套機制與另一套證據，不要把兩件事混在一起承諾。

在本專案的應用

RecordStuff 的計畫 038 把這個模式命名為「中斷哨兵」：每次錄影開始前，在 userData 的專用目錄寫一個以 session id 為檔名的小檔案，用的就是模式一提到的 writeFileAtomic。啟動時殘留的哨兵各轉成一筆失敗歷史，文案是「App 在錄影中未正常結束、檔案可能不完整」，並沿用既有的還原檢查：路徑上的檔案還在就標成「部分保留」並可在 Finder 定位，不在就標成「不明」。它明確不做的事是修復檔案與掃描資料夾。

模式三：用 promise 鏈做有上限的並行

成立的前提

  • 多個長操作可能重疊：A 在發布，B 想開始。
  • 它們共用資源：磁碟頻寬、獨占的目的檔名、記憶體中等待寫入的資料。
  • 你想要一定程度的並行，不想讓使用者等 A 發布完才能錄 B；但不要無上限，不想把 C、D、E 都排進去吃記憶體。
  • 只有一條執行緒。

天真做法與它們的症狀

完全不管：A 發布中直接讓 B 開始，B 停止時也直接發布。兩個大檔同時往慢碟複製，兩邊都變慢，B 的即時分片開始積壓在記憶體裡。

無上限佇列：所有停止的錄影都排隊發布。慢碟上佇列愈排愈長，記憶體跟著長，而使用者以為每一段都存好了。

開執行緒做發布：發布本來就是 fs.promises 的非同步操作，不需要執行緒。RecordStuff 的計畫草稿曾寫「一個 publication worker」，意思是「一次做一件」，但讀者很容易把它讀成「開一個 worker 執行緒」，於是模式一裡拒絕的複雜度就從後門回來了。用字要能區分「一次一件」和「一條執行緒」。

模型：佇列就是一條 promise 鏈

在單執行緒環境裡，「一次只做一件、依序執行」最小的實作是一條不斷延長的 promise 鏈。RecordStuff 的 FileWriter 已經用它來排序媒體分片的寫入，節錄如下：

TypeScriptprivate queue: Promise<void> = Promise.resolve();
private failure: FileWriteError | undefined;

private enqueue(task: () => Promise<unknown>): Promise<void> {
  const run = this.queue.then(async () => {
    // 第一個錯誤之後，後面的工作不再碰磁碟
    if (this.failure) throw this.failure;
    try {
      await task();
    } catch (cause) {
      this.failure = toFileWriteError(cause);
      throw this.failure;
    }
  });
  // 即使呼叫端忽略 rejection，鏈也要活著
  this.queue = run.catch(() => undefined);
  return run;
}

每個 task 都接在前一個之後，所以順序有保證；第一個錯誤被閂住，後續工作直接以同一個錯誤失敗，不再對壞掉的檔案做任何事；鏈的尾端永遠吞掉 rejection，所以一次失敗不會讓整條鏈變成永遠 rejected。這裡沒有執行緒、沒有鎖、沒有佇列資料結構，只有一個 promise 變數。

計畫 037 把同一個形狀套到發布上：同一時間只有一個發布工作。它和「不管」的差別在於明確的准入規則：

狀態規則
A 已停止、正在發布A 的擷取資源在排空、flush、close 之後釋放；此時 B 可以開始擷取
B 停止時 A 還沒發布完B 安全封存（flush、close），排在 A 之後；不丟棄 B，也不同時複製兩個檔案
B 封存中，C 要求開始拒絕，並明確顯示「正在等待存檔」；上限是一段擷取中加一段收尾中
磁碟餘裕不足或寫入積壓過高不准入，理由可見；非同步排程不會增加磁碟吞吐量

還有一個和佇列同樣重要的原則：每次操作有自己的擁有權與終止結果。A 有自己的 id、自己的暫存路徑、自己的成功或失敗；一個晚到的 A 事件，例如延遲抵達的停止訊息，不能因為此時正在錄 B 就被套到 B 身上。實作上就是每個訊息帶 session id，收到時比對，不符就丟掉並記 log。這和模式二的「每個操作一份」是同一個思路：並行一旦出現，任何共用的、單一的東西都會變成錯誤歸屬的來源。

與模式二的交互

A 的意圖紀錄要留到 A 自己的終止結果，也就是發布成功或失敗，才能刪除。如果實作者把「A 停止擷取」當成刪除時機，那麼 A 發布途中當機時，下次啟動只看得到 B 的紀錄，A 那個可能不完整的檔案就沒人交代。這是為什麼計畫 037 要明寫「每次錄影保有自己的哨兵直到自己的終止結果」，即使這句話在 038 的設計裡看起來是理所當然的。

邊界與替代方案

  • 工作是 CPU 重的：promise 鏈仍在主執行緒上執行 task，這時需要執行緒或子程序，回到模式一的量測。
  • 佇列要跨程序重啟仍然存在：promise 鏈只活在記憶體裡，需要持久化佇列。持久化佇列的第一步就是先把工作寫到磁碟，也就是回到模式二。
  • 只需要限制併發數，工作彼此獨立：一個小型 limiter 就夠了，promise 鏈是 limit 等於 1 的特例。它的優點是順序保證與第一錯誤閂鎖，缺點是沒有優先權，插不了隊。

三個模式共同的判斷準則

換到另一個程式碼庫時，用這幾個問題判斷前提是否還成立：

先問如果答案是選擇
這項工作的等待在磁碟還是 CPU？磁碟fs.promises，不要執行緒
CPU，而且量測超過畫面預算worker_threads，並把量測數字留在文件裡
這是程序退出前的最後一次寫入嗎？是同步版本，或有限時間等待後如實顯示未完成
程序死掉後，有人需要知道這個產物嗎？需要，而且不能掃描先寫意圖再建資源；每個操作一份；每種終止都清除
多個長操作會重疊嗎？會promise 鏈加明確上限與可見的拒絕理由；每次操作有自己的 id 與終止結果
重疊的操作各自有磁碟產物嗎？有意圖紀錄留到各自的終止結果才刪

三個模式背後只有一個原則：每一層機制都要能指出它解決的具體失敗。執行緒解決的是 CPU 阻塞，不是磁碟阻塞；意圖紀錄解決的是「當機後沒人知道」，不是「當機後自動修好」；promise 鏈解決的是順序與上限，不是吞吐量。當你說不出一個機制對應哪個失敗，它就是多餘的，而多餘的機制在長期維護裡會變成新的失敗來源。

本專案的現況。模式一已於 2026-09-25 由計畫 036 實作：失敗歷史改用 fs.promises 與既有的 writeFileAtomic。量測最大允許的 32 MiB 快照時，整份序列化約 40 ms，超過畫面預算；但把快照交給 worker 所需的 structured clone 在主執行緒上也要相近的時間，所以改為逐筆快取序列化結果，並在累積約 8 ms 工作後讓出事件迴圈，寫入時單一 turn 最長約 10 ms；只有啟動時一次 JSON.parse 在上限約 38 ms。模式二已於 2026-09-25 由計畫 038 實作：每次錄影在建立暫存檔前先寫入自己的中斷哨兵。模式三的重疊收尾沒有實作：計畫 037 於 2026-09-27 在量測門檻結案，實測的等待幾乎都是發布時的整檔複製，改用硬連結發布後已沒有值得重疊的等待，所以 Recorder 仍在 stopping 狀態拒絕新的開始。本文說明的是設計理由與前提，不是目前行為；目前行為以 docs/system-design/ 為準。
