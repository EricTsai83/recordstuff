## Goal and product gate

Make future recordings editable after capture (cursor, zoom and optional camera placement), while ordinary direct MP4 stays the default. **D1 — whether and in what scope**, taken by the maintainer only after 085 is in use, from a prototype's measured costs: the extra encoders, disk writes, CPU and the permissions mouse events need. Old flattened recordings cannot recover camera or clean-screen pixels and are not promised to. Styling (backgrounds, padding, corners, shadows, output shapes), removed with 086, stays out of scope; the scene model below leaves room for it.

## Steps and ownership

- [ ] **Prototype the cost first.** An explicit editable-capture option, off by default, captures clean screen video, an optional separate camera and independent system and microphone tracks on a common media clock, with offsets, pause/stop rules and loss metadata, reusing the engine's encoders and muxer. Measure it before building UI; do not also encode a flattened MP4 unless the budget and D1 allow it, since the rendered export below makes one on demand.
- [ ] **Mouse events, opt-in and bounded.** Position, clicks and cursor shape in bounded, chunked sidecars, with the coordinate transforms and bounds changes needed for high-DPI and multi-display alignment; missing events degrade to a standard cursor and no automatic zoom. No keyboard logging, typing detection, passwords or window titles. The permission each platform needs is documented from the API actually used and tested, and asked for in context; a failed logger disables the enhancement, never screen capture, and never switches recording mode silently.
- [ ] **A small pure scene model** (from 086) in Rust: from the edit's revision, a rational media time and an output size it returns the render parameters (the zoom's crop, the cursor, the camera's place). Time stays integer/rational to the platform boundary and is never advanced by UI frame deltas; coordinate spaces, rounding, aspect and crop are defined once; colour is BT.709 with its range carried through. It reuses `camera_layout`'s math rather than copying it, holds no capture clock or OS handle, and is checked by deterministic fixtures replayed forward, backward and in random order.
- [ ] **Automatic zoom in that model.** Click-based zoom targets with bounded scale and speed, edge clamping and time-evaluated springs that are independent of seek and call order; observed events kept apart from editable zoom keyframes. A small zoom inspector in 085's edit view with manual adjustment, disable/reset and bounded undo; no full non-linear timeline or plugin system.
- [ ] **Rendered preview and export** (from 086) in 085's export worker, on the existing WGSL compositor that already runs on Metal and Direct3D 11 (plan 075); wgpu is reconsidered only if multipass rendering the kernel cannot do becomes necessary, after measuring its cost. Preview: rendered on demand and while playing at the Studio's preview rate, sent over the existing encoded preview transport with 084's bounds, a generation per seek. Audio: the system and microphone tracks are decoded, placed on the common media clock by their offsets (a dropout is silence, never a shift), cut with 085's sample-exact rule and faded joins, mixed by the engine's existing mixer with the per-input volumes the Studio set (plans 074 and 075), and encoded to one AAC track; the preview plays the same mix, so what is heard while editing is what is exported, and no player is relied on to mix separate tracks. Export: hardware decode → scene render → hardware H.264 encode → mux, with finite frame and byte queues and backpressure; without hardware support the export is refused with a reason. Publication, cancellation, admission (recording always wins) and quit follow 085 unchanged; a job is bound to one edit revision.
- [ ] **Multi-track recovery.** 085's edit state and export worker extend to a session of several files: one session owner, per-track size and backlog limits, an aggregate disk-space policy, the manifest committed last and recovery metadata written incrementally (never rewriting a growing JSON array per event). After a worker's death the recoverable screen fragments are kept and missing camera, microphone and time gaps marked; disk exhaustion ends the media safely under the existing outcome contract.

## Gates and verification

Before implementation freeze ceilings against the pipeline baseline on the reference machine. Proposed for the prototype: total app CPU at most 1.5× the direct mode's with the same camera and audio inputs, at most 256 MiB more resident memory, and queues bounded independently of the take's length; disk amplification reported per track. These are proposed product budgets, not evidence. If exceeded, reduce the tracks or resolution or stop at D1; never loosen the default recording's budget.

The default mode stays within the baseline's spread and its cadence and sync budgets. The editable mode meets the existing sync and cadence criteria on every enabled track, with `pnpm matrix -- long` since several clocks can drift. Scene parameters match within stated tolerances in every replay order, and preview and export render the same frame at the same media time within tolerances declared before testing (no UI pixel baselines). The rendered export of a frozen 1080p30 reference runs at least in real time on the reference Mac with queue memory independent of length and cancel within 2 s at p95; decode, render, encoder wait and write are reported apart, and no speed gain may come from lower fidelity. On a fixture with distinct tones in the system and microphone tracks, both stay audible in the export and in sync with the picture across every cut, including a microphone dropout. Event fixtures cover pause boundaries, rotation and DPI, window movement where supported, cursor loss and random seeks; checks cover chunk bounds, the absence of keyboard data, camera and microphone dropout and recovery after process death, then edit → export → native playback. Permissions follow the existing hands-on boundaries; TCC is never reset automatically.

Broad capture, storage, UI and lifecycle integration requires `pnpm check`, the final `pnpm acceptance:regression`, a fresh signed recording with media verification and playback, the affected capture-settings, Studio and lifecycle cases, the CPU comparison and the relevant matrix including `long`. Windows CI checks contracts and build only; untested hardware behaviour is listed. Close with the recovery, format and privacy documentation and bilingual help, failed experiments kept, probes removed and durable decisions updated.
