## Purpose and boundary

Recording begins about 0.3 seconds after the click or shortcut: `starting → recording` took 318 ms in the [2026-09-25 hotkey round](../docs/verification/measurements/2026-09-25T08-32-13-558Z-hotkey-acceptance/report.md). The first frames therefore show the pointer leaving the menu bar, and RecordStuff has no editor to trim them. This plan adds a short countdown before capture and gives every tray state its own icon, so idle, preparing/saving, countdown and recording can be told apart at a glance. It adds no start sound, full-screen overlay, pause, editor, per-entry-point behavior or new recording format.

Maintainer decisions (2026-09-25, from the discussion and static HTML drafts that are not repository artifacts):

- The countdown defaults to 3 seconds; Settings → Recording offers Off, 3, 5 and 10 seconds. The default also applies to existing users: a settings file without the field reads as 3 seconds.
- Only a highly transparent digit (3, 2, 1) appears at the top-right of the recorded display, drawn directly over the screen with no box, background or border (maintainer follow-up the same day). No ring, text, cancel hint, sound or full-screen dimming.
- Tray icons: idle keeps the ring; preparing and saving use an hourglass, replacing the ring plus `…` title (a ring with three small dots inside was tried first and rejected as too faint at menu-bar size); the countdown uses a stopwatch with no title, because the corner already shows the digits; recording keeps the filled dot plus `REC`. Every icon is the same 16 pt template image, so only `REC` changes the item width.
- The countdown is cancelled by left-clicking the tray icon, the recording shortcut, the tray menu's Cancel countdown item, or Quit. A cancel is not a failure.

Owners: [Recorder](../src/main/recorder.ts), [protocol](../src/shared/protocol.ts), [renderer capture host](../src/renderer/capture-host.ts), [main capture host](../src/main/capture-host.ts), a new countdown overlay (main-owned window, renderer page and preload), [tray model](../src/main/tray-model.ts), [tray](../src/main/tray.ts), [settings](../src/main/settings.ts), [settings model](../src/main/settings-model.ts), [translations](../src/shared/i18n.ts), [app wiring](../src/main/index.ts), [autorecord](../src/main/autorecord.ts), the [icon generator](../scripts/make-icons.mjs), affected acceptance runners, and their tests. Keep every timing and appearance value in one shared module with a stated initial target; tune only with written evidence.

- The Chrome extension overlay [leaves 140 ms before capture with a 220 ms fade](https://github.com/CapSoftware/Cap/blob/119edf04864b59abfc0d52f60bf77d7f33cfd2b8/apps/chrome-extension/src/content/countdown-overlay.tsx#L10-L16), because the tail of the count otherwise lands in the first frames.
- Cap [arms the gate after its start sound leaves the device](https://github.com/CapSoftware/Cap/blob/119edf04864b59abfc0d52f60bf77d7f33cfd2b8/apps/desktop/src-tauri/src/recording_start_sound.rs#L5-L14) and on macOS [does not apply native content protection to its recording controls](https://github.com/CapSoftware/Cap/blob/119edf04864b59abfc0d52f60bf77d7f33cfd2b8/apps/desktop/src-tauri/src/windows.rs#L3793-L3795).

Adopted: the default and choices, preparing capture before the count and starting it at zero, removing the overlay before capture, and a cancellable countdown. Not adopted: a start sound (RecordStuff records system audio, and whether `restrictOwnAudio` excludes the app's own sounds is unverified), a frame-discarding gate (`MediaRecorder.start()` is the gate here), a full-screen overlay, and content protection (`getDisplayMedia` offers no per-window exclusion; separation in time is the protection).

## Implementation contract

- [ ] **Start sequence.** A toggle from idle enters `starting` with the busy icon; preflight, the folder probe and the exclusive temporary file are unchanged. The filename keeps the local time of the start request, so with a countdown it precedes the first frame by preparation plus the countdown; document that. Main sends `start`; the renderer requests the stream, validates audio, measures frames, applies quality, rechecks track liveness, constructs an inactive MediaRecorder and replies `prepared` with its CaptureReport. The existing 120-second capture-request deadline now bounds `start → prepared`, so permission prompts, missing audio, unsupported MP4 and display errors surface before any countdown. With the countdown Off, main sends `record` at once. Otherwise Recorder enters `countdown`, shows the overlay and ticks once per second from one monotonic anchor, never accumulating timer drift. At N seconds minus the overlay lead (initial target 300 ms) it asks the overlay to dismiss and awaits confirmation within a bound (initial target 500 ms; on timeout destroy the window, log it and continue). It sends `record` at N seconds, or when the dismissal settles if that is later. The renderer calls `recorder.start(CHUNK_INTERVAL_MS)` and replies `started`. Recorder enters `recording`, emits `captureStarted` with the stored report, and arms the first-media deadline and 038's stall timer exactly as today; `record → started` uses the 8-second start deadline. REC appears only after capture began, so the first frames may show the stopwatch in the menu bar, as they show `…` today; the countdown digit must not appear in them.
- [ ] **Cancel.** A toggle, the Cancel countdown item or the shortcut before `record` is sent cancels the attempt: clear its timers, stop the host, dismiss the overlay, abandon the writer so the empty temporary file is removed, return to the idle state that existed before the attempt (keeping `lastSavedPath`), and emit a `cancelled` event with its reason plus a log line. Emit no `failureStatus`, failure-history entry, notification or display diagnostic. After `record` is sent, a toggle is a stop request applied once `started` arrives (the existing `stopOnStart`), so a race of a few milliseconds cannot leave capture running. Clicks during `starting` and `stopping` stay ignored.
- [ ] **Quit.** Quit during the countdown cancels it immediately. Quit during opening or preparation marks the attempt, so `prepared` cancels it instead of counting down or recording. This replaces the current rule that a starting session records and then saves: no media existed yet, for every countdown setting. The quit coordinator's other safety conditions are unchanged; update the recording and desktop design text that describes the old rule.
- [ ] **Failures before capture.** Track end, display removal, a crashed or unresponsive host and a refused or timed-out `record` during preparation or countdown are start failures: `capture_start_failed` with a detail naming the phase, the display diagnostic still emitted, and an empty outcome. Keep 038's rule that a disk error the writer already retained is reported with its own code. A stale `prepared` or `started` for a detached session triggers a host stop, as the existing stale rule does.
- [ ] **State and protocol.** `RecordingState` adds `{ type: "countdown"; remaining: number }`, where `remaining` is at least 1 and is kept through the `record → started` gap. Each tick re-emits the state, and the app logs `state → countdown (n)`. `MainMessage` adds `record { sessionId }`; `HostMessage` adds `prepared { sessionId, mimeType, capture }`, and `started` may drop its report; update the guards and their tests. The renderer holds a prepared session (live stream, inactive recorder): `stop` releases its tracks and replies `stopped`, a track `ended` replies an error, and `record` for any other session is refused. The session snapshot adds `countdownSeconds`, read once like quality. Recorder stays free of Electron: inject a countdown presenter with `show(remaining)`, `update(remaining)` and `dismiss(): Promise<void>`. Presenter errors are logged and never fail a recording; the tray still shows the countdown. Audit every consumer of the state type and treat `countdown` as an in-flight session: the settings lock, the display-media answer, the hotkey and update flushes, saved-notification cancellation, the output-folder guard (which does not cover `starting` today either), host destruction when settled, and autorecord.
- [ ] **Countdown overlay.** A main-owned window created during preparation and destroyed when the countdown ends, is cancelled or fails; none remains between recordings, and the app destroys it again on any settled state as a safety net. It is transparent, frameless, fixed in size and position, shadowless, absent from the taskbar, not focusable, shown inactive (prefer a non-activating panel on macOS), ignores mouse events, and sits above normal windows and full-screen apps (`screen-saver` level, visible on full-screen Spaces). It must never activate RecordStuff or take keyboard focus from the frontmost app. Place it on the display DisplayMedia resolved for the session (the primary display, logged, when that is unknown): an 88 × 88 pt fully transparent window, 16 pt from the right edge of the work area and 12 pt below its top, that draws only the digit: no background, box, border, ring or blur. Because nothing sits behind the digit, its own outline and shadow carry legibility over white as well as dark content. Initial appearance: SF Pro Rounded semibold 56 pt, tabular, centred, white at 28% alpha, a 1 px outline of black at 10%, and shadows `0 0 1px` black 20%, `0 1px 3px` black 14% and `0 0 14px` black 8%. The maintainer compared drafts at 80%, 55%, 40% and 28% and chose the most transparent one, accepting that it fades on bright photos; N32 judges it on the real app. Motion: 120 ms fade-in, 150 ms crossfade between digits, and a 120 ms fade-out that finishes before the window hides; `prefers-reduced-motion` removes the fades, and `prefers-reduced-transparency` makes the digit opaque and strengthens its outline, still without a background. The page is local, sandboxed, context-isolated, uses the settings page's CSP, and has a preload exposing only a value subscription; main sends values and the page only renders them. Add its renderer and preload build entries. No content protection is applied.
- [ ] **Tray.** `TrayIcon` adds `busy` and `countdown`. `starting` and `stopping` use `busy` with an empty title and their existing tooltip and menu text. `countdown` uses the stopwatch with an empty title, a tooltip saying recording starts in n seconds and a click cancels, and a menu with a disabled status line, Cancel countdown (its tooltip names the shortcut when registered) and the usual footer. idle, needsPermission and recording are unchanged; the warning badge still replaces only the idle ring. The generator adds macOS templates at 16 and 32 px: busy is an hourglass outline, with bars across the top and bottom (x 0.22–0.78 of the size, y 0.10–0.19 and 0.81–0.90) joined by two strokes 0.09 wide that narrow to a waist 0.07 wide at the centre; the stopwatch is a ring centred at y 0.56 with radii 0.31/0.20, a crown at x 0.40–0.60 and y 0.05–0.14, a stem at x 0.46–0.54 and y 0.13–0.27, a hand at x 0.46–0.54 and y 0.40–0.56, and a hub of radius 0.07. Windows ICOs in the existing gray at 16, 24, 32 and 48 px keep the states distinct there; 034 redesigns Windows artwork and this plan claims no Windows appearance. Generation stays deterministic and leaves every other asset byte-identical.
- [ ] **Settings.** `Settings.countdown` is `0 | 3 | 5 | 10`, read leniently: missing reads as 3 and invalid reads as 3 with a warning, with no version bump. Settings → Recording adds a Countdown group after Screen, a segmented control (Off / 3 s / 5 s / 10 s) with a note explaining that the digits appear at the top-right of the recorded screen and that clicking the menu bar icon or pressing the shortcut cancels. It is locked during sessions like the other recording settings. Add the `setCountdown` action and the tray action `cancelCountdown`. Provide English and Traditional Chinese text for the group, choices, note, tray status line, tooltip and menu item.
- [ ] **Development and acceptance tooling.** Autorecord uses countdown 0 in memory unless its configuration names one, so the matrix and audio-quality runs keep their timing. Every runner that starts a real recording either seeds the countdown explicitly in its isolated or restored settings or waits for it deliberately; none may absorb it into a latency threshold. `pnpm acceptance` uses the real settings: it reports preparation latency, countdown ticks and `record → started` separately, and gains a cancel case (a second press cancels, with no file and no failure entry). The notification and update runners seed 0 and restore. The lifecycle fixture's host supports prepare and record. The countdown round saves crops of the digit region from the first 15 frames to its report; when the test material keeps that region static, it also compares them with the same crop two seconds later against a stated threshold.
- [ ] **Documentation and website.** Update in both languages: the recording design (state diagram, start steps, deadlines table, terminal ownership and quit), the desktop design (tray state table with the new icons, overlay, settings), the product overview (status row), the architecture, function and repository references for the new window and module, the tooling guide (autorecord and runners), the acceptance guide (countdown cases), and a design decision recording the default, presentation and exclusions above. The English website's how-it-works steps, hero story and help text describe an immediate REC after one click; update them to show the stopwatch and corner digits before REC, and state how to cancel.

## Verification and exclusions

- [ ] Recorder tests with an injected clock and fake host: the Off path; ticks at anchor times; `record` sent only after dismissal or its bound; cancelling through toggle, menu and quit before `record`; a toggle after `record` stopping on start; quit during preparation cancelling at `prepared`; failure codes and empty outcomes during preparation and countdown; no failure status on cancel; `lastSavedPath` retained; stale messages; the countdown snapshot. Renderer tests for the prepare/record split, stop while prepared, track end while prepared and a refused `record`. Protocol guards; tray states, icons, titles, menus and warning precedence; settings parsing (missing, invalid, each value), group, lock and actions; translation coverage; overlay placement from a work area, window options and destruction on every path through a fake window; generator dimensions and determinism; autorecord defaulting to 0. Assert real events, files and window calls, not only call counts.
- [ ] `pnpm acceptance:regression` (settings changed; includes `pnpm check`) and inspection of the Settings screenshots in both languages.
- [ ] On a fresh `pnpm start:app` bundle: the default 3 seconds through the shortcut runner and one tray click; Off; 10 seconds once (two digits); cancel by a second press. Media verification and playback for each saved file, the digit-region crops, and logged timings (preparation, each tick, dismissal to `record`, `record` to `started`, `started` to first chunk).
- [ ] Native checks the agent can observe, through the [native acceptance skill](../.agents/skills/astra-acceptance-with-computer-use/SKILL.md): tray icons on light and dark menu bars with unchanged width, digit position and legibility, Cancel countdown in the menu, and keyboard focus kept by a text editor while the countdown runs. Cases that need the maintainer's judgment or hardware are 035's N32–N35.
- [ ] `pnpm site:check` and inspection of the changed pages.
- [ ] Exclusions: quality and audio matrices (MediaRecorder options and encoding are unchanged), long recordings, permission resets (the capture request is unchanged; only what follows it moves), and Windows native appearance (034). VoiceOver does not reliably announce a window that cannot take focus; record what it does in 035 rather than claim support.
