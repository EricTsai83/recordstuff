## 順序與狀態

目前順序：063 → 064。每個計畫都完整做完、寫好結案紀錄後，才開始下一個；不會兩個計畫同時進行，也不會做到一半就換。計畫內的決定點會讓該計畫暫停，等維護者回答後，同一個計畫繼續或結案：063 步驟 2 決定是否允許腳本操作 RecordStuff 自己的 UI（拒絕時，063 完成文件步驟後結案）；064 步驟 1 決定 Windows 硬體、安裝方式、簽章與發布綁定（沒有 Windows 機器或拒絕時，064 記錄後結案或延後）。063 寫明何時用 runner、何時用 Computer Use，核准後再加入 tray、設定與通知 runner。064 加入 Windows 建置、驗證與發布；它排最後，因為它要在已結案的 062 之後修改 `scripts/start-app.mjs`、用 063 的 runner 複驗 macOS tray 文案，最後還要推 tag 發布。已延後、不在佇列內：058 → 059 → 060。061 量測到兩個設定 fixture 是 check 後最大的成本，每次設定修改 93 秒，但所有案例都通過，也沒有觀察到診斷問題。此鏈只在維護者選擇時恢復，時機是佇列完成後或兩個計畫之間，從 058 的步驟 0 量測門檻開始；該門檻也可能以在現有 driver 修正等待的方式結案 058，並取消 059–060。來自簽章 A/B/A 對照、依維護者要求排入的完整簽章通知驗收 fixture 062 已於 2026-10-02 結案：`pnpm acceptance:quit-dialog` 現在啟動每輪完整簽署並驗證的 Electron.app 副本，identity 缺少時不啟動（blocked），簽章失敗時也不啟動（fail），並分開回報簽章 App、生命週期、送達事件、視覺觀察與清理；兩種語言都已送達，其紀錄保留英文橫幅被截斷、未看到完整文字的部分。依維護者要求進行的 check 後驗收最佳化 061 已於 2026-10-02 結案：`pnpm acceptance:recipe` 以一次建置跑完組合檢查並寫出分段計時報告，`pnpm open:app` 現在會拒絕過期的 bundle，因此只改測試、腳本或文件後的下一輪可在 0.66 秒內重開已驗證的 bundle，不必花約 38 秒重建；其紀錄保留未量測的原生入口與 agent 區間，以及量測中發現並修正的 hotkey runner 競態。設定 fixture 視窗失去啟用時的結果判定 057，來自 2026-09-30 的 20 項稽核、依維護者要求排入，已於 2026-09-30 結案：視窗被其他 App 取消啟用的案例現在標為未執行、該輪為 blocked（exit 2），截圖失敗時也保留已記錄的案例；其紀錄保留只由單元測試涵蓋的實際回合截圖失敗。處理仍可能遇到進行中錄影的對話框與看不到的延後退出的 056，來自 055 的剩餘風險、依維護者要求排入，已於 2026-09-29 結案：未捕捉例外對話框與儲存位置警告現在會等待或避開未完成的媒體工作，延後退出也會在 tray 說明；其紀錄保留只由單元測試涵蓋的錄影中儲存位置通知。會讓 main process 停擺的原生對話框 055，發現於 2026-09-29 20 項稽核的錄影回合，已於 2026-09-29 結案：無視窗的訊息框會卡住 main 直到關閉，因此延後退出提示改為通知；其紀錄保留了開發用 Electron 無權顯示的隔離 fixture 橫幅。補完 053 未能完成的原生檢查、並加入該次稽核兩項快捷鍵 runner 修正與兩項原生觀察的 054，已於 2026-09-29 結案，所有原生檢查都通過、App 沒有變更；其紀錄保留無法製造的快捷鍵衝突橫幅，以及因沒有合適螢幕而未執行的 1080p 通知。053 承接 2026-09-29 第三輪稽核在其修正 `ba8b651`…`4740520` 之外留下的六項，在它之前結案；053 又在承接 2026-09-29 第二輪稽核中 runner 那一組的 052 之後（該輪 20 項 App、發布工具與網站修正為 `ea86b99`…`7f1f3a8`）。錄影時保持喚醒、睡眠時存檔的 050 已於 2026-09-28 結案（[紀錄](../docs/zh-TW/verification/history-2026-09.md#plan-050-保持喚醒與睡眠時停止--2026-09-28)），在最後的逐步原生驗收 035 之後（[結案紀錄](../docs/zh-TW/verification/history-2026-09.md#plan-035-結案--2026-09-28)）。
