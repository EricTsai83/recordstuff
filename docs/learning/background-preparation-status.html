背景準備中的檔案，狀態怎麼顯示才不會閃：先問、延遲加最短顯示、不倒退的進度

當一個面板打開時才開始在背景準備檔案，而這些工作有的 0.2 秒就做好、有的要好幾分鐘，「準備中」這個狀態很容易在畫面上閃一下、跳來跳去，或者把使用者的選取擠掉。這篇說明四個彼此配合的做法，每個做法對應哪一種閃爍，以及什麼情況下不該這樣做。

情境：打開面板，背景開始準備

想像一個錄影 App 的「分享」面板。使用者在一段錄影上按「分享…」，面板從卡片的位置飛到畫面中央，列出可以拿走的檔案：完成的影片、只有聲音、原始檔。這些檔案不一定已經存在，App 會在面板打開時把缺的檔案準備起來，讓使用者按下「拷貝」時不用等。

這個模式要處理的前提有五個，缺一個，後面的取捨就會不同：

  • 狀態由另一方擁有。工作佇列在主程序（或伺服器），畫面只能透過訊息得知「誰在準備、做到多少」。畫面打開的那一刻，手上不一定有最新的狀態。
  • 工作長短差很多。只是複製一條聲音軌約 0.1–0.3 秒；重新算繪一段剪輯過的影片要幾秒到幾分鐘。打開的那一刻，畫面不知道會是哪一種。
  • 工作之間有相依。「只有聲音」是從做好的影片裡複製出來的，所以它得等影片做完。
  • 選取是使用者自己的狀態。影片預設被選取（打勾），這和它有沒有做好無關。
  • 同一個狀態出現在好幾處。每個檔案的圖示上有標記，面板底部還有一行說明文字。

天真的做法會怎麼壞

最直接的實作是：面板打開後才去問狀態，一收到「準備中」就顯示進度，做好就拿掉。在上面的前提下，使用者會看到這些症狀：

  • 狀態翻轉。面板先畫出來，這時還不知道影片沒做好，影片格顯示「已就緒」的打勾；幾百毫秒後狀態到了，才變成準備中。看起來像是 App 改口。
  • 一閃而過。0.2 秒就做好的聲音檔，進度提示出現一下又消失。使用者看不清楚它是什麼，只覺得畫面在閃。
  • 門檻邊緣的閃爍。如果只加「超過 0.5 秒才顯示」，那 0.55 秒做好的工作，提示會在 0.5 秒出現、0.55 秒消失，只露臉 50 毫秒。
  • 進度倒退。聲音在等影片時一直停在 0%，像是卡住；影片做完後聲音自己的複製又從 0% 開始，整條進度看起來跑了兩次。
  • 選取被擠掉。把進度畫在打勾的位置，準備中的影片就看不出被選取了；如果再加延遲，前半秒甚至什麼標記都沒有。

心智模型：三種資訊，各有主人和位置

這些症狀背後是同一件事：把三種不同的資訊混在一起。

資訊誰擁有放在畫面哪裡
真實狀態：準備中、做到多少、失敗了擁有工作佇列的一方從它那裡取得，畫面不自己猜
要不要現在顯示這個狀態畫面依時間決定：延遲與最短顯示
使用者選了哪個檔案使用者（畫面保存）自己的位置，不和進度共用

分開之後，每一種閃爍都有對應的修正：狀態翻轉是「真實狀態」來得太晚；一閃而過和門檻邊緣是「要不要顯示」沒有規則；選取被擠掉是兩種資訊搶同一個位置；進度倒退則是擁有者回報的數字本身不連續。

四個做法，各自修哪一種問題

1. 打開之前先問，但等待要有上限

面板動畫開始前，先向擁有狀態的一方要一次最新狀態，拿到後才畫出面板。對方在回覆前就把缺的檔案排進佇列，所以回覆裡缺的檔案已經是「準備中」。面板一出現就是正確狀態，不會再從打勾翻成準備中。

這一步會延後打開，所以等待一定要有上限。查詢本身很便宜（讀檔頭和檔尾算出指紋，約幾毫秒），但對方可能正忙著別的事，例如搬移檔案。超過 150 毫秒沒回覆就照常打開，狀態等下一次推送再補上。等待期間情境也可能改變，所以開始動畫前要再確認一次：還在同一個分頁、那張卡片也還在畫面上。

TypeScriptexport async function openShare(id: string): Promise<void> {
  if (opening) return;
  opening = id;
  try {
    // 先問擁有狀態的一方：它會開始準備缺的檔案，並回覆每個檔案現在的狀態
    const answered = settings.choose(`recordingShare:${id}`, { action: "open" }).then((r) => r.view, () => undefined);
    const answer = await Promise.race([answered, delay(150)]); // 最多等 150 毫秒
    if (answer) render(answer);
    // 等待期間情境可能變了：換了分頁、卡片被篩掉。這時就不打開
    if (selectedTab !== "library" || !document.getElementById(`clip-${id}`)) return;
    await morph(id, () => { sharing = { id, selected: ["video"] }; draw(); });
  } finally {
    opening = undefined;
  }
}

代價是：準備工作現在和打開動畫同時開始，不再等動畫結束。只有在擁有者推送進度的頻率有上限（這裡是每秒最多四次）、而且每次推送畫面只重畫有變動的部分時，這樣才不會讓動畫掉幀。

2. 延遲顯示，加上最短顯示時間

有了正確的狀態，下一個問題是何時顯示。這裡用兩個時間參數：

  • 延遲：開始準備滿 0.5 秒才顯示。延遲內就做好的工作，畫面上什麼都不會出現。
  • 最短顯示時間：提示一旦出現，就至少停留 0.5 秒。工作在這段期間做好，提示會以滿格停留到時間到才消失。

這兩個參數是業界常見的組合。React 常用的 spin-delay 套件預設延遲 500 毫秒、最短顯示 200 毫秒，並說明應該依實際延遲調整。Jakob Nielsen 的建議更保守：不到約 1 秒不必顯示任何提示，一旦顯示就至少留 0.5 秒，免得看起來像畫面出錯。延遲值不是憑感覺定的，要看你自己的工作分佈：這裡快速工作實測約 130–280 毫秒，0.5 秒留了餘裕，而真的要等的工作通常是好幾秒以上。

這些規則只靠 CSS 做不到。延遲可以用動畫的 animation-delay 模擬，但最短顯示時間需要在狀態結束後繼續保留元素，元素一移除就沒了。所以由元件自己記住「何時開始顯示」：

TypeScriptconst SHOW_AFTER_MS = 500;    // 超過才顯示
const SHOW_AT_LEAST_MS = 500; // 顯示後至少停留

/** active：真的在準備；since：何時被要求準備（epoch 毫秒）；cut：失敗了，要立刻讓位給失敗標記。 */
function useShownWhile(active: boolean, { since, cut = false }: { since?: number; cut?: boolean } = {}): boolean {
  const waited = () => since !== undefined && Date.now() - since >= SHOW_AFTER_MS;
  const shownAt = useRef(0);
  // 已經等超過門檻的工作，第一次 render 就顯示，不用等計時器
  const [shown, setShown] = useState(() => {
    const now = active && !cut && waited();
    if (now) shownAt.current = performance.now();
    return now;
  });
  useEffect(() => {
    if (cut) { setShown(false); return undefined; }
    if (active && !shown) {
      const wait = since === undefined ? SHOW_AFTER_MS : Math.max(0, since + SHOW_AFTER_MS - Date.now());
      const timer = setTimeout(() => { shownAt.current = performance.now(); setShown(true); }, wait);
      return () => clearTimeout(timer); // 延遲內就做好：計時器取消，什麼都不顯示
    }
    if (!active && shown) {
      const left = shownAt.current + SHOW_AT_LEAST_MS - performance.now();
      const timer = setTimeout(() => setShown(false), Math.max(0, left));
      return () => clearTimeout(timer); // 停留期間又開始準備：取消隱藏，繼續顯示
    }
    return undefined;
  }, [active, shown, cut, since]);
  return shown && !cut;
}

失敗是例外：檔案做不出來時，提示要立刻讓位給失敗標記，不能為了湊滿最短時間繼續顯示「準備中」。

延遲要從工作被要求的時間算起，而不是從畫面出現的時間。使用者打開面板時，有些工作可能已經排隊好一陣子了；如果從面板出現才開始計時，這些明顯要等的工作反而要再晚半秒才顯示。所以擁有工作佇列的一方會一併送出每個工作排進佇列的時間，已經等超過門檻的，面板第一幀就直接顯示。

給輔助技術的語意也要跟上：進度條用 role="progressbar" 並提供 aria-valuenow，螢幕閱讀器才會把它當成進度，而不是一張標籤不斷改變的圖。

3. 選取和進度各放一處

打勾表示「這是你選的」，進度表示「它還在做」，這兩件事會同時成立。把進度畫在打勾的位置，就得二選一：準備中的影片會看不出被選取；如果再加上延遲，前半秒甚至兩者都沒有。

做法是讓兩者各有位置：打勾留在圖示右上角，準備進度改成圖示下方的一條細進度條，就像 Finder 在複製中的檔案圖示下方畫的那條。這樣延遲和最短顯示可以只套用在進度條上，選取永遠看得到。

4. 相依工作的進度，由擁有者合成成不倒退的一條

「只有聲音」要等影片，它自己的工作只是最後一小段複製。如果照實回報，它會停在 0% 很久，影片做完後又從 0% 跑一次。修正放在擁有工作佇列的那一方，因為只有它知道誰在等誰：

TypeScriptconst SOUND_AFTER_VIDEO = 0.9; // 影片做完時，聲音的進度走到這裡

// 回報狀態時（擁有工作佇列的那一方）
const video = runningVideoOrQueuedVideo(source);
for (const job of queue) {
  if (job.kind === "sound" && video) report(job, video.progress * SOUND_AFTER_VIDEO); // 等影片：跟著影片走
  else report(job, job.progress);
}

// 影片做完的那一刻，排在後面的聲音直接走到 0.9，而不是掉回 0
onVideoMade(source, () => { for (const job of waitingSounds(source)) job.progress = SOUND_AFTER_VIDEO; });

// 聲音自己的複製步驟只占最後 10%
const copying = (fraction: number) => progress(SOUND_AFTER_VIDEO + (1 - SOUND_AFTER_VIDEO) * fraction);

把整段進度分成兩段：影片的部分占 90%，聲音自己的複製占最後 10%。這個比例不必精確，因為它只需要保證兩件事：進度一直往前，而且等待期間看得出在動。畫面那邊只負責顯示一個數字，不需要知道版本之間的相依關係。

補充：同一個狀態出現在幾處，就要用同一個時機

在實機測試時，進度條已經不閃了，但面板底部的說明文字還會閃：它一收到「準備中」就立刻換成「準備中 0%」，0.2 秒後又換回檔案的說明。凡是顯示同一個狀態的地方（圖示上的進度、說明文字、螢幕閱讀器的朗讀），都要套用同一個「要不要顯示」的判斷，否則閃爍只是換了位置。反過來，同一個數字也只需要出現在一處：進度條已經畫出做到多少，說明文字只要說「準備中，好了就能拷貝」，不必再跟著跳百分比，畫面上就不會有兩個數字同時在動。

隱藏的是提示，不是狀態。延遲期間檔案依然是「準備中」。使用者在這段期間嘗試的操作必須照真實狀態回應：準備中拖曳檔案時，拖曳需要在按下滑鼠的當下就拿到檔案，所以什麼都不會被拖出去，而且要立刻說明原因（「還在準備中，準備好之後才能拖曳」），不能因為提示還沒出現就沉默。

為什麼這是合理的預設

前提成立時（狀態在別處、工作長短差很多、快速工作佔多數），這組做法比較最常見的幾種替代方案：

做法快速工作慢速工作代價
立刻顯示閃一下立刻看到最常見的閃爍來源
只有延遲不閃晚 0.5 秒看到剛過門檻的會只露臉幾十毫秒
立刻顯示＋最短顯示出現一下再消失（不算閃，但多餘）立刻看到快速工作也會讓人以為要等
延遲＋最短顯示不顯示晚 0.5 秒看到慢速工作的提示晚一點出現
由擁有者依工作類型決定（算繪立刻顯示、複製不顯示）不顯示立刻看到擁有者要先知道工作類型，有時得讀完檔案描述才確定

「延遲＋最短顯示」不需要擁有者預測工作會多久，只靠畫面就能做到，而它付出的代價（慢速工作晚 0.5 秒出現提示）在有打勾和檔案說明撐著的情況下幾乎無感。如果慢速工作的提示晚出現會造成誤解，就值得再加上最後一種：由擁有者標記「確定要算繪」的工作，讓它立刻顯示。

什麼時候不該這樣做

  • 使用者明確按下按鈕、正在等結果時。按下「拷貝」後，按鈕應該立刻進入忙碌狀態，延遲的對象只是「使用者沒有在等的背景工作」。
  • 工作一定很慢時。例如固定要好幾分鐘的匯出，延遲只會讓回饋晚到，直接顯示即可。
  • 狀態本來就在畫面手上時。不需要跨程序查詢，就沒有「先問」這一步，狀態翻轉的問題也不存在。
  • 工作很快、但結果本身就會讓畫面改變時。例如搜尋結果出現，這時該處理的是結果的過渡，不是載入提示。
  • 先問的等待會讓操作明顯變慢時。如果查詢要走網路、常常超過 100–200 毫秒，先打開面板、再用骨架畫面或明確的「讀取中」，會比卡住使用者的點擊更好。

在 RecordStuff 的實作與結果

RecordStuff 是一個 macOS 選單列錄影 App，用 Electron 寫成。錄影檔分頁的「分享…」面板就是上面的例子：主程序擁有準備佇列與版本快取，設定頁的畫面透過 IPC 取得狀態，面板以 View Transition 從卡片飛到中央。

  • 先問：面板打開前送出一次查詢，最多等 150 毫秒。剪輯過、還沒快取的錄影，面板第一幀影片格就是準備中；原本是先打勾，約 300 毫秒後才翻成準備中。
  • 延遲＋最短顯示：都是 500 毫秒，從工作排進佇列的時間起算，進度條和底部說明共用同一個判斷。在使用者真實的 210 支錄影上，快速工作在 130–280 毫秒內做好，進度條存在的期間不透明度始終是 0，說明文字也沒有換過。
  • 進度不倒退：等待影片的聲音以影片進度的 90% 回報，影片做好時直接跳到 0.9，複製再走完最後 10%。單元測試會檢查每次回報的進度序列都是遞增的。
  • 選取與進度分開：打勾留在右上角，準備進度是圖示下方 3 像素高的進度條，只用 transform: scaleX 更新，不觸發排版。

判斷清單

在另一個程式碼庫遇到類似畫面時，可以依序問：

  1. 狀態由誰擁有？畫面打開的那一刻，手上的狀態可能過時嗎？如果會，能不能在畫出來之前先問一次，並給等待設上限？
  2. 工作時間的分佈長什麼樣子？快速工作是否佔多數、而且明顯短於某個門檻？
  3. 延遲和最短顯示是否都設了？用剛好超過門檻的工作想一遍，提示會不會只露臉幾十毫秒？
  4. 狀態出現在幾個地方？它們是否共用同一個「要不要顯示」的判斷？
  5. 選取、錯誤、進度是否各有自己的位置，還是有兩種資訊在搶同一處？
  6. 有相依的工作，進度是否由知道相依關係的一方合成，保證不倒退？
  7. 提示隱藏期間，使用者的操作是否仍照真實狀態回應，並說明原因？
