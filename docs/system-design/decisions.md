# Design Decisions

[English](decisions.md) | [繁體中文](../zh-TW/system-design/decisions.md)

These are adopted decisions, not a future-work checklist. Current code and measured results supersede assumptions from old execution plans.

| Decision | Rationale | Tradeoff or reconsideration trigger |
| --- | --- | --- |
| Electron and TypeScript for the app; media stays out of them (plan 076) | Desktop lifecycle, tray, Settings, the recorder's state machine and the file's lifecycle stay in one language with their tests; capture, encoding and writing moved to the native engine below | Electron resource cost. Moving the app itself is a separate decision (see Tauri below) |
| Native capture engine instead of Chromium's `getDisplayMedia` and `MediaRecorder` (plan 076; removed the Chromium path 2026-10-16; [why](webrtc.md)) | The trigger this table named, a measured limitation, was met: `getDisplayMedia` records one display or one window and can leave out only this app's protected windows; it cannot hide the menu bar or Dock, record an area or chosen apps, or one app's sound, which all need ScreenCaptureKit's `SCContentFilter` on macOS. Mature recorders (OBS, Cap, Screen Studio, CleanShot X) capture natively. Measured on the M1 Pro against Chromium (2026-10-15/16): recording CPU 10.4% / 14.0% of a core at 30 / 60 fps against 15.3% / 23.3%, flash-to-beep −25 ms against +68 to +74 ms, audio fidelity checks equal, and no renderer or audio service left idle after a recording | Frames 50 ms apart in 0.22–0.44% of a take against Chromium's none, cause not yet found (plan 078); start to `prepared` about 0.1 s slower, inside the countdown. Both accepted by the maintainer (2026-10-16). Sleep, display removal, permission denial and the Dock with D6 passed hands-on rounds on 2026-10-22 ([plan 077](../verification/history-2026-10.md#plan-077-closure--2026-10-22)). Reconsider only on a measured regression on these axes that the engine cannot fix |
| Capture runs in an Electron `utilityProcess`, one per attempt (076's D2) | A crash in native code ends that child, not the app: killing it mid-recording left an 8.0 s playable partial file, which main keeps, still fragmented under its temporary name, and reports the failure. It keeps the earlier shape, a capture process speaking `start`/`prepared`/`record`/`stop` over a `MessagePort`, so the recorder's states, deadlines and countdown stayed. Loading the module in main would let a native crash end the app; a separate executable would need proof that macOS's screen permission applies to it | The process starts with each attempt (74–88 ms of a 457–535 ms start) and ends once its file is finished. Starting it ahead of time saved about 50 ms for an idle process of about 73 MB and was declined by the maintainer (2026-10-15). The development Electron's `utilityProcess` is refused capture (`-3801`), so recordings need the signed bundle (`pnpm start:app`) |
| The engine writes the file: hybrid MP4, plain at save (076's D3) | Most containers need to seek back to finish (MP4's index, MKV's cues), which a chunk stream to main cannot do cleanly once formats are selectable; a stalled main event loop no longer delays writing; media stays in one language. Main keeps the file's lifecycle: name and folder, free-space check, session sentinel, publication, history, notifications, quit and sleep. The engine reports bytes written, write errors (disk full, write failed), then `stopped` and a separate `finished`, so a slow volume's save is no part of the stop | Main no longer sees the media bytes; it trusts the engine's progress and outcome, bounded at 150 s after the stop. A file whose index could not be written stays fragmented, which some players cannot read. Rejected: chunks to main's existing writer, which changed least but blocked other containers |
| System encoders and RecordStuff's own ISO BMFF muxer; no FFmpeg when recording (076's D4) | VideoToolbox and AudioToolbox on macOS; Media Foundation on Windows, so far Microsoft's software H.264 encoder (a GPU's hardware encoder, an asynchronous transform, is not built yet; plan 078). A Windows N edition without the Media Feature Pack fails as `capture_start_failed` with "Media Foundation could not start", not yet a code of its own. The muxer, written in Rust for this project from the ISO BMFF specification, writes OBS-style hybrid MP4. Recorders capture with system encoders and a lean muxer (Chromium, Cap, Kap, QuickTime, OBS) and keep FFmpeg for export; leaving it out keeps the app small and free of LGPL linking | The muxer is this project's code to keep correct, covered by `cargo test` and by decoding with `ffprobe`/`ffmpeg` in CI. Media Foundation's AAC encoder takes at most 192 kbps, so Windows records below the 256 kbps request. HEVC and MOV are later settings on the same layers; GIF, WebM or MKV belong to a later export feature, which may bring FFmpeg in for conversion only |
| Rust for both platforms, not Swift on macOS and C++ or Rust on Windows (076's D1) | The operating systems expose their APIs through binary calling conventions, so one compiled language can call both; one language keeps one capture pipeline, one muxer, one session state machine (`native/capture/src/core/`) and one set of tests. Electron with a Rust core is common (Cap, Signal Desktop, 1Password 8). Cap's AGPL recording code is a design reference only and is not copied (076's D5) | A Rust toolchain for every contributor who records and in both CI runners; the `.node` module is unpacked from asar and signed with the app, and `start-app.mjs --verify-app` refuses a bundle without it; platform code is still written twice (`mac/`, `win/`); the `objc2` and `windows` bindings may lag a new Apple or Microsoft API. Reconsider Swift on macOS if a needed Apple API is unavailable from Rust for long |
| Stay on Electron rather than move to Tauri (plan 076) | Tauri is also TypeScript plus Rust, but moving would rewrite about 14,600 lines of main, shared and preload code and about 32,000 lines of tests and acceptance tools, and change the Mac web engine, for app size and memory gains [the plan index](../../plans/README.md) already declined to rewrite for | Electron's size and memory stay. The Rust capture module would carry over unchanged if a move is ever chosen |
| The native engine on Windows is verified by CI only (076's D8, as for every Windows change) | The maintainer has no Windows machine. On `windows-2025` CI builds the module, runs `cargo test`, records the display, an area, a window and one process's sound live, decodes the results, and the installer smoke loads the installed module | Untested on Windows: real capture quality and frame timing, own windows absent from frames, system audio content, CPU, the microphone and every hands-on case; listed in release records and left to users' reports. Record hardware evidence when a Windows machine becomes available |
| Hide menu bar and Dock: a switch in Settings → Recording, off by default, macOS only (076's D6) | The recording leaves out the menu bar, Dock, desktop icons and widgets while the user still sees them; its ⓘ says an open menu is still recorded, because it is that app's window. Off by default because recordings must not change after an update and what is on screen is what users expect to be recorded; Loom and CleanShot X also make it an option | Locked while recording. On Windows the row reads Hide taskbar, off and unavailable with the reason, because Windows.Graphics.Capture cannot leave the taskbar out, and nothing is cropped. Revisit Windows if its capture API gains that |
| RecordStuff's own windows are always left out of recordings (075's D14; plan 076) | Settings, the library or a dialog opened during a recording is not what the user is recording. On macOS ScreenCaptureKit's application filter leaves the whole app out, including windows opened after the start and its app menus; on Windows main marks its windows `WDA_EXCLUDEFROMCAPTURE` while an attempt runs. Verified on macOS (2026-10-16): Settings opened during a recording was on screen and absent from the recording's frame. The composed camera (plan 075) is not a window, so no exception is needed for it, and the Recording Studio open beside a recording stays out of it: absent from the frames of a 2026-10-18 recording started from the Studio on the recorded display | No switch turns it off. The menu-bar icon stays in the recording, as no product hides its own status item. Unverified on Windows hardware |
| The camera is composed into the recorded frames by the engine, on the GPU before the encoder, as OBS does (plan 075's D15, D19; [design](recording.md#camera), [Studio](desktop.md#recording-studio)) | Redesigned on 2026-10-17 at the maintainer's request. A recorded floating camera window (Loom, Cap's Instant mode) must lock its placement while recording, because anything drawn on it is recorded and a movable window catches clicks meant for the app below; composing removes both, keeps the screen clear and lets the bubble change while recording from the next frame. A separate camera track placed afterwards (Cap Studio, Screen Studio) needs an editor, which RecordStuff does not have. One WGSL compute shader (`native/capture/shaders/compose.wgsl`) is the only source of the rounding, crop and mirror, translated by naga to Metal and Direct3D 11 at build; not wgpu, which would share only the shader and has no Direct3D 11 back end. Composing in Metal measured about 4 points at 30 fps and 7 at 60 over a recording without the camera (Core Image's per-frame graph: 10) | While the camera is shown every frame changes, so the encoder runs at the full rate even over a still screen. The camera cannot be moved after the recording, and a camera window cannot be shown on the screen. Windows' compositor and camera are checked by CI on WARP only, never with a real camera. Move to wgpu when a scene of several passes (an editor, effects) is needed; the shaders are already WGSL |
| The Studio's preview is a small H.264 stream decoded with WebCodecs, at the rate the user chooses: Off by default, Power saving (10 fps while someone works in the Studio, 5 otherwise), Standard (10) or Smooth (15) (plan 075's D17, D21; plan 081's D1; plan 092's D1) | A Chromium page must receive the frames a native preview (OBS's `obs_display`, Cap's wgpu window) would draw directly. Uncompressed NV12 drawn with WebGL (Cap's editor) cost 12.7 points on 2026-10-17, 9 of them the renderer and Chromium's GPU process uploading textures; a 640-pixel stream from the hardware encoder over a `MessageChannelMain` port, decoded in software (Chromium's hardware decoder held about six frames, 397 ms, back) needs no new plumbing. A native layer hosted by main was estimated at four to six times the work, needs native code in main, cannot carry HTML over it and needs its own Windows path. 10 fps instead of 15 (2026-10-18) took the Studio's share at 30 fps from about 14 points to 8.9 | At 30 fps the share over a recording without the Studio is within D18's 8 points since plan 081 (below). Plan 080 measured the alternative on macOS on 2026-10-19 ([record](../verification/history-2026-10.md#plan-080-closure--2026-10-19)): the compositor's IOSurface sent to main as a Mach port, received by a small native module there and handed to the page by Electron's `sharedTexture` as a `VideoFrame`. It worked, but saved nothing (13.9 points over the recording at 30 fps against 13.6): the encoder and decoder it removed cost about as much as main's import and transfer and the GPU process drawing the shared frame, so it was not kept and 076's D2 stays as it is. Reconsider only if Electron can reuse an imported surface cheaply and the page's own composing, about half a point per frame a second (plan 081), has fallen far enough for the transport to matter |
| Live preview holds the recording's own session, which Start takes (plan 075's D20; [design](desktop.md#recording-studio)) | OBS has one pipeline, whose picture the preview shows and a recording encodes, so starting a recording never breaks the preview. Live preview prepares the session a recording would (the display through its filter, the camera composed, system audio, the microphone) and holds it without writing; Start, from the Studio, the tray or the shortcut, takes it through the countdown with no gap, the camera opened once and the file named at Start (783 ms to prepare and 912 frames, none dropped, across preview and recording on 2026-10-18). Rejected: ending the preview's session and preparing a new one at Start, a 0.5–1.5 s gap and a camera reopened for nothing | A held preview costs a recording without the file, only while the Studio shows it; leaving the Studio, hiding the window, sleep and quit release it, and a change to the display, quality, menu bar, folder, microphone or camera prepares it again. A preview that cannot start is not a recording failure and is not kept in the history. A camera that stalls during a preview is not told lost until a recording starts |
| The Recording Studio shows the recording at 10 frames a second while someone works in it and 5 while it is only looked at (plan 081's D1, maintainer 2026-10-19; [design](desktop.md#recording-studio)) | Plan 081 measured each frame Chromium composes for the Studio's window at about half a point of a core per frame a second on the reference Mac, whatever changed, so the frame rate, not what is drawn, is the Studio's cost. Someone dragging the bubble, a fader or a mute needs the full rate's feedback; someone glancing at a recording made in another app does not, which is most of a recording. The pointer over the window, or a key, click or scroll in it within 3 s, is the signal, in the page alone; the engine's preview thread then makes a frame at every other tick, so its encoding and the page's decoding halve too. The levels come on the preview's port instead of through main (Electron's guidance keeps high-rate data off main; it also removed main's `LevelsLink`). Rejected: a `<video>` fed by `MediaStreamTrackGenerator` (2.2 points more beside the meters), always 5 frames a second (the same cost while working, choppier feedback), focus as the signal (a window in front is not always watched), a native layer for the preview and meters over the page (two UI systems, position syncing and a second platform's path for a few points). Deferred: skipping unchanged preview frames in the engine, which helps only a still screen and was not measured | Someone watching the Studio from the corner of an eye, the pointer elsewhere, sees 5 frames a second. Rates other than 10 and 5 are refused on the port. Reconsider when the preview must be larger or faster, or when a measurement of a still screen shows unchanged frames worth skipping |
| Per-input volume faders, saved between recordings, beside per-recording mutes (plan 075's D21, D19) | OBS's mixer gives each source a meter, a fader in dB and a mute, kept between recordings. System audio and the microphone each get a fader, said in percent of the input as it comes since 2026-10-21 (dB before), from 0%, silent, to 600%, a microphone often needing raising, which OBS leaves to a gain filter; the engine applies it before metering, muting and mixing, from the next sound, during a Live preview or a recording, and the track's soft limiter above −1 dBFS keeps a raised input from clipping. A mute, like hiding the camera, is that recording's choice only | A fader is a setting: one left low quiets every later recording until moved, and it is changed only in the Studio, not in the tray. Two inputs only, since system audio is one mix; per-app levels would need the engine to capture apps apart |
| The camera's CPU budgets: over D18 accepted on 2026-10-17 and 2026-10-18, within it since plan 081 (2026-10-19; [budget](tooling.md#cpu-budget)) | D18 set, on the reference M1 Pro, a recording with the camera at most 20% / 25% of a core at 30 / 60 fps, the Studio showing it at most 8 points more, and a Live preview within a recording's figures. Measured on 2026-10-18 with D21's 10 fps: R 15.5% / 19.4%, S 24.5% / 30.7%, L 16.9% at both rates; every absolute budget passes, but S is 8.9 and 11.3 points over R. The excess is spent only while the Studio is open in sight; the step 2 prototype's preview share (10.5 and 8.7 points) had been accepted the same way on 2026-10-17. Plan 081 found the share to be mostly the page's composing and halved the Studio's rate while no one works in it: on 2026-10-19, with an iPhone camera delivering, R 11.6% / 16.1% and S 18.9% / 23.8% at 30 / 60 fps, 7.4 and 7.7 points over R (medians of three), L 15.7% / 17.3%; without a camera 7.6 and 9.6, the 60 fps figure the capture process's own spread between launches | While someone works in the Studio it shows 10 frames a second and costs more: 9.9 points over R at 30 fps with the camera (2026-10-19), above D18's 8; D2's gate covers the Studio while no one works in it, and the full rate while someone does is the feedback dragging or adjusting needs. Since plan 092 (2026-10-23) the preview is the user's choice and Off by default, as OBS can turn its preview off: Off draws and encodes nothing, though the Studio's window and its meters still cost 3–5 points over R, within D18; Power saving costs what the Studio did before; Standard (about 9.5 points) and Smooth (about 13.4) are opt-in costs over D18 that 092's D2 accepted, Smooth kept at 3.7–3.9 points over Standard ([baseline](tooling.md#pipeline-baseline)) |
| Bundle identifier is the reverse of a domain the maintainer controls (`com.ericts.record`; [why](signing.md#bundle-identifier)) | Identifiers have no registry, so an owned domain is the only uniqueness guarantee; the identifier is the app's identity for TCC grants, notifications and the signature | Chosen once and kept: changing it makes macOS treat the app as new and users must re-allow screen recording |
| Main owns state and the file's lifecycle | UI and capture must not independently claim success | Main coordinates cleanup and publication; the capture process needs readiness, session IDs and a heartbeat |
| H.264/AAC MP4 | Verified QuickTime playback and hardware encoding | Fragmented while recording, plain at save; no universal repair guarantee or format fallback |
| Native Tray/Menu/Notification | A one-button recorder does not need a UI framework | OS controls notifications and foreground ordering |
| Scripted native input on RecordStuff's own UI, by committed runners only (maintainer decision 2026-10-02, plan 063; [tooling](tooling.md#scripted-native-acceptance)) | Computer Use cannot reach the tray-only process, so tray cases waited for the maintainer or were blocked; CoreGraphics clicks and keys with Accessibility reads reached every state in the 048 and 035 rounds, and a runner repeats them and compares the native menu with the production model's log line | Scripted input proves delivery and state, never appearance, which stays an observation of its screenshots. A click moves the real pointer (posting to the process did not open the menu on macOS 26), so rounds still need the desktop handoff and a person's input can disturb them undetected; an isolated macOS session or VM is the step that would remove that. Recheck the status-item lookup after each macOS update, since Control Center hosts the item |
| Recording failure history in its own Settings tab, not a separate window (plan 047; [design](desktop.md#recording-failure-results)) | Failures above the preferences made every Settings open start with a long block of reasons; Cap keeps history and diagnostics as pages of its one Settings window and links the tray straight to them. Failures and preferences are used together (guidance leads to the Recording tab), and a second window would need its own lifecycle, preload, sender authorization, size persistence, close shortcut, crash and focus handling | Revisit a separate window only if the history grows beyond failures into, for example, a library of saved recordings, a separate product decision. Error text only in a tooltip, a recordings library and a log upload were not adopted |
| Pre-recording countdown, 3 s by default (plan 040; [design](recording.md#countdown)) | Capture began about 0.3 s after the click, so the first frames showed the pointer leaving the menu bar and there is no editor to trim them. Capture is prepared before the count and the engine's `record` is the gate at zero, as Cap prepares its pipeline and gates frames; Off, 3, 5 and 10 s follow Cap's choices, and the default applies to existing users | Only a 28%-white digit at the top-right, no box, ring, text, full-screen dimming or content protection; the overlay leaves 300 ms before capture, chosen when `getDisplayMedia` had no per-window exclusion and kept with the native engine, which leaves RecordStuff's windows out as well. An optional tick with each digit (plan 046) is on by default by the maintainer's choice, also for existing users, and switchable in Settings; it ends 860 ms before capture, so time separation keeps it out of the recording. There is still no start sound at zero, because RecordStuff records system audio and whether the engine's exclusion of RecordStuff's processes also keeps such a sound out is unverified. The digit fades on bright photos; in 035's N32 the maintainer judged it readable and transparent enough over a bright photo, a white document and a dark editor, so the alpha stays. Its size scales with the recorded display, 14% of the shorter side clamped to 56–216 pt (plan 045), because a fixed 56 pt was about 5% of a 1080 pt screen and read as too small; a size setting and a centred digit were not adopted. Any click, the shortcut, the menu or Quit cancels, and a cancel is not a failure |
| Save in the background once capture stops (2026-10-09; supersedes plan 037's "no overlapping finalization") | A save on a network volume that stopped answering held the stopping state forever: no new recording, the display-sleep hold kept, quit deferred indefinitely. Cap (CapSoftware/Cap at d327051c) also ends its recording state before finalizing in a separate registry; neither it nor OBS bounds the save. The recorder now returns to idle at `stopped`, saves in the background, tells a save slower than 30 s and offers Quit Without Waiting for the Save while only saves hold a quit | Saves may overlap the next recording's writes on the same drive; a save is never abandoned for being slow (Node cannot cancel the I/O); quitting without waiting leaves the file to the next launch's interruption report. Chosen by the maintainer (2026-10-09) |
| Publish by exclusive hard link; no overlapping finalization (plan 037; [design](recording.md#file-completion-and-failure)) | Measured stop-to-ready was the publication copy: libuv never clones on macOS, so saving a 2 GB recording copied for 1.3–1.9 s and a low-disk early stop failed for lack of room. A link takes constant time, needs no space and, like the copy, never replaces a name; with it no separable wait was left, so a second lifecycle for overlapping saves was not built | Volumes without hard links (exFAT, some network volumes) still copy: a 2 GB save waited 2.2–3.1 s on an exFAT image and the copy needs the file's size free, which overlap would not fix, and on a slow drive the copy would contend with the next recording's writes. Accepted by the maintainer (2026-09-27). If such output folders prove common, first remove the copy there (for example reserve the final name exclusively, then rename over the reservation, after measuring it on that file system) rather than overlap; reconsider overlap only if a measured representative case again spends over 0.5 s after the file is closed |
| CPU budget measured from outside the app (plan 049; [budget](tooling.md#cpu-budget)) | Idle had no measurement and the matrix read `ps`'s decaying `%cpu`, too coarse for an idle second and blind to system helpers. As in Cap's harness, a small helper reads `proc_pid_rusage` for the app's process tree, reports VTEncoderXPCService apart and discards windows whose process set changed; unlike Cap, the thresholds fail a run | No monitoring timer in the shipped app, which would itself wake the idle app. Thresholds hold for the reference M1 Pro; another machine or an Electron upgrade takes a new baseline first. The 5-second permission poll stays until a measurement shows it matters; the idle contract names processes by role (since plan 076: no renderer before the first window, no audio service and no capture process after a recording, where Chromium's capture had left a pre-warmed renderer of about 65 MB and an audio service of about 49 MB, accepted on 2026-09-28) and the post-recording check counts growth per recording rather than the difference from launch; memory is reported, not budgeted. The baselines were retaken for the native engine on 2026-10-16 |
| Keep awake during a session; stop and save on sleep (plan 050; [design](recording.md#file-completion-and-failure)) | Nothing kept the Mac awake, so idle display or system sleep could end a long recording without input, and a sleep the user asked for ended it as capture_failed 146 ms after `suspend` with its banner lost (035's N31). A `prevent-display-sleep` blocker covers the session; a sleep that cannot be refused becomes a normal stop with a note, and notifications wait for waking. Cap ([static review](https://github.com/CapSoftware/Cap/tree/20c224073bece3fbebed8acb631bd2df97cd6f40)) holds no blocker and rebuilds its capture into the same recording after a system stop | The display stays on for as long as a recording runs, with no setting. The same file is not continued after waking (decided when `MediaRecorder` could not swap tracks; the native engine does not continue one either); reconsider if users need recordings that span a sleep. A forced display sleep or a screen lock without system sleep is not handled and still fails the recording; the maintainer accepted that on 2026-09-28 |
| Global shortcuts register by physical key (`LayoutAwareGlobalHotkeys` disabled on macOS; [why](desktop.md#recording-shortcut)) | The editor records physical keys and refuses the keypad; Chromium's layout-aware lookup moved the default ⇧⌘1 to the keypad under Zhuyin | On non-QWERTY Latin layouts a letter shortcut is the US position, not the keycap letter. On every Electron upgrade, run `pnpm acceptance:shortcut-layout` ([check](tooling.md#keyboard-layout-shortcut-check)): if its Chromium renamed or dropped the feature, registration silently returns to layout lookup |
| Handwritten guards and one repository | Small protocol/state surface stays readable and testable | No protocol negotiation; independently shipped peers would need a stronger contract |
| Size from the source the engine probes | Chromium's `getSettings` once caused an incorrect 1080×606 output from a 1080p display, so size is never taken from a request: the engine probes the display, main fits it within the resolution cap, and the report carries what the engine prepared | One probe at each start; the log line names the source size beside the recorded one |
| A key frame and a fragment about every second | Each fragment starts at a key frame, so a file cut off by a crash plays up to its last fragment (an 8.0 s partial after a kill); a still screen is encoded again each second so fragments keep closing. Through Chromium, timeslice alone had let low-motion Retina recordings miss the first-chunk deadline | Each track flushes separately, so a crashed file's tracks can differ by about a second (147 ms measured); a nominal interval is not a delivery guarantee |
| Retain quality coefficients | 30 fps outputs were near target; 60 fps remained useful despite excess bitrate | Larger 60 fps files; distinguish requests, track reports, and measured output |
| Remove audio-quality selector | Through Chromium, different requests produced about 160 kbps AAC on this setup | Fixed 256 kbps request does not promise that bitrate or stereo separation; Media Foundation's AAC encoder on Windows takes at most 192 kbps |
| Do not compensate inherent A/V latency | Measured latency/drift met the project's accepted limits; remeasured for the native engine (2026-10-14/15): 0 ms drift over 10 minutes, audio and picture equally long, flash-to-beep −25 ms | Remeasure after capture-engine changes |
| Fixed self-signing identity and DMG | Recipients can install without developer tools or certificates | No Apple notarization; first-launch exception may be needed; TCC behavior is not universally guaranteed |
| DMG holds only the App and Applications link | The drag-to-Applications window is the installer convention users already know; bundled documents added clutter and ambiguity | Help, update and removal guidance must stay reachable online and linked from every release; the release gate fails on any extra visible file |
| Tag is the release and the version; verification precedes tagging | One maintainer and one Mac cannot support nightly channels, an in-pipeline manual acceptance gate only repeated checks already done during development, and a version stored in the repository before tagging was one more thing to get wrong | CI proves build, signature, layout and byte identity but not capture; a bad release is fixed by a new version, never by overwriting; the record job commits to main as a bot |
| Manual update, no updater; Trash removal on macOS, the per-user uninstaller on Windows (Windows part: maintainer decision 2026-10-03) | Same identity and path keep settings and permissions across replacements; a one-button recorder gains little from background update machinery. On Windows, an entry in Settings → Apps is how users expect to remove an installed app, and the per-user installer registers it | Users must download new versions themselves on both platforms; user data is never deleted automatically. The macOS rule is unchanged. The Windows uninstaller removes the app, its Start-menu shortcut and its registration and keeps recordings, settings and logs (`deleteAppDataOnUninstall: false`). Revisit an updater only through the deferred update assessment |
| Windows x64 published with macOS by the same tag, checked by CI only, without Windows hardware (maintainer decision 2026-10-03, plan 064, [closure](../verification/history-2026-10.md#plan-064-closure--2026-10-03); [release contract](releases.md#release-contract)) | The maintainer has no Windows machine but wants Windows users served by the same flow as the Mac; GitHub's Windows runners can build, install, inspect and uninstall an installer, though not record. A per-user one-click NSIS installer (`oneClick`, `perMachine: false`, no admin prompt) is the common practice for an Electron app released on GitHub (T3 Code, pingdotgg/t3code, ships one beside its DMG), and its Start-menu shortcut carries the appId `com.ericts.record` as the AppUserModelID Windows toasts need | Hardware verification remains macOS only. Windows evidence is CI only: `pnpm check` on `windows-2025` and, before and after publication, the silent per-user install, registration, version, architecture, signature state, tray icons, shortcut and silent uninstall; capture, system audio, notifications and the tray are unverified on Windows (035's N17 tray matrix stays open), the Windows wording (system tray, the computer going to sleep, the default playback device, Ctrl-only shortcut messages and reserved keys) has never been seen on Windows, and the app enforces no Windows version floor: Electron 44 itself supports Windows 10 and newer, below which the app cannot start to check, and without hardware no narrower floor can be set. Unsigned, as the asset name says, so SmartScreen warns; integrity rests on SHA256SUMS, `release-win32-x64.json` and a GitHub build-provenance attestation. A Windows failure fails the whole tag before publication. x64 only: Windows on Arm and Linux have no build. Record hardware evidence when a Windows machine becomes available; reconsider signing if SmartScreen or user reports make the unsigned installer impractical |
| English source and optional Traditional Chinese | GitHub documentation and diagnostics use a common source language; users may choose Chinese UI | Catalog and paired documentation must be maintained together |
| Separate design from plans | Execution logs are poor long-term specifications | Keep behavior/evidence in docs and unfinished work in plans |
| Raw measurement runs stay local | Per-run reports, logs and probes are machine-specific and would multiply with every contributor; only the interpreted conclusion is durable | `docs/verification/measurements/` is gitignored; the verification record and release records must carry enough numbers to stand without the raw files; history before `acc6342` still holds the early raw runs |
| [Known-fixture audio diagnostics](audio-quality.md) | Simultaneous pilot, frequency fitting, and continuity windows distinguish spectral loss, gain, and clock error | Invalid measurements cannot support quality claims; retain repeated failures, never learn a bad baseline automatically; not a substitute for listening or long-duration verification |

## Evolution boundaries

Builds use electron-vite, electron-builder and Cargo. Follow stable dependency releases and rerun relevant checks and media verification when upgrading; an old measurement is not proof about a new engine.

The native capture engine is a Rust crate (`native/capture/`) built by Cargo with the app. There is no speculative Effect, schema framework, monorepo, React, or full PlatformRecorder layer. A UI renderer stays outside the media byte path, which now never enters Electron's processes. A new capture capability belongs in the engine behind the recorder's existing contract. Recording libraries, editing, shortcuts, automatic updating, Windows hardware verification and support for platforms beyond macOS and Windows x64 are not prerequisites for the current downloadable build.

Third-party comparisons and native-engine candidates from historical planning are not current dependencies or commitments. Reevaluate their APIs and suitability if an actual need arises.

2026-10-06: Updates and ordinary uninstall continue to retain user data. An explicit, confirmed “Clear local app data and quit” exit path removes app-owned data while retaining recordings and the output folder. Old settings migrate at startup; newer schemas refuse overwrite. Migration support and removal policy are independent: cleanup does not replace upgrade support. See [desktop design](desktop.md#local-app-data-cleanup).
