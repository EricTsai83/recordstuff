RecordStuff records through one path, the native engine of plan 076. For each attempt main forks an Electron `utilityProcess` (`RecordStuff Capture`) that runs the capture host and loads the Rust module (`recordstuff-capture.node`, built with napi-rs and unpacked from the asar archive). The engine captures (ScreenCaptureKit on macOS; Windows.Graphics.Capture and WASAPI on Windows), encodes with the platform's encoders (VideoToolbox and AudioToolbox; Media Foundation), muxes and writes the file itself (plan 076's D3, 2026-10-14). Main keeps the file's lifecycle: the folder and name, the free-space checks, the session sentinel, publication under the final name, history, notifications, and the state machine with its deadlines, quit and sleep. A native crash ends only the capture process; main fails the session and keeps what was written. The earlier path, a hidden Chromium renderer that recorded with `getDisplayMedia` and `MediaRecorder` and sent one-second pieces to main's writer, was removed on 2026-10-16. Platforms other than macOS and Windows have no engine: a recording there fails because the module does not load.

## State and user actions

```mermaid
stateDiagram-v2
    [*] --> idle
    idle --> needsPermission: Screen capture unavailable
    needsPermission --> idle: Grant and source validated
    idle --> starting: toggle
    starting --> countdown: prepared (countdown on)
    starting --> recording: prepared, record, started (Off)
    countdown --> recording: record, started
    countdown --> idle: cancelled (toggle / menu / quit / sleep)
    starting --> idle: cancelled (toggle after 1 s / menu / quit / sleep)
    recording --> stopping: stop / quit
    stopping --> idle: stopped (the save continues in the background)
    starting --> idle: failed
    countdown --> idle: failed
    recording --> idle: failed
    stopping --> idle: failed
```

NeedsPermission carries needsRelaunch. Idle may carry outputDirUnavailable. Countdown carries `remaining`, whole seconds, at least 1 and kept at 1 while `record` waits for `started`. A session's end (stopped or failed) settles into needsPermission instead of idle when the latest permission status is not granted ([screen permission](desktop.md#screen-permission)). Recording carries an ISO startedAt. Failure is an event, not a persistent failed state; a cancel is neither a failure nor a state. Clicking without permission emits permissionRequested; clicks during stopping, and during the first second of starting, are ignored and logged. During the countdown, and once a start has lasted a second, a click or the shortcut cancels (see [countdown](#countdown)). The Recorder's internal phases are finer than the state: `opening` (folder and file), `preparing` (until `prepared`), `previewing` (a Live preview's prepared session held without writing while the state stays idle, plan 075's D20; see [camera](#camera)), `countdown`, `arming` (`record` sent, waiting for `started`), `recording` and `stopping`.

## Start

1. Recorder checks idle/no existing session and OS preflight (macOS 13 or later), captures the quality and countdown snapshots, creates a session ID, and enters starting (the tray shows the hourglass).
2. ensureWritableDir creates only the default folder; custom folders must exist. It writes/removes a probe and rejects starts below 200 MiB free; a free-space lookup that fails is logged and the start proceeds, as the guard during recording does. Failure never silently selects a different folder. A check still unanswered at its attempt's deadline (a network volume that stopped answering) holds one of the main process's four file-system threads, so a new attempt on that folder waits on the same check instead of starting another until it answers.
3. Write the session's interruption sentinel naming the temporary path, then reserve `YYYY-MM-DD HH-mm-ss.recording.mp4` (local time, or the file-name template): `EngineFileWriter.open` creates it empty with exclusive `wx` and closes it, and the engine later opens that same file for writing, never creating a name of its own. A temporary-file collision rewrites the sentinel and retries suffixes `-2` through `-10`. The name is the local time of the start request, so with a countdown it precedes the first frame by preparation plus the countdown.
4. With a countdown, the overlay window is built now so the first digit appears on time. `NativeCaptureHost.start` ends any earlier capture process, registers the file whose outcome it will report, forks a fresh process and, at the same time, resolves the display through `DisplayMedia` ([screen selection](#screen-selection)), so neither waits for the other. With the microphone on (plan 074) main also asks macOS for microphone access alongside them, if macOS never has (`askMicrophoneAccess`), so the system prompt comes as the first recording with the microphone starts; the tray stays at starting without a countdown while it waits, `start` is posted only after the answer, within the 120 s capture-request deadline, and a refusal is left to the engine to report. The process must report `ready` within 8 s; the heartbeat starts. A refused display becomes a host `capture_start_failed` that main's refusal reason replaces. On Windows main computes a physical point on the display and marks its own windows excluded from capture ([own windows](#own-windows-and-system-ui)). Main then posts `start` with the quality snapshot and the native options: display ID, the Windows point, the reserved path, RecordStuff's process IDs (main first), the D6 switch (macOS only), with the microphone on, the chosen input's ID (none for the system default), and with the camera on (plan 075), the camera: its device (none for the system default) and the bubble at the position kept for the recorded display, else the primary display's, else the default ([camera](#camera)).
5. The host asks the engine to `probe` the display's size in pixels, applies the quality rules to choose the output size and the video bit rate ([quality](#quality-and-encoding)), and calls `prepare`. On macOS preparing reads the shareable content (kept 2 s from the probe, so an attempt asks the system once; bounded at 15 s; a missing grant fails here as `permission_denied`), finds the display (`no_display` when it is not shareable), builds the content filters, opens the reserved file, makes the encoders on their own thread while the `SCStream` starts (bounded at 10 s), and waits up to 3 s for the first frame. Windows does the same with its own sources (its first-frame bound is also 3 s; audio activation 5 s). With the microphone on, prepare also opens it (AVFoundation's `AVCaptureSession` on macOS, a WASAPI endpoint on Windows): access not allowed (denied, restricted, or never asked, since AVFoundation would then deliver silence), no input device, or a device that does not open fails the start as `microphone_unavailable`. A chosen input that is not connected (on Windows, also one not active) falls back to the system default input, and the report's warnings say `microphone: {id} is not connected; the default input is used`. With the camera on, prepare opens it before the screen's stream, and a camera that cannot open fails the start as `camera_unavailable` ([camera](#camera)). From here capture runs, but only the newest frame is kept and nothing is written. The host replies `prepared` with the CaptureReport and logs `timing: probe … ms, prepare … ms (content …, filter …, stream start …, …)`; main logs `process ready` and `display chosen`, and its `prepared` line ends `mic off` or `mic on (<name>)` with the device the engine opened (CaptureReport's `microphone`). Permission, display, encoder, audio and microphone errors therefore all surface before any countdown. A stop that arrives while the engine prepares makes the host cancel it as soon as `prepare` returns and answer `stopped`.
6. With the countdown Off, main sends `record` at once. Otherwise it counts down ([countdown](#countdown)) and sends `record` at the end.
7. The engine takes the recording's time zero on its clock, starts its writer thread and returns at once; the host replies `started` (2 ms from `record` on 2026-10-14). The engine's refresh thread then encodes the newest captured frame at time zero as a key frame, so the file starts with a picture however still the screen is, and only then lets later frames and sound in. Main enters recording, emits captureStarted with the report from `prepared`, and arms the first-media deadline, the stall guard and the disk guard. REC appears only after capture began, so the first frames may show the stopwatch in the menu bar, as they showed `…` before; the digit never appears in them. The engine reports the bytes it has written once a second while media arrives (`progress`); the first nonzero report must come before the first-media deadline, and its log line (`first chunk … bytes (engine progress)`, a name kept from the hidden renderer because the acceptance runners time to it) marks it.

Measured on a signed bundle (plan 076, 2026-10-14 and 2026-10-15): pressing the shortcut to `prepared` took 457–535 ms, against 347–369 ms through Chromium; the native time is the process start (74–88 ms), the shareable-content query (59–83 ms) and ScreenCaptureKit's `startCapture` (206–227 ms). Starting the process ahead of time brought it to 437–439 ms at the cost of an idle process of about 73 MB; the maintainer declined that on 2026-10-15, since about 50 ms is inside the countdown, so no capture process exists between recordings. With the microphone on, `prepared` came after 611 and 666 ms, against about 440–670 ms with it off (plan 074, 2026-10-16).

## Countdown

Settings → Recording chooses Off, 3, 5 or 10 seconds; the default is 3, also for a settings file written before the field existed. Recording measured 318 ms from click to capture in the 2026-09-25 hotkey round ([plan 040 closure](../verification/history-2026-09.md#plan-040-closure--2026-09-26)), so the first frames showed the pointer leaving the menu bar and RecordStuff has no editor to trim them. Capture is prepared before the count and started at zero, as Cap does ([decision](decisions.md)).

- Recorder enters `countdown` with N and ticks once per second from one monotonic anchor taken at `prepared`; every tick is scheduled from that anchor, so timer lateness never accumulates. Each tick re-emits the state; the app logs `state → countdown (n)`.
- 300 ms before N seconds it asks the overlay to leave: the digit fades out over 120 ms and main destroys the window after one more settle interval (34 ms). Recorder waits for that confirmation at most 500 ms; past it the window is destroyed, the timeout is logged and capture proceeds. `record` goes out at N seconds, or when the dismissal settles if that is later.
- The overlay ([desktop](desktop.md#countdown-overlay)) is injected as a presenter with `show`, `update`, `dismiss` and `close`, so Recorder stays free of Electron. Presenter errors are logged and never fail a recording; the tray still shows the countdown.
- The countdown sound (plan 046, on by default, switchable in Settings → Recording) is read once per session with the countdown and passed to the presenter; the `prepared` log line ends with `sound on` or `sound off`. The overlay page plays a soft 523 Hz marimba-like tick at −20 dBFS with each new digit, the digit 1 a fifth higher, and nothing at zero, on cancel or with the countdown Off. Each tick lasts 140 ms from the digit's tick time, so the last one, with the digit 1, ends 860 ms before `record` and long before the overlay leaves: the recording stays clean by time separation, as the digit does, besides the engine leaving RecordStuff's own sound out ([audio](#audio)). `pnpm acceptance` checks the first 500 ms of a ticking session's audio at both pitches. Autorecord never ticks, so matrix and audio-quality recordings keep the material's audio alone.
- A toggle, the tray menu's Cancel recording or the shortcut before `record` cancels the attempt: timers cleared, host stopped, overlay closed, writer abandoned so the empty temporary file is removed, and the idle state from before the attempt returns. A `cancelled` event names the reason (`toggle`, `menu`, `quit` or `sleep`) and the log says `cancelled: session … (reason); no media was recorded`. No failure status, history entry, notification or display diagnostic is produced.
- After `record` was sent, a toggle becomes the existing stop-on-start request applied once `started` arrives, so a race of a few milliseconds cannot leave capture running. Should capture stop before its first frame, nothing was recorded: the attempt ends as that cancel (or quit or sleep), not as a failed start. With the countdown Off, `record` goes out at `prepared` while the state still reads starting, so the menu's Cancel recording, or a toggle after the grace, becomes the same request. A tray menu opened during the countdown is not updated while it stays open ([desktop](desktop.md#tray-and-notifications)), so its Cancel recording chosen after capture began stops the recording, which is saved.
- A toggle while starting (plan 065) cancels the attempt exactly as Cancel recording does once the start has lasted `START_CANCEL_GRACE_MS`, 1 s, on the Recorder's monotonic clock from the session's request, taken in the same step that enters starting: opening the folder or preparing capture, it is cancelled with no file, failure entry or notification; after `record`, it becomes stop-on-start. Within the grace the press is a double press and is ignored, as is every press while stopping; both are logged (`recorder: session <id> toggle ignored while starting (<n> ms after the start)` and `… while stopping (<n> ms after the stop)`), so a report that the shortcut did nothing can be told from a lost key. The starting menu's Cancel recording names the registered shortcut, as the countdown's does ([desktop](desktop.md#tray-and-notifications)).
- Plan 065's decisions, the maintainer's on 2026-10-03, rest on the retained log of 2026-09-12 to 2026-10-02, recorded through the hidden renderer: 739 starts with a median of 289 ms and a 95th percentile of 396 ms; the nine over 1 s all waited in preparation (1.1–9.4 s for permission denials, a missing audio track and the earlier 8 s limit; 120 s four times while the capture request stayed pending), none in opening the folder, and one, on 2026-09-13, after `record`. The fastest logged double press was 290 ms. The grace is 1 s rather than "at any time while starting" or "only while preparing"; the starting Cancel recording names the shortcut; and quit while opening or preparing cancels at once (see [terminal ownership](#terminal-ownership-and-normal-exit)) instead of waiting for the capture request, which once held a quit for 286 s.
- Every timing and appearance value lives in [countdown.ts](../../src/shared/countdown.ts) as an initial target; tune them only with written evidence.

## Deadlines and supervision

| Protection | Default | Outcome |
| --- | --- | --- |
| Folder/open phase | 8 s (`DEFAULT_START_TIMEOUT_MS`) | output_open_failed; a late writer is abandoned |
| Host ready | 8 s (`readyTimeoutMs`) | Start rejects as capture_start_failed; the next attempt forks a new process |
| Capture/interactive permission request (`start → prepared`) | 120 s | capture_start_failed and stop session |
| Inside the engine's prepare (macOS) | Shareable content 15 s, stream start 10 s, first frame 3 s | capture_start_failed (permission_denied for a missing grant) |
| Inside the engine's prepare (Windows) | Audio activation 5 s, first frame 3 s | capture_start_failed |
| Countdown overlay dismissal | 500 ms from the dismiss request, which comes 300 ms before N | Destroy the overlay, log it, record anyway |
| `record → started` | 8 s | capture_start_failed (while starting capture) |
| First nonzero `progress` after started | 8 s | capture_start_failed; preserve any written data |
| Next nonzero `progress` after media began | Warn once at 10 s, fail at 30 s; reset by every nonzero report, disarmed by stopped or failure | capture_failed with a stall detail; preserve the partial file |
| Output-folder free space | Poll every 5 s from started until stop; log once below 1 GiB | Below 200 MiB request the normal stop once; saved with a disk-almost-full reason, not a failure |
| Stop response (`stop → stopped`) | 10 s | stop_timeout |
| Sound up to the stop | The engine waits up to 250 ms | What has not arrived is silence; logged |
| File finish after `stopped` | Engine 120 s; host process 150 s (`FINISH_BOUND_MS`) | output_write_failed (engine), or the process is ended (host); the file is kept either way |
| Slow save | 30 s (`saveSlowMs`) | Logged and told once (`savingSlow`); never abandoned |
| Unanswered cleanup check | 15 s (`cleanupCheckMs`) | A failed recording's check for a kept partial is reported as unknown with the file's path, a cancel's is logged; a drive that stopped answering cannot hold quit |
| Own windows let back in (Windows) | When the capture process exits, at most 5 s after it was told to end | Windows are capturable again |
| Quit wait | 13 s per attempt (stop timeout + 3 s) | Defer quit with localized feedback while any owned work remains; never truncate finalization |
| Heartbeat | Ping every 5 s while a session is in flight | Tear down when the check finds two unanswered pings: capture_host_unresponsive |

Before `record` nothing was captured, so the end of a source, display removal, a crashed or unresponsive host and a refused or timed-out `record` during preparation or countdown are start failures: `capture_start_failed` with a detail naming the phase (`while preparing capture`, `while counting down`, `while starting capture`), the display diagnostic still emitted and an empty outcome. A stale `prepared`, `started` or `progress` for a detached session triggers a host stop, so an abandoned attempt cannot keep capturing unseen.

These are project waiting limits, not OS standards or exact end-to-end timing guarantees. A timed-out disk operation is not actually canceled. The main-side health rows (stall, free space, slow save) are initial targets kept in one place, [recording-health.ts](../../src/main/recording/recording-health.ts); tune them only with written evidence. Heartbeats only prove the capture process's JavaScript answers; the stall guard proves the engine still writes media. The engine's writer sends `progress` only when media reached it during the last second, and a healthy still recording keeps sending it, because the engine encodes the last frame again every second while the screen stands still, and at every slot while a camera is shown ([frame pacing](#frame-pacing), [camera](#camera)), and the audio track advances with the clock. A failed free-space poll is logged once and never stops a recording. `powerMonitor` suspend and resume are logged with the in-flight session ID so a later failure can be read against sleep; how sleep itself stops a recording or cancels an attempt is described under [file completion](#file-completion-and-failure).

## Terminal ownership and normal exit

The first failure wins at every layer. The engine reports the first capture or encoding failure once, as `capture_failed` while recording or draining to the stop and `capture_start_failed` while only prepared, and none once its drain has ended. The host forwards engine events only while its session lasts and drops that session as it sends `stopped`, so later capture events belong to nobody; from then on the engine answers only for the file, with `finished` or `writeError`. Main validates every inbound message (`isHostMessage`) and drops malformed ones; a host that sends a code only main can find (folder, disk deadline, supervision, launch) is malformed rather than believed. A `stopped` that arrives while the Recorder is not stopping is `capture_failed` ("capture host ended capture without a stop request").

Once Recorder accepts `stopped`, its finalizer owns the attempt and the recording is over: since 2026-10-09 the state returns to idle at once, releasing the display-sleep hold, and the file is finished in the background (the engine making it plain MP4, then main's size check and publication), owned like other recording work, so quit still waits for it, while the next recording may already start. `NativeCaptureHost` keeps the finishing process alive after the attempt is torn down, hands its outcome to the writer and ends the process afterwards, or once 150 s have passed (the engine's own bound is 120 s); a process that exits before reporting fails the save with the file kept. On the desktop the Recorder was idle 0–1 ms after `stopped` and the file finished 19–22 ms later (2026-10-15). `Recorder.saving` lists those saves for the tray and Settings; one still running after `saveSlowMs` (30 s, a drive that stopped answering) is logged and told once (`savingSlow`), and main never abandons it: a slow drive that still works finishes it, within the engine's bound. Its outcome (saved, failed with the partial kept, or the cancel of a start stopped before its first frame) is reported without touching the state, which may belong to the next recording by then; a save that finishes during that recording holds its saved notification until the recording ends, as the capture notices are held. Late host crashes/errors, duplicate stop messages and display removal cannot abandon a publishing file; the engine's write error still enters failure cleanup. All opening/finalizing/cleanup operations are registered before synchronous subscribers run. An opening timeout returns UI to idle immediately, but its result stays pending until the late open and close settle. Multiple failed attempts retain independent cleanup ownership.

Every `before-quit`, including idle, uses `installQuitCoordinator`. Repeated requests join one attempt and new recordings are blocked during admission. Capture is stopped automatically. No media exists before `record`, so quit never records a session that has not started (plan 040, for every countdown setting): quit during the countdown, while the folder opens or during preparation cancels it at once, as Cancel recording does (plan 065; before it, quit during preparation waited for `prepared` or the 120 s capture-request deadline). The host is told to stop and cancels the engine as soon as its prepare returns, so a late `prepared` is a stale session's and is stopped again; a folder check still in flight stays owned by the cancelled attempt, and quit waits for it. The attempt is also marked when quit is requested, so whatever ends it before the coordinator's check runs is that cancel. Only a session whose `record` was already sent keeps stop intent, so capture stops and saves as soon as it starts. Success requires no session and no outstanding work, including late opens, earlier failed attempts and failure-result verification/publication. The quit deadline only defers exit; the existing stop-response timer retains authority over a started capture's failure. Pending disk/result-publication work stays owned, the app stays open and the user can retry quitting. The app never destroys the host or exposes an unconfirmed retained path merely to meet a quit deadline. Force-quit, process kill and power loss bypass these guarantees and nothing is repaired afterwards; what the engine had written stays a fragmented MP4 readable up to its last whole fragment ([plain MP4 at save](#plain-mp4-at-save)). The one exit that does not wait for media is offered only while a quit waits for saves in the background alone: Quit Without Waiting for the Save (2026-10-09, [desktop](desktop.md#deferred-quit)) exits after bounded metadata flushes and leaves those saves' sentinels. The next launch reports such a session through its interruption sentinel (see [file completion](#file-completion-and-failure)). Only after this media phase does quit attempt the failure-history save; its explicit metadata-only exit can never abandon media work (see [desktop](desktop.md#deferred-quit)). Windows ends a session (shutdown, restart, sign-out) without `before-quit`, so each window's `query-session-end` is answered instead ([session-end.ts](../../src/main/app/session-end.ts), 2026-10-05): while recording work is pending the end is refused and the same quit runs; once it exits Windows goes on. With nothing pending the session ends as chosen. The hold is certain only while a window is visible (Settings open): Windows terminates an app with no visible window that refuses the end without a reason registered through ShutdownBlockReasonCreate, which Electron does not expose, so a recording made from the menu bar alone gets its stop and save started at once but may be terminated before they finish. Not verified on Windows hardware.

## Quality and encoding

| Setting | Rule |
| --- | --- |
| Video quality | Economy 0.07, Standard 0.13, High 0.24 bits/pixel/frame |
| Video bit rate | Output width × height × frame-rate setting × coefficient, rounded to 100 kbps, clamped to 1.5–60 Mbps; the encoder's average bit rate |
| Resolution | The probed source size in pixels unchanged; 1080p/1440p/4K caps preserve aspect/orientation, never upscale, and use even dimensions when downscaling. The engine scales to that size: `SCStreamConfiguration`'s width and height on macOS, the Direct3D 11 video processor on Windows |
| Frame rate | 30/60; only darwin enables 60; other platforms use 30 without rewriting stored settings. The setting is the encoder's rate and the pacer's grid ([frame-rate request](#frame-rate-request)) |
| Video codec | H.264: no frame reordering (decode order is presentation order, so no composition offsets), a key frame at least every second of presentation time (each fragment starts at one), BT.709 tags |
| Audio | AAC-LC, 48 kHz stereo, 256,000 bps target; Windows' encoder takes at most 192 kbps, so it records at 192 and says so in the warnings |
| Format | MP4 with H.264 + AAC (`video/mp4;codecs=avc1,mp4a.40.2`, reported in `prepared`), written as hybrid MP4 ([plain MP4 at save](#plain-mp4-at-save)) |

The host computes the size and bit rate from the settings in [quality.ts](../../src/shared/quality.ts) once the engine has probed the source, and passes them to `prepare`; the engine never reads settings. Encoders (plan 076's D4): on macOS VideoToolbox, which uses the Mac's media engine when it has one, and AudioToolbox's AAC converter; on Windows Media Foundation's H.264 and AAC transforms. Windows encodes with the GPU's hardware H.264 encoder when it can and with Microsoft's software encoder otherwise ([Windows specifics](#windows-specifics), plan 078); a Windows without Media Foundation is `media_components_missing`, checked before a recording ([errors](#errors)). 60 fps stays macOS-only (`isFrameRateAvailable`): other platforms remain unverified at 60.

CaptureReport keeps its fields, so the Recorder's log and notices are unchanged: the output width and height, the frame-rate setting, 48,000 Hz and 2 channels, the requested bit rates, and warnings, which hold the engine's own (a macOS that cannot leave the menu bar out, RecordStuff not found among the shareable applications with the evidence of why, Windows' lowered AAC rate, which H.264 encoder records on Windows and why, the per-frame log's path) and a summary line (`native engine: source WxH, AAC priming N frames, X own app(s) excluded, Y system window(s) hidden`). The engine scales to the size it was given and paces frames at the chosen rate, so the Chromium path's frame-rate downgrade and unconfirmed resolution-cap notices, which compared what Chromium granted with what was asked, were removed with their strings (plan 078). The bit rates are targets, not measured output; output still needs ffprobe measurement. The engine delivers 101–102% of its target at 30 and 60 fps (2026-10-15/16), so Settings' size estimate is the target plus audio at both rates (`estimatedBytesPerMinute`); it no longer doubles the 60 fps video for MediaRecorder.

### Frame-rate request

The frame-rate setting goes to the engine unchanged, as the encoder's rate and the [pacer](#frame-pacing)'s grid. Capture itself is asked for more: a minimum frame interval of a quarter of the frame interval (`Pacer::capture_interval_ns`, 8.3 ms at 30 fps and 4.2 ms at 60), set as `SCStreamConfiguration.minimumFrameInterval` on macOS and `MinUpdateInterval` on Windows, well below any display's refresh period at these rates, so capture delivers every refresh and every slot has a frame near it. ScreenCaptureKit's minimum interval is a floor, not a period, and it delivers on the display's refresh: asked for an interval near the frame rate's, each frame lands two or three refreshes after the last, and 30 fps on a 60 Hz display comes out 33 or 50 ms apart. Measured on the signed bundle: twice the frame rate dropped 1.8% of 30 fps frames to 50 ms gaps (2026-10-14); asking for every refresh by name (no minimum interval) dropped 0.17% at both 30 and 60 fps against 0.06% and 0.11% with a quarter, for about the same CPU (10.8% against 10.4% of a core at 30 fps, 14.4% against 15.0% at 60; 2026-10-15). The quarter stays.

The hidden renderer met the same floor through Chromium and asked for 30.3 and 62.5 fps to record the setting (plan 041; results in the [verification history](../verification/history-2026-09.md#plan-041-closure--2026-09-26)); that request was removed with it.

## Frame pacing

The engine keeps one captured frame per slot of a grid anchored at the recording's time zero with the frame rate's interval ([pacing.rs](../../native/capture/src/pacing.rs)), as OBS's frame-rate divisor and Cap's pacing do: a 60 Hz display then gives 30 fps exactly, each kept frame two refreshes after the last. A frame more than half an interval before the next slot is left out; one at or after that is kept for the slot nearest it, and the slot after that becomes the next. A frame left out stays the newest picture: if the screen then stands still, the refresh thread encodes it at its slot once that time has come (`Pacer::due`), never later than the present, so a change captured afterwards is still newer.

- **Display time.** Frames keep ScreenCaptureKit's display time, about 11 ms ahead of their arrival (Windows: the frame's `SystemRelativeTime`). Stamping them on arrival moved the flash-to-beep offset from −7 and −15 ms to +5 and +3 ms but dropped 1.4% and 16% of the frames, because arrival jitters with the callback's scheduling and the grid keeps the wrong ones (2026-10-15).
- **Idle refreshes.** ScreenCaptureKit reports a refresh at which the screen did not change as an idle frame without a picture. When it is a slot's, the newest picture is encoded again at it (`frame_unchanged`), as Chromium repeats one, instead of the slot taking the next picture a refresh late. On 2026-10-16 the stop report's new counters showed 15–37 idle frames per 15 s, and every 50 ms gap at 30 fps on a 60 Hz display then was at an idle refresh.
- **Skipped refreshes.** ScreenCaptureKit also skips a refresh now and then, delivering neither a picture nor an idle frame for it: the per-frame log of 2026-10-17 found about five per 15 s at 60 Hz, two deliveries 33.3 ms apart (the stop report's "33.3 ms apart at most" had been read as no refresh missed). When the refresh skipped was a slot's, the file had a frame 50 ms after the last, then one 17 ms after that as the grid caught up. Now, when capture delivered a frame since the last kept one that was too soon to keep and the next delivery comes more than an interval and an eighth after the last kept frame, the newest picture is encoded at the slot in between, an interval after the last kept frame, before the new delivery is judged (`Pacer::skipped`, `fill_skipped`). Only after a frame left out: a source that delivers only when the screen changes (Windows) and changes more slowly than the frame rate is kept as it comes.
- **A still screen.** While nothing changes, the last frame is encoded again every second (`REFRESH_NS`), so a key frame still comes every second, fragments keep closing and `progress` keeps reaching the stall guard. While a camera is shown the newest frame is encoded at every slot instead, with the camera's newest picture composed into it (`Core::encode_every_slot`, [camera](#camera)), so the encoder runs at the full rate however still the screen is; hidden or off, the camera leaves this pace as it was.
- **The stop.** A frame is kept only when its time is before the stop. The newest change the pacer left out is encoded at its own capture time before the stop, so it lasts until the video's end; the muxer's own drop of later samples stays as a guard.

The stop report is logged with the host's timing line: how far ahead of the host clock frames were stamped (average and maximum), and `capture delivered N pictures and M frames without one, X ms apart at most`; a longest gap of two refresh periods means capture skipped a refresh. For one frame at a time, the per-frame log ([tooling](tooling.md#per-frame-log)) records every delivery and every encoded frame with the pacer's decision. Measured on a 60 Hz 1920×1080 display: dropped frames 0.00% at 30 fps and 0.06–0.22% at 60 fps (2026-10-14, against Chromium's 0.00% and 0.14–0.22%); in `pnpm matrix -- quick` 0.66–2.17% of 30 fps frames were 50 ms apart against Chromium's none (2026-10-15), 0.22–0.44% after the idle-refresh fix (2026-10-16), and 0.00% in all three cases, the longest gap 33 ms, after the skipped-refresh fill, against 0.44–0.66% on the same build without it back to back (2026-10-17, plan 078). Chromium could not be measured again, its path having been removed. Recording CPU on the same machine (2026-10-16, `pnpm measure:cpu -- --fps 60 --repeat 3`): 10.4% of a core at 30 fps and 14.0% at 60, against 15.3% and 23.3% through Chromium.

## Audio

The track's inputs are system audio (by default everything the system plays except RecordStuff), a chosen set of apps' sound or none, and the microphone; they are mixed into the one AAC track. The user chooses only whether the microphone joins the default system audio: chosen apps' sound is in the engine and its tests (`RECORDSTUFF_CAPTURE_AUDIO` is a development switch). The microphone (plan 074) is off by default and turned on in Settings → Recording → Audio or by the idle menu's Record microphone ([desktop](desktop.md#microphone-permission)), with the system default input or a chosen one; a session reads the switch and the device once, as it reads the quality, and since plan 079 the device can be switched while recording (**Switching while recording**, below). With it off nothing new is opened or mixed, so the recorded audio-quality evidence stands. With it on, the track is system audio plus the microphone, raw, at unity gain unless the user moves an input's volume fader (**Volume**, below), with no voice processing ([audio quality](audio-quality.md#16-the-native-audio-path--why-it-preserves-fidelity)). Measured on macOS on 2026-10-16 ([audio quality §18](audio-quality.md#18-microphone-results--2026-10-16)), before the engine changes that followed the comparison against OBS, Chromium and Cap (the soft limit, the mono microphone, one-frame drift correction, taking a stalled microphone back, Windows' packet times and ducking opt-out): the system part kept its format and level, with no ducking; the microphone's sound arrived 20–40 ms before the frame of the same key press; recording CPU rose by about 3.4 points of a core. A desktop round on the changed engine the same day verified the mono microphone (an iPhone recording's left minus right was −inf dB over 35 s), a microphone-on `pnpm acceptance` pass and the lost microphone's notice and record; fidelity, sync and CPU were measured again on CoreAudio's HAL by plan 078 ([audio quality §19](audio-quality.md#19-microphone-results-on-coreaudios-hal--2026-10-17)). The microphone is untested on Windows.

- **Capture.** On macOS system audio comes from the picture's `SCStream` (48 kHz stereo float, `excludesCurrentProcessAudio`), whose filter already leaves RecordStuff's apps and therefore their sound out; when the picture's filter is not the sound's (a window, chosen apps, or chosen apps' sound) a second, audio-only stream with its own filter carries it. On Windows it is WASAPI process loopback (Windows 10 2004 and later) of everything except RecordStuff's process tree, whose root is main, opened at 48 kHz stereo float with the audio engine converting. Neither path applies voice processing; the hidden renderer needed explicit constraints for that ([audio quality](audio-quality.md)). `pnpm audio:quality` passed every check natively and through Chromium on 2026-10-15, the clock at −0.07 ppm natively and −1.45 ppm through Chromium.
- **One clock.** Every timestamp is host time in nanoseconds (mach absolute time; QueryPerformanceCounter), counted from time zero at `record` ([timing.rs](../../native/capture/src/timing.rs)). Audio is placed by counting samples, as Cap does: the first buffer is placed exactly, and each later one continues where the last ended unless its timestamp disagrees by more than 10 ms (480 frames). A disagreement just past that, by at most 2 ms more, is a device clock drifting and is corrected by one frame per buffer, a frame of silence inserted or one dropped, so a microphone 20–100 ppm off is held at the tolerance without a whole-tolerance cut or hole every few minutes; a larger gap is filled with silence at once and a larger overlap dropped at once. The stop's log line reports, per input, the frames of silence inserted and dropped to keep it on the clock when there are any. Audio therefore cannot drift against video by much more than the tolerance however long the recording lasts: a 10-minute recording measured 0 ms drift with 600 of 600 flash–beep pairs, and audio and picture equally long in every file (2026-10-14, before the one-frame correction). On Windows a microphone's packet times follow Chromium's rule (crbug.com/1439283), since some drivers give QueryPerformanceCounter positions seconds off, or 0: a device whose first packet's position is more than 500 ms from the moment it arrived is timed by arrival (that moment less the packet's length) for the rest of the stream, and a packet flagged `AUDCLNT_BUFFERFLAGS_TIMESTAMP_ERROR` takes its arrival time ([timing.rs](../../native/capture/src/timing.rs) `PacketTimes`, [win/audio.rs](../../native/capture/src/win/audio.rs) `pump`). Loopback's positions are not checked: they come from the render clock the recording is timed by.
- **The mixer.** The track is the sum of the inputs, stereo, each at its volume, which is unity (0 dB) unless its fader was moved: nothing is resampled, collapsed or levelled, and with one input at 0 dB it is that input's samples exactly ([mixer.rs](../../native/capture/src/core/mixer.rs)). With the microphone on there are two inputs, system audio and the microphone, summed sample by sample. Where two or more inputs with nonzero samples sum past −1 dBFS (loud media under a voice), a tanh soft limit takes the sum towards full scale without reaching it, continuous at the threshold; one input sounding, or a sum below −1 dBFS, is left exactly as it is, bit for bit, and the stop's log line counts the limited samples when there are any. It advances to where every input has delivered, so inputs that arrive at different delays still line up, and also with the clock, 500 ms behind it, counting what an input has not delivered by then as silence: WASAPI's loopback sends no packets while nothing plays, and without this the audio fragments would wait for the next sound. Sound that arrives for a part already mixed is dropped and counted; the stop's log line names those late frames by input when there are any.
- **Volume** (plan 075's D21, 2026-10-18). System audio (with any chosen apps' sound) and the microphone each have a volume, set by a fader under each meter in the Recording Studio, as OBS's mixer gives each source one: a whole percent of the input as it comes, from 0% to 600% (since 2026-10-21; whole dB from −60 to +12 before, read as the nearest 5%), saved as the setting `audioVolume` ([audio-volume.ts](../../src/shared/audio-volume.ts)), 100% by default, and used by every recording. Main gives the engine each volume in dB (`volumeDb`). The engine scales each buffer's samples by its input's volume as it arrives, before the meters, the mute and the mixer (`Core::set_gains`, `NativeCapture.setGains`): −60 dB and below is silence (the fader's bottom, 0%), the top is 600%, about +15.6 dB (`MAX_GAIN_DB`), and an input raised above unity goes through the mixer's tanh soft limit above −1 dBFS on its own, so a raised voice is not clipped by the encoder; at 100% (0 dB) the factor is exactly 1 and the samples are untouched, so the recorded audio-quality evidence stands. The Recorder sends the volumes as a `gain` message once a session is prepared, before its levels are watched or its sound taken, and again on each change while previewing or recording (`Recorder.updateGains`); the host logs `audio: system … dB, microphone … dB`, and a change applies from each input's next buffer. On 2026-10-18 (signed bundle, a 440 Hz tone through the speakers) System audio's fader taken to its bottom from the keyboard 6.5 s into a recording was logged by settings and the engine within 3 ms, and the file, peaking at −24 dB before, was silent (−inf) from 8 s on while the tone still played. In step 8's round the same day (the microphone on, hearing the speakers) System audio's fader went to the bottom 12.2 s in and the Microphone's 15.2 s in: the file peaked at about −23 dB, then at −31 and −41 dB from the microphone alone, and was silent from 16 s on; the System audio meter had fallen to silence 4.5 s after its fader reached the bottom.
- **Meters and mutes** (D19). While the Recording Studio shows a meter in sight, main asks the session for its levels (`StudioLink`, a `levels` message with `watching`, `NativeCapture.watchLevels`), which the capture process sends the page on the Studio's port, the preview's, without passing through main (plan 081; `studio-port.ts`); only then does the engine gather each kind of input's loudest sample as its sound arrives (system audio and apps' sound together, the microphone apart), after its volume and before its mute, and tell them about 10 times a second (`LEVELS_INTERVAL_NS`; 15 before D21) as `levels` events. The meters run from −60 dB to full scale. A prepared session reads sound while its levels are watched, so a Live preview's meters move before anything is recorded ([camera](#camera)); nothing is mixed or written then. A mute (a `mute` message, `NativeCapture.setMuted`) puts silence in the input's place from its next sound on, so the input stays on the clock and unmuting needs no realigning; a muted input's meter still moves, greyed. Mutes belong to the recording in progress only, as hiding the camera does; volumes are settings. On 2026-10-17 (signed bundle, the system's Submarine sound looping through the speakers, the BenQ monitor's microphone on) muting system audio 11.1–15.6 s and the microphone 17.9–22.1 s into a recording was logged by the recorder and the engine and showed in the file's peaks per half second: the beeps at −7.5 to −8.9 dB unmuted, at −10.9 to −11.4 dB with system audio muted (the microphone's pickup of the speakers alone), and with the microphone muted the beeps unchanged but the floor between them down from about −55 dB to −63 dB and silence. Volumes, meters and mutes run in the shared core on Windows too, untested there on hardware.
- **Edit list.** The file's edit list skips the AAC encoder's priming, so presentation time 0 is the first captured frame. AudioToolbox reports its priming; Media Foundation's is measured when the encoder is made (0 frames on the CI runner, unconfirmed on Windows hardware).
- **Up to the stop.** At `stop` the track is cut at the stop's sample count; capture keeps running until the sound up to that moment has arrived, at most 250 ms, because capture hands audio over a few tens of milliseconds late. What has not arrived by then is silence, and the log says how long the drain took and how many frames were filled. The audio track is therefore as long as the video's.
- **Microphone capture.** On macOS CoreAudio's HAL (plan 078 step 6, [mac/hal.rs](../../native/capture/src/mac/hal.rs)): an AUHAL input unit on the device by its UID, read as one channel of 32-bit float at the device's own rate, because the AUHAL does not convert rates on input (Apple's TN2091), and converted to 48 kHz with AudioConverter (a Bluetooth headset runs at 16 or 24 kHz); each buffer is timed by its `mHostTime`, the host clock the screen's samples use. The HAL's real-time thread only renders the buffer and hands it on; conversion, mixing and encoding run on a reader thread. It is a plain HAL unit, never the voice-processing one. The UID is the string AVFoundation called the device's unique ID, so a stored choice is still found, and the device list comes from the HAL too; the authorization is still read from AVFoundation. It replaced an `AVCaptureSession`, whose device state follows a main run loop that the utility process does not run. On Windows a WASAPI capture endpoint opened as 48 kHz mono float with `AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM`, so the audio engine mixes the device's channels down. The core hears the one channel in both of the track's channels, as Cap does, so an audio interface's microphone on input 1 is not in the left ear only; a stereo microphone is recorded as mono. On Windows the stream calls `IAudioSessionControl2::SetDuckingPreference(TRUE)` (best effort) so opening it does not make Windows duck other apps, whose lowered sound the recorded system audio would carry. Starting it is described under [start](#start).
- **Losing the microphone and taking it back.** A microphone is told lost (`microphoneLost`, from the engine through the host to the Recorder) when it delivers no sound for 2 s while the session records or drains to the stop, and when its sound cannot be read (a sample-rate conversion error on macOS, a capture-pump error on Windows). The 2 s without sound is what tells a disconnection on both platforms. The recording goes on with system audio, the microphone's part silent. When its sound comes back the track takes it again from then on, the gap left as silence, and the engine tells `microphoneResumed`, which the Recorder logs as `microphone resumed: the microphone delivered sound again after {n} s`; a later dropout is told again. On macOS the sound comes back from a device that was disconnected and connected again too (plan 078 step 6). A device that leaves does not stop its AUHAL unit: the HAL moves the unit to another input, which goes on delivering sound at that input's rate, so silence alone never told the loss (the 2026-10-17 round: an iPhone Continuity microphone disconnected and a FreeClip 2 headset put in its case were each followed by another microphone's room, and the headset's take dropped 2.9 million frames that arrived at the wrong rate). Every 250 ms the reader therefore checks that the unit still records its device (`InputUnit::moved`: the device alive, the unit's current device unchanged, the device's nominal rate unchanged); when it does not, the unit is closed at once, what it queued is discarded, and the silence that follows tells the loss after 2 s. A device that is gone, or still there but silent for 2 s, is opened again by the same UID as soon as the HAL lists it, retrying after 2 s and backing off to 30 s, as Cap reconnects through cpal. The device taken back is always the one opened at the start, or the one the user switched to since (plan 079), the system default included: a new default input does not replace it, and the recording never switches to another microphone on its own (the maintainer's decisions, 2026-10-17). The HAL follows devices without a main run loop, which AVFoundation did not (074's probe). On Windows, after `AUDCLNT_E_DEVICE_INVALIDATED` (an unplugged endpoint), the microphone is told lost and the stream's thread looks for the same endpoint ID once a second, opening it again when it is `DEVICE_STATE_ACTIVE`, with the same backoff after a failed open; the device opened at the start is the one taken back, the default's included. This is checked by CI's compilation only; no Windows microphone was unplugged. Each dropout is logged as `microphone lost; recording continues without it: …`. The first per recording raises the notification "The microphone dropped out during the recording. Only system audio was recorded while it was out.", held until capture ends like the capture notices ([desktop](desktop.md#tray-and-notifications)), whose click opens Recording settings; the saved record carries `"microphoneLost":true`, and the session log's saved line adds "(the microphone dropped out partway)". An encoder failure that the microphone's sound happens to reach first is the recording's failure, `capture_failed`, not a lost microphone. On 2026-10-16 an iPhone Continuity microphone switched off 85 s into a recording gave the lost line, notice and record, and a file whose video and audio were both 98.984 s long; on AVFoundation none of the later disconnections was taken back after it reconnected. On 2026-10-17, on the HAL with the device check, a HUAWEI FreeClip 2 put in its case 14 s into a recording was closed at once (`stopped being recorded (the device is gone)`), told lost 2 s later, opened again at 16 kHz when it reconnected (`resumed … after 20.8 s`), and the file's 20 s in between were silent, with no other microphone's sound; video and audio were both 44.785 s, nothing dropped, and the record carried `microphoneLost`. Taking back an iPhone Continuity microphone was not verified: once disconnected from the iPhone it stayed unavailable to macOS. A pause from the iPhone's own controls, about 1 s, stayed under the 2 s and was not told.
- **Switching while recording** (plan 079's D3, the maintainer's decision of 2026-10-19). While a recording records the microphone, from its countdown until it stops, Settings' Input device stays open and a choice switches it: main saves the setting and the Recorder sends `{ type: "microphone", sessionId, deviceId? }` (`Recorder.updateMicrophone`, `NativeCaptureHost.setMicrophone`; absent `deviceId` is the system default input), and the host calls `NativeCapture.setMicrophone`. The microphone's thread opens the new device before it closes the old one, strictly: a chosen device that is not connected is refused rather than replaced by the default. The sound the old one queued goes into the track first and the new one's from then on, each device on a queue of its own; the aligner drops the new one's first buffers where they overlap the old one's last and leaves a gap between them as silence, and the 2 s without sound that tells a loss counts from the switch (`Shared::microphone_switched`), since a Bluetooth headset can take a second or two to open. The engine tells `microphoneSwitched` with both devices' names, which the Recorder logs as `microphone switched from {a} to {b}`, and the saved line and record name every device recorded in turn (`microphones`, only when there was a switch); a device that does not open is told as `microphoneSwitchFailed`, logged, and the old one goes on; one that is the device recorded already (System default and that device by name) is answered as kept. The Recorder sends one switch at a time and a choice made meanwhile after its answer, so each answer is the request it answers. From then on the new device is the one taken back after a loss. A Live preview is prepared again instead, as for any other input change. A session without the microphone keeps the picker locked: the switch itself is not changed while recording. On Windows the stream's thread does the same between packets ([win/audio.rs](../../native/capture/src/win/audio.rs)), checked by CI's compilation only.
- **Listing the inputs.** The device picker's list (`listMicrophones`) comes from a short-lived capture process of its own, bounded at 8 s and ended once it answers, so the engine stays out of main and an attempt's process is never asked. It runs only while preferences are unlocked (idle), one at a time, is cancelled when a recording starts or the state leaves idle, re-checks at `ready` that it is still allowed, and is refreshed when the Settings window is activated, when the microphone is turned on and by Search for devices beside the picker (plan 079's D2), whose button is busy until the listing answers. Since plan 079 the list also follows connections on its own: while the Settings window is in sight and the microphone is on, a monitor process of its own (`MicrophoneMonitor`, `NativeCaptureHost.openMonitor`) follows the device list (`watchDevices`) and answers each change with a new `microphones` list, 300 ms after the last of a burst (`DEVICES_SETTLE_MS`), as one connection is told several times; on macOS a listener on the HAL's device list and default input, told on the HAL's own thread since the process runs no main run loop (`hal::DeviceWatch`), on Windows `IMMNotificationClient` (checked by CI's compilation only). It goes on while recording, unlike the short-lived listing, so an input connected then can be switched to (D3; it captures nothing then); the microphone turned off, a quit, or the window hidden or closed ends it, and one that ends on its own is started again at most three times while the window stays open.
- **The input level in Settings** (plan 079's D1). Under the Input device, the Input level shows the chosen input's level between recordings, so the user can check that it hears them without recording: a horizontal meter from −60 dB to full scale, `role="meter"`, drawn as the Recording Studio's meters are. The monitor process reads the input a recording would open (the chosen one, or the default while it is not connected) through the same capture as a recording, an AUHAL input unit on macOS and a 48 kHz mono WASAPI stream on Windows, and tells its peak and RMS over each 50 ms, 20 times a second (`core::meter::LevelMeter`, `NativeCapture.startMeter`), before any volume; nothing is resampled, mixed or written. It reads only while the Recording tab shows the meter in a focused window, the microphone is on and, on macOS, access is allowed, and stops when the window loses focus, closes or hides, when a recording starts, when the microphone is turned off or when another input is chosen, which starts it again on that one; a changed device list starts it again too. A device that leaves or that the HAL moves stops it (`meterStopped`) until the list changes. While recording the row rests and says the Recording Studio shows the recording's level.

## Camera

The camera (plan 075, 2026-10-17 and 2026-10-18) is composed into the recorded frames by the engine, on the GPU before the encoder, as OBS composes its canvas, instead of being recorded as a window on the screen or kept as a track of its own: the user's screen stays clear, nothing covers the app below or catches its clicks, and the bubble can be moved while recording. It is off by default; the Camera switch in Settings → Recording or the idle menu's Record camera turns it on and asks for access, and the Recording Studio, a tab of the main window, shows the preview and arranges the bubble: width and height 5–60% of the recorded display's shorter side, a circular-arc rounding 0–100% (100% being half the shorter side), a position kept per display as a fraction of the free space, and Mirror in recording ([camera-layout.ts](../../src/shared/camera-layout.ts); the permission and the Studio in [desktop](desktop.md)). When the switch is on and the camera available, `start` carries the camera ([start](#start)); with it off nothing is opened or composed and recordings are as before.

- **Capture on macOS** ([mac/camera.rs](../../native/capture/src/mac/camera.rs), D16). AVFoundation's `AVCaptureSession` with an `AVCaptureVideoDataOutput`, the 1280×720 preset in the camera's video-range 4:2:0 YUV (`420v`), delivered as IOSurface-backed pixel buffers on a serial queue and stamped with each frame's presentation time on the host clock. No run loop is needed: an iPhone's Continuity Camera delivered about 30 frames a second in the capture process and in plain Node (2026-10-17). A chosen camera is found by its unique ID, and one not connected falls back to the system default. The system default is macOS's `systemPreferredCamera` (macOS 13), which follows a Continuity Camera and the user's choice in other apps, else AVFoundation's default, else any connected camera, never a suspended one: on 2026-10-17 `systemPreferredCamera` sometimes answered nothing and AVFoundation's default was the FaceTime HD camera behind a closed lid, connected but suspended, which opens and runs but delivers nothing, so a recording with System default chosen opened it and had no camera; the device listing, which the Settings picker reads in a process of its own, uses the same rule. The engine only reads the authorization: main asks when the switch is turned on.
- **Capture on Windows** ([win/camera.rs](../../native/capture/src/win/camera.rs)). Media Foundation's source reader: cameras listed by `MFEnumDeviceSources` and found by their symbolic link, which stays the same while a camera is connected to the same port; Windows has no system default camera, so the first one listed stands for it, and a chosen one not connected falls back to it. NV12 near 1280×720 at up to 30 fps, the reader decoding a camera's MJPEG and scaling (`ENABLE_ADVANCED_VIDEO_PROCESSING`), read on a thread of its own, uploaded to the GPU per frame and stamped on the host clock as it arrives.
- **The newest frame only.** Each frame goes to the core's `CameraFeed` ([core/camera.rs](../../native/capture/src/core/camera.rs)), which keeps only the newest with its time, so a camera slower or faster than the recording never queues frames: the compositor takes the newest whenever a frame is encoded (the core's tests feed 15 and 60 fps cameras into 30 fps).
- **The compositor** (D2, D15). One compute shader, [compose.wgsl](../../native/capture/shaders/compose.wgsl), is the only source of the bubble's rounding, crop and mirror: [build.rs](../../native/capture/build.rs) validates it with naga and translates it to Metal's MSL and Direct3D 11's HLSL (shader model 5.0), and a shader that does not translate fails the build on every platform. Its `luma` kernel writes the output's Y plane and `chroma` its CbCr plane, blending the screen's and the camera's video-range YUV by the bubble's coverage, anti-aliased over one luma pixel; the camera fills the bubble by its largest centred crop of the bubble's shape, and a BT.601 camera frame is converted to the recording's BT.709. The shader reads its textures by hand rather than with a sampler, which naga's HLSL would write as a Direct3D 12 sampler heap. The parameters come from [camera_layout.rs](../../native/capture/src/camera_layout.rs) (`compose_params`), whose formula the TypeScript layout shares through the same 180 cases (`camera-layout.cases.json`), so the preview's bubble and the recording's agree at every resolution cap. Not wgpu: it would share only the shader, which naga already does, and on Windows it has no Direct3D 11 back end; an editor or effects of several passes would be the time to move to it, the shader already in WGSL.
  - On macOS ([mac/compositor.rs](../../native/capture/src/mac/compositor.rs)) Metal reads the screen's frame and the camera's and writes the output in place as textures of their IOSurface planes (`CVMetalTextureCache`, no copy), in one command buffer, before VideoToolbox. It replaced a Core Image compositor that rebuilt a filter graph on the CPU for every frame and cost about 10 points of a core at 30 fps (2026-10-17). Its output buffers are laid out as VideoToolbox's own pool for the encoder, padded to whole 16-pixel macroblocks with 64-byte rows: without the padding (1080 and 1800 rows are each 8 short of one) VideoToolbox copied every composed frame into a buffer with it before encoding, about 0.5 ms of CPU a frame at 1920×1080 and 0.6 ms at 2880×1800 (2026-10-19).
  - On Windows ([win/compositor.rs](../../native/capture/src/win/compositor.rs)) Direct3D 11 compiles the HLSL at run time (`D3DCompile`). Direct3D 11.1 writes an NV12 texture's planes as render targets but from a compute shader only with 11.3's optional planar views, so each kernel writes a texture of its own plane (`R8`, and `R8G8` at half size) and one triangle per plane draws it into the NV12 output as a render target. The screen's NV12 is copied into a texture the kernels can read, since capture's are made for the video processor only; on a device without a video processor (WARP) the screen, which is then BGRA in memory, is converted on the CPU as the encoder would and uploaded. Composed frames come from the compositor's own pool, which either H.264 encoder takes as it takes capture's ([Windows specifics](#windows-specifics)).
  - Without a camera there is no compositor and the frames go to the encoder as before; a frame composed without a camera frame (before its first, or while lost) or while hidden is the screen's byte for byte, which the pixel tests check on both platforms.
- **Changes while recording** (D7). The bubble's placement, size, rounding and mirror change from the Studio while recording, from the next encoded frame. The Recorder sends `{ type: "cameraLayout", sessionId, camera, hidden }` ([protocol](../../src/shared/protocol.ts), checked by `isMainMessage`; `camera.deviceId` is ignored, as the camera is not switched while recording) through `Recorder.updateCamera`; the host logs `camera layout: …` and calls `NativeCapture.setCameraLayout(options, hidden)`, and the compositor reads its layout at each frame (`Compositor::set_layout`, `set_hidden`). A change is taken only once the session is prepared (a Live preview, the countdown, the start or the recording); a layout changed while a Live preview still prepares is sent once it is prepared. On 2026-10-17 (signed bundle, an iPhone's camera) a width change during a recording was logged by settings, the recorder and the engine within 4 ms and composed at once, and Mirror turned off 3.6 s in flipped the camera between the frames at 3.2 and 4.2 s; a bubble dragged in the preview during recordings was composed from then on where the preview showed it.
- **Hiding** (D13). Hide camera / Show camera in the tray's recording menu and Show camera in recording in the Studio choose for that recording only. Hidden, the compositor composes nothing and the camera stays open, so showing it again is immediate; showing it moves the pacer to the current slot and wakes the refresh thread, so no slot the hiding left empty is filled afterwards. On 2026-10-17 Hide camera at 13.1 s and Show camera at 23.7 s were logged by the host and the engine within 20 ms each, and frames at 8, 18 and 30 s showed the bubble, the screen alone and the bubble again.
- **The pacer.** While the camera is shown, `Core::encode_every_slot` makes the refresh thread encode the newest screen frame at every slot capture leaves empty, the camera's newest picture composed into it, so the camera moves on a still screen; hidden or off, the still-screen pace of one frame a second returns ([frame pacing](#frame-pacing)). The encoder then runs at the full rate all the time, which is most of the camera's cost. Measured: 30.00–30.03 and 59.97–60.03 fps files with the camera, the camera delivering 1,766–1,795 frames a minute with none dropped (2026-10-17); a 60 fps recording started from the Studio, 1,247 frames in 20.77 s with no interval over 17.5 ms (2026-10-18).
- **Unavailable at the start** (D11). The camera is opened during preparing, before the screen's stream, so access not allowed, no camera, or one that does not open fails the start as `camera_unavailable` before any countdown ([errors](#errors)); the opened camera, its layout and whether the preview is watched are in the report's warnings (`camera: …`). On 2026-10-17 the camera opened in 219–241 ms during preparing.
- **Losing the camera and taking it back** (D12). A camera that delivers no frame for 2 s while recording (`CAMERA_SILENT_NS`, from the first encoded frame to the stop) is told lost (`cameraLost`), as the microphone is ([audio](#audio)): the recording goes on, and from then on the compositor is given no camera frame, so the recording shows the screen alone instead of a frozen picture. The first frame after a loss tells its return (`cameraResumed`, logged by the Recorder as `camera resumed: the camera delivered frames again after {n} s`), and it is composed again from that frame. The platform also tells a loss at once: on macOS a watch thread checks every 250 ms that the device is still connected and closes its session if not; on Windows a failed read (unplugged, access withdrawn, taken by another app) is a loss, and a source silent for 2 s while recording is shut down, which ends a read that waits for it. A lost camera is then opened again by the unique ID or symbolic link it was opened with, never another, after 2 s and backing off through 4, 8 and 16 s to 30 s. On macOS composing the camera into a frame can fail too (a GPU command buffer that errors, such as around sleep and wake): that frame is the screen alone, the failure is told once as a loss (its recovery is only logged, since a camera's return is the feed's to tell), and the recording goes on, where until 2026-10-22 it failed. The Recorder logs each dropout as `camera lost; recording continues without it: …`; the first per recording raises "The camera dropped out during the recording. The screen was recorded without it while it was out." once capture ends, the saved record carries `"cameraLost":true`, and the session log's saved line adds "(the camera dropped out partway)". On 2026-10-18 the maintainer chose Disconnect on an iPhone used as a Continuity Camera 31.6 s into a recording: the loss was told after 2 s without a frame, the recording went on without the camera and was saved marked, and the notice waited for the end; the engine tried the same camera again 9 times and, the iPhone staying disconnected, never had it back, which the maintainer judged right for a Disconnect the user chose. Picking the iPhone up or unlocking it did not pause it (3,250 frames in 106 s, none over 2 s apart), and its Pause sends black frames, not none, so neither is a loss. A camera's return within a recording is checked by the core's tests only, and whether AVFoundation's device lists follow a camera that leaves without a run loop is still open: neither list changed when the iPhone disconnected, and no USB camera was at hand to unplug.
- **Closing.** The core closes the camera when capture ends, when a prepared session is released and when the session is dropped (`CameraControl::close`), so a stop, a cancel, a failure, sleep and quit all close it and turn its light off. On 2026-10-17 the light went off at once at a stop and at a countdown cancelled at 2; on 2026-10-18 a countdown cancelled from the tray left the menu bar's camera indicator gone 2.5 s later and its temporary file removed.
- **The camera's age.** At the stop the session logs `camera: the camera's picture N ms older than its frame on average (min to max ms) in K frame(s)` (`CameraAges`): each composed frame's time less the capture time of the camera frame in it. On 2026-10-18, at 60 fps with an iPhone's Continuity Camera, the wireless link included, it was 113.9 ms on average, 87.7 to 138.7 ms over 1,005 frames. Windows stamps camera frames on arrival, so its figure leaves out the time the camera and Media Foundation hold a picture.
- **The preview** (D17, D19, D20). Every session has a preview, composed by the same kernels at 640 pixels wide (`PREVIEW_WIDTH`, or the output's width when smaller, `preview_size`) 10 times a second (`PREVIEW_FPS`, 15 before D21; the recording keeps its own rate), or 5 while no one works in the Studio (`PREVIEW_RESTING_FPS`, plan 081's D1: the page asks on the Studio's port, `NativeCapture.setPreviewRate`, and the preview thread makes a frame at every other tick, `preview_tick_shows`) and encoded as a 1 Mbps H.264 stream by VideoToolbox on macOS and Microsoft's software encoder on Windows, with the `avcC` record on every key frame so a page that joins late can start; a session without a camera makes it through a hidden compositor of its own, so the Studio shows the screen alone. Frames are made only while the Studio has the preview in sight: main gives the session's capture process one end of a fresh `MessageChannelMain` and the page the other (`StudioLink`, the `cameraPreview` message, `NativeCapture.setCameraPreview`; the same port carries the levels and the page's rate), so frames go from the engine to the renderer without passing through main, and the page decodes them with WebCodecs' `VideoDecoder` into a canvas ([preview-decoder.ts](../../src/renderer/lib/preview-decoder.ts)) in software: Chromium's hardware decoder held about six frames back (397 ms at 15 fps with `optimizeForLatency` and a Constrained Baseline stream), while software decoding shows each frame about 2.5 ms after it was sent, for the same processor time. A preview whose encoder fails stops showing; the recording does not. Of D17's options, NV12 frames read back and drawn with WebGL measured 12.7 points over the recording (2026-10-17), and a native layer hosted by main was not pursued; the compositor's IOSurface handed to the Studio through Electron's `sharedTexture`, with no encoding or decoding, worked on macOS but saved nothing and was not kept ([plan 080's record](../verification/history-2026-10.md#plan-080-closure--2026-10-19)). Before a Live preview the Studio shows the display's outline with the camera alone through `getUserMedia`, which never captures the screen.
- **Live preview** (D5, D20). Live preview in the Studio prepares the recording's own session (the display through its filter, the camera composed, system audio and the microphone) and holds it in the Recorder's `previewing` phase without writing, while the state stays idle, so the tray and the shortcut still start a recording; no sentinel is written for it. Start, from the Studio, the tray or the shortcut, takes that session through the countdown into the recording, with no gap and no camera reopened, and names the file then, at Start's time (`EngineFileWriter.retarget`), or once prepared if it still prepares. Leaving the Studio, hiding or closing the window, sleep and quit let a preview go as a cancel (`preview`); a preview that cannot start is no recording's failure (nothing is reported or kept, and the Studio says why); a change to the display, quality, menu bar, folder, microphone or camera prepares it again while the Studio is open. On 2026-10-18 (signed bundle, camera and microphone on) a Live preview was prepared in 783 ms with its temporary file empty; Start took it through the 3 s countdown with the picture never breaking and the camera opened once (912 frames, none dropped, for preview and recording), and the file was named 00-46-31, Start's time, not the preview's 00-46-16; a second preview, left by changing tab, was cancelled (`cancelled (preview) while previewing`), its temporary file removed and its capture process gone, with no failure recorded. Known on both platforms: a camera that stalls during a Live preview, before recording, is not told lost or opened again until a recording starts, since loss is judged only while recording.
- **CPU** (D18, D21; [tooling](tooling.md#cpu-budget)). Composing in Metal and encoding every slot cost about 4 points of a core at 30 fps and 7 at 60 over a recording without the camera (Core Image: about 10; 2026-10-17). - **Windows.** Built on 2026-10-18 and checked by CI only, as plan 075 allows for Windows: the compositor's six pixel tests (byte-identical without a camera, the rounded bubble and its colour, hiding, a new layout on the next frame, mirror, the preview's scaling, a screen uploaded from memory) and the preview stream's test pass on the `windows-2025` runner (WARP). ## Message and stop ordering

<a id="chunk-and-stop-ordering"></a>

```mermaid
sequenceDiagram
    participant U as User
    participant R as Recorder
    participant N as NativeCaptureHost
    participant P as Capture process (engine)
    participant W as EngineFileWriter
    U->>R: toggle start
    R->>W: reserve .recording.mp4
    R->>N: start(id, quality, path)
    N->>P: fork; ready
    N->>P: start(id, quality, native)
    P-->>R: prepared(capture)
    Note over R: countdown N s (overlay leaves 300 ms before 0)
    R->>P: record(id)
    P-->>R: started(id)
    loop About once a second while media arrives
      P-->>R: progress(id, bytes)
    end
    U->>R: toggle stop
    R->>P: stop(id)
    P-->>R: stopped(id)
    Note over R: idle; the save goes on in the background
    R->>W: finish
    P-->>N: finished(id, file) or writeError
    N-->>W: the file's outcome
    W-->>R: final path (link or copy)
    R-->>U: saved notification
```

Every message carries the session ID, and the Recorder acts only on its current session's; a `prepared`, `started` or `progress` for any other session makes it stop that session. The process speaks only to its attempt: `start` while a session exists, or `record` for a session that is not prepared, is refused as `capture_start_failed`; a repeated `record` is ignored. The protocol has no sequence numbers, because no media crosses it: the engine writes the file, and `progress` only reports the bytes written so far.

`stop` while the engine prepares marks the session cancelled; the host cancels the engine once `prepare` returns and answers `stopped`. `stop` while prepared cancels it at once; the file stays empty and main removes it. `stop` while recording calls the engine's `stop`, which ends both tracks at that moment ([audio](#audio), [frame pacing](#frame-pacing)), halts capture, flushes the encoders and asks the writer to finish; it answers once capture has ended, the host logs the stop report and sends `stopped`, then calls `finish`, which answers once the file is plain or why it is not is known, and sends `finished` (bytes, how long after the stop, and why it stayed fragmented, if it did) or `writeError`. Separating the two (2026-10-15) keeps a slow volume's save out of the 10 s stop deadline: plan 076's first prototype finished the file before `stopped`, so such a save would have been killed as `stop_timeout`. A capture failure during recording sends `error` with `capture_failed`; a write failure sends `writeError` with `disk_full` or `output_write_failed`, and the Recorder fails the session in both cases unless the finalizer already owns it.

## File completion and failure

The engine's writer ([writer.rs](../../native/capture/src/writer.rs)) is one thread that owns the file and the muxer. Capture and encoder callbacks hand it encoded samples over a channel and never wait on the disk, so a slow or stalled volume cannot hold capture up and a busy main event loop cannot delay writing. It syncs the file every 5 seconds, as main's FileWriter did, and reports the bytes written once a second while media arrives. The first I/O failure is classified as main's `classifyWriteError` names it (ENOSPC, Windows' disk-full errors and Rust's `StorageFull` are disk_full; everything else output_write_failed), reported once as `writeError`, and nothing more is written; what was written stays. Media waiting for the disk is bounded at 64 MiB (`BACKLOG_LIMIT_BYTES`): past it the writer refuses all further media, so the file has no gap, and reports output_write_failed with a backlog detail. There is no pause, drop or retry, so sustained disk throughput below the bit rate ends the recording with a preserved partial instead of unbounded memory. There is no disk reservation, folder switch, quality downgrade or unlimited-recording guarantee.

After the engine's outcome, `EngineFileWriter.finish` checks the file's size and publishes it as `.mp4` with a hard link, trying suffixes `-2`, `-3`, … on a final-name collision ([publishRecording](../../src/main/recording/file-writer.ts)). A link never replaces an existing name (EEXIST moves on to the next suffix, up to `-100`, after which the save fails as output_write_failed and keeps the `.recording.mp4`), takes constant time and needs no free space, so saving takes the same time for a 15-second and a one-hour recording and a low-disk early stop can still save. The saved file is the same file the recording wrote, so its creation time is the recording's start. A volume that refuses the link for any other reason, such as exFAT (ENOTSUP) or some network volumes, falls back for this and every later suffix to an exclusive copy (`COPYFILE_EXCL`), which is synced before the temporary name is removed; that copy takes time proportional to the file and needs the file's size in free space. A failed publication reports disk_full for ENOSPC, like any other write, and output_write_failed otherwise. `COPYFILE_FICLONE` is still requested but on macOS never clones: libuv implements no clone there (`COPYFILE_FICLONE_FORCE` fails with ENOSYS in Electron 44), so before plan 037 every save, on APFS too, was a full copy. After publication the temporary name is removed on a best-effort basis; only then does Recorder emit saved with the actual destination. A cleanup failure leaves the temporary name, a second link to the saved file (or a full copy after the fallback), but does not invalidate the saved file. The log's `finalize timing` line names how long the host took to stop, the wait for the engine's outcome, the engine's finish (`to plain MP4`, or `kept fragmented (<reason>)`), main's size check, the publication (`by link` or `by copy (link <code>)`), the cleanup and the checkpoint took, and the bytes; its `flush` is always 0, since the engine syncs its own file.

Success requires nonempty media, and `EngineFileWriter.finish`, the only publication step, is the gate. The engine writes nothing until its first frame is encoded, so a stop before that leaves zero bytes. The engine's write error, or the reason it ended without finishing the file, is reported first with its own code (a reason without one is output_write_failed). Otherwise a zero-byte file is removed and the finish rejects with `capture_start_failed` and the detail `capture ended without media; no bytes were written`, the code the first-media deadline already uses; when a cancel or quit had asked to stop on start, the attempt ends as that cancel instead. Recorder routes the rejection through its single failure path, so no saved event or `.mp4` is produced and an immediate retry starts cleanly. Abandon is idempotent, so the failure path's later cleanup cannot delete a same-second retry that has reused the freed name. There is no minimum duration; a very short nonempty recording is saved.

Nonempty is a necessary minimum, not proof of a playable file. The engine starts the file with a key frame at time zero and ends both tracks at the stop, and Cap's AVFoundation writer likewise [rejects a finish without a last frame](https://github.com/CapSoftware/Cap/blob/ce785e705e79652adba4b8bf752669c4093499e0/crates/enc-avfoundation/src/mp4.rs#L961-L990) (static review at that revision), but nothing decodes the file at runtime. Playability is established only by media verification such as ffprobe and full decoding during acceptance.

Failure first detaches the session, clears deadlines, stops the host and returns the UI to idle; it then abandons the writer, which reads the file's size: a nonempty file is kept under its temporary name and reported as the partial path, an empty one is removed on a best-effort basis, and a size that cannot be read (other than a file already gone) marks preservation uncertain. A partial from a failure during recording is normally the fragmented file as written, since the capture process is ended when the attempt is torn down. Partial files are not automatically repaired or remuxed. Exclusive creation protects the temporary name and every final name. Complete writes are distinct from fsync durability and do not guarantee recovery after every crash, power loss or filesystem failure; stronger durability requirements need targeted tests before implementation changes.

The free-space guard reads `fs.statfs` of the output folder. Below the stop threshold it requests the normal stop, so the file is finished and published while space remains; the saved event carries `stoppedEarly: "lowDisk"`, the log says so, and the saved notification reads "Saved {file}. Stopped early: the disk is almost full." Such a recording is a success and never enters failure history. If publication still fails, the ordinary failure path and partial preservation apply.

Sleep is handled the same way (plan 050). From `starting` until the state settles, main holds one `powerSaveBlocker` of type `prevent-display-sleep` ([keep-awake.ts](../../src/main/recording/keep-awake.ts)), so idle display sleep and idle system sleep cannot end the capture; every path back to idle or needsPermission and `will-quit` release it, and the log names each blocker. A sleep the user asks for (Apple menu → Sleep, closing the lid without an external display, the power button) or a low-battery or thermal sleep cannot be refused, and in 035's N31 capture ended about 150 ms after it began. So the `powerMonitor` `suspend` handler, after only setting the tray's notification hold, calls `Recorder.systemWillSleep()` before any logging, and `stop()` sends the stop to the host before the `stopping` state reaches subscribers: a recording requests the normal stop with `stoppedEarly: "sleep"`, so the file is published like any stop and the saved notification reads "Saved {file}. Stopped because the Mac went to sleep."; a countdown is cancelled with reason `sleep` at once and an attempt still preparing when its `prepared` arrives, since unlike quit (plan 065) sleep does not stop a pending capture request (whatever else ends an attempt that sleep already marked before `prepared` — a host error or loss, a removed display, a timed-out or refused capture request, or a folder that did not open in time or reported an error — cancels it too, because nothing was captured), and one whose `record` was sent stops once capture starts. The engine ignores capture failures only once its drain to the stop has ended (at most 250 ms); a stream that ends inside the drain still reports `capture_failed`, and the Recorder, still stopping, fails the session. Through the hidden renderer macOS entered sleep about 5 s after `suspend` and the save took 13 ms (plan 050's acceptance), so it normally completes before sleep; a save still running when the Mac sleeps completes after waking, but timers keep counting during sleep, so its stop deadline may already have passed. Sleep during a recording has not yet run through the native engine (plan 077). Continuing the same file after waking is not attempted; Cap instead rebuilds its own capture into the same recording.

Before `record` nothing is written: the engine opens the reserved file at `prepare` but starts its writer at `record`, so a start failure or cancel leaves the empty file, which is removed, and its outcome is empty. (The hidden renderer's writer opened before a capture request that could wait 120 s and synced meanwhile, so its start failures first drained the writer for up to 2 s to report a retained disk error; nothing needs that now.)

Interruption evidence is one sentinel file per session in `userData/recording-sessions/`, named by the session ID and holding the session ID, start time and temporary path. It is written with the atomic writer before the temporary file is created, so a crash cannot leave a temporary file that no sentinel names; a failed write is logged once and does not block the recording. When the rewrite for a collision suffix fails, the earlier attempt's sentinel is removed, because it names the colliding file, which belongs to another session. Every terminal outcome removes the session's own sentinel after its result is published, and a normal quit waits for that removal. At launch, before the history restore, each unfinished sentinel left by an earlier process becomes one `app_terminated` failure entry ("RecordStuff did not exit normally while recording.") whose path is a lookup hint rechecked like a restored partial: partial only while a nonempty file exists there, otherwise unknown. Its time is the session's start. The sentinel is removed only once the entry has been saved, including by a later automatic history retry, so the history owns the evidence first and a reviewed, removed entry cannot return; its ID is derived from the session, so a history that stays unsaved retries at the next launch without a duplicate. The single-instance lock and the process's own session list guarantee that reported sentinels belong to dead processes. A complete temporary write (`<id>.json.tmp`, flushed before a rename a power loss kept from the disk) is the newest content and takes the sentinel's place; a torn write or invalid content names no media and is discarded; a sentinel that cannot be read at launch, or that a newer version wrote, is kept for a later launch. No other file in the output folder is scanned, and nothing is recovered, remuxed or repaired.

### Plain MP4 at save

The engine writes a hybrid MP4 ([mp4.rs](../../native/capture/src/mux/mp4.rs), [session.rs](../../native/capture/src/mux/session.rs)), written from ISO/IEC 14496-12, -14 and -15 with no code taken from other muxers (plan 076's D4 and D5). While recording, the file is an initialization segment (`ftyp`, then a `moov` with `mvex` and empty sample tables) followed by fragments (`moof` + `mdat`), each written in one append. Tracks are fragmented independently, one track per fragment as ISO BMFF allows, so a late audio packet never holds video back: a video fragment closes at the first key frame after a second of video, so every fragment starts with one, and an audio fragment every second. A file cut off at any point is still a fragmented MP4 that players read up to its last whole fragment, which is what a crash or a failure keeps: killing the capture process mid-recording left an 8.0 s playable partial whose tracks differed by 147 ms, because each track's fragments are flushed about once a second (2026-10-14), and `pnpm acceptance:lifecycle`'s `native-crash` mode keeps checking that the partial is kept.

A fragmented file is slow to open. On 2026-10-10, a 36-minute, 2.7 GB recording from the hidden renderer (2,106 fragments, no `sidx` or `mfra`) took about 1.1 s, 1,722 range requests and 358 MB read through `recordstuff-media:` before Chromium showed its first frame, repeated by every open, including the seek bar's frame preview and the full-screen window; the same media as a plain MP4 took 27–41 ms, 14–17 requests and 14–19 MB. Appending an `mfra` did not help: Chromium still read every fragment. AVFoundation (QuickTime, Quick Look) could not open that fragmented file at all (`-11832`), and opened the plain one. So the file is made plain before it is published, in place, as OBS's hybrid MP4 does ([`mp4_mux_finalise`](https://github.com/obsproject/obs-studio/blob/7d98bebe1115b12608837b622164ea5fe6d9483a/plugins/obs-outputs/mp4-mux.c#L2967-L3028), static review at that revision). The muxer keeps every sample's size, duration and sync flag and one MP4 chunk (an `stsc` run) per fragment while recording, and at `finish`, after a sync:

1. The whole `moov` is appended at the end: the sample tables of every sample where it already lies (`co64` past 4 GiB), the real durations, the edit list that skips the AAC priming, and no `mvex`. Then the file is synced.
2. The first 16 bytes of the old `moov` are overwritten with a 64-bit `mdat` header covering everything from there to the new `moov`, so the file reads `ftyp`, `mdat`, `moov`. Then the file is synced again.

Nothing is copied or moved and no space beyond the index is needed, so saving stays constant time. Interrupted between the two steps, the file is the fragmented one with an unused index after it, which players read as before. The muxer never leaves a file players cannot read: when the index cannot be written the file is truncated back to the fragmented one, when the header cannot be written its original 16 bytes are put back, and in each case the file is published fragmented with the reason in `finished` and the `finalize timing` line (`index not written: …`, `header not written: …`, `header not confirmed: …`). A writer that refused media for its backlog finishes nothing: the file stays fragmented, as written, and the save fails. Unlike OBS, which writes no barrier, each step is synced before the next, and the saved notification follows both. The temporary `.recording.mp4` is the one file throughout, so an interruption anywhere leaves the same evidence. Partial files stay fragmented; nothing rewrites them.

Cap takes the other route: it records DASH segments into a folder and, after stop, copies them into a new MP4 in the background ([remux.rs](https://github.com/CapSoftware/Cap/blob/8d808e09e0541efdf5e8318f57bbf3b2ed88bc76/crates/enc-ffmpeg/src/remux.rs), static review at that revision) while its editor plays the segments; RecordStuff saves one file the user can open at once, so it keeps OBS's in-place finish. The same finish was first built in TypeScript over MediaRecorder's fragments (`mp4-finalize.ts`, verified on 2026-10-10 by streaming four real recordings through it and comparing every packet with ffmpeg `framemd5`); the engine's muxer carries its cases (64-bit `mdat`, the index, a failed index write left fragmented) in its Rust tests, and the TypeScript module was removed with the hidden renderer.

## Errors

| Category | Codes | User outcome |
| --- | --- | --- |
| Permission/environment | permission_denied, unsupported_os_version | Settings/relaunch guidance or version explanation |
| Source/codec | no_display, display_unavailable, no_audio_track, media_components_missing | Refuse start and explain missing capability |
| Microphone | microphone_unavailable | Refuse start before any countdown: "The microphone was unavailable, so recording did not start.", with the platform's microphone privacy pane in the guidance |
| Camera | camera_unavailable | Refuse start before any countdown: "The camera was unavailable, so recording did not start.", with connecting a camera, the platform's camera privacy pane or turning Camera off in the guidance |
| Capture | capture_start_failed, capture_failed, capture_host_crashed, capture_host_unresponsive | Return idle and reveal any preserved partial file; before `record` every capture loss is capture_start_failed with an empty outcome |
| Storage | output_open_failed, output_write_failed, disk_full | Explain location/disk failure and preserve bytes where possible |
| Stop | stop_timeout | Stop waiting for capture and attempt partial-file cleanup |
| Previous process | app_terminated | Reported only at launch from an interruption sentinel; says the app did not exit normally and the file may be incomplete; never sent by the capture host |

Who produces each: the engine rejects with `code|detail`, and the host passes on only the capture codes of `HOST_ERROR_CODES` (anything else becomes `capture_start_failed`) and only `disk_full` or `output_write_failed` as write errors.

- `permission_denied`: macOS, when the shareable-content query is declined or a stream refuses to start with `-3801`. A `permission_denied` while macOS reports access granted marks the running process as needing a relaunch (PermissionWatcher).
- `unsupported_os_version`: main's preflight, macOS before 13.
- `no_display`: the engine cannot find the display main chose (macOS: its ID is not among the shareable displays; Windows: no display contains the point). `display_unavailable` is main's own refusal ([screen selection](#screen-selection)).
- `no_audio_track`: Windows, when system-audio loopback gives no client.
- `media_components_missing` (plan 078): Windows without Media Foundation, a Windows N edition without the Media Feature Pack. Main looks for `mfplat.dll`, `mfh264enc.dll` and `mfaacenc.dll` in System32 at launch, as it checks the screen permission on macOS: when one is missing, Start recording is unavailable and the tray says why, the shortcut is refused and logged, and Settings' status card says so with Open Optional features (`ms-settings:optionalfeatures`). The code is the last line for what that check cannot see: the module cannot even load without `mfplat.dll`, which windows-rs links as an import (the host process then exits with code 4 instead of 3), Media Foundation does not start, or the H.264 or AAC encoder is not registered. Its guidance names the Media Feature Pack under Optional features and a restart. The Chromium path's `mp4_unsupported` was removed with it; a failure history holding one becomes unreadable, which the maintainer accepted (2026-10-16), and Settings' Reset failure history replaces it.
- `microphone_unavailable` (plan 074): with the microphone on, access is not allowed (macOS: denied, restricted, or never asked, which the development Electron always is, since it has no usage description and macOS refuses it without a prompt), there is no input device, or the device fails to open; on Windows also a failure at or after the capture client's `Initialize`, and `E_ACCESSDENIED` at `Activate` or `Initialize` is reported as "access is not allowed (Settings > Privacy & security > Microphone)". The guidance names System Settings → Privacy & Security → Microphone on macOS and Settings → Privacy & security → Microphone on Windows, or turning Microphone off. It is deliberately not grouped with the screen-permission failures, whose Open System Settings opens the Screen Recording pane. A microphone lost while recording is no failure ([audio](#audio)).
- `camera_unavailable` (plan 075's D11): with the camera on, access is not allowed (macOS: anything but authorized, since main asks when the switch is turned on and opening without access delivers nothing), no camera is connected, or the camera cannot be opened, added to a session or read in a format the engine takes; on Windows also the cameras cannot be listed or the chosen one refuses its first read (the start waits up to 3 s for a first frame or a refusal, then goes on). The guidance names System Settings → Privacy & Security → Camera on macOS and Settings → Privacy & security → Camera, which must allow desktop apps, on Windows, or turning Camera off. A camera lost while recording is no failure ([camera](#camera)).
- `capture_start_failed`: every other failure before `record`, among them a source or encoder that cannot be made, a stream that does not start, no first frame within 3 s, a module that does not load for another reason (the process exits with code 3 before `ready`), and the no-media gate.
- `capture_failed`: a stream stopped with an error, a captured item closed, an encoder failing while recording (also when the microphone's sound reaches the failure first); main also uses it for a stall, a removed display and a `stopped` it did not ask for.
- `capture_host_crashed` (the process exited during a session) and `capture_host_unresponsive` (two unanswered pings) are main's own findings, as are the folder, disk and deadline codes.

Main replaces a host error with its own refusal reason only where that refusal explains it: `DisplayMedia.explain` maps `capture_start_failed`, `permission_denied` and `no_display` to the reason main refused the display for this attempt, once.

## Screen selection

`display-source.ts` separates live Screen API resolution from capture-source matching. Explicit choices store `{ kind: "display", id, label }`; labels are presentation only. Missing/duplicate targets fail immediately. Missing/duplicate capture sources or topology changes retry at 150 ms intervals, at most three enumerations. An enumeration exception is reported through `failed` and refuses the attempt as `capture_start_failed` (`source_missing`), not as a permission problem. The recorder timeout remains the outer bound for a hung enumeration. Settling or superseding an attempt cancels callbacks and retry timers; delayed completions cannot grant capture or replace diagnostics. `display-media.ts` owns this state across attempts: the preference snapshot, the refusal reason that explains the next host error, the active display watched for removal (also where the countdown overlay goes), and the display diagnostic. The Recorder begins a `DisplayMedia` attempt as the session starts, and `NativeCaptureHost` asks it for the display while the capture process starts; a display chosen for an attempt that has since been torn down is discarded by the host's generation check.

`display_unavailable` means the exact target could not safely resolve, with separate `target_missing`, `source_missing` or `topology_changed` detail. No matching by name, size or position occurs, and stored ids are never rewritten automatically. Id reuse is not proof of physical hardware identity. The engine receives Electron's display ID, which on macOS is the `CGDirectDisplayID` ScreenCaptureKit lists; on Windows those IDs name no monitor, so main also passes the physical point at the display's centre (`screen.dipToScreenPoint`), and the engine records the monitor that contains it. Screen metadata is logical DIP size and scale; output dimensions come from the engine's probe in pixels and the resolution cap.

Display removal is noticed by main's topology watcher, which invokes the recorder's idempotent `capture_failed` path with the `target_removed` diagnostic and preserves the partial without switching targets; the engine may report its own end first (macOS: the stream stopped with an error; Windows: the captured item closed). The hidden renderer's structured `displayFailure: "track_ended"` for a video track that ended is still accepted by the protocol, but the native host never sends it. Removal once a normal stop was sent, whether the host has replied or the file is already finalizing, does not create a failure or diagnostic: the stop reply or its deadline decides, and the file keeps what was recorded up to the stop. Display removal through the native engine has not yet been tested on hardware (plan 077).

Failure presentation is independent of the terminal event: failureStatus reports pending immediately and partial/empty/unknown after cleanup, while saved/failed remains the terminal contract. A size that cannot be read sets preservationUncertain and cannot be presented as confirmed preservation. See [recording failure results](desktop.md#recording-failure-results).

Failure IDs are UUIDs across recorder instances. Pending status includes the writer candidate path when known; settled events remove that candidate for empty results, retain it as a lookup hint for unknown results, and expose a partial path only for confirmed preservation. Each persisted result restores interrupted cleanup as unknown, never as ongoing processing or a successful save.

## Own windows and system UI

RecordStuff's own windows are left out of every recording, those opened after the start included (the countdown overlay, Settings), and nothing turns this off (075's D14, moved into plan 076 on 2026-10-15). The camera's bubble is not a window: the engine draws it into the frames ([camera](#camera)), so it needs no exception, and the Recording Studio, which shows the preview, is one of RecordStuff's windows and is left out like the others. On 2026-10-18 a 60 fps recording started from the Studio, which stayed on the recorded display, had the bubble in its frames and no RecordStuff window.

- **macOS.** The display's `SCContentFilter` excludes RecordStuff's applications: those whose process IDs main passes, and every app whose bundle identifier begins with main's, which covers its helpers. Excluding the application, rather than listing windows, also leaves out windows opened later and their sound. Off-screen windows are read too. ScreenCaptureKit lists an application only while it owns a window, though, and a menu-bar app with nothing open owns none: on macOS 26 the status item is Control Center's window. Plan 078 found this was why the development app logged `RecordStuff's own app was not found among the shareable applications`, and why the signed bundle reported `1 own app(s) excluded`: every one of its recordings had a countdown, whose overlay window existed when capture was prepared; with no countdown and nothing open, either build would have recorded the Settings window or the player opened during the recording. Main therefore makes one hidden 1-pixel `BaseWindow` on macOS before the engine reads what it may capture (`beforeCapture` in `NativeCaptureHost`), made once and never shown, with no page and so no renderer process. When RecordStuff is still not found, the warning says so with the evidence: the process IDs asked for, how many applications and windows were listed, the windows those processes own and the related applications. On 2026-10-16 Settings, opened a second into a recording on the main display, was on the screenshot and absent from the recording's frame of the same moment, which showed the window behind it; RecordStuff's app menus in the menu bar were left out too, while its status item stays, as 075's D14 notes no product hides its own.
- **Windows.** Windows.Graphics.Capture records the whole display and cannot leave out another process's windows, so main marks its own with `setContentProtection(true)`, which is `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` there (shown black before Windows 10 2004), from `start` until the attempt is torn down; windows created meanwhile are marked as they appear. They are let back in once the capture process has exited, or at most 5 s after it was told to end, so screenshots of Settings work between recordings; a later attempt's exclusion is never undone by an earlier one's release. Untested on Windows hardware.

D6, Hide menu bar and Dock (Settings → Recording, after Screen, off by default, locked while recording, saved as `hideSystemUi`; decided 2026-10-14), leaves the system's chrome out of the recording while the user still sees it: the menu bar and its status items, the Dock, desktop icons and widgets. The filter lists their windows (those at the Dock, main-menu and status window levels, and Finder's and Notification Center's windows below the normal level) as exceptions, and on macOS 14.2 and later sets `includeMenuBar` off; an older macOS says in the warnings that it cannot. An app's open menu is that app's window above these levels, so it is still recorded, which the setting's ⓘ says. Off by default because existing recordings must not change after an update and what is on screen is what users expect to be recorded. On 2026-10-15 the engine reported 35 system windows hidden and the frame showed the wallpaper where the menu bar had been; the Dock was not on screen in that round, so its absence is plan 077's. The engine gets the switch only on macOS; on Windows the row reads Hide taskbar and is unavailable, because Windows.Graphics.Capture cannot leave the taskbar out, and nothing is cropped.

## Windows specifics

The Windows module ([native/capture/src/win](../../native/capture/src/win)) shares the core, the clock, the mixer, the writer and the muxer with macOS; what differs:

- Capture: Windows.Graphics.Capture of the monitor containing main's point, with the cursor and without the yellow border where the system allows it. Each BGRA frame is converted at once on the GPU by the Direct3D 11 video processor into NV12 at the recording's size (scaled, BT.709 limited range); only frames that are encoded are read back to memory. A device without a video processor (WARP, on a virtual machine or a runner without a GPU) copies each frame to a staging texture and converts encoded frames on the CPU. The captured item closing ends the recording as `capture_failed`.
- Encoding (plan 078 step 4; decided by the maintainer on 2026-10-16: the hardware encoder, on by default, as Cap does): the GPU's hardware H.264 encoder, a Media Foundation asynchronous transform found with `MFTEnum2` by the capture device's adapter LUID and given the Direct3D device, takes the converted NV12 textures where they are, so encoded frames are not read back to memory ([win/hardware.rs](../../native/capture/src/win/hardware.rs)); a platform-independent driver feeds it as it asks and watches it ([async_encoder.rs](../../native/capture/src/async_encoder.rs)). Following Cap (revision `83237e9`, AGPL code read for design only), OBS and Chromium, none of which trusts a hardware encoder without a way back ([encoder_choice.rs](../../native/capture/src/encoder_choice.rs)): never on WARP, never AMD's (Cap skips it; OBS dropped Media Foundation encoders after AMD's broke), and a new adapter, driver or size first passes a self-test, a few grey frames encoded and decoded back by Microsoft's software decoder and the grey checked, because some drivers open a session and then emit green or black frames. The outcome is kept in `h264-encoders.txt` under the folder main names in `RECORDSTUFF_ENGINE_DATA` (`userData/engine`), since each recording runs in a process of its own. A failure before the first sample reaches the muxer (the self-test, opening, an error or the watchdog) records with the software encoder silently, the frames the hardware encoder still held included; during a recording the watchdog (60 frames taken without a sample, three refused in a row, nothing back for 5 s, `MEError`) ends the recording with what was written as `capture_failed`. Either failure is recorded, and later recordings on that adapter and driver use the software encoder. `RECORDSTUFF_SOFTWARE_ENCODER=1` forces the software encoder; there is no user setting. Otherwise Microsoft's software H.264 encoder on its own thread, as before; the warnings name the encoder and why. Either way the Annex B output becomes the muxer's length-prefixed samples. The AAC encoder takes 16-bit PCM at 96–192 kbps only, so the 256 kbps target is lowered to 192 kbps with a warning, and its priming is measured when it is made.
- Sound: WASAPI process loopback of everything except RecordStuff's process tree, which keeps the countdown's ticks out as on macOS; it sends nothing while nothing plays, which the mixer's clock covers. The microphone is the chosen WASAPI capture endpoint or the default; a chosen one that is missing or not `DEVICE_STATE_ACTIVE` falls back to the default, and a failure at or after `Initialize` (48 kHz mono refused, the event, its handle, the capture service, `Start`) is `microphone_unavailable` for the microphone, `capture_start_failed` for loopback; `E_ACCESSDENIED` at `Activate` or `Initialize` names the privacy setting. The microphone is opened as 48 kHz mono float with `AUTOCONVERTPCM`, opts out of ducking with `SetDuckingPreference(TRUE)`, and has its packet times checked ([audio](#audio)); after `AUDCLNT_E_DEVICE_INVALIDATED` it is told lost and opened again by its endpoint ID once connected ([audio](#audio)).
- Camera (plan 075): Media Foundation's source reader and the Direct3D 11 compositor, which draws compose.wgsl's kernels into NV12 render targets and, on WARP, works from the screen read back to memory; the preview comes from Microsoft's software encoder ([camera](#camera)). CI only; a real camera is untested.
- Frame rate: 30 fps only (`isFrameRateAvailable`).
- Verification is by CI only (plan 076's D8, the maintainer's on 2026-10-14). The `native-windows` job on `windows-2025` runs `cargo test`, decodes a synthetic file, and records the display, an area, a window and one process's sound as live tests; `pnpm check` loads the module, and the installer smoke loads the installed one. For the hardware encoder the runner, which has no GPU, tests that WARP lists none and the software encoder records with the reason, the self-test's check against the software encoder (grey back grey, black not), and the driver against a fake asynchronous transform that stalls, refuses input, fails and changes its format; real GPUs (NVIDIA, Intel), the pictures they produce and the CPU they save are untested and fixed from users' reports. On the runner (no GPU, a 1024×768 display through the CPU conversion) three seconds gave a decodable file with both tracks 3000 ms long and an AAC priming of 0 frames. Untested on Windows: real capture quality and frame timing, the video processor and any hardware path, own windows absent from the frames, system audio content and A/V sync, the microphone and a camera (the runner has neither), DPI with several displays, CPU, long recordings, and the session-end hold. These are left to users' reports.

## Audit hardening

Explicit Cancel recording also cancels folder opening and capture preparation; repeated start toggles stay ignored for the first second of a start and cancel it after that (plan 065). A prepare that fails halts the streams it had started. `EngineFileWriter.finish` runs once and shares its promise; abandon is idempotent and, after a finish, keeps the file only if the finish failed, so repeated terminal calls cannot delete a newer recording.

Full-copy publication checks free space against the entire recording plus 8 MiB before copying. A destination whose post-copy open/sync/close fails is removed; the original remains. Successful publication writes a durable finalized-path checkpoint before removing its sentinel. A retained completed checkpoint is discarded at launch without an interruption warning. The small publication/checkpoint crash gap cannot prove completion, so an unfinished sentinel explicitly says completion is unknown and a final file may already exist. A failure likewise names its report on the sentinel (`failureId`) before publishing it: a process that ends while that failure's cleanup still runs (a stalled share, then a force quit) leaves a sentinel the next launch reports under the same id, so the history keeps one entry, the saved report, or the sentinel's when the report was never saved (2026-10-05).

Quit protection is installed before the first interactive asynchronous yield. After media settles, settings, geometry and log queues receive a bounded five-second flush; a timeout defers quit and reopens admission. Resolution-cap degradation would be visible in Settings, on the Screen row until the next recording starts or another display or resolution cap is chosen, and in a notification shown after the session settles ([desktop](desktop.md#tray-and-notifications)), with detailed capture warnings in the log; it is raised only when the report carries `capUnconfirmed`, which the native engine never sets ([quality](#quality-and-encoding)).
