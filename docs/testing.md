# Testing guide

[English](testing.md) | [繁體中文](zh-TW/testing.md)

This is the shared test-selection policy for contributors and AI agents. [Tooling](system-design/tooling.md) explains commands and thresholds; [acceptance cases](acceptance.md) define observable results and reporting; [verification records](verification/README.md) preserve evidence, not current instructions.

## Select tests from behavior

Read the diff and affected callers before selecting tests. Classify by behavior and dependencies, not just filename, change size or the author's description. A refactor can affect runtime behavior; a string can be an IPC key rather than display copy. Combine all applicable rows below. Explicit task requirements add to this baseline; record any user-requested waiver as an untested limitation.

Before execution, briefly state the affected behavior, selected checks and why expensive checks are omitted. This is a scope statement, not an approval request. After the final edit, run the required checks against that revision; when a composite command includes a check, do not run it twice. Run `git diff --check` for every change.

| Change / impact | Required checks | Normally unnecessary unless another row applies |
| --- | --- | --- |
| Documentation, plans, instructions or skills only | Check affected relative links/anchors, command names against package scripts, and English/Traditional Chinese consistency; validate skill metadata if changed | App build, unit tests, launching the app, recording. Do not execute commands merely because documentation contains them |
| App source, runtime assets or refactoring | `pnpm check`; add/update focused behavior tests when useful, especially a reproducible bug regression; inspect affected visible behavior when not covered by a more specific row | Packaged/native acceptance when no affected OS or visible behavior requires it |
| Display copy or translations only | `pnpm check`; inspect changed text in each affected language/surface for overflow and meaning. For Settings, use `pnpm acceptance:settings` after the check's build and inspect relevant screenshots | Recording, native shortcut delivery, audio/matrix tests |
| Settings layout, themes, controls, persistence, window lifecycle or settings IPC/preload | `pnpm acceptance:regression` (already includes check/build); inspect relevant screenshots for visual edits; cover changed interactions with real mouse/keyboard input in the fixture | Recording for layout/appearance-only changes. Native checks only for affected OS boundaries or behavior the fixture cannot represent |
| Global shortcut registration/delivery, tray actions, focus, native entry or OS accessibility | `pnpm acceptance:regression` for settings/shortcut integration; otherwise `pnpm check`. Exercise the affected native action on a freshly built app; settings entry can use `pnpm acceptance:settings-shortcut` plus visible observation | Full native state matrix; recording when the changed action cannot start/stop or interfere with capture |
| Recording start/stop, capture host/protocol, encoding, file writing, source/quality selection, recording locks, permissions or shutdown during recording | `pnpm check` plus one recording smoke round on a fresh `pnpm start:app` bundle: start, stop, save, media verification and playback. Add the changed behavior's case (for example output folder or display selection); use settings regression too if its path changed | All resolutions/qualities, long recordings, permission resets and hardware removal unless that behavior is affected/requested |
| Frame timing, sync, resolution/fps or audio fidelity | Recording row plus relevant matrix subset: `pnpm matrix -- quick`, `levels`, `fps` or `long` (choose the affected cases); for fidelity, use the relevant `pnpm audio:quality` diagnostics described in tooling | Full matrix by default; ten-minute recordings without a long-duration requirement |
| Saved notification delivery, timing or Finder reveal | `pnpm check`; fresh signed bundle, then `pnpm acceptance:notification -- --install --clicks 2`. For intermittent/timing fixes use the five-click or `--full` scope matching the failure, and record missing banners | Separate duplicate smoke recording if this run already supplies the required recording evidence; bilingual native runs for unchanged text |
| Update logic, feed filtering or update lifecycle | `pnpm check` and `pnpm acceptance:updates`; add `--full` for feed filtering/timeouts. Use `--logic-only` only when the diff is confined to logic and cannot affect capture, lifecycle or OS integration; disclose the omitted capture scope | Repeating normal recording acceptance unless normal-bundle behavior is also affected; instrumented results cannot establish native tray/browser behavior |
| Test files, fixtures, analyzers or developer scripts only | Relevant tests; `pnpm typecheck` for TypeScript. For runner orchestration changes, exercise the affected runner (including changed failure/cleanup paths); for analyzer-only changes, use controlled media and retained samples | App recording for pure assertions/parsing/report formatting. If changing input delivery or real recording orchestration, exercise that real path; if fixtures load `out/`, build it first |
| Build configuration, Electron/runtime dependencies, preload security, signing or packaging | `pnpm check` and the affected build/package verification (`pnpm start:app` or `pnpm dist:mac`); inspect affected bundle/installer behavior. Electron/media/runtime/entitlement changes also require recording smoke; settings preload/CSP changes require settings regression | Publishing, installing over the user's app, resetting permissions, full capture matrix for packaging-only changes |
| Website source/assets/configuration | `pnpm site:check` (website tests, diagnostics, online manifest verification, build and generated-link checks); inspect affected pages for visual edits | App tests and native recording when no shared app/release input changes |
| Release workflow or publication | Relevant release-tool tests and checks from the [release guide](system-design/releases.md); actual release acceptance is tied to the candidate SHA | Publishing as a test; a code/documentation task never authorizes a tag push |

Examples: a settings CSS spacing fix needs settings regression and screenshot inspection, but no recording; changing a recording shortcut needs integration, real OS key delivery and recording smoke; changing an output-folder label needs copy checks, while changing folder persistence needs settings regression and a saved-file destination check. A permission explanation string does not require permission reset; changing permission recovery does require its affected native case.

## Evidence boundaries and stopping

- `pnpm check` covers root TypeScript/Vitest/build, not website checks, Electron fixtures or real capture. Settings regression covers production components with controlled tray/registration boundaries, not OS shortcut delivery or physical tray clicks.
- A short recording verifies only its tested settings/environment. Media verification does not establish subjective listening, VoiceOver, first-time permissions, long-run stability or installation. Native clicks, physical display removal and playback must be observed when required.
- Reuse media analysis for the same file, analyzer version/options and scope. Reuse prior UI evidence only when the affected implementation, artifact and environment are unchanged; cite its origin. Rebuild changed code before native acceptance. Historical test counts are not current pass thresholds.
- After required checks pass, stop. Broaden/rerun only for a further edit, failure, unresolved risk, changed environment or explicit requirement. Do not ask the user to repeat unaffected passed manual cases. Do not add tests that only mirror implementation or assert documentation wording.
- Distinguish **not applicable** (outside the impact scope, with reason), **not run** (required but not attempted), **blocked** (required but a prerequisite is unavailable), **fail**, and **pass**. A missing permission/tool is blocked, not a reason to relabel a required test unnecessary. A waiver remains not run with the user's reason; never label it pass. Do independent checks while reporting the gap.

## Environment and shared-machine use

Use the pinned pnpm version and lockfile; Node 24 supports the TypeScript runners. Ordinary unit/type/build checks do not need capture permission, signing, Chrome or FFmpeg. Some audio integration tests explicitly skip without FFmpeg/ffprobe; disclose relevant skips. Website verification needs network access. See [signing setup](system-design/signing.md) for native bundles; do not create/import credentials as an incidental test step.

Real recording needs a supported Mac, screen/system-audio permission, Chrome and FFmpeg/ffprobe. System Events runners also need Accessibility/Automation access. Record OS/architecture, source display, audio output/volume and test-material version. Native settings integration needs an Electron-capable graphical session; it does not require a signed installed app. Missing prerequisites should identify the exact blocked layer.

Separate checkouts/worktrees may run independent pure tests concurrently. In one checkout, serialize builds and runners that consume `out/` or `dist/`; do not rebuild beneath an active fixture. A single executor owns the desktop, system audio, global shortcuts and installed-app replacement at a time, even across worktrees. Isolated preferences do not isolate OS focus or capture devices. These are coordination rules, not a claim that every runner provides a cross-process lock.

Before a desktop round, identify its owner, checkout/artifact and intended cases. During development, stopping recordings and quitting/restarting/rebuilding RecordStuff as needed is authorized without additional confirmation; possible active use is not a blocker. Finish saving, restore changed preferences, close owned test UI, quit the tested app normally and confirm process exit before handing the desktop to another executor. A cleanup failure blocks the next rebuild/round; report remaining processes or windows. See [acceptance cases and report format](acceptance.md).

## Report the selected scope

For ordinary edits, include a compact final summary: affected behavior; checks and results; omitted checks with scope reasons; required-but-unverified cases and blockers. Do not create a permanent test report for every documentation edit. For native/recording runs, use the [acceptance report template](acceptance.md#report-template) and preserve the runner's evidence. These same rules apply to humans and LLMs; agent-specific tool operation belongs in skills.
