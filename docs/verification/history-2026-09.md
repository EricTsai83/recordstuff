## Notification switch replaces the native bridge — 2026-09-21

Plan 019 was first implemented as a Node-API bridge to macOS `UserNotifications` (preserved on `wip/019-native-notification-bridge`): a permission state machine, launch-time guidance dialog, status display in Settings and a build/packaging pipeline that compiled a `.node` on every build. Review found the bridge inverted the failure direction. `AppTray.show` was gated on a status that starts as `unknown`, so a bridge that failed to load dropped every notification — and because the gate also suppressed `Notification.show()`, it suppressed the authorization request Electron makes from inside that call. Two realistic triggers existed: the build script compiled for `process.arch` only, and it hard-coded `-mmacosx-version-min=13.0` while the app declares no `minimumSystemVersion`. An affected user would have got fewer working notifications than before the change.

Electron 44.3.0's behaviour was established by inspecting the shipped framework binary, which the plan's first step had asked for and had not completed. `Electron Framework` contains `requestAuthorizationWithOptions:completionHandler:` and Electron's own `Notification authorization granted: ` log string, so `Notification.show()` does request macOS authorization. It contains no `getNotificationSettingsWithCompletionHandler`, and `systemPreferences.getMediaAccessStatus` is typed for `microphone | camera | screen` only, so there is no way to read the state. The `'notifications'` value in `setPermissionRequestHandler` is Chromium's web-content permission, not the app's. This is binary symbol inspection, not a source reading; Objective-C selectors are stored as literal strings, so presence and absence are both reasonably reliable.

The replacement follows Cap (`apps/desktop/src-tauri/src/notifications.rs`): one `notifications` boolean in settings.json, default on, read leniently so a file written before the field exists is not a warning; `AppTray.show` checks it first; Settings → General offers On/Off plus a macOS Open notification settings… action, and the note names System Settings → Notifications → RecordStuff rather than a status the app cannot read. Turning the switch on sends a confirmation notification, which is when Electron's authorization request can reach the user at their own initiative and which doubles as a repeatable delivery test. `native/`, `scripts/build-notifications.mjs`, the `electron.vite.config.ts` compile hook, the `electron-builder.yml` `asarUnpack` entry, the `node-api-headers` dependency and three main-process modules are gone.
