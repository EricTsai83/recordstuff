# 085 — 剪輯既有錄影

[English](085-editing-gate-and-trim.md) | [繁體中文](085-editing-gate-and-trim.zh-TW.md)

狀態：已規劃、尚未開始。建立：2026-10-22，原名「可復原、版本化的編輯專案」；2026-10-23 依維護者要求改為編輯階段的第一個垂直切片：從頭到尾交付一項使用者看得到的能力（剪輯並匯出），而不是在後面兩個計畫完成前什麼都交付不了的儲存基礎設施。D1 已於同日決定：要做這個切片，而且可以刪掉任何一段，不只頭尾；087 等這個切片上線使用後再決定（086 樣式美化已於同日移除）。硬性相依：083（已結案）。佇列的下一個：排在它前面的 084 已於 2026-10-24 結案。依[計畫索引](README.zh-TW.md)與[系列契約](README.zh-TW.md#glide-參考演進083087)執行。本次只寫計畫，以下都尚未實作或驗證。

## 目標與決定

**D1 — 編輯階段只從這個切片開始（維護者，2026-10-23）。** RecordStuff 是小型的選單列錄影工具，[設計決策](../docs/zh-TW/system-design/decisions.md)讓它保持精簡，所以這個階段一次只長一個切片：087 等這個切片上線使用後才決定，屆時若不採用，這個切片本身仍是完整的。流程：在「錄影」分頁，錄影的選單提供**編輯…**；編輯畫面在時間軸上播放錄影，使用者標出要刪掉的部分，可以在開頭、結尾或中間任何地方（多段）；**匯出**在旁邊寫出新檔，原檔不動；編輯會被記住，重新開啟時回到上次的位置。成本：一個編輯畫面、一個匯出 worker，以及每段編輯過的錄影幾 KB 的編輯狀態；錄影不受影響。

**來源絕不被寫入。** 這裡的每條路徑都只讀取原檔：匯出寫出新檔並以新名稱發布，編輯狀態另外存在 userData，本計畫沒有任何地方會以寫入模式開啟來源，也不會重新命名、移動或刪除它。匯出失敗、被取消或崩潰、磁碟已滿或編輯紀錄損毀，最多損失匯出結果或編輯內容，絕不損失錄影。

Glide 的素材與編輯分離是參考，不是照搬它的 schema。

## 開始時要做的決定

- **D2 — 剪輯精確到幀（維護者，2026-10-23），以 smart cut 達成。** 兩個平台的錄影至少每秒一個 key frame，而且沒有 B-frame（macOS 的 `MaxKeyFrameIntervalDuration` 為 1 秒並關閉 frame reordering；Windows 的 GOP 為一秒的幀數且沒有 B-picture）。所以保留的片段本來就可以靠複製**結束**在任何一幀；只有在 GOP 中間**恢復播放**時才需要新的畫面。因此匯出時，影片 sample 除了以下部分都原封不動地複製：在每個不是 key frame 的恢復點 S，從 S 到下一個 key frame 的畫面（最多一秒）會從前一個 key frame 解碼，再用引擎自己的 H.264 編碼器重新編碼成一個從 S 的 key frame 開始的封閉 GOP，解析度、profile 與 level 和來源相同，bitrate 不低於來源。每個接點最多只有一秒的解碼與編碼，所以匯出仍接近磁碟速度，其餘影片完全不動。重新編碼畫面的參數組（SPS/PPS）應該和來源相同，因為來源就是同一個引擎以同樣的設定寫出的；若不同，輸出會為這些 sample 加上第二個 `avc1` sample description。能不能這樣做，在實作時以下方的播放檢查決定一次，不在匯出時臆測：若每個必須支援的播放器都能播放，參數組不同的接點就使用它；若不行，這種接點**退回從 S 之後（含）的第一個 key frame 恢復**，絕不往前退，所以被刪的內容絕不會重新出現，也不會和前一段保留內容重疊；代價是該段保留內容最多少一秒，比這還短的保留片段會被丟掉。調整後的範圍同時套用到影片、音訊與編輯畫面的預覽，編輯畫面會標示該接點並說明移動了多少。**音訊重新編碼**，使用引擎的 AAC 編碼器（[aac.rs](../native/capture/src/aac.rs)），在影片的剪點精確到 sample 剪開，每個接點加幾毫秒淡入淡出，讓接點不會有爆音、也不會偏移同步；不為每個接點使用 AAC edit list，因為播放器對多段 edit list 的支援不一致。
- **D3 — 編輯存在哪裡。** 建議：存在 userData，以來源的身分（路徑、大小、修改時間，以及開頭與結尾各 1 MiB 的 hash）為 key，而不是在輸出資料夾放 sidecar；輸出資料夾的子資料夾就是「錄影」分頁的分類（plan 071）。來源只被參考、絕不複製：編輯不需要副本，而複製每段編輯過的錄影會讓磁碟用量加倍。

## 步驟與責任

- [ ] **編輯狀態。** 每個來源一筆第 1 版紀錄：來源身分、以整數媒體時間（影片軌的 timescale）表示的刪除範圍（已排序、不重疊、數量有上限），以及 revision。只有一個 writer：main，single-instance lock 已讓它對每位使用者唯一（[index.ts](../src/main/index.ts)）；不需要跨程序的檔案鎖。寫入是原子的（暫存檔、fsync、rename、目錄 fsync）；寫入失敗時保留最後一個有效的 revision。讀取有上限（大小限制；畸形紀錄會回報並維持唯讀，絕不重設為預設值）；未知版本以唯讀拒絕。在第 2 版出現之前不做 migration 框架。來源不見或不再符合身分時，編輯顯示為過期，並提供捨棄；沒有任何東西會刪除使用者的檔案。
- [ ] **在匯出 worker 中 remux。** 一個獨立的 `utilityProcess`，以和 capture host 相同的方式監督，在原生引擎中執行 remux：以有上限的 MP4 reader 讀取引擎自己寫出的檔案（plan 076 以來的一般與 hybrid MP4；其他檔案以清楚的原因拒絕）的 sample，複製保留的影片 sample 並把每個刪除範圍的時間戳接起來，重新編碼每個非 key frame 恢復點到下一個 key frame 之間的畫面（D2；兩個平台都用硬體 H.264 解碼與編碼，佇列有上限），解碼並重新編碼保留的音訊（macOS 用 AudioToolbox，Windows 用 Media Foundation），再透過引擎既有的 muxer（[mux](../native/capture/src/mux)）寫出。這不需要新的相依；若有人提議加入，先記錄其授權、平台與回退成本。媒體 buffer 的上限與檔案長度無關；唯一隨長度增長的是輸出的 sample index，muxer 把它留在記憶體中、最後寫入 `moov`（每個 sample 約十幾 bytes，兩小時約幾 MB），和錄影的 writer 現在的做法相同。進度回報給 main；畫面 bytes 絕不經過 main。
- [ ] **安全發布。** main 在來源旁邊保留一個新的目的地（`<name> (edited).mp4`，衝突時加編號），絕不覆寫；worker 在同一個資料夾寫入自己擁有的暫存檔並 sync，main 只在 worker 成功完成 finalize 後以 rename 發布。取消、worker 崩潰、磁碟已滿或退出時，只移除自己擁有的暫存檔；崩潰留下的暫存檔以其專屬名稱辨識，在下次啟動時移除。來源的 bytes 絕不改變。
- [ ] **准入。** 一次只有一個匯出。錄影或 Live preview 進行中時拒絕匯出；匯出期間要求錄影時先取消匯出（錄影永遠優先），透過既有的錄影狀態與退出 gate 處理。匯出期間退出時，在下方的上限內取消。
- [ ] **編輯畫面。** 在設定的「錄影」分頁使用正式元件與 CSS（[UI 對齊規則](../docs/zh-TW/testing.md#測試-ui-與-app-保持一致)）：時間軸上的播放器，可以標出要刪除的範圍（在播放頭分割、選取、刪除、復原），依 D2 精確到幀的剪點（退回的接點會標示），預覽時跳過已刪除的範圍、匯出的進度、取消與錯誤／重試、過期編輯的狀態，英文與繁中。沿用既有的播放器與 library 動作。

## 門檻與完成條件

所有路徑都不改變來源的 checksum，包括在每個發布步驟注入故障（worker 被終止、磁碟已滿、rename 失敗、退出）。匯出的檔案通過 `pnpm verify --sync` 與完整解碼且沒有錯誤，並在 QuickTime、App 自己的播放器（Chromium）與 Windows 的 Media Foundation（由 CI）都能播放並跨接點 seek。每個 smart cut 接點後的第一幀就是來源在要求位置的畫面（與解碼後的來源相比 PSNR 至少 40 dB，重新編碼的那一段也一樣）；每個 fallback 接點（以 fixture 強制觸發）後的第一幀是來源在要求位置之後（含）的 key frame，且被刪範圍的任何一幀都不出現；另有 fixture 涵蓋比 fallback 距離還短的保留片段，它會被丟掉並回報。長度精確到幀等於調整後保留片段的總長。第二個 sample description 的路徑以一個強制參數組不同的 fixture 在三個播放器上各檢查一次，結果記錄為 D2 套用的規則。音畫偏差在來源的範圍內，在開頭與每個接點之後都要量；以純音 fixture 檢查接點聽不出來（沒有超過淡入淡出幅度的跳變）。在產生的 64 MiB 與 2 GiB 檔案，以及一個兩小時、60 fps 的檔案（sample 數最多）上，remux 速度至少為同一個 worker 在同一磁碟上串流複製同樣 bytes 的速度的一半（以有上限的區塊 read、write 與 fsync；不用 clone 或 hard link，所以能 link 時就 link 的 `pnpm bench:publication` 不是參考），每種情況的 worker 記憶體峰值都不超過 64 MiB，取消的 p95 在 1 秒內完成。錄影、閒置與設定的成本維持在[管線 baseline](../docs/zh-TW/system-design/tooling.md#管線-baseline) 的範圍內；一般的 MP4 存檔絕不依賴這些功能。

## 驗證

編輯紀錄（原子寫入、有上限的讀取、未知版本、過期身分）、MP4 reader（以引擎寫出的檔案做 fixture，加上一組畸形輸入）與 worker 協定的 focused 測試；引擎、worker 與 host 的變更跑 `pnpm check`；UI 跑 `pnpm test:scope -- library player`，最後跑 `pnpm acceptance:regression`。在新的簽章 bundle 上、經「好了」交接後做一輪桌面測試：編輯並匯出兩段真實錄影（30 與 60 fps），一段刪掉頭尾，一段刪掉中間兩段，剪點都落在 key frame 之間，在 QuickTime 播放並 seek，再加以驗證。Windows 只由 CI 檢查（remux 是共用程式碼，實機行為未觀察）。CI 不是斷電的證據。
