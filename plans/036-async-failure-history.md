# 036 — Background failure-history persistence and safe exit

This is a separate implementation task, not a claim that current history storage is asynchronous.

## Purpose and boundary

Failure history currently serializes, writes, fsyncs and renames synchronously in main. A slow user-data disk can freeze the UI, and recovery from a failed save requires a manual retry. Move this metadata work off the UI thread, automatically retry recoverable failures, and make normal quit/relaunch account for unsaved history. Recording media already uses asynchronous ordered writes; this plan neither changes media finalization nor admits another recording while a successful recording is still stopping.

Owners: [history coordinator](../src/main/recording-result.ts), [storage](../src/main/recording-result-store.ts), [app lifecycle](../src/main/index.ts), shared models, Settings renderer and tests. Preserve independent IDs, all unread plus the 20 most recently reviewed records, per-ID warnings, manual retry, migration, future/corrupt-file protection, atomic replacement and the 32 MiB safety bound.

025 owns media terminal operations and the single quit coordinator. This plan registers metadata work with that coordinator, rather than adding a competing before-quit handler. Metadata-loss consent never permits abandoning a media write. Execute with [Codex implementation / Opus 5.5 review](../.agents/skills/codex-implement-with-opus-5-5-review/SKILL.md).

## Implementation contract

- [ ] Use an owned background worker or equivalent isolated executor for serialization and filesystem operations. Merely wrapping synchronous writes in a Promise is insufficient. Include startup read/validation/migration and snapshot-transfer cost in responsiveness measurements; never write an empty startup state over history that has not finished loading. Merge failures arriving during load by UUID. If worker packaging changes, verify the worker exists and starts in the built bundle.
- [ ] One persistence owner and one in-flight write. Assign snapshot revisions; an older completion must not clear warnings for newer unsaved changes. Coalesce replaceable pending snapshots, but preserve every failure and explicit action outcome; keep at most one in-flight and one latest queued snapshot, not an unbounded write queue. A timeout does not cancel OS I/O or authorize a competing writer/rename.
- [ ] New errors remain visible immediately. Got it/remove show localized saving feedback, and commit their visible acknowledgement/removal only when the relevant revision is durable. Preserve new arrivals and late file outcomes while an action waits. Disable duplicate action submission without globally freezing recording controls. Failed actions retain the previous state and a per-row error; only genuinely unsaved rows get persistence warnings. Independent retry never acknowledges a row.
- [ ] Retry recoverable failed writes with one timer and bounded backoff: initial target 2, 5, 15, then 30 seconds maximum between retries while dirty. Manual retry triggers promptly without duplicating an active write. Reset backoff on success, suspend when clean, and avoid notification/log floods. Invalid/future history must not be overwritten by retry; offer accurate guidance rather than claiming that freeing disk space fixes every storage error. Worker failures retain the in-memory snapshot and cannot resurrect older data or create multiple writers.
- [ ] Integrate quit and relaunch through 025's coordinator. Stop admitting new captures, drain media safely, then attempt the latest metadata save with a bounded wait (initial target 5 seconds, measured during implementation). Repeated requests join the same attempt. On failure show the affected reminder count and identifiable times/reasons, with Retry / Stay in app. Offer a clearly worded “Exit without saving these reminders” only after all media work is safe and no metadata write can still publish; never use worker termination as proof that OS I/O stopped. A hanging write keeps the app open with honest status. Cancel restores admission safely; relaunch uses the same rules. OS force-quit/power loss remain outside guarantees.
- [ ] Define settings loading/saving/retry/quit feedback in English and Traditional Chinese. No automatic OS notification replay, no fake saved status, and no implicit acknowledgement on exit. Document that volatile unsaved metadata may be lost on forced termination and that background work does not increase disk throughput.
