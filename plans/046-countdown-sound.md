# 046 — Optional countdown sound

[English](046-countdown-sound.md) | [繁體中文](046-countdown-sound.zh-TW.md)

Status: planned, not implemented. Created: 2026-09-27. Queue after [045](045-countdown-digit-scaling.md) and before [035](035-guided-native-acceptance.md), which stays last. It has no hard dependency on 045; both edit the countdown overlay page and its documentation, so running them in order avoids overlapping edits. Execution order: see [queue](README.md#order-and-status).

## Purpose and boundary

The countdown is silent: 040 ruled out sound ([design decision](../docs/system-design/decisions.md)). On 2026-09-27 the maintainer asked for a switch, so the countdown can be Off, run with a sound, or run silently. This plan adds a Countdown sound switch in Settings → Recording and a short tick with each digit when it is on.

The tick plays only while the digits count down. There is no sound at zero or when recording begins, no sound when a countdown is cancelled, and no sound when the countdown is Off. Nothing else changes: the digit's appearance and size (045), the timing, the cancel paths, the tray and the recording pipeline stay as they are. No other sounds are added, such as saved or failure sounds, and the countdown lengths stay Off, 3, 5 and 10 seconds.

Maintainer decision (2026-09-27): the switch exists and is independent of the countdown length. Assumed here, open to the maintainer's change before implementation: the sound is **off by default**, also for existing users, so nobody who updates starts hearing sounds, and 040's silent countdown stays the out-of-the-box behaviour.

## Why the recording stays clean

RecordStuff records system audio, and whether `restrictOwnAudio: true` in the capture request keeps the app's own sounds out of it is unverified; that is why 040 added no start sound. Cap, which plays a start sound, [arms its start gate only after the sound has left the device](https://github.com/CapSoftware/Cap/blob/119edf04864b59abfc0d52f60bf77d7f33cfd2b8/apps/desktop/src-tauri/src/recording_start_sound.rs#L5-L14). This plan needs neither: every tick is short and plays with a digit, so the last one, with the digit 1, starts a full second before `MediaRecorder.start()` and ends long before it. Correctness therefore rests on time separation, as the digit's does, not on `restrictOwnAudio`. The acceptance round checks the recording's first audio for the tick anyway.

## Implementation contract

- [ ] **Maintainer choice first.** Before the source changes, let the maintainer listen to two or three candidate ticks, for example a short sine tick and a softer woodblock-like click, each at two levels, played at the real one-second rhythm through their usual output. Static HTML drafts using the same Web Audio synthesis are enough; they are not repository artifacts. Every candidate stays away from the test material's 660 Hz beep, so the analyzer can tell them apart, and ends within 150 ms. Record the chosen sound, its level, whether the last digit uses a different pitch, and the default (off unless the maintainer says otherwise) in this plan before implementing.
- [ ] **Shared values.** In [shared/countdown.ts](../src/shared/countdown.ts), add the tick's values (waveform, frequency, duration, attack, release, peak level and any last-digit variant), each commented as the maintainer's choice, keeping the module free of Electron and DOM imports. A unit test asserts that the tick's duration is shorter than `tickMs` minus `overlayLeadMs`, so the last tick ends before the overlay leaves and before capture begins.
- [ ] **Settings.** `Settings.countdownSound` is a boolean, additive like `notifications` with no version bump: a missing or non-boolean value reads as off. Settings → Recording adds a Countdown sound switch group directly after Countdown, with a note that a short tick plays with each digit, stops before recording begins and is not recorded. The switch is disabled while the countdown is Off (its value is kept) and locked during sessions like the other recording settings. Add the `setCountdownSound` action and log the change as the countdown's is. Provide English and Traditional Chinese text for the label and note.
- [ ] **Session snapshot and presenter.** The Recorder reads the sound setting once per session with the countdown seconds and passes it to the presenter when the overlay is built (`prepare`, and `show` when it builds the window itself). The `prepared` log line keeps its current prefix, which [countdown-evidence](../scripts/lib/countdown-evidence.mts) parses, and gains whether the sound is on. Autorecord keeps the sound off in memory, so the matrix and audio-quality runs never hear it.
- [ ] **Playing the tick.** The [overlay page](../src/renderer/countdown.ts) plays it, because main already sends it each new digit at the tick time: main keeps owning every timing decision and the page renders the digit and, when the sound is on, its tick. The page learns whether the sound is on from a query parameter on the page it loads (`loadFile` with a query, or the development URL with the same parameter), so the preload, the value channel and the rule that the page cannot reply stay unchanged. It creates one `AudioContext` at load, so output is warm before the first digit, and synthesizes the tick with Web Audio from the shared values; no audio file and no CSP change is needed. It plays one tick per new digit and none for a repeated value or for `null`; destroying the window at the end or on cancel silences it. The overlay window sets `autoplayPolicy: "no-user-gesture-required"` explicitly rather than relying on Electron's default. The tick follows the system output volume and mute. If the overlay fails, the countdown continues silently and the tray still shows it, as for the digit today.
- [ ] **Acceptance tooling.** `pnpm acceptance` reports whether the sound was on and gains `--countdown-sound`, which turns it on for its round and restores the setting afterwards. When the sound was on, the runner checks the first 500 ms of the recording's audio for energy at the tick's frequency against a stated threshold, next to the existing marker counts, which must still find no extra beep onset. The notification and update runners, which seed the countdown to 0, are unaffected; confirm that nothing else records with the user's real settings and a countdown.
- [ ] **Documentation and website.** Update in both languages: the desktop design (settings list, the settings file example and the note that the overlay page plays the tick), the recording design's countdown section (the tick's timing and why it cannot reach the recording), the countdown row in design decisions (an optional tick, off by default, still no start sound, with the reason), the function reference for the new values and action, the acceptance guide's countdown row, and the tooling guide's `pnpm acceptance` options. The English website's help text says where to choose the countdown length; add the sound switch there.

## Verification and exclusions

- [ ] Unit tests: settings parsing (missing, non-boolean, true, false) and saving; the settings model's switch (enabled, disabled while the countdown is Off with its value kept, locked during a session) and its action; translation coverage; the Recorder passing the session's snapshot to the presenter and ignoring a change made after the session began; the overlay window's options including the autoplay policy and the loaded page carrying the flag for both the file and the development URL; the page, with a fake `AudioContext`, playing exactly one tick per new digit with the shared values when on, none when off, none for a repeated value or `null`; the duration constraint; autorecord keeping the sound off; the evidence parser reading the extended `prepared` line.
- [ ] `pnpm acceptance:regression` (settings changed; includes `pnpm check`) and inspection of the Settings screenshots in both languages: the switch on and off, disabled under Off, and locked.
- [ ] On a fresh `pnpm start:app` bundle, one `pnpm acceptance -- --skip-cancel --countdown-sound` round with the default 3 seconds: the log shows the sound on; the file passes media verification; the marker counts match the material; the first 500 ms hold no energy at the tick's frequency; the digit crops still pass. The cancel case is skipped because no cancel path changes; closing the window already silences it and the unit tests cover that no tick plays for `null`. A silent round is not repeated: with the sound off the countdown takes 040's path, which the unit tests cover.
- [ ] In the built app, confirm that the overlay's audio context runs without a user gesture, for example by reading its state from main with `webContents.executeJavaScript` in a development-only check, and record how it was confirmed. Whether the tick is heard is not something the agent can observe: report it as not verified by tool and leave it to the maintainer.
- [ ] `pnpm site:check` and inspection of the changed help page.
- [ ] Exclusions: the quality and audio matrices (capture and encoding are unchanged, and autorecord keeps the sound off); long recordings; permissions; the tray; the digit's appearance and size (045); Windows (macOS-only verification; the page's Web Audio is platform-neutral and nothing is claimed for Windows). Whether the tick is audible, pleasant and at the right level, including over Bluetooth headphones where the first tick may be clipped while the device wakes, is the maintainer's judgement and belongs to 035.
