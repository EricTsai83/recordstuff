# Testing guide

[English](testing.md) | [繁體中文](zh-TW/testing.md)

This is the shared test-selection policy for contributors and AI agents. [Tooling](system-design/tooling.md) explains commands and thresholds; [acceptance cases](acceptance.md) define observable results and reporting; [verification records](verification/README.md) preserve evidence, not current instructions.

## Select tests from behavior

Read the diff and affected callers before selecting tests. Classify by behavior and dependencies, not just filename, change size or the author's description. A refactor can affect runtime behavior; a string can be an IPC key rather than display copy. Combine all applicable rows below. Explicit task requirements add to this baseline; record any user-requested waiver as an untested limitation. A plan's verification list names the evidence it needs: reused evidence that meets the [reuse rule](#keep-recording-rounds-short) satisfies an item unless the plan explicitly asks for a fresh run.

Start with the smallest scope that can establish the intended result. The following low-risk path takes precedence over the broad app, display-copy and Settings rows below when its conditions hold; it does not waive checks for an affected recording, OS, security, lifecycle, performance or build boundary.

- **Display copy or translations only:** inspect the diff for meaning, matching languages and placeholders. Run `pnpm typecheck` only when message keys, placeholders or typed call sites change. Inspect the affected surface when text length or wrapping may change; do not automatically run unit tests, a build, the UI suite or every language/theme/size combination. If a fresh rendered view is needed, build once and inspect that surface or run its focused UI case.
- **Local appearance only:** for spacing, colours, typography or decoration confined to one surface, inspect that surface at the relevant size/theme. If automated visual evidence is useful, run only the relevant UI cases: `pnpm test:scope -- <scope>` (for one Settings tab, its scope: `recording-settings`, `general`, `library` or `failures`) builds once when `out/` is stale and runs that tab's cases in every language, theme and size, and `--dry-run` lists them first. No default `pnpm check` or full Settings regression. Shared tokens/components, interaction, focus, hit targets, native drag regions and window controls fall outside this exception.
- **Isolated logic or a local refactor:** when callers and dependencies show the impact is confined to one module and none of the high-risk boundaries above changes, run the relevant existing tests (for example `pnpm test src/path/example.test.ts`, or a module's folder such as `pnpm test src/main/recording`; do not insert `--`, which makes Vitest ignore the filter and run every file), or let `pnpm test:changed` select the files that import the uncommitted change and name any test that only spawns or reads it, and `pnpm typecheck` for TypeScript changes. `pnpm test:scope -- <test file>` does both in one command and launches no Electron for unit files alone. Add a regression test when it captures a reproducible failure; do not add tests that merely mirror the implementation. A build or full suite needs a specific integration/build risk. If no useful existing test covers the change, use a focused behavior check and report its limits rather than running unrelated tests.

Use the broader rows for shared runtime changes, cross-module behavior, dependencies/configuration, or a concrete uncertainty that focused checks cannot resolve. For each added check, name the failure it could detect; do not expand the scope just because the change is in app source, a composite command is convenient, or unrelated working-tree edits exist. Full CI and release gates remain unchanged. A user-requested test omission takes precedence over this default policy and is reported as untested, without repeatedly asking for approval.

Before execution, briefly state the affected behavior, selected checks and why expensive checks are omitted. This is a scope statement, not an approval request. After the final edit, run the required checks against that revision; when a composite command includes a check, do not run it twice. Run `git diff --check` for every change.

| Change / impact | Required checks | Normally unnecessary unless another row applies |
| --- | --- | --- |
| Documentation, plans, instructions or skills only | Check affected relative links/anchors, command names against package scripts, and English/Traditional Chinese consistency; validate skill metadata if changed | App build, unit tests, launching the app, recording. Do not execute commands merely because documentation contains them |
| App source, runtime assets or refactoring outside the low-risk path | `pnpm check`; add/update focused behavior tests when useful, especially a reproducible bug regression; inspect affected visible behavior when not covered by a more specific row | Packaged/native acceptance when no affected OS or visible behavior requires it |
| Display copy or translations only | Follow the low-risk path above; inspect only affected text/surfaces and run type checks when typed messages change | Full check/build/UI suite by default; recording, native shortcut delivery, audio/matrix tests |
| Settings layout/themes outside the local-appearance exception, controls, persistence, window lifecycle or settings IPC/preload | The affected scopes with `pnpm test:scope` ([focused scopes](#focused-scopes)): a change whose behavior one or more scopes name (one tab's controls, the player, the shortcut editor, persistence and IPC as `settings-bridge`) runs their union. `pnpm acceptance:regression` (check/build and the whole background suite: Playwright input in hidden, offscreen windows, with no desktop round) when the change reaches shared components or tokens, several tabs, the window lifecycle as a whole or something no scope names, and as a plan's or release's final run; inspect the relevant pictures for visual edits (`test-results/ui/`; `pnpm preview:ui` also draws a gallery of every tab, language, theme and size); cover changed interactions with Playwright mouse/keyboard input in the background suite. A change that depends on the OS activating a window, the native frame, focus across windows or full screen on the display also needs its native case on the same build: `pnpm acceptance:settings-native` for activation and the frame, `pnpm acceptance:player` (a desktop round) for the recordings player's or the full-screen video's full screen and focus return; `pnpm acceptance:recipe -- native-ui` runs those and `pnpm acceptance:shortcut-native` with one build. A change to the window's options (`settingsWindowOptions`), to `src/shared/window-controls.ts` or to what the page draws in its top-left corner also needs `pnpm acceptance:settings-shortcut -- --observe` on a fresh `pnpm start:app` bundle, the one check of the window controls macOS draws, with its `settings-window.png` observed | Recording for layout/appearance-only changes. Other native checks only for affected OS boundaries or behavior the fixture cannot represent |
| Global shortcut registration/delivery, tray actions, focus, native entry, the application menu or OS accessibility | `pnpm acceptance:regression` for settings/shortcut integration (background, with a registration adapter); otherwise `pnpm check`. Exercise the affected native action on a freshly built app: tray actions and menus with `pnpm acceptance:tray`, settings entry and the application menu's keys with `pnpm acceptance:settings-shortcut -- --observe`, Electron's real registration refusal and real Settings window state (minimize, restore, focus, the close key) with `pnpm acceptance:shortcut-native`, and their appearance by observing the saved screenshots. Registration changes also require `pnpm acceptance:shortcut-native` and `pnpm acceptance:shortcut-layout`; `pnpm acceptance:recipe -- shortcut-registration` runs the regression and both with one build | Full native state matrix; recording when the changed action cannot start/stop or interfere with capture |
| Recording start/stop, capture host/protocol, encoding, file writing, source/quality selection, recording locks, permissions or shutdown during recording | `pnpm check` plus one recording smoke round on a fresh `pnpm start:app` bundle: start, stop, save, media verification and playback. Add the changed behavior's case (for example output folder or display selection); use settings regression too if its path changed | All resolutions/qualities, long recordings, permission resets and hardware removal unless that behavior is affected/requested |
| Quit, relaunch or session-end admission, deferred-quit feedback, or failure-history persistence at quit (`quit-coordinator.ts`, `quit-feedback.ts`, `session-end.ts`, `recording-result*.ts`, the quit wiring in `index.ts`) | `pnpm check` plus `pnpm acceptance:lifecycle`: isolated Electron fixtures over the production Recorder, FileWriter, quit coordinator and history quit, in seconds and without a desktop round ([details](system-design/tooling.md#recording-lifecycle-acceptance)). It does not load `index.ts`, so wiring there is also inspected against the coordinator's contract. A change to the deferred-quit banner's text or delivery also runs `pnpm acceptance:quit-dialog` (a desktop round); quitting during a real recording follows the recording row | Recording smoke when no capture or file-writing path changed; the quit-dialog round for logic that sends no banner |
| Frame timing, sync, resolution/fps or audio fidelity | Recording row plus relevant matrix subset: `pnpm matrix -- quick`, `levels`, `fps` or `long` (choose the affected cases); for fidelity, use the relevant `pnpm audio:quality` diagnostics described in tooling | Full matrix by default; ten-minute recordings without a long-duration requirement |
| Idle or recording CPU: new or changed timers, polling, watchers, windows or renderers that stay alive, tray work, or an Electron upgrade | `pnpm check` (its timer tests catch a timer a session leaves behind) plus `pnpm measure:cpu` on a fresh `pnpm start:app` bundle, judged against the [CPU budget](system-design/tooling.md#cpu-budget). An Electron upgrade takes a new baseline with `pnpm measure:cpu -- --fps 60 --repeat 3` and updates the recorded baselines. A change that already requires the matrix reads its CPU figures too | `--fps 60` and repeats unless recording CPU is affected; idle runs longer than 5 minutes unless a result sits near a threshold |
| Saved notification delivery, timing or Finder reveal | `pnpm check`; fresh signed bundle, then `pnpm acceptance:notification -- --install --clicks 2`. For intermittent/timing fixes use the five-click or `--full` scope matching the failure, and record missing banners | Separate duplicate smoke recording if this run already supplies the required recording evidence; bilingual native runs for unchanged text |
| Update logic, feed filtering or update lifecycle | `pnpm check` and `pnpm acceptance:updates`; add `--full` for feed filtering/timeouts. Use `--logic-only` only when the diff is confined to logic and cannot affect capture, lifecycle or OS integration; disclose the omitted capture scope | Repeating normal recording acceptance unless normal-bundle behavior is also affected; instrumented results cannot establish native tray/browser behavior |
| Test files, fixtures, analyzers or developer scripts only | Relevant tests; `pnpm typecheck` for TypeScript. For the background suite's specs, run the edited specs on a fresh build (`pnpm test:scope -- tests/ui/<file>`, which builds when `out/` is stale); a change to its hosts, boundary, fixtures or teardown runs the whole suite (`pnpm acceptance:regression`) and `pnpm test:ui:drills`. For runner orchestration changes, exercise the affected runner (including changed failure/cleanup paths); for analyzer-only changes, use controlled media and retained samples | App recording for pure assertions/parsing/report formatting. If changing input delivery or real recording orchestration, exercise that real path; if fixtures load `out/`, build it first |
| Build configuration, Electron/runtime dependencies, preload security, signing or packaging | `pnpm check` and the affected build/package verification (`pnpm start:app` or `pnpm dist:mac`; for Windows packaging, which no maintainer machine can build or run, a dispatched [check.yml](../.github/workflows/check.yml) run, whose `windows-installer` job builds the installer and runs its install/uninstall gates on a runner); inspect affected bundle/installer behavior. Electron/media/runtime/entitlement changes also require recording smoke, and an Electron change also requires `pnpm acceptance:shortcut-layout` (the `shortcut-registration` recipe adds it to the regression without a second build) and, on its `pnpm start:app` bundle, `pnpm acceptance:settings-shortcut -- --observe`, since Electron installs the default menu and routes its keys; settings preload/CSP changes require settings regression | Publishing, installing over the user's app, resetting permissions, full capture matrix for packaging-only changes |
| Website source/assets/configuration | `pnpm site:check` (website tests, diagnostics, online manifest verification, build and generated-link checks); inspect affected pages for visual edits | App tests and native recording when no shared app/release input changes |
| Release workflow or publication | Relevant release-tool tests and checks from the [release guide](system-design/releases.md); actual release acceptance is tied to the candidate SHA | Publishing as a test; a code/documentation task never authorizes a tag push |

Examples: a local settings CSS spacing fix needs inspection of that surface (or a focused UI case), but no full regression or recording; changing a recording shortcut needs integration, real OS key delivery and recording smoke; changing an output-folder label needs copy checks, while changing folder persistence needs settings regression and a saved-file destination check. A permission explanation string does not require permission reset; changing permission recovery does require its affected native case.

Changes to native window drag regions also need `pnpm acceptance:window-drag` ([scope](system-design/tooling.md#window-drag-acceptance)): real CoreGraphics dragging and AX bounds in a shown production-page/window fixture. CSS declarations and background renderer input do not prove OS movement. If another required check already built the same final `out/`, run `node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON scripts/acceptance-window-drag.mts` on that artifact rather than rebuilding. Runner-only changes exercise its normal and cancellation/cleanup paths; they do not add unrelated recording or signed-bundle checks.

## Keep test UI aligned with the app

UI tests do not guard the design: layout, spacing, sizes, positions, colours, shadows, radii, typography, decoration, class names, component variants and visual DOM structure may change at any time without a test change. Playwright cases assert behaviour (input, state, persistence, IPC), accessibility semantics (roles, names, states, focus and keyboard operation) and design-agnostic invariants (no outer or horizontal overflow, no cut-off text, controls visible, reachable and uncovered, including by the window controls, and the readability floors of plan 067: text at least 12 px and control hit areas at least 24 px). Do not add pixel baselines or assertions on design values; judge a visual change by looking at the pictures.

UI tests and preview galleries must render the production pages and share the app's components, CSS, fonts and design tokens. At the same language, theme, window size and zoom, their layout, typography, colours, spacing and control appearance must match the app. Do not create a separate test design, copy production styles into fixtures or inject style overrides to make a visual assertion pass; fix the shared production implementation when the design changes.

Fixtures may use demonstration recordings, controlled states and different version text. These data differences do not require exact parity with the user's app. Offscreen rendering and OS adapters may isolate desktop effects, but must preserve the page's design. A gallery's surrounding report UI is separate from the app pictures it presents. Refresh affected pictures after a style change before presenting them as the current app design; use native evidence for appearance drawn by the OS.

## Select once, validate once

Turn the selected rows into a task-local recipe before running anything: the required checks, the composite command that covers each, the artifact each needs (`out/`, a signed bundle, a saved recording) and the justified exclusions. It belongs in the task's notes or report, not in a permanent file, and is the same for human and agent work. No command may lower a requirement of the table above.

| Situation | Execution rule |
| --- | --- |
| Editing or debugging | Run focused checks only to answer a concrete question. A successful check on unchanged final inputs also satisfies the selected final scope; do not rerun it merely to label it final |
| Final revision | Run only the selected checks. Use a composite such as `pnpm acceptance:regression` when its entire scope is required, without first running its `check` or build on their own; otherwise use focused commands |
| Several runners need `out/` | Build the final inputs once and run the runners serially on that `out/`. `pnpm acceptance:regression && pnpm acceptance:shortcut-layout` builds twice; `pnpm acceptance:recipe -- shortcut-registration` runs the same checks with one build |
| Native acceptance needs a signed bundle | Build and sign once with `pnpm start:app` for the final runtime inputs; `out/` evidence cannot replace signed-bundle evidence. A later round reopens that bundle with `pnpm open:app`, which refuses a bundle whose runtime inputs changed since it was built |
| Later edit or review fix | Reclassify its impact; invalidate the evidence and artifacts it affects and rerun the checks that apply, not automatically the whole desktop matrix |
| Failed check or changed environment | Resolve the failure or uncertainty, then rerun the affected scope; a failed or blocked result is never reused as a pass |

`pnpm acceptance:recipe -- --list` shows the recipes for the common combinations: `check`, `settings` (the regression, with no desktop phase), `shortcut-registration`, `native-ui` (the native Settings, shortcut and player cases, a desktop round) and `recording` (check, `pnpm start:app` and `pnpm acceptance`, building once inside `start:app`). Each runs the same leaf checks as the commands it replaces and writes a phase timing report ([tooling](system-design/tooling.md#verification-recipes-and-timing)). Running the composite commands yourself is equally valid as long as nothing builds identical inputs twice. These are broad compositions for a final revision or a cross-cutting change, not the default for each local edit.

### Focused scopes

`pnpm test:scope -- <scope or test file>…` runs one task's selection: `pnpm typecheck`, the selected Vitest files, a build only when UI cases are selected and `out/` is not the current sources' build, then the selected background cases ([tooling](system-design/tooling.md#focused-test-scopes)). `--list` shows the scopes and what each answers for; `--dry-run` prints the exact files, cases, build decision and commands without running anything. Name every scope the diff reaches: a shared change takes the union of its consumers, and a change no scope describes uses the rows above. An unknown scope, a missing file or a selection that matches nothing is an error, never a silent full run. Report a focused pass as that scope's evidence, not as a full regression; CI and release gates are unchanged.

Reuse stays inside one task and is bounded by source, dependency and configuration identity, evidence scope, artifact and environment. After a later edit, earlier evidence stays valid only when the affected callers and dependencies show that it is unaffected, as the [evidence rules](#evidence-boundaries-and-stopping) allow. HEAD or file timestamps cannot prove that an artifact matches an uncommitted working tree; rebuild when freshness cannot be established. `pnpm open:app` establishes it for the signed bundle by comparing a digest of its runtime inputs, recorded at build time, with the current ones. There is no skip cache across tasks.

One recording may supply start/stop/save, media verification and playback when it meets every required case; reuse its media analysis only with the same file, analyzer and options. After the required checks pass, stop: another run needs an edit, a failure, an unresolved uncertainty or an explicit extra requirement. Restoring settings and the runners' cleanup and outcome contracts stay in place; speed is never a reason to drop them.

## Evidence boundaries and stopping

- `pnpm check` covers root TypeScript/Vitest/build, not website checks, Electron fixtures or real capture. Settings regression covers production components in hidden, offscreen windows with controlled tray, registration, window-activation and notification boundaries: an adapter call is a request production made, not an OS effect. It does not cover OS shortcut delivery, window activation, the native frame, full screen on the display or physical tray clicks.
- A notification has three evidence layers: the lifecycle around it, its delivery event (`shown` or `failed`) and the visual banner. A `shown` event is not visual proof, and a passing lifecycle is not delivery. macOS refuses notifications from the linker/ad-hoc-signed Electron in `node_modules`, so a runner that judges a notification launches a fully signed artifact: the `pnpm start:app` bundle, or the per-round signed copy of `pnpm acceptance:quit-dialog` ([plan 062](verification/history-2026-10.md#plan-062-closure--2026-10-02)).
- A short recording verifies only its tested settings/environment. Media verification does not establish subjective listening, VoiceOver, first-time permissions, long-run stability or installation. Native clicks, physical display removal and playback must be observed when required.
- Reuse media analysis for the same file, analyzer version/options and scope. Reuse prior UI evidence only when the affected implementation, artifact and environment are unchanged; cite its origin. Rebuild changed code before native acceptance. Historical test counts are not current pass thresholds.
- After required checks pass, stop. Broaden/rerun only for a further edit, failure, unresolved risk, changed environment or explicit requirement. Do not ask the user to repeat unaffected passed manual cases. Do not add tests that only mirror implementation or assert documentation wording.
- Distinguish **not applicable** (outside the impact scope, with reason), **not run** (required but not attempted), **blocked** (required but a prerequisite is unavailable), **fail**, and **pass**. A missing permission/tool is blocked, not a reason to relabel a required test unnecessary. A waiver remains not run with the user's reason; never label it pass. Do independent checks while reporting the gap.

### Scripted runner or Computer Use

Choose how each native case is operated before the round. Use a project runner when one covers the operation. Use Computer Use to observe what the screen shows and to operate what no runner covers. Leave subjective judgments and steps that need the maintainer's presence to the maintainer. A runner and an observation answer different questions, so neither stands in for the other; the [native cases](acceptance.md#scripted-runner-or-computer-use) list which runner covers which operation and what remains with Computer Use or the maintainer.

| Evidence | Meaning | Proves | Does not prove |
| --- | --- | --- | --- |
| Scripted native input | A committed project runner posts real OS events (System Events keys and presses, CGEvents, AppleScript to the player it opened) to its target and asserts accessibility state, logs and files | The OS delivered the input; the native menu, window, banner, Finder or player reached the expected state and the app reacted | Pixels, legibility, alignment, appearance, sound |
| Computer Use observation | An agent inspects screenshots or the live desktop and judges them | What a person would see in the captured frames | Anything the frames do not show; input delivery when it did not send the input |
| Manual | The maintainer operates or judges | Subjective listening, readability, password or Touch ID steps | Cases the maintainer did not perform |

Label every case's evidence by kind and keep the kinds apart in the report; a case backed by more than one kind lists each. A scripted pass is never reported as visual or subjective evidence, and a scripted pass that disagrees with what is visible is a runner failure, not a product pass. Only a committed runner sends scripted input: an executor does not improvise AppleScript, System Events, IPC or test hooks to stand in for an operation. How an agent drives Computer Use belongs to the [acceptance skill](../.agents/skills/native-acceptance/SKILL.md).

## Keep recording rounds short

Recording rounds are the slowest checks and hold the whole desktop. Before starting one, list each recording and the question it answers, and drop any recording whose question another item already answers.

- **Reuse a baseline.** "Before" evidence may cite the latest run of the same runner and case when nothing on the capture path changed since then (capture, encoding and quality code, the Electron version, the artifact kind), on the same machine, display, audio route and test-material version. Record that run's date and commit. Re-record only when one of these changed or the earlier run lacks a metric the comparison needs. This holds for conclusions that do not rest on a small difference, such as every metric still passing its threshold. A before/after conclusion that rests on a difference smaller than the metric's drift between rounds must not reuse another round: on the reference machine, 30 fps cases on the same code measured about 0.25 fps apart in rounds ten minutes apart, several times the spread inside one round ([plan 042](verification/history-2026-09.md#plan-042-closure--2026-09-26)). Record the baseline's affected cases back to back with the change instead, and when the result still hinges on that difference, record the baseline once more afterwards (A, B, A) and accept the comparison only if the two baselines agree within their spread.
- **Record only cases that differ here.** Choose matrix cases by the changed dimension and skip cases that take the same path in this environment: on a display no larger than a resolution cap, the capped and source cases record the same unscaled capture and differ only in quality level. Keep `long` whenever drift can change.
- **Screen once, then confirm the choice.** When comparing candidates, run each once per setting; repeat only the chosen candidate and any result whose margin to a threshold or go criterion is smaller than the run-to-run spread seen for that metric.
- **Measure each quantity once after a change.** Do not confirm one quantity with two runners. `pnpm matrix` reports the average frame rate and the median frame interval, so the cadence diagnostic locates a layer but is not rerun to confirm a fix.
- **Let one recording serve several cases.** A smoke recording supplies media verification and playback; a matrix recording supplies every metric of its case.
- **Measure size-dependent I/O without recording.** When the question is how a file step scales with size (publication, copy, sync), measure it with `pnpm bench:publication` on the target volume in seconds and keep recordings at ordinary lengths for the end-to-end path; never record long takes only to produce large files. For timing questions `pnpm measure:finalization` decodes the first take fully and only the first and last second of the rest by default. Plan 037 spent about 49 of its 60 recording minutes on eight 5-minute takes, which such a benchmark answers in under a minute ([history](verification/history-2026-09.md#faster-finalization-measurement--2026-09-27)).
- **Repeat only on doubt.** A second run is needed when a result is near a threshold, a failure may be environmental, or repeatability is itself the question; otherwise one run answers it.

Report which evidence was reused (runner, case, date and commit) and which planned recordings were skipped and why.

## Environment and shared-machine use

Use the pinned pnpm version and lockfile; Node 24 supports the TypeScript runners. Ordinary unit/type/build checks do not need capture permission, signing, Chrome or FFmpeg. Some audio integration tests explicitly skip without FFmpeg/ffprobe; disclose relevant skips. Website verification needs network access. See [signing setup](system-design/signing.md) for native bundles; do not create/import credentials as an incidental test step.

Real recording needs a supported Mac, screen/system-audio permission, Chrome and FFmpeg/ffprobe. System Events runners also need Accessibility/Automation access. Record OS/architecture, source display, audio output/volume and test-material version. The background suite and native settings integration need an Electron-capable graphical session (on macOS a logged-in user session; the background suite also passed with the screen locked, while a machine without a display was not tested); neither requires a signed installed app. The background suite does not use the desktop: it needs no readiness handoff and may run while someone works. Missing prerequisites should identify the exact blocked layer.

Separate checkouts/worktrees may run independent pure tests concurrently. In one checkout, serialize builds and runners that consume `out/` or `dist/`, the background suite included; do not rebuild beneath an active fixture. A single executor owns the desktop, system audio, global shortcuts and installed-app replacement at a time, even across worktrees. Isolated preferences do not isolate OS focus or capture devices. These are coordination rules, not a claim that every runner provides a cross-process lock.

Before a desktop round, identify its owner, checkout/artifact and intended cases. During development, stopping recordings and quitting/restarting/rebuilding RecordStuff as needed is authorized without additional confirmation; possible active use is not a blocker. Finish saving, restore changed preferences, close owned test UI, quit the tested app normally and confirm process exit before handing the desktop to another executor. A cleanup failure blocks the next rebuild/round; report remaining processes or windows. See [acceptance cases and report format](acceptance.md).

On macOS, every runner that records the display or depends on real windows, focus, banners or native dialogs first declares user activity (waking a display that idled off) and then holds a display/idle-sleep assertion for its own lifetime, because synthetic input does not reset the idle timer. A password-locked session is never bypassed: a round that starts locked stops before launching or sending keys, and a lock seen during the round makes its result **blocked** (exit code 2) even if its cases passed. Unlock and rerun; do not count such a round as pass or fail. A manual lock, closed lid or managed policy can still interrupt a round.

### Confirm desktop handoff before testing

Before taking over the shared desktop for a test, tell the user which cases will run and that the test may move the pointer, send keys, change focus or record the screen/audio. Ask for an explicit readiness reply, for example: “Please pause your keyboard and mouse use. Reply ‘好了’ when you are ready for me to start.” Then stop output and yield the turn; do not launch desktop test runners, activate apps or send input until that reply arrives. A fixed delay, silence, a progress message or general authorization to test is not a readiness reply. This handoff coordinates desktop use; it does not require renewed approval for already-authorized app changes.

One reply covers the stated uninterrupted test round, including its cleanup. If control has been returned to the user or they ask to pause, stop desktop interaction and obtain a new readiness reply before taking over again. State when cleanup is complete and the user can resume. Record the readiness reply and tested scope in the acceptance evidence. File reads, code edits and checks that do not use the desktop do not require this handoff.

## Report the selected scope

For ordinary edits, include a compact final summary: affected behavior; checks and results; omitted checks with scope reasons; required-but-unverified cases and blockers. Do not create a permanent test report for every documentation edit. For native/recording runs, use the [acceptance report template](acceptance.md#report-template) and preserve the runner's evidence. These same rules apply to humans and LLMs; agent-specific tool operation belongs in skills.
