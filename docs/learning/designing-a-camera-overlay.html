在螢幕錄影裡放進攝影機：合成在哪裡、預覽怎麼送、形狀與鏡像的取捨

教學影片、產品示範、程式碼導覽，常在畫面一角放一個講者的小圓框。看起來只是「把攝影機疊在螢幕上」，但疊在哪一層，決定了觀眾看到的和使用者看到的是不是同一件事、圓框會不會擋住正在操作的 App、錄完還能不能調整，以及每秒要多編碼多少張畫面。本文先比較三種架構：讓攝影機成為螢幕上的一個視窗被錄下（Loom 的泡泡）、在錄影器裡先合成再編碼（OBS 的場景）、分軌錄製再在編輯器組合（Cap Studio、Screen Studio）。接著深入第二種：在 GPU 上、編碼器之前合成時的著色器、YUV 平面與色彩矩陣、時間與攝影機遺失；再談怎麼把即時預覽從另一個行程送進網頁，以及形狀、尺寸與鏡像的慣例。貫穿範例是 RecordStuff 的計畫 075。

問題：講者的臉要放進錄影，放在哪一層？

想像一個螢幕錄影工具要加上攝影機。使用者的期待很具體：

  • 錄出來的影片右下角有他的臉，位置、大小、圓角都是他選的。
  • 錄影時他照常操作螢幕上的 App，攝影機框不擋住他要點的按鈕。
  • 錄到一半發現框擋住了程式碼，可以把它拖開，或暫時藏起來。
  • 開始錄之前，他能確認自己入鏡、光線可以、框沒有蓋到重點。
  • 不開攝影機時，錄影和以前完全一樣：不多吃 CPU，畫面也不變。
  • 攝影機中途斷線（無線的 iPhone 相機、USB 線鬆了），錄影不會毀掉。

最直覺的做法，是開一個無邊框、永遠在最上層的小視窗，裡面播放攝影機畫面，再照常錄整個螢幕。框就在螢幕上，錄影自然就有它。這個做法很快就能做出來，也確實是 Loom 這類產品的核心體驗，但它把幾件事綁在一起：

  • 使用者看到的就是觀眾看到的。框在螢幕上擋住什麼，錄影裡就擋住什麼；框上的任何控制項（調整大小的把手、關閉按鈕、滑鼠游標停在上面時的提示）也都會被錄進去，除非刻意藏起來。
  • 框會攔截點擊。一個可以拖曳的視窗必須接收滑鼠事件，於是它底下那塊 App 就點不到。要讓點擊穿透，就不能拖曳；要能拖曳，就擋住點擊。
  • 錄影工具自己的視窗通常要排除在錄影之外，但這個框又必須被錄到，所以排除規則要開一個例外。
  • 錄完就固定了。攝影機已經被燒進螢幕的像素裡，事後無法移動或拿掉。

這些問題背後有幾股互相拉扯的力量：

  • 所見即所錄：使用者要能確認錄影裡會是什麼樣子。
  • 不干擾：錄影工具不應該擋住、改變或攔截使用者正在操作的東西。
  • 可修改：錄影中或錄影後還能調整框的位置與形狀。
  • 成品即可分享：停止錄影時，檔案就是最終成品，不需要再匯出。
  • 成本：CPU、GPU、記憶體，以及每秒要編碼的畫面數。
  • 可攜：同一套規則要在 macOS 和 Windows 上畫出同樣的框。

所以本文要回答的是：攝影機畫面該在管線的哪一層和螢幕畫面相遇？選定之後，合成、時間、遺失、預覽、形狀與鏡像各要怎麼處理，才能讓使用者確認的和觀眾看到的一致，又不付出不必要的代價？

心智模型：合成、畫布、YUV 與兩個觀眾

先把幾個詞講清楚。

合成（compositing）是把多張圖依序疊成一張的動作。螢幕上本來就時時刻刻在合成：作業系統的視窗伺服器（macOS 的 WindowServer、Windows 的 DWM）把每個視窗的內容疊成你看到的畫面。螢幕擷取 API 拿到的，就是這個合成之後的結果，或是依過濾條件重新合成、排除了某些視窗的結果。所以「把攝影機放進錄影」的問題，其實是：由誰來做這次合成？可以是作業系統（攝影機是一個視窗）、錄影器（攝影機是一個來源），或是事後的編輯器（攝影機是一條軌）。

畫布（canvas）是錄影器自己的合成目標。OBS 的術語是場景（scene）與來源（source）：螢幕擷取是一個來源，攝影機是另一個來源，每個來源在畫布上有位置、大小、裁切、翻轉等變形，OBS 每一格都在 GPU 上把它們畫到畫布上，畫布再交給編碼器。

YUV 與 NV12。螢幕和攝影機的畫面，送進硬體編碼器之前通常不是 RGB，而是亮度（Y）與兩個色差（Cb、Cr）分開存放的 YUV。4:2:0 取樣讓每 2×2 個像素共用一組色差，資料量是 RGB 的一半；NV12 是它最常見的排列：一個全尺寸的 Y 平面，加上一個半寬半高、Cb 與 Cr 交錯的 UV 平面。在 YUV 上直接合成，就是兩個平面各畫一次，而且色差平面的一個樣本，對應亮度平面的四個像素。

色彩矩陣。從 RGB 換到 YUV 的係數有不只一套。標準畫質的 BT.601 以 Y = 0.299R + 0.587G + 0.114B 計算亮度，高畫質的 BT.709 用 0.2126、0.7152、0.0722。兩者的 Y 和色差意義不同；把 BT.601 的攝影機畫面當成 BT.709 直接貼進錄影，膚色會微微偏綠或偏紅。另外，影像用的「video range」只用 16–235（亮度）與 16–240（色差），不是 0–255。

兩個觀眾。這是整篇文章最重要的區分。錄影時有兩個人在看：使用者，他看著自己的螢幕和預覽；觀眾，他之後看錄好的檔案。三種架構的差別，說到底就是這兩個人看到的東西何時相同、何時不同，以及使用者靠什麼確認觀眾會看到什麼。

三種架構與它們的後果

攝影機和螢幕相遇的位置有三種典型選擇：

A：錄下一個視窗

攝影機是一個無邊框、置頂的視窗，螢幕擷取把它和其他視窗一起錄下。Loom 是代表：它的 macOS App 提供方形圓角、圓形、橫向與直向矩形四種泡泡形狀與五種尺寸，泡泡可以拖到螢幕任何位置，靠近角落與邊緣時會吸附，下次開啟會記得位置；錄影中雙擊泡泡會讓攝影機佔滿畫面。Cap 的 Instant 模式也屬於這一類。

它的優點是簡單、即時、成品即可分享：作業系統已經在做合成，錄影器什麼都不用加。它的代價就是前一節列的那些：框擋住的東西在錄影裡也被擋住；框要嘛能拖曳、要嘛讓點擊穿透；框的控制項要小心藏好；錄影工具必須讓自己的這一個視窗被錄到，而其他視窗不被錄到；錄完就無法調整。Loom 的說明甚至直接提醒：鏡像要在錄影前設定，錄完就不能翻轉了。

B：在錄影器裡合成

攝影機是錄影器的一個來源，錄影器每一格把它畫到螢幕畫面上，再交給編碼器。OBS Studio 是代表：所有來源都在它的 GPU 畫布上合成，使用者在 OBS 主視窗的預覽裡看到合成後的畫布，並可以在錄影中移動任何來源。macOS 的 Presenter Overlay 也是這個模型，只是合成者換成了系統：它把講者疊在分享的畫面上，小型模式下講者是一個可以拖曳的泡泡。

這個架構把兩個觀眾分開了：使用者的螢幕上沒有框，不擋東西、不攔點擊、沒有控制項會被錄到；錄影工具自己的視窗可以照常全部排除，不需要例外。代價是使用者必須靠預覽確認觀眾會看到什麼，所以預覽成了這個架構的必要部分，而不是附加功能；而且合成要由錄影器自己做，每一格都要付出 GPU 工作，螢幕靜止時也得一直編碼（攝影機畫面在動）。錄完一樣是燒進像素，事後不能修改，但錄影中可以隨時修改，並在下一格生效。

C：分軌，事後在編輯器組合

螢幕與攝影機錄成兩條獨立的軌，錄影結束後在編輯器裡排版，匯出時才合成。Cap 的 Studio 模式與 Screen Studio 都是這一類：Cap 說明它分開錄下螢幕與攝影機，再即時合成或在編輯器裡調整版面；Screen Studio 的說明則提到錄完之後可以修改攝影機的大小、版面與位置，畫面縮放時還會自動縮小攝影機框，並可以在時間軸上切換版面。錄影時，這些產品通常仍顯示一個浮動的攝影機視窗讓使用者看到自己，但它被排除在螢幕軌之外。

這是最有彈性的架構：位置、大小、圓角、甚至要不要出現，全部可以事後決定，也可以隨時間變化。代價是停止錄影時還沒有成品，需要一個編輯器和一次匯出；兩條軌要對齊時間；匯出時的合成往往比錄影時昂貴得多（Cap 的編輯器要畫背景、模糊、游標、字幕、轉場等十幾層）。

RecordStuff 一開始（2026-10-14）選了 A：一個會被螢幕擷取錄到的泡泡視窗。維護者問「為什麼錄影中不能移動泡泡」，答案正好暴露了 A 的結構：視窗上畫的任何東西都會被錄進去，可移動的視窗又一定會攔截底下 App 的點擊，所以設計只好在錄影中鎖住位置。2026-10-17 設計改成 B：引擎合成，鎖住位置的兩個理由同時消失，泡泡也不必出現在螢幕上，它擋住什麼改由預覽呈現。檢查過的產品裡，沒有一個是「看不到、也不能動」的泡泡：一旦攝影機改由程式合成，OBS 用預覽呈現結果，Cap Studio 與 Screen Studio 讓它事後移動。RecordStuff 沒有編輯器，所以照 OBS 即時做。

在 GPU 上、編碼器之前合成

選了 B 之後，合成器要回答四個問題：在 CPU 還是 GPU 上做、用哪一套繪圖 API、在什麼色彩格式上做，以及沒有攝影機時要不要碰畫面。

為什麼在 GPU、為什麼在編碼器之前

螢幕擷取與硬體編碼器之間，畫面一直待在 GPU 記憶體裡：macOS 上是 IOSurface 撐起的 CVPixelBuffer，Windows 上是 Direct3D 11 的貼圖。合成如果在 CPU 上做，每一格都要把整張螢幕畫面讀回主記憶體、改幾萬個像素、再上傳，一張 4K 的 NV12 畫面約 12 MB，60 fps 時光是單向就超過每秒 700 MB。在 GPU 上做，畫面原地讀寫，CPU 只負責送出指令。合成必須在編碼器之前，因為編碼之後的位元流已經無法逐像素修改。

用什麼 API 也有差別。RecordStuff 的第一個原型在 macOS 用 Core Image：寫起來最短，但它每一格都在 CPU 上重建一次濾鏡圖。在參考機（M1 Pro）上，30 fps 錄影時，攝影機加上「每一格都編碼」一共多了約 10 個百分點的單核 CPU（10.4% 變成 20.9%）。改成自己寫的 Metal compute 著色器之後，同樣的錄影只多約 4 個百分點（14.7%），60 fps 多約 7 個百分點（14.0% 變成 21.2%）。差別不在 GPU，而在每一格的 CPU 準備工作。

一個著色器，翻譯到每個平台

macOS 要 Metal，Windows 要 Direct3D 11，兩邊的泡泡必須畫得一模一樣：同樣的圓角、裁切、鏡像，以及同樣的邊緣反鋸齒。最容易出錯的做法是各寫一份著色器，然後期待它們永遠同步。另一個常見選擇是用 wgpu 這類跨平台繪圖函式庫，讓它在各平台選後端。

RecordStuff 走中間的路：只寫一份 WGSL 著色器（WebGPU 的著色語言），在建置時用 naga（wgpu 專案的著色器翻譯器）驗證並翻譯成 Metal 的 MSL 與 Direct3D 11 的 HLSL（shader model 5.0）。各平台仍用自己的原生 API 綁定貼圖、送出工作、把結果交給自己的編碼器。著色器只要驗證或翻譯失敗，任何平台的建置都會失敗，所以 macOS 上開發時也能抓到 Windows 那一份的問題。

Rust// build.rs（節錄，註解為本文所加）：一份 WGSL，兩份輸出
let module = naga::front::wgsl::parse_str(&source)?;
let info = Validator::new(ValidationFlags::all(), Capabilities::empty()).validate(&module)?;
// macOS：MSL，執行時由 Metal 編譯
let (metal, _) = msl::write_string(&module, &info, &msl_options, &pipeline)?;
// Windows：HLSL，執行時由 D3DCompile 編譯
let mut direct3d = String::new();
hlsl::Writer::new(&mut direct3d, &hlsl_options, &hlsl_pipeline).write(&module, &info, None)?;

為什麼不直接用 wgpu？因為在這個情境下，wgpu 能共用的也只有著色器，而 naga 已經做到了：貼圖仍要從各平台的擷取 API 進來、再交給各平台的編碼器，跨過 wgpu 的邊界反而多了一層。更具體的是，wgpu 在 Windows 上沒有 Direct3D 11 後端，而 RecordStuff 的擷取與編碼都在 Direct3D 11 上，每一格都得在 Direct3D 11 與 12 之間共用貼圖並用 fence 同步。Cap 用 wgpu 是合理的，因為它的編輯器在很多個 pass 裡畫十幾層東西；當合成的場景長到那個規模（一個編輯器、需要多個 pass 的特效），就是換到 wgpu 的時候，而著色器已經是 WGSL。

翻譯也有它的稜角。naga 輸出的 HLSL 會把取樣器（sampler）寫成 Direct3D 12 的 sampler heap 形式，Direct3D 11 沒有這個東西，所以著色器不用取樣器，而是自己用四次 textureLoad 做雙線性內插。另一個稜角在 Windows：Direct3D 11.1 可以把 NV12 貼圖的兩個平面當成 render target 寫入，但要從 compute shader 寫入，得靠 Direct3D 11.3 的選用功能。所以 Windows 版讓兩個 kernel 各寫一張自己平面的貼圖，再用一個三角形把它畫進 NV12 輸出的對應平面。

在 NV12 的兩個平面上畫圓角

著色器有兩個進入點：luma 寫 Y 平面，chroma 寫 UV 平面。每個輸出像素先讀螢幕在同一位置的值，再算出泡泡蓋住這個像素多少（0 到 1），以這個比例混入攝影機的值。蓋住多少用圓角矩形的有號距離（signed distance）來算：像素中心在形狀內部為負、外部為正，邊界上的那一個像素依距離取 0 到 1 之間的值，這就是反鋸齒。

WGSL// compose.wgsl（節錄）：像素中心 p 被泡泡蓋住多少，一個像素寬的反鋸齒
fn coverage(p: vec2<f32>) -> f32 {
    if (params.camera_on < 0.5) {
        return 0.0;
    }
    let half_size = params.bubble_size * 0.5;
    let local = p - (params.bubble_origin + half_size);
    let r = min(params.radius, min(half_size.x, half_size.y));
    let q = abs(local) - half_size + vec2<f32>(r, r);
    let distance = length(max(q, vec2<f32>(0.0, 0.0))) + min(max(q.x, q.y), 0.0) - r;
    return clamp(0.5 - distance, 0.0, 1.0);
}

// 色差樣本的覆蓋率：它對應的四個亮度像素的平均
fn chroma_coverage(p: vec2<f32>) -> f32 {
    return 0.25 * (coverage(p + vec2<f32>(-0.5, -0.5)) + coverage(p + vec2<f32>(0.5, -0.5))
        + coverage(p + vec2<f32>(-0.5, 0.5)) + coverage(p + vec2<f32>(0.5, 0.5)));
}

第二個函式處理 4:2:0 的細節。色差平面的一個樣本代表 2×2 個亮度像素；如果它只看自己中心的覆蓋率，泡泡邊緣的顏色會比亮度「硬」半個像素，在圓弧上看得到一圈色邊。取四個亮度像素覆蓋率的平均，邊緣的顏色就和亮度一樣柔和地過渡。

攝影機的顏色也要先換算。攝影機常交出標成 BT.601 的 YCbCr，錄影的輸出則標成 BT.709。著色器讀到 BT.601 的攝影機畫面時，先把它的亮度與色差換算成 BT.709 的值再混合（亮度的換算也要用到色差，因為兩套矩陣對 R、G、B 的權重不同）。少了這一步，泡泡裡的膚色會有些微但看得出來的偏色，而且只有某些攝影機會這樣，很難追。

沒有攝影機時，不要碰畫面

一個重要的不變式：不開攝影機、攝影機被隱藏、或攝影機暫時沒有畫面時，錄影要和沒有這個功能時逐位元組相同。RecordStuff 的做法分三層：攝影機沒開時根本不建立合成器；隱藏時把螢幕原本的畫面直接交給編碼器；有合成器但還沒有攝影機畫面（剛開啟、或遺失中）時，著色器的覆蓋率全為 0，而且螢幕是在輸出像素的中心取樣，同尺寸時剛好讀到每個像素本身。合成器的單元測試直接比對：沒有攝影機畫面或隱藏時，輸出的兩個平面與螢幕畫面逐位元組相同。這個不變式讓「加了攝影機功能之後，不開攝影機的錄影有沒有變」成為一個可以自動驗證的問題，而不是一個靠感覺的問題。

Pacer：攝影機在動，就要每一格都編碼

螢幕錄影器常有一個省資源的設計：螢幕沒有變化時，擷取 API 不送新畫面，錄影器也只偶爾（例如一秒一次）重送最後一張，讓檔案的時間軸不中斷。RecordStuff 的引擎就是這樣。加上攝影機之後，這個假設失效了：螢幕靜止，攝影機裡的人還在說話，每一格的合成結果都不同。所以泡泡顯示時，pacer 要在每一個時間格（30 fps 就是每 33.3 ms）都取最新的螢幕畫面重新合成並編碼；泡泡隱藏時，回到靜止螢幕原本的節奏。從隱藏切回顯示時，pacer 從目前的時間格開始，而不是把隱藏期間空下來的格子全部補上。

這是 B 架構最容易被低估的成本：原本靜止畫面幾乎免費，現在每一格都要合成與編碼。硬體編碼器讓它停在「螢幕一直在動」的成本，而不是更多，但它不再是零。

時間：攝影機和螢幕是兩個來源

攝影機有自己的節奏：一台 30 fps 的攝影機每 33 ms 交一張，錄影可能是 60 fps；Continuity Camera 走無線，交付時間會抖動。合成器每一格要決定：用攝影機的哪一張？

  • 排隊，一張配一張。每一格都等攝影機的下一張。攝影機一慢，錄影就跟著卡；攝影機比錄影快，佇列就越積越長，延遲越來越大。
  • 依時間戳配對。為每一格找出拍攝時間最接近的攝影機畫面。這需要保留一段攝影機的歷史畫面，而且攝影機的時間戳本身就落後實際拍攝一段時間，配對得再準，也只是把螢幕延後去配合攝影機。
  • 只留最新的一張。攝影機每交一張就覆蓋前一張，合成器每一格取當下最新的那張。攝影機比錄影慢時，同一張會用兩次；比錄影快時，中間的會被丟掉。永遠不排隊，延遲有上限。

對講者泡泡來說，第三種是合理的預設：泡泡是一張小小的臉，觀眾對它的時間精度要求，遠低於對嘴型與聲音的要求（聲音與畫面的對齊另有機制）。RecordStuff 的 CameraFeed 就只存最新一張畫面與它的拍攝時間；macOS 上攝影機輸出設定 alwaysDiscardsLateVideoFrames，讓 AVFoundation 自己也不排隊。攝影機畫面的時間戳換算到螢幕畫面用的同一個主機時脈，於是可以量一件事：每一格錄影裡的攝影機畫面，比這一格本身老多少。

RecordStuff 在停止錄影時把這個數字寫進記錄。2026-10-18 在參考機上用 iPhone 的 Continuity Camera 錄一段 60 fps 的影片，1005 格含攝影機的畫面裡，攝影機畫面平均比它所在的那一格老 113.9 ms，範圍 87.7 到 138.7 ms。這包含無線連線與 iPhone 本身的處理，換成 USB 攝影機數字會不同，這次沒有量。這個量測有一個平台差異要記得：Windows 上 Media Foundation 的攝影機畫面是在到達時才蓋時間戳，所以同樣的數字在 Windows 上會漏掉攝影機自己持有畫面的時間。

約 0.1 秒的落後意味著什麼？講者的臉會比螢幕上的游標晚一點點，通常沒人注意；但如果講者說「看這裡」同時指向螢幕，或錄的是手部示範，就值得考慮把螢幕延後一點去配合。那需要為螢幕畫面排隊，記憶體與複雜度都上升，而且延遲要量對才能補對。這是一個可以等量測和使用回饋再決定的選擇。

攝影機遺失與回來

攝影機會在錄影中消失：USB 線被拔、Continuity Camera 的 iPhone 被拿走或在 iPhone 上選了中斷連線、權限被撤銷。設計要回答三件事：怎麼知道它不見了、不見時錄影裡顯示什麼、它回來時怎麼辦。

怎麼知道。攝影機和麥克風不同：攝影機只要開著就持續交畫面，所以「一段時間沒有畫面」本身就是可靠的訊號。RecordStuff 錄影中超過 2 秒沒有畫面就判定遺失；macOS 上另外每 250 ms 檢查裝置是否仍然連著，斷線時立刻判定，不必等那 2 秒。只看交付有一個盲點，值得記下來：iPhone 的 Continuity Camera 在 iPhone 上按「暫停」時，交的是黑畫面而不是沒有畫面，所以那不會被當成遺失（拿起或解鎖 iPhone 也沒有讓它停頓）。

不見時顯示什麼。最簡單的實作會一直用最後一張畫面，於是錄影裡出現一張凍結的臉，觀眾會以為講者當機了。RecordStuff 遺失時不再給合成器任何攝影機畫面，錄影只剩螢幕；錄影繼續，結束時才告知使用者，存下的紀錄標記這次錄影遺失過攝影機，和麥克風遺失的處理一致。

回來時。同一個工作階段再交出畫面，就重新合成。更難的是裝置真的離開又回來：RecordStuff 以開啟時的唯一 ID 重新開啟同一台攝影機，第一次在 2 秒後，之後逐步退避到 30 秒，絕不改開另一台；換一台攝影機會讓錄影裡突然出現另一個角度，比沒有攝影機更糟。2026-10-18 的實測中，維護者在 iPhone 上選了中斷連線：引擎在 31.6 秒時判定遺失，錄影繼續並在存檔時標記；引擎又試了 9 次，因為 iPhone 一直沒有重新連上，攝影機也就沒有回來。維護者判定這對使用者自己選擇的中斷是正確的行為。

沒有主 run loop 的行程裡，裝置清單可能不會更新。RecordStuff 的引擎跑在一個沒有主 run loop 的子行程裡。先前的麥克風工作發現，AVFoundation 在這種行程裡看不到裝置的離開與回來；對攝影機，實測時 CoreMediaIO 與 AVFoundation 的清單在 iPhone 中斷連線後都沒有變化，但這也可能只是 Continuity Camera 中斷後仍留在清單上。要等拔掉一台真正的 USB 攝影機才能分辨，這一點仍未驗證；攝影機在同一個錄影中回來的情況，目前只由核心的單元測試涵蓋。

還有一個和遺失相近的陷阱：「系統預設攝影機」在不同行程裡可能不是同一台。RecordStuff 的設定頁（Chromium 的 renderer）和錄影引擎（另一個行程）各自問 macOS 預設攝影機是哪一台，結果在筆電闔上螢幕時，設定頁顯示 iPhone，引擎卻開了內建的 FaceTime HD 相機。內建相機在螢幕闔上時仍列為已連線，也能開啟，只是送不出任何畫面，於是錄影從頭到尾沒有攝影機，還被標成遺失。修正是讓兩邊都用同一個規則決定預設：先問系統偏好的攝影機（systemPreferredCamera，會跟著 Continuity Camera 與使用者的選擇），跳過處於暫停狀態的裝置。教訓是：「預設」是一個要明確解析、在每個行程用同一規則解析的值，不是一個可以各自去問的常數。

從另一個行程顯示即時預覽，以及網頁的代價

B 架構把確認的責任交給預覽，所以預覽必須是錄影本身，而不是另一個模擬。最可靠的方式，是直接顯示合成器產生的畫面。問題在於合成器在哪裡，而預覽要畫在哪裡。

原生應用程式：同一個行程，直接畫貼圖

OBS 的預覽是一個原生的 display：libobs 在主視窗的一塊原生視圖上註冊繪製回呼，回呼裡呼叫 obs_render_main_texture()，把畫布那張貼圖直接畫上去。合成器與預覽在同一個行程、同一個 GPU 裝置上，沒有複製也沒有編解碼。Cap 錄影時的攝影機預覽是一個獨立的原生視窗，用 wgpu 繪製；在 macOS 上，攝影機畫面從 IOSurface 經 Metal 匯入 wgpu，同樣不經 CPU。

Electron：合成器和網頁在不同行程

RecordStuff 的介面是 Electron 的網頁，錄影引擎跑在另一個 utilityProcess 裡（原生程式碼當掉時只會結束那個子行程，main 會保住已寫好的部分並回報失敗）。預覽要從擷取行程進到網頁的 renderer，跨過行程邊界，再由 Chromium 的 GPU 行程畫到螢幕。每一條路都有代價：

  1. 原始畫面經訊息傳送，網頁用 WebGL 畫。在 GPU 上把合成結果縮成約 640 像素寬的 NV12，讀回 CPU，透過 MessagePort 直接送到網頁，網頁上傳成貼圖再畫。Cap 的編輯器把畫面送進網頁也是類似的路線：未壓縮的 NV12 或 RGBA，經本機 WebSocket。這條路不需要第二個編碼器，但 RecordStuff 量到它在 30 fps 錄影上多了約 12.7 個百分點，其中 9 點是網頁 renderer 與 Chromium GPU 行程在上傳貼圖。

  2. 小尺寸的 H.264 串流，網頁用 WebCodecs 解碼。同樣縮成 640 像素寬，但交給硬體編碼器編成約 1 Mbps 的 Constrained Baseline H.264，送到網頁用 WebCodecs 的 VideoDecoder 解碼再畫到 canvas。資料量小了一個數量級，代價是一次編碼和一次解碼。

  3. 原生圖層由 main 託管。OBS 的做法搬進 Electron：main 行程放一塊原生圖層顯示合成結果。代價最高：引擎的 IOSurface 要跨進 main（utilityProcess 不傳 Mach port，得自己建管道），main 要載入原生程式碼，網頁的 HTML 無法畫在原生圖層上面（拖曳把手、提示、選單都不行），Windows 還要另做一套。估計工作量是第一種的四到六倍。

  4. Electron 的 sharedTexture。Electron 44 有一個實驗性的模組，能把平台的共用貼圖（macOS 的 IOSurface、Windows 的 Direct3D 11 共用 handle）匯入成網頁裡的 VideoFrame，不經複製。限制是 importSharedTexture 只能在 main 行程呼叫，所以在 macOS 上，IOSurface 還是得先以 Mach port 送進 main，而 main 需要一個小的原生模組來接收。

WebCodecs 的意外：硬體解碼器扣住了六格

第二條路有一個量了才知道的細節。Chromium 的硬體解碼器即使設了 optimizeForLatency、串流也是不重排的 Constrained Baseline，仍扣住約六格才交出畫面：15 fps 時預覽比擷取行程送出的時間晚了 397 ms。改成軟體解碼，每一格在擷取行程送出後約 2.5 ms 就畫出來，而且處理器時間差不多（640 像素寬的畫面，軟體解碼一格約 2 ms）。所以 RecordStuff 的預覽解碼器明確要求軟體解碼：

TypeScript// preview-decoder.ts（節錄）：每個關鍵畫格附帶 avcC，用它設定解碼器
decoder = new VideoDecoder({ output: draw, error: (error) => reset(`Decoding failed: ${error.message}`) });
decoder.configure({
  codec,
  description: message.description,
  optimizeForLatency: true,
  // 硬體解碼器扣住約六格（15 fps 時 397 ms）；軟體解碼約 2 ms 一格
  hardwareAcceleration: "prefer-software",
});

「硬體一定比較好」在這裡不成立：對一個 640 像素的小串流，延遲比吞吐量重要，而硬體解碼器為吞吐量做的緩衝，正好傷到延遲。

網頁的代價有多大

RecordStuff 的預覽後來移到一個獨立的「Recording Studio」分頁（像 OBS 主視窗那樣放預覽、攝影機設定、音量表與錄影控制）。量測用三種情境：R 是一般錄影，Studio 關著；S 是同樣的錄影，Studio 開著並顯示它；L 是開始錄影前的「即時預覽」，跑的是錄影本身的管線，只是不寫檔。數字是 RecordStuff 所有行程合計的單核 CPU 百分比：

情境（2026-10-18，M1 Pro）30 fps60 fps
R：錄影，Studio 關著15.5%19.4%
S：錄影，Studio 顯示預覽24.5%（多 8.9 點）30.7%（多 11.3 點）
L：即時預覽，不寫檔16.9%16.9%

預算原本給預覽 8 個百分點。預覽在 15 fps 時，S 起初是 35.7%，把音量表改成不經 React 繪製後是 31.1%，再讓所有繪製共用一個時鐘後是 28.9%，仍比 R 多約 14 點，幾乎全是網頁在解碼與繪製預覽。把預覽降到 10 fps（錄影本身的幀率不變）後得到上表，超出預算的 0.9 與 3.3 點由維護者接受，理由是這筆成本只在 Studio 開著、而且看得到時才付。

這組數字說明了 Electron 這類網頁介面在這件事上的結構性代價：合成本身很便宜（每格幾個百分點），把畫面送進網頁再畫出來才是大宗。原生應用程式沒有這筆費用。換成 Tauri 也不會消失，它一樣是透過網頁顯示預覽。

試過的另一條路：IOSurface 直接進網頁

RecordStuff 的計畫 080 在 macOS 上試做了省掉預覽編碼與解碼的做法，並在 2026-10-19 量測後放棄。引擎把預覽的 IOSurface 以 Mach port 送出；main 行程在 Studio 第一次觀看預覽時才載入一個很小的原生模組，它只做三件事：建立管道、收一個 surface、釋放一個 surface；main 再用 sharedTexture 把它匯入成 VideoFrame 交給頁面。幾個設計重點都是為了守住「main 不能被卡住」：

  • 永遠不等。引擎先送 Mach 訊息，再經既有的 port 送該格的 JavaScript 訊息，而且頁面放掉上一格之前不送下一格（同時只有一格在路上）；main 以零逾時接收，沒東西就跳過這一格。
  • 驗證對方。管道名稱含 bundle ID、行程 ID 與隨機部分，用 bootstrap_check_in 建立（Chromium 的 Mach port rendezvous 也是這樣）；每則訊息的 audit trailer 必須來自正在被觀看的那個擷取行程。
  • 壽命明確。每個 surface 在 main 只有一個擁有者，等 Electron 回報所有參照都釋放才放掉；引擎在它被持有時不重用那塊貼圖。
  • 能退回。模組載入失敗、管道建不起來或接收失敗，該次預覽就退回現在的 H.264 串流，錄影不受影響。

這個形狀參考了開源的 ghostty-xterm-bench（MIT 授權的研究示範）：它在 utilityProcess 裡算繪終端機，用 IOSurfaceCreateMachPort 把 IOSurface 變成 Mach send right，經 main 裡 N-API 模組建立的管道送出，main 用 IOSurfaceLookupFromMachPort 取回、importSharedTexture 匯入，再把 VideoFrame 送到沙箱化的頁面。計畫的閘門是：Studio 在 30 fps 錄影上的額外成本至少降 2 個百分點，且 main 事件迴圈延遲的 p99 不比現在多超過 2 ms，否則保留現有做法並記錄結果。Windows 繼續用編碼後的串流（Direct3D 11 的共用 handle 不需要原生模組就能複製進 main，是之後的選項）。

原型在簽署過的 App 上一切照設計運作：動態名稱的 bootstrap_check_in 成功，畫面持續更新、NV12 的顏色正確，main 的事件迴圈也沒有變慢。但 CPU 沒有降：30 fps 時 Studio 的額外成本是 13.9 點，編碼路徑是 13.6 點。拆開來看，省下的部分（擷取行程不用編碼約 1.1 點、VideoToolbox 0.9 點、頁面不用解碼 2.1 點）幾乎全被新的成本吃掉：main 每格匯入與傳送多 1.5 點，GPU 行程多 1.6 點。在 App 外另做的量測說明了原因：每次 importSharedTexture 都會在 GPU 行程建立一個新的 SharedImage；而網頁上一個每秒變化 10 次的 canvas，不論用 2D canvas、WebGL、WebGPU 還是 bitmaprenderer 來畫，GPU 行程都要花約 6 點；同樣收到影格但只是用 CPU 像素重畫 canvas，也比不畫多約 3.5 點。換句話說，「把畫面送進網頁」的大宗不是編解碼，而是網頁合成本身；在這個規模（640 像素、10 fps），編碼與解碼本來就便宜，零複製能省的不多。這個結論會在幾個條件下翻轉：預覽更大或更快，讓編解碼變得昂貴；Electron 能便宜地重用已匯入的 surface（RecordStuff 估計約可再省 1 點）；或改用原生視圖直接顯示，不再經過網頁合成。

代價其實在每一格的合成

計畫 081 接著拆開「網頁的代價」到底花在哪裡，做法是同一套量測跑好幾次，每次用開發開關藏起一部分頁面。30 fps 時 Studio 比錄影多 10.8 點：藏起預覽剩 8.8 點，藏起音量表剩 11.3 點，兩者都藏起來只剩 2.4 點。也就是說，不論是預覽還是音量表在動，成本都差不多；兩者共用同一個重繪時鐘，一起動也不比單獨一個貴。

原因在 Chromium 的算繪模型：網頁只要有任何東西改變，renderer 就要產生一個新的合成影格，GPU 行程再把整個視窗合成一次交給系統。這筆固定開銷和改了多少像素關係不大。在 M1 Pro 上量到的是每秒每格約半個百分點的單核 CPU：每秒 10 格，光是合成就約 5 點；預覽另外再加上軟體解碼（約 1.8 點）與擷取行程的編碼（約 1 點）。原本以為 main 行程花了 2.2 點，拆開後只有 0.4 點，幾乎都是在轉送音量。

試過的替代顯示方式也印證了這點。在只有預覽的基準測試裡，以 MediaStreamTrackGenerator 餵 <video> 比 canvas 便宜 2.7 點，因為影片影格走 Chromium 的影片圖層，不必重畫頁面；但放回 App、旁邊有音量表時，影片影格和頁面的影格各自觸發合成，反而多了 2.2 點，所以沒有採用。

既然成本跟著幀率走，能調的就是幀率。RecordStuff 依「有沒有人在用」決定：游標在 Studio 視窗上，或 3 秒內在裡面按鍵、點擊或捲動時，每秒 10 格，拖曳泡泡、調推桿的回饋不變；否則每秒 5 格，這是錄影大部分時間的情況（使用者在別的 App 裡錄東西，Studio 擺在旁邊）。頁面在預覽的 port 上告訴擷取行程，引擎的預覽執行緒就改成每兩個 tick 產生一格，所以編碼、解碼和合成一起減半；音量也改走同一個 port，不再經過 main。結果是有攝影機出畫面時，Studio 的額外成本在 30 fps 降到 7.4 點、60 fps 降到 7.7 點，回到 8 點的預算以內；有人操作、每秒 10 格時則是 9.9 點。

被否決的做法也值得記下：用視窗焦點當訊號（在前景的視窗不一定有人在看）、一律每秒 5 格（操作時回饋變差，成本卻沒更低），以及在網頁上蓋一層原生圖層來畫預覽與音量表。最後這個能省最多（頁面幾乎不再合成），但會讓同一個畫面變成兩套 UI，還要處理捲動、縮放時的位置同步，以及另一個平台的實作，為了幾點 CPU 並不值得。「畫面沒變就不送」這種依內容跳格的做法方向正確，但只對靜止畫面有幫助，又沒有量過，所以留作日後有數據時再評估的候選。

錄影前的預覽

還沒錄影時，引擎沒有在跑，預覽可以有兩種：一種只用網頁自己的 getUserMedia 打開攝影機，螢幕則只畫出顯示器的輪廓與選單列的位置，完全不擷取螢幕；另一種是按下「即時預覽」，讓引擎準備好錄影本身的工作階段（同樣的螢幕過濾條件、攝影機合成、系統音訊與麥克風），只是不寫檔。RecordStuff 兩者都有，第二種只在使用者要求時開始，離開分頁或關閉視窗就停止，所以設定頁不會一打開就擷取螢幕。按下開始錄影時，引擎直接把這個預覽的工作階段帶進倒數與錄影：畫面不中斷，攝影機也不重開（另開一個新工作階段會留下約 0.5 到 1.5 秒的空檔）。這也是 OBS 的模型：一條管線，預覽顯示它，錄影只是多掛一個編碼器。

自由的形狀與尺寸

泡泡的形狀選擇，從固定幾個（Loom 的四種形狀與五種尺寸；Cap 的錄影預覽是 150 到 600 像素、圓形或方形或完整畫面）到完全自由（Cap 編輯器的 0 到 100 圓角，可選 squircle 或一般圓角）。如果給使用者自由，有幾個表示法的問題要先決定，因為同一個設定要套用到不同大小、不同比例的螢幕上。

尺寸用短邊的比例

用像素存尺寸，換到另一台解析度不同的螢幕就會變大或變小；用「畫面寬度的比例」存，換到直立的螢幕又會變形。RecordStuff 把寬與高都存成畫面短邊的比例（5% 到 60%，預設 20% × 20%）：一個 20% 的圓，在 1920×1080 上是 216 像素，在 3840×2160 上是 432 像素，在直立的 1080×1920 上一樣是 216 像素，形狀永遠是圓。寬與高是兩個獨立的值，再加上圓角，三者合起來就能表示圓、膠囊、方形與各種比例的圓角矩形。

位置用剩餘空間的比例

位置如果存成左上角的座標比例，泡泡在小螢幕上可能超出畫面，換顯示器或解析度時就得夾回來。RecordStuff 存的是剩餘空間的比例：x = 0 貼左邊、1 貼右邊，實際位置是 (畫面寬 − 泡泡寬) × x。這個表示法保證泡泡永遠在畫面內，任何顯示器或解析度改變都不需要夾值。位置也依顯示器分開記（最多 16 台），因為在一台螢幕上避開內容的位置，到另一台不一定合適。

圓角用圓弧

圓角是「泡泡短邊一半」的比例（0 到 100%），100% 時短邊兩端是半圓：正方形變成圓，寬的矩形變成膠囊。角的形狀是一般的圓弧圓角矩形，不是 squircle（Apple 圖示那種曲率連續的超橢圓）。理由很實際：同一個公式要在兩個地方畫，網頁的預覽和引擎的合成，必須逐像素相符；圓弧在 CSS（border-radius）、著色器（上面的有號距離）與測試裡都是同一個簡單的定義，squircle 則每個地方的近似都不同。Squircle 留作日後的選項。

攝影機畫面怎麼填滿泡泡

攝影機是 16:9 的 1280×720，泡泡可能是圓、4:3 或 16:9。填法和 CSS 的 object-fit: cover 相同：取攝影機畫面中央、與泡泡同比例的最大區塊，等比縮放到蓋滿泡泡，不變形、不留黑邊。鏡像在這一步之後做，對泡泡內的座標左右翻轉。

操作：比例按鈕與吸附

完全自由的寬與高，對大多數人反而難用，所以 RecordStuff 提供 1:1、4:3、3:4、16:9 四個比例按鈕：保留寬度、調整高度去符合比例（超出範圍時才改動寬度）。拖曳泡泡時，靠近邊緣與中央（剩餘空間的 3% 以內）會吸附；鍵盤方向鍵每次移動 1%，加 Shift 移動 10%，讓不用滑鼠的人也能精確擺放。

兩種語言，一組測試案例

泡泡的幾何在兩種語言裡各實作一次：TypeScript 給網頁的預覽與拖曳，Rust 給引擎的合成。兩份實作很容易在某個邊界上分歧，例如四捨五入：Rust 的 round 是遠離零進位，JavaScript 的 Math.round 是往正無窮進位，兩者只在負數的 .5 上不同，而這裡的值都是正數。RecordStuff 的做法是一個共用的 JSON 檔，放 180 個案例（各種解析度上限、比例、圓角，包含落在半個像素上的位置），兩種語言的測試都讀它、比對同一組答案。預覽與錄影「看起來一樣」就從一個期望，變成一個每次測試都驗證的事實。

鏡像：通話和錄影的慣例不同

人看自己的臉，習慣看鏡子裡的樣子：舉右手，畫面裡的人舉的是靠右邊的那隻手。不鏡像的自拍畫面會讓人覺得自己「歪了」，動作也難以對準。另一方面，別人看你時看到的是不鏡像的你；鏡像畫面裡，你衣服上的字和你舉起的書都是反的。

視訊通話軟體用一個區分解決這個衝突：只鏡像自己看到的預覽。Zoom 的「Mirror my video」只改變你看到的自己，其他參與者與錄影看到的都是不鏡像的畫面；Microsoft Teams 的「Mirror my video」預設開啟，同樣只影響自己的畫面，關掉它是為了在舉起文字或白板時看到和別人一樣的畫面。

錄影工具通常也是預設不鏡像：Cap 的攝影機預覽設定預設 mirrored: false；OBS 的攝影機來源預設照原樣，要鏡像得在來源的變形裡選水平翻轉。Loom 提供「Flip camera」設定，說明裡特別提醒要讓畫面裡的文字讀起來正確，就要關掉它，而且錄完之後無法翻轉。

對錄影來說，困難在於：B 架構的預覽就是錄影，沒有「只給自己看」的那一層。可以有兩種預覽策略：

  • 預覽鏡像、錄影不鏡像（通話的慣例）。使用者看預覽時覺得自然，但預覽和錄影就不一樣了，正好打破 B 架構「預覽就是錄影」的前提：他舉起一本書，預覽裡的字是反的、錄影裡卻是正的，預覽不再能回答「錄影裡會是什麼樣子」。
  • 預覽和錄影一致（所見即所錄）。預覽顯示錄影將會是的樣子，鏡像是一個明確的「錄影時鏡像」選項。代價是不鏡像時，使用者在預覽裡看到的自己有點陌生。

RecordStuff 選了第二種：「Mirror in recording」預設關閉，預覽一律顯示錄影將會是的樣子，包括鏡像與否。名稱本身就說清楚了它影響的是什麼。理由是這個架構的預覽是用來確認錄影的；一旦預覽可以和錄影不同，使用者就失去了確認的依據。鏡像是錄影的屬性，可以在錄影中改，下一格生效。實測中，錄影進行到 3.6 秒時關掉鏡像，畫面在 3.2 秒與 4.2 秒的兩格之間翻轉。

實例：RecordStuff 的攝影機與它量到的數字

RecordStuff 是一個 macOS 與 Windows 的選單列錄影工具，介面以 Electron 撰寫；擷取、時鐘、編碼與寫檔由一個 Rust 原生引擎負責，跑在 Electron 的 utilityProcess 裡（計畫 076）。它的攝影機功能（計畫 075）沒有編輯器，所以選了 B 架構，各部分的選擇整理如下：

  • 擷取：macOS 用 AVFoundation 的 AVCaptureVideoDataOutput，1280×720 的 420v（video range 的 NV12），只留最新一張；Windows 用 Media Foundation 的 source reader，要求接近 1280×720、最多 30 fps 的 NV12，MJPEG 的攝影機由 reader 解碼與縮放。
  • 合成：compose.wgsl 一份，建置時由 naga 翻成 MSL 與 HLSL；macOS 經 CVMetalTextureCache 把 IOSurface 的兩個平面當成 Metal 貼圖原地讀寫，Windows 在 Direct3D 11 上做；沒有硬體影像處理器的 Windows 裝置（WARP）則把螢幕讀回 CPU 再上傳。
  • 錄影中修改：位置、大小、圓角與鏡像從 Studio 的預覽送出一則版面訊息，下一格生效，每次修改都記進該次錄影的記錄；系統匣（選單列）可以隱藏與顯示攝影機，隱藏時攝影機仍開著。
  • 遺失：2 秒沒有畫面，或裝置斷線，就判定遺失；錄影只剩螢幕，結束時告知並標記；以同一個唯一 ID 重新開啟，退避 2 到 30 秒。
  • 預覽：640 像素寬（2026-10-24 起配合放大的預覽區改為 960）、有人操作時 10 fps、只是看著時 5 fps 的 H.264，經 MessagePort 送到 Studio 頁面，以 WebCodecs 軟體解碼。

不要這樣做的情況

  • 不要在已經有編輯器的產品裡，把攝影機燒進螢幕畫面。使用者既然會打開編輯器，分軌就幾乎免費地換來事後調整的自由；燒進去等於丟掉它。
  • 不要為了 B 架構而放棄預覽，或讓預覽變成另一份模擬。使用者看不到框，唯一的確認依據就是預覽；預覽若不是合成器的輸出，它和錄影遲早會不一致。
  • 不要讓預覽鏡像、錄影不鏡像，如果你的預覽就是錄影本身。要通話式的自拍鏡像，就需要一層只給使用者看的畫面，例如 A 或 C 的浮動視窗。
  • 不要在 CPU 上逐像素合成整張螢幕，除非畫面本來就在 CPU 記憶體裡（例如沒有 GPU 的虛擬機）。讀回與上傳本身就比合成貴。
  • 不要因為有跨平台繪圖函式庫就引入它，如果你的合成只有一層、而它在某個平台上沒有你用的 API 後端。先問它除了著色器還共用了什麼。
  • 不要在攝影機遺失時凍結最後一張畫面。錄影裡一張不動的臉，比沒有臉更令人困惑。
  • 不要讓每個行程各自決定「預設攝影機」是哪一台。同一個規則、明確解析，否則設定頁和錄影會各開一台。
  • 不要假設硬體解碼器的延遲比較低。對小而即時的預覽串流，先量從送出到畫出的時間。
  • 不要把「預覽送進網頁」的成本算成合成的成本。它們在不同行程，成因不同，解法也不同；分開量，才知道該改哪一個。

可以帶走的判斷準則

  • 停止錄影時，使用者要的是成品還是素材？成品就是 A 或 B；素材而且有編輯器，就是 C。
  • 使用者的螢幕能不能讓出一塊？能，A 最便宜；不能（要點到底下的按鈕、框會擋住內容），就是 B 或 C。
  • 使用者靠什麼確認觀眾會看到什麼？如果答案是預覽，預覽就是核心功能，要量它的成本、要保證它就是錄影。
  • 合成器和顯示預覽的地方在不在同一個行程、同一個 GPU 裝置上？在，直接畫貼圖；不在，就要選一條跨行程的路，並量網頁那一側的成本。
  • 沒有攝影機時，錄影有沒有逐位元組不變？把它寫成測試。
  • 你的錄影器在螢幕靜止時做了什麼省資源的事？攝影機會讓它失效，成本要用「螢幕一直在動」來估。
  • 每個尺寸與位置的表示法，在別的螢幕上還成立嗎？短邊比例與剩餘空間比例讓「換顯示器」不需要任何修正。
  • 同一個形狀在幾個地方畫？每多一個，就選一個更簡單、更容易在每處精確實作的公式，並用共用的測試案例綁住它們。
  • 你的預覽是給自己看的，還是給觀眾看的？這決定了鏡像的預設值。
