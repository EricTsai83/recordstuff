## Goal and decision

**D1 — the editing phase starts with this slice only (maintainer, 2026-10-23).** RecordStuff is a small menu-bar recorder and [design decisions](../docs/system-design/decisions.md) keep it small, so the phase grows one slice at a time: 087 is decided only after this slice is in use, and declining it then leaves this slice complete on its own. The flow: in the Recordings tab, a recording's menu offers **Edit…**; an edit view plays the recording on a timeline where the user marks parts to remove, at the start, at the end or anywhere in the middle (several ranges); **Export** writes a new file beside it and leaves the original untouched; the edit is remembered so the view reopens where it was left. Its cost: an edit view, an export worker and a few kilobytes of edit state per edited recording; no change to recording.

**The source is never written.** Every path here only reads the original: the export writes a new file and publishes it under a new name, the edit state lives apart in userData, and nothing in this plan opens the source for writing, renames, moves or deletes it. A failed, cancelled or crashed export, a full disk or a corrupt edit record can lose the export or the edit, never the recording.

Glide's separation of media and edits is the reference, not its schema.

## Decisions to take at the start

- **D2 — cuts are frame-exact (maintainer, 2026-10-23), by a smart cut.** Recordings have a key frame at least every second and no B-frames on both platforms (`MaxKeyFrameIntervalDuration` 1 s and frame reordering off on macOS; a GOP of one second's frames and no B-pictures on Windows). So a kept part may already **end** at any frame by copying; only where it **resumes** inside a group of pictures does it need new pictures. The export therefore copies the video's samples unchanged everywhere except, at each resume point S that is not a key frame, the frames from S to the next key frame (at most one second): those are decoded from the preceding key frame and re-encoded with the engine's own H.264 encoder as a closed group starting with a key frame at S, at the source's resolution, profile and level and at least its bit rate. Each join costs at most a second of decoding and encoding, so export stays close to the disk's speed, and the rest of the video is untouched. The re-encoded pictures' parameter sets (SPS/PPS) should equal the source's, since the same engine with the same settings wrote it; where they differ, the output gets a second `avc1` sample description used by those samples. Whether that is allowed is settled once during implementation by the playback checks below, not guessed at export time: if every required player plays it, a join whose parameter sets differ uses it; if not, such a join **falls back to resuming at the first key frame at or after S**, never before it, so removed content never reappears and never overlaps the previous kept part; the cost is up to a second less of the kept part, and a kept part shorter than that is dropped. The adjusted range then drives the video, the audio and the edit view's preview alike, and the edit view marks the join and says what moved. **Audio is re-encoded** with the engine's AAC encoder ([aac.rs](../native/capture/src/aac.rs)), cut sample-exactly at the video's cut times with a few milliseconds' fade at each join, so joins neither click nor shift sync; an AAC edit list per join is not used, since players handle multi-entry edit lists unevenly.
- **D3 — where edits live.** Recommended: in userData, keyed by the source's identity (path, size, modification time and a hash of its first and last MiB), not as a sidecar in the output folder, whose subfolders are the Recordings tab's categories (plan 071). The source is referenced, never copied: an edit needs no copy, and copying every edited recording doubles its disk use.

## Steps and ownership

- [ ] **Edit state.** A version-1 record per source: its identity, the removed ranges as integer media time (the video track's timescale, sorted and non-overlapping, a bounded count), and a revision. One writer: main, which the single-instance lock already makes unique per user ([index.ts](../src/main/index.ts)); no cross-process file lock. Writes are atomic (temporary file, fsync, rename, directory fsync); the last valid revision survives a failed write. Reading is bounded (a size limit; a malformed record is reported and kept read-only, never reset to defaults); an unknown version is refused read-only. No migration framework until a version 2 exists. A source that is missing or no longer matches its identity shows the edit as stale and offers to discard it; nothing deletes a user's file.
- [ ] **Remux in an export worker.** A `utilityProcess` of its own, supervised as the capture host is, runs a remux in the native engine: read the source's samples with a bounded MP4 reader for the files the engine itself writes (plain and hybrid MP4 since plan 076; other files are refused with a clear reason), copy the kept video samples with their timestamps closed up across each removed range, re-encode the pictures from each non-key-frame resume point to the next key frame (D2; hardware H.264 decode and encode on both platforms, the queues bounded), decode and re-encode the kept audio (AudioToolbox on macOS, Media Foundation on Windows), and write both through the engine's existing muxer ([mux](../native/capture/src/mux)). No new dependency is needed for this; if one is proposed, record its license, platforms and rollback cost first. Media buffers are bounded independently of the file's length; the only state that grows with it is the output's sample index, which the muxer keeps in memory to write `moov` at the end (about a dozen bytes a sample, a few MB for two hours), as the recording's writer already does. Progress is reported to main; frame bytes never pass through main.
- [ ] **Safe publication.** Main reserves a new destination beside the source (`<name> (edited).mp4`, numbered on collision), never overwriting; the worker writes an owned temporary file in the same folder, syncs it, and main publishes it by rename only after the worker's finalization succeeded. Cancel, a worker crash, disk full or quit remove only the owned temporary file; a temporary file left by a crash is recognised by its owned name and removed at the next launch. The source's bytes never change.
- [ ] **Admission.** One export at a time. An export is refused while a recording or a Live preview runs, and a recording asked for during an export cancels the export first (the recording always wins), through the existing recording state and quit gates. Quit during an export cancels it within the bound below.
- [ ] **The edit view.** Production components and CSS in Settings' Recordings tab ([UI alignment rules](../docs/testing.md#keep-test-ui-aligned-with-the-app)): the player on a timeline where ranges are marked for removal (split at the playhead, select, remove, undo), frame-exact cuts per D2 (a join that fell back is marked), a preview that skips removed ranges, Export with progress, cancel and error/retry, the stale-edit state, English and Traditional Chinese. The existing player and library actions are reused.

## Gates and completion

The source's checksum is unchanged by every path, including fault injection at each publication step (worker killed, disk full, rename failure, quit). The exported file passes `pnpm verify --sync` and a full decode without errors, and plays and seeks across every join in QuickTime, in the app's own player (Chromium) and in Windows' Media Foundation (by CI). For each smart-cut join, the first frame after it is the source's frame at the requested point (PSNR at least 40 dB against the decoded source, the re-encoded run alike); for each fallback join (forced in a fixture), it is the source's key frame at or after the requested point and no frame of a removed range appears; a fixture also covers a kept part shorter than its fallback, which is dropped and reported. The duration equals, to the frame, the total of the kept parts as adjusted. The second-sample-description path is checked on all three players once with a fixture whose parameter sets are forced to differ, and its result recorded as the rule D2 applies. The A/V offset stays within the source's, measured after every join as well as at the start; joins are inaudible on a tone fixture (no step above the fade's level). On generated 64 MiB and 2 GiB files and a two-hour, 60 fps file (the largest sample count), the remux runs at least at half the rate of a streaming copy of the same bytes by the same worker on the same volume (read, write and fsync in bounded chunks; no clone or hard link, so `pnpm bench:publication`, which links where it can, is not the reference), with peak worker memory at most 64 MiB in every case, and cancel completes within 1 s at p95. Recording, idle and Settings costs stay within the [pipeline baseline](../docs/system-design/tooling.md#pipeline-baseline)'s spread; a normal MP4 save never depends on any of this.

## Verification

Focused tests for the edit record (atomic write, bounded read, unknown version, stale identity), the MP4 reader against files the engine wrote (unit fixtures plus a malformed-input set) and the worker protocol; `pnpm check` for the engine, worker and host change; `pnpm test:scope -- library player` and the final `pnpm acceptance:regression` for the UI. A desktop round on a fresh signed bundle after the “好了” handoff: edit and export two real recordings (30 and 60 fps), one with a head and tail removed and one with two ranges removed from the middle, each cut between key frames, play the results in QuickTime with seeks, and verify them. Windows by CI only (the remux is shared code, its hardware behaviour unobserved). CI is not power-loss evidence.
