開著的檔案擋住資料夾改名：Windows 與 macOS 的差異，以及有上限的重試

同一行 fs.rename，在 macOS 上永遠成功，在 Windows 上卻偶爾失敗、而且本機重現不出來。原因是兩個系統對「檔案正開著」的處理方式不同：macOS 和 Linux 記住的是檔案本身，Windows 則會讓開著的檔案擋住它所在資料夾的改名。本文說明這個差異、Node.js 會回報哪些錯誤碼，以及為什麼「只在 Windows、只對特定錯誤碼、有上限地重試」是這種情況下較好的預設。範例來自一個選單列錄影 App 的錄影檔資料夾改名。

這篇文章要回答的問題

很多桌面 App 都會管理使用者的一個資料夾：列出檔案、產生縮圖、讀取中繼資料，也讓使用者重新命名或移動子資料夾。這些工作通常在背景進行，使用者隨時可能按下「重新命名」。

在 macOS 上，這兩件事互不干擾。移植到 Windows 後，改名卻偶爾失敗，錯誤是看起來像權限問題的 EPERM，再按一次又成功了。可遷移的問題是：當檔案操作會被「別人暫時開著檔案」擋住時，程式該怎麼分辨暫時失敗和真正的失敗，又不讓使用者等太久？

兩種記住「開著的檔案」的方式

macOS 與 Linux：記住的是檔案本身

在 macOS 和 Linux（POSIX 系統）上，程式打開檔案後拿到一個「檔案描述子」（file descriptor）。它直接指向磁碟上的檔案本體（inode），之後就和路徑無關了。路徑只是「資料夾裡的一筆名字對到哪個 inode」，改資料夾的名字只動到上一層的那筆名字，裡面的 inode 完全沒變。

Linux 的 rename(2) 手冊明確寫著：改名時，指向舊路徑的已開啟檔案描述子不受影響。所以檔案開著，照樣可以改它所在資料夾的名字，正在讀的程式也繼續讀得到。

Windows：開著的檔案會擋住上層資料夾

Windows 上打開檔案拿到的是一個 handle。開檔時要指定「共用模式」（share mode），決定別人能不能同時讀、寫或刪除這個檔案。Node.js 底層的 libuv 開檔時三種都允許：

共用旗標允許別人同時做的事
FILE_SHARE_READ讀這個檔案
FILE_SHARE_WRITE寫這個檔案
FILE_SHARE_DELETE刪除或改名這個檔案本身

所以在 Windows 上，改「開著的那個檔案」的名字可以成功。但這個允許只涵蓋檔案本身，不涵蓋它上面的資料夾：資料夾裡只要有任何一個檔案開著，改資料夾的名字就會被拒絕。Microsoft 的 MoveFileExW 文件沒有明寫這條規則，但這是 Windows 上常見而且可重現的行為，下面提到的 graceful-fs 也是為了它才在 Windows 上重試。

更麻煩的是，在 Windows 上開著檔案的往往不是你的程式：檔案總管的預覽與縮圖、防毒軟體掃描、搜尋索引都會短暫打開檔案，通常很快就關掉。

Node.js 看到的錯誤碼

fs.rename 失敗時，Node.js 會把各系統的錯誤統一成 POSIX 風格的錯誤碼，放在 error.code。在 Windows 上，libuv 呼叫 MoveFileExW，再把 Windows 的錯誤對應過來：ERROR_ACCESS_DENIED 變成 EPERM，ERROR_SHARING_VIOLATION 變成 EBUSY。所以同一個錯誤碼在兩個平台上代表的事不一樣：

錯誤碼macOS / Linux 常見原因Windows 常見原因
EPERM真的沒有權限沒有權限，或資料夾裡有檔案開著，或目標名稱已經是一個資料夾
EACCES沒有寫入上層資料夾的權限沒有權限，或被占用
EBUSY資料夾正被系統使用，例如是掛載點共用衝突：檔案正被其他程式以不相容的模式開著
ENOENT來源不存在來源不存在
ENOTEMPTY / EEXIST目標是非空的資料夾目標已存在

在 Windows 上看到 EPERM，不一定是權限問題。很多時候只是有人暫時開著裡面的檔案，等一下再試就會成功。把它直接顯示成「沒有權限」，會誤導使用者。

天真做法的失敗方式

最直接的寫法是呼叫一次 fs.rename，失敗就把錯誤回報給使用者。在 macOS 上開發和測試時，這個寫法完全正確，因為背景工作開著檔案也不影響改名。

到了 Windows，它會出現三種典型症狀：

  • 偶發失敗：只在背景工作剛好開著檔案的那幾十毫秒內失敗，再按一次就成功。
  • 錯誤訊息誤導：使用者看到「改名失敗」，但他其實有權限，也沒做錯任何事。
  • 測試時好時壞（flaky）：CI 上的 Windows 偶爾紅燈，開發者在 macOS 上怎麼跑都重現不出來。

有上限的重試：三個條件

這類「被暫時占用」的失敗通常很快就會消失，所以合理的做法是等一下再試。但重試本身也有成本，需要三個條件把它限制住，每個條件各對應一個風險：

條件它防止的問題
只在 Windows 上重試macOS / Linux 的 EPERM 就是真的沒權限，重試只會拖慢錯誤回報。
只對 EPERM、EACCES、EBUSY 重試ENOENT、EEXIST 這類錯誤再試多少次結果都一樣。
總等待時間有上限真正的權限問題在 Windows 上也是 EPERM，不設上限會讓使用者一直乾等。

等待的間隔可以逐步拉長：一開始短，因為多數占用很快就放開；後面長一點，給防毒軟體這類較慢的程式時間。

和其他做法比較

  • 完全不重試：最簡單，但會把暫時的占用當成失敗回報給使用者，正是上面那三種症狀。
  • 只等自己的背景工作結束：能避開自己開的檔案，也值得做；但檔案總管、防毒軟體開的檔案你控制不了，所以仍然需要重試。
  • 像 graceful-fs 一樣重試很久：這個常見的 npm 套件在 Windows 上會對同樣三個錯誤碼重試最多 60 秒，而且只在目標名稱還不存在時才重試。它適合建置工具這類沒人盯著的批次工作；但使用者按下「重新命名」後，等一分鐘才看到失敗太久了。

什麼時候不該用

  • 開著檔案的就是你自己：先把自己的 handle 關掉，或等自己的工作結束再改名，比重試更直接。
  • 操作不能重複執行：rename 失敗時什麼都沒發生，可以安全地再試；複製、寫入這類失敗時可能已經做了一半的操作，不能直接套用同樣的重試。
  • 目標名稱可能已存在：在 Windows 上，目標是一個現有資料夾時也會得到 EPERM。先檢查目標是否存在，否則會白白重試到上限才失敗。

回到範例：錄影 App 的資料夾改名

這個 App 在選單列執行，會列出使用者錄影資料夾裡的影片，並在背景逐一打開影片讀取時長。使用者可以把錄影分到子資料夾，也能重新命名子資料夾。它的 CI 在 macOS 和 Windows 上都會跑同一套測試。

有一次 CI 的 macOS 通過、Windows 失敗，失敗的是資料夾改名的測試，而且在本機 macOS 上連跑五次都通過。測試的步驟是：

  1. 建立 Demos 資料夾，放入 a.mp4 和 b.mp4。
  2. 把 a.mp4 標記為「等待移到垃圾桶」，App 隨即重新列出檔案，並在背景打開 b.mp4 讀取時長。
  3. 測試立刻把 Demos 改名為 Talks，預期得到 { folder: "Talks" }。

第 2 步的讀取不會等完成才往下走。讀取剛好還沒結束時，Windows 拒絕改名；App 只把 ENOENT、ENOTEMPTY、EEXIST、ENOTDIR 對應成具體的問題，其他一律回報 { problem: "failed" }，測試因此失敗。這也是 App 的真實問題：在 Windows 上，縮圖或防毒軟體同樣會讓使用者的改名偶爾失敗。

需要說明的是，那次 CI 的紀錄沒有印出實際的錯誤碼，因為測試把記錄函式換成了假的。EPERM 是根據「只有 Windows 失敗」和上面的行為推斷出來的，並以修正後 Windows CI 是否穩定通過來驗證。

修正採用上面的三個條件：只在 Windows 上，遇到這三個錯誤碼時依序等 50、100、200、300、400 毫秒再試，總共大約一秒，仍然失敗才照原本方式回報。改名前，App 本來就會先檢查目標名稱是否被占用，所以不會白白重試。

TypeScriptconst FOLDER_RENAME_RETRIES_MS = [50, 100, 200, 300, 400];
const HELD_OPEN = new Set(["EPERM", "EACCES", "EBUSY"]);

async function renameHeldFolder(from: string, to: string): Promise<void> {
  for (const wait of process.platform === "win32" ? FOLDER_RENAME_RETRIES_MS : []) {
    try {
      return await fs.rename(from, to);
    } catch (cause) {
      if (!HELD_OPEN.has(errnoCode(cause) ?? "")) throw cause;
      await new Promise(resolve => setTimeout(resolve, wait));
    }
  }
  await fs.rename(from, to);
}

在 macOS 上迴圈是空的，只會執行最後那一次 fs.rename，行為和修正前完全一樣。對應的測試把 process.platform 假裝成 win32，並讓前兩次 rename 回報 EPERM，確認第三次成功。這樣在 macOS 上跑測試，也能驗到 Windows 專用的重試邏輯。

帶走的判斷問題

  1. 這個檔案操作只在 Windows 上偶爾失敗、本機重現不出來嗎？先懷疑有東西開著相關的檔案。
  2. 開著檔案的是誰？是自己的程式，就先關掉或等它結束；是系統或其他程式，才需要重試。
  3. 失敗的操作能不能安全地再做一次？只有失敗時什麼都沒發生的操作，才能直接重試。
  4. 哪些錯誤碼代表「暫時」？只對它們重試，其他錯誤立刻回報。
  5. 誰在等結果？使用者在等，就把上限設在一秒左右；批次工作沒人盯著，可以等久一點。
