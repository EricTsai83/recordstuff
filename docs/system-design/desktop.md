## Tray and notifications

Sources: [tray-model.ts](../../src/main/menus/tray-model.ts), [tray.ts](../../src/main/menus/tray.ts), [index.ts](../../src/main/index.ts).

TrayModel is a pure projection containing icon, title, tooltip, and a flat list of commands; preferences are not in the tray at all, so what the model returns is exactly what the menu shows. AppTray maps it to Electron without a separate business state machine. What a left click does is the user's choice (`trayClick`, Settings → General, 2026-10-04): open the same menu, as menu bar icons usually do, or toggle recording — start, and during the countdown, or once a start has lasted a second (plan 065), cancel. A new install opens the menu; a settings file from before the choice keeps the click that records, the behaviour its user learned. Right-click always builds the menu from current state and settings. Hovering over the tray icon shows the current status in the native tooltip, with the notes it holds back (a deferred quit, an error box waiting) and the unread failure count; it says nothing about clicking, which the user's own choice decides (2026-10-04, formerly “Click to open the menu” or “Right-click to open the menu”, and “Click to cancel.” during a countdown). Windows shows only the first 127 characters of a tooltip, so a longer one is cut there with “…”; the menu repeats every line in full. On macOS a left click that opens the menu attaches it with `setContextMenu` on the press (Electron's `mouse-down`, emitted before it looks for an attached menu), so macOS opens it there with the item highlighted once: popped from the click with `popUpContextMenu`, it opened after the release and Electron pressed the item again, and the highlight blinked on, off and on (2026-10-05). The menu comes off once it closes, or at once if it did not open. It never stays attached: an attached menu opens on every left click regardless of the choice, and Accessibility reports it as an open menu, which `pnpm acceptance:tray` read as a menu that never closed, with each of its polls logged as an opening (2026-10-05). VoiceOver's press reports the click first and pops the menu as before; the click that records, and Windows, attach nothing. The [global shortcut](#recording-shortcut) always toggles, whatever the click does.

Every menu follows one group order (plan 048), omitting a group with nothing to show so that no separator leads, trails or doubles and an item never changes places between states: the state's actions (Start recording, Stop, Cancel recording or the permission steps, with the fix that follows Start while the folder or display blocks it); the window (Open RecordStuff, Open Recording Studio… since 2026-10-17, which opens the window at its Recording Studio tab, plan 075 D19, and Show last recording, with the shortcut explanation under them when its shortcut is unavailable); the status (the state's status line, idle's last display failure, the notes a notification may not have told, then unread failures: "Unreviewed recording failures: n" and View recording failures…, only while any is unread); and Quit RecordStuff. Since 2026-10-09 the actions lead and the status sits above Quit, so Start recording is the first item and no line pushes it or the window down; only the permission line still heads its steps, which mean nothing without it while nothing can be recorded. Since 2026-10-05 the status line shows only when it says more than the actions, so a plain Ready, the countdown's seconds, which an open menu would leave stale, and Recording, which `REC` and Stop already say, are left to the tooltip, while the chosen display, an unavailable folder or display, Starting, Saving, the permission and quit lines stay. Since 2026-10-04 the menu keeps only what is to be done now: the output folder, Change output folder…, the folder-revealing Show last recording, the way back to reviewed failures and Show log moved into RecordStuff (Recordings' Show in Finder and newest-first list, Recording settings → Output folder, the Failures tab, General → Troubleshooting), and Change output folder… returns to the state group only while an unavailable folder is what stops the next recording, as Use Primary display does while the chosen display is unavailable (2026-10-04, the fix the Settings card and Screen row already offered). Show last recording came back the same day as a way into the window, offered in every state beside Open RecordStuff: it lists the output folder afresh and opens RecordStuff on Recordings with the newest recording (the tab's first card) scrolled into view and its Play button focused, as the saved notification's click does for its own file, never the folder; an empty or unreadable folder opens the tab on what it shows. Open RecordStuff replaced Settings…, since the window holds the recordings as well. Reviewed failures no longer head the menu, and the "Recent failure" line is gone. Start recording, Stop and Cancel recording show the registered recording shortcut, and Open RecordStuff the shortcut that opens it, as native right-aligned accelerators with `registerAccelerator: false`, so the menu never registers a second global shortcut; an unregistered shortcut shows none, and the tooltips stay. A Start recording chosen from an open menu after the state moved on does nothing and is logged (`Recorder.startIfIdle`). Settings is never disabled for a recording: the panel itself says which preferences are locked. While the tray shows a quit in progress (below), only Quit stays enabled, because a quit in progress ignores every other action and stops capture itself. RecordStuff's window does the same: its Quit RecordStuff stays and every other control is disabled, so either Quit can still turn a Relaunch waiting on a save into a plain quit. Each state has its own 16 pt template (plan 040): the hourglass replaced the ring plus `…` title for starting and saving (a ring with three small dots inside was tried first and read as too faint at menu-bar size), and the countdown shows a stopwatch with no title because the corner of the recorded screen carries the digits. Only `REC` changes the item width. The unread-failure badge still replaces only the idle ring. An open menu does not follow the state: on macOS 26 with Electron 44.3 a menu shown by `popUpContextMenu` keeps its items while open, and neither changing them nor `closeContextMenu()` affects it (an isolated probe, 2026-09-27), while main's timers keep running. Rebuilding it would cost nothing; the platform does not allow it. So each choice is resolved against the current state when clicked: a Cancel recording from a menu opened during the countdown that is chosen after capture began stops the recording, which is saved. While a quit waits for recording work or the history save for longer than 0.3 s, a settled tray shows the hourglass and "Quitting once the recording is saved or cleaned up…", or, once recording work has settled, "Quitting once settings and failure history are saved…", until the app exits, the quit is deferred with its notification or the user stays (plans 035 and 055). Exit cancels that pending status, and a destroyed tray ignores later updates, because the modal unsaved-history prompt can delay the timer past teardown (035's D4). macOS uses template PNG/@2x assets and a title. Windows shows no title, so its ICOs carry the state alone (plan 034). An ICO has no template mode, so every state sits on the app icon's dark rounded base with a grey rim, and one image reads on light, dark and accent-coloured taskbars. Idle is a white ring with an empty centre; recording adds a red centre, which differs in shape and grey level, not only in hue; the warning puts an amber "!" inside the ring; busy and countdown keep the hourglass and stopwatch, whose hand stops short of the ring so it does not read as a power symbol. Each ICO holds 16, 20, 24, 32 and 48 px entries drawn on the pixel grid, for the 100/125/150/200% notification-area scales. A candidate without the base needed a dark outline that turned the ring into a thin double line on a light taskbar. The artwork has not been seen on a native Windows taskbar yet; the maintainer accepted that as untested when closing [035](../verification/history-2026-09.md#plan-035-closure--2026-09-28) (N17). REC and the stopwatch may appear in full-display recordings; this is an accepted visibility tradeoff.

### Countdown overlay

Sources: [countdown-overlay.ts](../../src/main/recording/countdown-overlay.ts), [renderer/countdown/countdown.ts](../../src/renderer/countdown/countdown.ts), [preload/countdown.ts](../../src/preload/countdown.ts), [shared/countdown.ts](../../src/shared/countdown.ts).

During the countdown ([recording design](recording.md#countdown)) a transparent square window 16 pt from the right edge of the recorded display's work area and 12 pt below its top draws only the digit: no background, box, border, ring or blur. Its size follows the recorded display (plan 045): the digit's font size is 14% of the shorter side of the display's bounds in points, clamped to 56–216 pt, and the window's side is the font size × 88 / 56 rounded to whole points, 040's ratio, so "10" still fits. The whole display rather than the work area sets it, so the Dock cannot change the digit, and a portrait display gets the same digit as the same panel in landscape. For example, a 1920 × 1080 or 1080 × 1920 display gets a 151 pt digit in a 238 pt window, a 14-inch MacBook Pro's 982 pt default 137 pt in 216 pt, and a short side of about 1543 pt or more the 216 pt maximum in 339 pt; only a short side of 400 pt or less falls back to 040's 56 pt digit in its 88 pt window. Main creates the window at the primary display's size and sets the recorded display's bounds before it sends the first digit; the window's size is all the page receives. It is placed on the display DisplayMedia resolved for the session, or on the primary display (logged) when that is unknown. The window is created during preparation and destroyed when the countdown ends, is cancelled or fails, so none remains between recordings; the app destroys it again on every settled state as a safety net. It is frameless, fixed, shadowless, absent from the taskbar, not focusable, shown inactive as a non-activating panel on macOS, ignores the mouse, and sits at the `screen-saver` level on every Space, including full-screen ones. It never activates RecordStuff or takes keyboard focus. The page is local, sandboxed and context-isolated under the settings page's CSP; its preload exposes only a value subscription, main sends the digit or `null`, and the page cannot reply. With the countdown sound on (plan 046) main loads the page with `?sound=1`, the page creates one `AudioContext` when it loads and synthesizes a tick with Web Audio for each new digit (none for a repeated value, `null` or a cancel); destroying the window silences it, and the window sets `autoplayPolicy: "no-user-gesture-required"` explicitly. The tick follows the system volume and mute; if audio fails, the digit continues silently.

The digit is SF Pro Rounded semibold, tabular and centred, sized from the window through `vmin`, white at 28% alpha with an outline of black at 10%, a white glow at 55% close round it and three soft shadows (the glow added on 2026-10-25, at the maintainer's request: without it the digit was hard to see over dark content; chosen over a white outline and a glass backing so the look over white stays as it was), both in `em` so they scale with the digit and at 56 pt equal 040's 1 px outline and shadows; its own outline and shadows carry legibility over white as well as dark content. The maintainer compared drafts at 80, 55, 40 and 28% and chose the most transparent, accepting that it fades on bright photos. It fades in over 120 ms, crossfades between digits over 150 ms and fades out over 120 ms before the window is destroyed; `prefers-reduced-motion` removes the fades and `prefers-reduced-transparency` makes the digit opaque with a stronger outline and the three shadows without the glow, still without a background. No content protection is applied: `getDisplayMedia` offers no per-window exclusion, so separation in time is the protection. VoiceOver does not reliably announce a window that cannot take focus; that is recorded as observed, not claimed as support.

Native notifications are localized and silent. Saved notifications reveal the completed file; when the disk guard ended the recording they say so ("Saved {file}. Stopped early: the disk is almost full."), as they do after the Mac went to sleep ("Saved {file}. Stopped because the Mac went to sleep."; elsewhere "…the computer went to sleep."), and the recording stays a success outside failure history ([recording design](recording.md#file-completion-and-failure)). Between `powerMonitor`'s `suspend` and `resume` every notification is held, because a banner shown during sleep is gone before the user is back; after `resume` they are shown in order at the first 1 s check that finds user input within the last 2 s (`powerMonitor.getSystemIdleTime()`), or at once on `unlock-screen`, and the notification switch applies when they are shown. A maintenance wake has no input, and timers keep counting during sleep, so neither a resume nor a timeout alone releases them (plan 050). Recording failure notifications always open Recording failures in Settings, where the confirmed outcome and recovery actions are shown; they are held and dropped like the capture notices below, and the unread failure row and its tray menu entry remain when one is dropped. Quality/language save failures are informational. A notice a session raises while capturing is held until the session settles and then shown once, like the saved notification 500 ms later on macOS, because macOS can decide `display shared` and mute a banner while the display is being recorded ([timing record](../verification/history-2026-09.md#saved-notification-timing--2026-09-20)); a new session or a quit before then drops them, and the log names each held, shown or dropped notice (plan 053). The Chromium path's resolution-cap and frame-rate downgrade notices, which compared what Chromium granted with what was asked, were removed with it (plan 078): the engine records the size and rate it is given. A microphone that dropped out during the recording ("The microphone dropped out during the recording. Only system audio was recorded while it was out.", plan 074) is held the same way, once per recording however many dropouts there were (a microphone that stalls, or is disconnected and connected again, is taken back, the same device only, plan 078), and its click opens Recording settings ([recording](recording.md#audio)).

A saved notification's click opens RecordStuff on Recordings with that recording in view (2026-10-04): the folder is listed afresh so the new file is there, its card is focused and outlined in the brand red for a moment, and nothing plays. The entry counts as pointer input, so once the outline has faded no keyboard focus line (drawn in the same red) stays behind; a key pressed there brings it back. The outline belongs to that one entry: cards drawn again later (a language switch regroups them under new day headings) are not outlined again. The log says `notification: show saved <path>`, then `show last recording: Recordings with <path>`. On macOS a notification click also asks the system to activate the clicked app; that activation once pushed Finder back behind the user's window when the click revealed the file there (the v0.1.0 report, which plan 014 answered with a second reveal after `did-become-active`). Opening the app's own window, the activation is what brings it forward, so that retry and its one-second window are gone. A save in the background opens nothing. Unsupported notifications and failed events are logged. OS notification preferences still decide whether a banner is visible. Native evidence is recorded by `pnpm acceptance:notification` ([tooling](tooling.md#notification-acceptance)). The notification icon was confirmed normal after the user's reboot on 2026-09-14.

`AppTray` retains each native `Notification` until `click`, `close`, or `failed`; `show` alone does not release it. Shutdown closes outstanding notifications and clears ownership; a synchronous `show()` failure releases the object and is logged. This keeps callbacks reachable after `show()` returns: Electron 44.3.0's [notification wrapper](https://github.com/electron/electron/blob/v44.3.0/shell/browser/api/electron_api_notification.cc) is garbage-collected and clears its native delegate on destruction. This lifecycle fix does not establish the cause of the historical undelivered click. There is no timer-based eviction; notifications without a terminal event remain owned until shutdown. Windows Action Center lifetime is not fixed or verified here: a Windows `close` event may be only a banner timeout while its history entry remains clickable.

Saved notifications are scheduled by `SavedNotification` after file finalization and idle, with one 500 ms timer on macOS; other platforms request immediately. This gives macOS time to clear the capture-related notification suppression state. It is a measured heuristic, not a readiness signal or delivery guarantee: Focus, another capture, and notification preferences still apply. Starting a new recording cancels the old pending notification permanently; a permission-recovery state (needsPermission) counts as settled, so a completed save is still announced there (the permission notice does not replace it); quit admission cancels it and suppresses saves during that attempt. A deferred quit restores future delivery without replaying suppressed saves. No queue or retry is retained. Notification request exceptions are logged without affecting the saved file. Saving and idle never wait for notification delivery. See [timing evidence](../verification/history-2026-09.md#saved-notification-timing--2026-09-20).

## Settings window

Accent controls in both themes share `--primary`: checked switches, badges, keyboard focus rings, the outline that marks where a jump landed, and shortcut-listening bars. That outline is one rule for every place that draws it (`lib/arrival.ts` and `.arrived` in `ui.css`, 2026-10-28): held for 60% of 2.4 s, then faded, a second jump restarting it; a recording card keeps its own state line's shape, and other elements set theirs through `--arrival-inset` and `--arrival-radius`. Filled accents use `--primary-foreground` for their symbols and switch thumbs. Recording marks and their halos use the fixed recording red independently of primary.

The current design (2026-10-07) follows the maintainer’s latest shadcn red reference and the [official base-mira component styles](https://ui.shadcn.com/r/styles/base-mira/button.json). [ui.css](../../src/renderer/ui.css) retains the supplied light/dark tokens, fonts, radius, tracking and shadows. Primary buttons use `hover:bg-primary/80` (the light reference’s hovered white label is about 3.75:1, below the 4.5:1 small-text AA target; no custom darkening is added); outline buttons use the input border and input hover; secondary and ghost buttons use the registry’s rules. Inputs and switches use a 2 px ring at 30% opacity; toggles and tabs use the registry’s 3 px ring. Grouped preferences use muted pressed states without a raised tile or shadow; selected icons use the primary token while labels retain foreground. The navigation preview uses a primary underline and a 24 px layout gap before narrow content; the sidebar uses a leading sidebar-primary line, with selected labels and icons using sidebar-selected-foreground. Its 190 px column has 14 px bold labels, 42 px rows and 4 px gaps; icons stay bold and hover does not change the sidebar colours. The former `chosen`, `selected`, custom hover/shadow aliases, thin-outline focus utilities and unlayered focus overrides have been removed. Those earlier appearance rules below are historical and do not override the current design. Remaining app extensions cover responsive layouts, text wrapping, recording-entry highlights, media contrast, forced colours and readable small text (13 px controls, 12 px metadata and a destructive ink companion). Brand colours remain fixed. Inter and JetBrains Mono are bundled locally; theme changes commit without an intermediate palette.

Sources: [ui-model.ts](../../src/main/app/ui-model.ts), [settings-model.ts](../../src/main/settings/settings-model.ts), [settings-window.ts](../../src/main/settings/settings-window.ts), [renderer/settings/settings.ts](../../src/renderer/settings/settings.ts).

The tray keeps the commands that must stay one click away; every preference lives in one separate, sandboxed window. Settings opens it or focuses the existing one. On macOS, while the window is open, RecordStuff is also an ordinary app (2026-10-04, at the maintainer's request; [app-menu.ts](../../src/main/menus/app-menu.ts)): it has a Dock icon, and the menu bar shows its menus with a Record menu holding the tray's state actions (Start recording, Stop recording, Cancel recording or the permission fixes, with SF Symbols and the registered shortcut) and Show last recording; the Dock icon's menu offers the same items. A Help menu holds Keyboard Shortcuts, which opens the window on the [Keyboard Shortcuts tab](#keyboard-shortcuts-tab) (plan 073); it has no key of its own. macOS shows an app's menus only while it is a regular app, which always brings a Dock icon, so both go when the window closes. The menus are in the app's language, and they keep the key equivalents the window relies on (Quit, Hide, copy and paste, Minimize) without Close or Zoom. The bundle declares no `LSUIElement` (2026-10-05, at the maintainer's request): main hides the Dock icon as the app finishes launching (`will-finish-launching`) and again once ready, so RecordStuff starts as a menu-bar app, and reopened from Finder or Spotlight it now brings its own menus every time (3 of 3 probes), where with `LSUIElement` macOS had made it active while still a menu-bar app and kept the previous app's menu bar (0 of 3). Closing the window, or Hide RecordStuff (⌘H, which hides the window as it is, keeps hidden a window whose first paint is still pending, and first tells the page, `settings:hidden`, so the player stops rather than sounding from a window out of sight, even when a full screen the viewer left playing answers after the hide), leaves only the menu bar's icon: no Dock icon and no menus stay behind; the window comes back as it was when opened again. A Dock icon still visible 0.3 s and 1 s after it was hidden is hidden again, since a hide that landed while macOS was still making the app regular (⌘H as the window loads) was undone when that finished (3 of 3 before, 0 of 3 after). Only Quit ends RecordStuff: the tray's Quit RecordStuff, ⌘Q or the Dock's Quit while the window is open, and Quit RecordStuff in the window's split control. The split control sits at the sidebar's foot or in General's narrow footer: its main button, Hide interface, hides immediately, and its arrow menu offers only Quit RecordStuff, so quitting takes two clicks. Hide uses the same state-preserving path as the application menu, keeping recording and the menu-bar app running. Every Quit entry goes through the same quit, which waits for a recording to be saved. The Record menu leaves out the tray's state lines, so a countdown does not rebuild a menu held open every second, and it names the shortcut only while that is registered: a menu's shortcut is also a key equivalent, which would start a recording while the editor records a new shortcut. The app focuses itself before the window shows, because a menu-bar app does not come forward when it merely shows a window. A new window stays hidden until the page reports that its first view, or its failed-read message, is painted: Electron's `ready-to-show` is the first frame, painted before the page has read its view, so showing then flashed an empty window for one frame. A page that never reports is shown one second after `ready-to-show`. Changes save immediately and the window stays open; a language change relabels it and retitles it in place. Closing it — with the red button or the platform close shortcut, which the panel handles itself because the application menu has no Close item; never with Escape, which closes only what is open in the window (2026-10-26, the maintainer's request, as macOS windows close with ⌘W) — leaves the menu-bar recorder running. The close shortcut is exactly ⌘W on macOS and Ctrl+W elsewhere, with no other modifier; one predicate serves the page and the shortcut editor, so macOS ⌃W and ⇧⌘W stay capturable. ⌘W itself never becomes the recording shortcut: the editor closes on it, and the validator reserves `CommandOrControl+W`, so a hand-edited settings file falls back to the default too. The typed character decides, as native menus do, and the physical W key counts only where the layout types no Latin letter there. If the page's renderer process dies, main disposes that window rather than keeping a blank one, and the next Settings open creates and loads a new window; it never reloads by itself, so a page that keeps crashing cannot loop. Close, blur and crash events act only on their own window instance, so a late event from a disposed window cannot clear its replacement. Capture still uses its own hidden renderer.

[settings-model.ts](../../src/main/settings/settings-model.ts) declares every preference once, with stable group and choice ids, and is the only place that knows what a choice does. It produces both the view the panel renders and the answer to "is this request allowed right now". The tray model is a sibling projection of the same state and context, not a source the panel reads from.

Main owns committed preferences; the panel only retains pending user choices. It renders the view it is given and sends back a group id and a choice id — never an action. Main refuses any sender but the panel's own main frame, resolves the pair against a freshly built model, and only then calls the same action handler the tray uses, which re-checks the recording state before saving. Starting, counting down, recording and saving lock every preference except language, appearance and the icon click, in the panel and again at that boundary. Saves are serialized in request order, so a second change waits instead of being reported as a failure. While saves are pending, controls display committed values from main, with non-layout save status and per-row aria-busy; newer user intent remains queued independently of older replies and pushes, and other groups remain locked until all requests settle. It then shows committed values, with an inline message when the latest choice did not take effect, and a shortcut the OS refused keeps its selection plus a note saying it is inert. A group may also carry `actions`: buttons rendered under its control, for a system pane that can override the preference in the same card. A choice in an actions group, or in that `actions` list, has no committed value to compare against, so its handler reports its own outcome as a boolean and that is used verbatim; every other choice is still judged by whether the requested value is the committed one, so a handler that reports nothing can never turn an unsaved change into a success. The control being changed stays live while its neighbours go inert, because a disabled element cannot hold keyboard focus. For the same reason a busy action button — while its own request runs, while another save is pending or while an update check is in progress — keeps `aria-disabled="true"` and the saving look instead of `disabled` and ignores activation until it settles, so Check for updates…, Retry shortcut registration or Open notification settings… activated from the keyboard keeps focus and the next Tab continues from it (plan 053). Main marks a running check `busy` rather than unavailable and still refuses it; only a choice main does not offer is natively disabled, as the failure-row actions already were. The preload exposes only read, choose, capture, change subscription and the one-time ready report; the one string the panel can need before its first view — a failed initial read — is localized from the language main puts in the page URL.

Meanwhile a toast at the window's bottom right, over every tab and drawn as Sonner draws shadcn/ui's (2026-10-06: a white card, near black in dark, with a hairline border, 8 px corners and a soft shadow, rising in), says “Moved to the Trash” over the file's name, with an Undo button showing ⌘Z and no close button. It stays 8 s, paused while the pointer is on it or focus is in it, closes at once with ×, or with Escape wherever focus is, and leaves as soon as nothing waits to be undone; a newer one replaces it rather than stacking. Undo outlives it: until the file is really moved, ⌘Z (Ctrl+Z elsewhere) on any tab, outside a text field and with the player closed, brings the newest back, and a short “Restored” toast without a button (3 s) says so. On Recordings the card that came back takes the focus; another tab stays where it is. Toast sizing and action placement follow Sonner's layout; a toast sliding out is inert so its Undo cannot act on a newer trash. It is not a live region: `#feedback` reads out the move and the restore. A file in the Trash cannot be put back from here, since `shell.trashItem` does not report its new name and macOS keeps apps out of `~/.Trash`, so the move itself waits instead; closing or hiding the window and quitting (with the settings and log flushes) move every waiting file at once. A move that fails lists the file again and says so under the header until the next action. Meanwhile the file is still in the folder, where Finder shows it.

The player is a modal shadcn/ui Dialog that only plays: a stage at the recording's own shape (since 2026-10-26, at the maintainer's request, taken from the card's picture as it opens and from the video once known, held within 21:9 either way and at least 320 px wide for its controls; formerly 16:9 for every recording, which left a portrait one a third of its width), sized by the window alone — as wide as the window less its margins or its height allows, whichever is less, so it grows and shrinks with the window (2026-10-16; until then it stopped at 860 px however large the window) — in which the recording fits, black above and below when it is wider and beside it when narrower (a Mac's screen, a portrait clip), so the stage neither grows when the recording's size arrives nor changes shape from one recording to the next (2026-10-05; until then the video's own shape set the dialog's height, from a 220 px start); the video alone, with its own controls laid over the picture as YouTube's full screen lays them out (2026-10-05, [player.tsx](../../src/renderer/player/player.tsx), shared with the full-screen window; formerly Chromium's controls with the name and buttons on a bar beneath). While it plays and the pointer rests for 2 s the shades, controls and pointer step aside, as they do when the pointer leaves it; a move, a press, keyboard focus on a control or a pause brings them back, and they stay while it is paused. A click on the picture plays or pauses; YouTube's keys work wherever focus is in the player: Space or K plays and pauses, ← and → move 5 s, ↑ and ↓ turn the volume up or down 5% (2026-10-06; muted counts as silent, so ↑ brings the sound back at 5% and ↓ to nothing mutes), M mutes, F plays full screen, and a focused control keeps its own (Space on a button, the arrows on the volume slider); on the seek bar ← and → move 5 s too, ↑ and ↓ still turn the volume, Page Up and Down move 10 s, and Home and End go to the start and the end, where its own steps would move 1% and 10% of the length. What ↑, ↓, ← and → did flashes over the picture, as YouTube shows it (2026-10-06): the volume as a speaker in a dark circle at the centre (two waves up, one down, crossed out at nothing) that grows as it fades in half a second, with its level, such as “55%”, in a pill near the top for 0.8 s; a seek as three arrows lighting in turn over “+5 s” in a dark arc at the right edge, or “−5 s” at the left, for 0.65 s. A click on the picture, Space or K flashes the play or pause sign in the same circle (2026-10-07). Pressed again it starts over; with reduced motion the circle, the level and the seek hold still and leave when their time is up. The picture and the seek bar take a pointing hand, the picture never draws a focus ring, and the seek bar's thumb grows in only under the pointer or with focus. The flashes are hidden from assistive technology, since the slider and the seek bar already say their values, and take no clicks. While the recording has no picture to show for more than a quarter second (its first load, data it waits for in playback, a seek), a white arc turns in the picture's middle, as YouTube's spinner does (2026-10-25, at the maintainer's request, in the player, its full screen and the edit view alike; a fast load never shows it), the player marked busy to assistive technology (`aria-busy`) while it shows, and held still with reduced motion. Escape, Close or a click on the backdrop closes it, before the window's own Escape, and closing pauses and releases the file. Full screen, a double-click on the video, or the page's own fullscreen should it start anyway, plays the recording in a window of its own ([video-fullscreen.ts](../../src/main/library/video-fullscreen.ts), 2026-10-05): RecordStuff's window keeps its size, where the page's fullscreen had to grow it to the screen and shrink it back, white where the picture had not yet followed. The new window is frameless and black over the whole screen RecordStuff's window is on; it starts hidden at that size, takes the simple fullscreen on macOS (nothing grows, no Space opens, the menu bar and the Dock step aside) or is created fullscreen elsewhere, and fades in over 150 ms once its page has drawn the first frame at the player's time, or after 2 s for a file it cannot decode. While the window is open it is a second idle renderer, which the [CPU budget](tooling.md#cpu-budget)'s Settings-open roles allow. It plays on with the player's time, volume and mute under the same controls, larger, and the recording's name over the top edge, which main writes into the page's query from the listing (`title`), never taken from the page; its way out (Exit full screen) sits at the bar's right end where Full screen was, and the controls step aside with the pointer after 2 s at rest while it plays. Escape, ⌘W, a double-click, F or that button leaves: the window's video stops first, so the two never sound together, and main hands the time, play state, volume and mute back at once, so the player seeks and resumes under the window as it fades out over 150 ms and closes, and RecordStuff's window takes focus again. Main resolves the source from the listing by id, never from the page. Only one plays at a time, and it ends at once, with no fade and no state, when RecordStuff's window closes or hides, leaving the player paused where it was, and a window the viewer left that is still fading out goes at once too, then or when a new one plays; only a window the viewer left, or whose page died, gives RecordStuff's window its focus back; a fullscreen page whose renderer dies closes its window, giving the menu bar and the Dock back. Escapes in the second after it ends, and every repeat of a held Escape, are dropped in main (`before-input-event`), because Chromium turned one into a close request that shut the player without a keydown the page could refuse. A held Escape, and any press within 1 s of one that closed the player (marked on the controlled Dialog's Escape close) or of the fullscreen's end, closes nothing, so pressing again and again closes one thing at a time; extra presses after the page's own fullscreen used to close the player and then the window. A recording it cannot play (gone since the listing, damaged, or a format Chromium does not decode) says so in the player and points to Open in its card's menu. A recording moved to the Trash, here or elsewhere, closes its player and menu and leaves the list; the Trash keeps it recoverable, so there is no confirmation. When the card or its playing player had focus, the card after it takes focus, else the one before, else the tab, also while the window is inactive (deleted in Finder), as a removed failure row hands its place on; leaving the Recordings tab closes the card menu.

The sandboxed page never holds a path. Main lists the folder into ids (a hash of the path) and registers one privileged, streaming scheme, `recordstuff-media:`, which serves `video/<id>` with byte ranges, so the player can seek, and `thumb/<id>` as JPEG, for listed ids only; the page's CSP allows images and media from it and nothing else. File actions arrive as group `recordingFile:<id>` and resolve only for a listed id and an offered action, outside the preference save queue, so a drag starts while the pointer is still down. Lengths are read from the MP4 boxes rather than by decoding: the capture host writes fragmented MP4, whose `mvhd` says 0, so the length is the last complete fragment's `tfdt` plus its `trun` sample durations (or the `tfhd`/`trex` defaults) in its track's timescale; only box headers are read on the way. The folder is listed when Settings opens or regains focus, while the window is open after a recording is saved or the output folder changes (with it closed nothing would show the listing, and opening it lists the folder anyway), when its saved notification opens Recordings (before the recording is selected), after a move to the Trash and after a file action that failed, so a reply already shows a recording that left the folder. While the window is open the folder is also watched (`fs.watch`, recursive since 2026-10-09 for its subfolders, FSEvents on macOS, event-driven and never polled): a video that appears, changes or leaves it, deleted in Finder for example, is listed again 250 ms after the burst of events ends, while a recording's growing `.recording.mp4` and other files are ignored; the watcher goes when the window closes or is hidden (⌘H), so the idle menu bar app watches nothing and runs no timer. A folder that cannot be watched, such as some network volumes, is still listed at the moments above. One listing reads the folder at a time; requests made meanwhile (opening Settings asks once for the show and once for the focus it brings) share one more listing after it. Lengths not yet known are read after the listing is shown and published as they are read, at most every 500 ms, so a folder of long recordings fills in as it goes; a folder that cannot be read says so instead of looking empty.

A recording's menu also offers Edit… (plan 085), which opens the edit view over the tab: the player above a timeline where parts are split off, removed and kept again with Undo, a preview that skips removed parts, and Export, which writes the kept parts beside the recording as `<name> (edited).mp4` and leaves the recording as it is; the edit is remembered. The cut, the edit records, the export worker and admission are described in [cutting a recording](editing.md).

**Live preview** (D20, 2026-10-18). OBS has one pipeline, whose picture the preview shows and a recording encodes; Live preview does the same with the recording's own session. Start recording, from the Studio, the tray or the shortcut, takes the held session through the countdown into the recording, with no gap and the camera opened once, naming the file only then (`RecorderWriter.retarget`), or takes it once prepared if it is still preparing. Between recordings switching it on holds the session and off ends it; during a recording it shows or hides the recording's picture, so the engine stops encoding the preview while hidden and the preview draws the bubble's place to drag instead (Live preview is off.), and the next recording shows its picture again. Leaving the Studio, hiding or closing the window, sleep and quit release a session that is not recording; a change to the display, quality, menu bar, folder, microphone or camera prepares it again while the Studio is open. In the 2026-10-18 round Live preview prepared in 783 ms, Start took it with the picture never breaking (912 camera frames across preview and recording, none dropped) and the file was named at Start's time, and a second preview left by changing tab was cancelled with its temporary file removed and its capture process gone. **Meters, mutes and faders.** The Audio panel has System audio (the display's sound and apps' together) and, while the recording takes the microphone or, before one, while the Microphone switch is on, Microphone. Each always shows its name, meter, mute and fader in the same places (2026-10-24, so nothing moves as a recording starts): between recordings there is no level to show or sound to mute, so the meter rests at silence, asks for no levels, and the mute is unavailable (from 2026-10-22 until then the meter and mute appeared only while a recording ran, from plan 095 in the toolbar line). The mute says Mute in words beside its icon, the same width muted or not, its state its pressed look. Each meter shows its input's loudest sample after its fader and before its mute, from −60 dB to full scale, rising at once and falling 20 dB a second; the page asks main for levels (`watchLevels`) only while a meter is shown and the window is visible, and they come from the capture process on the Studio's port, not through main (plan 081); it paints them on the Studio's one redraw clock at the preview's rate, 10 or 5 times a second, the preview's frames when it draws, else a timer (`frame-clock.ts`), since separate redraws for each preview frame, level and fall step cost Settings' processes more than the preview itself; a meter falls by the time since its last paint, so at either rate, and is drawn to whole pixels of its track, so a change no one can see composes no frame. Assistive technology hears the level at most four times a second, and the elapsed time changes once a second, just after each second of the recording. A mute belongs to the recording in progress, from its countdown or start until it stops, as hiding the camera does (the next recording starts unmuted): the muted input becomes silence in its place from its next sound, so it stays on the clock, and its meter turns grey under a crossed speaker while still moving. The faders (D21, 2026-10-18, as OBS's mixer) are saved settings (`audioVolume`, a whole percent of the input as it comes, from 0% to 600% in steps of 5%, default 100%). Since 2026-10-25, at the maintainer's request, 100% sits in the middle of each fader (`volumeToFader`): its left half goes from 0% to 100% by 5% and its right half from 100% to 600% by 25%, so turning an input down, the common change, has half the travel instead of a sixth; the arrow keys move a position, and a volume saved off that grid sits between two. Since 2026-10-21, at the maintainer's request, they are said in percent rather than dB, which few read at a glance: 100% leaves an input as it is, 50% halves it, 200% doubles it, and 0% is silence. Volumes saved in whole dB before then (`audioGain`) are read as the nearest step (−6 dB 50%, +12 dB 400%, −60 dB, the old bottom, 0%) and saved in percent from the next save on. They change only what is recorded, never the Mac's own output volume. They are offered before, during and between recordings, sent to a session once it is prepared and again on each change, Live preview included, and take effect from the input's next sound (`NativeCapture.setGains`), given to the engine in dB (`volumeDb`: 600% is about +15.6 dB, the engine's `MAX_GAIN_DB`; 0% its silence at −60 dB). Raising exists because a microphone often needs it, which OBS leaves to a gain filter, and the track's soft limiter above −1 dBFS keeps a raised input from clipping.

Opening the Studio starts Chromium's `VideoCaptureService` (the camera's picture before recording, through `getUserMedia`) and `AudioService`. Both stay after the Studio closes; on 2026-10-18 they were still there 70 s later and in the 60 s from 10 s after the close used 0.00 s and 0.01 s of CPU (64 MB and 41 MB resident). Chromium keeps its services for the next use at no measurable cost, so they are left as they are, but a CPU run's process roles after the Studio are not those of a launch without it ([CPU budget](tooling.md#cpu-budget)).

## Recording shortcut

Sources: [hotkey.ts](../../src/main/shortcuts/hotkey.ts), [shortcuts.ts](../../src/main/shortcuts/shortcuts.ts), [shared/hotkey.ts](../../src/shared/hotkey.ts), [index.ts](../../src/main/index.ts). Plan 016 added a global start/stop shortcut so recording can be toggled while another app is frontmost and so unattended acceptance has a system-level entry point on a process with no window.

RecordingHotkey wraps Electron `globalShortcut`. A press calls the same `toggle` function as a tray click that records, so `Recorder.toggle()` remains the only decision point: it starts when idle, cancels a countdown, stops when recording, re-issues the permission notification in needsPermission, cancels a start that has lasted a second as Cancel recording does (plan 065), and ignores presses within that first second and while stopping. Every press is logged as `hotkey: <accelerator> pressed` before the toggle, and an ignored one also as `recorder: session <id> toggle ignored while starting (<n> ms after the start)` or `… while stopping …`, so a press that did nothing is visible in the log ([recording design](recording.md#countdown)). `apply(settings)` releases the previous registration before registering the new one, so a change never leaves two combinations active; `dispose()` runs on will-quit.

The user chooses one recommended shortcut, Custom shortcut… or Off from **Settings → Shortcut** (idle/needsPermission only, like quality). The default is `CommandOrControl+Shift+1` (⇧⌘1 on macOS, Ctrl+Shift+1 elsewhere), set by maintainer decision on 2026-09-21. A global shortcut wins over the frontmost app, so the default has to be a combination no common app expects. The obvious mnemonic ⇧⌘R was rejected twice for that reason: the 2026-09-19 conflict check found it bound to hard reload in Chrome and Firefox, Reader in Safari and local recording in Zoom, so pressing it in a browser starts a screen recording instead of reloading. Existing users keep it as their current custom value; it is no longer a suggested option. Digits are the quieter range — macOS owns ⇧⌘3/4/5 for screenshots and screen recording, and apps bind plain ⌘1…9 for tabs and view modes rather than the shifted form — but ⇧⌘1 has not been through the same app-by-app check; that belongs to native acceptance. `CommandOrControl+Alt+Shift+R`, the previous default, was verified unbound in Chrome, Safari, Firefox, Finder, Xcode, VS Code, Slack and Zoom as of 2026-09 and remains valid for existing users without being offered as an alternative. Every accelerator an earlier version shipped stays valid, which a compatibility test checks; the menu offers only `DEFAULT_HOTKEY`. Custom values pass `validateAccelerator`: at least CommandOrControl or Control, optional Alt/Shift, one supported key, no duplicate modifiers, at most 64 characters, and a short macOS reserved list. Canonical order is CommandOrControl, Control, Alt, Shift, key. Unsupported stored values still fall back with a warning.

Custom… records physical letter/digit/function/punctuation key codes and named Space/arrows; on Windows a letter key records the letter it types, as below. Unsupported codes, including numpad keys, are refused. Shifted punctuation aliases normalize to Shift plus the base key before reserved-combination validation. Reserved combinations follow the platform (plan 064): macOS reserves ⌘Tab, ⌘Q, ⌘W, ⌘Space, ⇧⌘3–6 and the clipboard screenshot forms ⌃⇧⌘3, ⌃⇧⌘4 and ⌃⇧⌘6 ("macOS reserves this combination."); elsewhere Ctrl+Tab, Ctrl+Q and Ctrl+W are refused whether Ctrl arrives as `Control` from the editor or as `CommandOrControl` ("Other apps use this combination."), and a chord without Ctrl says "A shortcut needs Ctrl.". On both, the editing keys every app shares are refused with "Other apps use this combination.", since a global shortcut on one would take it from every app and pasting would start a recording: ⌘X, ⌘C, ⌘V, ⌘A, ⌘Z and ⇧⌘Z on macOS (⌃ is a key of its own there, so ⌃C stays a choice), Ctrl+X, C, V, A, Z, Y and Ctrl+Shift+Z elsewhere; a saved one falls back to the default with a warning, like any unsupported value. The same platform check validates a saved settings file, so `CommandOrControl+Shift+3` and `CommandOrControl+Space` survive in a Windows file, where they mean Ctrl, and fall back to the default in a macOS one, where they mean ⌘; macOS `Control+Shift+3` and `Control+Space` stay valid as before. The shortcut group is the only value-carrying control; main revalidates and canonicalizes its candidate before saving. Escape, Tab/Shift+Tab navigation away, clicking elsewhere, window blur/close, renderer failure and a 15-second timeout cancel capture. The editor states the 15-second limit; an unsubmitted timeout leaves a visible, localized message explaining that the shortcut is unchanged and how to edit again, and the same message is announced. A submitted save may outlive the lease and never receives that timeout warning. Main suspends the OS registration before acknowledging arming, then restores it on completion or cancellation; quit disposes it. Each capture is a lease owned by the window that armed it, separate from the setting transaction it may start. Cancel, blur, timeout, close, renderer failure, a recording lock and quit release it at once — even while a confirmed save is still writing — and restore the registrations committed at that moment. Release is idempotent; a late event from an older window, or an older save completing, ends only its own lease and never a newer window's capture. A confirmed save runs to completion after its window closes or crashes; an unconfirmed draft is never submitted. `AppShortcuts` owns both registrations and the persist-then-register order below. Recording locks the group. Invalid candidates show a localized reason and leave settings unchanged; the Settings combination is refused the moment it is pressed, like the other reserved ones, so the editor stays open for another try, and main refuses it again. Off preserves a custom accelerator as a selectable option. The capture button is keyboard reachable; its accessible name carries the current state, and status changes are read through the panel's single `#feedback` announcer rather than a live region of its own. The card's note and diagnostics, which main hides while the editor is open, are not read again when the same ones return as it closes, and a note that a diagnostic states as its reason is read once.

On macOS global shortcuts register by physical key. On Windows they register by virtual key, which follows the layout's letters (the key AZERTY labels A is VK_A, at the US Q position), so the editor records a letter key as the Latin letter it types, and as its US position only where the layout types none there, which is also where Windows keeps the US virtual key (2026-10-05; unverified on Windows hardware). On macOS, before app ready, main disables Chromium's `LayoutAwareGlobalHotkeys` (`physicalHotkeyFeatures` in [hotkey.ts](../../src/main/shortcuts/hotkey.ts), merged into any `disable-features` list already on the command line). With the feature on, Chromium 152 binds an accelerator to whichever key types its character in the current layout and re-registers on every keyboard change. Under Zhuyin, whose ZhuyinBopomofo layout types Bopomofo on the number row, the default ⇧⌘1 moved to the keypad, a key the editor refuses. Registration now uses the fixed US position the editor records, as Cap does through `global-hotkey`. On non-QWERTY Latin layouts such as Dvorak or AZERTY, a letter shortcut is therefore the US position rather than the keycap letter ([decision](decisions.md), [plan 043 closure](../verification/history-2026-09.md#plan-043-closure--2026-09-26)). `pnpm acceptance:shortcut-layout` checks the built app under a layout whose number row types no digits and fails if registration follows the layout again ([tooling](tooling.md#keyboard-layout-shortcut-check)).

`pnpm acceptance` sends digits, Space, arrows, F1–F20 and common unshifted punctuation as macOS key codes, and letters as typed characters. Other combinations fail explicitly with the accelerator in the error before recording begins. Because registration is physical, a key sent by key code reaches the registered shortcut under any input source, including Zhuyin. A letter sent as a character reaches it only where that letter sits at its US position, as on ABC and Zhuyin; on Dvorak or AZERTY the runner would press a different key.

A registration the OS refuses (another app owns the combination, or `register` throws) is never silent: it is logged as `hotkey: registration failed for …`, shown in Settings → Shortcut as "Another app may be using this shortcut." with a retry, and announced by a notification whose click opens Settings on the General tab, at the shortcut control. The tray menu then omits the shortcut beside Start recording. The setting is still saved so the user's choice survives a relaunch; the tray keeps working. Disabling the shortcut leaves tray behavior unchanged and remembers the accelerator so re-enabling restores it. Changing the shortcut persists first and registers second: a failed write keeps the old registration and reports "Could not save the shortcut". If a recording starts while that write is pending, the registration change is deferred (`request` → `flush` on the next settled state) so the combination that started the session can still stop it; until then the menu shows the saved choice as unavailable.

The background suite's shortcut integration (`pnpm acceptance:shortcut`, part of `pnpm test:ui`) verifies reported registration failure and failed-choice persistence across isolated Electron processes with a registration adapter, including process/window/temporary-data cleanup; `pnpm acceptance:shortcut-native` verifies Electron's real registration refusal and the real window state. Notification assertions observe invocation, not macOS banner delivery; this does not guarantee detection of every case where another app intercepts keys. Plan 020 closed with maintainer acceptance of this evidence, retaining actual OS conflict and notification banners as untested limitations; see the [closure record](../verification/history-2026-09.md#plan-020-closure--2026-09-23).

Source: [i18n.ts](../../src/shared/i18n.ts). English (`en`) is the default, including upgrades from settings files without a language field. The user can choose English or Traditional Chinese (`zh-TW`) from Settings → General → Language. There is no implicit OS-locale selection.

## Screen permission

Source: [permission.ts](../../src/main/permission/permission.ts). PermissionWatcher is created only on macOS.

1. Check getMediaAccessStatus('screen') every five seconds and on activate. A windowless app cannot rely on activate alone. This stage never prompts and materialises nothing, so polling it is cheap.
2. If not granted, clear validation and any pending retry, emit needsPermission, and call getSources at most once per process to register the app/show the system prompt.
3. If granted but unvalidated, require at least one capturable screen. A validation still unanswered after four seconds shows relaunch guidance (needsRelaunch), but the call keeps its slot: the deadline cannot cancel getSources.
4. At most one watcher-owned getSources call, prompt or validation, is unresolved at a time. While it is pending only stage 1 is polled. A grant that arrives during the prompt is validated once the prompt settles; a prompt result never counts as validation.
5. Cache success. A failure requires relaunch and is retried after a backoff counted from that failure's completion: 5, 10, 20 and 40 seconds, then every 60 seconds. Revocation resets the backoff.
6. Revocation, an actual permission-denied capture (markRelaunchRequired) and stop() start a new generation: a validation from an older generation that settles later is logged and ignored, and a fresh one follows. stop() removes the interval, the activate listener and both timers; a call still pending stays owned until it settles.

Only stage 1 is polled, and caching stage 2 for the process is what makes that safe. Cap polled the equivalent macOS call for permission state — `SCShareableContent`, which materialises every window, app and display — for the whole process lifetime, leaking about 15 MB/min until macOS exhausted swap ([CapSoftware/Cap issue #2023](https://github.com/CapSoftware/Cap/issues/2023), fixed in 0.5.9 as "Memory growth while idle on macOS"). Their post-incident design is the one used here: a cheap preflight gate polled freely, an expensive validation cached after one success, serialized, and retried no sooner than the poll period after it completes, with the same five-second and four-second constants. Cap also times out `ShareableContent::current`, but dropping that future was not shown to cancel the macOS request, so RecordStuff keeps the real promise owned instead of issuing a replacement (plan 027). A call that never returns cannot be recovered inside the process: the guidance is to relaunch, which ends it with the process. A runtime revocation is caught by stage 1, by the capture attempt itself, and in practice by macOS asking the app to relaunch. A revocation and regrant that both fall between two polls are not observed, so a validation started before them can still apply.

Only changed permission states are emitted. Recorder always stores the latest status, including while starting, recording or stopping, and never interrupts a running session for it. Every return to a non-busy state (saved, capture failure or start failure) settles from that stored status into idle or needsPermission, so a revocation reported once during a session is not lost, and a grant later in the same session needs no further event. Once permission returns, the recorder restores the idle details needsPermission does not carry (outputDirUnavailable, unless the folder was changed meanwhile). A save completed meanwhile is still announced, as described under notifications. Actual track termination, capture failure, or an OS-requested quit follows the recording cleanup path. Revoking the grant in System Settings and choosing macOS's Later leaves `getMediaAccessStatus` reporting granted to the running process while capture lists no screen at all; a capture request that finds no source although displays are connected is therefore reported as `permission_denied` on macOS, not `no_display`, which marks the relaunch-required state and its recheck (plan 035 D2).

System Settings opens through a fixed ScreenCapture URL. The app does not reset TCC. The missing-permission menu always offers relaunch because the running process may not observe a new grant. System audio has its own permission and is validated through returned audio tracks. See the [verification record](../verification/README.md) for first-grant, denial, recovery, and revocation evidence.

## Microphone permission

## Settings and output folder

Sources: [settings.ts](../../src/main/settings/settings.ts), [quality.ts](../../src/shared/quality.ts).

```json
{
  "version": 4,
  "outputDir": "/Users/example/Movies/RecordStuff",
  "quality": { "videoQuality": "standard", "resolutionCap": "source", "frameRate": 30 },
  "language": "en",
  "hotkey": { "enabled": true, "accelerator": "CommandOrControl+Shift+1" },
  "notifications": true,
  "countdown": 3,
  "countdownSound": true,
  "fileNameTemplate": "{date} {time}",
  "libraryLayout": "grid"
}
```

Only settings version 4 is read. At startup, any older positive integer version is replaced with the complete current defaults, including output folder, quality, language, appearance, shortcut and tray-click behavior. The original is kept under the first free `settings.json.reset-backup[.N]` name before the serialized atomic write. A failed backup or write retains the original and retries at the next launch or save. Once version 4 is saved, subsequent launches preserve user edits. Recording files are never moved or deleted by this reset; the library initially shows the default output folder, so choose the old folder again to see its recordings. A numeric version newer than 4 is never overwritten. Corrupt or otherwise unusable settings still use defaults and are kept as `settings.json.unreadable[.N]` before a write. Within the current format, missing fields use their defaults and unsupported values also log a warning; invalid quality alone preserves a valid output folder. `outputDir` must be a nonempty absolute path and `hotkey.accelerator` must pass the current shared validator. `microphone` (plan 074) is a boolean, false when missing, and anything else is off with the warning `microphone is not a boolean: using off`; the optional `microphoneDevice` is `{ id, label }` with a nonempty ID of at most 512 characters and a label of at most 512, and an invalid one means the system default, with a warning. The default left click opens the menu. No per-version field conversion remains.

Save operations are serialized and derive each update from the last committed settings. Write and fsync settings.json.tmp, rename it, then update memory. A failed save removes the temporary file and rejects its caller without blocking later saves. Flushing before the rename prevents an empty or half-written settings.json after a crash or power loss; without a directory fsync, a very recent change may still revert to the previous file.

Folder selection uses a native dialog, with app focus on macOS. A successful save clears the idle folder-unavailable flag and refreshes labels. Actual writability is probed when recording starts. There is no automatic fallback to a different output folder.

The tray's output-folder entry ([output-folder.ts](../../src/main/library/output-folder.ts), plan 033) opens an existing folder in Finder, as it always did. Recording creates the default `Movies/RecordStuff` only when it starts, so opening creates it as well: only that folder, with a non-recursive `mkdir`, and only when its parent exists and is a folder. A missing custom folder is never recreated. It may be on a disconnected drive, and recreating the path would put later recordings on the system disk. A path that is a file, a missing default parent, a refused creation, an unreadable path and a Finder failure (an error string or a rejected `shell.openPath`) each end in one localized warning. The warning names the full path, adds technical details where there is an error, and offers Change output folder or Cancel. The choice reuses the folder chooser above with its locks; Cancel changes nothing. When RecordStuff itself is refused access to a folder, Finder is still asked to open it, because macOS privacy folders can refuse the app but not Finder. Only a Finder failure after that produces the permission warning. Opening never writes settings.json. One attempt runs at a time: a repeated click joins it, and while the warning is open it only brings the warning forward. Every failure is also logged with its path. Recording keeps its own `mkdir -p` and write probe.

Quality, the countdown, its sound and the shortcut can change only while idle/needsPermission, and each recording has a quality and countdown snapshot, the sound included; autorecord never ticks. The output folder cannot change while a session is starting, counting down, recording or saving: its temporary file is already open there. Platform frame-rate clamping affects effective settings, not persisted preferences.

## Local app data cleanup

[DataCleanupRequest](../../src/main/app/data-cleanup-request.ts) owns the native, cancellation-default confirmation offered by General → Local app data. Main authorizes the offered ID and checks capture is settled both before and after the prompt. Starting, countdown, recording, saving and quitting cannot request cleanup. Cancellation changes nothing; repeated requests join/refuse rather than opening another prompt. Normal uninstall keeps data; explicit cleanup does not uninstall the app, reset OS permissions, or delete recordings.

Confirmed cleanup reuses normal media/metadata shutdown, waits for the history writer to settle, and deliberately discards failure history without asking for a second unsaved-history confirmation. `beforeExit` prepares [data-cleanup.ts](../../src/main/app/data-cleanup.ts); unlike the final bounded log flush, preparation failure refuses exit and restores admission. The one-shot Node helper requires an explicit commit and parent-process exit before clearing userData, sessionData and logs, including old formats, migration backups and Chromium caches. This prevents Electron from writing profile files back at shutdown. It runs from the same executable with `ELECTRON_RUN_AS_NODE`; no resident service or additional installer is added.

The helper rejects filesystem/home/temp roots, directory symlink roots and output folders containing a data root. Canonical paths protect a nested output folder (including its non-media files), history-referenced media and every `.mp4`, including partial recordings. Directory links are unlinked without following them. Protected files and their containing directories remain; unrelated output folders are untouched. Cleanup cannot erase OS permission records, OS-managed crash reports, system backups or copies outside app-owned data roots.

A `.data-cleanup.json` marker makes a simultaneous new launch wait before settings, cache or log writes. The helper removes it after success; failure leaves a diagnostic marker. A failed or interrupted cleanup is reported on the next launch, then a stopped helper's marker is released so the user can retry from Settings. A live helper or invalid status never permits new profile writes. A force quit before commit does not authorize deletion; after commit the helper still requires process exit. Filesystem deletion may partially succeed before an I/O failure, so failures do not promise rollback or secure erasure.

## Logs

Source: [log.ts](../../src/main/lib/log.ts). Current macOS paths are `~/Library/Logs/recordstuff/recordstuff.log` and `~/Library/Application Support/recordstuff/settings.json`. Electron's internal lowercase app name determines these paths; the displayed product name remains RecordStuff.

Each line starts with a UTC ISO timestamp. Startup records app/Electron/OS versions, the launch's run id, output folder, quality, packaged status, and executable path. Recording events include session, state, capture report, first chunk, saved (with any early-stop reason), failed, the stall and low-disk warnings with the writer backlog, a start failure reclassified to a retained disk error, and interruption sentinels found at launch. `power: suspend` and `power: resume` lines name the in-flight session and state; `power: keeping the display awake (blocker n)` and `power: display may sleep again (blocker n)` bracket each session, `power: keeping the system awake for a save (blocker n)` and `power: system may sleep again (blocker n)` a save that outlasts it, and `notification: held during sleep: …` marks a notification that waits for waking. Logs include local paths, but no media bytes.

Session records (plan 029). A run id, launch time plus pid such as `20260925T101530123Z-4242`, appears in the `start:` line only; ordinary lines carry no prefix. Beside the human-readable capture, `saved` and `failed:` lines the app writes one versioned record per event, `session-record: {"v":1,"run":…,"kind":…}`: `capture` (session, requested quality, capture report), `saved` (session, final path, recording and stop-request times, early-stop reason), `failed` (session, code, detail, file outcome, kept and temporary paths, times; written even when no file remains) and `refused` (a preflight refusal, which names no session). JSON keeps paths with spaces, quotes or line breaks on one escaped line. The Recorder carries the session on its terminal events because a failure's cleanup can finish after the next session started, so completion order is no identity. Development analyzers pair recordings by run and session id and read only these records where a launch writes them, never both forms as two outcomes; older logs are not rewritten.

All messages go to stdout. Before an append, a file larger than 5 MiB rotates through three archives; development runners follow a rotation with file-identity cursors ([tooling](tooling.md#selecting-acceptance-coverage)) and the policy itself is unchanged. File writes go through one serialized asynchronous queue capped at 1 MiB, so a line never waits on the disk; exit paths flush it with a bound. The active file's size is read once per process and counted from then on, so a line costs one append and no stat. A full disk or a removed logs folder only skips file lines: the next line creates the folder again and, once one is written, the file says how many it missed. A rotation another process blocks (Windows will not rename a file a viewer or scanner holds open) keeps appending to the active file, says so in it once, and retries after 512 KiB more. Any other disk logging failure reports once to stderr and disables file output for the process while retaining stdout. The first uncaught main error also shows a localized dialog, once recording work has settled ([dialogs and main's event loop](#dialogs-and-mains-event-loop)); later ones and unhandled rejections are only logged, so a fault that repeats cannot stack dialogs. A startup that fails before the app is wired up logs the cause, shows the same dialog and exits, since a menu-bar app with no tray offers no other way to quit.

Show log, in Troubleshooting → Diagnostics and cleanup → Diagnostic tools, reveals the file, falling back to opening its directory if absent, and says so when neither opens. The saved notification opens Recordings with the saved file in view; when the user has moved or deleted it since, Recordings shows what the folder holds and the log says the file is not there. Neither affects capture. Development Electron.app and installed RecordStuff.app are different permission subjects; inspect executable before interpreting a grant or failure.

## Update checks

[updates.ts](../../src/main/app/updates.ts) owns the update-check lifecycle, independently of recording. Settings → General contains Check for updates…, its result, and Check for updates on launch. Results never change the tray title or open a dialog. One case notifies (maintainer decision 2026-10-03): when the launch check finds a newer version the user has not been told about, the app sends one notification, "RecordStuff {version} is available. Click to open the download page.", whose click opens the website download page for the app's own platform (`/download?platform=mac` or `?platform=windows`, see [the website](#official-website)) directly (not through `openUpdate`, whose destination follows the checker's state at click time) under the same lock: a click while starting, recording, saving or quitting opens nothing and is logged. A version shown by a manual check counts as told, so a manual check never notifies and a later launch stays quiet about that version; a newer one notifies again. The told version only moves forward: a stale source offering an older release than one already told neither notifies nor lowers it. The notification follows the Notifications switch and the sleep hold, and a result withheld during a session is announced when it is shown. With the switch off a launch check notifies nothing and leaves the version untold, so a later launch with notifications on still announces it. Starting, recording and saving disable update actions; checks and pending results wait for idle/needsPermission.

The current settings format includes an optional `updates: { enabled, lastAttempt, notifiedVersion? }` block. Missing fields default to enabled and no prior attempt; `notifiedVersion`, the newest stable version the user was told about, is omitted until one is, and an invalid value is dropped with a log warning. 1.2.0 and earlier drop it when they save, so after a downgrade the same version may be announced once more. Atomic serialized writes preserve unrelated settings. The launch attempt timestamp is persisted before networking, including failed checks, to enforce a 24-hour limit across restarts. Future timestamps after a clock correction are treated as due. Manual checks bypass this limit and still proceed if timestamp persistence fails (with a log entry). No timer polls during the app lifetime. Disabling the preference affects launch checks only.

The app injects Electron `net.fetch` to use Chromium networking and system proxy/PAC settings; unit tests inject their own transport. A check reads `https://record.ericts.com/release.json`, falling back to the repository's GitHub latest-release API. On Windows x64 it reads only the GitHub latest-release API and accepts a release only when it carries `RecordStuff-<version>-x64-unsigned-setup.exe`, because the feed keeps the shape installed macOS apps parse and describes only the DMG; on a platform with no published asset a check finds no compatible release. This Windows path is covered by unit tests only. Each source has an 8-second deadline and shutdown aborts pending requests. Stable semantic versions are compared with `app.getVersion()`; incompatible assets, malformed data and prereleases cannot produce an update offer. A failed launch check restores the previous menu and logs; a failed manual check offers Releases and a retry. Successful checks display the local check time or a newer version that opens the same platform-specific download page; the feed's `downloadUrl` stays the bare `/download`. Downloads and replacement stay manual.

## Notification switch

Settings → General contains a Notifications On/Off switch with, on macOS, an Open notification settings… button in the same card, so the switch and the OS permission that can override it read as one decision rather than two unrelated settings. `AppTray.show` checks the switch before asking the OS (after the sleep hold, which applies it when a held notice is finally shown) and logs `notification: turned off in settings, dropped: …`, so one boolean governs every notification the app sends on its own — saved recordings, errors, update announcements, and every write-failure hint. Only direct answers to the user's own action bypass it: a deferred quit, an output-folder problem found while recording work is pending, and the permission notice that answers a click or shortcut press while screen permission is missing, and the microphone-denied notice that answers turning Microphone on ([microphone permission](#microphone-permission)). The switch is locked while a capture is running, like every other preference.

The app deliberately does not mirror the OS notification permission. Electron exposes no way to read it: `systemPreferences.getMediaAccessStatus` accepts `microphone`, `camera` and `screen` only, and `Electron Framework` contains no `getNotificationSettingsWithCompletionHandler`. It does contain `requestAuthorizationWithOptions:completionHandler:`, so Electron asks macOS for authorization from inside `Notification.show()` — the first notification of a fresh install is what raises the system prompt. `UNUserNotificationCenter` offers that prompt only while the status is `notDetermined`, and the status is kept per bundle ID and survives reinstalling the app, so there is exactly one chance to show it and a denial is final as far as the app is concerned. It is therefore spent on first launch, by the first-run hint that also tells the user where a menu-bar app lives: launch is when macOS is already asking this app for screen recording, so the notification ask arrives in that same context instead of at the end of the user's first recording. When screen permission is missing at launch, the permission notice is that first notification and the hint, which promises that a click records, waits for the first launch where it is true. The switch stays on by default — a recorder that never says it saved reads as broken, and an unspent prompt the user never finds is no better than a denied one. Turning the switch off and on again also sends a confirmation notification, which doubles as a delivery test the user can repeat. A status line would have to claim a permission state the app cannot read, so the group's ⓘ names the recovery path instead — System Settings → Notifications → RecordStuff — and the macOS action opens that pane. Turning the switch off suppresses OS notifications. In that state, the question-mark help shows where failures remain on hover or keyboard focus, rather than adding a persistent line below the switch. Help popups hide their scrollbars from initial mount so opening them never changes the available text width; height-constrained explanations remain scrollable. Recording failures still appear in the menu bar and the Recording failures section described below. `PermissionNotices` gives a permission-denied recording one notification: the failure notice if its result arrives first, or the permission notice if revocation already changed the state. The failure record and recovery actions remain available in either case. Later permission changes and direct responses to the user still notify.

This follows Cap's design (`apps/desktop/src-tauri/src/notifications.rs`), where the send path checks one `enable_notifications` boolean and nothing else. Cap additionally gates its switch on `isPermissionGranted()`, which `@tauri-apps/plugin-notification` provides and Electron does not; the ⓘ text carries that gap instead. Plan 019 first implemented a Node-API bridge to macOS `UserNotifications` to close it. That was reverted: the bridge made a bridge-load failure — a wrong-architecture or too-new `.node` — silently suppress every notification, including the implicit authorization request Electron would otherwise have made, which is strictly worse than having no status at all.

The static website endpoint projects the online-verified release manifest with version, tag, platform/architecture, DMG metadata, publication date and trusted page URLs. Unverified preview builds emit an error object instead of an advertised release. Vercel caches the feed for five minutes; the app requests it without caching. `pnpm site:check` verifies the built feed matches the manifest; Vercel's production build runs the same `pnpm check`, so `check-release.mts` verifies the feed in the `dist/` it then serves; the deployment workflow itself only uploads (`vercel deploy --archive=tgz --prod`) and runs no further check on the served output. No installation identifier, query parameter, telemetry, updater dependency or changed signing identity is involved.

The macOS settings action opens the Notifications overview; select RecordStuff there to reach its permission controls. This existing route was retained when plan 019 closed. Ordinary settings value/text updates preserve the live form controls, focus and scroll position; only tab/structure changes rebuild the form. Save-only interaction locks retain normal opacity to avoid a brief whole-panel dimming, while recording/platform restrictions remain visibly disabled.

## Settings shortcut

⌥⌘, on macOS and Ctrl+Shift+, elsewhere (`settingsShortcut` in [hotkey.ts](../../src/shared/hotkey.ts); until 2026-10-05 Ctrl+Alt+, there too, but Windows sends AltGr as Ctrl+Alt, so it took AltGr+, from every app on the layouts that type with it) opens, restores and focuses the single Settings panel through `openSettings`, including while recording.

Opening the app again while it runs does the same (plan 053), for a user whose menu bar icon is hidden behind the notch or a crowded menu bar. A second process reaches the running one as `second-instance` before it exits on the single-instance lock; on macOS, opening the running app from Finder, Spotlight or the Dock starts no second process but sends a reopen, which Electron reports as `activate`. Both go through `handleAction("openSettings")`, so a quit in progress ignores them and an open panel is reused. A notification click or the panel's own `app.focus()` only makes the app active (`did-become-active`), so neither opens Settings, and the permission watcher's `activate` check is unchanged. A click can still arrive as a launch: with a development bundle running, clicking its banner made macOS start the copy registered in /Applications, which reached the running app as `second-instance` about 0.5 s later. A registered copy that is itself running receives the click as a reopen instead: on the installed app, macOS sent `activate` 113 and 121 ms after two clicks (plan 054). Either event within `NOTIFICATION_ACTIVATION_MS` (2 s) of a notification click is therefore taken as the click's activation and ignored, with a log line; the click's own action, such as opening Settings for a capture warning, is unaffected. [reopen.ts](../../src/main/app/reopen.ts) logs each reopen and whether Settings opened. It never toggles recording; ordinary ⌘, remains untouched. `settings-hotkey.ts` owns this registration independently of the recording shortcut and releases only its own key on quit. The tray advertises it only when registered and otherwise explains failures in the selected language.

New recording choices cannot use the platform-equivalent Settings combination. A legacy stored collision is preserved and takes priority; change or disable the recording shortcut through the tray's Open RecordStuff to recover. Both registrations suspend during custom capture and resume when its lease is released (commit, cancel, blur, timeout, close or renderer failure), without waiting for a pending save. Recording locks still apply.

### Screen preference and diagnostics

Settings → Recording → Screen lists Primary display followed by unique connected displays from `screen.getAllDisplays()`; opening the panel never enumerates capture sources or asks for capture permission. The default follows the current primary. A specific choice stores only id and label in the existing version-4 settings file; versions 1–3 without the field use the default, and invalid values warn and fall back. Empty names receive localized id-based labels. The panel sends a choice id and main resolves the current action, including its label.

Added/removed/metrics events always advance topology generation; settled UI refreshes immediately and busy UI refreshes when settled. Recording locks selection. An absent or ambiguous stored choice remains selected but disabled, alongside Primary and available recovery choices. The idle tray names a healthy explicit target. Current absence and the last display failure are distinguished in both projections. Last failure lives in memory even when notifications are off; only successful recording start or a successfully saved different choice clears it. Failed saves preserve both preference and diagnostic and send the normal preference-gated notification. There is no tray submenu or system picker; system audio policy is unchanged.

Appearance in General offers System default (the default), Light and Dark, including while recording. After a successful save main sets `nativeTheme.themeSource`, updating native window appearance and CSS immediately, and restores it at startup. Missing or invalid values in older files fall back to system independently of other preferences.

## Recording failure results

Recorder emits a separate failure-status update before file cleanup completes. Main retains individual failures and their acknowledgement in `userData/recording-history.json` (version 2), independent of notification preferences and capture state. New failures appear first; delayed cleanup updates its own ID without replacing or reordering other failures. All unread records and the 20 most recently acknowledged records are retained. This is failure history, not a media library or orphan-recovery mechanism.

There is one tray item. Its idle ring carries an integrated warning badge whenever any failure is unread; recording still takes precedence with the filled icon and REC. The menu reports the unread count and offers View recording failures. A left click does what the user chose for it, as everywhere else. View recording failures and error notifications select the Troubleshooting tab, open only the newest unread row (the newest row when all are reviewed), scroll it into view and focus its header, without acknowledging it; Open RecordStuff and its shortcut open the tab last shown in a new window and keep the current tab in an open one. Opening a menu, dismissing a notification, successful recordings and elapsed time do not clear failures.

The history occupies Troubleshooting’s Failure history content tab; Recording and General show none of it, and diagnostics about a preference, such as an unavailable saved display, stay beside their control. The tab shows the history-wide status line (loading), then the rows newest first, then the retention note as a footnote; with no failures it says “No recording failures.”. Rows are grouped under day headings (Today, Yesterday, then the date, with the year only for an earlier year), which main supplies with each row's short local time. Since 2026-10-07 each day is one card, like a settings section: a row leads with a neutral cause icon (disk/folder, display, permission, audio, capture, process, timeout or compatibility), with a neutral dot for an unread row. A short badge beside the reason shows preservation: Not kept in red, Partially kept in amber, Processing and Unconfirmed result in neutral colours. These states come from the recording outcome, never from a file path; all outcome descriptions use the same secondary text colour. Each row opens inside the card with its guidance in a soft callout. Before that the rows sat directly on the window background, separated by hairlines that stop 10 px short of each side; warning colour is kept for save warnings and action errors. A row's header has two lines: the unread marker (a dot and a bold reason, with “Unread” in its accessible name, so it is not colour alone and stays visible in forced colors), the reason and its wrapping preservation badge, the time and a chevron; then the file outcome. Every row starts collapsed and opens on its own (2026-10-05; until then one at a time, which moved the row just clicked when the one above it closed, and kept two failures from being compared); a pending save or action keeps its state by ID. An open row reads apart from the closed ones: a tint over the whole record, a hairline between its header and its details, its reason in heavier ink and its chevron darker, with the hairlines beside it hidden. An explicit entry opens its target alone. The details, indented under the title, do not repeat a heading or the time: the guidance, the file name (the full path is with the technical details), the actions with Got it at the end and Remove from history only on reviewed rows, the saving and error lines, and Technical details. The header is the focus target: keyboard focus draws a thin accent border (the shared focus weight, 6 px corners, no fill) around the whole record and hides the two hairlines beside it; focus on a control inside an open row turns the row's border neutral at 1 px while the control's own border turns accent. The chevron turns over 150 ms, at once with Reduce motion. Up and Down move between headers across day groups, Home and End go to the first and last, and Enter and Space open or close. A row that moves to another day group, as across midnight, keeps the focus of its header or control, and the Technical details disclosure shows the shared focus line just off its text. Missing system audio (`no_audio_track`) names a Mac under very heavy load before the permission, because the capture host sees the same already-ended track for both causes (plan 040's load tests); its System Settings and Relaunch actions stay. Pending cleanup disables Got it and has no reveal action. Partial files are checked before presentation and again before reveal; unknown or missing paths remain hints, not promises of playable or recoverable media. File/folder/permission actions retain recording locks. Normal updates preserve each row's expansion and identity, so an older button cannot act on a newer record.

Got it durably acknowledges only the offered settled ID and collapses that row. Each Got it, Remove from history and Retry saving the record logs one line when it settles, `recording result: <action> <id> saved`, `failed (<io|blocked|tooLarge>)` or `refused (<pending record|not reviewed|… in flight|unknown record>)`, with no path or failure detail, so the log agrees with the row and can be paired with the record by ID. The badge clears only after every retained failure is acknowledged. Reviewed rows can be removed from history; neither manual removal nor trimming the oldest reviewed rows deletes recordings or logs. Acknowledgement and removal become visible only once the snapshot containing them is durable; meanwhile the row shows a localized saving line, its buttons stay focusable with `aria-disabled` and ignore activation, and other rows, preferences and recording controls stay usable. Failed acknowledgement/removal leaves the previous visible state intact with a per-row error. Retry saving the record independently saves the history without changing acknowledgement, including for unread or pending failures. Saving any update writes the current history snapshot, so a successful retry also persists other unsaved failures.

Focus follows the action's recorded intent, not whether `document.activeElement` survived the wait: after acknowledgement, collapse or failure it returns to that row's summary; after a removal it moves to the row that took the removed row's place, or to the new last row, scrolled into view; after removing the last row it goes to the Troubleshooting tab, which then shows its empty state. It never moves when the user moved focus or the window lost focus during the wait, and never enters another row's controls. Result actions bypass the preference save queue and never end shortcut capture.

Restart does not replay notifications. Interrupted pending cleanup becomes unknown. A session that was still recording when an earlier process ended (force-quit, crash, process kill or power loss) is reported once at launch through its interruption sentinel as an unread `app_terminated` entry: "RecordStuff did not exit normally while recording.", timed at the session's start, with guidance that the file may be incomplete and is not repaired. Its temporary path is rechecked like a previously confirmed partial below, so it offers reveal only while a nonempty file exists there and is otherwise unknown with the path as a hint. It raises no notification, and it does not reappear after acknowledgement or another restart because the sentinel is removed once the entry is saved. Until then the sentinel keeps the entry, so it is not counted as unsaved: a quit while the history cannot be saved (an unreadable or newer file included) neither lists it nor warns that it is lost, and the next launch adopts it again (2026-10-05; until then every quit asked to exit without saving it). No recovery, remux or repair is performed. Previously confirmed partial files start unknown and are rechecked sequentially with a two-second bound; a timeout stops further checks to avoid filling the filesystem worker pool; a successful check restores partial status while preserving intervening acknowledgement. Unavailable paths retain their candidate/provenance for another restart. Existing bytes alone never promote interrupted cleanup to confirmed preservation. Removed IDs cannot be resurrected by a delayed check or terminal event.

Only the current `recording-history.json` version 2 is read; old single-result files are ignored and left untouched. When current history is absent, startup writes an empty version-2 history. An older positive integer version at the current path is backed up as `.reset-backup[.N]` and replaced with empty history. No old records are imported and recording/partial files are never modified. Initialization failure is exposed as a load issue and retries on the next launch. Corrupt, oversized or newer history is protected from overwrite; subsequent writes report a persistence warning, and Troubleshooting says "Could not read the failure history, so new failures cannot be saved. Resetting keeps the file as a backup." with Reset failure history… beside it (plan 078). The reset asks first (Cancel, Reset failure history), keeps the unreadable file as `.reset-backup[.N]` (a hard link, so it holds the old content), writes an empty version-2 history and saves the failures of the running session into it without a relaunch; a failed reset leaves everything as it was. Only that action replaces a file the load refused, so a downgraded app still never overwrites a newer one's history by itself; it also covers a history damaged for any other reason, or one holding the removed `mp4_unsupported` code. History validates unique IDs and retains its 32 MiB safety bound without evicting unread records.

History uses a private temporary file, fsync and rename through Node's asynchronous `fs.promises` (the libuv threadpool); main never waits on the disk. Startup reads the file asynchronously, never writes before it has loaded, and merges failures that arrive meanwhile by ID; Settings shows a localized loading line until then. One owner keeps at most one write in flight and one coalesced follow-up; each snapshot is the whole history, so it carries every failure and action outcome of an earlier one, and a completion settles only the revision it contained. An older completion never clears the warning of a newer unsaved change. Unchanged history is not rewritten after startup checks.

Save failure keeps new information in memory and shows a localized warning only for records that differ from the last saved snapshot. Ordinary I/O failures retry automatically on one timer, 2, 5, 15 and then every 30 seconds while unsaved; success resets the backoff, a clean history stops it, and a failure streak logs once plus its recovery. Manual retry starts promptly and joins an active write instead of adding a second writer. Unreadable or newer history is never retried or overwritten and says so instead of suggesting disk space; a history over the 32 MiB bound asks for reviewed rows to be removed. Atomic replacement cannot guarantee recovery from power loss or a full/unwritable disk, and background saving does not add disk throughput. Restored permission errors use historical guidance and offer Relaunch only when current permission state requires it. Failure IDs are UUIDs across processes.

Save serialization stays on main without a worker. Large-file parsing now uses a worker (see Audit hardening below). Whole-snapshot `JSON.stringify` at the 32 MiB bound measured about 40 ms on an M1 Pro, over one 16 ms frame, but handing that snapshot to a worker costs a comparable structured clone on main, so records instead cache their encoded JSON and fingerprints (records are immutable) and history loops yield after about 8 ms of work. Measured longest single main-thread turn: saves at most about 10 ms, including at the bound; before the audit repairs, startup reading took one turn of about 38 ms at the bound (a single `JSON.parse`), about 6 ms at 3.8 MiB and about 2 ms for a typical history. See the [verification record](../verification/history-2026-09.md#plan-036-closure--2026-09-25).

## Deferred quit

Normal quit waits for recording and all pending disk work, even when the tray is idle. Saves in the background (2026-10-09) are named in the tray menu and tooltip in every state (“Saving {file}…”, or “Still saving {file}. The drive may not be responding.” after 30 s, also told once as a notification held until any recording ends) and on Settings' status card while idle, which locks nothing. A save that finishes while the next recording runs holds its saved notification until that recording ends, with the capture notices, so no banner interrupts a recording. While a quit, running or deferred, waits for such saves alone, the tray offers Quit Without Waiting for the Save beside Quit RecordStuff, enabled during the quit too; it exits after flushing settings, window size, the Trash and failure history, each bounded, and the log, leaving the saves' sentinels so the next launch reports each recording as possibly incomplete with its `.recording.mp4` kept. It is a menu item, not a dialog, because a windowless dialog would hold main's I/O (plan 055). After 13 seconds with work pending (the tray says it is quitting meanwhile), an English/Traditional Chinese notification says RecordStuff will remain open and asks the user to retry after saving/cleanup finishes. It is shown even with the notification switch off, because it answers the user's own quit; macOS notification permission and Focus still decide whether a banner appears, and the log names it either way. Because the banner may not be seen, the tray menu and tooltip also carry a short line, “Quit or relaunch postponed: …”, naming recording work or a settings/log write, in every state until the next state change or quit request, or until what held the quit has finished (plan 056). A refused notification reaches the log as Electron's `failed` event, but Focus and a banner muted while the display is shared give no signal, so the line does not depend on delivery. Until plan 055 this was a windowless information dialog, which stopped main's timers and log while it was open: shown exactly while recording work is pending, it held a capture-request deadline 2 min 46 s past due until the user closed it ([record](../verification/history-2026-09.md#plan-055-closure--2026-09-29)). Repeated requests cannot bypass this gate. Starting capture retains stop intent across deferral. Relaunch is registered only after safe admission and is canceled by a deferred quit. Both the notification and tray line ask the user to retry the original action (Quit or Relaunch), rather than directing a deferred relaunch to ordinary Quit. No force-exit control is offered for media work.

Only after media is safe, while new captures stay refused, quit and relaunch attempt the latest failure-history save for up to 5 seconds (a local save measured about 5–10 ms; the 32 MiB bound under 200 ms). Saved history exits normally. If a write is still in flight, a warning offers Keep waiting / Stay in app and never an exit, because a timed-out write is not proof that the OS stopped writing. If the save failed with no write in flight, the warning lists the number of unsaved records with their times and reasons (five, then a count) and offers Retry, Stay in app and a separate Exit without saving. Retry is left out, and Stay in app becomes the default, when the history is unreadable, from a newer version or over its bound: every attempt fails the same way while the prompt holds the app. Exiting without saving is logged, the log is flushed with a bound before the app quits, and the history writer is closed. Staying reopens capture admission and automatic retry and clears relaunch intent. Repeated requests join the running attempt and bring its prompt forward. Nothing is acknowledged or saved as a side effect of exit, and no OS notification is replayed. Force-quit and power loss may lose failure records that were not yet saved.

### Dialogs and main's event loop

A native dialog may stop main entirely (plan 055). An isolated probe on macOS 26.6 with Electron 44.3, with a 1 s interval, a 3 s timeout and a file read due while each dialog was open, found that a windowless `dialog.showMessageBox` and `dialog.showErrorBox` hold main until they are closed: the call returns only then, and no tick, timer or I/O completion runs meanwhile. `showMessageBox` with a parent window, which becomes a sheet (a hidden parent is put on screen to carry it), and a windowless `showOpenDialog` return at once and leave the timers on time ([record](../verification/history-2026-09.md#plan-055-closure--2026-09-29)). A sheet needs a visible window, which a menu-bar app has only while Settings is open, so the deferred-quit notice became a notification rather than a sheet. The quit path therefore shows no dialog while media work is pending. “Pending” is the recorder's `mediaPending`: a session, or the cleanup and saving one left behind, which can outlive the idle state; `whenMediaSettled` resolves when it ends, by the same test quit waits on. Other dialogs still block and are kept away from that work (plan 056):

- The unsaved-history quit prompt: shown only after media has settled, with capture admission closed, so no media deadline can be due; it needs an explicit answer.
- The output-folder warning: answers to a click on Show in Finder or Open folder; a saved notification's click opens Recordings instead (2026-10-04). When the opener finds a problem while media work is pending, it logs it and sends the same text as a notification titled “Could not open the output folder” instead, held like the capture-start notices until the display is no longer shared and shown even with the switch off, since it answers the user's click; the chooser stays with the settled tray and Settings. A new session or a quit before delivery drops the notification, and the log keeps the problem. A settled app keeps the warning and its Change output folder choice.
- The permission-pane fallback: an answer to a click in a settled state (idle or needsPermission), where no capture runs; a failed session's cleanup still pending then waits for the answer and has no deadline of its own. This is accepted.
- `showErrorBox`, which is synchronous. The startup-failure box appears before any media exists. The uncaught-exception box, shown at most once per process, marks a programming fault ([fault-dialog.ts](../../src/main/app/fault-dialog.ts)): the log line comes first, a settled app shows the box at once, and while media work is pending the box waits until it settles, re-checking before it opens. Meanwhile the tray menu and tooltip say “An unexpected error occurred. See the log for details.” A fault that also keeps the work from settling therefore never shows the box; that tray line, the log and the recorder's own deadlines are how it surfaces. A box that waited may open during a quit, after media has settled, like the unsaved-history prompt.

The folder chooser does not block and opens only in a settled state.

### Audit hardening

Preference orchestration lives in preferences.ts: folder dialogs are deduplicated and recheck recording admission when they return. Settings getters return copies and queued updates snapshot caller input. Logging and window geometry use asynchronous serialized writes; logging caps queued text at 1 MiB and keeps stdout when file output fails.

Unreadable history remains preserved and is shown as a load error. Files above 1 MiB are JSON-parsed in a worker, which hands each record back as JSON text: an object graph would cost main a structured clone about as long as the parse (38 of 46 ms at the bound, 2026-10-04), text only a copy (13 ms), and main parses the records one at a time in its sliced loop. Save encoding remains cached and sliced on main. Settings caches immutable row projections and initially renders 50 history rows, with explicit batches of 50. Monotonic view revisions reject stale renderer replies; a retired window cannot update its replacement's delivery cache. Partial-file metadata checks have a two-second UI deadline; the underlying filesystem request may still finish later.

Saved notifications may be delivered in needsPermission because the prior recording already completed. Construction failures are contained, click actions recheck current permission state, and saved-file clicks share the missing-file fallback. Wake polling exists only while notifications await delivery. A retry control reattempts shortcut registration after a conflict is removed.
