# 設計決策與取捨

[English](../../system-design/decisions.md) | [繁體中文](decisions.md)

這是目前採用的決策，不是新的工作計畫。原始計畫中已被實測推翻的假設，以此處及程式為準。

| 決策 | 原因 | 代價／重新評估條件 |
| --- | --- | --- |
| 一段錄影是它的原始檔、它的剪輯（狀態，沒有檔案）與從它存出的副本；離開的是當下做進 App 自己管理的快取的版本（plan 100，2026-10-30 結案；[設計](editing.md#版本與分享)、[紀錄](../verification/history-2026-10.md#plan-100-結案--2026-10-30)） | 以前錄影離開 App 的每一種方式都交出原始檔：移除的片段、靜音的時段與隱藏的相機都一起帶走，而匯出是另一張使用者得知道要挑的卡片。「照片」、Screen Studio 與 Final Cut 都保留原始檔加上配方，離開時才算繪 | 衍生檔案需要快取、上限（10 GB 或可用空間的 10%）與清理；想要自己的檔案就用「另存副本…」 |
| 拖曳給出影片，也就是卡片播放的樣子；⌥ 拖曳給出原始檔；拖曳只拷貝，影片準備中時會等待（plan 100，D1、D2） | 預設離開的是使用者看到的樣子，剪掉的東西除非要求否則不會離開；「照片」、「音樂」與 Lightroom 從資料庫拖出的也是拷貝 | 尚未做好的影片拖曳不會開始（卡片說明原因並提供 ⌥ 拖曳）；原生的 file promise 可以免去等待，但需要原生模組，網頁 App 也不接受 |
| 只標示原始檔：可編輯錄影的原始檔是 `<名稱>.recordstuff.mp4`（D3），會和來源同名的版本是 `<名稱>（剪輯版）.mp4`（D8、D9，暫定），其他一律以成品命名，只有內容不同時才加標記（`（聲音）`、`（僅畫面）`、`（原始檔）`） | 收件人在意檔案裡有什麼，不在意有沒有剪輯；macOS 預設隱藏副檔名，所以由標記說明檔案內容；雙副檔名讓原始檔仍是任何播放器都能開的 MP4 | 沒有標記的舊式可編輯錄影，即使沒剪輯，影片也會加上「（剪輯版）」 |
| 已存副本把來源資訊存在自己的 `moov/udta/rsfm`；錄影分頁依此列出錄影的副本（plan 100，D4） | 檔案以外沒有需要同步的東西：副本或它的錄影在 Finder 中改名後仍對得上 | 移出監看資料夾或被刪除的副本不會列出；`moov` 不在檔尾的檔案不帶來源資訊 |
| 「分享…」是卡片選單的項目，像一個小資料夾，每個版本一頁，提供「拷貝」與「存到…」，素材與無相機影片放在「更多」；沒有分享選單也沒有滑過動作（維護者的設計 D，以及 2026-10-28 與 2026-10-30 的決定） | 拖曳與拷貝能到達的地方和分享選單一樣；卡片畫面保留給影片預覽 | 第一次使用者先把原始檔當成分軌素材，之後才找到「更多 → 素材」（步驟 6）；原始檔的說明改為「全部在一個檔案」，沒有把素材移到第一層 |
| 拷貝把獨立的複本放上剪貼簿，從不放快取裡的檔案（plan 100 步驟 5） | 同一顆磁碟上 Finder 的 ⌘V 會搬走指名的檔案，使用者的檔案會與快取共用資料，未剪輯的錄影甚至可能被搬出資料夾 | 快取的 `.copied` 保留一份複本，直到下次拷貝或「清除」；在 APFS 上，兩邊都沒變動前不佔空間 |
| 與錄影同時準備的版本，在每台 Mac 上都於下一張畫面暫停到錄影結束；依健康數據調節的機制已實作，但沒有對任何機型開啟（plan 100 步驟 4，維護者 2026-10-30 的決定） | 暫停時，版本對錄影沒有可量測的影響；在 M1 Pro 上以 30 fps 調節時沒有遺失畫面，但 App 的 CPU 升到 16–29%，預算為 30%；60 fps 時編碼器平常就有 2–4 張在途，永遠會暫停；沒有 base M1 可量 | 機型要先用 `pnpm matrix -- pace` 量過（有相機與沒有相機），才會加入 `GOVERNED_CLASSES` |
| 分享時不採用（plan 100）：每次拖曳剪輯過的錄影都跳警告；以儲存的連結把副本歸到錄影底下；可編輯原始檔用 `.recordstuff` 套件；檔名加版本號（V1、V2）；每個版本都加「（剪輯版）」；錄影時讓可編輯檔案的啟用畫面就是合成畫面；把剪輯寫進原始檔；每次錄影後跳出快速存取縮圖；拷貝素材時壓縮成 zip；分享選單；「分享…」的滑過動作 | 對話框會被直接點掉；儲存的連結遇到改名就斷；套件失去「任何播放器都能開」；版本號與標記對收件人沒有意義；錄影時合成要多一個編碼器；原始檔從不寫入；準備好才送的存檔通知會帶到卡片；zip 是沒人選的檔案 | 只有使用者確實需要時，才重新考慮滑過動作或分享選單 |
| 「系統聲音」開關放在「麥克風」與「相機」旁邊、排在最前面，出現在選單列的「錄影時包含」、錄影設定與錄影工作室；所有人預設開啟，錄影中鎖定，關閉時完全不擷取系統的聲音（plan 101，D1–D3、D5，2026-10-30 結案；[設計](desktop.md#系統聲音開關)、[紀錄](../verification/history-2026-10.md#plan-101-結案--2026-10-30)） | 想錄沒有通知音的旁白解說時，錄之前沒得選；推桿拉到 0% 是會一直留著的設定，而且仍會擷取聲音。Loom、CleanShot X、Cap 與 Camtasia 都在開始錄影的地方把系統聲音與麥克風做成獨立開關；預設開啟，在有人關掉之前什麼都不變 | 錄影開始後，「不錄製」仍是單次錄影的選擇；Windows 只由 CI 檢查 |
| 系統聲音與麥克風都關閉的錄影可以進行、不跳警告，並保留一條靜音音軌（plan 101，D4） | 只錄畫面是合理的選擇；選單列的勾選已經顯示哪些沒有錄 | 若有人回報不小心錄成無聲，再重新考慮 |
| 選擇輸入時不採用（plan 101，D6）：切換輸入的全域快捷鍵；錄影模式（螢幕與相機、只有螢幕……） | 全域快捷鍵很少、會與其他 App 衝突，而且盲按的切換在錄影前看不到結果；模式會與三個獨立開關重複，兩者不一致時還需要規則 | 只有在使用者要求時，才提供可選、預設不指定的快捷鍵 |
| 不去除麥克風裡的喇叭回音（plan 096，2026-10-29 由維護者在停止點 2 結案；[紀錄](../verification/history-2026-10.md#plan-096-結案--2026-10-29)） | 在維護者自己的喇叭上、以事先凍結的門檻量測，WebRTC AEC3 和我們自己的離線消除器都無法在不削掉人聲的情況下去除回音：最好的方案在 MacBook Pro 喇叭 21 個情境通過 1 個、外接喇叭 21 個通過 0 個，去掉回音的地方最多有 65.5% 的人聲分析框被削掉超過 10 dB，保住人聲的地方則留下回音。檢視過的螢幕錄影工具（Cap、OBS、Camtasia、Loom、Screen Studio）也都沒有去除，而是建議戴耳機、把輸入分開保存，可編輯錄影本來就是這樣。 | 用喇叭的人會在錄影裡聽到聲音重複一次。若有能分辨人聲與殘留回音的第二步（例如開源的 DTLN-aec 或 LocalVQE，16 kHz、模型幾 MB 外加執行環境），或 macOS 的語音處理（只能即時處理，會壓低要錄的聲音），可用新的實機錄音重新評估；測試工具與消除器保留在 Git 的 `d49232f9`。 |
| 錄影工作室採單一版面：選擇放在預覽上方、即時控制放在下方，問題由該輸入自己的 picker 說明（plan 097，D1、D2，2026-10-27；[設計](desktop.md#錄影工作室)） | 原本相機有兩個開關、泡泡有五種外觀、裝置只能在錄影設定選，問題又同時在好幾處出現，畫面不對或沒收到聲音時得離開 Studio；現在「錄什麼」和「錄得如何」分開，正常時保持安靜 | 不用狀態燈，也不用展開條、側邊欄或疊加 HUD；條件未變不重新討論。泡泡形狀改為錄影前決定；移除「只看螢幕」（要看相機遮住什麼，隱藏相機即可） |
| 在 Studio 選擇錄影類型，可編輯錄影一律照原樣錄下每個輸入（plan 097，D6；[設計](editing.md#可剪輯錄影)） | 原本可編輯錄影的靜音、fader 與隱藏相機會永久改掉各自的軌，而「編輯…」本來就能事後設定這三項 | 可編輯錄影的 live row 只有音量表；不支援可編輯錄影的平台（Windows）會列出該類型但標示不可用並說明原因，不會隱藏 |
| 不提醒「麥克風有訊號但太小聲」（維護者決定，2026-10-28，取消 plan 097 的 D3） | 在參考機上實測，正常的 USB 麥克風在安靜房間的峰值約 −78～−84 dBFS，提案的 −60 dBFS 門檻在安靜一段時間後就誤判；在意錄影狀況的使用者會看 Studio 的音量表 | 引擎原有的中斷偵測（數位靜音 2 秒）仍會在錄完後通知；若找到正常麥克風都不會低於的實測門檻再重新評估 |
| 可剪輯錄影是一個 MP4，額外的軌是停用的 alternate，描述放在 `moov/udta/rsed`（plan 087；[設計](editing.md#可剪輯錄影)） | 匯出前任何播放器都顯示畫面與第一條聲音，引擎的單一 fragmented 檔保有原本的復原能力，剪輯讀取的是一個能辨識的檔案 | 每個可剪輯檔約為直接模式的兩倍大；忽略 enabled 旗標的播放器可能顯示相機軌 |
| 兩個輸入都錄時，可剪輯錄影的第一條、啟用的聲音軌是兩個輸入照一般錄影的方式混合，各自的軌接在後面作為停用的 alternate（plan 098；[設計](editing.md#可剪輯錄影)） | 播放器一次只呈現一條聲音軌，QuickTime 與 Chromium 都不會把兩條啟用的軌相加，所以除了剪輯畫面，麥克風在哪裡都聽不到；自成一軌的混音不需要播放器配合 | 多一條 AAC 軌：引擎多 0.84 個核心百分點（門檻 1.0），每分鐘約 1.9 MB；版本 1 的錄影維持原樣（D2），3.0.0 無法剪輯版本 2 的檔案 |
| 剪輯畫面預覽可剪輯錄影時，把複製出的相機與第二聲音放在播放器旁同步播放、以 Web Audio 混音，而不是由引擎算繪（plan 087） | D1 讓整段錄影只有一個位置，所以泡泡只是畫在播放器上的版面；剪輯時不需編碼，同一條 limiter 曲線讓聽到的就是匯出的 | 預覽與匯出是依構造一致，不是以像素比對；分段擺放或畫面樣式需要算繪的預覽 |
| 剪輯錄影時複製 AAC packet，只重新編碼每個接點附近的幾個（plan 085，維護者 2026-10-24 的選擇；[設計](editing.md#剪輯方式)） | 整條音軌重新編碼（plan 的 D2）在單執行緒約為 160 倍即時，對 10 Mbps 的錄影只有磁碟速度的六分之一，而 gate 要求一半；複製 packet 是 LosslessCut、Avidemux 的 copy 模式與 `ffmpeg -c:a copy` 剪聲音的方式，重新編碼約 85 ms 的視窗讓接點精確到 sample 並有淡入淡出。每個片段的起點最多移動半個 packet，讓複製的 packet 保持在格線上；畫面隨之移動，所以每個片段內的同步與來源相同 | 複製的 packet 與重新編碼的 packet 相接處，若兩者的 AAC window 不一致可能出現喀聲：已在 tone fixture 檢查（沒有比 tone 本身更大的跳階）；若在實際素材聽到喀聲就重新檢討，退路是整條音軌重新編碼 |
| 重新編碼畫面的參數集與來源不同時，接點從 key frame 接續（plan 085 D2 的規則，2026-10-24 決定） | 同一軌中第二個 `avc1` description 在 AVFoundation 可以播放，但 app 的播放器 Chromium 解碼失敗；在來源的 level 下，所有量測過的錄影參數集都相同，因此很少需要退回 | Chromium 能跟隨 description 變更，或 encoder 經常無法與來源參數集一致 |
| Electron + TypeScript 負責 App；媒體不經過它們（plan 076） | 桌面生命週期、tray、設定、recorder 狀態機與檔案生命週期，連同測試維持同一種語言；擷取、編碼與寫檔移到下列原生引擎 | 有 Electron 資源成本。整個 App 是否搬家是另一個決策（見下方 Tauri） |
| 以原生擷取引擎取代 Chromium 的 `getDisplayMedia` 與 `MediaRecorder`（plan 076；Chromium 路徑於 2026-10-16 移除；[原因](webrtc.md)） | 本表原先設下的條件「實測到具體限制」已成立：`getDisplayMedia` 只能錄一個螢幕或一個視窗，只能排除本 App 受保護的視窗；無法隱藏選單列或 Dock、無法錄區域或指定 App、也無法只錄單一 App 的聲音，這些在 macOS 都需要 ScreenCaptureKit 的 `SCContentFilter`。成熟的錄影工具（OBS、Cap、Screen Studio、CleanShot X）都原生擷取。在 M1 Pro 上與 Chromium 對照實測（2026-10-15／16）：30／60 fps 錄影 CPU 為單核 10.4%／14.0%，Chromium 為 15.3%／23.3%；閃光到嗶聲 −25 ms，Chromium 為 +68 到 +74 ms；音質檢查結果相同；錄影後不留下 renderer 或音訊服務 | 每段有 0.22–0.44% 的影格間隔達 50 ms，Chromium 為零，原因尚未找到（plan 078）；從開始到 `prepared` 約慢 0.1 秒，仍在倒數之內。兩者皆經維護者接受（2026-10-16）。睡眠、螢幕移除、權限拒絕，以及 D6 下的 Dock 已於 2026-10-22 親手驗收通過（[plan 077](../verification/history-2026-10.md#plan-077-結案--2026-10-22)）。只有在這些量測項目出現引擎無法修正的退步時才重新評估 |
| 擷取在 Electron `utilityProcess` 中執行，每次嘗試一個（076 的 D2） | 原生程式碼當掉只會結束這個子程序，不會結束 App：錄影中殺掉它，留下 8.0 秒可播放的部分檔，main 以暫存檔名保留這個仍是 fragmented 的檔案，並回報失敗。它保留原本的形狀，也就是一個透過 `MessagePort` 交換 `start`／`prepared`／`record`／`stop` 的擷取程序，所以 recorder 的狀態、期限與倒數都沒變。在 main 載入模組會讓原生當機結束整個 App；獨立執行檔則必須先證明 macOS 的螢幕權限適用於它 | 程序隨每次嘗試啟動（457–535 ms 的開始時間中占 74–88 ms），檔案完成後就結束。預先啟動可快約 50 ms，但會多一個約 73 MB 的待機程序，維護者已拒絕（2026-10-15）。開發用 Electron 的 `utilityProcess` 會被拒絕擷取（`-3801`），所以錄影需要簽章的 bundle（`pnpm start:app`） |
| 由引擎寫檔：hybrid MP4，存檔時轉為一般 MP4（076 的 D3） | 多數容器都要回頭寫入才能完成（MP4 的索引、MKV 的 cues），一旦格式可選，傳 chunk 給 main 就無法乾淨地做到；main 的事件迴圈卡住也不再延誤寫入；媒體維持單一語言。main 保留檔案的生命週期：檔名與資料夾、可用空間檢查、session sentinel、發布、歷史、通知、退出與睡眠。引擎回報已寫入的位元組、寫入錯誤（磁碟已滿、寫入失敗），然後是 `stopped` 與獨立的 `finished`，所以慢速磁碟的存檔不算在停止裡 | main 不再看到媒體位元組，只能信任引擎的進度與結果，停止後上限 150 秒。索引寫不進去的檔案會維持 fragmented，部分播放器無法讀取。不採用：把 chunk 傳給 main 原本的 writer，改動最少，但會擋住其他容器 |

## 工具與演進邊界

現有建置採 electron-vite、打包採 electron-builder，原生模組由 Cargo 建置。依賴維持穩定版本路線；升级需重新跑相關檢查及媒體驗證，不能只因套件更新就沿用舊平台結論。

原生擷取引擎是一個 Rust crate（`native/capture/`），隨 App 由 Cargo 建置。沒有為未來先引入 Effect、schema framework、monorepo、React 或完整 PlatformRecorder。當確實需要新視窗，可新增 UI renderer 但媒體仍不經 UI，而媒體現在已完全不進入 Electron 的程序；新的擷取能力放進引擎，維持 Recorder 既有的契約。沒有排程的錄影庫、編輯、快捷鍵、自動更新、Windows 實機驗證，以及 macOS 與 Windows x64 以外的平台支援，不是目前下載版的必要前置。

歷史原生引擎候選與第三方比較未當成現有實作或未來承諾；需要採用時重新調查相應 API 與依賴。

2026-10-06：更新與一般移除繼續保留使用者資料；新增明確確認的「清除本機 App 資料並結束」退場入口，保留錄影與儲存資料夾。舊設定在啟動時遷移，未知較新格式拒絕覆寫；遷移器與移除政策各自管理，清除入口不取代升級支援。見[桌面設計](desktop.md#清除本機-app-資料)。
