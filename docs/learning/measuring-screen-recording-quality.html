錄影到底錄得好不好：螢幕錄影工具的品質量測入門

開發錄影工具，最難的往往不是「讓它能錄」，而是證明它「錄對了」：畫面有沒有少格、聲音有沒有變悶、音畫有沒有對齊，而這些人眼和耳朵幾乎都分辨不出來。本文以一個 macOS 選單列錄影 App 為貫穿範例，從零說明錄影管線、測試素材、量測工具與每一個指標的意義，再用實際量到的數字解釋：為什麼 30 fps 比 60 fps 準、為什麼 60 fps 的位元率會超出目標兩倍、為什麼「有兩個聲道」不代表立體聲。最後說明如何一層一層找出問題所在，以及怎麼用最少的錄影取得足夠的證據。

這篇文章要回答的問題

想像你寫了一個錄影工具，按下按鈕、錄十秒、停止，得到一個能播放的 MP4。畫面在動、聲音有出來。這樣算完成了嗎？

還不算。以下這些問題，播放時幾乎都看不出來：

  • 設定 60 fps，檔案裡其實只有每秒 57.5 格。每秒少 2.5 格，肉眼察覺不到，但長時間下來動作會比原本「稀疏」一點，也代表錄影工具沒有做到它宣稱的事。
  • 檔案標示「兩個聲道」，但左右聲道內容一模一樣。播放時一樣有聲音，立體感卻已經消失。
  • 聲音比畫面晚 90 毫秒。這在可接受範圍內；但如果它每分鐘多晚 10 毫秒，半小時後嘴型就對不上了。
  • 高頻被濾掉，音樂聽起來「悶悶的」。取樣率仍然是 48 kHz，位元率也很高，數字看起來都正常。

所以真正要回答的問題是：怎麼用可重複、可反駁的方式，判斷一條媒體管線的輸出忠於輸入，並且清楚知道每個結論的邊界？

答案的核心是一個受控實驗：

  1. 準備一個性質已知的輸入。例如一個「每秒閃一次白光、同時響一聲」的網頁。
  2. 讓它通過真正的錄影管線：真的 App、真的作業系統、真的編碼器。
  3. 把錄出來的檔案解碼，用程式量出客觀數字。
  4. 和已知性質比較。閃光應該每秒一次，短音應該和閃光同時；量到的差距就是管線造成的。

因為輸入已知，「結果不對」才有辦法被證明。人工播放仍然重要，它能確認實際觀感，但它不是可重複的量測。

本文的貫穿範例是 RecordStuff：一個 macOS 選單列 App，按一下就錄主螢幕和系統聲音，輸出 MP4。使用者可以選 30 或 60 fps、三種畫質（Economy、Standard、High），以及解析度上限（1080p、1440p、4K 或原尺寸）。文中的數字都來自一台 M1 Pro、60 Hz 的 1920×1080 外接螢幕上的實際量測；它們證明的是這台機器上的結果，不是所有 Mac 的保證。

先懂資料怎麼流：錄影管線與基本名詞

要知道問題可能出在哪裡，得先知道畫面和聲音在變成檔案之前，經過了哪些環節。RecordStuff 建立在 Electron 上，Electron 內建 Chromium 瀏覽器引擎，所以錄影用的是瀏覽器的媒體 API，而不是自己寫的擷取程式。

逐層來看：

  • macOS 擷取。ScreenCaptureKit 是 Apple 提供的螢幕擷取框架，負責「在畫面改變時產生一張影格」。系統聲音則由 CoreAudio 的 tap 以 loopback 方式取得，也就是直接拿電腦正在播放的數位聲音，不經過麥克風。
  • Chromium 與 getDisplayMedia。getDisplayMedia 是 W3C 的 Web 標準 API，意思是「給我某個螢幕的畫面與聲音」。呼叫時可以附上 constraints（限制條件），例如 frameRate: { ideal: 30, max: 30 }。Chromium 會把這些條件翻譯成給作業系統的設定。
  • MediaStream 與 track。拿到的結果是一個 stream，裡面有一條影像軌（video track）和一條音訊軌（audio track）。軌道可以回報自己的設定（getSettings()）和統計數字（track.stats），但回報的內容不一定等於實際情況，後面會看到例子。
  • MediaRecorder 編碼。MediaRecorder 是瀏覽器內建的錄製 API，把影像壓縮成 H.264、聲音壓縮成 AAC，再包進 MP4。H.264 在 Mac 上由硬體編碼器（VideoToolbox）處理，所以 CPU 負擔不大。
  • 寫檔。MediaRecorder 每秒交出一段 fragmented MP4（分段 MP4），主程序依序寫進磁碟。分段的好處是即使中途當機，已寫入的段落仍然能播放。
  • 量測。ffprobe 和 ffmpeg 是開發時用的命令列工具，只讀成品、算指標，不隨 App 發佈。

已知的輸入：為什麼需要固定的測試素材

量測要有意義，輸入必須固定。如果每次錄的是不同網頁、不同影片，數字變了也說不出是 App 變了還是內容變了。RecordStuff 的做法是用一個固定的網頁當測試素材，每次量測都錄同一頁，並記下這一頁的 SHA-256，讓結果能對應到素材的版本。

素材元素用來測什麼為什麼這樣設計
持續捲動的小字銳利度縮放或壓縮過度時，細小文字會先變糊，人眼一看就知道。
紅藍細線與彩色文字色彩邊緣H.264 常用 4:2:0 色度取樣，顏色的解析度只有亮度的一半，細的彩色線條最先出問題。
每格都移動的方塊影格時序畫面每一格都不同，擷取端就必須一直產生新影格。
右上角方框：平常全黑，每秒閃白 100 ms畫面側的同步標記黑白對比最容易被程式偵測，而且只看一小塊區域，不受畫面其他部分影響。
660 Hz 短音：120 ms、約 −10 dBFS、左右交替，與閃光同一個時鐘聲音側的同步標記和閃光同時發生，所以錄進檔案後兩者的時間差就是音畫偏移。左右交替則讓兩個聲道都有能量。
其他時間完全無聲避免誤判偵測器靠「安靜之後出現聲音」找短音，任何背景聲都會干擾，所以量測時電腦不能播放其他聲音。

一個容易誤會的地方：畫面不動，就不會有新影格。螢幕擷取只在畫面改變時產生影格。錄一個靜止的桌面，fps 本來就會很低、位元率也很低，這不是故障。所以跟「影格時序」有關的指標（平均 fps、掉格、同步），只有在錄持續移動的素材時才判定；錄一般畫面時，工具會照樣顯示數值，但標為 n/a（不適用），不判定通過或失敗。

自動化測試會用 Chrome 的 app 模式、以全新的設定檔在主螢幕全螢幕開啟這一頁，並允許自動播放聲音，所以不需要人去點按鈕。

量測工具：ffprobe 與 ffmpeg 在看什麼

FFmpeg 是開源的影音處理工具組。ffprobe 負責「讀」：列出檔案裡有哪些串流、各自的格式與時間。ffmpeg 負責「處理」：它內建上百個濾鏡（filter），可以對解碼後的畫面或聲音做分析。錄影工具本身不呼叫它們；它們只在開發時用來檢查成品。

下面是量測時實際使用的指令（檔名以 rec.mp4 代表）：

Shell# 1. 串流資訊，並完整解碼一次來數影格、抓解碼錯誤
ffprobe -v error -show_format -show_streams -count_frames -of json rec.mp4

# 2. 每一格的時間戳（pts），用來算間隔、掉格與 median
ffprobe -v error -select_streams v:0 -show_entries frame=pts_time -of csv=p=0 rec.mp4

# 3. 每個聲道的平均能量（RMS）
ffmpeg -hide_banner -nostats -vn -i rec.mp4 \
  -af astats=measure_perchannel=RMS_level:measure_overall=none -f null -

# 4. 同步標記：只看右上角方框找閃光，並在聲音裡找短音
ffmpeg -hide_banner -nostats -an -i rec.mp4 \
  -vf "crop=ih*0.08:ih*0.08:iw-ih*0.115:ih*0.035,blackdetect=d=0.4:pix_th=0.10:pic_th=0.90" -f null -
ffmpeg -hide_banner -nostats -vn -i rec.mp4 -af silencedetect=n=-35dB:d=0.4 -f null -

每一行在做什麼：

  • 第 1 行取得寬高、編碼、時長、起始時間，-count_frames 會把整個檔案解碼一遍，同時得到影格總數；解碼中出現的錯誤會印在 stderr，那就是「解碼錯誤」指標。
  • 第 2 行列出每一格的 pts。相鄰兩格相減就是間隔：正常 30 fps 大約每格 0.033 秒，如果突然出現 0.100 秒，代表中間少了兩格。
  • 第 3 行的 astats 濾鏡計算每個聲道的 RMS 能量，用來發現「有音軌但完全無聲」或「某一邊聲道壞掉」。
  • 第 4 行先用 crop 裁出右上角那個方框，再用 blackdetect 找出「持續至少 0.4 秒的黑色」區間；每個黑色區間結束的時刻，就是閃光開始的時刻。聲音這邊用 silencedetect 找「低於 −35 dB 且持續至少 0.4 秒」的安靜區間，安靜結束的時刻就是短音開始。裁切尺寸用畫面高度的比例表示，所以任何橫向解析度都裁得到方框。

另一個好用的濾鏡是 mpdecimate：它會找出「和上一格幾乎一模一樣」的影格。擷取端如果送出重複的畫面，這個濾鏡就數得出來。用它之前要先確認它真的能抓到：拿一段正常影片硬把幀率升到兩倍（等於每格重複一次），它應該標出大約一半的影格。確認偵測器真的會失敗，是量測工作的基本功，第 9 節會再談。

只有正常結束的工具輸出才算量測。ffmpeg 如果中途失敗，可能已經印出一部分結果。把「量到一半」當成結果，會得到看似合理、實際錯誤的數字。所以工具只要不是 exit 0，這一項就判定為失敗，印出的部分內容一律丟棄。

每一個指標在問什麼

指標分成兩層。完整性（integrity）指標對任何內容都成立，它問的是：「這個檔案是不是這次錄影完整產生的？」發布前的驗收只需要這一層。效能（performance）指標只有在錄持續移動的測試素材時才有意義，它問的是：「影格時序和音畫同步好不好？」

完整性指標

指標怎麼算門檻為什麼是這個門檻、失敗代表什麼
輸出尺寸檔案的寬高，對照 App 自己回報的尺寸與解析度上限相符；符合上限並維持來源長寬比抓出「App 以為錄的尺寸」和「實際檔案」不一致的情況。
錄影長度檔案時長，對照要求的秒數或 log 裡的錄影期間±2 秒按下開始與真正開始錄之間本來就有一點時間差；差太多代表開頭或結尾遺失。
音訊與影像長度差兩條串流各自的時長相減小於 100 ms兩條串流應該一起開始、一起結束，差很多代表其中一條中途斷掉。

音訊位元率音訊串流的位元率，對照 256 kbps 目標至少 50%；錄測試素材時只回報AAC 依內容分配位元，測試素材大多是靜音，位元率自然很低，這不代表音質差。

效能指標

指標怎麼算門檻為什麼是這個門檻、失敗代表什麼
平均 fps影格總數 ÷ 影像時長；旁邊另外列出影格間隔的 median 與標稱週期（只回報，不判定）要求值 ±2 fps平均 fps 看總數，median 間隔看「每一格」的節奏。兩者一起看，才能分辨「每格都慢一點」和「偶爾掉格」。
掉格率相鄰 pts 的間隔大於 1.5 個週期就算有掉格，遺失格數 = 四捨五入（間隔 ÷ 週期）− 1小於 2%例：30 fps 出現一個 100 ms 的間隔，100 ÷ 33.3 = 3，所以遺失 2 格。超過 120 秒的長檔只取頭尾各 60 秒計算，中間跳過的部分不能算成掉格。
閃光／短音偏移每個閃光開始時間，找 400 ms 內最近的短音開始時間，相減（聲音減畫面）後取 median介於 −45 與 +125 ms 之間，且至少 3 組配對正值表示聲音晚到。少於 3 組配對時數字不可靠，所以判定為「不完整」而不是通過。
端到端漂移開頭 60 秒的偏移 median 與結尾 60 秒的偏移 median 相減小於 100 ms；頭尾各至少 3 組配對；只判定 120 秒以上的錄影固定的偏移可以接受，會越拉越大的偏移不行。只算整段的 median 會把漂移平均掉，所以要分頭尾比較。
CPU每秒加總所有 Electron 程序的 ps %cpu，略過開頭 3 秒啟動期，取平均平均不超過 40%（僅自動化 matrix）100% 代表用滿一顆核心。門檻依第一次量測的數字加上寬裕空間訂出（1080p30 約 15%、1080p60 約 23%），讓較慢的機器也有餘裕。

數字的解讀要小心一件事：偵測器本身也有誤差。閃光從「黑色結束」判斷、短音從「安靜結束」判斷，兩者的偵測方式不同，大約會帶進 10 ms 的系統性偏差。所以 80 ms 的偏移不代表剛好 80 ms，而是「落在可接受範圍、且每次量測都差不多」。

判定：通過與失敗之外的三種狀態

只有「通過／失敗」兩種結果的量測，會在最危險的地方出錯：量不到的時候，程式很容易默默當作通過。例如電腦沒有安裝 ffmpeg，同步標記根本量不出來；如果這時報告顯示「全部通過」，就是一份假的證據。所以每一項檢查都有五種結果：

結果意思例子
pass量到了，且符合門檻平均 29.9 fps，要求 30 ± 2
fail量到了，不符合門檻；或量測工具本身執行失敗60 fps 只量到 57.0
blocked必要的證據因為缺少工具而量不到沒有安裝 ffmpeg
incomplete有量，但證據太少，不足以判斷只找到 2 組閃光／短音配對；長檔缺少頭或尾的配對
n/a這次不需要，或不適用於這個檔案錄一般畫面時的 fps；短檔的漂移

整份報告的結論依「最嚴重者優先」的順序決定：只要有一項 fail 就是 fail；沒有 fail 但有 blocked 就是 blocked；再來是 incomplete；都沒有才看是否至少有一項 pass。程序的 exit code 也跟著這個順序：fail 或 incomplete 為 1，blocked 為 2，其餘為 0。自動化腳本因此能分辨「測了但失敗」和「沒辦法測」。

「哪些證據是必要的」由呼叫的一方宣告。例如自動化的 matrix 一定要求聲道能量與同步標記，所以缺 ffmpeg 就是 blocked；單獨檢查一個檔案時，如果沒有要求同步，同步那一項就是 n/a，並附上原因。無論哪一種，缺少證據都不會被當成通過。

聲音要另一套量測：「有聲音」不等於「聲音對」

前面的聲道能量只能證明「不是靜音」。使用者抱怨「錄出來的聲音很悶」時，它回答不了。聲音的品質要回答的是：頻率分布有沒有被改變？左右聲道是不是真的獨立？音量是否被自動調整？有沒有斷斷續續？

看得到的數字它證明了什麼它證明不了什麼

先解釋一個常見的誤會。48 kHz 取樣率理論上最高可以表示 24 kHz 的聲音，這叫 Nyquist 頻率（取樣率的一半）。但這只是「能表示的上限」，不是「保證保留」。如果管線前段有一個濾波器把 10 kHz 以上都去掉了，檔案仍然是 48 kHz，位元率再高也救不回已經消失的高頻。同樣的道理，把單聲道複製成兩份，檔案標示是兩聲道，卻沒有任何立體聲資訊。

用已知的測試音來量

RecordStuff 的音質診斷產生一段 12.1 秒、48 kHz 雙聲道的 WAV 測試音，由系統播放，App 同時錄下來，再把錄到的檔案和原始測試音比較。測試音的內容：

  • 開頭與結尾的標記音：1 kHz 與 2 kHz，兩個聲道同時播放，用來在錄音裡找到測試音的起點與終點，並估計時間比例。
  • 六個探測頻率：250 Hz、1、4、8、12、16 kHz，涵蓋低音、中音到高音。先在左聲道依序播一遍，再在右聲道播一遍。
  • 同時播放的 1 kHz 引導音（pilot）：每個探測音都和一個 1 kHz 的引導音一起播放。如果系統在兩段探測音之間自動把音量調小，拿「12 kHz 和同時的 1 kHz 相比」，音量變化會互相抵消，才不會把「音量被調小」誤判成「高頻流失」。

比較時用的方法叫最小平方正弦擬合：用數學找出「最像錄到的波形」的正弦波組合，量出每個頻率的強度，擬合不了的剩餘部分稱為 residual，代表雜訊、失真或斷續。錄音和原始檔的時脈也可能有極小差異（以 ppm，百萬分之一為單位）；例如 10 ppm 會讓 16 kHz 變成 16000.16 Hz。第一版分析器沒有考慮時脈差，結果把乾淨的測試音誤判成失真，所以第二版會先估計時脈，把「時脈誤差」和「波形被改變」分開判定。

分貝的換算在這裡很關鍵：功率比用 10 × log₁₀，振幅比用 20 × log₁₀。功率 −3 dB 約等於剩一半，−20 dB 是剩百分之一。混用兩個公式會得到錯誤的 dB 值。

一個真實案例：為語音通話設計的處理，會傷害錄音

使用者回報錄音很悶。量測結果是 16 kHz 的響應約 −44 到 −47 dB（幾乎完全消失），左右聲道分離度約 0 dB（兩邊一樣）。原因在瀏覽器擷取系統聲音時，預設會套用三種為語音通話設計的處理：

  • 回音消除（echo cancellation）：去掉喇叭播出、又被麥克風收回去的聲音，避免對方聽到自己的回音。
  • 降噪（noise suppression）：去掉背景雜音，讓人聲更清楚。
  • 自動增益（automatic gain control）：自動調整音量，讓忽大忽小的講話聲維持一致。

這些功能讓視訊會議好用，但錄音工具要的是忠實保留電腦播放的數位混音，包括音樂的高頻細節、立體聲和原本的強弱變化。在擷取 constraints 裡把三項同時關閉（echoCancellation: false、noiseSuppression: false、autoGainControl: false）之後，兩次有效的量測中 16 kHz 與引導音的差距在 0.004 dB 以內，分離度也超過 30 dB。同一批三次量測裡有一次因為間隔被污染而判定 invalid，所以這批結果整體仍然是 invalid，沒有被說成通過。實驗證明的是「三項一起關閉」的效果，不能拆出是哪一項造成的。

要求、回報與成品是三種不同強度的證據。程式送出 echoCancellation: false 只證明「我們要求了」；軌道的 getSettings() 回報關閉，只證明「執行環境這樣說」；只有解碼後的成品量測，才證明聲音真的沒被處理。單元測試能確認第一種，不能取代第三種。

為什麼有些範圍表現好、有些差

有了指標，就能回答開頭的問題：同一個 App、同一台機器，為什麼某些設定的數字漂亮、某些不理想？下面每一個案例都有一個共同點：問題出在「某一層的設計和我們的期待不同」，而不是隨機的故障。

30 fps 與 60 fps：最小影格間隔是下限，不是節拍器

很長一段時間裡，RecordStuff 每支錄影的影格都比設定少一點：30 fps 實際約 29.4，60 fps 約 57.5，而且完全沒有掉格。30 fps 用掉 ±2 容許範圍的 0.6，60 fps 則每次判定幀率都失敗。

原因在 Chromium 把 frameRate 交給 ScreenCaptureKit 的方式：它把要求的幀率換成 ScreenCaptureKit 的「最小影格間隔」。要求 30 fps，就設定「兩格之間至少隔 33.33 ms」。這是一個下限：ScreenCaptureKit 保證不會比 33.33 ms 更快送出下一格，但真正送出還要再加上系統排程的延遲，實測約 0.6 ms。所以每一格的平均間隔是 33.33 + 0.6 ≈ 33.9 ms。

0.6 ms 看起來很小，但每一格都會累積。30 fps 一秒 30 格，每格晚 0.57 ms，一秒累積約 17 ms，大約是半格，所以每秒只剩 29.5 格左右。60 fps 一秒 60 格，累積約 33 ms，將近兩格，所以只剩 58 格左右。實測分別是 29.4 與 57.5，吻合。

修正方式是把下限往前挪：要求比設定值略高的幀率，讓「下限 + 延遲」剛好約等於一個週期。RecordStuff 最後選擇 30.3 與 62.5，也就是 33 ms 與 16 ms 的下限（週期無條件捨去到整數毫秒）。改完之後：

為什麼不乾脆要求 35 或 70？因為要求值同時也是「這條軌道允許的最高幀率」，要得太多可能超過設定值。60 fps 還有另一層保護：60 Hz 螢幕每秒只產生 60 張新畫面，下限再低也不會多出影格。用 mpdecimate 檢查，60 fps 錄影裡沒有任何重複影格。但在 120 Hz 的螢幕上，16 ms 的下限可能讓 60 fps 錄影略高於 60，這件事還沒有量測。

60 fps 還有一個 30 fps 沒有的現象：偶爾會出現一個約 33 ms 的間隔，也就是錯過一次螢幕更新。改動前後都有，掉格率在 0.1% 到 1.1% 之間，低於 2% 的門檻。60 fps 本來就比 30 fps 更貼近螢幕刷新的極限，偶發的錯過自然比較多。

位元率：30 fps 很準，60 fps 超出目標兩倍

RecordStuff 的影像位元率目標由公式決定：寬 × 高 × fps × 每像素位元數。三種畫質的每像素位元數是 0.07、0.13、0.24。1080p、30 fps、Standard 是 1920 × 1080 × 30 × 0.13 ≈ 8.1 Mbps。

30 fps 時，編碼器幾乎完全照目標輸出：Economy、Standard、High 分別約 4.4、8.1、14.9 Mbps，和目標相差約 2% 以內。60 fps 時，Standard 的目標是 16.2 Mbps，實際卻是 31 到 33 Mbps，約兩倍。這是 Chromium 編碼器在 60 fps 時的行為，不是錄影壞掉；畫質沒有變差，只是檔案變大。

這也是為什麼位元率只設下限（至少 70%）而不設上限：位元率高只代表檔案大，位元率過低才可能代表畫面被過度壓縮。反過來，錄一個靜止的畫面，位元率會遠低於目標，這也是正常的，因為沒有變化的畫面幾乎不需要空間。

聲音位元率：稀疏的短音只有 26 kbps

音訊的目標是 256 kbps，但錄測試素材時實際只有 20 多 kbps。測試素材每秒只響 120 ms，其他時間都是靜音，AAC 編碼器對靜音幾乎不花位元。這說明位元率是「編碼器依內容分配的結果」，不是音質指標。錄測試素材時，音訊位元率只回報、不判定；真正的音質要用上一節的音質診斷量。

解析度：平台回報的尺寸會說謊

在多螢幕的環境裡，Chromium 的 getSettings() 曾經把 1920×1080 的螢幕回報成 1920×1920，高度用的是另一台直立螢幕。如果照這個數字套 1080p 上限，畫面會被錯誤地縮成 1080×606。所以 App 改成實際量測影格尺寸：把軌道接到一個隱藏的 <video> 元素，讀它的實際寬高，只有讀不到時才退回使用 getSettings()，並在 log 裡留下警告。

解析度上限有三條規則：維持來源的長寬比、永遠不放大、縮小時取偶數尺寸，因為 H.264 的 4:2:0 色度取樣以 2×2 像素為單位。在 1080p 的螢幕上選 1440p、4K 上限或原尺寸，畫面都不會被縮放，錄出來一樣是 1920×1080；在這種螢幕上比較這幾種設定時，差別只剩畫質等級造成的位元率。

音畫同步：固定延遲可以接受，漂移不行

實測的閃光／短音偏移大約在 56 到 97 ms，而且都是聲音比畫面晚。這是固定的處理延遲，落在 −45 到 +125 ms 的可接受範圍內，觀眾不容易察覺。真正危險的是漂移：3 分鐘的錄影頭尾偏移只差 1 到 3 ms，之前量過一次 10 分鐘的基準也只有約 3 ms。漂移接近零，代表聲音與畫面用的是一致的時鐘，錄再久也不會越差越多。

負載與長時間：硬體編碼讓 CPU 維持低檔

錄 30 fps 時，所有 Electron 程序合計的 CPU 約 13 到 14%，60 fps 約 21 到 22%，1080p30 的 10 分鐘基準約 17%。負擔低的原因是 H.264 由 macOS 的硬體編碼服務處理。另外做過一個對照實驗：同時跑 8 個佔滿 CPU 的程序，影格節奏並沒有變差，所以前面的 0.6 ms 延遲是固定的下限延遲，不是負載造成的。

找出問題在哪一層：分層觀察與對照實驗

知道「60 fps 只有 57.5」還不夠，修正之前得先知道是哪一層造成的。上一節的解釋（最小影格間隔是下限）一開始只是閱讀 Chromium 原始碼得出的假設。同樣的症狀，至少有三種可能的來源，修法完全不同：

  • (A) 來源下限：ScreenCaptureKit 本來就送得慢，影格到達軌道時已經晚了。修法是調整送給它的要求。
  • (B) 軌道限速器：來源送得夠快，但 Chromium 的軌道為了遵守 max 而丟掉一部分影格。修法是放寬限速。
  • (C) 錄影時間戳：影格準時到達，但 MediaRecorder 寫進檔案的時間戳被拉長了。修法在編碼端，或者根本不在我們能控制的範圍。

要分辨這三種，就要在管線的不同位置同時觀察同一批影格。RecordStuff 為此做了一個不隨 App 發佈的診斷工具：它用正式的錄影程式碼錄測試素材，但在三個位置各放一個觀察點。

分類觀察點 1：送達時間戳觀察點 2：丟棄計數觀察點 3：檔案 pts
(A) 來源下限已經變慢幾乎沒有丟棄和送達時間戳一樣慢
(B) 軌道限速器夠快或剛好丟棄超過 1%變慢或變少
(C) 錄影時間戳準時幾乎沒有丟棄變慢

實際結果：四次錄影的送達時間戳 median 已經是 33.9 到 34.0 ms（30 fps）與 17.2 到 17.3 ms（60 fps）；每次只丟棄 1 到 4 格，最多 0.45%；檔案 pts 和送達時間戳的 median 相差不到 0.05 ms。三個觀察點一致指向 (A)。

分類之後還要做對照實驗，一次只改一個變因：

  • 加負載：同時跑 8 個佔滿 CPU 的程序。偏差沒有變大，排除「CPU 太忙」這個解釋。
  • 只給 ideal、不給 max：結果和原本完全一樣（29.29 與 57.01 fps）。原因是 Chromium 的裝置幀率與軌道限速器都由 ideal 決定，拿掉 max 不會改變任何東西。這個結果和讀原始碼的推論一致。
  • 候選 30.6／62.4：平均幀率達標，但 30 fps 的間隔 median 剛好卡在標稱週期的 1% 邊界上。
  • 候選 30.3／62.5：平均與 median 都達標，30 fps 的間隔分布也最集中，最後採用這組。

採用之前，還要對照一份事先寫好的標準（go criteria），而不是看到數字變好就接受：平均在 30 的 0.5 fps、60 的 1 fps 以內；間隔 median 在週期的 1% 以內；掉格低於 2% 且不比改動前多；CPU 差距在 3 個百分點以內；偏移、漂移、聲道能量與位元率都在門檻內。這些條件全部成立，改動才算成功；有任何一條做不到，就要記錄成平台限制，而不是放寬門檻。

測試量測工具本身

觀察點本身也可能出錯，所以診斷工具也要被檢查：

  • 觀察端可能漏看：renderer 用來讀影格的 buffer 有上限，讀取端如果卡住，會漏掉一些影格，讓「觀察到的節奏」看起來比實際慢，像是來源變慢。所以工具會比對觀察到的影格數和檔案裡的影格數，少於 99% 時結果標為「無法判定」，不指派任何一層。
  • 計數窗口要選對：軌道的丟棄計數每秒取樣一次。如果把錄影開始前的啟動瞬間也算進去，一段 10 秒的短錄影會因為啟動時丟掉的 4 格（1.3%）被誤判成限速器問題。改成從錄影開始後的第一個取樣起算，結果就變成 0 次丟棄。
  • 中斷時要收乾淨：工具會啟動測試瀏覽器、隔離的 App 程序，以及製造負載的程序。被中斷時如果留下一個佔滿 CPU 的程序，下一次量測就會被污染。所以任何中斷都要停掉自己啟動的程序，並確認它們真的結束了。

音質診斷用的是同一個原則：乾淨的樣本必須通過，刻意破壞過的樣本（濾掉高頻、改成單聲道、刪掉一段、加入削波）必須因為正確的原因失敗。只測壞樣本，會做出一個什麼都判失敗的偵測器；只測好樣本，則會做出一個什麼都判通過的偵測器。

證據的層級：每一種測試能證明什麼

錄影工具的測試不是只有一種。越接近真實使用情境的測試，證明力越強，但也越慢、越需要一台不被打擾的電腦。了解每一層能證明什麼、不能證明什麼，才能決定一次修改需要跑哪些測試。

層級做什麼能證明不能證明大約成本
單元測試用假的 MessagePort、假的 getDisplayMedia 驗證純邏輯送出的 constraints、判定規則、錯誤處理正確作業系統與瀏覽器實際怎麼錄全部約 800 多個測試，幾秒鐘
隔離的 Electron fixture在真正的 Electron 裡跑某一段正式程式碼，但輸入是受控的跨程序、真實視窗下的行為完整 App 的所有互動每個數十秒

一次修改不需要跑完所有層級。選擇時可以參考幾個原則，它們也是讓一輪驗收不要拖太久的關鍵：

  1. 依「行為」選測試，而不是依檔名。只改設定頁面的間距，不需要錄影；改了送給擷取端的幀率要求，就一定要錄影量測，但不需要重測權限流程。
  2. 只量受影響的維度。改幀率要量 fps 和同步，不需要把每一種畫質等級都重錄一遍；位元率公式沒變，畫質矩陣就可以不跑。
  3. 能重用的證據就重用。同一台機器、同樣的擷取程式碼、同樣的素材，前一輪量到的「改動前」數字可以直接當基準，不必重錄。只有程式碼、環境或素材改變時，舊證據才失效。
  4. 一段錄影可以同時提供多項證據。同一個檔案能同時量尺寸、長度、幀率、同步與聲道能量；同一個檔案也可以拿去做播放驗收，不需要每一項各錄一次。
  5. 接近門檻時才增加重複次數。結果遠在門檻內時，一次就足以下結論；結果卡在邊界時，才需要多錄幾次確認是不是偶然。
  6. 確認工具會失敗，再相信它通過。每一個新的偵測器都要先用刻意做壞的樣本確認它能抓到問題。

可以帶走的判斷清單

這些問題不只適用於螢幕錄影，也適用於任何「輸入經過一條你無法完全控制的管線、變成輸出」的系統，例如音訊處理、影像轉檔、串流服務：

  • 輸入已知嗎？如果輸入的性質不確定，輸出不對時就無法證明是管線的錯。
  • 這個指標在問什麼問題？它證明不了什麼？每一個指標旁邊都應該寫得出這兩句話。取樣率不是頻寬，聲道數不是立體聲，位元率不是畫質。
  • 回報的數字是要求、回報，還是成品量測？三者的證據強度不同，只有成品量測能證明最後的結果。
  • 平均值會不會藏住問題？平均幀率要搭配間隔 median，整段同步要搭配頭尾比較，三次量測的 median 不能蓋掉其中一次失敗。
  • 量不到的時候，報告說什麼？缺少工具、證據太少、素材不對，都必須有明確的狀態，而且都不能算通過。
  • 問題出在哪一層？在多個位置同時觀察，第一個出現異常的位置，就是問題的歸屬；再用一次只改一個變因的對照實驗確認。
  • 成功的標準是事先定好的嗎？先寫下 go criteria，再看數字；做不到時記錄限制，而不是事後放寬門檻。
  • 這些數字能推廣到哪裡？一台機器、一種螢幕、一個版本的量測，只證明那個環境。其他更新率的螢幕、其他電腦，都要另外量過才能下結論。
