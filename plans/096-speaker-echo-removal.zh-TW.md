# 096 — 從麥克風移除喇叭回音（選用、非破壞性）

[English](096-speaker-echo-removal.md) | [繁體中文](096-speaker-echo-removal.zh-TW.md)

狀態：進行中；步驟 0、1 與 2 已於 2026-10-29 完成（G0 通過；步驟 2 的資料確定了 D2）（先做測試工具，尚未做回音消除器）；D3 已於 2026-10-29 回答（維持 AAC）；D1 已回答（門檻凍結）；步驟 3 已執行：C1、C2、C3 在階段 B 都不通過，停止點 2 等待維護者確認。建立：2026-10-26，依維護者要求。硬性相依：無未完成的項目。本計畫建立在已結案的 087（可編輯錄影、分開的聲音軌、場景與算繪匯出）與已結案的 085（剪輯畫面、匯出 worker 與發布）之上。依[計畫索引](README.zh-TW.md)的順序執行。目前只有步驟 1 的測試工具（[回音移除測試工具](../docs/zh-TW/system-design/tooling.md#回音移除測試工具)）；回音消除器尚未實作、量測或驗證。

維護者的條件（2026-10-26）：只有量測證明確實有幫助才做；沒有明顯幫助就不做。因此本計畫把量測放在最前面，並設有明確的停止點。測試全部自動化，素材由工具自己產生；只有最後一個階段交給維護者試聽與判斷（2026-10-26）。停止也是有效的結果：計畫帶著證據結案，不算交付失敗。

## 目標與現況

Mac 的喇叭在播放聲音、同時麥克風在錄音時，麥克風也會收到那些聲音。錄影裡於是有兩份系統聲音：一份是數位擷取的乾淨訊號，另一份是房間傳回麥克風的版本，晚了幾十毫秒，還帶著房間的殘響。兩者疊在一起，聽起來像回音，或空洞、有梳狀濾波的金屬感。戴耳機就沒有這個問題。

現況：

- **兩個輸入分開擷取。** 系統聲音來自 ScreenCaptureKit（48 kHz 立體聲浮點數，`excludesCurrentProcessAudio`），麥克風來自 CoreAudio 的 HAL，單聲道，照原樣讀取，從不經過語音處理（[microphone.rs](../native/capture/src/mac/microphone.rs)、[錄影](../docs/zh-TW/system-design/recording.md)）。
- **一般錄影把它們混成一條音軌。** [混音器](../native/capture/src/core/mixer.rs)以原始音量相加成單一 AAC 音軌（256 kbps）。之後兩者無法分開，回音也無法移除。
- **可編輯錄影把它們分開保存**（087，macOS，預設關閉）：一個 MP4 裡系統聲音和麥克風各有自己的音軌，場景有逐輸入的音量與音量區段，算繪匯出經引擎的 limiter 混音（[剪輯](../docs/zh-TW/system-design/editing.md)）。錄影時設定的音量已經在各音軌裡。
- RecordStuff 目前沒有任何回音消除，這是刻意的：已停用的 Chromium 路徑曾讓系統聲音經過語音處理，16 kHz 測試音因此掉了 44–47 dB（[學習文章](../docs/learning/audio-clocks-mixing-and-av-sync.html)、[音質](../docs/zh-TW/system-design/audio-quality.md)）。

目標：讓用喇叭錄影的使用者，**可以選擇**把喇叭的聲音從麥克風裡移除，同時保留錄到的人聲原貌；效果要經自動化量測與維護者試聽證明，系統聲音則完全不動。

## 產品定位與設計原則

RecordStuff 是「螢幕、聲音和攝影機，其他都沒有」，錄成一般的 MP4，忠實保留錄到的內容：原始音量、不做處理、經過測試的音訊路徑。回音移除必須符合這個定位：

- **P1 — 預設關閉，由使用者選擇。** 永遠不自動開啟。
- **P2 — 非破壞性。** 錄影本身永遠不改。回音移除是剪輯的一項屬性，在預覽與匯出時套用，可以再關掉，就像 Cap 的 Studio Sound 和 087 的音量一樣。
- **P3 — 只處理麥克風。** 系統聲音永遠不處理，只當參考訊號。
- **P4 — 只處理回音。** 不做降噪、不做自動增益，不做任何其他會改變人聲的處理。那些是另外的問題，不在本計畫範圍。
- **P5 — 人聲優先。** 多消一點回音如果會聽得出人聲被改變，就以人聲為準。殘留一點回音可以接受，人聲受損不行。
- **P6 — 證明了才上線。** 每個結論都是在本機量到的數字，比較的門檻在試任何候選方案之前就固定，最後再由維護者親自試聽確認。

## 需求（維護者，2026-10-26）

- **R1 — 可選的開關。** 預設不開，使用者需要時再開啟。
- **R2 — 盡可能好的音質。** 盡量移除喇叭的聲音，同時讓錄到的人聲盡量接近原樣。
- **R3 — 證明它有效**；沒效就放棄這個功能。
- **R4 — 直到最後都自動化。** 測試不需要維護者參與：工具自己產生素材（人聲、音樂，以及回音本身）並量測結果。只有最後一個階段交給維護者，聽有標示的片段（不需要盲聽），判斷這個功能是否真的有效。

## 設計（提案，待量測確認）

### 在哪裡執行：可編輯錄影的剪輯與匯出

回音移除需要麥克風和系統聲音分開。只有可編輯錄影把兩者分開保存，所以這是可編輯錄影（macOS）的剪輯功能：

- 可編輯錄影同時有麥克風軌和系統軌時，剪輯畫面為麥克風提供**移除喇叭回音**。否則這個控制項不出現，或顯示為無法使用並說明原因（沒有麥克風、沒有系統聲音、不是可編輯錄影、Windows）。
- 開啟後存進剪輯的場景（例如 `echoRemoval: { enabled }`，確切格式在步驟 4 決定），在 [shared/editing.ts](../src/shared/editing.ts) 逐欄驗證，並可和其他剪輯一起還原。
- **預覽。** 匯出 worker 把麥克風軌處理後寫入剪輯畫面已在播放的預覽檔（`userData/edits/preview`），有進度與取消，讓使用者匯出前先聽到結果。處理過的預覽只在畫面開著時保留，和現在複製出來的音軌一樣。
- **匯出。** [render.rs](../native/capture/src/edit/render.rs) 在混音前，把解碼後的麥克風送進回音消除器，以解碼後的系統軌為參考。系統的樣本原封不動進入混音。
- **一般錄影不在範圍內。** 它們只有一條混好的音軌，無法分開。錄影當下即時、破壞性的回音移除違反 P2，不在範圍內；之後可以根據本計畫的量測結果再考慮。

為什麼離線而不是即時：離線處理可以把音軌跑兩次（先讓濾波器收斂，再用收斂好的濾波器處理整條音軌，開頭幾秒就不會殘留回音），可以從整段錄音估計延遲與喇叭到麥克風的路徑，也沒有即時運算的時間限制。代價是要等處理，以 G5 量測。是否採用兩次處理，視步驟 3 的結果而定。

### 參考訊號

參考訊號就是喇叭播出的聲音。可編輯錄影的系統軌就是這份聲音，但有兩個前提，在步驟 2 量測：

- **錄影時的音量。** 系統軌包含錄影時設定的音量。不是 0% 的音量只是等比例縮放，回音消除器可以跟上。系統被靜音或設為 0% 的區段沒有參考訊號，那段時間麥克風裡的喇叭聲無法移除，剪輯畫面會說明。
- **系統的輸出音量。** 如果 ScreenCaptureKit 擷取的是系統輸出音量調整之前的訊號，錄影中調整 Mac 的音量會改變喇叭的大小聲，參考訊號卻不變，回音消除器必須重新適應。步驟 2 量測實際是哪一種，步驟 3 量測各候選方案多快恢復。

RecordStuff 自己的聲音不會被擷取。它只在錄影開始前播放倒數音效，所以不影響錄影內容。

### 回音消除器：候選方案，由便宜到昂貴

- **C1 — WebRTC AEC3，只開回音消除。** 透過 `webrtc-audio-processing`，關閉降噪、增益控制和其他所有階段，以 48 kHz 處理麥克風的單一聲道，系統軌（混成單聲道）作為 reverse stream。
- **C2 — 抑制器較溫和的 AEC3。** 同上，但透過 `experimental-aec3-config` 調整抑制器，偏向在雙方同時說話時保住人聲（P5）。
- **C3 — 自己寫的離線回音消除器，只在 C1 和 C2 都失敗時才做。** 兩次處理、全頻段的線性自適應濾波器（頻域區塊濾波器）、從整段錄音估計延遲與時鐘飄移，殘餘抑制只用在遠端有聲音、近端沒有聲音的地方。AEC3 的線性濾波器可能只涵蓋低頻段（約 0–8 kHz），高頻只靠抑制增益處理。這點尚未查證，在步驟 3 按頻段量測。如果屬實，8 kHz 以上的回音只能壓低、不能扣除，那正是 C3 可能做得更好的地方。

採用能通過門檻的最小方案（共通要求：歸屬範圍要小）。只有 C1 和 C2 失敗的原因是 C3 能解決的，才寫 C3。

### 不採用的做法

- **macOS 語音處理（VoiceProcessingIO、`setVoiceProcessingEnabled`）。** 它屬於即時 I/O，無法處理錄好的音軌；會壓低其他 App 的音量（ducking），還附帶自己的降噪和增益控制。違反 P2 和 P4。
- **Windows 通訊串流或 voice capture DMO。** 同樣的問題，而且可編輯錄影只支援 macOS。
- **機器學習回音移除。** 對音樂的行為難以預測、體積較大、授權較不明確、資源也較難設上限。只有 C1–C3 全部失敗且維護者要求時才考慮。
- **用降噪來處理回音。** 它消除不了喇叭回音（OBS 論壇的共識），而且違反 P4。

## 衡量機制：先自動化，最後由維護者試聽

分三個階段。前兩個階段不需要有人在 Mac 前面；第三個階段由維護者檢查。

| 階段 | 在哪裡 | 回音怎麼產生 | 誰 |
| --- | --- | --- | --- |
| **A. 模擬** | 任何機器，包括 CI | 模擬的房間：遠端訊號與房間脈衝響應做卷積，再加一點削波模擬小喇叭的失真 | 自動 |
| **B. 實際喇叭** | 這台 Mac，桌面測試 | Mac 自己的喇叭和麥克風 | 自動（需要桌面只是因為要用到喇叭和麥克風） |
| **C. 試聽檢查** | 這台 Mac | 階段 B 的錄音 | 維護者 |

### 素材由工具自己產生

不需要下載，也不需要人來錄。每次執行都依隨機種子，以可重現的方式產生素材：

- **人聲**用 macOS 的語音合成（`say`，輸出成檔案）：中文（台灣）和英文語音、多個說話者、短的稿子。用來代表使用者的聲音，以及影片或通話裡的人聲。
- **音樂**由工具合成：泛音到 16 kHz 的和弦、打擊樂的瞬態和低音旋律，讓低頻、高頻和突然的聲音都有。
- **測試音**沿用現有的 fixture v2，用於分頻段的數據。
- **腳本**定義邊界已知的區段：靜音、只有遠端（有聲音在播、沒人說話）、只有近端（有人說話、沒聲音在播），以及雙方同時說話。

### 事先知道正確答案

判斷回音移除的好壞，要拿它的輸出和「應該得到的結果」比較。為了知道正確答案，回音和人聲分開產生，再相加：

- **階段 A。** 人聲就是產生的語音；回音是遠端訊號經過模擬房間；麥克風訊號是兩者相加。理想輸出就是那段人聲。
- **階段 B。** 用 RecordStuff 的引擎自動錄兩次，都是開麥克風的可編輯錄影：
  1. **回音錄音：** 遠端素材從 Mac 的喇叭播放。麥克風只錄到回音，系統軌錄到參考訊號。
  2. **人聲錄音：** 不播放任何聲音，維護者用平常的音量和距離，朗讀引導網頁上的句子（2026-10-29 維護者的決定，取代由喇叭播放人聲素材：若由喇叭播放，人聲大小就是素材的大小，G0 只是比較兩個由測試工具設定的音量）。它的麥克風軌當作「這支麥克風在這個房間聽到的人聲」；裡面沒有遠端聲音，所以不會把人聲消掉。一次朗讀供同一回合的所有回音錄音使用。

  雙方同時說話 = 兩次錄音的麥克風軌相加，在 session 時鐘上對齊，以回音錄音的系統軌當參考訊號。人聲錄音的麥克風軌就是理想輸出。

這樣不需要第二台裝置，只需要有人依網頁引導說話一次，約 20 秒，其餘全部自動。回音與人聲分開錄再相加，不是真正的對話，但要量的問題一樣：回音消除器有沒有把遠端聲音消掉、其他聲音都保留下來。

### 指標

按區段、按頻段（125 Hz–1 kHz、1–4 kHz、4–8 kHz、8–12 kHz、12–16 kHz）計算，並以 20 ms 為一幀，取中位數與第 95 百分位：

- **回音消除量**（ERLE）：在只有遠端的區段，處理前麥克風能量除以處理後能量，單位 dB。另外量多快生效：從第一個遠端聲音、或音量改變開始，到 ERLE 穩定高於 15 dB 為止。
- **沒有回音時不改變任何東西：** 在只有近端的區段，（輸出 − 輸入）相對於輸入的能量。
- **雙方同時說話時保住人聲：** 和理想輸出比較，人聲有聲音的每一幀的音量損失，以及斷音（被壓低超過 10 dB 的幀）。
- **成本：** 參考機 M1 Pro 單執行緒的即時倍率、增加的記憶體、App 增加的體積，以及匯出與取消的時間。

### 先測試測試工具

量測任何回音消除器之前，分析工具必須能找回已知的答案，以單元測試在 CI 上執行：移除已知比例的模擬回音，讀數要在已知 ERLE 的 0.5 dB 以內；原封不動輸出的「回音消除器」，要讀到 0 dB ERLE 且人聲沒有改變；輸出全靜音的，每項人聲指標都要失敗；刻意損壞的人聲（某些幀壓低 12 dB、4 kHz 低通）必須被抓出來。

### 測試情境

| 情境 | 階段 | 用途 |
| --- | --- | --- |
| 模擬房間：小、中、殘響多；喇叭乾淨與輕微失真 | A | 門檻 G1–G3 |
| **主要情境：** 內建喇叭與麥克風，輸出音量 50% 與 100% | B | 門檻 G0–G4 |
| 錄音中改變輸出音量；系統靜音一段時間 | B | 重新收斂（G1c）；靜音區段只回報 |
| 耳機，或關掉喇叭（沒有回音） | B | G4，不造成傷害 |
| 有接 USB 麥克風或外接喇叭的話 | B | 只回報 |

輸出音量由測試工具自己設定（結束後還原）。階段 B 的每個情境跑三次，回報中位數那次，以及最差的那次。

### 門檻（2026-10-29 於 D1 凍結）

| 門檻 | 標準（提案） |
| --- | --- |
| **G0** 問題存在 | 階段 B 的主要情境中，麥克風裡的原始回音比人聲低不到 30 dB。否則問題太小：停止。 |
| **G1a** 消除回音 | 收斂後，只有遠端的區段 ERLE 中位數 ≥ 25 dB，語音與音樂都要達到，階段 A 與階段 B 的主要情境都要 |
| **G1b** 各頻段 | 125 Hz 到 12 kHz 的每個頻段 ERLE ≥ 15 dB |
| **G1c** 夠快 | 第一個遠端聲音後 2 秒內、以及音量改變後 2 秒內，ERLE 高於 15 dB |
| **G2** 沒有回音時不改變 | 沒有聲音在播時，（輸出 − 輸入）比輸入低至少 40 dB，音量差在 ±0.5 dB 以內 |
| **G3** 保住人聲 | 雙方同時說話時，人聲音量損失中位數 ≤ 1 dB、第 95 百分位 ≤ 3 dB，全頻段與每個至少有 20 個人聲分析框的頻段都要符合（D1：人聲在 4 kHz 以上被切掉時，全頻段的數字幾乎不變）；人聲有聲音的幀中，被壓低超過 10 dB 的不超過 1% |
| **G4** 不造成傷害 | 沒有回音的錄音符合 G2。匯出時，進入混音的系統樣本在功能開與關時完全相同（引擎測試中的 null test）。 |
| **G5** 成本 | 單執行緒至少即時 20 倍（一小時的麥克風最多 3 分鐘），峰值記憶體最多增加 64 MB，打包後的 App 最多增加 5 MB，匯出取消在 p95 仍於 2 秒內，macOS 與 Windows 的 CI 編譯都通過 |
| **G6** 維護者檢查 | 在階段 C，維護者判斷回音明顯減少，而且人聲沒有變差 |

停止規則：

- **停止點 1，步驟 2 之後：** G0 不通過。問題太小，記錄證據後結案。
- **停止點 2，步驟 3 之後：** 沒有任何候選方案通過 G1–G3 和 G5。帶著證據結案。
- **停止點 3，步驟 6 之後：** 維護者在階段 C 判斷它沒有真的幫助。移除開關，帶著證據結案。

### 階段 C：試聽檢查

只在階段 A 和 B 都通過後才進行。工具用階段 B 的錄音，為每個情境和素材產生一組試聽片段：

| 片段 | 內容 |
| --- | --- |
| 1. 只有人聲 | 理想狀態：沒有回音的人聲 |
| 2. 原始麥克風 | 帶著喇叭回音的人聲，也就是現在錄到的樣子 |
| 3. 移除回音後 | 同一段麥克風經過回音移除 |
| 4. 沒有移除的混音 | 現在匯出的效果：系統聲音加原始麥克風 |
| 5. 有移除的混音 | 開啟開關後匯出的效果 |
| 6. 只有回音，處理前與處理後 | 只有遠端聲音，可以單獨聽出回音還剩多少 |

片段都有標示，不是盲聽。附一份簡短的指南（試聽組裡的一個頁面、README 或清單），說明每個片段是什麼、要注意聽什麼（停頓時的回音、雙方同時說話時人聲的清晰度和音量、像水聲般的顫動或字被切掉之類的瑕疵），以及每個片段量到的數字，讓聽到的和數字可以互相對照。維護者也可以自己錄一段可編輯錄影，在剪輯畫面切換開關比較。維護者的判斷就是 G6。

## 決定點

- **D1 — 凍結門檻。2026-10-29 已回答：照提議凍結，G3 也逐頻段判定。** 步驟 3 之前，維護者接受或調整上面的門檻，之後本計畫不再更改。維護者維持回音的門檻（整體 25 dB、到 12 kHz 的每個頻段 15 dB），沒有放寬到 20 dB 與 8 kHz，並決定人聲除了整體，也在每個有人聲的頻段判定。
- **D2 — 系統被靜音時的參考訊號。** 提案：用錄下來的系統軌；錄影時被靜音或設為 0% 的區段不做移除，剪輯畫面會說明。另一個選擇是額外錄一條原始音量的參考軌，這會改變可編輯格式（`rsed`）與磁碟用量。依步驟 2 的資料決定。
- **D3 — AAC 或無損。2026-10-29 已回答：維持 AAC。** 音軌是 256 kbps 的 AAC，編碼噪音可能限制能扣除的回音量。維護者決定維持現狀：不論步驟 3 的結果如何，可編輯格式都不加入無損的麥克風或參考訊號。步驟 3 只用 AAC 版本的錄音（也就是 App 檔案實際存的內容）測試候選方案，不再做無損對照。如果是 AAC 讓某個候選方案過不了門檻，就記錄為原因，不再另提選項。

- [ ] **7. 文件與結案。** [剪輯](../docs/zh-TW/system-design/editing.md)、[音質](../docs/zh-TW/system-design/audio-quality.md)新增一節（方法、結果與限制）、[設計決策](../docs/zh-TW/system-design/decisions.md)（採用的相依套件、不採用的做法與原因）、[第三方授權聲明](../website/THIRD_PARTY.md)、開關有上線的話更新說明與 README、翻譯、驗證紀錄與計畫索引。如果是停止規則結束了計畫，就改為記錄證據與原因，避免在條件沒變的情況下重開這個問題。

## 門檻與完成

本計畫以下列兩種方式之一完成：

- **上線：** 採用的方案經由 App、在全新的已簽署 bundle 上通過 G1–G5，並經維護者檢查（G6）確認。開關預設關閉，只套用在可編輯錄影的麥克風，從不改動錄影本身或系統聲音。限制寫入文件：靜音區段、一般錄影與 Windows。
- **不上線：** 觸發停止規則。證據、門檻與原因記錄在驗證紀錄與設計決策。App 裡不留下做到一半的功能。

## 驗證

- 步驟 1：測試工具的單元測試（新 scope 的 `pnpm test:scope`，如果放在 `scripts/` 就用它的 Node 測試）。
- 步驟 3–4：`native/capture` 的 `cargo test`（包裝層測試、null test，以及作為 ignored test 的 bench）、`pnpm test:scope -- editing`；因為引擎、匯出與剪輯契約都有改動，需要 `pnpm check`；以 macOS 與 Windows CI 確認編譯。
- 步驟 2、5 與 6：「好了」交接後的桌面測試，App 操作使用[原生驗收 skill](../.agents/skills/native-acceptance/SKILL.md)。使用 `out/` 與 `dist/` 的工作依序執行；桌面與音訊只由一個執行者使用。每輪結束都要還原輸出音量與設定並清理。
- 分開回報：自動化結果（階段 A 與 B）、維護者的判斷（階段 C），以及仍未驗證的部分（Windows 不在此功能範圍；USB 麥克風與外接喇叭只在有接上時才測）。

## 執行與結案約定

依[計畫索引](README.zh-TW.md)處理順序、決定點、桌面交接與結案。步驟 3 之前必須先回答 D1。觸發停止規則時暫停，等維護者確認後，計畫帶著證據結案。除非另外要求，本計畫不包含 commit、push、PR 或發布。
