# 076 — Native capture engine for macOS and Windows

[English](076-native-capture.md) | [繁體中文](076-native-capture.zh-TW.md)

Status: in progress; step 1 decided on 2026-10-14, steps 2 and 3 done on 2026-10-14, step 4 done on 2026-10-15 (PR #6), step 5 done on 2026-10-15 except removing the display-media handler, which waits for D7's flag to go after step 7, step 6 done on 2026-10-15. Created: 2026-10-14. Priority: next, before 074 and 075, because its result decides where 074 mixes the microphone and how 075 keeps RecordStuff's windows out of the recording. Hard dependencies: none. Execute the steps in order under [the plan index](README.md).

## Goal and boundaries

Replace the part of recording that Chromium and the file writer do today, capturing the screen and system audio, encoding, muxing and writing the file, with a native Rust module that runs in an Electron `utilityProcess`, on macOS and Windows in the same plan. Electron, TypeScript, the Settings window, the tray, the Recorder's state machine, the file's lifecycle (name, sentinel, history, notifications) and the library stay. Success is: on both platforms a recording made through the native engine matches today's recordings or is better on the measured quality, frame timing, audio fidelity and CPU; the engine exposes the capabilities listed below; the old Chromium capture path is removed at closure; macOS is verified on hardware and Windows by CI, as step 1 records.

Capabilities the engine provides in this plan, with the user-facing settings that use them now:

| Capability | macOS | Windows | User-facing in this plan |
| --- | --- | --- | --- |
| Whole display with system audio (today's behavior) | ScreenCaptureKit | Windows.Graphics.Capture, WASAPI loopback | yes, unchanged |
| RecordStuff's own windows left out | `SCContentFilter` excluding the app's windows | `WDA_EXCLUDEFROMCAPTURE` on its windows | yes, always on (075's D14) |
| Hide system UI: menu bar, Dock, desktop icons and widgets | `SCContentFilter` excluding those windows | not possible with Windows.Graphics.Capture (taskbar); step 1 decides | yes, a switch in Settings → Recording |
| Microphone input mixed into the audio track | AVFoundation or Core Audio input | WASAPI capture | used by 074 |
| One window, an area, chosen apps; one app's audio | `SCContentFilter`, `sourceRect`; app-filtered audio | Windows.Graphics.Capture window item, crop; process loopback (Windows 10 2004+) | engine and tests only; the pickers are a later plan |

Out of scope: a browser tab (only a browser or its extension can capture a tab, so it is a separate product), moving to Tauri, an editor or separate tracks, and the pickers for window, area and app.

## Why native capture, why Rust, why not Tauri (assessment)

- **A concrete limitation has been measured.** [Design decisions](../docs/system-design/decisions.md) say to consider native capture "only after measuring a concrete limitation". Chromium's `getDisplayMedia` captures one display or one window and can exclude only this app's own protected windows (Electron patches Chromium for that); it cannot hide the menu bar, Dock or desktop, capture an area or chosen apps, or capture one app's audio. Each item the maintainer asked for on 2026-10-14 needs `SCContentFilter` on macOS, which no Electron or Chromium API exposes.
- **What others do.** Mature desktop recorders capture natively: OBS (per-platform capture plugins), Cap (Rust, ScreenCaptureKit on macOS, Windows.Graphics.Capture on Windows), Screen Studio and CleanShot X (native macOS). Browser-based recorders (Loom's extension, Screenity) are limited to browser APIs.
- **Rust, one language for both platforms.** The operating systems expose their APIs through binary calling conventions (the Objective-C runtime and C on macOS; C, COM and WinRT on Windows), so any compiled language can call them. Swift is Apple's first language and the most direct on macOS, but does not help on Windows. Rust reaches ScreenCaptureKit through binding crates (Cap uses `cidre` in production), and `windows-rs` is Microsoft's own binding. One language keeps one capture pipeline, one muxer and one set of tests. The cost is a Rust toolchain in the two CI jobs that already exist (`check.yml` and `release.yml` already build on `macos-15` and `windows-2025`), build caching, and bindings that may lag a new Apple API. Combining TypeScript with Rust is common: Cap (TypeScript UI, Rust backend), Signal Desktop (Electron with Rust libsignal), 1Password 8 (Electron with a Rust core), and JavaScript tools built with napi-rs.
- **Why `utilityProcess`.** A crash in native code then ends that child process, not the app: what was already written stays on disk in its recoverable form, and main finishes the file and reports the failure. It also keeps today's shape, a separate capture process that talks to main over a `MessagePort` (`prepared`, `record`, `stop`, progress), so the Recorder's state machine changes little.
- **Why not Tauri.** Tauri is also TypeScript plus Rust (its UI is HTML in WKWebView or WebView2). Moving would rewrite about 14,600 lines of main, shared and preload code and about 32,000 lines of tests and acceptance tools that rely on Electron, and change the Mac web engine, for gains in app size and memory that [the plan index](README.md) already declined to rewrite for. The Rust capture module carries over unchanged if a move is ever chosen, so this plan is not a dead end.

## Current state

- `src/renderer/capture/capture-host.ts`, a hidden renderer, calls `getDisplayMedia` (main's handler in `src/main/index.ts` answers with the screen and `audio: "loopback"`) and encodes with `MediaRecorder` to fragmented MP4 (H.264 + AAC 256 kbps), sending one chunk per second over the protocol in `src/shared/protocol.ts`.
- `src/main/recording/recorder.ts` runs the session; `file-writer.ts` writes chunks, syncs every 5 s and keeps the session sentinel; `mp4-finalize.ts` follows fragments and makes the file plain MP4 at save ([recording](../docs/system-design/recording.md)).
- Quality settings, the frame-rate request and the audio constraints are in `src/shared/quality.ts` and `src/renderer/capture/apply-quality.ts`; their reasons are in [recording](../docs/system-design/recording.md#quality-and-encoding) and [audio quality](../docs/system-design/audio-quality.md).
- Verification tools that record through the app: `pnpm acceptance`, `pnpm matrix`, `pnpm audio:quality`, `pnpm measure:cpu`, `pnpm acceptance:lifecycle` ([tooling](../docs/system-design/tooling.md)).
- Cap's license (revision `3d19c5cfa5e636107e78adde6d55be78404d4f23`): the `scap-*` and `camera*` crates, including `scap-screencapturekit`, `scap-direct3d`, `scap-targets` and `scap-ffmpeg`, are MIT; everything else, including its recording pipeline, encoders and muxer, is AGPLv3 and must not be copied into this MIT project.

## Steps

### 1. Decide (decision point)

- [x] **D1 Language (decided 2026-10-14: Rust for both platforms).** Recommended: Rust for both platforms (napi-rs). Alternative: Swift on macOS and Rust or C++ on Windows, which is the most direct on macOS and gets new Apple APIs first, at the cost of two native languages.
- [x] **D2 Process (decided 2026-10-14: `utilityProcess`).** Recommended: the module loaded in an Electron `utilityProcess`, talking to main over a `MessagePort` with the existing message shapes. Alternatives: loaded in main (simplest, but a native crash ends the app), or a separate executable (isolated, but macOS's screen permission must then be proven to apply to it).
- [x] **D3 Who writes the file (decided 2026-10-14: the engine).** The engine captures, encodes, muxes and writes the file, syncing periodically and writing a crash-recoverable fragmented form that becomes plain MP4 at save, as OBS's hybrid MP4 and today's `mp4-finalize.ts` do. Main keeps the file's lifecycle: the name and folder, the free-space check before start, the session sentinel, the history entry, notifications, and the state machine with quit and sleep; the engine reports bytes written and write errors (disk full, write failed) as events. Reasons: most containers need to seek back to finish (MP4's index, MKV's sizes and cues), which a chunk stream to main cannot do cleanly once output formats are selectable; a stalled main event loop no longer delays writing; and media stays in one language. `file-writer.ts` and `mp4-finalize.ts` are rewritten in Rust, carrying over their design and test cases. Rejected: chunks to main's existing writer, which changes least today but blocks other containers.
- [x] **D4 Encoding and muxing (decided 2026-10-14).** Two replaceable layers. Encoders: the platform's hardware encoders, VideoToolbox and AudioToolbox on macOS, Media Foundation on Windows (hardware when the GPU offers it, Microsoft's software encoder otherwise; Windows N editions without the Media Feature Pack get a clear error). Muxer: an ISO BMFF muxer written for this project in Rust, covering MP4 and MOV, writing OBS-style hybrid MP4 (fragmented while recording, plain at save). This plan ships H.264 + AAC in MP4, today's format; HEVC and MOV are later settings on the same layers. Other formats (GIF, WebM, MKV) belong to a later export feature, which may bring FFmpeg in for conversion only. Basis: recorders capture with system encoders and a lean muxer (Chromium, Cap, Kap, QuickTime, OBS's hybrid MP4) and use FFmpeg for export or broad format support; no FFmpeg in the recording path keeps the app small and free of LGPL linking.
- [x] **D5 Reuse from Cap (decided 2026-10-14).** Depend on or adapt Cap's MIT `scap-*` crates where they fit, keeping their license notices, and record each crate, license and revision. Cap's AGPL code is a design reference only: it may be read to understand an approach, but nothing is copied or translated line by line, and the implementation follows Apple's and Microsoft's documentation and the ISO BMFF specification.
- [x] **D6 Hide system UI (decided 2026-10-14).** A "Hide menu bar and Dock" switch in Settings → Recording, off by default, macOS only: the recording leaves out the menu bar, the Dock, desktop icons and widgets while the user still sees them; the ⓘ says that an app's open menu is still recorded, because it is that app's window. On Windows the switch is shown unavailable with the reason (Windows.Graphics.Capture cannot leave out the taskbar), and nothing is cropped. Off by default because existing recordings must not change after an update and what is on screen is what users expect to be recorded; Loom and CleanShot X also offer this as an option.
- [x] **D7 Transition (decided 2026-10-14).** Keep the Chromium path behind a development flag for side-by-side comparison until the native engine passes step 7 on macOS, then remove it in this plan; Windows switches with it and is checked by CI (D8).
- [x] **D8 Windows verification (decided by the maintainer on 2026-10-14).** Windows is verified by CI only, as every Windows change is today: the `windows-2025` jobs build the module, run its tests and load it, and record through it as far as the runner's desktop allows. What CI cannot exercise is listed as untested in the plan's closure and in the release record, and is left to users' reports; there is no Windows hardware or virtual-machine round.

All of step 1 was decided by the maintainer on 2026-10-14.

### 2. macOS prototype and measurement gate (decision point)

- [x] A minimal Rust module records the chosen display with system audio through ScreenCaptureKit, excludes RecordStuff's windows, optionally hides the menu bar and Dock, encodes with VideoToolbox and AudioToolbox and writes a hybrid MP4 file through the D4 muxer (commit `c4f9a2dd`; optimised in `9df50a25`). It is chosen with `RECORDSTUFF_CAPTURE_ENGINE=native`.
- [x] Permissions: on a signed `pnpm start:app` bundle the screen and system-audio grants apply to the module in the `utilityProcess`. The development Electron's `utilityProcess` is refused (`-3801`), so native measurements use the signed bundle. The first-time prompt was not seen, since the grant already existed.
- [x] Crash safety: killing the `utilityProcess` mid-recording left an 8.0 s playable partial file. Its tracks differed by 147 ms in length, because each track's fragments are flushed about once a second.
- [x] Measured against today's engine on the same machine, 2026-10-14, after the optimisation round (Chromium in brackets):
  - Start, shortcut to `prepared`: 457–535 ms (347–369 ms). `record` to `started`: 2 ms (1–2 ms).
  - Audio and picture length difference: -0 ms in every file, including 10 minutes (+13 to +15 ms).
  - Dropped frames: 0.00% at 30 fps, 0.06–0.22% at 60 fps (0.00%; 0.14–0.22%).
  - Recording CPU at 30/60 fps: 10.0–10.5% / 15.0% (15.6% / 23.0%).
  - 10-minute drift: 0 ms, 600 of 600 flash–beep pairs.
  - Flash-to-beep offset: -22 to +9 ms, fixed within a recording (+6 to +8 ms).
  - `pnpm matrix` and `pnpm audio:quality record` cannot drive the native engine, because the development Electron is refused capture. Their place was taken by `pnpm acceptance` with `pnpm verify --sync`, by `audio:quality verify` on a recording that played the fixture, and by `pnpm measure:cpu` on the signed bundle.
  - `pnpm measure:cpu` fails `IDLE_ROLES` natively on Electron's early renderer, which step 4 handles.
- [x] Reported to the maintainer, who decided on 2026-10-14 to continue after the optimisation round. Accepted: the start is about 0.1 s slower than Chromium's, inside the countdown. The follow-ups are in step 4 (frame timing, start latency, the idle renderer) and in its writing item (separating stop from file completion).

### 3. Windows prototype

- [x] The same module on Windows: Windows.Graphics.Capture for the display, WASAPI loopback for system audio, Media Foundation H.264/AAC, the shared muxer; `WDA_EXCLUDEFROMCAPTURE` on RecordStuff's windows (PR #5).
- [x] In CI on `windows-2025`: build, `cargo test`, load the module, and try a short display recording with system audio. Whether the runner's session can capture at all is itself a finding; when it cannot, the recording is listed as untested rather than failed. The runner can capture: the `native-windows` job passes on commit `886a7f55`.
- What was done (2026-10-14, PR #5):
  - The session state machine moved out of `mac/session.rs` into `native/capture/src/core/`, generic over the platform's frames, encoders and clock, so both platforms share one set of rules for pacing, the stop and the sound up to it. It has tests with fake encoders that run on both platforms. macOS was re-verified on the signed bundle (`pnpm acceptance`, `pnpm verify --sync`, `pnpm measure:cpu`).
  - `native/capture/src/win/` implements the module:
    - Windows.Graphics.Capture, converted to NV12 by the Direct3D 11 video processor. A device without one (WARP on a machine without a GPU, as on the runner) copies each frame to a staging texture, and the frames that are encoded are converted on the CPU (`nv12.rs`).
    - WASAPI process loopback without RecordStuff's process tree.
    - Media Foundation's software H.264 encoder, with a key frame every second of presentation time.
    - Its AAC encoder, which takes at most 192 kbps, with its priming measured when it is made.
    - `avc.rs` turns its Annex B output into the muxer's form.
  - Main passes a physical point on the display (Electron's display ids name no monitor there) and marks its own windows `setContentProtection(true)` while an attempt runs (`capture-exclusion.ts`). The Windows build is opt-in (`RECORDSTUFF_BUILD_NATIVE=1`), so the check and release builds are unchanged until step 6.
  - The `native-windows` job in `check.yml` runs `cargo test`, decodes the synthetic file with `ffprobe`/`ffmpeg`, runs system audio alone, the display alone and a whole three-second session as live tests in separate processes (rerun under `cdb` with full page heap when one fails), and loads the module in Node. Its first runs found two defects, both fixed: the runner's device had no video processor, and the loopback activation's `PROPVARIANT` freed its stack-held parameters when dropped.
  - Results on the runner (run 38569135126): the 1024×768 display through the CPU conversion; `prepare` in 92 ms; three seconds gave 6 video samples (3 key frames, a still desktop) and 141 AAC packets, both tracks lasting 3000 ms; a 2 ms drain with no silence filled in; the measured AAC priming was 0 frames; `probe` from Node returned 1024×768. The synthetic file decoded without errors.
  - Untested on Windows (D8): the video processor and hardware paths, picture content and quality, audio content and A/V sync, the own-window exclusion, DPI with several displays, CPU, and long recordings.
- Carried to step 4 from this prototype: the hardware H.264 encoder (an asynchronous transform), sound while nothing plays (process loopback may deliver no packets, so audio fragments wait for the next sound), and confirming on real Windows hardware the measured AAC priming (0 on the runner; if the encoder's output is in fact delayed, audio is late by that much) and the own-window exclusion, which D8 leaves to users' reports.

### 4. The engine

- [x] Add the Rust crate (proposed `native/capture/`) with napi-rs bindings, `cargo test` for the muxer, timestamps and source filters, and platform modules behind one Rust interface. The crate exists since step 2; step 4 adds the sources and the mixer behind the same `Core` (2026-10-15).
- [x] Writing (D3): the Rust writer and muxer take over `file-writer.ts` and `mp4-finalize.ts` (periodic sync, write-error classification, fragment index, plain MP4 at save), with their test cases ported; main keeps the sentinel, the free-space check, publication and history, and drops the two TypeScript modules at closure. The step 2 prototype finishes the file before it reports `stopped`, so a slow volume's save falls under the recorder's 10 s stop deadline and is killed as `stop_timeout` (review of step 2): separate capture stop from file completion, as today's renderer stop and main's finalize are.
  - Done 2026-10-15: the engine's `stop` answers once capture and the encoders have stopped, and a separate `finish` once the file is plain or why it is not is known. The host sends `stopped`, then a new `finished` (or `writeError`). `NativeCaptureHost` keeps a process that is finishing alive after the recorder goes idle, hands its outcome to `EngineFileWriter`, ends it afterwards, and bounds it at 150 s. On the desktop the recorder was idle 0–1 ms after `stopped` and the file finished 19–22 ms later.
  - The muxer's tests already covered the TypeScript cases that apply to it (64-bit `mdat`, fragment index, a failed index write left fragmented); the rest of `file-writer.test.ts` is chunk appending and publication, which stays in main. A volume slow enough to outlast the old deadline was not available: the separation is shown by the order of events and unit tests.
- [x] Clock and sync: one monotonic clock per session (mach absolute time; QueryPerformanceCounter); audio timestamps from cumulative sample counts and gaps filled with silence, as Cap does, so audio never drifts against video over long recordings. In place since step 2 (`timing.rs`); step 4's mixer keeps it per input.
- [x] Frame timing, from step 2's optimisation round (commit `9df50a25`, maintainer's request of 2026-10-14), measured 2026-10-15 on the signed bundle:
  - One stop rule: a frame is kept only when its time is before the stop. Done; a test feeds a frame stamped at the stop. The muxer's drop stays as a guard.
  - Capture interval: asking for every refresh dropped 0.17% at 30 and at 60 fps, against 0.06% and 0.11% with a quarter of the frame interval, for about the same CPU (10.8% against 10.4% at 30 fps, 14.4% against 15.0% at 60). The quarter stays.
  - Frame times: display time gave flash-to-beep offsets of -7 and -15 ms with 0.22–0.27% dropped; arrival time gave +5 and +3 ms but dropped 1.4% and 16%, because arrival jitters with the callback and the pacer's grid keeps the wrong frames. Display time stays. Both findings are in `pacing.rs`, and the two switches used to measure them are gone.
- [x] Start latency: after step 2's optimisation round, pressing the shortcut to `prepared` took 457–535 ms natively, against 347–369 ms through Chromium. The native time is the `utilityProcess` start (74–88 ms), the shareable-content query (59–83 ms) and ScreenCaptureKit's `startCapture` (206–227 ms).
  - [x] Time the Chromium path's start by phase the same way. Done (`CaptureHost.phase`): its hidden window is ready after 83–84 ms, the display is answered by 98–101 ms, and Chromium's own capture start and `MediaRecorder` take the remaining 180–215 ms, `prepared` at 282–313 ms from `start`.
  - [x] Measure starting the capture `utilityProcess` ahead of time. Measured behind a development switch, since removed: shortcut to `prepared` 437–439 ms against 484–497 ms without it and 369–395 ms through Chromium, at the cost of one more idle process of about 73 MB.
  - [x] Report the latency and memory to the maintainer, who decides; that process would change the idle list in [Waiting in the menu bar](../docs/system-design/design-overview.md#waiting-in-the-menu-bar). Decided by the maintainer on 2026-10-15: no process ahead of time. About 50 ms is not worth a process of about 73 MB held while idle, and the start stays inside the countdown, so the idle list is unchanged.
- [x] Idle renderer: Electron 44 launches a renderer ahead of time when the default session is first used, which the display-media handler does at launch. Through Chromium the first capture host takes it. Natively nothing does, so it stays (about 65 MB), and `pnpm measure:cpu` fails `IDLE_ROLES` after a recording.
  - Natively, main no longer registers the display-media handler, and the library's media protocol, which used the default session at launch too, is registered as the first window is made.
  - `pnpm measure:cpu` passes its process-role checks natively: no renderer at launch or after a recording.
  - Settings' first open took 253–341 ms natively against 241–245 ms with the early renderer (the 341 ms run was the first launch after a build).
- [x] Inputs: display (now), window, area and app filters, per-app audio (engine and tests only), microphone (for 074), each with clear errors mapped to the existing `HostErrorCode`s or new ones.
  - Implemented 2026-10-15: `prepare` takes a source (display, window, area, apps) and the sound (system audio, chosen processes' sound or none, and the microphone, default or by id); `microphones()` lists the inputs. The core mixes every input into the one AAC track (`core/mixer.rs`), advancing with the clock 500 ms behind an input that sends nothing, so WASAPI loopback's silence no longer holds audio fragments back. Errors use `capture_start_failed` with a reason; user-facing codes come with the pickers and 074.
  - macOS: verified by live tests on this Mac (a window, an area, one app's windows and sound, each 3 s with audio and video equally long) and through the signed app (an area and a Finder window, `RECORDSTUFF_CAPTURE_SOURCE`). Recording a window first ended the capture process (`CGS_REQUIRE_INIT`, no window-server connection), now fixed. The microphone refuses while macOS has not been asked for access, since AVFoundation then delivers silence; its sound is untested here, as the test's host app has not been granted it.
  - Windows: Windows.Graphics.Capture windows and crops, process loopback per process, WASAPI microphone; chosen apps' windows are refused (Windows.Graphics.Capture cannot). The `native-windows` job passed on commit `985221bd` (run 38692860341): an area recorded at 640×360 and a window the test opened at 786×592, each 3001 ms with an audio track as long (the area's, with system sound off, all silence the clock filled in); one process's sound opened, read and stopped. The runner has no audio input, so the Windows microphone is untested, as is everything step 3 listed.
- [x] Quality: the existing settings in `src/shared/quality.ts` (size cap, frame rate, bit rates) applied natively; the `CaptureReport` keeps its fields so the Recorder, logs and warnings stay as they are. In place since step 2 (`native-host-process.ts`).
- Found on the way: `pnpm measure:cpu`'s scenario C (Settings open behind another app) measured 38.5% and 39.0% in two native runs and 10.0% in a Chromium run, against 0.15–0.18% in two other runs on the same build. The busy process was Settings' renderer with the GPU process; it was not limited to the native engine. Cause, found on 2026-10-15: the pointer left resting on a library card, whose hover preview then looped behind Finder (33.6% with `--hover-card`). The runner now parks the pointer first (PR #7), and Settings stops a preview when it loses the focus and starts none without it (PR #8; `--hover-card` then measured 0.33%).
