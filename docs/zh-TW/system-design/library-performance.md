# 錄影檔分頁的效能設計

[English](../../system-design/library-performance.md) | [繁體中文](library-performance.md)

更新日期：2026-10-27。

這是一份設計紀錄，說明輸出資料夾裡的錄影越來越多時，錄影檔分頁如何保持順暢：做了什麼、刻意不做什麼，以及何時該重新評估。分頁顯示什麼、行為如何，見[桌面功能](desktop.md#錄影檔)。程式碼在 main 的 [recordings-library.ts](../../../src/main/library/recordings-library.ts)，以及頁面的 [library.tsx](../../../src/renderer/settings/tabs/library.tsx)、[clip.tsx](../../../src/renderer/settings/tabs/library/clip.tsx) 與 [clip-preview.tsx](../../../src/renderer/settings/tabs/clip-preview.tsx)。

## 整體做法

列出的每一支錄影都是 DOM 裡真正存在的卡片，清單沒有虛擬化。分頁保持輕量的方式，是把真正昂貴的工作控制住：讀磁碟、解碼影片、排版頁面。下面每一項都經過限流、快取、延後或在畫面外略過，所以成本跟著「畫面上看得到的」或「實際有變動的」走，而不是跟著資料夾大小走。

設計和量測的規模是幾十到幾百支錄影。縮圖量測使用 240 支真實影片。

## 成本在哪裡、怎麼控制

### 縮圖

縮圖是用 QuickLook 讀取影片產生的（`nativeImage.createThumbnailFromPath`，[video-thumbnail.ts](../../../src/main/library/video-thumbnail.ts)），要讀磁碟又要解碼，是卡片要求的工作中最貴的一項。

| 做法 | 效果 | 接受的代價 |
| --- | --- | --- |
| `<img loading="lazy" decoding="async">` | 只有接近畫面的卡片才要縮圖；JPEG 解碼不阻塞頁面 | 快速捲到的卡片會短暫顯示替代圖示 |
| 同時最多產生四張（`THUMBNAILS_AT_ONCE`），其餘排隊，**最新要求的優先** | 快速捲動不會一次啟動上百個 QuickLook 讀取；停下來時，先產生畫面上的卡片，捲過去的排後面 | 捲過去的卡片較晚出圖 |
| 以帶檔案版本的網址（`thumb/<id>?v=<version>`）回應，標為 `immutable` | 切換分頁、捲回去或重開視窗都不必再向 main 要；檔案改變就換新網址，永遠不會保留過期的圖 | 列出後又改變的檔案以 `no-cache` 回應，頁面會再要一次 |
| main 在記憶體只保留最近顯示的 64 張（`THUMBNAILS_KEPT`，最久沒顯示的先丟） | 連續執行好幾天的 menu bar app 不會隨資料夾變大而膨脹；每張 JPEG 約幾十 KB | 已從記憶體丟掉、頁面快取也沒有的圖要重新產生 |
| 960×540、品質 85 的 JPEG | 三欄格狀在 Retina 螢幕上清晰，比 PNG 小好幾倍 | 對單欄格狀來說偏大 |

四張是量出來的，不是猜的（`pnpm measure:thumbnails`，[thumbnails.measure.ts](../../../tests/ui/measure/thumbnails.measure.ts)，M1 Pro，2026-10-08）：240 支真實影片捲到底再捲回來，四張和不限制一樣快，三張則讓縮圖的等待時間長了好幾倍。這項量測是在同一台機器上比較不同設定，不是效能預算。

### 滑鼠停留預覽

在卡片裡播放錄影需要一個解碼器，播放期間是頁面上最貴的工作。

- **同一時間只有一個預覽。** 滑鼠離開的卡片會卸載影片，所以掃過再多張卡片，最多也只佔用一個解碼器。
- **停留 400 ms 才開始**（`PREVIEW_DELAY_MS`），所以滑過格狀不會觸發任何預覽。
- **沒有焦點的視窗不啟動預覽**；視窗隱藏或其他 app 取得焦點時，預覽就停止（2026-10-15，起因是一個留在其他 app 後面循環播放的預覽吃掉約 30% 的核心）。
- **進度條上的畫格縮圖是第二支影片，只在滑鼠停在進度條的那條區域時才載入。**
- **列表模式和減少動態效果（reduced motion）時不預覽。**

接受的代價：無法並排預覽兩張卡片，而這個分頁本來就不需要。

### 長度

錄影長度是讀 MP4 box 得到的，不靠解碼。擷取程式寫的是 fragmented MP4，所以長度等於最後一個完整 fragment 的 `tfdt` 加上它的樣本長度，過程中只讀 box header。

- **先顯示清單**，再**逐一讀取**還不知道的長度。
- 長度**最多每 500 ms 推送一次**（`LENGTHS_PUBLISH_MS`），讀完時再推送一次。2026-10-04 之前要等全部讀完才推送，長錄影多的資料夾會很久都沒有長度。
- 長度依檔案版本快取，之後重新列出時只讀新的或變動過的檔案。重新命名和移動時會沿用。
- **關閉或隱藏視窗時，讀完當前這一個檔案就停止**（2026-10-08）。在此之前，視窗關掉後還會繼續逐一解析大資料夾，甚至在下一次錄影寫檔時也一樣。

接受的代價：大資料夾打開的最初一段時間，長度會陸續補上；每次推送都會重算頁面的清單和按天分組。卡片本身不會重新渲染（見下文）。

### 列出與監看資料夾

- **同一時間只有一次列出**；這期間的其他請求會合併成之後的一次。例如打開設定視窗時，「顯示」和「取得焦點」各會要求一次。
- **只在視窗開著時監看資料夾**（`fs.watch`，macOS 上是 FSEvents，事件驅動，從不輪詢）。一連串事件會在平靜下來 250 ms 後（`WATCH_SETTLE_MS`）只列出一次。隱藏或關閉的視窗不監看任何東西，也不跑任何計時器。

### 頁面渲染

| 做法 | 效果 | 接受的代價 |
| --- | --- | --- |
| `Clip` 用 `memo`，並**逐欄位比較** | IPC 每次更新（儲存版面偏好、推送長度）都會複製整個 view，只比 reference 的話每張卡片都會重新渲染；逐欄位比較後，只有值真的變了的卡片才渲染 | 每次更新都要逐一比較每張卡片的欄位 |
| 每一天（`.library-day`，[ui.css](../../../src/renderer/ui.css)）加上 `content-visibility: auto`，並設 `contain-intrinsic-size: auto 500px` | 畫面外的天略過 style、layout 和 paint，所以縮放視窗（雙擊標題列會動畫經過幾十種寬度）時只排版看得到的天 | 不省 React 的工作，也不減少 DOM 節點。以「天」為單位，某一天有幾百支錄影時，只要有一部分在畫面上，整天都要排版。從沒顯示過的天先假設 500 px，第一次捲過時捲軸可能會跳動 |
| 同一元素加上 `overflow-clip-margin: 8px` | `content-visibility` 帶來的 paint containment 不會切掉畫在卡片外 5 px 的狀態外框 | — |
| 搜尋過濾的是延後的搜尋字（`useDeferredValue`） | 輸入框每個按鍵都立即回應，清單在可中斷的背景渲染中跟上，不像 debounce 有固定延遲 | 清單會短暫落後輸入框。由程式自己清除的搜尋（從通知跳到某支錄影）改用即時的值（`queryNow`），確保要聚焦的卡片存在，代價是一次同步渲染 |

## 刻意不做的事

### 清單虛擬化

只渲染畫面上的卡片（例如用 `@tanstack/react-virtual`）可以讓頁面的成本跟著視窗大小走，而不是跟著資料夾大小走。不做的理由是：在上述規模下，它能省下的成本還沒被證明有影響，而它帶來的代價是確定的：

- **依賴「每張卡片都在 DOM 裡」的行為。** ⌘F 能用名稱找到卡片；Tab 能走過每張卡片；輔助技術能讀完整份清單；從通知或「顯示上一次錄影」進來時，能直接聚焦並捲到某張卡片；卡片移到垃圾桶時，焦點會交給相鄰的卡片。虛擬化之後，這些都需要各自處理、各自測試。
- **分組的格狀是最難的情況。** 每列幾張卡片取決於視窗寬度（一到三張），每一天有標題；滑鼠預覽、打開的選單和焦點都在某張卡片上，而這張卡片可能在它們底下被卸載。
- **在這個規模下最明顯的成本（縮放時的排版），`content-visibility` 已經解決了**，只用一條 CSS，不必改元件。

這樣做仍沒有上限、也還沒量測過的成本：

- 第一次顯示分頁、以及切換分類時，**mount 每一張卡片**。
- 每次推送長度時的**清單 diff**。

兩者都隨錄影數量成長。

### 沒採用的小優化

- **預先算好小寫標題。** 比對標題不是時間花費所在，省下的時間小到量不出來。
- **搜尋用 debounce。** 清單是在記憶體中過濾，每個按鍵沒有 I/O；debounce 只會多一段固定延遲，計時器到期時照樣會阻塞。`useDeferredValue` 更適合這種情況（見[學習筆記](../../learning/deferred-search-in-react.html)）。

## 何時重新評估

以下**兩個條件都成立**時，再考慮虛擬化：

1. 實際使用中出現**上千支錄影**的資料夾，或單一天常有幾百支。
2. **量測**顯示明顯卡頓：在打開分頁、切換分類、清除搜尋或捲動時，trace 裡出現超過一個畫格的長任務。

在完整虛擬化之前，先試比較便宜的一步：把一天切成固定大小的區塊（例如每 30 張一組），各自加上 `content-visibility: auto`，讓錄影很多的那一天不必整天排版。兩個條件沒有同時成立前，這兩項改動都不需要。

調整 `THUMBNAILS_AT_ONCE`、`THUMBNAILS_KEPT` 或推送間隔時，應比照目前數值的做法量測：縮圖用 `pnpm measure:thumbnails`，長度用一個真實的大資料夾。
