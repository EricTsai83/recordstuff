從瀏覽器 API 到作業系統 API：native 是什麼，什麼時候值得往下走

用網頁技術（Electron、Tauri 或其他 WebView 外殼）做的桌面 App，遲早會碰到一個瀏覽器給不了的功能。這時有好幾條路：繼續用 runtime 給的 API、寫一個原生模組、把原生程式碼放進獨立的 process、換一個框架，或整個改寫成原生 App。本文先說明「native API」在技術上是什麼、為什麼 JavaScript 必須靠 runtime 才碰得到它，再把每條路的前提、代價與會讓結論翻轉的條件攤開比較。範例是一個 Electron 螢幕錄影 App 把擷取從 Chromium 移到 Rust 的過程，它只是一個例子，不是答案。

這篇文章要回答的問題

一個用 TypeScript 寫的桌面 App，UI、設定、狀態機和測試都在同一個語言裡，開發起來很順。某天產品要一個功能，而這個功能只有作業系統才提供，瀏覽器沒有對應的 API。可遷移的問題是：

一個建立在網頁技術上的桌面 App，什麼時候應該往下寫原生程式碼？往下寫的話，要寫在哪一層、用什麼語言、放在哪個 process？又什麼時候乾脆換框架？

這些選擇彼此牽連。語言決定你能用哪些綁定（binding）；process 的位置決定當機會帶走多少東西、系統權限算在誰頭上；框架決定 UI 用哪個網頁引擎、哪些工具能留下來。要做好判斷，得先知道「native」到底指什麼。

三層 API：瀏覽器、runtime、作業系統

一段 JavaScript 能做什麼，取決於執行它的環境把哪些能力交給它：

  • 瀏覽器 API：getDisplayMedia、MediaRecorder、fetch 這類由 Web 標準定義、瀏覽器實作的介面。它們為了安全與跨平台而刻意收窄：能做的事由標準決定，不由作業系統決定。
  • runtime API：Node.js 的 fs、child_process，或 Electron 的 Tray、Notification、desktopCapturer。它們由 runtime 的作者用 C/C++ 包好作業系統的功能再交給 JavaScript，範圍比瀏覽器寬，但仍只涵蓋作者選擇包的部分。
  • 作業系統 API：macOS 的 ScreenCaptureKit、AVFoundation、CoreGraphics，Windows 的 Windows.Graphics.Capture、WASAPI、Media Foundation。這是功能真正所在的地方，也是新功能最先出現的地方。

以螢幕錄影為例：Chromium 的 getDisplayMedia 能擷取一個螢幕或一個視窗，Electron 另外打了補丁，讓 App 自己的受保護視窗不被錄進去。但它不能把選單列、Dock 或桌面圖示排除在錄影之外，不能只錄一塊區域或幾個指定的 App，也不能只錄某一個 App 的聲音。在 macOS 上這些都要用 ScreenCaptureKit 的 SCContentFilter，而 Electron 或 Chromium 沒有任何 API 把它交給 JavaScript。這就是「瀏覽器給不了」的典型樣子：不是效能不夠，而是能力根本不在那一層。

native API 是什麼：二進位的呼叫慣例

作業系統不是用某種程式語言「提供」API，而是用一套二進位層級的呼叫慣例（calling convention 與 ABI）：參數放在哪些暫存器或堆疊位置、物件長什麼樣子、誰負責釋放記憶體、錯誤怎麼回報。任何能產生符合這套慣例的機器碼的語言，都能呼叫它。桌面平台主要有四種：

慣例平台與例子呼叫方式
C兩邊都有：CoreGraphics 的 CGMainDisplayID、Win32 的 SetWindowDisplayAffinity依函式名稱連結，直接呼叫。最簡單，幾乎所有語言都支援。
Objective-C runtimemacOS 的 AppKit、AVFoundation、ScreenCaptureKit呼叫方法其實是送「訊息」：用 selector（方法名稱）呼叫 objc_msgSend，由 runtime 在執行期查出實作。所以程式可以先問物件「你認不認得這個 selector」，再決定要不要呼叫。
COMWindows 的 WASAPI、Media Foundation、Direct3D 11物件是一個指向函式表（vtable）的指標；每個介面都繼承 IUnknown（查詢介面、參考計數），方法回傳 HRESULT 錯誤碼。
WinRTWindows 的 Windows.Graphics.Capture建立在 COM 之上，另外附帶描述型別的中繼資料（.winmd），讓 C++、C#、Rust 等語言能自動產生「投影」（projection）來呼叫。

Swift 在 macOS 上能直接呼叫 Objective-C 與 C 的框架，是 Apple 的第一語言；C++ 可以透過 Objective-C++ 呼叫 Apple 的框架，也是 Windows 上 COM 與 C++/WinRT 的原生語言；Rust 則透過綁定函式庫做同樣的事：objc2 系列（或 cidre）對應 Apple 的框架，Microsoft 自己維護的 windows-rs 從 Windows 的中繼資料產生綁定。

下面三段 Rust 程式碼來自本文範例的錄影引擎，分別示範三種慣例。重點不是語法，而是「同一個編譯語言可以直接走三種慣例」：

Rust// C：宣告 CoreGraphics 的函式，直接呼叫
unsafe extern "C" {
    fn CGMainDisplayID() -> u32;
}
unsafe { CGMainDisplayID() };

// Objective-C runtime：先問物件認不認得這個 selector，再送訊息
if filter.respondsToSelector(sel!(setIncludeMenuBar:)) {
    let _: () = unsafe { msg_send![&filter, setIncludeMenuBar: false] };
}

// WinRT 加上 COM interop 介面：用螢幕的 handle 建立擷取項目
let interop = windows::core::factory::<GraphicsCaptureItem, IGraphicsCaptureItemInterop>()?;
let item = unsafe { interop.CreateForMonitor::<GraphicsCaptureItem>(monitor) }?;

第二段也說明了綁定函式庫的一個代價：setIncludeMenuBar 只有較新的 macOS 才有，程式在執行期先確認物件支援，才直接送出訊息。當綁定還沒跟上某個新 API，或需要依系統版本決定是否呼叫時，就得退回這種較低階、編譯器幫不上忙的寫法。

為什麼 JavaScript 需要 runtime 幫忙

編譯語言產生的是機器碼，可以直接按照上面的慣例跳進系統函式。JavaScript 不是：它在 V8 這類虛擬機裡執行，只能操作虛擬機給它的值和函式，沒有辦法自己載入一個動態函式庫、把參數排進暫存器、跳到一個函式指標。這個「跳過去」的動作必須由 runtime 用原生程式碼完成，再把結果包成 JavaScript 的值。

因此 JavaScript 碰觸作業系統只有三種方式：

  1. runtime 內建：等 runtime 的作者把你要的功能包進去（例如等 Electron 新增某個 API）。你不寫原生程式碼，但功能的範圍和時程都不由你決定。
  2. 執行期 FFI（foreign function interface）：runtime 或套件提供「載入某個函式庫、照某個簽名呼叫某個函式」的通用機制，例如 Node.js 的 koffi 套件、Deno 的 Deno.dlopen、Bun 的 bun:ffi。不用編譯，但型別與記憶體管理全在 JavaScript 這邊描述，錯一個參數就是當機；面對 Objective-C 訊息、COM 物件與回呼（callback）時尤其笨重。
  3. 原生模組（native addon）：用 C、C++、Rust 等語言寫一個動態函式庫（Node.js 裡副檔名是 .node），由 runtime 用 require() 載入。模組在原生那一側自由呼叫作業系統，只把整理好的介面交給 JavaScript。

原生模組和 runtime 之間也需要一套慣例。早期 Node.js 的原生模組直接使用 V8 的 C++ API，每次 Node 或 Electron 升級都可能要重新編譯。Node-API（舊稱 N-API）是 Node.js 為此提供的穩定 C 介面：模組只依賴 Node-API，原則上就不必為每個 Node 或 Electron 版本重新編譯，但仍然要為每個作業系統與 CPU 架構各編一份。

直接用 Node-API 的 C 函式寫模組很繁瑣，所以多數專案會用產生器：C++ 有官方的 node-addon-api，Rust 有 napi-rs。napi-rs 讓你在 Rust 的型別與方法上加標註，自動產生 Node-API 的膠水程式碼與 TypeScript 型別宣告。下面是範例錄影引擎對 JavaScript 公開的介面（省略了實作）：

Rust#[napi]
pub struct NativeCapture { /* 錄影工作階段、事件回呼 */ }

#[napi]
impl NativeCapture {
    #[napi(constructor)]
    pub fn new(on_event: Function<EngineEvent, ()>) -> Result<Self> { /* … */ }

    #[napi(ts_return_type = "Promise<PreparedInfo>")]
    pub fn prepare(&self, options: PrepareOptions) -> AsyncTask<PrepareTask> { /* … */ }

    #[napi]
    pub fn record(&self) -> Result<()> { /* … */ }

    #[napi(ts_return_type = "Promise<StopReport>")]
    pub fn stop(&self) -> AsyncTask<StopTask> { /* … */ }
}

從 TypeScript 看，這只是一個有 prepare、record、stop 方法的類別，耗時的工作回傳 Promise，不會卡住事件迴圈。介面刻意做得很窄：只有幾個粗粒度的操作和一個事件回呼，每一幀畫面、每一段聲音都留在原生那一側。這是混合語言時最重要的設計原則：跨語言邊界的次數越少、資料越小越好。

原生程式碼要放在哪個 process

決定寫原生模組之後，下一個問題是它在哪裡執行。原生程式碼沒有 JavaScript 的安全網：一個空指標、一個用錯的參數，或系統框架自己判定狀態不對而中止，都會讓整個 process 立刻結束，try/catch 接不到。所以「放在哪個 process」其實是「當機時要犧牲多少」。以 Electron 為例有三個選項：

A. 直接載入 main process

最簡單：require() 之後直接呼叫，沒有訊息往返，沒有額外的 process。代價是原生程式碼和整個 App 同生共死。對一個小而成熟、只做純計算的模組（例如雜湊或壓縮）這通常可以接受；對一個長時間持有系統資源、每秒處理幾十張影像的模組，一次當機就會讓托盤圖示消失、正在進行的工作中斷，而且沒有人能回報發生了什麼事。

B. Electron 的 utilityProcess

utilityProcess 是 Electron 提供的子 process：裡面跑的是 Node.js 環境，可以 require() 原生模組，和 main 之間用 MessagePort 傳訊息。原生程式碼當機只會結束這個子 process，main 看到它結束，就能把這次工作標成失敗、清理資源、通知使用者。代價是一次 process 啟動的時間、要設計訊息協定，以及子 process 和 App 主體並不完全相同（下面的範例會遇到一個這樣的差異）。

C. 獨立執行檔（sidecar）

把原生程式碼編成一個完整的執行檔，由 App 啟動，透過標準輸入輸出或 socket 溝通。Tauri 稱這種做法為 sidecar。它的隔離最強，也不受 Node 或 Electron 版本影響，甚至可以用和 App 完全無關的語言撰寫。但在 macOS 上，螢幕錄影、麥克風這類隱私權限是授給「某個 App」的；一個獨立執行檔會被算在誰頭上、使用者看到的權限提示會是什麼名字，都必須實際驗證，不能假設。

權限歸屬在 utilityProcess 上也不是理所當然的。範例專案在簽署過的 App 套件裡，螢幕與系統音訊權限確實套用到了 utilityProcess；但在開發用、未簽署的 Electron 裡，同一個 utilityProcess 被系統拒絕擷取（錯誤 -3801），所以所有錄影量測都必須在簽署過的套件上做。凡是涉及系統權限的原生功能，都要把「權限在這個 process 安排下是否有效」當成第一個驗證項目。

語言怎麼選：Swift、C++ 或 Rust

只要能產生符合系統慣例的機器碼，任何編譯語言都行。真正的差別在綁定、跨平台、安全性和團隊：

SwiftC++（macOS 上是 Objective-C++）Rust
macOS 框架第一語言，Apple 的新 API 第一天就能用，文件與範例最多透過 Objective-C++ 直接呼叫，也是第一手透過社群綁定（objc2、cidre），新 API 可能落後，必要時退回直接送訊息
Windows API就這個用途幫助不大，通常要再加一種語言COM 與 C++/WinRT 的原生語言Microsoft 維護的 windows-rs，從中繼資料產生，覆蓋完整

這張表沒有通用的贏家。只做 macOS、而且需要最新 Apple API 的產品，Swift 幾乎總是對的；已經有一大片 C++ 程式碼與人力的團隊，C++ 的成本最低；要在兩個平台上共用同一套媒體處理邏輯、又擔心原生程式碼當機的團隊，Rust 的吸引力最大。TypeScript 加 Rust 也不是冷門組合：Signal Desktop 是 Electron 加上 Rust 寫的 libsignal，1Password 8 是 Electron 加 Rust 核心，Cap 用 Tauri 做 TypeScript UI、Rust 做錄影後端。

決策框架：每條路的代價

把所有選項放在一起比較。「能力」指能碰到多少作業系統功能；「隔離」指原生程式碼出錯時影響多大；成本分成一次性的與之後每次發版都要付的。

選項能力隔離一次性成本持續成本團隊需要
只用瀏覽器／runtime 已有的 API受標準與 runtime 限制最好（沒有原生程式碼）無無；但功能只能等別人加只要 TypeScript
執行期 FFIC 函式容易，Objective-C、COM、回呼很笨重差（在呼叫者的 process 裡）低簽名寫錯就當機，型別沒有編譯器把關要懂 C ABI
原生模組載入 main完整差：當機帶走整個 App中：新語言、建置、簽署每個平台與架構各編一份一種原生語言
原生模組放 utilityProcess完整（權限要驗證）好：當機只結束子 process中：再加一套訊息協定同上，加上 process 啟動時間一種原生語言加 IPC 設計
獨立執行檔／sidecar完整（權限歸屬要另外證明）最好中到高：自己的打包、簽署、啟動與溝通版本對應、多一個要簽署公證的二進位任一語言
換框架（例如 Electron → Tauri）同樣要寫原生（Rust）才有新能力看後端怎麼放高：重寫 main 端程式與測試工具不同平台用不同網頁引擎Rust 加網頁
整個改寫成原生 App完整，UI 也最貼近系統原生程式碼就是 App最高：每個平台一套 UI每個平台各維護一份 App每個平台的 UI 技術

讀這張表的方法是由上往下：選能滿足需求的第一列。每往下一列，都應該有一個上一列做不到、而且已經量到的理由。注意「換框架」那一列的能力欄：從 Electron 換到 Tauri，本身並不會讓你得到 ScreenCaptureKit，你還是要寫一樣的 Rust 程式碼。框架決定的是外殼，不是你能碰到多少作業系統。

其他產品怎麼選

螢幕錄影是一個很好的觀察對象，因為瀏覽器 API 和原生 API 的落差在這裡特別明顯：

  • OBS：用 C/C++ 寫成的原生 App，每個平台各有一個擷取外掛。它的需求是最大的能力與效能，願意付每個平台各寫一份的代價。
  • Cap：Tauri 外殼，TypeScript UI，Rust 後端；macOS 用 ScreenCaptureKit（透過 cidre 綁定），Windows 用 Windows.Graphics.Capture。一種原生語言涵蓋兩個平台。
  • Screen Studio、CleanShot X：只做 macOS 的原生 App。只有一個平台時，最直接的路就是 Apple 自己的語言與框架。
  • Loom 的瀏覽器擴充、Screenity：完全建立在瀏覽器 API 上，換來的是零安裝與跨平台，也因此只能做瀏覽器允許的事，例如無法把選單列排除在錄影之外。
  • Signal Desktop、1Password 8：不是錄影工具，但同樣是 Electron UI 加 Rust 核心。它們的原生部分是加密與資料處理，說明「UI 留在網頁技術、敏感或吃重的核心放進編譯語言」是很常見的分工。

這些選擇各自對應不同的前提：需要多少平台、需要多少作業系統能力、團隊原本擅長什麼、已經有多少程式碼。沒有一個是另一個的錯誤版本。

範例：一個 Electron 錄影 App 把擷取移到 Rust

範例是一個常駐選單列的開源螢幕錄影 App。它原本完全用 Electron 與 TypeScript：一個隱藏的 renderer 呼叫 Chromium 的 getDisplayMedia 取得螢幕與系統聲音，用 MediaRecorder 編碼成 MP4 片段，每秒把一段送給 main process 寫檔。專案的設計決策裡早有一條：「只有在量到具體的限制之後，才考慮原生擷取」。

前提：什麼條件成立了

  • 能力限制被具體指出：使用者要求隱藏選單列與 Dock、錄一塊區域或指定的 App、只錄某個 App 的聲音。上面說過，這些都需要 SCContentFilter，沒有任何 Electron 或 Chromium API 提供。這不是「原生應該比較快」的猜測，而是一張做不到的功能清單。
  • 兩個平台：App 同時發佈 macOS 與 Windows 版，需要的能力在 Windows 上對應 Windows.Graphics.Capture 與 WASAPI。
  • 大量 Electron 相依的程式碼與工具：main、shared 與 preload 約 14,600 行，測試與驗收工具約 32,000 行。

三個選擇與被放棄的替代方案

語言：兩個平台都用 Rust。替代方案是 macOS 用 Swift、Windows 用 C++ 或 Rust。Swift 在 macOS 上最直接，也最先拿到 Apple 的新 API，但兩種原生語言意味著兩套擷取管線、兩個 MP4 封裝器（muxer）、兩套測試。選 Rust 之後，錄影的狀態機、音訊時間戳、混音和 MP4 封裝器都在一個共用的核心裡，兩個平台只各自實作「從系統拿到畫面與聲音、交給系統編碼器」那一段。專案的決策紀錄寫明了翻轉條件：如果某個需要的 Apple API 長期無法從 Rust 使用，就重新考慮 macOS 改用 Swift。

位置：每次錄影開一個 utilityProcess。載入 main 被放棄，因為原生當機會結束整個 App；獨立執行檔被放棄，因為必須先證明 macOS 的螢幕權限會套用在它身上。utilityProcess 還保留了原本的結構：舊架構本來就有一個獨立的擷取 process（隱藏 renderer）透過訊息和 main 溝通，所以 main 裡的錄影狀態機幾乎不必改。

TypeScript// main：每次錄影 fork 一個新的 utilityProcess，把原生模組的路徑當參數傳入
const child = utilityProcess.fork(entryPath, [addonPath], { serviceName: "RecordStuff Capture", stdio: "pipe" });
child.on("exit", (code) => {
  // 子 process 結束：這次錄影標成失敗，已經寫到磁碟的部分保留下來
});

// utilityProcess 裡（簡化）：載入 .node，把引擎的事件轉成給 main 的訊息
const engine = require(process.argv[2]);
const capture = new engine.NativeCapture((event) => parentPort.postMessage(event));

框架：留在 Electron，不換 Tauri。Tauri 同樣是 TypeScript 加 Rust，看起來很順手。但換框架要重寫那約 14,600 行程式碼與 32,000 行測試工具，Mac 上的網頁引擎也會從 Chromium 換成 WebKit（WKWebView），換來的是 App 大小與記憶體的改善，而專案先前已經決定不為了大小與記憶體重寫。另一方面，新的 Rust 擷取模組不依賴 Electron，未來真的要換框架時可以原封不動帶走，所以這個決定不是死路。

量到了什麼，也付出了什麼

在同一台 M1 Pro 上和原本的 Chromium 路徑對照：

錄影時 CPU（一個核心的百分比），30 fps10.4%15.3%
錄影時 CPU，60 fps14.0%23.3%

CPU、影音同步和功能都變好了，但不是每一項都變好。啟動慢了約 0.1 秒，拆開來看，其中 74–88 ms 是 utilityProcess 自己的啟動，其餘是查詢可擷取內容與 ScreenCaptureKit 開始擷取。團隊量過「預先啟動 process」：大約省 50 ms，代價是閒置時多一個約 73 MB 的 process，最後決定不做，因為啟動時間仍落在倒數計時之內。畫面偶爾相隔 50 ms 的問題，原因尚未找到，維護者記錄後接受。

隔離的價值也被實際驗證了兩次。第一次是刻意的：錄影中途強制結束 utilityProcess，留下一個 8.0 秒、可以播放的片段檔。第二次是意外：加入「只錄一個視窗」時，擷取 process 一開始就直接結束了。原因是視窗篩選需要和 macOS 的視窗伺服器（window server）建立連線，一般 App 啟動時就有這個連線，utilityProcess 沒有，CoreGraphics 於是以 CGS_REQUIRE_INIT 中止 process。修正只要在使用前呼叫一次 CGMainDisplayID() 建立連線（就是前面那段 C 呼叫）。如果模組是載入在 main 裡，同樣的錯誤只會讓整個 App 消失；在子 process 裡，它只是一次失敗的錄影和一行日誌。這也提醒了另一件事：子 process 不是 App 的完整複本，系統框架對「App」的某些假設在那裡可能不成立。

代價則持續存在：

  • CI 的 macOS 與 Windows 兩個 job 都要裝 Rust 工具鏈並快取建置；沒有 Cargo 的建置會直接失敗，而不是做出一個不能錄影的 App。
  • .node 檔必須從 Electron 的 asar 封包裡解開，並和 App 一起簽署；驗證腳本會拒絕缺少它或簽署不對的套件。
  • 平台相關的程式碼仍然要寫兩次（mac/ 與 win/），只有核心是共用的；而沒有 Windows 實機的團隊，Windows 那一半只能靠 CI 驗證，真實硬體上的畫質、音訊內容與 CPU 都列為未驗證。
  • 綁定函式庫可能晚於 Apple 或 Microsoft 的新 API。

同一個專案裡的反例

這個專案更早之前也寫過一個原生模組，結局相反。為了讀取 macOS 通知權限的狀態，它寫了一個 Node-API 橋接到 UserNotifications 框架，後來整個撤掉。原因是：當這個 .node 載入失敗（例如架構不對，或比執行環境新的版本），程式會把所有通知都靜默略過，連 Electron 本來會自動發出的授權請求都一起消失，結果比完全不知道權限狀態還糟。這個功能只是「顯示一個狀態」，帶來的好處很小，卻引入了一個新的失敗模式。兩個案例的差別在於：錄影引擎解決的是做不到的功能，通知橋接解決的只是一點資訊不足。

換框架什麼時候值得

「既然都要寫 Rust 了，為什麼不乾脆換到 Tauri？」是很自然的問題。Tauri 的後端是 Rust，UI 用作業系統內建的 WebView：macOS 上是 WKWebView（WebKit），Windows 上是 WebView2（Chromium 核心），Linux 上是 WebKitGTK。它不打包 Chromium，所以 App 通常小很多，閒置記憶體也較低。值不值得換，取決於這些條件：

  • 值得考慮：專案剛開始，或和 Electron 綁在一起的程式碼與測試工具還很少；App 大小與記憶體是產品的核心指標，而且已經量到它們造成實際問題；團隊本來就熟 Rust；能接受 macOS 與 Windows 用不同網頁引擎，並為兩個引擎都做 UI 測試。
  • 不值得：主要動機是「需要某個作業系統功能」，因為這在 Electron 裡寫原生模組就能得到，換框架不會讓那段原生程式碼變少；或者大量測試、驗收工具、打包與簽署流程都和 Electron 綁在一起，重寫的成本遠高於大小與記憶體的收益。

一個實用的做法是讓原生程式碼不依賴外殼：用 napi-rs 包一個純 Rust 的核心，核心本身不知道 Electron 的存在。這樣「先在 Electron 裡寫原生」與「以後換 Tauri」就不互相排斥，換框架時只需要換掉最外面那層綁定。

不要這樣做的時候

  • 瀏覽器或 runtime 的 API 已經夠用時，不要因為「原生應該比較快」就往下寫。沒有量到具體的能力限制或效能問題之前，原生程式碼只會增加建置、簽署與跨平台驗證的負擔。
  • 好處只是一點方便或資訊時，不要引入會讓核心功能一起失效的原生依賴（上面通知橋接的教訓）。如果一定要，載入失敗時必須退回原本的行為，而不是靜默停用功能。
  • 只支援一個平台而且需要最新系統 API 時，不要為了「以後可能跨平台」選 Rust 或 C++；Swift 與 Apple 的第一手工具會更省事。
  • 原生程式碼很小、只做純計算、而且非常成熟時，不需要為它開一個 utilityProcess；載入 main 的簡單性在這裡勝出。
  • 還沒驗證系統權限會套用到某個 process 時，不要把需要隱私權限的功能放進獨立執行檔或子 process 就上線。
  • 只是因為要寫一點 Rust 就換框架，不划算；框架決定外殼，不決定作業系統能力。

帶走的判斷問題

  1. 需要的能力在哪一層？瀏覽器、runtime，還是只有作業系統有？能不能列出一張「現在做不到」的具體清單？
  2. 這個能力用的是哪種呼叫慣例（C、Objective-C、COM、WinRT）？你考慮的語言有沒有成熟的綁定，新 API 出來時要等多久？
  3. 要支援幾個平台？共用的部分（狀態機、檔案格式、測試）大到值得用同一種原生語言嗎？
  4. 原生程式碼當機時，你願意犧牲什麼？只是這次工作，還是整個 App？
  5. 系統權限會算在哪個 process 頭上？在簽署過的正式套件裡驗證過了嗎？
  6. JavaScript 和原生之間的介面夠窄嗎？大量資料是否留在原生那一側？
  7. 原生核心是否不依賴外殼，讓將來換框架時可以帶走？
  8. CI、簽署、貢獻者環境多出來的成本，誰來付？每次發版都要付嗎？
  9. 哪個量測結果或外部變化（例如 runtime 新增了 API、綁定長期落後、團隊組成改變）會讓你推翻這個決定？
