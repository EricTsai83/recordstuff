# 036 — Background failure-history persistence and safe exit

[English](036-async-failure-history.md) | [繁體中文](036-async-failure-history.zh-TW.md)

Status: planned, not implemented. Created: 2026-09-25. Schedule immediately after [025](../docs/verification/history-2026-09.md#plan-025-closure--2026-09-25), before [037](037-overlapping-recording-finalization.md) and final [035](035-guided-native-acceptance.md). This is a separate implementation task, not a claim that current history storage is asynchronous.

## Purpose and boundary

Failure history currently serializes, writes, fsyncs and renames synchronously in main. A slow user-data disk can freeze the UI, and recovery from a failed save requires a manual retry. Make this metadata I/O asynchronous so main never blocks on the disk, automatically retry recoverable failures, and make normal quit/relaunch account for unsaved history. Recording media already uses asynchronous ordered writes; this plan neither changes media finalization nor admits another recording while a successful recording is still stopping.

Owners: [history coordinator](../src/main/recording-result.ts), [storage](../src/main/recording-result-store.ts), [app lifecycle](../src/main/index.ts), shared models, Settings renderer and tests, including the [Settings fixture](../scripts/fixtures/settings-panel.ts). Preserve independent IDs, all unread plus the 20 most recently reviewed records, per-ID warnings, manual retry, migration, future/corrupt-file protection, atomic replacement and the 32 MiB safety bound.

Merged finding (2026-09-25): result actions lose keyboard focus when the reply is slower than one frame. [choose()](../src/renderer/settings.ts) disables the focused Got it/Remove button while saving; Chromium's focus fixup then moves focus to `body` at the next rendering update, and `updateRecordingResult` decides restoration from `document.activeElement` only when the reply arrives, so restoration is skipped. On unmodified HEAD `6377c62`, a 100 ms delay in the Settings fixture's `recordingResult:` choose handler failed "real mouse Got it acknowledges only the offered result and collapses it", "acknowledged result can be reopened with keyboard" and "removing the final reviewed row returns keyboard focus to the active tab" in 2/2 runs; without the delay they failed intermittently (one of three interleaved baseline runs). Real saves are slower than the fixture, and this plan's durable, asynchronous acknowledgement slows the reply further, so the fix belongs with the saving flow here. VoiceOver and native behavior have not been observed.

025 owns media terminal operations and the single quit coordinator. This plan registers metadata work with that coordinator, rather than adding a competing before-quit handler. Metadata-loss consent never permits abandoning a media write. Execute with [Codex implementation / Opus 5.5 review](../.agents/skills/codex-implement-with-opus-5-5-review/SKILL.md).

## Implementation contract

- [ ] Move every filesystem operation to Node's asynchronous `fs.promises` API, which runs on the libuv threadpool: the store's `load()` and `save()` become asynchronous, and `save()` uses the existing `writeFileAtomic` instead of `writeFileAtomicSync`. Merely wrapping the synchronous calls in a Promise is insufficient, because main still blocks. Serialization stays on main: the history is bounded to all unread plus the 20 most recently reviewed records with details capped at 64 KiB, so JSON work is small. Measure serialization of the largest allowed snapshot; add a `worker_threads` executor only if that measurement exceeds one frame (16 ms), and record the number. Without a worker there is no packaging, lifecycle or crash-recovery machinery to maintain. Include startup read/validation/migration cost in responsiveness measurements; never write an empty startup state over history that has not finished loading. Merge failures arriving during load by UUID.
- [ ] One persistence owner and one in-flight write. Assign snapshot revisions; an older completion must not clear warnings for newer unsaved changes. Coalesce replaceable pending snapshots, but preserve every failure and explicit action outcome; keep at most one in-flight and one latest queued snapshot, not an unbounded write queue. A timeout does not cancel OS I/O or authorize a competing writer/rename.
- [ ] New errors remain visible immediately. Got it/remove show localized saving feedback, and commit their visible acknowledgement/removal only when the relevant revision is durable. Preserve new arrivals and late file outcomes while an action waits. Disable duplicate action submission without globally freezing recording controls. Failed actions retain the previous state and a per-row error; only genuinely unsaved rows get persistence warnings. Independent retry never acknowledges a row.
- [ ] Keep focus ownership through a pending result action. Before any control is disabled, record which result and control started the action; when the reply or durable commit arrives, restore focus from that intent: to that result's summary after acknowledgement, collapse or failure, and to the active tab after removing the last row. Do not rely on `document.activeElement` surviving the wait; a busy control may stay focusable with `aria-disabled` and ignored activation instead of native `disabled`. Never steal focus when the user moved elsewhere or the window lost focus during the wait, and never move focus into another result's controls.
- [ ] Retry recoverable failed writes with one timer and bounded backoff: initial target 2, 5, 15, then 30 seconds maximum between retries while dirty. Manual retry triggers promptly without duplicating an active write. Reset backoff on success, suspend when clean, and avoid notification/log floods. Invalid/future history must not be overwritten by retry; offer accurate guidance rather than claiming that freeing disk space fixes every storage error. A rejected or timed-out write retains the in-memory snapshot and cannot resurrect older data or create a second writer.
- [ ] Integrate quit and relaunch through 025's coordinator. Stop admitting new captures, drain media safely, then attempt the latest metadata save with a bounded wait (initial target 5 seconds, measured during implementation). Repeated requests join the same attempt. On failure show the affected reminder count and identifiable times/reasons, with Retry / Stay in app. Offer a clearly worded “Exit without saving these reminders” only after all media work is safe and no metadata write can still publish; never treat a timed-out or abandoned promise as proof that OS I/O stopped. A hanging write keeps the app open with honest status. Cancel restores admission safely; relaunch uses the same rules. OS force-quit/power loss remain outside guarantees.
- [ ] Define settings loading/saving/retry/quit feedback in English and Traditional Chinese. No automatic OS notification replay, no fake saved status, and no implicit acknowledgement on exit. Document that volatile unsaved metadata may be lost on forced termination and that background work does not increase disk throughput.
