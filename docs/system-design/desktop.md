## Tray and notifications

Sources: [tray-model.ts](../../src/main/tray-model.ts), [tray.ts](../../src/main/tray.ts), [index.ts](../../src/main/index.ts).

TrayModel is a pure projection containing icon, title, tooltip, and a flat list of commands; preferences are not in the tray at all, so what the model returns is exactly what the menu shows. AppTray maps it to Electron without a separate business state machine. What a left click does is the user's choice (`trayClick`, Settings → General, 2026-10-04): open the same menu, as menu bar icons usually do, or toggle recording — start, and during the countdown, or once a start has lasted a second (plan 065), cancel. A new install opens the menu; a settings file from before the choice keeps the click that records, the behaviour its user learned. Right-click always builds the menu from current state and settings. Hovering over the tray icon shows the current status in the native tooltip, with the notes it holds back (a deferred quit, an error box waiting) and the unread failure count; it says nothing about clicking, which the user's own choice decides (2026-10-04, formerly “Click to open the menu” or “Right-click to open the menu”, and “Click to cancel.” during a countdown). Windows shows only the first 127 characters of a tooltip, so a longer one is cut there with “…”; the menu repeats every line in full. On macOS a left click that opens the menu attaches it with `setContextMenu` on the press (Electron's `mouse-down`, emitted before it looks for an attached menu), so macOS opens it there with the item highlighted once: popped from the click with `popUpContextMenu`, it opened after the release and Electron pressed the item again, and the highlight blinked on, off and on (2026-10-05). The menu comes off once it closes, or at once if it did not open. It never stays attached: an attached menu opens on every left click regardless of the choice, and Accessibility reports it as an open menu, which `pnpm acceptance:tray` read as a menu that never closed, with each of its polls logged as an opening (2026-10-05). VoiceOver's press reports the click first and pops the menu as before; the click that records, and Windows, attach nothing. The [global shortcut](#recording-shortcut) always toggles, whatever the click does.

| State | Icon/title | Tray commands | Preferences in Settings |
| --- | --- | --- | --- |
| needsPermission | Ring/empty | Permission guidance; Open System Settings and "Already allowed? Relaunch RecordStuff", or only Relaunch once capture was refused despite the grant | All editable |
| idle | Ring/empty | Ready, folder unavailable or display unavailable; Start recording (the toggle's start, countdown included); Change output folder… only while the folder is unavailable, otherwise Use Primary display while the chosen display is unavailable and a primary exists | All editable |
| starting | Hourglass/empty | Permission-prompt guidance; Cancel recording (tooltip names the shortcut when registered, as in the countdown) | Language, appearance and icon click; About links stay available |
| countdown | Stopwatch/empty | "Recording starts in n s" (disabled); Cancel recording (tooltip names the shortcut when registered) | Language, appearance and icon click; About links stay available |
| recording | Filled dot/`REC` | Stop (tooltip names the shortcut when registered) | Language, appearance and icon click; About links stay available |
| stopping | Hourglass/empty | Saving | Language, appearance and icon click; About links stay available |

Every menu follows one group order (plan 048), omitting a group with nothing to show so that no separator leads, trails or doubles and an item never changes places between states: the state (its status line, idle's last display failure, and its primary action: Start recording, Stop, Cancel recording or the permission steps; since 2026-10-05 the status line shows only when it says more than the action under it, so a plain Ready, the countdown's seconds, which an open menu would leave stale, and Recording, which `REC` and Stop already say, are left to the tooltip, while the chosen display, an unavailable folder or display, Starting, Saving, the permission and quit lines stay); unread failures ("Unreviewed recording failures: n" and View recording failures…, only while any is unread); the window (Open RecordStuff and Show last recording, with the shortcut explanation under them when its shortcut is unavailable); and Quit RecordStuff. Since 2026-10-04 the menu keeps only what is to be done now: the output folder, Change output folder…, the folder-revealing Show last recording, the way back to reviewed failures and Show log moved into RecordStuff (Recordings' Show in Finder and newest-first list, Recording settings → Output folder, the Failures tab, General → Troubleshooting), and Change output folder… returns to the state group only while an unavailable folder is what stops the next recording, as Use Primary display does while the chosen display is unavailable (2026-10-04, the fix the Settings card and Screen row already offered). Show last recording came back the same day as a way into the window, offered in every state beside Open RecordStuff: it lists the output folder afresh and opens RecordStuff on Recordings with the newest recording (the tab's first card) scrolled into view and its Play button focused, as the saved notification's click does for its own file, never the folder; an empty or unreadable folder opens the tab on what it shows. Open RecordStuff replaced Settings…, since the window holds the recordings as well. Reviewed failures no longer head the menu, and the "Recent failure" line is gone. Start recording, Stop and Cancel recording show the registered recording shortcut, and Open RecordStuff the shortcut that opens it, as native right-aligned accelerators with `registerAccelerator: false`, so the menu never registers a second global shortcut; an unregistered shortcut shows none, and the tooltips stay. A Start recording chosen from an open menu after the state moved on does nothing and is logged (`Recorder.startIfIdle`). Settings is never disabled for a recording: the panel itself says which preferences are locked. While the tray shows a quit in progress (below), only Quit stays enabled, because a quit in progress ignores every other action and stops capture itself. RecordStuff's window does the same: its Quit RecordStuff stays and every other control is disabled, so either Quit can still turn a Relaunch waiting on a save into a plain quit. Each state has its own 16 pt template (plan 040): the hourglass replaced the ring plus `…` title for starting and saving (a ring with three small dots inside was tried first and read as too faint at menu-bar size), and the countdown shows a stopwatch with no title because the corner of the recorded screen carries the digits. Only `REC` changes the item width. The unread-failure badge still replaces only the idle ring. An open menu does not follow the state: on macOS 26 with Electron 44.3 a menu shown by `popUpContextMenu` keeps its items while open, and neither changing them nor `closeContextMenu()` affects it (an isolated probe, 2026-09-27), while main's timers keep running. Rebuilding it would cost nothing; the platform does not allow it. So each choice is resolved against the current state when clicked: a Cancel recording from a menu opened during the countdown that is chosen after capture began stops the recording, which is saved. While a quit waits for recording work or the history save for longer than 0.3 s, a settled tray shows the hourglass and "Quitting once the recording is saved or cleaned up…", or, once recording work has settled, "Quitting once settings and failure history are saved…", until the app exits, the quit is deferred with its notification or the user stays (plans 035 and 055). Exit cancels that pending status, and a destroyed tray ignores later updates, because the modal unsaved-history prompt can delay the timer past teardown (035's D4). macOS uses template PNG/@2x assets and a title. Windows shows no title, so its ICOs carry the state alone (plan 034). An ICO has no template mode, so every state sits on the app icon's dark rounded base with a grey rim, and one image reads on light, dark and accent-coloured taskbars. Idle is a white ring with an empty centre; recording adds a red centre, which differs in shape and grey level, not only in hue; the warning puts an amber "!" inside the ring; busy and countdown keep the hourglass and stopwatch, whose hand stops short of the ring so it does not read as a power symbol. Each ICO holds 16, 20, 24, 32 and 48 px entries drawn on the pixel grid, for the 100/125/150/200% notification-area scales. A candidate without the base needed a dark outline that turned the ring into a thin double line on a light taskbar. The artwork has not been seen on a native Windows taskbar yet; the maintainer accepted that as untested when closing [035](../verification/history-2026-09.md#plan-035-closure--2026-09-28) (N17). REC and the stopwatch may appear in full-display recordings; this is an accepted visibility tradeoff.

### Countdown overlay

Sources: [countdown-overlay.ts](../../src/main/countdown-overlay.ts), [renderer/countdown.ts](../../src/renderer/countdown.ts), [preload/countdown.ts](../../src/preload/countdown.ts), [shared/countdown.ts](../../src/shared/countdown.ts).

During the countdown ([recording design](recording.md#countdown)) a transparent square window 16 pt from the right edge of the recorded display's work area and 12 pt below its top draws only the digit: no background, box, border, ring or blur. Its size follows the recorded display (plan 045): the digit's font size is 14% of the shorter side of the display's bounds in points, clamped to 56–216 pt, and the window's side is the font size × 88 / 56 rounded to whole points, 040's ratio, so "10" still fits. The whole display rather than the work area sets it, so the Dock cannot change the digit, and a portrait display gets the same digit as the same panel in landscape. For example, a 1920 × 1080 or 1080 × 1920 display gets a 151 pt digit in a 238 pt window, a 14-inch MacBook Pro's 982 pt default 137 pt in 216 pt, and a short side of about 1543 pt or more the 216 pt maximum in 339 pt; only a short side of 400 pt or less falls back to 040's 56 pt digit in its 88 pt window. Main creates the window at the primary display's size and sets the recorded display's bounds before it sends the first digit; the window's size is all the page receives. It is placed on the display DisplayMedia resolved for the session, or on the primary display (logged) when that is unknown. The window is created during preparation and destroyed when the countdown ends, is cancelled or fails, so none remains between recordings; the app destroys it again on every settled state as a safety net. It is frameless, fixed, shadowless, absent from the taskbar, not focusable, shown inactive as a non-activating panel on macOS, ignores the mouse, and sits at the `screen-saver` level on every Space, including full-screen ones. It never activates RecordStuff or takes keyboard focus. The page is local, sandboxed and context-isolated under the settings page's CSP; its preload exposes only a value subscription, main sends the digit or `null`, and the page cannot reply. With the countdown sound on (plan 046) main loads the page with `?sound=1`, the page creates one `AudioContext` when it loads and synthesizes a tick with Web Audio for each new digit (none for a repeated value, `null` or a cancel); destroying the window silences it, and the window sets `autoplayPolicy: "no-user-gesture-required"` explicitly. The tick follows the system volume and mute; if audio fails, the digit continues silently.

The digit is SF Pro Rounded semibold, tabular and centred, sized from the window through `vmin`, white at 28% alpha with an outline of black at 10% and three soft shadows, both in `em` so they scale with the digit and at 56 pt equal 040's 1 px outline and shadows; its own outline and shadows carry legibility over white as well as dark content. The maintainer compared drafts at 80, 55, 40 and 28% and chose the most transparent, accepting that it fades on bright photos. It fades in over 120 ms, crossfades between digits over 150 ms and fades out over 120 ms before the window is destroyed; `prefers-reduced-motion` removes the fades and `prefers-reduced-transparency` makes the digit opaque with a stronger outline, still without a background. No content protection is applied: `getDisplayMedia` offers no per-window exclusion, so separation in time is the protection. VoiceOver does not reliably announce a window that cannot take focus; that is recorded as observed, not claimed as support.

Native notifications are localized and silent. Saved notifications reveal the completed file; when the disk guard ended the recording they say so ("Saved {file}. Stopped early: the disk is almost full."), as they do after the Mac went to sleep ("Saved {file}. Stopped because the Mac went to sleep."; elsewhere "…the computer went to sleep."), and the recording stays a success outside failure history ([recording design](recording.md#file-completion-and-failure)). Between `powerMonitor`'s `suspend` and `resume` every notification is held, because a banner shown during sleep is gone before the user is back; after `resume` they are shown in order at the first 1 s check that finds user input within the last 2 s (`powerMonitor.getSystemIdleTime()`), or at once on `unlock-screen`, and the notification switch applies when they are shown. A maintenance wake has no input, and timers keep counting during sleep, so neither a resume nor a timeout alone releases them (plan 050). Recording failure notifications always open Recording failures in Settings, where the confirmed outcome and recovery actions are shown; they are held and dropped like the capture notices below, and the unread failure row and its tray menu entry remain when one is dropped. Quality/language save failures and frame-rate downgrade notifications are informational. What a session learns when capture starts — the resolution cap it could not confirm, a frame rate below the request — is held until the session settles and then shown once, like the saved notification 500 ms later on macOS, because macOS can decide `display shared` and mute a banner while the display is being recorded ([timing record](../verification/history-2026-09.md#saved-notification-timing--2026-09-20)); a new session or a quit before then drops them, and the log names each held, shown or dropped notice (plan 053). The cap warning is also shown in Settings at once; the frame-rate downgrade has only the notification and the log.

A saved notification's click opens RecordStuff on Recordings with that recording in view (2026-10-04): the folder is listed afresh so the new file is there, its card is focused and outlined in the brand red for a moment, and nothing plays. The log says `notification: show saved <path>`, then `show last recording: Recordings with <path>`. On macOS a notification click also asks the system to activate the clicked app; that activation once pushed Finder back behind the user's window when the click revealed the file there (the v0.1.0 report, which plan 014 answered with a second reveal after `did-become-active`). Opening the app's own window, the activation is what brings it forward, so that retry and its one-second window are gone. A save in the background opens nothing. Unsupported notifications and failed events are logged. OS notification preferences still decide whether a banner is visible. Native evidence is recorded by `pnpm acceptance:notification` ([tooling](tooling.md#notification-acceptance)). The notification icon was confirmed normal after the user's reboot on 2026-09-14.

`AppTray` retains each native `Notification` until `click`, `close`, or `failed`; `show` alone does not release it. Shutdown closes outstanding notifications and clears ownership; a synchronous `show()` failure releases the object and is logged. This keeps callbacks reachable after `show()` returns: Electron 44.3.0's [notification wrapper](https://github.com/electron/electron/blob/v44.3.0/shell/browser/api/electron_api_notification.cc) is garbage-collected and clears its native delegate on destruction. This lifecycle fix does not establish the cause of the historical undelivered click. There is no timer-based eviction; notifications without a terminal event remain owned until shutdown. Windows Action Center lifetime is not fixed or verified here: a Windows `close` event may be only a banner timeout while its history entry remains clickable.

Saved notifications are scheduled by `SavedNotification` after file finalization and idle, with one 500 ms timer on macOS; other platforms request immediately. This gives macOS time to clear the capture-related notification suppression state. It is a measured heuristic, not a readiness signal or delivery guarantee: Focus, another capture, and notification preferences still apply. Starting a new recording cancels the old pending notification permanently; a permission-recovery state (needsPermission) counts as settled, so a completed save is still announced there (the permission notice does not replace it); quit admission cancels it and suppresses saves during that attempt. A deferred quit restores future delivery without replaying suppressed saves. No queue or retry is retained. Notification request exceptions are logged without affecting the saved file. Saving and idle never wait for notification delivery. See [timing evidence](../verification/history-2026-09.md#saved-notification-timing--2026-09-20).

## Settings window

Sources: [ui-model.ts](../../src/main/ui-model.ts), [settings-model.ts](../../src/main/settings-model.ts), [settings-window.ts](../../src/main/settings-window.ts), [renderer/settings.ts](../../src/renderer/settings.ts).

The tray keeps the commands that must stay one click away; every preference lives in one separate, sandboxed window. Settings opens it or focuses the existing one. On macOS, while the window is open, RecordStuff is also an ordinary app (2026-10-04, at the maintainer's request; [app-menu.ts](../../src/main/app-menu.ts)): it has a Dock icon, and the menu bar shows its menus with a Record menu holding the tray's state actions (Start recording, Stop recording, Cancel recording or the permission fixes, with SF Symbols and the registered shortcut) and Show last recording; the Dock icon's menu offers the same items. macOS shows an app's menus only while it is a regular app, which always brings a Dock icon, so both go when the window closes. The menus are in the app's language, and they keep the key equivalents the window relies on (Quit, Hide, copy and paste, Minimize) without Close or Zoom. The bundle declares no `LSUIElement` (2026-10-05, at the maintainer's request): main hides the Dock icon as the app finishes launching (`will-finish-launching`) and again once ready, so RecordStuff starts as a menu-bar app, and reopened from Finder or Spotlight it now brings its own menus every time (3 of 3 probes), where with `LSUIElement` macOS had made it active while still a menu-bar app and kept the previous app's menu bar (0 of 3). Closing the window, or Hide RecordStuff (⌘H, which hides the window as it is, keeps hidden a window whose first paint is still pending, and first tells the page, `settings:hidden`, so the player stops rather than sounding from a window out of sight, even when a full screen the viewer left playing answers after the hide), leaves only the menu bar's icon: no Dock icon and no menus stay behind; the window comes back as it was when opened again. A Dock icon still visible 0.3 s and 1 s after it was hidden is hidden again, since a hide that landed while macOS was still making the app regular (⌘H as the window loads) was undone when that finished (3 of 3 before, 0 of 3 after). Only Quit ends RecordStuff: the tray's Quit RecordStuff, ⌘Q or the Dock's Quit while the window is open, and Quit RecordStuff in the window itself, the only row at the sidebar's foot (a power mark beside the links in General's narrow footer); every one goes through the same quit, which waits for a recording to be saved. The Record menu leaves out the tray's state lines, so a countdown does not rebuild a menu held open every second, and it names the shortcut only while that is registered: a menu's shortcut is also a key equivalent, which would start a recording while the editor records a new shortcut. The app focuses itself before the window shows, because a menu-bar app does not come forward when it merely shows a window. A new window stays hidden until the page reports that its first view, or its failed-read message, is painted: Electron's `ready-to-show` is the first frame, painted before the page has read its view, so showing then flashed an empty window for one frame. A page that never reports is shown one second after `ready-to-show`. Changes save immediately and the window stays open; a language change relabels it and retitles it in place. Closing it — including with Escape or the platform close shortcut, which the panel handles itself because the application menu has no Close item — leaves the menu-bar recorder running. The close shortcut is exactly ⌘W on macOS and Ctrl+W elsewhere, with no other modifier; one predicate serves the page and the shortcut editor, so macOS ⌃W and ⇧⌘W stay capturable. ⌘W itself never becomes the recording shortcut: the editor closes on it, and the validator reserves `CommandOrControl+W`, so a hand-edited settings file falls back to the default too. The typed character decides, as native menus do, and the physical W key counts only where the layout types no Latin letter there. If the page's renderer process dies, main disposes that window rather than keeping a blank one, and the next Settings open creates and loads a new window; it never reloads by itself, so a page that keeps crashing cannot loop. Close, blur and crash events act only on their own window instance, so a late event from a disposed window cannot clear its replacement. Capture still uses its own hidden renderer.

[settings-model.ts](../../src/main/settings-model.ts) declares every preference once, with stable group and choice ids, and is the only place that knows what a choice does. It produces both the view the panel renders and the answer to "is this request allowed right now". The tray model is a sibling projection of the same state and context, not a source the panel reads from.

Main owns committed preferences; the panel only retains pending user choices. It renders the view it is given and sends back a group id and a choice id — never an action. Main refuses any sender but the panel's own main frame, resolves the pair against a freshly built model, and only then calls the same action handler the tray uses, which re-checks the recording state before saving. Starting, counting down, recording and saving lock every preference except language, appearance and the icon click, in the panel and again at that boundary. Saves are serialized in request order, so a second change waits instead of being reported as a failure. While saves are pending, controls display committed values from main, with non-layout save status and per-row aria-busy; newer user intent remains queued independently of older replies and pushes, and other groups remain locked until all requests settle. It then shows committed values, with an inline message when the latest choice did not take effect, and a shortcut the OS refused keeps its selection plus a note saying it is inert. A group may also carry `actions`: buttons rendered under its control, for a system pane that can override the preference in the same card. A choice in an actions group, or in that `actions` list, has no committed value to compare against, so its handler reports its own outcome as a boolean and that is used verbatim; every other choice is still judged by whether the requested value is the committed one, so a handler that reports nothing can never turn an unsaved change into a success. The control being changed stays live while its neighbours go inert, because a disabled element cannot hold keyboard focus. For the same reason a busy action button — while its own request runs, while another save is pending or while an update check is in progress — keeps `aria-disabled="true"` and the saving look instead of `disabled` and ignores activation until it settles, so Check for updates…, Retry shortcut registration or Open notification settings… activated from the keyboard keeps focus and the next Tab continues from it (plan 053). Main marks a running check `busy` rather than unavailable and still refuses it; only a choice main does not offer is natively disabled, as the failure-row actions already were. The preload exposes only read, choose, capture, change subscription and the one-time ready report; the one string the panel can need before its first view — a failed initial read — is localized from the language main puts in the page URL.

The Recording settings tab contains screen selection, the countdown (Off, 3 s, 5 s or 10 s as a segmented control, whose ⓘ says how to cancel: a click on the menu bar icon, or Cancel recording in its menu when the click opens the menu, and the shortcut while it works), the countdown sound (plan 046: a switch, on by default, whose ⓘ says the tick is not recorded; disabled while the countdown is Off, which keeps its value), video quality, resolution cap and frame rate, with ⓘ explanations distinguishing encoding quality from pixel dimensions. The Recording tab's Output folder row, after Screen (plan 048), shows the path with Change… and Show in Finder through main's own folder actions and locks, which the status card's fix and the menu's Change output folder… (offered only while an unavailable folder stops the next recording) share. A session locks Change… only: showing the folder touches nothing it holds, so Show in Finder stays available, as on the Recordings tab and its cards (2026-10-04). File name format (2026-10-05) follows: a text field holding the pattern new recordings are named by, with `{date}`, `{time}`, `{year}`, `{month}`, `{day}`, `{hour}`, `{minute}` and `{second}` replaced by the local time a recording is requested at ([file-name.ts](../../src/shared/file-name.ts)); its note is an example, which follows the draft while it is typed, or says what is wrong with it. Enter or leaving the field saves it, Escape puts the saved one back. Main validates every pattern it is sent: it must hold `{time}` or `{second}`, so each recording gets its own name (a name already taken still gets `-2` and on), no other placeholder, and nothing a file system refuses (`/ \ : * ? " < > |`, control characters, a leading dot, a leading space or a trailing space or dot, Windows device names with or without an extension, more than 120 characters or 200 UTF-8 bytes, so a suffix and `.recording.mp4` still fit a 255-byte name); a refused one says why under the row. It is locked while recording like the other recording settings; a session reads it once, as it starts. General runs the icon's click (“Icon click”: Open the menu or Start / stop recording, whose ⓘ says a right click always opens the menu; never locked, since nothing a session holds depends on it), Shortcut, Notifications, Language, Appearance, Updates, Troubleshooting (Log file) and the About footer, everyday preferences before maintenance (plan 048). The last tab, Failures (“失敗紀錄”), holds the recording failure history ([below](#recording-failure-results)); it is always present, its label carries the unread count, such as “Failures (2)”, drawn as a badge, and its accessible name gives the full name and the count. The four tabs never wrap: the sidebar lists them, and in a narrow strip the open tab shows its name while the others show their icons and keep their names for assistive technology, so they fit the 380 pt minimum in both languages. General's tab is a gear (2026-10-05, formerly sliders), as macOS System Settings draws it. ⌘+ and ⌘- (Ctrl elsewhere) zoom the window's page a step between 80% and 150%, and ⌘0 returns to 100% (2026-10-05): main reads the keys before the page (`before-input-event`), the page's zoom is isolated from every other page of the same origin, so the full-screen video and the countdown keep theirs, and the factor is saved beside the window's size in `settings-window.json`. On macOS a View menu lists the three without binding their keys. Tabs support arrow keys, Home and End across all four and remain selected across preference changes; a new window opens on [Recordings](#recordings), an open window keeps its tab, and an explicit failure entry selects Failures, as the shortcut banner selects General, the capture-warning banner selects Recording, and a saved recording's notification selects Recordings with that recording. Each tab keeps its own scroll position for the life of the window: switching away stores it, switching back restores it once the panel, failure rows included, is complete, a first visit starts at the top, and a background update within the tab keeps its position. The offset is applied after everything above the content has settled, so scroll anchoring cannot move it. Update commands use buttons and report completion separately from saved preferences.

The 960×640 settings window (minimum 380×360) has two layouts (2026-10-04). From 600 px wide, a sidebar holds the brand, the four tabs as a list (icon, name, unread badge) and the status card at its foot, beside the open tab's content under its name; on macOS the title bar is hidden (`hiddenInset`), the window controls sit inset in the sidebar and a 40 px strip along the top drags the window, while the native title still names it for the window list and accessibility. Narrower windows put a segmented tab strip, then the status card, above the scrolling list. In both layouts the card follows the tabs in the page's order, so the first Tab reaches the tabs, then the card, then the content (2026-10-05; until then the card came first even where the sidebar draws it at its foot); on macOS their title bar strip, 48 pt high and still a drag region, shows the RecordStuff mark and name centred and level with the window controls, and the tabs start below it (2026-10-04). Rows put their control under the label when the content column, not the window, is narrower than 440 px (a container query), so both layouts share one row style. A size stored before the sidebar was chosen for the tabs-on-top layout, so every window opens once at the new default; sizes saved since carry `layout: 3` and are kept, a narrow one included. Main declares optional `control`, `section` and `noteKind` fields: Notifications, the countdown sound and startup update checks are native checkbox switches; countdown, quality, language and appearance use native radio segments, Appearance's drawn as three icons — a screen for the system's choice, a sun and a moon — each named by its label for assistive technology and in its tooltip (`iconChoices`, 2026-10-05, formerly a menu); other preferences retain native popup menus. Omitted fields preserve menu/explanation defaults. A line under a control is kept for what the user needs to see at once: a status (notifications off, the update result), the output path, the shortcut editor's limit and diagnostics. A secondary explanation is the optional `info` field instead, behind an ⓘ button beside the label: hover and keyboard focus show it while they last, a click pins it until another click, and Escape, losing focus or the window going inactive close it, an open one taking the first Escape before the window does. It is a `popover="manual"` in the top layer, placed above the button (below when there is no room), so it covers the row before rather than the control it explains, inside the window and following it as the panel scrolls; a transparent bridge over the 6 px gap keeps it open while the pointer crosses slowly, so the scrolling list cannot clip it, and its text stays in the control's `aria-describedby` whether shown or not. Explanations that only restated a label (the screen menu, what a notification is, where the digits appear) were removed (2026-10-03). Consecutive section ids share an inset list headed on its first row: Recording groups Source and output (screen, output folder), Before recording (countdown and its sound) and Video (quality, resolution cap, frame rate); General groups Controls and notifications (icon click, shortcut and notifications), Language and appearance, Updates, whose manual row is labelled Manual check so it does not repeat the heading, and Troubleshooting (the log). Rows share one line height whatever their control, and each preference row leads with a line icon in a small tile, so a row is found by its shape before its label is read; its note, text link, diagnostics and shortcut editor start under the label, past the icon. Segments are drawn like the tab strip, a recessed track with the selection raised, so fill is left to switches (Apple Music's red when on) and the ink of the status card's fix, Confirm and Download (the one action an update result is for). Menus draw their own chevron from a wrapper, since a select has no pseudo-elements. A row's extra action, such as Open notification settings… or Retry shortcut registration, is an underlined text link under it. A move that fails lists the file again and says so under the header until the next action. Meanwhile the file is still in the folder, where Finder shows it.

The player is a modal `<dialog>` that only plays: a 16:9 stage sized by the window alone, as YouTube's is — as wide as 860 px, the window less its margins, or its height allows, whichever is least — in which the recording fits, black above and below when it is wider and beside it when narrower (a Mac's screen, a portrait clip), so the stage neither grows when the recording's size arrives nor changes shape from one recording to the next (2026-10-05; until then the video's own shape set the dialog's height, from a 220 px start); the video alone, with its own controls laid over the picture as YouTube's full screen lays them out (2026-10-05, [player-controls.ts](../../src/renderer/player-controls.ts), shared with the full-screen window; formerly Chromium's controls with the name and buttons on a bar beneath). Along the top, on a shade, its name with its file name, length and size, and Close; along the bottom, on a shade, a seek bar the picture's width that thickens under the pointer, then play/pause, a mute button whose volume slider slides out beside it, the time as `0:02 / 0:08`, and Full screen at the right end. While it plays and the pointer rests for 2 s the shades, controls and pointer step aside, as they do when the pointer leaves it; a move, a press, keyboard focus on a control or a pause brings them back, and they stay while it is paused. A click on the picture plays or pauses; YouTube's keys work wherever focus is in the player: Space or K plays and pauses, ← and → move 5 s, M mutes, F plays full screen, and a focused control keeps its own (Space on a button, the arrows on the volume slider); on the seek bar the arrows, Up and Down move 5 s too, Page Up and Down 10 s, and Home and End go to the start and the end, where its own steps would move 1% and 10% of the length. The seek bar and volume are native range inputs, named and with the time and the percentage as their value text, and the seek bar follows `timeupdate`, which fires only while the video plays, so a paused or idle player runs nothing. On macOS it centres in the space below the 48 pt title bar strip, so however small the window, its corner, title and picture never lie under the window controls (`TRAFFIC_LIGHT_ZONE`); while it is open that strip stops dragging the window, since a drag region takes the click at the system's level before the page sees it, so a click on the backdrop above the player closes it too, and closed the strip drags again. Escape, Close or a click on the backdrop closes it, before the window's own Escape, and closing pauses and releases the file. Full screen, a double-click on the video, or the page's own fullscreen should it start anyway, plays the recording in a window of its own ([video-fullscreen.ts](../../src/main/video-fullscreen.ts), 2026-10-05): RecordStuff's window keeps its size, where the page's fullscreen had to grow it to the screen and shrink it back, white where the picture had not yet followed. The new window is frameless and black over the whole screen RecordStuff's window is on; it starts hidden at that size, takes the simple fullscreen on macOS (nothing grows, no Space opens, the menu bar and the Dock step aside) or is created fullscreen elsewhere, and fades in over 150 ms once its page has drawn the first frame at the player's time, or after 2 s for a file it cannot decode. It plays on with the player's time, volume and mute under the same controls, larger, and the recording's name over the top edge, which main writes into the page's query from the listing (`title`), never taken from the page; its way out (Exit full screen) sits at the bar's right end where Full screen was, and the controls step aside with the pointer after 2 s at rest while it plays. Escape, ⌘W, a double-click, F or that button leaves: the window's video stops first, so the two never sound together, and main hands the time, play state, volume and mute back at once, so the player seeks and resumes under the window as it fades out over 150 ms and closes, and RecordStuff's window takes focus again. Main resolves the source from the listing by id, never from the page. Only one plays at a time, and it ends at once, with no fade and no state, when RecordStuff's window closes or hides, leaving the player paused where it was, and a window the viewer left that is still fading out goes at once too, then or when a new one plays; only a window the viewer left, or whose page died, gives RecordStuff's window its focus back; a fullscreen page whose renderer dies closes its window, giving the menu bar and the Dock back. Escapes in the second after it ends, and every repeat of a held Escape, are dropped in main (`before-input-event`), because Chromium turned one into a close request that shut the player without a keydown the page could refuse. A held Escape, and any press within 1 s of one that closed the player (marked on the dialog's `cancel`, which both ways reach) or of the fullscreen's end, closes nothing, so pressing again and again closes one thing at a time; extra presses after the page's own fullscreen used to close the player and then the window. A recording it cannot play (gone since the listing, damaged, or a format Chromium does not decode) says so in the player and points to Open in its card's menu. A recording moved to the Trash, here or elsewhere, closes its player and menu and leaves the list; the Trash keeps it recoverable, so there is no confirmation. When the card or its playing player had focus, the card after it takes focus, else the one before, else the tab, also while the window is inactive (deleted in Finder), as a removed failure row hands its place on; leaving the Recordings tab closes the card menu.

The sandboxed page never holds a path. Main lists the folder into ids (a hash of the path) and registers one privileged, streaming scheme, `recordstuff-media:`, which serves `video/<id>` with byte ranges, so the player can seek, and `thumb/<id>` as JPEG, for listed ids only; the page's CSP allows images and media from it and nothing else. File actions arrive as group `recordingFile:<id>` and resolve only for a listed id and an offered action, outside the preference save queue, so a drag starts while the pointer is still down. Lengths are read from the MP4 boxes rather than by decoding: the capture host writes fragmented MP4, whose `mvhd` says 0, so the length is the last complete fragment's `tfdt` plus its `trun` sample durations (or the `tfhd`/`trex` defaults) in its track's timescale; only box headers are read on the way. The folder is listed when Settings opens or regains focus, while the window is open after a recording is saved or the output folder changes (with it closed nothing would show the listing, and opening it lists the folder anyway), when its saved notification opens Recordings (before the recording is selected), after a move to the Trash and after a file action that failed, so a reply already shows a recording that left the folder. While the window is open the folder is also watched (`fs.watch`, FSEvents on macOS, event-driven and never polled): a video that appears, changes or leaves it, deleted in Finder for example, is listed again 250 ms after the burst of events ends, while a recording's growing `.recording.mp4` and other files are ignored; the watcher goes when the window closes or is hidden (⌘H), so the idle menu bar app watches nothing and runs no timer. A folder that cannot be watched, such as some network volumes, is still listed at the moments above. One listing reads the folder at a time; requests made meanwhile (opening Settings asks once for the show and once for the focus it brings) share one more listing after it. Lengths not yet known are read after the listing is shown and published as they are read, at most every 500 ms, so a folder of long recordings fills in as it goes; a folder that cannot be read says so instead of looking empty.

## Recording shortcut

Sources: [hotkey.ts](../../src/main/hotkey.ts), [shortcuts.ts](../../src/main/shortcuts.ts), [shared/hotkey.ts](../../src/shared/hotkey.ts), [index.ts](../../src/main/index.ts). Plan 016 added a global start/stop shortcut so recording can be toggled while another app is frontmost and so unattended acceptance has a system-level entry point on a process with no window.

RecordingHotkey wraps Electron `globalShortcut`. A press calls the same `toggle` function as a tray click that records, so `Recorder.toggle()` remains the only decision point: it starts when idle, cancels a countdown, stops when recording, re-issues the permission notification in needsPermission, cancels a start that has lasted a second as Cancel recording does (plan 065), and ignores presses within that first second and while stopping. Every press is logged as `hotkey: <accelerator> pressed` before the toggle, and an ignored one also as `recorder: session <id> toggle ignored while starting (<n> ms after the start)` or `… while stopping …`, so a press that did nothing is visible in the log ([recording design](recording.md#countdown)). `apply(settings)` releases the previous registration before registering the new one, so a change never leaves two combinations active; `dispose()` runs on will-quit.

The user chooses one recommended shortcut, Custom shortcut… or Off from **Settings → Shortcut** (idle/needsPermission only, like quality). The default is `CommandOrControl+Shift+1` (⇧⌘1 on macOS, Ctrl+Shift+1 elsewhere), set by maintainer decision on 2026-09-21. A global shortcut wins over the frontmost app, so the default has to be a combination no common app expects. The obvious mnemonic ⇧⌘R was rejected twice for that reason: the 2026-09-19 conflict check found it bound to hard reload in Chrome and Firefox, Reader in Safari and local recording in Zoom, so pressing it in a browser starts a screen recording instead of reloading. Existing users keep it as their current custom value; it is no longer a suggested option. Digits are the quieter range — macOS owns ⇧⌘3/4/5 for screenshots and screen recording, and apps bind plain ⌘1…9 for tabs and view modes rather than the shifted form — but ⇧⌘1 has not been through the same app-by-app check; that belongs to native acceptance. `CommandOrControl+Alt+Shift+R`, the previous default, was verified unbound in Chrome, Safari, Firefox, Finder, Xcode, VS Code, Slack and Zoom as of 2026-09 and remains valid for existing users without being offered as an alternative. Every accelerator an earlier version shipped stays valid, which a compatibility test checks; the menu offers only `DEFAULT_HOTKEY`. Custom values pass `validateAccelerator`: at least CommandOrControl or Control, optional Alt/Shift, one supported key, no duplicate modifiers, at most 64 characters, and a short macOS reserved list. Canonical order is CommandOrControl, Control, Alt, Shift, key. Unsupported stored values still fall back with a warning.

Custom… records physical letter/digit/function/punctuation key codes and named Space/arrows; on Windows a letter key records the letter it types, as below. Unsupported codes, including numpad keys, are refused. Shifted punctuation aliases normalize to Shift plus the base key before reserved-combination validation. Reserved combinations follow the platform (plan 064): macOS reserves ⌘Tab, ⌘Q, ⌘W, ⌘Space, ⇧⌘3–6 and the clipboard screenshot forms ⌃⇧⌘3, ⌃⇧⌘4 and ⌃⇧⌘6 ("macOS reserves this combination."); elsewhere Ctrl+Tab, Ctrl+Q and Ctrl+W are refused whether Ctrl arrives as `Control` from the editor or as `CommandOrControl` ("Other apps use this combination."), and a chord without Ctrl says "A shortcut needs Ctrl.". On both, the editing keys every app shares are refused with "Other apps use this combination.", since a global shortcut on one would take it from every app and pasting would start a recording: ⌘X, ⌘C, ⌘V, ⌘A, ⌘Z and ⇧⌘Z on macOS (⌃ is a key of its own there, so ⌃C stays a choice), Ctrl+X, C, V, A, Z, Y and Ctrl+Shift+Z elsewhere; a saved one falls back to the default with a warning, like any unsupported value. The same platform check validates a saved settings file, so `CommandOrControl+Shift+3` and `CommandOrControl+Space` survive in a Windows file, where they mean Ctrl, and fall back to the default in a macOS one, where they mean ⌘; macOS `Control+Shift+3` and `Control+Space` stay valid as before. The shortcut group is the only value-carrying control; main revalidates and canonicalizes its candidate before saving. Escape, Tab/Shift+Tab navigation away, clicking elsewhere, window blur/close, renderer failure and a 15-second timeout cancel capture. The editor states the 15-second limit; an unsubmitted timeout leaves a visible, localized message explaining that the shortcut is unchanged and how to edit again, and the same message is announced. A submitted save may outlive the lease and never receives that timeout warning. Main suspends the OS registration before acknowledging arming, then restores it on completion or cancellation; quit disposes it. Each capture is a lease owned by the window that armed it, separate from the setting transaction it may start. Cancel, blur, timeout, close, renderer failure, a recording lock and quit release it at once — even while a confirmed save is still writing — and restore the registrations committed at that moment. Release is idempotent; a late event from an older window, or an older save completing, ends only its own lease and never a newer window's capture. A confirmed save runs to completion after its window closes or crashes; an unconfirmed draft is never submitted. `AppShortcuts` owns both registrations and the persist-then-register order below. Recording locks the group. Invalid candidates show a localized reason and leave settings unchanged; the Settings combination is refused the moment it is pressed, like the other reserved ones, so the editor stays open for another try, and main refuses it again. Off preserves a custom accelerator as a selectable option. The capture button is keyboard reachable; its accessible name carries the current state, and status changes are read through the panel's single `#feedback` announcer rather than a live region of its own. The card's note and diagnostics, which main hides while the editor is open, are not read again when the same ones return as it closes, and a note that a diagnostic states as its reason is read once.

On macOS global shortcuts register by physical key. On Windows they register by virtual key, which follows the layout's letters (the key AZERTY labels A is VK_A, at the US Q position), so the editor records a letter key as the Latin letter it types, and as its US position only where the layout types none there, which is also where Windows keeps the US virtual key (2026-10-05; unverified on Windows hardware). On macOS, before app ready, main disables Chromium's `LayoutAwareGlobalHotkeys` (`physicalHotkeyFeatures` in [hotkey.ts](../../src/main/hotkey.ts), merged into any `disable-features` list already on the command line). With the feature on, Chromium 152 binds an accelerator to whichever key types its character in the current layout and re-registers on every keyboard change. Under Zhuyin, whose ZhuyinBopomofo layout types Bopomofo on the number row, the default ⇧⌘1 moved to the keypad, a key the editor refuses. Registration now uses the fixed US position the editor records, as Cap does through `global-hotkey`. On non-QWERTY Latin layouts such as Dvorak or AZERTY, a letter shortcut is therefore the US position rather than the keycap letter ([decision](decisions.md), [plan 043 closure](../verification/history-2026-09.md#plan-043-closure--2026-09-26)). `pnpm acceptance:shortcut-layout` checks the built app under a layout whose number row types no digits and fails if registration follows the layout again ([tooling](tooling.md#keyboard-layout-shortcut-check)).

`pnpm acceptance` sends digits, Space, arrows, F1–F20 and common unshifted punctuation as macOS key codes, and letters as typed characters. Other combinations fail explicitly with the accelerator in the error before recording begins. Because registration is physical, a key sent by key code reaches the registered shortcut under any input source, including Zhuyin. A letter sent as a character reaches it only where that letter sits at its US position, as on ABC and Zhuyin; on Dvorak or AZERTY the runner would press a different key.

A registration the OS refuses (another app owns the combination, or `register` throws) is never silent: it is logged as `hotkey: registration failed for …`, shown in Settings → Shortcut as "Another app may be using this shortcut." with a retry, and announced by a notification whose click opens Settings on the General tab, at the shortcut control. The tray menu then omits the shortcut beside Start recording. The setting is still saved so the user's choice survives a relaunch; the tray keeps working. Disabling the shortcut leaves tray behavior unchanged and remembers the accelerator so re-enabling restores it. Changing the shortcut persists first and registers second: a failed write keeps the old registration and reports "Could not save the shortcut". If a recording starts while that write is pending, the registration change is deferred (`request` → `flush` on the next settled state) so the combination that started the session can still stop it; until then the menu shows the saved choice as unavailable.

`pnpm acceptance:shortcut` verifies reported registration failure and failed-choice persistence across isolated Electron processes, including process/window/shortcut/temporary-data cleanup. Notification assertions observe invocation, not macOS banner delivery; this does not guarantee detection of every case where another app intercepts keys. Plan 020 closed with maintainer acceptance of this evidence, retaining actual OS conflict and notification banners as untested limitations; see the [closure record](../verification/history-2026-09.md#plan-020-closure--2026-09-23).

## Language

Source: [i18n.ts](../../src/shared/i18n.ts). English (`en`) is the default, including upgrades from settings files without a language field. The user can choose English or Traditional Chinese (`zh-TW`) from Settings → General → Language. There is no implicit OS-locale selection.

English source messages are typed catalog keys; ZH_TW supplies each translation. Translate selects a template and substitutes named placeholders; the compiler requires a value for every placeholder. The model receives language through TrayContext. Notifications read the current context when created; existing OS notifications are not rewritten retroactively.

A language action serializes a settings save, switches the in-memory language only after success, and refreshes the tray. Failure preserves the old language and reports the failure in that language. Switching during recording changes presentation only; recording state, source, output location, and quality snapshot are unaffected.

Menu labels, tooltips, permission guidance, folder dialog title, application error summaries, and notifications are localized. Diagnostic details and developer tool output remain English. Technical failure details remain in the log rather than appearing as untranslated fragments in Chinese error notifications. Native OS permission dialogs follow macOS language settings, not the app's selector.

## Screen permission

Source: [permission.ts](../../src/main/permission.ts). PermissionWatcher is created only on macOS.

1. Check getMediaAccessStatus('screen') every five seconds and on activate. A windowless app cannot rely on activate alone. This stage never prompts and materialises nothing, so polling it is cheap.
2. If not granted, clear validation and any pending retry, emit needsPermission, and call getSources at most once per process to register the app/show the system prompt.
3. If granted but unvalidated, require at least one capturable screen. A validation still unanswered after four seconds shows relaunch guidance (needsRelaunch), but the call keeps its slot: the deadline cannot cancel getSources.
4. At most one watcher-owned getSources call, prompt or validation, is unresolved at a time. While it is pending only stage 1 is polled. A grant that arrives during the prompt is validated once the prompt settles; a prompt result never counts as validation.
5. Cache success. A failure requires relaunch and is retried after a backoff counted from that failure's completion: 5, 10, 20 and 40 seconds, then every 60 seconds. Revocation resets the backoff.
6. Revocation, an actual permission-denied capture (markRelaunchRequired) and stop() start a new generation: a validation from an older generation that settles later is logged and ignored, and a fresh one follows. stop() removes the interval, the activate listener and both timers; a call still pending stays owned until it settles.

Only stage 1 is polled, and caching stage 2 for the process is what makes that safe. Cap polled the equivalent macOS call for permission state — `SCShareableContent`, which materialises every window, app and display — for the whole process lifetime, leaking about 15 MB/min until macOS exhausted swap ([CapSoftware/Cap issue #2023](https://github.com/CapSoftware/Cap/issues/2023), fixed in 0.5.9 as "Memory growth while idle on macOS"). Their post-incident design is the one used here: a cheap preflight gate polled freely, an expensive validation cached after one success, serialized, and retried no sooner than the poll period after it completes, with the same five-second and four-second constants. Cap also times out `ShareableContent::current`, but dropping that future was not shown to cancel the macOS request, so RecordStuff keeps the real promise owned instead of issuing a replacement (plan 027). A call that never returns cannot be recovered inside the process: the guidance is to relaunch, which ends it with the process. A runtime revocation is caught by stage 1, by the capture attempt itself, and in practice by macOS asking the app to relaunch. A revocation and regrant that both fall between two polls are not observed, so a validation started before them can still apply.

Only changed permission states are emitted. Recorder always stores the latest status, including while starting, recording or stopping, and never interrupts a running session for it. Every return to a non-busy state (saved, capture failure or start failure) settles from that stored status into idle or needsPermission, so a revocation reported once during a session is not lost, and a grant later in the same session needs no further event. Once permission returns, the recorder restores the idle details needsPermission does not carry (outputDirUnavailable, unless the folder was changed meanwhile). A save completed meanwhile is still announced, as described under notifications. Actual track termination, capture failure, or an OS-requested quit follows the recording cleanup path. Revoking the grant in System Settings and choosing macOS's Later leaves `getMediaAccessStatus` reporting granted to the running process while capture lists no screen at all; a capture request that finds no source although displays are connected is therefore reported as `permission_denied` on macOS, not `no_display`, which marks the relaunch-required state and its recheck (plan 035 D2).

System Settings opens through a fixed ScreenCapture URL. The app does not reset TCC. The missing-permission menu always offers relaunch because the running process may not observe a new grant. System audio has its own permission and is validated through returned audio tracks. See the [verification record](../verification/README.md) for first-grant, denial, recovery, and revocation evidence.

## Settings and output folder

Sources: [settings.ts](../../src/main/settings.ts), [quality.ts](../../src/shared/quality.ts).

```json
{
  "version": 3,
  "outputDir": "/Users/example/Movies/RecordStuff",
  "quality": { "videoQuality": "standard", "resolutionCap": "source", "frameRate": 30 },
  "language": "en",
  "hotkey": { "enabled": true, "accelerator": "CommandOrControl+Shift+1" },
  "notifications": true,
  "countdown": 3,
  "countdownSound": true,
  "fileNameTemplate": "{date} {time}",
  "libraryLayout": "grid"
}
```

OutputDir must be a nonempty absolute path. Version 1 loads with default quality, version 1 and 2 load with the default shortcut (each logged as a warning), and both are written as version 3 on the next save. The additive language field is optional on disk for older files; it defaults to English. Unsupported language values default to English with a warning, preserving valid folder/quality settings. `hotkey.accelerator` must pass the shared accelerator validator; a missing or unsupported hotkey block in a v3 file falls back to the default shortcut with a warning and keeps the other fields. Unsupported versions or invalid folder data fall back to defaults; an invalid quality block alone does not discard a valid folder. A file that exists but cannot be read, parsed or used (for example one written by a newer version) is kept as `settings.json.unreadable` before the first write, including the launch update check's automatic stamp, so the user's choices are never silently replaced by defaults. A name an earlier copy holds is never replaced: the next free `.unreadable.1`, `.unreadable.2`… is used instead. If the copy cannot be kept, that write is refused and the file stays in place. Obsolete audioQuality fields are ignored. `notifications` is additive like `updates`: a missing value reads as `true` without a warning, because a file written before the switch existed is not a broken file; a non-boolean value also reads as `true`, with a warning. `countdown` (plan 040) is additive the same way, with no version bump: a missing value reads as 3 seconds silently, so existing users get the default too; a value other than 0, 3, 5 or 10 reads as 3 with a warning. `countdownSound` (plan 046) is additive too: a missing value reads as `true` silently, the maintainer's default also for existing users, and a non-boolean value reads as `true` with a warning. `fileNameTemplate` and `libraryLayout` (2026-10-05) are additive the same way: missing, they read as `{date} {time}` (the names every recording had before) and `grid` silently; a pattern [file-name.ts](../../src/shared/file-name.ts) refuses, or a layout other than `grid` or `list`, reads as the default with a warning.

Save operations are serialized and derive each update from the last committed settings. Write and fsync settings.json.tmp, rename it, then update memory. A failed save removes the temporary file and rejects its caller without blocking later saves. Flushing before the rename prevents an empty or half-written settings.json after a crash or power loss; without a directory fsync, a very recent change may still revert to the previous file.

Folder selection uses a native dialog, with app focus on macOS. A successful save clears the idle folder-unavailable flag and refreshes labels. Actual writability is probed when recording starts. There is no automatic fallback to a different output folder.

The tray's output-folder entry ([output-folder.ts](../../src/main/output-folder.ts), plan 033) opens an existing folder in Finder, as it always did. Recording creates the default `Movies/RecordStuff` only when it starts, so opening creates it as well: only that folder, with a non-recursive `mkdir`, and only when its parent exists and is a folder. A missing custom folder is never recreated. It may be on a disconnected drive, and recreating the path would put later recordings on the system disk. A path that is a file, a missing default parent, a refused creation, an unreadable path and a Finder failure (an error string or a rejected `shell.openPath`) each end in one localized warning. The warning names the full path, adds technical details where there is an error, and offers Change output folder or Cancel. The choice reuses the folder chooser above with its locks; Cancel changes nothing. When RecordStuff itself is refused access to a folder, Finder is still asked to open it, because macOS privacy folders can refuse the app but not Finder. Only a Finder failure after that produces the permission warning. Opening never writes settings.json. One attempt runs at a time: a repeated click joins it, and while the warning is open it only brings the warning forward. Every failure is also logged with its path. Recording keeps its own `mkdir -p` and write probe.

Quality, the countdown, its sound and the shortcut can change only while idle/needsPermission, and each recording has a quality and countdown snapshot, the sound included; autorecord never ticks. The output folder cannot change while a session is starting, counting down, recording or saving: its temporary file is already open there. Platform frame-rate clamping affects effective settings, not persisted preferences.

## Logs

Source: [log.ts](../../src/main/log.ts). Current macOS paths are `~/Library/Logs/recordstuff/recordstuff.log` and `~/Library/Application Support/recordstuff/settings.json`. Electron's internal lowercase app name determines these paths; the displayed product name remains RecordStuff.

Each line starts with a UTC ISO timestamp. Startup records app/Electron/OS versions, the launch's run id, output folder, quality, packaged status, and executable path. Recording events include session, state, capture report, first chunk, saved (with any early-stop reason), failed, the stall and low-disk warnings with the writer backlog, a start failure reclassified to a retained disk error, and interruption sentinels found at launch. `power: suspend` and `power: resume` lines name the in-flight session and state; `power: keeping the display awake (blocker n)` and `power: display may sleep again (blocker n)` bracket each session, and `notification: held during sleep: …` marks a notification that waits for waking. Logs include local paths, but no media bytes.

Session records (plan 029). A run id, launch time plus pid such as `20260925T101530123Z-4242`, appears in the `start:` line only; ordinary lines carry no prefix. Beside the human-readable capture, `saved` and `failed:` lines the app writes one versioned record per event, `session-record: {"v":1,"run":…,"kind":…}`: `capture` (session, requested quality, capture report), `saved` (session, final path, recording and stop-request times, early-stop reason), `failed` (session, code, detail, file outcome, kept and temporary paths, times; written even when no file remains) and `refused` (a preflight refusal, which names no session). JSON keeps paths with spaces, quotes or line breaks on one escaped line. The Recorder carries the session on its terminal events because a failure's cleanup can finish after the next session started, so completion order is no identity. Development analyzers pair recordings by run and session id and read only these records where a launch writes them, never both forms as two outcomes; older logs are not rewritten.

All messages go to stdout. Before an append, a file larger than 5 MiB rotates through three archives; development runners follow a rotation with file-identity cursors ([tooling](tooling.md#selecting-acceptance-coverage)) and the policy itself is unchanged. File writes go through one serialized asynchronous queue capped at 1 MiB, so a line never waits on the disk; exit paths flush it with a bound. The active file's size is read once per process and counted from then on, so a line costs one append and no stat. A full disk or a removed logs folder only skips file lines: the next line creates the folder again and, once one is written, the file says how many it missed. A rotation another process blocks (Windows will not rename a file a viewer or scanner holds open) keeps appending to the active file, says so in it once, and retries after 512 KiB more. Any other disk logging failure reports once to stderr and disables file output for the process while retaining stdout. The first uncaught main error also shows a localized dialog, once recording work has settled ([dialogs and main's event loop](#dialogs-and-mains-event-loop)); later ones and unhandled rejections are only logged, so a fault that repeats cannot stack dialogs. A startup that fails before the app is wired up logs the cause, shows the same dialog and exits, since a menu-bar app with no tray offers no other way to quit.

Show log, in General → Troubleshooting since 2026-10-04, reveals the file, falling back to opening its directory if absent, and says so when neither opens. The saved notification opens Recordings with the saved file in view; when the user has moved or deleted it since, Recordings shows what the folder holds and the log says the file is not there. Neither affects capture. Development Electron.app and installed RecordStuff.app are different permission subjects; inspect executable before interpreting a grant or failure.

## Update checks

[updates.ts](../../src/main/updates.ts) owns the update-check lifecycle, independently of recording. Settings → General contains Check for updates…, its result, and Check for updates on launch. Results never change the tray title or open a dialog. One case notifies (maintainer decision 2026-10-03): when the launch check finds a newer version the user has not been told about, the app sends one notification, "RecordStuff {version} is available. Click to open the download page.", whose click opens the website download page directly (not through `openUpdate`, whose destination follows the checker's state at click time) under the same lock: a click while starting, recording, saving or quitting opens nothing and is logged. A version shown by a manual check counts as told, so a manual check never notifies and a later launch stays quiet about that version; a newer one notifies again. The told version only moves forward: a stale source offering an older release than one already told neither notifies nor lowers it. The notification follows the Notifications switch and the sleep hold, and a result withheld during a session is announced when it is shown. With the switch off a launch check notifies nothing and leaves the version untold, so a later launch with notifications on still announces it. Starting, recording and saving disable update actions; checks and pending results wait for idle/needsPermission.

Settings version 3 gains an optional `updates: { enabled, lastAttempt, notifiedVersion? }` block. Older files default to enabled and no prior attempt; `notifiedVersion`, the newest stable version the user was told about, is omitted until one is, and an invalid value is dropped with a log warning. 1.2.0 and earlier drop it when they save, so after a downgrade the same version may be announced once more. Atomic serialized writes preserve unrelated settings. The launch attempt timestamp is persisted before networking, including failed checks, to enforce a 24-hour limit across restarts. Future timestamps after a clock correction are treated as due. Manual checks bypass this limit and still proceed if timestamp persistence fails (with a log entry). No timer polls during the app lifetime. Disabling the preference affects launch checks only.

The app injects Electron `net.fetch` to use Chromium networking and system proxy/PAC settings; unit tests inject their own transport. A check reads `https://record.ericts.com/release.json`, falling back to the repository's GitHub latest-release API. On Windows x64 it reads only the GitHub latest-release API and accepts a release only when it carries `RecordStuff-<version>-x64-unsigned-setup.exe`, because the feed keeps the shape installed macOS apps parse and describes only the DMG; on a platform with no published asset a check finds no compatible release. This Windows path is covered by unit tests only. Each source has an 8-second deadline and shutdown aborts pending requests. Stable semantic versions are compared with `app.getVersion()`; incompatible assets, malformed data and prereleases cannot produce an update offer. A failed launch check restores the previous menu and logs; a failed manual check offers Releases and a retry. Successful checks display the local check time or a newer version that opens the fixed website download page. Downloads and replacement stay manual.

## Notification switch

Settings → General contains a Notifications On/Off switch with, on macOS, an Open notification settings… button in the same card, so the switch and the OS permission that can override it read as one decision rather than two unrelated settings. `AppTray.show` checks the switch before asking the OS (after the sleep hold, which applies it when a held notice is finally shown) and logs `notification: turned off in settings, dropped: …`, so one boolean governs every notification the app sends on its own — saved recordings, errors, update announcements, and every write-failure hint. Only direct answers to the user's own action bypass it: a deferred quit, an output-folder problem found while recording work is pending, and the permission notice that answers a click or shortcut press while screen permission is missing. The switch is locked while a capture is running, like every other preference.

The app deliberately does not mirror the OS notification permission. Electron exposes no way to read it: `systemPreferences.getMediaAccessStatus` accepts `microphone`, `camera` and `screen` only, and `Electron Framework` contains no `getNotificationSettingsWithCompletionHandler`. It does contain `requestAuthorizationWithOptions:completionHandler:`, so Electron asks macOS for authorization from inside `Notification.show()` — the first notification of a fresh install is what raises the system prompt. `UNUserNotificationCenter` offers that prompt only while the status is `notDetermined`, and the status is kept per bundle ID and survives reinstalling the app, so there is exactly one chance to show it and a denial is final as far as the app is concerned. It is therefore spent on first launch, by the first-run hint that also tells the user where a menu-bar app lives: launch is when macOS is already asking this app for screen recording, so the notification ask arrives in that same context instead of at the end of the user's first recording. When screen permission is missing at launch, the permission notice is that first notification and the hint, which promises that a click records, waits for the first launch where it is true. The switch stays on by default — a recorder that never says it saved reads as broken, and an unspent prompt the user never finds is no better than a denied one. Turning the switch off and on again also sends a confirmation notification, which doubles as a delivery test the user can repeat. A status line would have to claim a permission state the app cannot read, so the group's ⓘ names the recovery path instead — System Settings → Notifications → RecordStuff — and the macOS action opens that pane. Turning the switch off suppresses OS notifications. Recording failures still appear in the menu bar and the Recording failures section described below. `PermissionNotices` gives a permission-denied recording one notification: the failure notice if its result arrives first, or the permission notice if revocation already changed the state. The failure record and recovery actions remain available in either case. Later permission changes and direct responses to the user still notify.

This follows Cap's design (`apps/desktop/src-tauri/src/notifications.rs`), where the send path checks one `enable_notifications` boolean and nothing else. Cap additionally gates its switch on `isPermissionGranted()`, which `@tauri-apps/plugin-notification` provides and Electron does not; the ⓘ text carries that gap instead. Plan 019 first implemented a Node-API bridge to macOS `UserNotifications` to close it. That was reverted: the bridge made a bridge-load failure — a wrong-architecture or too-new `.node` — silently suppress every notification, including the implicit authorization request Electron would otherwise have made, which is strictly worse than having no status at all.

The static website endpoint projects the online-verified release manifest with version, tag, platform/architecture, DMG metadata, publication date and trusted page URLs. Unverified preview builds emit an error object instead of an advertised release. Vercel caches the feed for five minutes; the app requests it without caching. `pnpm site:check` verifies the built feed matches the manifest; Vercel's production build runs the same `pnpm check`, so `check-release.mts` verifies the feed in the `dist/` it then serves; the deployment workflow itself only uploads (`vercel deploy --archive=tgz --prod`) and runs no further check on the served output. No installation identifier, query parameter, telemetry, updater dependency or changed signing identity is involved.

The macOS settings action opens the Notifications overview; select RecordStuff there to reach its permission controls. This existing route was retained when plan 019 closed. Ordinary settings value/text updates preserve the live form controls, focus and scroll position; only tab/structure changes rebuild the form. Save-only interaction locks retain normal opacity to avoid a brief whole-panel dimming, while recording/platform restrictions remain visibly disabled.

## Settings shortcut

⌥⌘, on macOS and Ctrl+Shift+, elsewhere (`settingsShortcut` in [hotkey.ts](../../src/shared/hotkey.ts); until 2026-10-05 Ctrl+Alt+, there too, but Windows sends AltGr as Ctrl+Alt, so it took AltGr+, from every app on the layouts that type with it) opens, restores and focuses the single Settings panel through `openSettings`, including while recording.

Opening the app again while it runs does the same (plan 053), for a user whose menu bar icon is hidden behind the notch or a crowded menu bar. A second process reaches the running one as `second-instance` before it exits on the single-instance lock; on macOS, opening the running app from Finder, Spotlight or the Dock starts no second process but sends a reopen, which Electron reports as `activate`. Both go through `handleAction("openSettings")`, so a quit in progress ignores them and an open panel is reused. A notification click or the panel's own `app.focus()` only makes the app active (`did-become-active`), so neither opens Settings, and the permission watcher's `activate` check is unchanged. A click can still arrive as a launch: with a development bundle running, clicking its banner made macOS start the copy registered in /Applications, which reached the running app as `second-instance` about 0.5 s later. A registered copy that is itself running receives the click as a reopen instead: on the installed app, macOS sent `activate` 113 and 121 ms after two clicks (plan 054). Either event within `NOTIFICATION_ACTIVATION_MS` (2 s) of a notification click is therefore taken as the click's activation and ignored, with a log line; the click's own action, such as opening Settings for a capture warning, is unaffected. [reopen.ts](../../src/main/reopen.ts) logs each reopen and whether Settings opened. It never toggles recording; ordinary ⌘, remains untouched. `settings-hotkey.ts` owns this registration independently of the recording shortcut and releases only its own key on quit. The tray advertises it only when registered and otherwise explains failures in the selected language.

New recording choices cannot use the platform-equivalent Settings combination. A legacy stored collision is preserved and takes priority; change or disable the recording shortcut through the tray's Open RecordStuff to recover. Both registrations suspend during custom capture and resume when its lease is released (commit, cancel, blur, timeout, close or renderer failure), without waiting for a pending save. Recording locks still apply.

### Screen preference and diagnostics

Settings → Recording → Screen lists Primary display followed by unique connected displays from `screen.getAllDisplays()`; opening the panel never enumerates capture sources or asks for capture permission. The default follows the current primary. A specific choice stores only id and label in the existing version-3 settings file; versions 1–3 without the field use the default, and invalid values warn and fall back. Empty names receive localized id-based labels. The panel sends a choice id and main resolves the current action, including its label.

Added/removed/metrics events always advance topology generation; settled UI refreshes immediately and busy UI refreshes when settled. Recording locks selection. An absent or ambiguous stored choice remains selected but disabled, alongside Primary and available recovery choices. The idle tray names a healthy explicit target. Current absence and the last display failure are distinguished in both projections. Last failure lives in memory even when notifications are off; only successful recording start or a successfully saved different choice clears it. Failed saves preserve both preference and diagnostic and send the normal preference-gated notification. There is no tray submenu or system picker; system audio policy is unchanged.

Appearance in General offers System default (the default), Light and Dark, including while recording. After a successful save main sets `nativeTheme.themeSource`, updating native window appearance and CSS immediately, and restores it at startup. Missing or invalid values in older files fall back to system independently of other preferences.

## Recording failure results

Recorder emits a separate failure-status update before file cleanup completes. Main retains individual failures and their acknowledgement in `userData/recording-history.json` (version 2), independent of notification preferences and capture state. New failures appear first; delayed cleanup updates its own ID without replacing or reordering other failures. All unread records and the 20 most recently acknowledged records are retained. This is failure history, not a media library or orphan-recovery mechanism.

There is one tray item. Its idle ring carries an integrated warning badge whenever any failure is unread; recording still takes precedence with the filled icon and REC. The menu reports the unread count and offers View recording failures. A left click does what the user chose for it, as everywhere else. View recording failures and error notifications select the Failures tab, open only the newest unread row (the newest row when all are reviewed), scroll it into view and focus its header, without acknowledging it; Open RecordStuff and its shortcut open Recordings in a new window and keep the current tab in an open one. Opening a menu, dismissing a notification, successful recordings and elapsed time do not clear failures.

The history has its own Settings tab (plan 047); Recording and General show none of it, and diagnostics about a preference, such as an unavailable saved display, stay beside their control. The tab shows the history-wide status line (loading), then the rows newest first, then the retention note as a footnote; with no failures it says “No recording failures.”. Rows are grouped under day headings (Today, Yesterday, then the date, with the year only for an earlier year), which main supplies with each row's short local time, and sit directly on the window background, separated by hairlines that stop 10 px short of each side; warning colour is kept for save warnings and action errors. A row's header has two lines: the unread marker (a dot and a bold reason, with “Unread” in its accessible name, so it is not colour alone and stays visible in forced colors), the reason, the time and a chevron; then the file outcome. Every row starts collapsed and opens on its own (2026-10-05; until then one at a time, which moved the row just clicked when the one above it closed, and kept two failures from being compared); a pending save or action keeps its state by ID. An open row reads apart from the closed ones: a tint over the whole record, a hairline between its header and its details, its reason in heavier ink and its chevron darker, with the hairlines beside it hidden. An explicit entry opens its target alone. The details, indented under the title, do not repeat a heading or the time: the guidance, the file name (the full path is with the technical details), the actions with Got it at the end and Remove from history only on reviewed rows, the saving and error lines, and Technical details. The header is the focus target: keyboard focus draws a thin accent border (the shared focus weight, 6 px corners, no fill) around the whole record and hides the two hairlines beside it; focus on a control inside an open row turns the row's border neutral at 1 px while the control's own border turns accent. The chevron turns over 150 ms, at once with Reduce motion. Up and Down move between headers across day groups, Home and End go to the first and last, and Enter and Space open or close. A row that moves to another day group, as across midnight, keeps the focus of its header or control, and the Technical details disclosure shows the shared focus line just off its text. Missing system audio (`no_audio_track`) names a Mac under very heavy load before the permission, because the capture host sees the same already-ended track for both causes (plan 040's load tests); its System Settings and Relaunch actions stay. Pending cleanup disables Got it and has no reveal action. Partial files are checked before presentation and again before reveal; unknown or missing paths remain hints, not promises of playable or recoverable media. File/folder/permission actions retain recording locks. Normal updates preserve each row's expansion and identity, so an older button cannot act on a newer record.

Got it durably acknowledges only the offered settled ID and collapses that row. Each Got it, Remove from history and Retry saving the record logs one line when it settles, `recording result: <action> <id> saved`, `failed (<io|blocked|tooLarge>)` or `refused (<pending record|not reviewed|… in flight|unknown record>)`, with no path or failure detail, so the log agrees with the row and can be paired with the record by ID. The badge clears only after every retained failure is acknowledged. Reviewed rows can be removed from history; neither manual removal nor trimming the oldest reviewed rows deletes recordings or logs. Acknowledgement and removal become visible only once the snapshot containing them is durable; meanwhile the row shows a localized saving line, its buttons stay focusable with `aria-disabled` and ignore activation, and other rows, preferences and recording controls stay usable. Failed acknowledgement/removal leaves the previous visible state intact with a per-row error. Retry saving the record independently saves the history without changing acknowledgement, including for unread or pending failures. Saving any update writes the current history snapshot, so a successful retry also persists other unsaved failures.

Focus follows the action's recorded intent, not whether `document.activeElement` survived the wait: after acknowledgement, collapse or failure it returns to that row's summary; after a removal it moves to the row that took the removed row's place, or to the new last row, scrolled into view; after removing the last row it goes to the Failures tab, which then shows its empty state. It never moves when the user moved focus or the window lost focus during the wait, and never enters another row's controls. Result actions bypass the preference save queue and never end shortcut capture.

Restart does not replay notifications. Interrupted pending cleanup becomes unknown. A session that was still recording when an earlier process ended (force-quit, crash, process kill or power loss) is reported once at launch through its interruption sentinel as an unread `app_terminated` entry: "RecordStuff did not exit normally while recording.", timed at the session's start, with guidance that the file may be incomplete and is not repaired. Its temporary path is rechecked like a previously confirmed partial below, so it offers reveal only while a nonempty file exists there and is otherwise unknown with the path as a hint. It raises no notification, and it does not reappear after acknowledgement or another restart because the sentinel is removed once the entry is saved. Until then the sentinel keeps the entry, so it is not counted as unsaved: a quit while the history cannot be saved (an unreadable or newer file included) neither lists it nor warns that it is lost, and the next launch adopts it again (2026-10-05; until then every quit asked to exit without saving it). No recovery, remux or repair is performed. Previously confirmed partial files start unknown and are rechecked sequentially with a two-second bound; a timeout stops further checks to avoid filling the filesystem worker pool; a successful check restores partial status while preserving intervening acknowledgement. Unavailable paths retain their candidate/provenance for another restart. Existing bytes alone never promote interrupted cleanup to confirmed preservation. Removed IDs cannot be resurrected by a delayed check or terminal event.

On first use, a valid `recording-result.json` v1 record migrates into the separate history file; the legacy file is preserved. A valid empty history suppresses re-import. A corrupt, oversized or newer history file is logged and protected from overwrite; subsequent writes report a persistence warning. The serialized history has a 32 MiB safety bound and validated unique IDs; unread records are not evicted to meet that bound, so exceeding it reports a save failure. This is not unlimited durable storage.

History uses a private temporary file, fsync and rename through Node's asynchronous `fs.promises` (the libuv threadpool); main never waits on the disk. Startup reads the file asynchronously, never writes before it has loaded, and merges failures that arrive meanwhile by ID; Settings shows a localized loading line until then. One owner keeps at most one write in flight and one coalesced follow-up; each snapshot is the whole history, so it carries every failure and action outcome of an earlier one, and a completion settles only the revision it contained. An older completion never clears the warning of a newer unsaved change. Unchanged history is not rewritten after startup checks.

Save failure keeps new information in memory and shows a localized warning only for records that differ from the last saved snapshot. Ordinary I/O failures retry automatically on one timer, 2, 5, 15 and then every 30 seconds while unsaved; success resets the backoff, a clean history stops it, and a failure streak logs once plus its recovery. Manual retry starts promptly and joins an active write instead of adding a second writer. Unreadable or newer history is never retried or overwritten and says so instead of suggesting disk space; a history over the 32 MiB bound asks for reviewed rows to be removed. Atomic replacement cannot guarantee recovery from power loss or a full/unwritable disk, and background saving does not add disk throughput. Restored permission errors use historical guidance and offer Relaunch only when current permission state requires it. Failure IDs are UUIDs across processes.

Save serialization stays on main without a worker. Large-file parsing now uses a worker (see Audit hardening below). Whole-snapshot `JSON.stringify` at the 32 MiB bound measured about 40 ms on an M1 Pro, over one 16 ms frame, but handing that snapshot to a worker costs a comparable structured clone on main, so records instead cache their encoded JSON and fingerprints (records are immutable) and history loops yield after about 8 ms of work. Measured longest single main-thread turn: saves at most about 10 ms, including at the bound; before the audit repairs, startup reading took one turn of about 38 ms at the bound (a single `JSON.parse`), about 6 ms at 3.8 MiB and about 2 ms for a typical history. See the [verification record](../verification/history-2026-09.md#plan-036-closure--2026-09-25).

## Deferred quit

Normal quit waits for recording and all pending disk work, even when the tray is idle. After 13 seconds with work pending (the tray says it is quitting meanwhile), an English/Traditional Chinese notification says RecordStuff will remain open and asks the user to retry after saving/cleanup finishes. It is shown even with the notification switch off, because it answers the user's own quit; macOS notification permission and Focus still decide whether a banner appears, and the log names it either way. Because the banner may not be seen, the tray menu and tooltip also carry a short line, “Quit or relaunch postponed: …”, naming recording work or a settings/log write, in every state until the next state change or quit request, or until what held the quit has finished (plan 056). A refused notification reaches the log as Electron's `failed` event, but Focus and a banner muted while the display is shared give no signal, so the line does not depend on delivery. Until plan 055 this was a windowless information dialog, which stopped main's timers and log while it was open: shown exactly while recording work is pending, it held a capture-request deadline 2 min 46 s past due until the user closed it ([record](../verification/history-2026-09.md#plan-055-closure--2026-09-29)). Repeated requests cannot bypass this gate. Starting capture retains stop intent across deferral. Relaunch is registered only after safe admission and is canceled by a deferred quit. Both the notification and tray line ask the user to retry the original action (Quit or Relaunch), rather than directing a deferred relaunch to ordinary Quit. No force-exit control is offered for media work.

Only after media is safe, while new captures stay refused, quit and relaunch attempt the latest failure-history save for up to 5 seconds (a local save measured about 5–10 ms; the 32 MiB bound under 200 ms). Saved history exits normally. If a write is still in flight, a warning offers Keep waiting / Stay in app and never an exit, because a timed-out write is not proof that the OS stopped writing. If the save failed with no write in flight, the warning lists the number of unsaved records with their times and reasons (five, then a count) and offers Retry, Stay in app and a separate Exit without saving. Retry is left out, and Stay in app becomes the default, when the history is unreadable, from a newer version or over its bound: every attempt fails the same way while the prompt holds the app. Exiting without saving is logged, the log is flushed with a bound before the app quits, and the history writer is closed. Staying reopens capture admission and automatic retry and clears relaunch intent. Repeated requests join the running attempt and bring its prompt forward. Nothing is acknowledged or saved as a side effect of exit, and no OS notification is replayed. Force-quit and power loss may lose failure records that were not yet saved.

### Dialogs and main's event loop

A native dialog may stop main entirely (plan 055). An isolated probe on macOS 26.6 with Electron 44.3, with a 1 s interval, a 3 s timeout and a file read due while each dialog was open, found that a windowless `dialog.showMessageBox` and `dialog.showErrorBox` hold main until they are closed: the call returns only then, and no tick, timer or I/O completion runs meanwhile. `showMessageBox` with a parent window, which becomes a sheet (a hidden parent is put on screen to carry it), and a windowless `showOpenDialog` return at once and leave the timers on time ([record](../verification/history-2026-09.md#plan-055-closure--2026-09-29)). A sheet needs a visible window, which a menu-bar app has only while Settings is open, so the deferred-quit notice became a notification rather than a sheet. The quit path therefore shows no dialog while media work is pending. “Pending” is the recorder's `mediaPending`: a session, or the cleanup and saving one left behind, which can outlive the idle state; `whenMediaSettled` resolves when it ends, by the same test quit waits on. Other dialogs still block and are kept away from that work (plan 056):

- The unsaved-history quit prompt: shown only after media has settled, with capture admission closed, so no media deadline can be due; it needs an explicit answer.
- The output-folder warning: answers to a click on Show in Finder or Open folder; a saved notification's click opens Recordings instead (2026-10-04). When the opener finds a problem while media work is pending, it logs it and sends the same text as a notification titled “Could not open the output folder” instead, held like the capture-start notices until the display is no longer shared and shown even with the switch off, since it answers the user's click; the chooser stays with the settled tray and Settings. A new session or a quit before delivery drops the notification, and the log keeps the problem. A settled app keeps the warning and its Change output folder choice.
- The permission-pane fallback: an answer to a click in a settled state (idle or needsPermission), where no capture runs; a failed session's cleanup still pending then waits for the answer and has no deadline of its own. This is accepted.
- `showErrorBox`, which is synchronous. The startup-failure box appears before any media exists. The uncaught-exception box, shown at most once per process, marks a programming fault ([fault-dialog.ts](../../src/main/fault-dialog.ts)): the log line comes first, a settled app shows the box at once, and while media work is pending the box waits until it settles, re-checking before it opens. Meanwhile the tray menu and tooltip say “An unexpected error occurred. See the log for details.” A fault that also keeps the work from settling therefore never shows the box; that tray line, the log and the recorder's own deadlines are how it surfaces. A box that waited may open during a quit, after media has settled, like the unsaved-history prompt.

The folder chooser does not block and opens only in a settled state.

### Audit hardening

Preference orchestration lives in preferences.ts: folder dialogs are deduplicated and recheck recording admission when they return. Settings getters return copies and queued updates snapshot caller input. Logging and window geometry use asynchronous serialized writes; logging caps queued text at 1 MiB and keeps stdout when file output fails.

Unreadable history remains preserved and is shown as a load error. Files above 1 MiB are JSON-parsed in a worker, which hands each record back as JSON text: an object graph would cost main a structured clone about as long as the parse (38 of 46 ms at the bound, 2026-10-04), text only a copy (13 ms), and main parses the records one at a time in its sliced loop. Save encoding remains cached and sliced on main. Settings caches immutable row projections and initially renders 50 history rows, with explicit batches of 50. Monotonic view revisions reject stale renderer replies; a retired window cannot update its replacement's delivery cache. Partial-file metadata checks have a two-second UI deadline; the underlying filesystem request may still finish later.

Saved notifications may be delivered in needsPermission because the prior recording already completed. Construction failures are contained, click actions recheck current permission state, and saved-file clicks share the missing-file fallback. Wake polling exists only while notifications await delivery. A retry control reattempts shortcut registration after a conflict is removed.
