## Tray 與通知

來源：[tray-model.ts](../../../src/main/tray-model.ts)、[tray.ts](../../../src/main/tray.ts)、[index.ts](../../../src/main/index.ts)。

TrayModel 是純函式產物，包含 icon、title、tooltip 與一份扁平的指令清單；偏好設定完全不在 tray 裡，所以模型回傳什麼、選單就顯示什麼。AppTray 只把模型映射到 Electron；不保存第二份業務狀態。左鍵的行為由使用者選擇（`trayClick`，設定 → 一般，2026-10-04）：開啟同一個選單（選單列圖示的慣例），或呼叫 toggle——開始，倒數期間或 start 已持續一秒時〔plan 065〕則取消。新安裝預設開選單；在這個選項出現前就有的設定檔保留「點一下就錄」，也就是使用者已經習慣的行為。右鍵一律依目前狀態與設定動態組選單。滑鼠停在 tray 圖示上時，原生 tooltip 只顯示目前狀態，以及它暫緩的附註（延後結束、等待中的錯誤對話框）與未確認的失敗筆數；不提點擊方式，因為那由使用者自己的設定決定（2026-10-04，原本會寫「按一下開啟選單」或「右鍵開啟選單」，倒數時寫「按一下即可取消」）。Windows 只顯示 tooltip 前 127 個字元，較長的會在該處以「…」截斷；選單會完整列出每一行。在 macOS 上，左鍵設為開選單時，會在按下的那一刻（Electron 的 `mouse-down`，在它檢查有沒有掛上的選單之前送出）以 `setContextMenu` 把選單掛上，由 macOS 在按下時開啟，圖示只反白一次：原本在 click 裡以 `popUpContextMenu` 彈出，要等放開滑鼠才開，而且 Electron 會再按一次圖示，反白因此亮、暗、再亮（2026-10-05）。選單關閉後就拿掉，沒有開出來則立刻拿掉。選單從不一直掛著：掛上的選單不論選擇為何，每次左鍵都會開啟，而且 Accessibility 會把它報告成開著的選單，`pnpm acceptance:tray` 因此以為選單一直沒關，它每次讀取也都被記成一次開啟（2026-10-05）。VoiceOver 的按壓會先送出 click，照舊彈出選單；左鍵設為錄影時，以及在 Windows 上，都不掛選單。[全域快捷鍵](#錄影快捷鍵)不論點擊怎麼設定都呼叫 toggle。

| 狀態 | 圖示／標題 | Tray 指令 | 設定視窗中的偏好 |
| --- | --- | --- | --- |
| needsPermission | 圓環／空白 | 權限說明；開啟系統設定與「已經允許了？重新啟動 RecordStuff」，或在已授權仍被拒絕錄影後只剩重新啟動 | 全部可調 |
| idle | 圓環／空白 | 待命、位置不可用或螢幕無法使用；「開始錄影」（與 toggle 相同的開始，包括倒數）；儲存位置無法使用時才有「更改儲存位置…」，否則在所選螢幕無法使用且有主螢幕時提供「使用主螢幕」 | 全部可調 |
| starting | 沙漏／空白 | 提醒完成系統提示；取消錄影（已註冊快捷鍵時，提示文字會和倒數時一樣標出快捷鍵） | 語言、外觀與點擊圖示；About 連結仍可用 |
| countdown | 碼錶／空白 | 「n 秒後開始錄影」（不可點）；「取消錄影」（已註冊快捷鍵時 tooltip 顯示組合鍵） | 語言、外觀與點擊圖示；About 連結仍可用 |
| recording | 實心圓點／`REC` | 可停止（已註冊快捷鍵時 tooltip 顯示組合鍵） | 語言、外觀與點擊圖示；About 連結仍可用 |
| stopping | 沙漏／空白 | 儲存中 | 語言、外觀與點擊圖示；About 連結仍可用 |

每個選單都依同一組順序排列（plan 048），沒有內容的組別就省略，因此不會出現開頭、結尾或連續的分隔線，項目也不會在不同狀態間換位置：狀態（狀態行、待命時的上次螢幕失敗，以及主要動作：「開始錄影」、「停止」、「取消錄影」或權限步驟）；未讀失敗（「尚未確認的錄影失敗：n 筆」與「查看失敗紀錄…」，只在有未讀時顯示）；視窗（「開啟 RecordStuff」與「顯示最後一個錄影」，其快捷鍵無法使用時說明放在它們下方）；以及「結束 RecordStuff」。2026-10-04 起選單只留「現在要做的事」：儲存位置、更改儲存位置…、在 Finder 中顯示的「顯示最後一個錄影」、回到已確認失敗的入口與「顯示 log」都移進 RecordStuff（「錄影檔」的「在 Finder 中顯示」與由新到舊的清單、「錄影設定 → 儲存位置」、「失敗紀錄」分頁、「一般 → 疑難排解」）；只有儲存位置無法使用而擋住下一次錄影時，「更改儲存位置…」才回到狀態群組；所選螢幕無法使用時，「使用主螢幕」也同樣出現（2026-10-04，即設定狀態卡與「螢幕」列原本就提供的修正）。同一天「顯示最後一個錄影」以進入視窗的方式回到選單，在每個狀態都與「開啟 RecordStuff」並列：它重新列出儲存位置，開啟 RecordStuff 的「錄影檔」，把最新的錄影（分頁的第一張卡片）捲入畫面並聚焦其播放按鈕，與點儲存通知開啟該檔案的行為相同，從不開啟資料夾；資料夾為空或無法讀取時，就開在分頁目前顯示的狀態。視窗現在也存放錄影，所以以「開啟 RecordStuff」取代「設定…」。已確認的失敗不再佔據選單頂端，「最近一次失敗」一行也已移除。「開始錄影」、「停止」與「取消錄影」以原生靠右的 accelerator 顯示已註冊的錄影快捷鍵，「開啟 RecordStuff」顯示開啟它的快捷鍵，並設定 `registerAccelerator: false`，選單不會再註冊第二個全域快捷鍵；快捷鍵未註冊時不顯示，tooltip 仍保留。在狀態改變後才從已開啟選單選取的「開始錄影」不做任何事並寫 log（`Recorder.startIfIdle`）。「設定」不會因錄影而停用：哪些偏好被鎖定由面板自己說明。tray 顯示退出進行中（見下文）時，只有「結束 RecordStuff」可點，因為進行中的退出會忽略其他所有操作，並自行停止擷取。RecordStuff 視窗也一樣：只保留「結束 RecordStuff」，其他控制項全部停用，因此兩邊的結束都能把仍在等待儲存的重新啟動改成單純結束。每個狀態都有自己的 16 pt template（plan 040）：starting 與儲存中改用沙漏，取代原本的圓環加 `…` 標題（先試過圓環內三個小點，在選單列尺寸下太淡而未採用）；倒數顯示沒有標題的碼錶，因為被錄影螢幕的角落已顯示數字。只有 `REC` 會改變選單列項目寬度。未讀失敗的警示標記仍只取代 idle 圓環。已開啟的選單不會跟著狀態變化：在 macOS 26 與 Electron 44.3 上，`popUpContextMenu` 開啟的選單在開著時會保持原本的項目，修改項目或呼叫 `closeContextMenu()` 都沒有作用（2026-09-27 以獨立 probe 驗證），而 main 的 timer 仍照常執行。重建選單本身幾乎沒有成本，是平台不允許。因此每個選項都在點擊當下依目前狀態解析：倒數期間開啟的選單中的「取消錄影」，若在擷取開始後才被點選，會停止錄影並存檔。退出因錄影工作或歷史保存而等待超過 0.3 秒時，已 settle 的 tray 會顯示沙漏與「錄影存檔或清理完成後即結束…」；錄影工作完成後則改為「設定與失敗紀錄儲存完成後即結束…」，直到 App 結束、退出延後並發出通知，或使用者選擇留在 App（plan 035 與 055）。結束時會取消尚未顯示的這個狀態，已銷毀的 tray 也會忽略之後的更新，因為模態的未存歷史退出提示可能把計時器延後到拆除之後（035 的 D4）。macOS 使用 template PNG／@2x，且只有 macOS 顯示圖示旁 title。Windows 沒有 title，因此 ICO 必須獨自表達狀態（plan 034）。ICO 沒有 template 模式，所以每個狀態都放在 App 圖示的深色圓角底座上，外加一圈灰色邊緣，讓同一張圖在淺色、深色與強調色工作列上都看得清楚。idle 是中心留空的白色圓環；錄影在中心加上紅色實心圓，與 idle 的差異同時在形狀與灰階，不只靠色相；警示在圓環內放琥珀色「!」；busy 與倒數沿用沙漏與碼錶，碼錶指針與外框之間留有空隙，避免看起來像電源符號。每個 ICO 含 16、20、24、32、48 px，並對齊像素格，對應通知區域 100／125／150／200% 縮放。沒有底座的候選需要深色外框，在淺色工作列上會變成細細的雙線圓環，因此未採用。這些圖示尚未在原生 Windows 工作列上觀察；維護者在 [035](../verification/history-2026-09.md#plan-035-結案--2026-09-28) 結案時接受這項未驗證（N17）。錄整個螢幕時 `REC` 與碼錶可能出現在影片，這是目前接受的呈現。

### 倒數 overlay

來源：[countdown-overlay.ts](../../../src/main/countdown-overlay.ts)、[renderer/countdown.ts](../../../src/renderer/countdown.ts)、[preload/countdown.ts](../../../src/preload/countdown.ts)、[shared/countdown.ts](../../../src/shared/countdown.ts)。

倒數期間（見[錄影設計](recording.md#倒數)），一個透明的正方形視窗位於被錄影螢幕工作區右緣 16 pt、頂端下方 12 pt，只畫數字：沒有背景、方框、邊框、圓環或模糊。大小隨被錄螢幕而定（plan 045）：字級為螢幕 bounds 短邊（pt）的 14%，限制在 56–216 pt；視窗邊長為字級 × 88 / 56 並四捨五入到整數 pt，維持 040 的比例，讓「10」仍放得下。以整個螢幕而非工作區為準，因此 Dock 不會改變數字大小，直立螢幕與同一面板橫放時的數字也相同。例如 1920 × 1080 或 1080 × 1920 的螢幕是 238 pt 視窗內 151 pt 的數字，14 吋 MacBook Pro 預設的 982 pt 是 216 pt 內 137 pt，短邊約 1543 pt 以上則是 339 pt 內 216 pt 的上限；只有短邊 400 pt 以下才會回到 040 的 88 pt 視窗與 56 pt 數字。main 以主螢幕的大小建立視窗，並在送出第一個數字前設定被錄螢幕的 bounds；頁面只從視窗大小得知尺寸。它放在 DisplayMedia 為這個 session 解析出的螢幕上；不知道是哪個螢幕時放在主螢幕並寫 log。視窗在準備階段建立，倒數結束、取消或失敗時銷毀，錄影之間不會殘留；App 在每次回到穩定狀態時也會再銷毀一次作為保險。它沒有邊框、固定大小與位置、沒有陰影、不出現在工作列、不可取得焦點，在 macOS 上以 non-activating panel 不啟動 App 地顯示，忽略滑鼠，位於 `screen-saver` 層級並出現在每個 Space（包括全螢幕）。它從不啟動 RecordStuff，也不奪取鍵盤焦點。頁面為本地、sandbox、context isolation，使用設定頁的 CSP；preload 只提供一個數值訂閱，main 傳送數字或 `null`，頁面無法回傳。倒數音效開啟時（plan 046），main 以 `?sound=1` 載入頁面；頁面載入時建立一個 `AudioContext`，每個新數字以 Web Audio 合成一聲提示音（重複的值、`null` 或取消都不響）；銷毀視窗即會靜音，視窗也明確設定 `autoplayPolicy: "no-user-gesture-required"`。提示音依系統音量與靜音設定；音訊失敗時數字仍無聲地繼續。

數字為 SF Pro Rounded semibold、等寬數字、置中，以 `vmin` 由視窗決定大小，白色 28% 不透明度，帶 10% 黑色外框與三層柔和陰影；外框與陰影以 `em` 表示，隨數字縮放，在 56 pt 時等於 040 的 1 px 外框與陰影；在沒有背景的情況下，靠自身外框與陰影在白色與深色內容上都保持可讀。維護者比較過 80、55、40 與 28% 的草稿，選了最透明的一版，接受它在明亮照片上會變淡。淡入 120 ms、數字間交叉淡化 150 ms、淡出 120 ms 後才銷毀視窗；`prefers-reduced-motion` 取消淡化，`prefers-reduced-transparency` 讓數字不透明並加強外框，仍然沒有背景。不套用 content protection：`getDisplayMedia` 無法排除個別視窗，所以靠時間上的分離保護。無法取得焦點的視窗 VoiceOver 不一定會朗讀；實際表現只記錄，不宣稱支援。

通知使用本地化文案與 silent 模式。存檔通知點擊顯示完整影片；若錄影因磁碟保護而結束，通知會說明（「已儲存 {file}。磁碟空間即將用盡，已提前停止錄影」），Mac 進入睡眠時也一樣（「已儲存 {file}。Mac 進入睡眠，已停止錄影。」；其他平台為「…電腦進入睡眠…」），該次錄影仍屬成功、不進入失敗紀錄（見[錄影設計](recording.md#寫檔與失敗)）。在 `powerMonitor` 的 `suspend` 與 `resume` 之間，所有通知都會先保留，因為睡眠當下顯示的橫幅在使用者回來前就已消失；`resume` 之後每秒檢查一次，只要發現 2 秒內有使用者輸入（`powerMonitor.getSystemIdleTime()`）就依序顯示；收到 `unlock-screen` 則立刻顯示，而且顯示時才套用通知開關。維護用的喚醒沒有使用者輸入，計時器在睡眠期間也照常計時，所以單靠 resume 或逾時都不會放出通知（plan 050）。錄影失敗通知一律開啟設定中的「失敗紀錄」，呈現已確認的檔案狀態與復原操作；它與下述擷取通知一樣先保留、也可能被丟棄，被丟棄時未讀的失敗紀錄與選單中的未讀項目仍在。品質與語言保存失敗、幀率降級通知只有說明。擷取開始時才得知的事（無法確認的解析度上限、低於要求的幀率）會保留到該次錄影結束後才顯示一次，並與存檔通知一樣在 macOS 上延後 500 ms，因為畫面分享期間 macOS 可能判定 `display shared` 而把橫幅靜音（[時序紀錄](../verification/history-2026-09.md#儲存通知時序2026-09-20)）；在那之前開始新的錄影或結束 App 會丟棄它們，log 會記下每則通知的保留、顯示或丟棄（plan 053）。解析度上限警告也會立即顯示在設定中；幀率降級只有通知與 log。

點存檔通知會開啟 RecordStuff 的「錄影檔」分頁並把那段錄影帶到眼前（2026-10-04）：先重新列出資料夾讓新檔在列，聚焦它的卡片並以品牌紅短暫框起，不會自動播放。log 依序記 `notification: show saved <path>` 與 `show last recording: Recordings with <path>`。macOS 點通知也會要求系統啟動被點的 App；以前點擊是叫 Finder 選取檔案時，這個啟動會把 Finder 壓回使用者視窗後方（v0.1.0 的回報，plan 014 以 `did-become-active` 後再 reveal 一次處理）。現在開的是 App 自己的視窗，這個啟動正好把它帶到前面，所以那次重試與它的一秒時窗已移除。背景存檔不會開啟任何東西。原生通知不支援或 `failed` event 會留下 log。通知是否顯示仍受系統通知設定影響。原生證據由 `pnpm acceptance:notification` 產生（[工具鏈](tooling.md#通知驗收)）。通知圖示已由使用者於 2026-09-14 重開機後確認正常。

`AppTray` 持有每個原生 `Notification`，直到 `click`、`close` 或 `failed`；單純 `show` 不會釋放。退出時關閉尚未處理的通知並清除參照；同步 `show()` 例外也會釋放並記錄。這讓 `show()` 返回後 callback 仍可到達：Electron 44.3.0 的[通知 wrapper](https://github.com/electron/electron/blob/v44.3.0/shell/browser/api/electron_api_notification.cc) 由 GC 管理，解構時會清除原生 delegate。此生命週期修正不代表已證實歷史未送達點擊的原因。不使用 timer 淘汰通知；沒有終止事件的通知會持有到退出。 Windows Action Center 的生命週期未在本次修正或驗證：Windows `close` 可能只是橫幅逾時，歷史通知仍可點擊。

儲存通知由 `SavedNotification` 在檔案完成且回到 idle 後排程：macOS 使用單次 500 ms timer，其他平台立即請求。這讓 macOS 有時間清除擷取造成的通知抑制狀態，但只是依實測選定的啟發式延遲，不是就緒訊號或送達保證；專注模式、其他擷取與通知偏好仍有效。開始新錄影會永久取消前次待送通知；權限恢復狀態（needsPermission）視為已 settled，已完成的存檔仍會通知（權限提示不會取代它）；退出判定取消 timer，也抑制該次退出過程中完成的儲存通知；延後退出後恢復未來通知，不重播已抑制的通知。不保留佇列、不重試；請求通知時的例外只記錄日誌，不影響已存檔案。寫檔與 idle 不等待通知。參見[時序證據](../verification/history-2026-09.md#儲存通知時序2026-09-20)。

## 設定視窗

來源：[ui-model.ts](../../../src/main/ui-model.ts)、[settings-model.ts](../../../src/main/settings-model.ts)、[settings-window.ts](../../../src/main/settings-window.ts)、[renderer/settings.ts](../../../src/renderer/settings.ts)。

Tray 只保留必須一鍵可達的指令，所有偏好設定都在同一個獨立的 sandbox 視窗。「設定」會開啟視窗，已開啟則聚焦。在 macOS 上，視窗開著時 RecordStuff 也是一般 App（2026-10-04，依維護者要求；[app-menu.ts](../../../src/main/app-menu.ts)）：有 Dock 圖示，選單列顯示它的選單，其中「錄影」選單放 tray 的狀態動作（開始錄影、停止錄影、取消錄影或權限修正，附 SF Symbols 與已註冊的快捷鍵）與「顯示最後一個錄影」；Dock 圖示的選單提供相同項目。macOS 只在 App 是一般 App 時顯示它的選單，而一般 App 必定有 Dock 圖示，因此兩者在視窗關閉時一起消失。選單使用 App 的語言，保留視窗依賴的按鍵對應（結束、隱藏、拷貝貼上、縮到最小），不含「關閉」與「縮放」。App 套件不宣告 `LSUIElement`（2026-10-05，依維護者要求）：main 在 App 完成啟動前（`will-finish-launching`）及 ready 後隱藏 Dock 圖示，因此 RecordStuff 仍以選單列 App 啟動；從 Finder 或 Spotlight 再次開啟時，現在每次都會帶出自己的選單（探測 3 次皆成功），先前有 `LSUIElement` 時，macOS 會在它仍是選單列 App 時就讓它成為作用中的 App，選單列停留在前一個 App（3 次皆失敗）。關閉視窗，或「隱藏 RecordStuff」（⌘H，視窗原樣隱藏；還在載入的視窗也會保持隱藏；隱藏前先以 `settings:hidden` 通知頁面，讓播放器停止，不會從看不見的視窗發出聲音，即使使用者剛離開、仍在播放的全螢幕在隱藏後才回傳狀態也一樣），都只留下選單列圖示，不留 Dock 圖示與選單；再次開啟時視窗原樣回來。隱藏 Dock 圖示後，0.3 秒與 1 秒時若圖示仍在就再隱藏一次，因為在 macOS 還在把 App 轉成一般 App 時送出的隱藏（視窗載入中按 ⌘H）會在轉換完成後被抵銷（修正前 3 次皆發生，修正後 0 次）。只有「結束」才會結束 RecordStuff：tray 的「結束 RecordStuff」、視窗開著時的 ⌘Q 或 Dock 的「結束」，以及視窗本身側邊欄底部唯一的一列「結束 RecordStuff」（窄版的「一般」頁尾則是連結旁的電源圖示）；它們都走同一個結束流程，會等錄影存檔完成。「錄影」選單不放 tray 的狀態文字，倒數時才不會每秒重建使用者正開著的選單；快捷鍵只在已註冊時才標示：選單上的快捷鍵同時是按鍵對應，編輯器錄入新快捷鍵時會變成開始錄影。視窗顯示前 App 會先取得前景，因為選單列 App 單純顯示視窗並不會被帶到最前。新視窗會保持隱藏，直到頁面回報第一份 view（或首次讀取失敗的訊息）已畫出：Electron 的 `ready-to-show` 是第一個畫面，在頁面讀到 view 之前就畫好，若在那時顯示，會先閃一格空白視窗。頁面一直沒有回報時，於 `ready-to-show` 後一秒照常顯示。變更立即儲存且視窗保持開啟；切換語言會就地更新標籤與標題。關閉視窗（含 Escape 與平台的關閉快捷鍵，這兩個由面板自己處理，因為應用選單沒有「關閉」項目）不會結束選單列 App。關閉快捷鍵在 macOS 精確為 ⌘W、其他平台為 Ctrl+W，不得帶其他修飾鍵；頁面與快捷鍵編輯器共用同一個判斷，因此 macOS 的 ⌃W 與 ⇧⌘W 仍可錄入。⌘W 本身永遠不會成為錄影快捷鍵：編輯器遇到它就關窗，驗證器也保留 `CommandOrControl+W`，手動編輯的設定檔同樣會回到預設值。與原生選單相同，以輸入的字元判斷；只有該鍵盤配置在該位置不輸入拉丁字母時，才採用實體 W 鍵。頁面的 renderer 程序結束時，main 會丟棄該視窗而不保留空白視窗，下次開啟設定再建立並載入新視窗；不會自動重新載入，因此反覆當掉的頁面不會形成迴圈。關閉、失焦與當掉事件只作用於自己的視窗實例，已丟棄視窗晚到的事件不會清掉替代視窗。錄影仍使用獨立的隱藏 renderer。

[settings-model.ts](../../../src/main/settings-model.ts) 只宣告每項偏好一次，配上穩定的群組與選項 id，也是唯一知道某個選項代表什麼的地方；它同時產生面板要畫的 view，以及「這個請求現在允不允許」的答案。Tray 模型是同一份狀態與 context 的兄弟投影，不是面板讀取的來源。

已提交設定由主程序持有，面板只暫存尚未完成的選擇：畫出收到的 view，回傳群組 id 與選項 id，不回傳 action。主程序只接受設定視窗自身 main frame 的請求，依當下重新產生的模型解析這組 id，然後才呼叫與 tray 相同的 action handler，而該 handler 在保存前會再檢查一次錄影狀態。啟動錄影、倒數中、錄影中與存檔中，除了語言、外觀與點擊圖示以外的設定在面板與該邊界都會鎖定。保存依請求順序序列化，第二個變更是排隊而不是被回報為失敗。保存期間顯示 main 已提交的值；儲存狀態不佔版面，並以列的 aria-busy 標示；較新的操作意圖獨立保留於佇列，不被舊回覆覆蓋，全部請求完成後才解除其他群組的鎖定，最新選擇未生效時顯示行內訊息；被 OS 拒絕註冊的快捷鍵會保留選取並加上「目前無效」的註解。群組也可以帶 `actions`：渲染在該控制項下方的按鈕，用於同一張卡片內可能凌駕該偏好的系統面板。actions 群組的選項、以及該 `actions` 清單中的選項，都沒有可比對的已提交值，因此由其 handler 以布林值回報自身結果並直接採用；其餘選項仍以「要求的值是否成為已提交值」判定，所以一個什麼都不回報的 handler 永遠無法把未保存的變更變成成功。保存期間正在操作的控制項維持可用、其餘暫時停用，因為停用中的元素無法保有鍵盤焦點。基於同一理由，忙碌中的操作按鈕（自己的請求進行中、其他保存尚未完成，或更新檢查進行中）改用 `aria-disabled="true"` 與保存中的外觀，而不是 `disabled`，並在結束前忽略觸發；因此以鍵盤觸發「檢查更新…」、「重試快捷鍵註冊」或「開啟通知設定…」後，焦點留在原按鈕，下一次 Tab 從它繼續（plan 053）。main 把進行中的檢查標為 `busy` 而非不可用，並仍拒絕重複請求；只有 main 未提供的選項才原生停用，與失敗紀錄列的操作一致。設定 preload 僅提供讀取、選取、擷取、變更訂閱與一次性的 ready 回報；面板在第一份 view 之前唯一可能需要的字串（首次讀取失敗）依主程序寫在頁面 URL 的語言在地化。

「錄影設定」分頁包含螢幕選擇、倒數（以分段控制選擇關閉、3 秒、5 秒或 10 秒，ⓘ 說明怎麼取消：點選單列圖示，或在點擊會開選單時從選單選「取消錄影」，快捷鍵可用時也可按快捷鍵）、倒數音效（plan 046：開關，預設開啟，ⓘ 說明提示音不會被錄進影片；倒數為關閉時停用並保留其值）、影像品質、解析度上限與幀率，並以 ⓘ 說明編碼品質與像素尺寸的差異。「錄影設定」分頁在「螢幕」之後的儲存位置列（plan 048）顯示路徑，並透過 main 自己的資料夾動作與鎖定提供「更改…」與「在 Finder 中顯示」；狀態卡的修正與選單的「更改儲存位置…」（只在儲存位置無法使用而擋住下一次錄影時出現）共用同一組動作。錄影期間只鎖「更改…」：顯示資料夾不會碰到錄影持有的東西，所以「在 Finder 中顯示」仍可使用，與「錄影檔」分頁及其卡片一致（2026-10-04）。「一般」依序為圖示點擊（「點擊圖示」：開啟選單，或開始／停止錄影；ⓘ 說明按右鍵一律開啟選單；不鎖定，因為錄影中沒有東西依賴它）、快捷鍵、通知、語言、外觀、更新、疑難排解（記錄檔）與 About 頁尾，日常偏好排在維護項目之前（plan 048）。最後一個分頁「失敗紀錄」（英文「Failures」）存放錄影失敗歷史（見[下方](#錄影失敗結果)）；它永遠存在，標籤帶未確認筆數，例如「失敗紀錄（2）」，畫成徽章，無障礙名稱包含完整名稱與筆數。四個分頁都不換行：側邊欄以清單列出；窄的分頁列只有目前分頁顯示名稱，其他顯示圖示並保留名稱給輔助技術，雙語都能放進 380 pt 的最小寬度。分頁支援方向鍵、Home 和 End（涵蓋四個分頁），變更設定後保留目前分頁；新視窗開在[錄影檔](#錄影檔)，已開啟的視窗保留原分頁，明確的失敗入口會切到「失敗紀錄」，快捷鍵通知會切到「一般」，擷取警告通知會切到「錄影設定」，存檔通知會切到「錄影檔」並帶出那段錄影。每個分頁在視窗存在期間各自記住捲動位置：切走時保存，切回時在面板（含失敗列）完成後還原，第一次開啟從頂端開始，同一分頁的背景更新保留位置。位置在內容上方的元素都穩定後才套用，因此 scroll anchoring 不會移動它。更新操作使用按鈕，其完成狀態與偏好儲存分開處理。

設定視窗預設 960×640、最小 380×360，有兩種版型（2026-10-04）。寬度 600 px 以上時，側邊欄放品牌、以清單呈現的四個分頁（圖示、名稱、未確認徽章）與底部的狀態卡，旁邊是目前分頁的內容與其名稱；macOS 隱藏標題列（`hiddenInset`），視窗控制按鈕內嵌在側邊欄，頂端 40 px 的區域可拖曳視窗，原生標題仍保留給視窗清單與輔助使用。較窄的視窗把分段分頁、其下的狀態卡放在捲動清單上方。兩種版型中，狀態卡在頁面順序上都緊接在分頁之後，所以第一次按 Tab 先到分頁，接著是狀態卡，然後才是內容（2026-10-05；之前即使側邊欄把狀態卡畫在底部，它在順序上仍排第一）；macOS 上，高 48 pt、仍可拖曳的標題列會置中顯示 RecordStuff 圖示與名稱，並與視窗控制按鈕對齊，分頁列從標題列下方開始（2026-10-04）。內容欄（而非視窗）窄於 440 px 時，列的控制項改放到標籤下方（container query），兩種版型共用同一套列樣式。側邊欄之前儲存的尺寸是為上方分頁版型選的，所以每個視窗都會以新預設開啟一次；之後儲存的尺寸帶有 `layout: 3`，照舊保留，窄尺寸也一樣。Main 以選填的 `control`、`section`、`noteKind` 宣告呈現方式：通知、倒數音效與啟動更新使用原生 checkbox 開關；倒數、品質、語言與外觀使用原生 radio 分段，其中「外觀」畫成三個圖示——代表跟隨系統的螢幕、太陽與月亮——每個都以其標籤作為輔助使用名稱與滑鼠提示（`iconChoices`，2026-10-05，原為選單）；其他偏好保留原生選單。省略欄位時預設選單與靜態說明。控制項下方的文字只留給使用者需要立刻看到的內容：狀態（通知已關閉、更新結果）、儲存路徑、快捷鍵編輯的時限與診斷。次要說明改用選填的 `info` 欄位，放在標籤旁的 ⓘ 按鈕後：滑鼠停留與鍵盤焦點期間顯示，點一下會固定到再點一次為止；按 Esc、失去焦點或視窗變為非作用中時關閉，開著時第一次 Esc 先關閉說明，不會關閉視窗。說明是位於 top layer 的 `popover="manual"`，放在按鈕上方（上方空間不足時改放下方），遮住的是上一列而不是它說明的控制項，並限制在視窗內，面板捲動時跟著按鈕移動；按鈕與說明之間 6 px 的空隙有透明的橋接區域，指標慢慢移過去時說明不會關閉，因此不會被捲動清單裁切；不論是否顯示，文字都保留在控制項的 `aria-describedby` 中。只是在重複標籤的說明（螢幕選單、通知是什麼、數字出現的位置）已移除（2026-10-03）。連續同 section 的列共用分組清單，標題放在第一列：「錄影設定」分為來源與輸出（螢幕、儲存位置）、錄影開始前（倒數與倒數音效）與影像（品質、解析度上限、幀率）；「一般」分為操作與通知（圖示點擊、快捷鍵與通知）、語言與外觀、更新（其中手動檢查的列標為「手動檢查」，不重複標題），以及疑難排解（log）。不論控制項種類，每列高度一致；每個偏好列開頭有一個放在小方塊裡的線條圖示，讓使用者先靠形狀找到那一列再讀標籤，列的說明、文字連結、診斷與快捷鍵編輯器都從標籤下方、圖示右側開始。分段控制與分頁列畫法相同，以凹陷的底槽加上浮起的選取項表示，因此填色只留給開關（開啟時為 Apple Music 的紅色），以及狀態卡的修正按鈕、「確認」與「下載」（更新結果唯一要做的事）的墨色填滿。選單由外層元素自行畫出箭頭，因為 select 沒有偽元素。列的附加操作（例如「開啟通知設定…」、「重試註冊快捷鍵」）以列下方加底線的文字連結呈現。配色（2026-10-05，依維護者要求，參考 Apple Music）：與官方網站一樣以墨色搭配安靜的灰色，紅色只用於「已選取」（`--chosen`）——目前分頁的圖示與名稱（淺色模式下在側邊欄近白的浮起底色上，窄版分頁列亦同）、開啟的開關、鍵盤焦點環——以及錄影卡片的播放按鈕：淺色為 Apple Music 的 #FA2D48，深色為維護者挑選、較柔和的 #E85A62（2026-10-05）；各列與其他分頁的圖示維持墨色，帶文字的按鈕（狀態卡的修正、「確認」、「下載」）維持墨色填滿，因為白字在該紅色上的對比只有 3.8:1。目前分頁名稱以該紅色顯示時，13 px 文字的對比低於 4.5:1（在淺色浮起底色上約 3.8:1）：審查提出後，維護者仍比照 Apple Music 保留。焦點環使用同一個紅色（`--focus`），在紅色填滿的開關外留 2 px 間距以保持可見；播放器自己的焦點環在畫面上維持白色。「失敗紀錄」分頁的未確認徽章與失敗列的圓點也使用同一個紅色（2026-10-05，依維護者要求，讓視窗裡需要注意的紅色只有一種）；品牌紅（`--rec`）只用於錄影與剛存好的卡片外框，警告用琥珀色。頁面以大號粗體標題開頭，「錄影檔」分頁的日期標題用粗體文字而非小型大寫。兩種模式都是卡片浮在稍深的視窗底色上。同一天試過但未採用：每列一種顏色、單一靛藍色、石墨色方塊配墨色膠囊，以及把品牌紅用在每個圖示與填色上。明暗模式共用同一組 token，強制色彩模式回到原生控制項。

目前阻擋與歷史錄影失敗以結構化診斷呈現，與一般說明分開。消失的已選螢幕保留選取並停用，加上「無法使用」後綴；僅目前阻擋且存在可用主螢幕時提供「使用主螢幕」，透過原本 screen/primary id 儲存，不自動錄影。儲存失敗顯示於原控制項旁；只有候選仍有效、未鎖定且已提交值未改變時才提供重試。復原成功只證明偏好儲存，不能推論擷取成功。復原按鈕消失時僅在原焦點仍位於按鈕才回到選單；背景推播保留控制項身分與該分頁的捲動位置。

快捷鍵使用單一選單，包含一組建議快捷鍵、目前自訂值（若有）、關閉及「自訂快捷鍵…」。不另設自訂按鈕；自訂成功會成為選單中標示「自訂」的目前組合，不累積歷史。選回建議值會取代自訂，不保留歷史，關閉則保留。擷取期間禁止重複開啟；按下組合僅預覽，按「確定」或無修飾鍵的 Enter 才儲存。有候選時 Tab 可移至確定與取消；沒有候選時 Tab 直接退出。取消保留原值，Esc／取消及成功提交回到選單，Tab／失焦維持使用者移動焦點的位置。Main 確認後才監聽，暫停註冊不視為衝突。「確定」左鍵按下時保留擷取焦點，避免 macOS 在 click 前先失焦取消候選；鍵盤確認及編輯器外取消維持原行為。

原生視窗標題中英文都是「RecordStuff」（2026-10-04，原為「RecordStuff - 設定」，因為視窗現在也存放錄影），不隨分頁改變；內容區沒有重複圖示、大標題或自動儲存說明，狀態卡只在有事要說時出現（2026-10-04）。文件仍保留視覺隱藏的 h1 供輔助使用。狀態卡（`status`）由 main 依 tray 顯示的同一個狀態產生，最多帶一個按鈕與一個文字連結：修正下一次錄影阻礙的操作，用詞與 tray 相同，以群組 `status` 送出，只在提供時才會執行——缺少權限時的開啟系統設定或重新啟動、儲存位置無法使用時的更改儲存位置…，以及所選螢幕無法使用時的使用主螢幕。尚不需要重新啟動的缺少權限狀態，另外在說明文字下方以文字連結提供 tray 的第二步「已經允許了？重新啟動 RecordStuff」，因為狀態卡本身就請使用者在允許存取後重新啟動。這裡從不開始、停止或取消錄影：那些留給選單列圖示（左鍵）、其選單與快捷鍵，（2026-10-04）。待命時狀態卡隱藏：開始的方式取決於圖示點擊的設定，已寫在選單與 README，狀態卡只會重複。啟動、倒數、錄影、儲存與結束中顯示當下狀態，在兩個設定分頁上第二行是鎖定提示（只能變更語言、外觀與點擊圖示），因為只有它們有被鎖定的控制項（在「錄影檔」與「失敗紀錄」旁狀態卡只顯示標題，2026-10-05）；缺少權限、儲存位置或所選螢幕無法使用時變成琥珀色。狀態卡不是 live region——`#feedback` 仍是唯一的朗讀來源，狀態卡新出現的狀態由它朗讀一次（倒數只在開始時讀，不是每秒；診斷已說明時不重複；就緒不讀）——也沒有計時器或動畫，錄影時開著視窗不增加負擔。視窗高度低於 440 px 時，忙碌狀態只保留標題。影像區塊下方的註腳依所選螢幕估算每分鐘的檔案大小——「每分鐘約 180 MB（3024 × 1964、30 fps）。」——以編碼目標加上音訊計算，60 fps 依實測把影像目標加倍（見 [quality.ts](../../../src/shared/quality.ts) 的 `estimatedBytesPerMinute`），讓使用者知道檔案大小再選畫質。不論視窗寬窄，「一般」最後都是左側的「由 Eric Tsai 製作」與目前版本，右側是官方網站（地球）與 GitHub 原始碼兩個 32px 圖示按鈕，帶在地化的輔助使用名稱與 hover 提示；窄視窗時「結束 RecordStuff」也加入它們。側邊欄底部只有「結束 RecordStuff」，排版與分頁相同（2026-10-05；自 2026-10-04 起它上方曾疊著製作者、版本與連結）。「顯示 log」不在其中：「一般」的「疑難排解」區塊給它獨立一列「記錄檔（log）」與「顯示 log」按鈕，讓使用者讀得出它的用途，不必猜圖示；診斷重試按鈕維持正常文字尺寸。Renderer 只送出 `about/website` 或 `about/source`，由 main 授權固定網址、用預設瀏覽器開啟並回報失敗，失敗訊息顯示在被點的連結旁，也就是「一般」的關於列；「結束」失敗時顯示在側邊欄的「結束」下方。這些按鈕錄影中仍可用，不接受任意 URL 或導覽設定頁面。

滑鼠操作不顯示焦點外框，但保留 DOM 焦點；Tab／方向鍵等鍵盤導覽會恢復它。焦點線在各處使用同一粗細（plan 047）：Retina 螢幕 1.5 px、1× 螢幕 1 px，兩者都約 0.3 mm；提高對比與強制色彩模式為 2 px，並使用 `Highlight`。分頁、分段、按鈕與選單上，這條線落在控制項自身的邊框上，也就是邊框直接變成強調色；以強調色填滿的控制項（開啟的開關、確認按鈕、下載）與列下方的文字連結保留 2 px 間隙。視窗不在前景時不顯示焦點線：頁面在 `blur` 時標記為非作用中，`focus` 時恢復。選單選項及 action 按鈕依 id 就地更新，新增自訂值或更新結果不重建整頁；暫時鎖定不讓下方分段控制閃暗。擷取經 main 確認後顯示三線監聽動畫，減少動態效果時靜止。開啟通知設定等 action 不顯示套用文字，只有失敗時顯示「操作失敗」。

捲動區平常隱藏 scrollbar，底部有剩餘內容時才顯示不攔截操作的漸層玻璃提示，不顯示箭頭，捲到底或內容可完全容納即隱藏；尺寸與內容變更會重新計算。增加對比／減少透明度改用實色邊界，forced-colors 恢復原生 scrollbar。再次檢查更新時保留上次結果文字與節點，僅更動檢查按鈕文字及可用性；完成後就地更新結果，避免區塊收合再展開。

視窗寬高獨立儲存在 userData 的 `settings-window.json`，不混入錄影偏好或其寫入佇列；初始 960×640（Electron 邏輯像素），側邊欄旁一排可放三張錄影卡片，雙語設定列也不擁擠；沒有 `layout: 3` 的尺寸（側邊欄之前，或依當初 720×580 預設儲存的）會以 960×640 開啟一次。調整尺寸後 250ms 合併寫入，關閉／退出時同步 flush 最後尺寸，關閉重開及下次 App 啟動皆沿用。最小 380×360；開啟時依游標所在螢幕工作區限制尺寸並置中，不保存位置，也不因單次螢幕限制覆寫原保存尺寸。缺檔或無效尺寸回預設；寫入失敗記 log 並保留本程序尺寸，既有磁碟檔不被半份 JSON 覆蓋。

### 錄影檔

來源：[recordings-library.ts](../../../src/main/recordings-library.ts)、[mp4-duration.ts](../../../src/main/mp4-duration.ts)、[settings-model.ts](../../../src/main/settings-model.ts)、[renderer/settings.ts](../../../src/renderer/settings.ts)、[settings-window.ts](../../../src/main/settings-window.ts)。

第一個分頁「錄影檔」（英文 Recordings，2026-10-04）列出儲存位置裡的影片，讓使用者不必開 Finder 就能找到、觀看並分享錄影；新視窗會開在這個分頁。資料夾內直接存放的 `.mp4`、`.m4v`、`.mov` 都會列出，依時間由新到舊、像失敗紀錄一樣依日期分組；隱藏檔與仍在寫入的 `.recording.mp4` 除外。App 自己的 `YYYY-MM-DD HH-MM-SS.mp4` 檔名以其時間戳記定日期、以時間為標題，其他檔案以建立時間定日期、以檔名為標題。摘要列顯示數量與總大小，旁邊是「在 Finder 中顯示」（其他平台為「開啟資料夾」）。每張卡片有縮圖（`nativeImage.createThumbnailFromPath`，macOS 為 QuickLook；記憶體保留最近顯示的 64 張，檔案未變時重複使用，較早的縮圖再次顯示時重新產生）、縮圖上的片長與下方的大小；點一下開啟頁面內的播放器。檔案操作放在開啟之前（2026-10-04）：縮圖右上角的「⋯」按鈕（滑鼠在卡片上或按鈕有焦點時顯示）與在卡片上按右鍵，都會打開同一個選單，內有「在 Finder 中顯示」（其他平台為「開啟資料夾」）、「開啟」（預設 App）與「丟到垃圾桶」（Windows 為「移到資源回收筒」），樣式比照 macOS 選單：每項前有圖示，反白只鋪一層淡色底、文字維持原色，「丟到垃圾桶」在分隔線下方，紅字配淡紅底，兩種外觀下對比皆至少 4.5:1。方向鍵與滑鼠移動的是同一個反白，Esc 關閉並把焦點還給「⋯」，面板捲動時選單跟著卡片移動。拖曳卡片則以原生拖曳帶出檔案本身（`webContents.startDrag`，圖示為縮圖或檔案圖示），可以放進任何接受檔案的 App。

播放器是只負責播放的 modal `<dialog>`：一個只由視窗決定大小的 16:9 舞台，與 YouTube 相同——寬度取 860 px、視窗扣除邊距後的寬度、或視窗高度所允許的寬度三者中最小者——錄影在其中等比縮放，比舞台寬時上下留黑、比舞台窄時（Mac 的螢幕、直式短片）左右留黑，因此讀到錄影尺寸時舞台不會長大，換一段錄影形狀也不變（2026-10-05；在此之前由影片本身的比例決定對話框高度，從 220 px 起跳）；舞台上只有影片，控制項疊在畫面上，配置與 YouTube 的全螢幕相同（2026-10-05，[player-controls.ts](../../../src/renderer/player-controls.ts)，與全螢幕視窗共用；以前是 Chromium 的原生控制列，名稱與按鈕放在下方的一列）。上緣的漸層上是錄影名稱，連同檔名、片長與大小，以及「關閉」；下緣的漸層上是與畫面同寬、滑鼠經過時變粗的進度條，下方依序是播放／暫停、旁邊會滑出音量滑桿的靜音按鈕、`0:02 / 0:08` 形式的時間，以及最右邊的「全螢幕」。播放中滑鼠靜止 2 秒，漸層、控制項與游標都會讓開，滑鼠離開播放器時也一樣；移動、按下、控制項取得鍵盤焦點或暫停都會讓它們回來，暫停期間一直顯示。點畫面即播放或暫停；焦點在播放器內任何位置都能用 YouTube 的按鍵：空白鍵或 K 播放／暫停、← 與 → 移動 5 秒、M 靜音、F 全螢幕播放，有焦點的控制項保留自己的按鍵（按鈕上的空白鍵、音量滑桿上的方向鍵）；進度條上的左右與上下方向鍵同樣移動 5 秒、Page Up／Page Down 移動 10 秒、Home 與 End 跳到開頭與結尾，否則它自己的步進會移動片長的 1% 與 10%。進度條與音量是原生 range input，具名稱，並分別以時間與百分比作為數值文字；進度條跟隨只在播放時觸發的 `timeupdate`，因此暫停或閒置的播放器不執行任何工作。macOS 上它置中於 48 pt 標題列下方的空間，因此視窗再小，它的角落、標題與畫面都不會落在視窗控制按鈕底下（`TRAFFIC_LIGHT_ZONE`）；播放器開著時該標題列不再拖曳視窗，因為拖曳區域會在系統層級先攔下點擊、頁面收不到，這樣點播放器上方的背景也能關閉它，關閉後標題列恢復拖曳。按 Esc、「關閉」或點背景都會關閉播放器，且優先於視窗本身的 Esc，關閉時會暫停並釋放檔案。按「全螢幕」、雙擊影片，或頁面本身的全螢幕意外啟動時，都改在獨立視窗裡播放這支錄影（[video-fullscreen.ts](../../../src/main/video-fullscreen.ts)，2026-10-05）：RecordStuff 的視窗維持原本大小；先前頁面本身的全螢幕必須先把視窗撐到整個螢幕再縮回，畫面還沒跟上的地方會先露出白色。新視窗無邊框、黑底，蓋滿 RecordStuff 視窗所在的整個螢幕；它一開始就以該大小隱藏建立，macOS 上取得 simple fullscreen（不會放大、不開 Space，選單列與 Dock 會讓開），其他平台則直接以全螢幕建立；頁面在播放器的時間點畫出第一格後，以 150 ms 淡入，無法解碼的檔案則在 2 秒後顯示。它沿用播放器的時間、音量與靜音，以同一套控制項放大播放，上緣顯示錄影名稱（由 main 依清單寫入頁面的 query `title`，絕不取自頁面）；離開的方式（「結束全螢幕」）放在控制列最右端、原本「全螢幕」的位置，播放中滑鼠靜止 2 秒後，控制項連同游標一起讓開。按 Esc、⌘W、雙擊、F 或該按鈕即離開：視窗裡的影片先停止，兩邊不會同時發出聲音，接著 main 立刻把時間、播放狀態、音量與靜音交回，播放器在視窗以 150 ms 淡出的同時跳到該時間並繼續播放，接著視窗關閉，RecordStuff 視窗重新取得焦點。影片來源由 main 依清單裡的 id 查出，絕不採用頁面傳來的網址。同時只會有一個全螢幕視窗，RecordStuff 視窗關閉或隱藏時它也會立即結束（不淡出、不交回狀態），播放器停在原本的位置不繼續播放；使用者已離開、仍在淡出的視窗，在此時或有新的全螢幕開始時也會立即消失；只有使用者自己離開或頁面當掉的視窗，才會把焦點還給 RecordStuff 視窗；全螢幕頁面的 renderer 當掉時會關閉該視窗，並交還選單列與 Dock。全螢幕結束後一秒內的 Esc，以及按住 Esc 時的每個重複按鍵，都會在 main 被丟棄（`before-input-event`），因為 Chromium 曾把其中一下變成 close request，在頁面收不到可攔截的 keydown 時就關掉播放器。按住 Esc 的重複按鍵，以及在 Esc 關閉播放器或全螢幕結束後 1 秒內再按的 Esc（播放器關閉在兩種路徑都會觸發的 dialog `cancel` 上標記），都不會關閉任何東西，因此連按只會一次關一層；以往在頁面本身的全螢幕結束後多按幾下，會接連關掉播放器和視窗。無法播放的錄影（列出後已離開、損毀，或 Chromium 無法解碼的格式）會在播放器說明，並指向卡片選單的「開啟」。在這裡或別處丟到垃圾桶的錄影會關閉其播放器與選單並從清單消失；垃圾桶仍可復原，因此不再確認。該卡片或正在播放它的播放器有焦點時，焦點交給後一張卡片，沒有則前一張，再沒有則交給分頁；視窗不在前景時（例如在 Finder 刪除）也一樣，與移除失敗紀錄列時相同。離開「錄影檔」分頁會關閉卡片選單。

沙箱中的頁面從不持有路徑。Main 把資料夾列成 id（路徑的雜湊），並註冊一個具特權、可串流的 scheme `recordstuff-media:`，只為已列出的 id 提供 `video/<id>`（支援 byte range，播放器才能拖曳進度）與 `thumb/<id>`（JPEG）；頁面的 CSP 只允許從這個 scheme 載入圖片與媒體。檔案操作以群組 `recordingFile:<id>` 送出，只對已列出的 id 與提供的操作生效，且不經過偏好設定的儲存佇列，拖曳才能在滑鼠仍按住時開始。片長從 MP4 box 讀取而不解碼：擷取端寫的是 fragmented MP4，其 `mvhd` 為 0，所以片長是最後一個完整片段的 `tfdt` 加上其 `trun` 樣本長度（或 `tfhd`／`trex` 預設值），以該軌的 timescale 換算；過程只讀 box 標頭。資料夾在設定開啟或重新取得焦點、視窗開著時錄影存檔或儲存位置變更後（視窗關閉時沒有東西會顯示這份清單，而開啟視窗本來就會讀取資料夾）、存檔通知開啟「錄影檔」時（選取那段錄影之前）、丟到垃圾桶後，以及檔案操作失敗後重新讀取，讓回覆已反映離開資料夾的錄影。視窗開著時也會監看資料夾（`fs.watch`，macOS 為 FSEvents，事件驅動、不輪詢）：影片出現、變更或離開（例如在 Finder 刪除）時，在這一串事件結束 250 毫秒後重新讀取；錄影中持續變大的 `.recording.mp4` 與其他檔案不會觸發。視窗關閉或隱藏（⌘H）即停止監看，待命中的選單列 App 不監看任何東西、也不跑計時器。無法監看的資料夾（例如部分網路磁碟）仍在上述時機重新讀取。同一時間只讀取一次；讀取期間的請求（開啟設定時，顯示與隨之而來的焦點各請求一次）共用其後的一次讀取。尚未讀到的片長在清單顯示後才讀取，邊讀邊更新（最多每 500 毫秒一次），長錄影很多的資料夾也會陸續顯示；無法讀取的資料夾會直接說明，而不是看起來像空的。

## 錄影快捷鍵

來源：[hotkey.ts](../../../src/main/hotkey.ts)、[shortcuts.ts](../../../src/main/shortcuts.ts)、[shared/hotkey.ts](../../../src/shared/hotkey.ts)、[index.ts](../../../src/main/index.ts)。計畫 016 加入全域開始／停止快捷鍵：其他 App 在最前景時也能切換錄影，而且讓沒有視窗的程序有一個系統層級入口，可供無人值守驗收使用。

RecordingHotkey 包裝 Electron `globalShortcut`。按下快捷鍵呼叫與 tray「點一下就錄」相同的 `toggle` 函式，所以 `Recorder.toggle()` 仍是唯一決策點：idle 開始、倒數中取消、recording 停止、needsPermission 重發權限通知；start 已持續一秒時，會和「取消錄影」一樣取消這次 start（plan 065）；start 的第一秒內與 stopping 期間則忽略。每次按下都先寫 log `hotkey: <accelerator> pressed` 再 toggle；被忽略的按鍵另寫 `recorder: session <id> toggle ignored while starting (<n> ms after the start)` 或 `… while stopping …`，所以沒有作用的按鍵也會出現在 log 中（見[錄影設計](recording.md#倒數)）。`apply(settings)` 先釋放前一個註冊再註冊新的，更改時不會同時有兩個組合鍵生效；`dispose()` 在 will-quit 執行。

使用者在 「設定」視窗的「快捷鍵」欄位選一組建議快捷鍵、「自訂快捷鍵…」或「關閉」（與品質相同，只在 idle／needsPermission 可改）。預設 `CommandOrControl+Shift+1`（macOS 顯示 ⇧⌘1，其他平台 Ctrl+Shift+1），2026-09-21 由維護者決定。全域快捷鍵優先於最前景 App，因此預設必須是常見 App 都不會預期的組合。最直覺的 ⇧⌘R 因此被否決過兩次：2026-09-19 的衝突檢查發現它是 Chrome／Firefox 的強制重新載入、Safari 的閱讀器、Zoom 的本機錄影，在瀏覽器按下去會變成開始螢幕錄影而不是重新載入。既有使用者若已選用它則保留，顯示為自訂；不再列為建議選項。數字鍵是比較安靜的區段 — macOS 以 ⇧⌘3/4/5 佔用截圖與螢幕錄製，而 App 綁定的是不加 Shift 的 ⌘1…9（分頁與檢視模式）— 但 ⇧⌘1 尚未經過同樣逐一 App 的查核，那屬於原生驗收範圍。前一個預設 `CommandOrControl+Alt+Shift+R` 在 2026-09 已驗證於 Chrome、Safari、Firefox、Finder、Xcode、VS Code、Slack 與 Zoom 均未被佔用，現在僅保留既有使用者已儲存的值，不另列替代選項。舊版曾提供的每一組快捷鍵都仍然有效，由相容性測試檢查；選單只提供 `DEFAULT_HOTKEY`。自訂值由 `validateAccelerator` 驗證：至少含 CommandOrControl 或 Control，可加 Alt／Shift，只能有一個支援按鍵、不可重複修飾鍵、長度最多 64 字元，並排除少量 macOS 保留組合。標準順序為 CommandOrControl、Control、Alt、Shift、按鍵。不合法的儲存值仍回預設並記 warning。

「自訂…」以實體 key code 錄入字母、數字、F 鍵與標點，並支援空白及方向鍵（Windows 的字母鍵改錄它輸入的字母，見下文）；不支援的鍵區（含數字鍵盤）拒絕錄入。Shift 標點別名會先轉成 Shift 加基礎鍵，再檢查保留組合。保留組合依平台而定（plan 064）：macOS 保留 ⌘Tab、⌘Q、⌘W、⌘Space、⇧⌘3–6，以及截圖到剪貼簿的 ⌃⇧⌘3、⌃⇧⌘4 與 ⌃⇧⌘6（「macOS 已保留這個組合。」）；其他平台拒絕 Ctrl+Tab、Ctrl+Q 與 Ctrl+W，不論編輯器送來的是 `Control` 還是 `CommandOrControl`（「其他 App 會使用這個組合。」），沒有 Ctrl 的組合顯示「快捷鍵需要包含 Ctrl。」。兩個平台都拒絕所有 App 共用的編輯按鍵（「其他 App 會使用這個組合。」），因為全域快捷鍵一旦用上它，所有 App 都會失去這個按鍵，貼上就會變成開始錄影：macOS 上是 ⌘X、⌘C、⌘V、⌘A、⌘Z 與 ⇧⌘Z（⌃ 在那裡是獨立的按鍵，⌃C 仍可選），其他平台是 Ctrl+X、C、V、A、Z、Y 與 Ctrl+Shift+Z；已儲存的這類組合會像其他不支援的值一樣，帶著警告退回預設值。讀取設定檔時也用同一個平台判斷，因此 `CommandOrControl+Shift+3` 與 `CommandOrControl+Space` 在 Windows 的設定檔中代表 Ctrl、會保留，在 macOS 的設定檔中代表 ⌘、會回到預設值；macOS 的 `Control+Shift+3` 與 `Control+Space` 仍和以前一樣有效。快捷鍵群組是唯一可傳值的控制項；main 重新驗證並標準化後才儲存。Escape、Tab／Shift+Tab 移出、點擊其他位置、視窗失焦／關閉、renderer 結束與 15 秒逾時都取消錄入。編輯器會說明 15 秒限制；尚未送出儲存就逾時時，卡片會顯示並朗讀本地化提示，說明快捷鍵未變更及如何重新編輯。已送出的儲存可以晚於 lease 結束，不能顯示這項逾時警告。main 先解除 OS 註冊才確認開始錄入，完成或取消後恢復；退出時清除註冊。每次錄入是一份由發起視窗持有的 lease，與它可能啟動的設定交易分開。取消、失焦、逾時、關閉、renderer 失敗、錄影鎖定與退出都立即釋放它，即使已確認的儲存仍在寫入，並恢復當下已提交的註冊。釋放可重複呼叫；舊視窗晚到的事件或較早的儲存完成時，只結束自己的 lease，不會結束新視窗的錄入。已確認的儲存在視窗關閉或當掉後仍會完成；尚未確認的草稿絕不送出。`AppShortcuts` 持有兩個註冊與下述「先保存再註冊」的順序。錄影期間整個群組鎖定。不合法組合顯示在地化原因且不改設定；設定快捷鍵的組合與其他保留組合一樣，按下當下就被拒絕，編輯器保持開啟可以再試，main 也會再拒絕一次。「關閉」保留自訂值，仍可直接選回。錄入按鈕可用鍵盤操作；目前狀態放在其無障礙名稱，狀態變化則透過面板唯一的 `#feedback` 宣告區朗讀，不另設 live region。編輯器開啟期間 main 會隱藏卡片的註解與診斷，關閉時若回來的是同一組內容就不再朗讀；註解與診斷原因相同時只讀一次。

在 macOS 上，全域快捷鍵依實體鍵位註冊。Windows 則依 virtual key 註冊，而 virtual key 跟著配置的字母走（AZERTY 標示 A 的鍵是 VK_A，位在 US 的 Q 位置），因此編輯器把字母鍵錄成它輸入的拉丁字母；只有該配置在那個位置不輸入拉丁字母時才錄 US 位置，而 Windows 在那裡保留的也正是 US 的 virtual key（2026-10-05；未在 Windows 實機驗證）。在 macOS 上，main 會在 app ready 之前停用 Chromium 的 `LayoutAwareGlobalHotkeys`（[hotkey.ts](../../../src/main/hotkey.ts) 的 `physicalHotkeyFeatures`，並與命令列上既有的 `disable-features` 清單合併）。這個功能開啟時，Chromium 152 會把快捷鍵綁到當下配置中輸入該字元的鍵，每次切換鍵盤都重新註冊。注音的 ZhuyinBopomofo 配置在數字列輸入注音符號，預設的 ⇧⌘1 因而被移到數字鍵盤，而編輯器拒絕數字鍵盤。現在改用編輯器所記錄的 US 固定位置註冊，與 Cap 透過 `global-hotkey` 的做法相同。因此在 Dvorak、AZERTY 等非 QWERTY 拉丁配置下，字母快捷鍵是 US 位置，而不是鍵帽上的字母（[決策](decisions.md)、[plan 043 結案](../verification/history-2026-09.md#plan-043-結案--2026-09-26)）。`pnpm acceptance:shortcut-layout` 會在數字列不輸入數字的配置下檢查建置好的 App，若註冊又跟著配置走就失敗（[工具](tooling.md#鍵盤配置快捷鍵檢查)）。

`pnpm acceptance` 以 macOS key code 送出數字、空白、方向鍵、F1–F20 與常見未加 Shift 的標點，字母則以輸入的字元送出；其他組合會在開始錄影前明確報錯並列出快捷鍵。由於註冊依實體鍵位，以 key code 送出的鍵在任何輸入法下（包含注音）都能觸發已註冊的快捷鍵。以字元送出的字母，只有在該字母位於 US 位置的配置（例如 ABC 與注音）才會按到同一顆鍵；在 Dvorak 或 AZERTY 下，runner 會按到別的鍵。

OS 拒絕註冊（其他 App 佔用，或 `register` 擲出）不會被吞掉：寫 log `hotkey: registration failed for …`、在 Settings → 快捷鍵顯示「這個快捷鍵可能被其他 App 佔用。」並提供重試，同時發出通知，點擊通知會開啟 Settings 的「一般」分頁並聚焦快捷鍵控制項；tray 選單的「開始錄影」旁不再顯示快捷鍵。設定仍會保存，使用者的選擇在重啟後保留；tray 照常可用。關閉快捷鍵不影響 tray 行為，並記住組合鍵，重新開啟即還原。更改快捷鍵先保存再註冊：寫入失敗保留舊註冊並通知「無法儲存快捷鍵設定」。若寫入期間開始了錄影，註冊變更會延後（`request` → 下一次回到 settled 狀態時 `flush`），讓開始這次錄影的組合鍵仍能停止它；期間選單把已保存的選擇顯示為無法使用。

`pnpm acceptance:shortcut` 以隔離 Electron 驗證註冊失敗回報與跨程序重啟保留選擇，並檢查程序、視窗、快捷鍵與臨時資料清理。通知斷言觀察呼叫，不驗證 macOS 橫幅送達；也不保證偵測所有其他 App 攔截按鍵的情況。Plan 020 依維護者接受此證據結案，真實 OS 衝突與通知橫幅保留為未測限制，詳見[結案紀錄](../verification/history-2026-09.md#plan-020-結案--2026-09-23)。

## 語言

來源：[i18n.ts](../../../src/shared/i18n.ts)。預設為英文 en，從沒有語言欄位的舊設定檔升級時也一樣，不自動沿用 OS 語言；可由「設定 → 一般 → 語言」切換 English 或繁體中文 zh-TW。英文文案為具型別的 key，ZH_TW 對應完整繁體中文模板，translate 代入具名 placeholder，編譯器要求每個 placeholder 都有值。

TrayContext 提供目前語言，通知建立時讀當前 context；已發送的 OS 通知不追溯改寫。語言操作排入 SettingsStore 保存佇列，成功後才更新記憶體與刷新選單，失敗保留舊語言並以原語言通知。錄影中可切換，但不改來源、品質快照、位置或錄影狀態。

選單標籤、tooltip、權限說明、資料夾對話框標題、App 錯誤摘要與通知都有翻譯；診斷細節與開發工具輸出維持英文，技術錯誤細節留在 log，不以未翻譯片段混入中文錯誤通知。macOS 原生權限對話框跟隨系統語言設定，而不是 App 的語言選項。

## 螢幕權限

來源：[permission.ts](../../../src/main/permission.ts)。只在 macOS 建立 PermissionWatcher。

1. 每 5 秒及 activate 時檢查 `getMediaAccessStatus('screen')`，不依賴無視窗 App 的 activate 一定出現。這一段不會跳提示、也不會產生任何物件，所以輪詢很便宜。
2. 未 granted：清除驗證快取與待執行的重試，發 needsPermission；每個程序最多主動呼叫一次 getSources，以便系統註冊與提示。
3. granted 但未驗證：用 getSources 查是否有螢幕，避免只相信設定開關。驗證 4 秒仍未回應時顯示重啟指引（needsRelaunch），但該呼叫仍佔著名額：期限無法取消 getSources。
4. Watcher 發出的 getSources（提示或驗證）同時最多一個未完成；等待期間只輪詢第一段。提示進行中才授權時，等提示結束後再驗證；提示的結果永遠不算驗證。
5. 查得到來源就快取成功；失敗則 needsRelaunch，並從該次失敗完成時起退避重試：5、10、20、40 秒，之後每 60 秒。撤銷授權會重設退避。
6. 撤銷授權、擷取實際被拒（markRelaunchRequired）與 stop() 都會開始新世代：舊世代的驗證晚到時只記 log 並忽略，接著重新驗證。stop() 移除 interval、activate listener 與兩個 timer；仍未完成的呼叫保留到它自己結束。

只有第一段會被輪詢，而讓這件事安全的正是「第二段成功一次就快取整個程序」。Cap 曾經長期輪詢對應的 macOS 呼叫 `SCShareableContent`（它會實體化系統上每個視窗、App 與顯示器），整個程序生命週期每次呼叫都洩漏，約 15 MB／分鐘，直到 macOS 耗盡 swap（[CapSoftware/Cap issue #2023](https://github.com/CapSoftware/Cap/issues/2023)，於 0.5.9 以「Memory growth while idle on macOS」修正）。這裡採用的就是他們事故後的設計：便宜的 preflight 可以自由輪詢，昂貴的驗證成功一次即快取、序列化執行，失敗後至少等一個輪詢週期（從完成時起算）才重試，連 5 秒與 4 秒兩個常數都相同。Cap 也會讓 `ShareableContent::current` 逾時，但未證明丟棄該 future 會取消 macOS 請求，所以 RecordStuff 持有真正的 promise，而不是再送替代請求（plan 027）。永遠不返回的呼叫無法在同一程序內恢復：指引是重新啟動，讓它隨程序結束。執行期撤銷仍由第一段、由擷取嘗試本身、以及實務上 macOS 要求 App 重啟三者抓到。撤銷與重新授權若都落在兩次輪詢之間就觀察不到，之前開始的驗證仍可能被套用。

只有狀態改變才通知 Recorder。Recorder 一律保存最新權限狀態，starting、recording、stopping 期間也一樣，但不因此打斷正在錄的 session。每次回到非忙碌狀態（存檔、擷取失敗或啟動失敗）都依保存的狀態決定 idle 或 needsPermission，因此 session 中只通知一次的撤銷不會遺失，同一 session 內之後又授權也不需要再次通知。權限恢復後，Recorder 還原 needsPermission 不帶的 idle 資訊（outputDirUnavailable，期間已改儲存位置則不還原）。期間完成的存檔仍會通知，見通知一節。實際軌道結束、擷取失敗或 OS 要求退出時，走錄影的收尾流程。在系統設定撤銷權限並選 macOS 的「稍後」後，`getMediaAccessStatus` 對執行中的程序仍回報已授權，但擷取完全列不出任何螢幕；因此 macOS 上若有接上螢幕、擷取請求卻找不到任何來源，會回報為 `permission_denied` 而不是 `no_display`，進入需要重新啟動的狀態與其重新檢查（plan 035 D2）。

開系統設定使用固定 ScreenCapture URL，不自動修改 TCC。缺權限選單始終提供重新啟動，因為執行中的程序可能察覺不到新的授權。系統音訊是另一項授權，螢幕 granted 不代表音訊可用；由 renderer 的音軌檢查處理拒絕。首次授權、拒絕、復原與撤銷的證據見[驗證紀錄](../verification/README.md)。

## 設定與儲存位置

來源：[settings.ts](../../../src/main/settings.ts)、[quality.ts](../../../src/shared/quality.ts)。

```json
{
  "version": 3,
  "outputDir": "/Users/example/Movies/RecordStuff",
  "quality": {
    "videoQuality": "standard",
    "resolutionCap": "source",
    "frameRate": 30
  },
  "language": "en",
  "hotkey": { "enabled": true, "accelerator": "CommandOrControl+Shift+1" },
  "notifications": true,
  "countdown": 3,
  "countdownSound": true
}
```

`language` 是相容新增欄位：舊檔未填時預設 en；不支援的值回 en 並記 warning，但保留合法位置與品質。`hotkey.accelerator` 必須通過共用快捷鍵驗證器；v3 檔缺少或不合法的 hotkey 區塊回預設快捷鍵並記 warning，保留其他欄位。`outputDir` 必須是非空絕對路徑。版本 1 可讀，補預設 quality；版本 1／2 補預設快捷鍵（各記 warning），下次保存寫成 v3。整份無效／未知版本／路徑無效回預設並記 log；僅 quality 壞掉則保留合法 outputDir，重設品質。檔案存在卻無法讀取、解析或使用（例如較新版本寫下的檔案）時，第一次寫入前（包括啟動時更新檢查自動寫下的嘗試時間）會先把它保留為 `settings.json.unreadable`，使用者的選擇不會被預設值靜默取代。先前保留的副本不會被取代：該名稱已被占用時，改用下一個空的 `.unreadable.1`、`.unreadable.2`…；無法保留時拒絕這次寫入，原檔留在原處。舊 audioQuality 額外欄位不參與目前設定。`notifications` 與 `updates` 同屬相容新增欄位：缺少時讀為 `true` 且不記 warning，因為在這個開關存在之前寫下的檔案並不是壞檔；非布林值同樣讀為 `true`，但會記 warning。`countdown`（plan 040）同樣是相容新增欄位，不升版本：缺少時靜默讀為 3 秒，讓既有使用者也套用預設值；0、3、5、10 以外的值讀為 3 並記 warning。`countdownSound`（plan 046）也是相容新增欄位：缺少時靜默讀為 `true`，即維護者選定、也套用到既有使用者的預設值；不是布林值時讀為 `true` 並記 warning。

保存以 Promise 佇列依「上一份成功提交的設定」合併更新，避免連點遺失前一次修改；先寫入並 fsync `settings.json.tmp` 再 rename，成功才切換記憶體。單次失敗會移除暫存檔並拒絕自己的 caller，後續儲存仍可執行。rename 前先 fsync，可避免當機或斷電後留下空白或半份的 settings.json；由於沒有目錄 fsync，剛完成的修改仍可能退回前一份檔案。

更改位置使用原生選資料夾對話框，macOS 先 focus 以免藏在別的視窗後方。保存設定成功會清除 idle 的位置錯誤旗標並刷新選單；真正能不能寫入於開始錄影時用 probe 驗證。沒有背景自動改存預設位置。

Tray 的儲存位置項目（[output-folder.ts](../../../src/main/output-folder.ts)，plan 033）遇到既有資料夾時照舊以 Finder 開啟。預設的 `Movies/RecordStuff` 要到開始錄影才會建立，所以開啟時也會建立它：只建這一層、使用非遞迴的 `mkdir`，而且上層必須存在並且是資料夾。不存在的自訂資料夾一律不重建：它可能在未連接的磁碟上，重建同一路徑會讓之後的錄影寫到系統磁碟。以下情況都會顯示一則在地化警告：路徑是檔案、預設資料夾的上層不存在、建立被拒、路徑無法讀取，以及 Finder 開啟失敗（`shell.openPath` 回傳錯誤字串或 reject）。警告列出完整路徑，有錯誤時附上詳細資訊，並提供「更改儲存位置」與「取消」。更改沿用上方的選資料夾流程與它的鎖；取消什麼都不改。RecordStuff 本身被拒絕存取某個資料夾時，仍會請 Finder 開啟，因為 macOS 的隱私資料夾可能拒絕 App 而不拒絕 Finder；之後 Finder 也失敗，才顯示權限警告。開啟永遠不寫入 settings.json。同一時間只進行一次：重複點擊會併入進行中的那次，警告開著時只把它帶到前景。每次失敗也會連同路徑寫入 log。錄影維持自己的 `mkdir -p` 與寫入 probe。

品質、倒數、倒數音效與快捷鍵只能在 idle／needsPermission 修改；每個 session 保存自己的品質與倒數快照（包含音效）；autorecord 永遠不發聲。session 啟動、倒數、錄影或存檔期間不能變更儲存位置：它的暫存檔已在那裡開啟。設定檔即使有其他平台不開放的 60 fps，effectiveQuality 只調整本次有效值，不重寫設定。

## Log 與診斷

來源：[log.ts](../../../src/main/log.ts)。macOS 目前路徑為 `~/Library/Logs/recordstuff/recordstuff.log`；設定為 `~/Library/Application Support/recordstuff/settings.json`。路徑由 Electron app 名稱與 `getPath` 決定，產品顯示名稱仍是 RecordStuff。

每行為 `[UTC ISO 時間] 訊息`。啟動時記 App／Electron／平台版本、本次啟動的 run id、outputDir、品質、packaged 與 executable；每次錄影記 session、狀態、capture report、first chunk、saved（含提前停止原因）／failed、停滯與低空間警告及 writer 積壓、改報為已保留磁碟錯誤的啟動失敗，以及啟動時找到的中斷 sentinel。`power: suspend` 與 `power: resume` 會記下進行中的 session 與狀態；每次錄影前後分別有 `power: keeping the display awake (blocker n)` 與 `power: display may sleep again (blocker n)`，`notification: held during sleep: …` 表示某則通知正在等待醒來。Log 含本機路徑，但不寫入媒體內容。

Session record（plan 029）。run id 由啟動時間加 pid 組成（例如 `20260925T101530123Z-4242`），只出現在 `start:` 行，一般行不加前綴。App 在人類可讀的 capture、`saved` 與 `failed:` 行旁，每個事件另寫一筆有版本的 record：`session-record: {"v":1,"run":…,"kind":…}`。種類有 `capture`（session、要求品質、capture report）、`saved`（session、最終路徑、錄影與要求停止時間、提前停止原因）、`failed`（session、code、detail、檔案結果、保留與暫存路徑、時間；沒有留下檔案也會寫）與 `refused`（preflight 拒絕，不指名任何 session）。JSON 讓含空白、引號或換行的路徑維持在一行跳脫後的內容。失敗收尾可能在下一個 session 開始後才結束，完成順序不是身分，所以 Recorder 的終止事件帶著 session。開發用分析器依 run 與 session id 配對錄影；該次啟動有寫 record 時只讀 record，不會把兩種形式算成兩個結果。舊 log 不改寫。

所有訊息先送 stdout。檔案在下次追加前若超過 5 MiB，將舊檔依序移到 `.1.log`～`.3.log`（開發 runner 以檔案身分 cursor 跟過輪替，見 [tooling](tooling.md#選擇驗收範圍)，政策本身不變）；檔案寫入經由一條序列化、上限 1 MiB 的非同步佇列，每行都不必等待磁碟；退出路徑會在時限內 flush。作用中檔案的大小每個程序只讀一次，之後自行累計，所以每行只有一次 append、沒有 stat。磁碟已滿或 logs 資料夾被刪除時只略過檔案行：下一行會重新建立資料夾，寫入成功後檔案會記下漏掉幾行。輪替被其他程序擋下時（Windows 不允許重新命名被檢視器或防毒程式開著的檔案），繼續追加到作用中的檔案、在檔案中記一次原因，並在再寫入 512 KiB 後重試。其他檔案寫入失敗則讓本程序停用檔案 log，只報 stderr 一次並繼續 stdout。主程序第一個未捕捉例外另外開錯誤對話框，但會等錄影工作 settle 後才開（[對話框與 main 的 event loop](#對話框與-main-的-event-loop)）；之後的例外與 unhandled rejection 只留 log，反覆發生的錯誤不會疊出多個對話框。啟動在完成佈線前失敗時，會記下原因、顯示同一個對話框後結束程序，因為沒有 tray 的選單列 App 沒有其他退出方式。

「顯示 log」（2026-10-04 起在「一般 → 疑難排解」）優先選取檔案，不存在則開 logs 資料夾，兩者都開不了時會說明。存檔通知會開啟「錄影檔」並帶出那段錄影；若使用者之後移動或刪除了它，「錄影檔」顯示資料夾現有的內容，log 記下檔案已不在。兩者都不影響正在錄影的工作。開發 Electron.app 與安裝的 RecordStuff.app 是不同的權限主體；判讀授權或失敗前先核對 executable。

## 更新檢查

[updates.ts](../../../src/main/updates.ts) 獨立管理更新檢查生命週期。「設定 → 一般」提供「檢查更新…」、檢查結果與「啟動時檢查更新」。結果不改變 Tray 標題，也不開啟對話框。只有一種情況會發通知（維護者 2026-10-03 決定）：啟動檢查發現使用者尚未被告知的新版時，App 發出一則通知「RecordStuff {version} 已推出，按一下開啟下載頁。」，點擊後直接開啟官網下載頁（不經由 `openUpdate`，因為它的目的地取決於點擊當下的檢查狀態），但遵守同一個鎖定：啟動錄影、錄影中、存檔或結束中點擊時不開啟任何頁面，只寫入 log。手動檢查顯示過的版本視為已告知，因此手動檢查不發通知，之後的啟動也不再為該版本通知；更新的版本會再通知一次。已告知的版本只會往前：過期的來源提供比已告知更舊的版本時，既不通知也不會把它調低。這則通知遵循通知開關與睡眠暫存，錄影期間被延後的結果在顯示時才通知。通知開關關閉時，啟動檢查不發通知，也不把該版本記為已告知，因此之後開啟通知再啟動時仍會通知。啟動錄影、錄影中與存檔時停用更新操作，檢查及待顯示結果延至 idle／needsPermission。

設定版本 3 新增可選的 `updates: { enabled, lastAttempt, notifiedVersion? }`。舊檔預設開啟且無檢查紀錄；`notifiedVersion` 是已告知使用者的最新穩定版本，告知前不寫入，無效的值會捨棄並寫入 log 警告。1.2.0 及更早的版本儲存時會刪掉它，所以降版後同一版本可能再通知一次。原子、序列化寫入保留其他設定。發出網路請求前保存嘗試時間，失敗亦計入，避免重開繞過 24 小時限制；系統時鐘回調造成的未來時間戳視為應重新檢查。手動檢查不受此限制，時間戳寫入失敗時記錄錯誤後仍繼續連線。App 執行期間沒有輪詢計時器。關閉偏好只影響啟動檢查。

App 注入 Electron `net.fetch`，採用 Chromium 網路層及系統代理／PAC 設定；單元測試注入測試用傳輸。檢查先讀取 `https://record.ericts.com/release.json`，失敗改查儲存庫的 GitHub latest-release API。Windows x64 上只讀 GitHub latest-release API，且只接受帶有 `RecordStuff-<version>-x64-unsigned-setup.exe` 的 release，因為 feed 維持已安裝 macOS App 解析的格式、只描述 DMG；在沒有發布資產的平台上，檢查找不到相容的 release。這條 Windows 路徑只有單元測試涵蓋。每個來源最多等待 8 秒，結束 App 時取消請求。與 `app.getVersion()` 比較穩定語意版本；不相容的產物、無效資料與預覽版不會產生更新提示。啟動檢查失敗恢復先前選單並寫 log；手動失敗提供發布頁與重試。成功顯示本地檢查時間，或顯示新版並開啟固定官網下載頁；下載、取代仍為手動。

## 通知開關

`PermissionNotices` 讓同一次權限拒絕只發出一則通知：失敗結果先到就顯示失敗通知；權限撤銷已先改變狀態時，則保留權限通知。兩種情況都保留失敗紀錄與復原操作。後續權限變更，以及直接回應使用者操作，仍會通知。

「設定 → 一般」提供「通知」開／關；macOS 的「開啟通知設定…」按鈕就放在同一張卡片內，讓開關與可能凌駕它的系統權限讀起來是同一個決定，而不是兩個無關的設定。`AppTray.show` 在詢問作業系統之前先檢查這個開關（睡眠保留在它之前，被保留的通知真正顯示時才套用開關），並寫下 `notification: turned off in settings, dropped: …`，因此單一布林值管轄 App 主動發出的每一則通知 — 存檔完成、錯誤、新版通知，以及各種寫入失敗提示。只有直接回應使用者自己操作的通知不受它限制：延後的退出、錄影工作進行中發現的儲存位置問題，以及缺少螢幕權限時回應點擊或快捷鍵的權限通知。錄影進行中這個開關與其他偏好一樣鎖定。

App 刻意不映射作業系統的通知權限。Electron 沒有任何方式可以讀取：`systemPreferences.getMediaAccessStatus` 只接受 `microphone`、`camera` 與 `screen`，而 `Electron Framework` 二進位中不存在 `getNotificationSettingsWithCompletionHandler`。其中確實存在 `requestAuthorizationWithOptions:completionHandler:`，所以 Electron 是在 `Notification.show()` 內部向 macOS 請求授權 — 全新安裝的第一則通知就是觸發系統提示的那一刻。`UNUserNotificationCenter` 只在狀態為 `notDetermined` 時提供該提示，而狀態按 bundle ID 保存、重新安裝 App 也不會重置，因此顯示提示的機會一輩子只有一次，被拒絕之後就 App 而言即為終局。所以這次機會花在首次啟動，由那則同時告訴使用者選單列 App 位置的首次啟動提示來使用：啟動正是 macOS 已經在為這個 App 索取螢幕錄製權限的時刻，通知的請求因此落在同一個脈絡裡，而不是出現在使用者第一次錄影結束的瞬間。啟動時缺少螢幕權限的話，第一則通知是權限通知，而承諾「點一下就錄影」的首次提示會等到第一次真的能錄影的啟動才顯示。開關維持預設開啟 — 一個從不說自己存好了的錄影工具讀起來像壞掉，而一個使用者永遠找不到、從未動用的提示機會，並不比被拒絕好。把開關關掉再打開同樣會送出確認通知，那也是可重複執行的送達測試。狀態列必然要宣稱一個 App 讀不到的權限狀態，所以群組的 ⓘ 改為標示恢復路徑 —「系統設定 → 通知 → RecordStuff」— macOS 的操作按鈕則直接開啟該面板。關閉開關會停止發送 OS 通知；錄影失敗仍顯示於選單列與下述「失敗紀錄」區塊。

此設計沿用 Cap（`apps/desktop/src-tauri/src/notifications.rs`）：送出路徑只檢查一個 `enable_notifications` 布林值，別無其他。Cap 另外會以 `isPermissionGranted()` 管控開關，該 API 由 `@tauri-apps/plugin-notification` 提供，Electron 沒有對應品；這段落差改由 ⓘ 說明承擔。Plan 019 最初實作了通往 macOS `UserNotifications` 的 Node-API 橋接來補上它，後來撤回：該橋接使得載入失敗（架構不符或最低系統版本過新的 `.node`）會靜默壓制每一則通知，連 Electron 原本會發出的隱式授權請求也一併消失，比完全沒有狀態資訊嚴格更糟。

網站靜態端點由已線上驗證的 manifest 產生版本、tag、平台／架構、DMG 資訊、發布日期與可信頁面 URL。未驗證的預覽建置輸出錯誤物件，不宣告可下載版本。Vercel 快取 feed 五分鐘，App 請求不使用快取。`pnpm site:check` 比對建置 feed 與 manifest；Vercel 正式建置執行同一個 `pnpm check`，因此 `check-release.mts` 會檢查它之後提供的 `dist/` 中的 feed；部署 workflow 本身只上傳（`vercel deploy --archive=tgz --prod`），不再檢查實際提供的產物。不新增安裝識別碼、查詢參數、遙測、更新器依賴或簽章身分。

macOS 設定入口會開啟通知總覽，再選 RecordStuff 即可進入權限控制；plan 019 結案保留此路徑。一般設定值／文字更新保留既有表單控制項、焦點與捲動位置，只有分頁／結構改變才重建表單。僅因儲存而暫時鎖定的操作維持原本亮度，避免整個面板短暫變淡；錄影或平台限制造成的停用仍有停用外觀。

## 設定快捷鍵

macOS 的 ⌥⌘,，其他平台的 Ctrl+Shift+,（[hotkey.ts](../../../src/shared/hotkey.ts) 的 `settingsShortcut`；2026-10-05 之前其他平台也是 Ctrl+Alt+,，但 Windows 把 AltGr 當成 Ctrl+Alt 送出，因此在以 AltGr+, 輸入字元的配置下，所有 App 都會失去這個字元）透過 `openSettings` 開啟、還原並聚焦同一個設定面板，錄影中也可使用。

App 執行中再次開啟它也會這樣做（plan 053），讓選單列圖示被瀏海或擁擠選單列遮住的使用者有入口。第二個程序會在因 single-instance lock 結束前，以 `second-instance` 通知正在執行的程序；在 macOS 上，從 Finder、Spotlight 或 Dock 開啟執行中的 App 不會產生第二個程序，而是送出 reopen，Electron 以 `activate` 回報。兩者都經過 `handleAction("openSettings")`，因此結束中的 App 會忽略它們，已開啟的面板會被重用。通知點擊或面板自己的 `app.focus()` 只會讓 App 成為作用中（`did-become-active`），都不會開啟設定；權限監看的 `activate` 檢查不變。點擊仍可能以啟動的形式出現：開發版 bundle 執行中時點它的橫幅，macOS 會啟動登記在 /Applications 的那一份，約 0.5 秒後以 `second-instance` 通知執行中的 App。登記的那一份自己在執行時，點擊則以 reopen 抵達：在已安裝的 App 上，兩次點擊後 macOS 分別於 113 與 121 ms 送出 `activate`（plan 054）。因此通知點擊後 `NOTIFICATION_ACTIVATION_MS`（2 秒）內的這兩種事件都視為點擊造成的啟用而忽略，並寫一行 log；點擊本身的動作（例如擷取警告開啟設定）不受影響。[reopen.ts](../../../src/main/reopen.ts) 會記錄每次 reopen 以及設定是否開啟。它不會切換錄影狀態，也不佔用一般的 ⌘,。`settings-hotkey.ts` 獨立管理註冊，結束時僅釋放自己的組合鍵；選單只在註冊成功時顯示快捷鍵，失敗則以目前語言說明。

新選取的錄影快捷鍵不得與設定組合鍵在目前平台等價。既存設定若衝突，保留原值並優先維持錄影功能；從選單列選「開啟 RecordStuff」後變更或停用錄影快捷鍵即可恢復。自訂擷取期間兩個註冊一起暫停，lease 釋放（提交、取消、失焦、逾時、關閉或 renderer 失敗）時即恢復，不等待尚未完成的儲存；錄影中的設定鎖定不變。

### 螢幕偏好與診斷

設定 → 錄影設定 → 螢幕先列主螢幕，再列 `screen.getAllDisplays()` 提供的唯一已連接螢幕；開啟面板不列舉錄影來源、不要求錄影權限。預設跟隨目前主螢幕；指定選擇只在現有 version-3 設定中保存 id 與 label。版本 1–3 缺少欄位時採預設，無效值記警告並回退。空白名稱使用本地化的 id 名稱；面板只送 choice id，由 main 重新解析目前動作與名稱。

新增／移除／尺寸事件一律推進配置世代；閒置時立即刷新，忙碌時於結束後刷新。錄影期間不能變更選擇。缺失或重複的保存目標保留勾選但停用，仍可選主螢幕或有效目標恢復。閒置 tray 顯示健康的指定目標；tray 與設定區分目前不可用與上次失敗。上次失敗只留在記憶體，關閉通知仍顯示，只有成功開始錄影或成功保存不同選擇才清除。保存失敗保留偏好與診斷，並依通知偏好送出錯誤通知。不新增 tray 子選單或系統 picker；系統音訊政策不變。

外觀偏好提供「跟隨系統」（預設）、「淺色」、「深色」，位於一般設定，錄影期間亦可切換。Main 成功儲存後設定 `nativeTheme.themeSource`，即時套用原生視窗與 CSS 深淺色；啟動時讀回。舊檔缺少此欄位或值不合法時回到 system，不影響其他偏好。

## 錄影失敗結果

Recorder 在檔案清理完成前發出獨立 failure-status。Main 將每筆失敗及其確認狀態存入 `userData/recording-history.json`（version 2），獨立於通知偏好與錄影狀態。新錯誤排最前面；延遲清理只更新自己的 ID，不取代或重排其他紀錄。保留所有未確認紀錄與最近確認的 20 筆紀錄。這是失敗歷史，不是媒體資料庫或遺留檔案復原機制。

選單列仍只有一個項目。只要有未確認失敗，待命圓環就整合警示標記；錄影中的實心圖示與 REC 優先。選單顯示未確認筆數及「查看失敗紀錄」。左鍵照使用者的選擇運作，與其他狀態相同。「查看失敗紀錄」與錯誤通知會切到「失敗紀錄」分頁，只展開最新一筆未確認紀錄（全部確認時則為最新一筆），捲入視野並聚焦其標題，不自動確認；「開啟 RecordStuff」與其快捷鍵在新視窗開啟「錄影檔」、在已開啟的視窗保留目前分頁。開選單、關通知、成功錄影或等待，都不清除失敗。

失敗歷史有自己的設定分頁（plan 047）；「錄影設定」與「一般」都不再顯示，關於某個偏好的診斷（例如已選螢幕無法使用）仍留在該控制項旁。分頁依序顯示整份歷史的狀態行（載入中）、由新到舊的紀錄，以及作為註腳的保留說明；沒有失敗時顯示「沒有失敗紀錄。」。紀錄依日期標題分組（今天、昨天，之後為日期，不是今年才加年份），由 main 連同每列的短時間一併提供；紀錄直接放在視窗背景上，以兩端各內縮 10 px 的細分隔線區隔，警告色只保留給儲存警告與操作錯誤。每列標題有兩行：未確認標記（圓點加粗體原因，無障礙名稱含「未確認」，因此不只靠顏色，強制色彩模式下也看得見）、原因、時間與箭頭；接著是檔案結果。每列預設收合，同時只展開一列：展開另一列會收合原本的，處理中的儲存或操作依 ID 保留其狀態。展開後的細節縮排於標題下方，不重複標題或時間：依序是指引、檔名（完整路徑放在技術資訊中）、操作按鈕（「知道了」在最後，「從紀錄移除」只出現在已確認的列）、儲存中與錯誤訊息，以及「技術資訊」。標題是焦點目標：鍵盤焦點以細強調色邊框（共用的焦點粗細、6 px 圓角、無填色）框住整筆紀錄，並隱藏相鄰的兩條分隔線；焦點在展開列內的控制項時，列框改為 1 px 中性色，該控制項自身的邊框變成強調色。箭頭在 150 ms 內轉動，開啟減少動態效果時立即轉動。上下鍵可跨日期群組在標題間移動，Home 與 End 到第一與最後一列，Enter 與 Space 展開或收合。紀錄移到另一個日期群組時（例如跨過午夜），其標題或控制項保留焦點；「技術資訊」揭露元件在文字外側顯示共用的焦點線。缺少系統音訊（`no_audio_track`）的指引先提到 Mac 負載過重，再提到權限，因為兩種原因在擷取端看到的都是一開始就已結束的音軌（plan 040 的負載測試）；「開啟系統設定」與「重新啟動」仍保留。清理中停用「知道了」，不提供檔案定位。部分檔案顯示前及定位前重新檢查；未知或遺失路徑只是查找線索，不保證可播放或復原。檔案／資料夾／權限操作仍遵守錄影鎖定。普通更新保留各筆展開狀態與 ID，舊按鈕不會操作新紀錄。

「知道了」只在精確 ID 的處理完成後，成功保存確認狀態才收合該筆。每次「知道了」、「從紀錄移除」與「重試儲存紀錄」在完成時寫一行 log：`recording result: <action> <id> saved`、`failed (<io|blocked|tooLarge>)` 或 `refused (<pending record|not reviewed|… in flight|unknown record>)`，不含路徑或失敗細節，讓 log 與列上顯示的一致，並可依 ID 與紀錄對應；所有保留的失敗都確認後，才消除選單列警示。已確認紀錄可移除；手動移除或淘汰最舊已確認紀錄，都不刪影片或 log。確認與移除要等包含它們的快照成功寫入磁碟後才顯示；等待期間該筆顯示本地化的「正在儲存」文字，按鈕以 `aria-disabled` 保持可聚焦並忽略啟用，其他紀錄、偏好與錄影操作不受影響。確認／移除保存失敗時，維持先前可見狀態並在該筆顯示錯誤。「重試儲存紀錄」獨立保存整份歷史，不改變確認狀態，未確認與處理中的失敗亦可重試。任何成功保存都包含其他尚未存入磁碟的失敗。

焦點依操作開始時記錄的意圖還原，不依賴 `document.activeElement` 撐過等待：確認、收合或失敗後回到該筆摘要；移除後移到遞補該位置的紀錄，若沒有則移到新的最後一筆，並捲動到看得見的位置；移除最後一筆後回到「失敗紀錄」分頁，分頁隨即顯示空白狀態。使用者在等待期間移動焦點或視窗失焦時不搶回焦點，也不會移入其他紀錄的操作按鈕。失敗紀錄操作不排在偏好保存佇列後面，也不會結束快捷鍵擷取。

重啟不重發通知。中斷的 pending 清理改為無法確認；先前程序結束時（強制結束、當機、程序被終止或斷電）仍在錄影的 session，會在啟動時依其中斷 sentinel 回報一次，成為一筆未確認的 `app_terminated` 紀錄：「RecordStuff 在錄影期間未正常結束」，時間為該 session 的開始時間，指引說明檔案可能不完整且不會修復。其暫存檔路徑以下述「先前確認的部分檔案」方式重新檢查：只有該處存在非空檔案時才提供定位，否則為無法確認並保留路徑作為線索。它不發通知；紀錄保存後即移除 sentinel，因此確認後或再次重啟都不會重複出現。在那之前由 sentinel 保留這筆紀錄，所以它不算未儲存：歷史無法保存時（包括檔案無法讀取或來自較新版本）退出既不列出它，也不警告它會遺失，下次啟動會再次採用它（2026-10-05；之前每次退出都要求「不儲存並結束」）。不執行任何復原、重新封裝或修復。先前確認的部分檔案也先顯示無法確認，再以一次一筆、每筆兩秒期限檢查；逾時停止後續檢查，避免佔滿檔案系統工作執行緒。檢查成功恢復部分檔案狀態，同時保留期間的確認操作。無法存取的路徑保留候選資訊與先前確認資格，供下次啟動檢查；中斷清理不因找到位元組就升級成已確認保留。已移除的 ID 不會被延遲檢查或完成事件重新加入。

首次使用會把有效 `recording-result.json` v1 單筆紀錄移入獨立歷史檔案，保留舊檔。有效的空歷史不會再匯入舊資料。歷史損壞、超大或版本較新時記入 log 並拒絕覆蓋；後續保存呈現持久化警告。歷史驗證唯一 ID，序列化上限為 32 MiB；不會為了符合上限刪除未確認紀錄，超過就回報保存失敗，並非無限的永久儲存。

歷史透過 Node 非同步 `fs.promises`（libuv 執行緒池）以私有暫存檔、fsync 與 rename 寫入；主程序不等待磁碟。啟動時以非同步方式讀檔，載入完成前絕不寫入，期間到達的失敗依 ID 合併；設定在此之前顯示本地化的載入文字。單一負責者最多只有一個寫入進行中、一個合併後的後續寫入；每份快照都是完整歷史，會包含較早快照中的所有失敗與操作結果，完成時只結算該快照包含的 revision。較舊的完成結果不會清除較新未保存變更的警告。啟動檢查後未變更的歷史不重寫。

保存失敗仍在記憶體顯示新資訊，只有與上次保存內容不同的紀錄才顯示本地化警告。一般 I/O 失敗以單一 timer 自動重試：尚未保存時依序間隔 2、5、15 秒，之後每 30 秒；成功後重設退避，歷史已保存則停止，一段連續失敗只記一次 log 並記錄恢復。手動重試會立即開始，若已有寫入進行中則加入該次寫入，不會產生第二個 writer。無法讀取或較新版本的歷史不會重試或覆寫，警告會如實說明而非建議釋放磁碟空間；超過 32 MiB 上限時請使用者移除已確認紀錄。原子替換不保證斷電或磁碟已滿／不可寫時恢復，背景保存也不會增加磁碟吞吐量。跨重啟權限錯誤採歷史指引，僅目前權限仍需要時提供重新啟動。失敗 ID 使用跨程序 UUID。

寫入序列化留在主程序，不使用 worker；大型檔案解析已改用 worker（見下方稽核加固）。在 M1 Pro 上，32 MiB 上限的整份快照 `JSON.stringify` 約 40 ms，超過一個 16 ms 畫面；但把這份快照交給 worker 需要在主程序做成本相近的 structured clone，因此改為快取每筆紀錄的已編碼 JSON 與 fingerprint（紀錄不可變），歷史迴圈累積約 8 ms 工作即讓出事件迴圈。實測主程序最長單一 turn：寫入（含上限）最多約 10 ms；本輪稽核修復前，啟動讀取在上限時有一次約 38 ms 的 turn（單次 `JSON.parse`），3.8 MiB 約 6 ms，一般歷史約 2 ms。見[驗證紀錄](../verification/history-2026-09.md#plan-036-結案--2026-09-25)。

## 延後退出

正常退出會等待錄影與所有未完成磁碟工作，即使 tray 已 idle 也一樣。等待 13 秒後若仍有工作（期間 tray 會顯示正在結束），英文／繁中通知會提示 RecordStuff 保持開啟，請在存檔／清理完成後重試退出。通知開關關閉時也會顯示，因為它回應的是使用者自己的退出；橫幅是否出現仍由 macOS 通知權限與專注模式決定，log 兩種情況都會記下。由於橫幅可能看不到，tray 選單與 tooltip 也會在任何狀態加上一行簡短的「…暫不結束或重新啟動…」，說明是錄影工作還是設定／log 寫入，直到下一次狀態改變或退出要求，或擋住退出的工作完成為止（plan 056）。通知被拒時 log 會記下 Electron 的 `failed` 事件，但專注模式與畫面分享時被靜音的橫幅沒有任何訊號，所以這一行不依賴通知是否送達。plan 055 之前這是無視窗的資訊對話框，它開著時 main 的 timer 與 log 都會停住：它正好在錄影工作未完成時出現，曾讓 capture request 期限晚了 2 分 46 秒，直到使用者關閉才觸發（[紀錄](../verification/history-2026-09.md#plan-055-結案--2026-09-29)）。重複要求不能略過此判定；啟動中的擷取在延期後仍保留停止意圖。重啟只在退出獲准後登記，退出延期會取消該次重啟意圖。通知與 tray 提示都要求重試原本的操作（退出或重新啟動），不會把延後的重啟引導成一般退出。媒體工作不提供強制退出控制。

只有在媒體已安全、且持續拒絕新擷取時，退出與重新啟動才會嘗試保存最新失敗歷史，最多等待 5 秒（本機保存實測約 5–10 ms；32 MiB 上限低於 200 ms）。已保存就正常退出。若仍有寫入進行中，警告只提供「繼續等待／留在 App」，不提供退出，因為逾時不代表作業系統已停止寫入。若保存失敗且沒有寫入進行中，警告列出尚未存檔的紀錄筆數及其時間與原因（前五筆，其餘顯示數量），並提供「重試」、「留在 App」與獨立的「不儲存並結束」。歷史檔無法讀取、來自較新版本或超過上限時不提供「重試」，改以「留在 App」為預設，因為提示開著時每次重試都會以同樣方式失敗。選擇不儲存就結束會記 log，並在 App 結束前有上限地清空 log，再關閉歷史 writer。留在 App 會重新開放擷取與自動重試，並清除重新啟動意圖。重複要求加入進行中的嘗試並把提示帶到前景。退出不會附帶確認或保存任何紀錄，也不重播系統通知。強制結束與斷電可能遺失尚未存檔的失敗紀錄。

### 對話框與 main 的 event loop

原生對話框可能讓 main 完全停住（plan 055）。在 macOS 26.6 與 Electron 44.3 上以獨立 probe 量測：每個對話框開著時，都有 1 秒 interval、3 秒 timeout 與一次讀檔到期。結果無視窗的 `dialog.showMessageBox` 與 `dialog.showErrorBox` 會卡住 main 直到關閉：呼叫到那時才返回，期間沒有任何 tick、timer 或 I/O 完成。有 parent 視窗的 `showMessageBox` 會變成 sheet（隱藏的 parent 會被放上螢幕承載它），以及無視窗的 `showOpenDialog`，都會立即返回，timer 也準時（[紀錄](../verification/history-2026-09.md#plan-055-結案--2026-09-29)）。sheet 需要可見視窗，而選單列 App 只有在設定開啟時才有，因此延後退出提示改為通知而不是 sheet。所以退出流程在媒體工作未完成時不會顯示任何對話框。「未完成」指 recorder 的 `mediaPending`：仍有 session，或 session 留下的清理與存檔，這些可能比 idle 狀態更晚結束；`whenMediaSettled` 在其結束時 resolve，判定與退出等待的相同。其他對話框仍會阻塞，並避開這些工作（plan 056）：

- 未存歷史的退出提示：只在媒體已 settle、擷取仍被拒絕時顯示，不會有媒體期限到期；它需要明確回答。
- 儲存位置警告：回應對「在 Finder 中顯示」或「開啟資料夾」的點擊；存檔通知的點擊改為開啟「錄影檔」（2026-10-04）。opener 在媒體工作未完成時發現問題，會記 log，並改以標題「無法開啟儲存位置」的通知送出同一段文字；它與擷取開始的提示一樣會等畫面不再分享才送出，通知開關關閉時也會顯示，因為它回應的是使用者的點擊；資料夾選擇器仍留給 settled 狀態的 tray 與設定。送出前若開始新 session 或退出，通知會被丟棄，問題仍留在 log。settled 的 App 保留原本的警告與「更改儲存位置」選項。
- 權限面板 fallback：回應 settled 狀態（idle 或 needsPermission）下的點擊，此時沒有擷取在進行；當時若還有失敗錄影的清理未完成，它會等待回答，本身沒有期限。這是已接受的限制。
- 同步的 `showErrorBox`。啟動失敗的對話框出現在任何媒體存在之前。未捕捉例外的對話框每個程序最多一次，代表程式錯誤（[fault-dialog.ts](../../../src/main/fault-dialog.ts)）：先寫 log；settled 的 App 立即顯示；媒體工作未完成時則等它 settle，開啟前再確認一次。等待期間 tray 選單與 tooltip 顯示「發生未預期的錯誤，詳見 log。」因此若錯誤同時讓工作無法 settle，對話框就永遠不會出現，改由這行 tray 文字、log 與 recorder 自身的期限呈現。等待過的對話框可能在退出期間、媒體 settle 之後才出現，與未存歷史的提示相同。

資料夾選擇器不會阻塞，而且只在 settled 狀態開啟。

### 稽核加固

偏好協調集中於 preferences.ts：資料夾對話框去重，回傳時重新確認錄影操作是否允許。設定 getter 回傳副本，排隊寫入先快照呼叫端輸入。Log 與視窗尺寸改為非同步序列寫入；log 佇列上限 1 MiB，檔案輸出失敗仍保留 stdout。

無法讀取的歷史保留原檔並顯示載入錯誤。超過 1 MiB 的 JSON 在 worker 解析，並把每筆紀錄以 JSON 文字交回：交回物件結構時，main 的 structured clone 幾乎與解析一樣久（上限時 46 ms 中占 38 ms，2026-10-04），文字只需複製（13 ms），main 再於分段迴圈中逐筆解析。寫入編碼仍於 main 快取並分段。設定快取不可變的列投影，初始顯示 50 筆，每次明確追加 50 筆。單調遞增的 view revision 排除過時回覆，舊視窗不能污染新視窗的傳送快取。部分檔案的 metadata 檢查有兩秒 UI 等待上限；底層檔案系統操作仍可能稍後才完成。

已完成錄影的存檔通知可在 needsPermission 顯示。通知建構失敗不向外拋出，點擊時重新確認目前權限狀態，存檔點擊共用遺失檔案的替代流程。喚醒輪詢只在有待送通知時存在。快捷鍵衝突排除後，可用重試按鈕重新註冊。
