# 075 — Camera bubble set up in advance, with a layout preview

[English](075-camera-bubble.md) | [繁體中文](075-camera-bubble.zh-TW.md)

Status: planned; step 1 decided on 2026-10-14, implementation not started. Created: 2026-10-14. Priority: next (074 closed on 2026-10-16). Hard dependencies: 076, whose native engine leaves RecordStuff's windows out of recordings (D14) while recording the bubble; reuse 074's media-permission card and failure pattern instead of building a second one ([desktop](../docs/system-design/desktop.md), [recording](../docs/system-design/recording.md)). Execute the steps in order under [the plan index](README.md).

## Goal and boundaries

Let the user show their own camera in a recording as a bubble on the screen, whose width, height, corner rounding and position they set freely **before** recording, in a layout preview in the RecordStuff window that shows how the recorded screen will look. Success is: the preview shows the chosen display with the bubble at its real proportion and place, and the live camera inside it; width, height and rounding are each adjustable on their own (rounding from a sharp rectangle to a circle or capsule), all persisted; at the start the real bubble appears on the recorded display exactly where the preview put it, is in the saved MP4 exactly as on screen, and keeps that placement until the recording ends, though the user can hide and show it from the tray while recording; RecordStuff's own windows stay out of the recording; with the camera off nothing changes.

The bubble is a live window that screen capture records (what you see is what is recorded), as Loom, Apple's Presenter Overlay and Cap's Instant mode do. Out of scope: moving, resizing or reshaping the bubble while recording, a separate camera track or file and editing it afterward (Cap Studio, Screen Studio, Tella, Camtasia), a live video preview of the whole screen, background blur or removal, camera-only or full-screen camera modes, and Windows hardware (CI only).

## Is a layout preview a good design? (assessment)

Yes, as a to-scale layout of the chosen display with the live camera in place, not as a live video of the screen.

- **It is the only place to set things up in advance.** The maintainer wants everything decided before recording. Loom, Cap and Screen Studio let the user arrange a floating camera window on the real screen, which works because their recorder panel is open anyway; RecordStuff is a menu-bar app with no recorder panel, and its Settings window is where recording choices already live. The Screen card already draws the displays' arrangement (`src/renderer/settings/tabs/display-arrangement.tsx`), so the preview extends an existing control instead of adding a surface.
- **Few products have it, and the one that does pays for it.** Only OBS shows a composed preview of the output before recording, as a live canvas where sources are dragged and resized. Its known cost is the "hall of mirrors" when OBS's own window is on the captured display; the forum fixes are to move OBS, hide its windows from capture, or turn the preview off. Loom, Cap, Screen Studio, Tella and Camtasia show the camera alone (a floating window or a thumbnail) and leave the screen as the preview; Cap's main window shows only static thumbnails of each display.
- **A live screen preview would cost more than it tells.** It would capture the screen while idle (CPU, and it would contradict the rule that opening the panel never enumerates capture sources or asks for screen permission, [desktop](../docs/system-design/desktop.md#screen-preference-and-diagnostics)), and the Settings window would see itself. What the user needs to judge is where the bubble sits, how big and how round it is relative to the screen; a to-scale outline with the live camera answers that. An optional still snapshot of the display, taken only when the user asks, is offered as decision D5.
- **What it cannot show.** The preview is a model; the windows that will be on screen during the recording are not in it. A "Show on screen" action places the real bubble for a final check (decision D4).

## Current state

**What 076 provides (closed 2026-10-16).** Recording runs only through the native engine. RecordStuff's own windows are left out of every recording by the engine, those opened after the start included: ScreenCaptureKit's application filter on macOS (verified 2026-10-16: Settings opened during a recording was absent from its frames; the app's menu-bar menus are left out too, its status item stays) and `WDA_EXCLUDEFROMCAPTURE` on every window while an attempt runs on Windows (CI only). The bubble therefore needs the opposite: the engine has to record it while excluding the app's other windows (on macOS an exception in the filter, on Windows leaving that one window unprotected), which 075 still builds. The engine also captures one window, an area of the display and chosen apps (engine and tests only, no picker), and D6 hides the menu bar and Dock. The bullets below describe the state before 076: read their capture and protection facts as history.

- No code calls `getUserMedia` for video. The countdown overlay (`src/main/recording/countdown-overlay.ts`) is the existing pattern for a transparent, frameless, always-on-top, non-activating, click-through macOS panel on the recorded display, created at preparation and destroyed with the attempt; the locked bubble can use the same pattern.
- Screen capture records every visible window; no window uses content protection, so the bubble is recorded unless explicitly protected.
- Settings → Recording → Screen draws the displays' arrangement from `screen.getAllDisplays()` without touching capture (`display-arrangement.tsx`).
- RecordStuff's own windows are recorded today: none uses content protection, so the Settings window is in the video whenever it is open on the recorded display, and so are the menu bar and RecordStuff's icon in it. On macOS, `setContentProtection(true)` alone does not keep a window out of ScreenCaptureKit capture ([Electron's `setContentProtection` note](https://github.com/electron/electron/blob/main/docs/api/browser-window.md), [maintainer explanation, 2025-09-09](https://github.com/electron/electron/issues/48258#issuecomment-3269893618)); but Electron patches Chromium (`feat_filter_out_non-shareable_windows_in_the_current_application_in.patch`) so that a full-display `getDisplayMedia` in the same app excludes that app's protected windows, for those protected when the capture starts. On Windows it uses `WDA_EXCLUDEFROMCAPTURE`.
- `electron-builder.yml` lacks `NSCameraUsageDescription`; `resources/entitlements.mac.plist` lacks `com.apple.security.device.camera`, which the hardened runtime requires.

## Steps

### 1. Decide behavior (decided 2026-10-14)

Each decision lists what others do and the basis for the recommendation.

- [x] **D1 Shape: free width, height and rounding.** Others: Loom offers four fixed shapes; Cap's preview cycles round/square/full; only Cap's editor (Corners 0–100 over Square or Source) and Screen Studio ("Roundness") expose rounding as a value; Tella and Camtasia let the frame be cropped to any ratio in their editors; Screenity is a circle only. None found offers free width, height and rounding together before recording. Recommended, per the maintainer: width, height and rounding are three independent values. The preview has edge handles (width or height alone) and corner handles (both), plus fields or sliders for exact values; ratio buttons (1:1, 4:3, 3:4, 16:9) are shortcuts that set the height from the width; rounding is 0–100%, where 100% is half the shorter side (a circle on a square, a capsule otherwise) and 0% a sharp rectangle; default a square at 100%. Basis: the maintainer's requirement; Cap's editor shows one rounding value over any frame covers every shape the others list.
- [x] **D2 Corner style.** Others: Cap's editor defaults to Squircle and also offers Rounded; Loom names a squircle shape. Recommended: plain circular arcs (`border-radius`) first, and squircle only if Chromium's `corner-shape: squircle` works in the bundled Electron. Basis: squircle is a refinement two products value, but it must not need a custom renderer.
- [x] **D3 Size units and bounds.** Others: Cap's preview is 150–600 px tall, default 230; Cap's editor is 20–80% of the shorter side, default 30%; Loom has five steps; Tella S/M/L or handles; Screenity free with a 150 px minimum. Recommended: width and height each as a fraction of the recorded display's shorter side, 5–60%, default 20% × 20%. Basis: fractions keep the look when the display changes, as Cap's editor does; 20% of a 14-inch MacBook Pro's 982-pt height is about 196 pt, close to Cap's 230 px default; the minimum keeps a face recognisable, and the maximum leaves most of the screen visible because the bubble covers live content that cannot be moved afterward.
- [x] **D4 Where it is set up.** Others: only OBS sets the layout in an in-app composed preview; Loom, Cap and Screen Studio use a floating camera window on the real screen. Recommended: the layout preview in Settings → Recording is the place; the bubble is dragged and resized inside it, with snapping to corners and edges; a "Show on screen" action places the real bubble for a last check and closes after 60 s without interaction. Basis: the assessment above; RecordStuff has no always-open recorder panel to host a floating window.
- [x] **D5 What the preview shows of the screen.** Others: OBS shows live video and suffers the mirror effect; Cap shows one static thumbnail per display. Recommended: the display's outline at its real aspect, the menu bar's band on macOS, and the live camera in the bubble; no screen capture. Optional: a "Take snapshot" button that grabs one still of that display on request, as Cap's thumbnails do, which needs screen permission and is never automatic. Basis: keeps the panel free of capture and permission prompts.
- [x] **D6 When the camera is on.** Others: Cap opens the camera as soon as one is chosen and keeps it on until set to none; Loom shows it whenever its recorder is open; Screen Studio when a camera is chosen. Recommended: only while the preview is visible (Recording tab open with the camera on), while "Show on screen" lasts, and from preparation to stop. Basis: those products show the camera while their recorder panel is open, which is the same rule here; a menu-bar app must not keep the camera light on while idle.
- [x] **D7 During recording.** Others: Cap locks nothing in Instant mode, so its hover controls can appear in the recording (inferred); Loom hides its controls while recording; OBS stays editable. Recommended: position, size, shape and mirror are locked; the bubble draws no controls and is click-through, so it never catches a click meant for the app below; showing and hiding it stays available (D13). Basis: the maintainer's requirement, and anything drawn on the bubble is recorded.
- [x] **D8 Mirror.** Others: Zoom, Teams and Google Meet mirror only the user's own preview and send or record the picture unmirrored (Teams mirrors the self-view by default); OBS does not flip a camera unless the user adds a transform; Loom's "Flip camera" changes the recording itself and Loom advises leaving it off so text reads correctly; Cap's preview defaults to not mirrored. Tutorial creators mostly leave the face camera unmirrored, and some flip it so they appear to look toward the content when the camera sits in a corner (forum consensus, no authoritative source). Recommended: "Mirror in recording", off by default. The Settings preview shows the recording as it will be, so it follows that setting rather than mirroring on its own; this differs from call apps, whose preview is only a self-view. Basis: the bubble is recorded as shown, so there is no separate self-view, and the industry default for what viewers see is unmirrored.
- [x] **D9 Device.** Others: every product has a camera picker; Cap lists "No Camera" first, remembers the last device and drops an invalid stored id with a warning; Loom offers built-in, external or none. Recommended: a picker with "System default" first, remembering id and label, falling back to the default with a note when the device is absent. Basis: universal practice, and Macs often have several cameras (built-in, Continuity Camera, external).
- [x] **D10 Switch.** Others: Cap and Loom have no separate switch; "No Camera" in the picker is off. Recommended: follow 074's answer for the microphone so both inputs work the same way; if 074 chose a switch, a switch here too.
- [x] **D11 Camera unavailable at start.** Others: Cap checks access before opening the device and refuses setup without permission. Recommended: refuse the start with `camera_unavailable` before any countdown, as 074 does for the microphone. Basis: a recording planned with a camera that silently lacks it is a lost take.
- [x] **D12 Disconnect mid-recording.** Others: Cap continues, notifies ("Camera disconnected — Recording continues without camera…") and reconnects when the device returns. Recommended: continue, hide the bubble, notify once; no reconnection. Basis: Cap's behavior without the reconnection machinery; the file stays valid.
- [x] **D13 Show and hide while recording.** Others: Cap's in-progress menu can switch the camera to "No webcam", which pauses the recording; Loom offers "Turn camera off" on its bubble (mid-recording unconfirmed); Tella toggles the camera between clips. Recommended, per the maintainer: a "Hide camera" / "Show camera" item in the tray's recording menu, keeping the camera open while hidden so it returns at once in the same place (the camera light stays on, which the item's note says); the start state is shown. Ask whether a global shortcut is also wanted; recommended not in this plan, because a new global shortcut brings registration, conflicts and the shortcut list (073) with it.
- [x] **D14 RecordStuff's own windows in the recording.** Others: Cap excludes all its own windows by default (main, settings, recording controls and more) with ScreenCaptureKit's window filter, the list editable in its settings, and applies protection to its controls only while recording; Loom omits its recording controls from the video on Mac and offers "Hide system UI" for the menu bar, Dock and widgets; Screen Studio omits its recording widget on macOS 12.3 and later; OBS offers "Hide OBS from capture", off by default. None was confirmed to hide its own menu-bar icon. Recommended: leave the Settings window (including the player and full-screen video windows) out of every recording, including one opened after the start. Since 076, its native engine does this with ScreenCaptureKit's window filter, updated when a window opens, and `WDA_EXCLUDEFROMCAPTURE` on Windows; the first draft's fallback, Electron's same-app filter with content protection, is no longer needed. Screen sharing and screenshots of RecordStuff by other apps are unaffected while idle. The camera bubble is never protected. Hiding the menu bar and Dock is 076's D6 switch. Basis: every product checked except OBS keeps its own controls out by default.

Decided by the maintainer on 2026-10-14: every recommendation above is adopted, so D5 has no snapshot button and D13 adds no global shortcut. D10 takes 074's recommended switch; 074's step 1 (2026-10-16) adopted it: a switch in the Recording tab plus a checkbox in the tray's idle menu, with a device picker.

### 2. Shape and placement model (shared, pure)

- [ ] Add `src/shared/camera-bubble.ts` (proposed): the stored settings (`width`, `height`, `rounding`, `mirror`, `device`, per-display `position` as a fraction of the display), defaults, validation, and pure functions used by both the preview and the real window: bounds from settings and a display, radius from rounding, snapping, and clamping after a display or resolution change or a missing display (falls back to the default bottom-right corner, which keeps clear of the countdown digit at the top right).
- [ ] Unit tests: square, wide and tall frames at rounding 0, 50 and 100; ratio buttons; width and height bounds on small and large displays and Retina scale factors; the preview's scaled bounds and the real window's bounds agree; snapping and clamping; invalid stored values fall back.

### 3. Permission, packaging and settings

- [ ] Add `NSCameraUsageDescription` and `com.apple.security.device.camera`; confirm with `codesign -d --entitlements` on a `pnpm start:app` bundle.
- [ ] Turning the camera on asks `systemPreferences.askForMediaAccess("camera")`; a denial shows the status and an action opening System Settings → Privacy & Security → Camera, as 074 does for the microphone.
- [ ] `src/main/settings/settings.ts`: the camera fields, parsed with the existing `field` pattern.

### 4. Layout preview in Settings

- [ ] A Camera group in Settings → Recording: switch or picker per D9/D10, permission status, the layout preview, Width, Height and Rounding controls with ratio buttons, and Mirror in recording, locked while recording like the other recording settings. New strings in `ZH_TW`.
- [ ] The preview draws the recorded display (the Screen card's choice) to scale with the production components and tokens, and the bubble from step 2's functions; the bubble is dragged with the pointer and resized by its edge handles (width or height) and corner handles (both), and with the keyboard (arrow keys move, modifiers resize width or height), with snapping. The camera stream runs only while the preview is visible (D6) and stops when the tab, window or switch changes.
- [ ] With several displays, the preview follows the Screen card's choice; "Primary display" previews the current primary.
- [ ] Page tests: controls and their values, drag and keyboard placement saved, locked while recording, denied status, zh-TW, the camera stream stopped when the tab is left (with a fake media device). Behavior and accessibility only; the sliders and the bubble have accessible names and value text ("Rounding 60%", "Bubble at bottom right").

### 5. The bubble window

- [ ] `src/main/recording/camera-bubble.ts` (proposed) creates the window at preparation on the recorded display from step 2's bounds: transparent, frameless, shadowless, click-through, always on top at the countdown's level, on all workspaces and over full-screen apps, a non-activating panel on macOS, not focusable, no content protection. Recorder receives it as an injected presenter, as it does the countdown overlay.
- [ ] A renderer page (`src/renderer/camera/`, proposed) calls `getUserMedia({ video: { deviceId, width: { ideal: 1280 }, height: { ideal: 720 }, frameRate: { ideal: 30 } } })`, Cap's target, and draws the `<video>` with `object-fit: cover`, the radius and the mirror, using the same component as the preview.
- [ ] "Show on screen" (D4) opens the same window, movable for that check only, writing its position back to the settings.
- [ ] Show and hide (D13): the tray's recording menu hides or shows the window without stopping the camera stream; the state is logged with the session.
- [ ] Own windows (D14): 076's engine excludes the Settings, player and full-screen windows; the bubble is passed to it as a window that must be recorded, and the countdown overlay is gone before capture.
- [ ] Lifecycle: destroyed with the attempt on every exit path the countdown overlay uses; the camera stream stops with it, so the macOS camera indicator turns off at stop, cancel, failure, sleep and quit. Disconnect follows D12.

### 6. Measurement

- [ ] Recording smoke with the camera on: the saved frames contain the bubble at the logged bounds with the chosen radius (located as acceptance locates the countdown digit), matching the preview's placement.
- [ ] Own windows: a recording with the Settings window open on the recorded display, and one with it opened after the start, checking that it is absent from the frames in each.
- [ ] Show and hide: a recording that hides and shows the bubble, checking the frames and that the bubble returns in place.
- [ ] CPU: `pnpm measure:cpu` with the preview open and while recording with the bubble, against the [CPU budget](../docs/system-design/tooling.md#cpu-budget).
- [ ] Frame timing: one relevant `pnpm matrix` case with the bubble shown.
