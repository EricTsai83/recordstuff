開源授權實務：別人的程式碼能怎麼用，又如何決定你的架構

開源授權不只是 repo 裡的一個 LICENSE 檔。它決定你能不能直接依賴某個套件、能不能把一段程式碼搬進來、某個函式庫要用動態還是靜態連結、要不要多開一個行程，甚至決定某個功能值不值得自己重寫。本文從「什麼時候可以使用或參考別人的程式碼」這個一般問題出發，整理 MIT、Apache-2.0、GPL、AGPL、LGPL 的義務與觸發條件，說明常見的誤解、各種替代做法的代價，以及哪些條件會讓答案改變。範例是一個 MIT 授權的桌面錄影 App，如何參考一個大部分是 AGPL 的開源錄影專案。

這不是法律建議。本文說明授權條款的一般讀法與工程上的取捨，幫助你提出對的問題。授權的實際效力取決於司法管轄區、條款版本與具體事實；涉及商業發佈、授權變更或爭議時，請以授權原文為準並諮詢律師。

這篇文章要回答的問題

寫軟體時，別人的程式碼會以幾種方式進入你的工作：你把一個套件列為依賴；你從另一個專案複製一個函式；你把別人的 TypeScript 改寫成 Rust；或者你只是讀懂別人怎麼解一個難題，然後自己寫。這四件事在工程上看起來差不多，在授權上卻差很多。

可遷移的問題是：我想用或想學別人的程式碼時，哪些做法是被允許的、要付出什麼義務，而這些義務又會怎麼限制我的架構與技術選擇？答案取決於三件事：對方的授權、你自己專案的授權與發佈方式，以及兩份程式碼最後如何結合。

先分清幾個基本概念

著作權保護表達，不保護想法

程式碼受著作權保護的是「表達」：具體的原始碼文字、結構與組織。演算法、做法、檔案格式的規格、「先抓四倍頻率的畫面再挑最接近時間格的那張」這種想法本身，一般不受著作權保護（不過可能受專利保護，那是另一個問題）。這就是「讀程式碼學想法」和「複製程式碼」在授權上分開的原因。

但界線不在於有沒有逐字複製。把一段程式碼逐行翻譯成另一種語言，表達的結構仍然來自原作；著作權法一般把翻譯視為衍生作品，GPLv2 甚至直接寫明「翻譯包含在『修改』之內」。改了變數名稱、換了語言，不會讓它變成你自己的作品。

沒有授權就是不能用

開源授權是「有條件的許可」：著作權人原本保有所有權利，授權書說明在什麼條件下允許你使用、修改與散佈。一個公開在 GitHub 上、但沒有授權檔的 repo，預設是保留所有權利；看得到不等於可以用。

衍生作品、散佈與網路使用

授權義務通常不是在你「使用」時發生，而是在特定動作時觸發：

  • 衍生作品（derivative work）：修改、翻譯，或把別人的程式碼與你的程式碼結合成一個作品。哪些結合方式算衍生作品，是 copyleft 授權爭議的核心。
  • 散佈（distribution，GPLv3 稱為 conveying）：把軟體的副本交給別人，例如發佈安裝檔、App、函式庫套件或內含軟體的硬體。只在公司內部使用、不交給外人，通常不算。
  • 網路使用：讓使用者透過網路與軟體互動，但不交出副本，例如 SaaS 服務。大多數授權不把它當成散佈；AGPL 是例外。

寬鬆授權與 copyleft

寬鬆授權（permissive，例如 MIT、BSD、Apache-2.0）允許你把程式碼放進任何專案，包括閉源商業產品，主要條件是保留授權與著作權聲明。Copyleft 則要求衍生作品在散佈時繼續使用同一份授權並提供原始碼。不同 copyleft 授權的差別在「範圍」：MPL-2.0 只管被修改的那些檔案，LGPL 管函式庫本身，GPL 管整個程式，AGPL 再把觸發條件延伸到網路使用。

主要授權逐一看

MIT：保留聲明即可

MIT 授權只有一個條件：著作權聲明與這段許可聲明，必須包含在軟體的「所有副本或實質部分」中。它允許商業使用、修改、再授權，也不要求公開你的原始碼。實務上最常被違反的方式是刪掉檔案開頭的著作權行、把複製過來的程式碼當成自己的，或在發佈的 App 裡完全沒有附上依賴套件的授權文字。MIT 沒有明文的專利授權條款。

Apache-2.0：明確的專利授權與 NOTICE 檔

Apache-2.0 也是寬鬆授權，但比 MIT 多了兩件工程上要注意的事：

  • 專利授權：每位貢獻者授予你使用其貢獻所涉專利的許可。如果你對該作品提起專利侵權訴訟，你得到的專利授權就會終止。對擔心專利風險的公司來說，這是選擇 Apache-2.0 套件的理由之一。
  • 散佈條件：要附上授權副本、在你修改過的檔案上標示已修改、保留原有的著作權與歸屬聲明；如果原作附有 NOTICE 檔，散佈時要把其中的歸屬聲明一起帶著，放在你自己的 NOTICE 檔、文件或軟體顯示的地方。

依 FSF 的說法，Apache-2.0 可以與 GPLv3 結合，但與 GPLv2 不相容。Rust 生態系常見的「MIT OR Apache-2.0」雙授權，就是讓使用者自己選：要專利條款就選 Apache-2.0，要和 GPLv2 專案結合就選 MIT。

GPL：散佈時整個程式都要開放

GPL（v2 與 v3）是程式層級的強 copyleft。你可以私下修改和使用，不用公開任何東西；但一旦散佈以 GPL 程式碼為基礎的作品，整個作品都要以 GPL 授權，並提供對應的完整原始碼給收到的人。對閉源產品而言，這代表 GPL 程式碼不能和你的專有程式碼結合成同一個程式後發佈。

AGPL：網路使用也算

AGPLv3 是 GPLv3 加上第 13 條：如果你修改了程式，並讓使用者透過網路與它互動，就要向這些使用者提供你修改後版本的原始碼。它是為了堵住「不散佈副本、只提供服務」的 SaaS 情境。要注意的是，AGPL 在散佈上的義務和 GPLv3 一樣；把 AGPL 程式碼放進一個桌面 App 發佈，觸發的就是 GPL 那一套，而不是只在伺服器上才有事。

LGPL：函式庫層級，可替換是關鍵

LGPL 讓閉源程式可以使用一個開源函式庫，同時保障使用者「替換這個函式庫」的權利。以 LGPLv3 第 4 條為例，把 LGPL 函式庫和你的程式組成「合併作品」散佈時，你需要：

  • 標明使用了該函式庫並受 LGPL 規範，附上 GPL 與 LGPL 授權全文；
  • 提供函式庫部分的原始碼（包括你對它的修改）；
  • 讓使用者能用修改過的函式庫重新組合：使用適當的共享函式庫機制（也就是動態連結，執行時載入使用者那份介面相容的函式庫），或提供足以重新連結的目的檔；
  • 你的授權條款不得限制使用者為了除錯這些修改而進行逆向工程。

所以「LGPL 只能動態連結」並不精確：靜態連結也可以，但你必須交出你程式的目的檔（object files）或同等的材料，讓使用者能換掉函式庫重新連結。對多數閉源產品來說這太麻煩，因此實務上幾乎都選動態連結。另一個常被忽略的點是：最終使用者授權合約（EULA）若一律禁止逆向工程，可能就和 LGPL 的要求衝突。

授權類型與範圍什麼動作觸發義務主要義務能否放進閉源產品

影響決策的幾股力量

授權本身是固定的條文，真正難的是它和其他工程目標互相拉扯：

  • 省工 vs 自己專案的授權承諾：直接用現成程式碼最快，但你的專案對使用者承諾了某種授權。一個 MIT 專案的價值之一，是任何人都能把它放進閉源產品；引入 copyleft 程式碼就會破壞這個承諾。
  • 技術最佳解 vs 授權最佳解：最好的實作可能剛好在 GPL 或 AGPL 專案裡。用寬鬆授權的次佳方案，或自己實作，都要付出成本。
  • 依賴大小與維護 vs 重寫成本：依賴一個寬鬆授權的套件通常比重寫便宜，但它帶來體積、相容性與上游停止維護的風險。
  • 架構乾淨 vs 授權邊界：為了守住 LGPL 的可替換性，你可能必須用動態連結、固定的 ABI、額外的打包步驟，這些都是授權而不是技術需求造成的架構限制。
  • 下游的自由：你選的授權與依賴，會變成使用你的程式的人要面對的限制。

常見的天真做法與它們出錯的方式

  • 「放在 GitHub 上就是開源。」沒有授權檔就是保留所有權利。要用，先找到授權，或聯絡作者。
  • 「repo 標示 MIT，所以整個 repo 都是 MIT。」大型專案常按目錄分授權：某些套件是 MIT，核心是 AGPL。要看的是你實際要用的那個檔案或套件的授權，而不是 repo 首頁的標籤。
  • 「我改寫成另一種語言了，所以不算複製。」逐行翻譯保留了原作的結構與表達，通常仍是衍生作品。
  • 「它跑在另一個行程裡，所以不受 GPL 影響。」行程邊界本身不是授權防火牆，下面會專門討論。
  • 「MIT 只要在 README 提一下作者。」MIT 要求的是授權文字與著作權聲明本身隨副本一起提供，不是一句致謝。
  • 「LGPL 就是可以隨便用。」靜態連結卻不提供目的檔、沒有附上函式庫原始碼、EULA 禁止逆向工程，都可能違反 LGPL。
  • 「只看直接依賴。」依賴的依賴也會被你一起散佈。FFmpeg 這類專案的授權甚至取決於建置選項：加上 --enable-gpl 就變成 GPL。
  • 「AGPL 只管伺服器。」散佈 AGPL 程式碼時，GPL 的全部義務都適用。

授權如何限制架構與技術選擇

依賴寬鬆授權的套件，還是自己重寫

當你需要的功能有一個 MIT 或 Apache-2.0 的套件可用時，直接依賴通常是最便宜的做法，你只需要把它的授權聲明帶進你的發佈物。選擇自己重寫的理由多半不是授權，而是其他條件：套件設計和你的需求不合、它帶來大量你用不到的依賴、上游維護不穩，或你需要掌控它的行為。授權在這裡的作用是「允許」，不是「推動」。

情況在「唯一好用的實作是 copyleft」時改變。這時你有幾條路，各有代價：

做法你得到什麼代價
接受 copyleft，自己的專案改用相容授權可以直接用最好的實作下游使用者失去把你的專案放進閉源產品的自由；MIT 這類寬鬆授權允許再授權，合併後的作品可以整體以 copyleft 散佈，只要保留原本的版權與授權聲明；但已經發出的 MIT 授權無法收回，舊版本仍是 MIT。真正需要每位貢獻者同意的，是把他們的程式碼改成 MIT 不允許的條件，例如從 GPL 改成更寬鬆的授權
購買商業授權（若對方提供雙授權）閉源使用費用與合約；只有著作權人能賣，社群貢獻多的專案未必提供
找寬鬆授權的替代品不改變自己的授權品質或功能可能較差，要重新評估
依公開規格自己實作，只參考對方的設計完整掌控，授權乾淨開發與測試成本最高；必須避免寫出實質相似的程式碼

FFmpeg：動態連結、靜態連結，或在核心路徑上避開它

FFmpeg 是多媒體軟體最常見的 LGPL 依賴。它的預設建置是 LGPL 2.1 或更新版本；啟用 --enable-gpl（例如為了 libx264）就變成 GPL，啟用 --enable-nonfree 則根本不能再散佈。FFmpeg 官方的法律頁面為想遵守 LGPL 的使用者列了一份檢查清單，重點包括：不要用這兩個選項建置、以動態連結使用 FFmpeg 的函式庫（在 Windows 上就是 DLL）、散佈你使用的那份 FFmpeg 原始碼（不論有沒有修改）、確保原始碼和你發佈的二進位檔完全對應，以及在產品中說明使用了 LGPL 授權的 FFmpeg。

對一個閉源或寬鬆授權的 App 而言，這幾種用法的取捨如下：

用法授權上要做的事工程代價
動態連結 LGPL 建置附原始碼與授權全文、標示使用、允許替換要打包多個共享函式庫並管理版本；App 體積增加
靜態連結 LGPL 建置以上全部，再加上提供讓使用者能重新連結的目的檔發佈流程複雜，實務上少見
呼叫隨附的 ffmpeg 執行檔仍然在散佈 FFmpeg，那個執行檔的授權義務照樣適用；若是 GPL 建置，就要為它履行 GPL行程啟動與資料傳遞的成本，錯誤處理較粗
核心路徑不用 FFmpeg，改用作業系統的編碼器FFmpeg 的義務不出現每個平台各寫一套；格式支援只限於系統提供的編碼器

還有一個和授權無關、卻常被混在一起的問題：編解碼器的專利。FFmpeg 的授權是著作權授權，不包含 H.264、AAC 等格式的專利授權；FFmpeg 官方也明說這一點。使用作業系統內建的編碼器時，專利問題通常由平台方處理，但這要以你的平台和發佈方式確認，不能假設。

行程邊界不是授權防火牆

一個流行的想法是：把 GPL 或 AGPL 的程式放在另一個行程裡，用管線或 socket 溝通，就不受 copyleft 影響。GNU 的 GPL FAQ 的立場是：透過管線、socket、命令列參數溝通，通常表示是兩個獨立的程式；但如果溝通的語義足夠緊密，例如交換複雜的內部資料結構，仍可能被視為同一個程式的兩個部分。換句話說，判斷看的是兩者實質上是不是一個整體，而不是有沒有行程邊界。

即使兩者真的是獨立程式，行程邊界也只回答了「我的程式要不要變成 GPL」，沒有免除另一半的義務：你只要散佈那個 GPL 或 AGPL 的程式，就要為它提供原始碼並履行授權。如果它是 AGPL 而且你修改後讓使用者透過網路使用，第 13 條同樣成立。行程邊界真正提供的是技術上的隔離，例如當機不會拖垮主程式；授權上的隔離要另外論證。

閉源或商業發佈者要做的事

  • 盤點：列出所有隨產品散佈的程式碼，包括間接依賴、執行環境（例如 Electron 內含的 Chromium）與建置時打包進去的資產。
  • 寬鬆授權：在產品中附上每個套件的授權文字與著作權聲明，常見做法是「關於 → 第三方授權」頁面或安裝目錄中的授權檔；Apache-2.0 套件還要帶上其 NOTICE 內容。
  • LGPL：動態連結、附授權全文與函式庫原始碼（或可取得原始碼的書面提供）、檢查 EULA 沒有禁止為除錯而逆向工程。
  • GPL / AGPL：不要和專有程式碼結合；需要的話找替代品或洽談商業授權。
  • 自動化：Rust 的 cargo-deny、cargo-about，或 npm 生態系的授權掃描工具，可以在 CI 中阻擋不允許的授權並產生聲明檔。工具只能讀套件中繼資料，複製進來的程式碼片段要靠審查。

MIT 專案複製 AGPL 程式碼，會失去什麼

假設一個 MIT 專案從 AGPL 專案複製（或逐行翻譯）了一個模組。著作權人並沒有用 MIT 授權那段程式碼，所以你無法把它以 MIT 再授權。結果是：

  • 專案作為一個整體散佈時，實際上要依 AGPL 履行義務；repo 上的 MIT 標示變得不正確。
  • 下游使用者以為可以依 MIT 把它放進閉源產品，結果會在不知情下違反 AGPL。這正是使用者選擇 MIT 專案時想避免的事。
  • 要修正，只能移除並重寫那段程式碼，或把整個專案改以 AGPL 散佈。後者不需要每位既有貢獻者同意：MIT 允許再授權，只要保留他們的版權與授權聲明，合併後的作品就能以 AGPL 散佈；只是已經以 MIT 發出的版本無法收回，那些版本仍可依 MIT 使用。
  • 重寫時，曾經直接看著那段程式碼的人寫出的版本仍可能被質疑相似，因此事前避免遠比事後清理便宜。

其他專案怎麼處理

以下只列有公開紀錄的做法；細節以各專案的授權檔與公告為準。

  • 按目錄分授權：有些開源產品把可重用的底層套件以寬鬆授權釋出，核心產品用 AGPL，讓社群能重用元件，又保護產品本身。下面範例中的 Cap 就是這樣。
  • 雙授權：Qt 同時以 LGPL/GPL 與商業授權提供；不想履行 copyleft 的公司可以付費。這要求著作權人能夠代表所有程式碼授權。
  • 為了讓更多人使用而放寬授權：VideoLAN 在 2012 年前後把 libVLC 從 GPL 改為 LGPL，過程中逐一取得貢獻者同意。
  • 為了限制雲端服務而收緊授權：Grafana 在 2021 年從 Apache-2.0 改為 AGPLv3；MongoDB 在 2018 年從 AGPL 改為自訂的 SSPL；Elastic 在 2021 年離開 Apache-2.0，2024 年又加入 AGPL 作為選項。授權會變，依賴的授權要按版本記錄。
  • 寬鬆雙授權作為生態系慣例：Rust 的 API 指南建議 crate 採用 MIT OR Apache-2.0，Microsoft 的 windows crate 就是如此。
  • 以共享函式庫隔離 LGPL：Chromium 把 FFmpeg 建成獨立的共享函式庫，Electron 的 macOS 發佈中可以看到 libffmpeg.dylib，其授權說明列在 Electron 附帶的 LICENSES.chromium.html。

決策流程

把上面的內容收成三個依序回答的問題。它不能取代逐條閱讀授權，但可以讓你在動手之前知道自己走在哪條路上。

實例：一個 MIT 錄影 App 怎麼參考 AGPL 專案

RecordStuff 是一個以 MIT 授權發佈的桌面錄影 App，介面用 Electron，原生錄影引擎用 Rust 寫成，在 macOS 上透過 ScreenCaptureKit、在 Windows 上透過 Windows.Graphics.Capture 擷取畫面，再以平台的編碼器編碼（macOS 用 VideoToolbox 的硬體編碼，Windows 目前用 Microsoft 的軟體 H.264 編碼器），最後由自己的 MP4 封裝器（muxer）寫成檔案。開始寫原生引擎前，它研究了 Cap：另一個用 Rust 寫原生擷取的開源錄影 App。

先確認授權的實際範圍

規劃文件記錄了 Cap 在某個特定修訂版（3d19c5cfa5e636107e78adde6d55be78404d4f23）的授權狀態：scap-* 與 camera* 這些 crate 是 MIT，包括 scap-screencapturekit、scap-direct3d、scap-targets 與 scap-ffmpeg；其餘所有程式碼，包括錄影管線、編碼器與 muxer，都是 AGPLv3，不能複製進這個 MIT 專案。

這一步避開了「repo 標著某個授權」的天真讀法：RecordStuff 最想參考的部分（錄影管線與 muxer）正好是 AGPL，而 MIT 的部分是底層的擷取綁定。記下修訂版也很重要，因為授權會隨版本改變，「當時是 MIT」只有對特定版本才成立。

寫下規則，再開始寫程式

規劃中的決策 D5 定下了使用規則：

  • Cap 的 MIT scap-* crate 在合適時可以依賴或改寫，保留其授權聲明，並記錄每個 crate 的名稱、授權與修訂版。
  • Cap 的 AGPL 程式碼只作設計參考：可以閱讀以理解做法，但不複製、不逐行翻譯；實作依據 Apple 與 Microsoft 的官方文件，以及 ISO BMFF（MP4 的基礎格式）規格。

決策 D4 則處理 FFmpeg：編碼用平台的系統編碼器（macOS 的 VideoToolbox 與 AudioToolbox、Windows 的 Media Foundation），封裝用專案自己的 Rust muxer。錄影路徑不用 FFmpeg，讓 App 保持小巧，也不必處理 LGPL 連結；日後的匯出功能若需要 GIF、WebM 等格式，可能只為轉檔引入 FFmpeg。這是「核心路徑避開它」的選擇：代價是要在兩個平台各寫一套編碼流程，並自己實作 MP4 封裝。

實際做了什麼

檢查原生引擎的 native/capture/Cargo.toml：它本身宣告 license = "MIT"，目前沒有依賴任何 scap-* crate。它直接透過綁定 crate 呼叫系統 API：macOS 用 objc2 系列（如 objc2-screen-capture-kit），Windows 用 Microsoft 的 windows crate，與 Node.js 之間用 napi。從本機 Cargo 登錄快取讀到的授權欄位，objc2、block2、napi 是 MIT，windows 是 MIT OR Apache-2.0，objc2-screen-capture-kit 與 dispatch2 是 Zlib OR Apache-2.0 OR MIT，都是寬鬆授權。規劃文件沒有記錄為什麼最後沒用 scap crate，所以這裡不推測原因；D5 允許依賴它們，但沒有要求。

參考來源則寫在程式碼裡。muxer 的模組說明直接記錄依據與「沒有複製」這件事：

Rust//! Written from ISO/IEC 14496-12 (boxes) and 14496-14/-15 (`esds`, `avcC`); no code was taken from other muxers.

畫面節奏（pacing）模組的說明也寫著，它挑選畫面的做法與 OBS 的影格率除數和 Cap 的 pacing 相同。這正是「學想法」的形態：做法（以錄影開始為基準的時間格，挑最接近的畫面）被引用並說明出處，程式碼則是依自己的量測寫成。在原始碼裡記錄規格與參考對象，日後有人質疑時，它就是程式碼來源的證據。

保留聲明的具體例子，與還要檢查的地方

專案根目錄的 LICENSE 是 MIT 全文。產品網站改寫了另一個 MIT 專案（T3 Code 的行銷網站）的版面與 CSS，於是在 website/THIRD_PARTY.md 中說明改寫了哪些部分、明確列出沒有包含的東西（圖示、截圖、文案、品牌素材），並附上對方的 MIT 授權全文與著作權行；字型則註明是 SIL Open Font License 1.1 與授權文字所在。這是寬鬆授權最典型的義務履行方式。

同一套方法套到桌面 App 時，會浮出兩個值得確認的問題。第一，原生模組靜態編譯了上述 MIT 與 Apache-2.0 的 crate，依 MIT「所有副本或實質部分」的字面要求，保守的做法是在 App 內附上它們的授權聲明。第二，「錄影路徑沒有 FFmpeg」不等於「App 裡沒有 FFmpeg」：Electron 本身就帶著 Chromium 建置的 libffmpeg.dylib，它在本機一份 macOS 打包產物中確實存在，而 Chromium 的授權清單把 FFmpeg 列為 LGPL v2.1+。撰寫本文時，在那份打包產物中沒有找到 Electron 的 LICENSE 或 LICENSES.chromium.html。這兩點是否需要調整，要以實際發佈的安裝檔重新檢查後決定。

這個例子示範了整個流程：先確認授權的實際範圍與版本，把規則寫在動手之前，依賴只選寬鬆授權，把 AGPL 程式碼當作只能閱讀的設計參考，在程式碼中記錄依據，最後回頭檢查發佈物是否帶齊了聲明。

邊界：哪些情況不能直接套用

  • 不要假設「只是參考」就安全，當你一邊看著原始碼一邊寫：如果新程式碼的結構、命名、註解與原作高度一致，就算沒有複製貼上，也可能被視為衍生作品。依規格寫、不開著原作，並記錄依據。
  • 不要假設行程邊界能隔離 copyleft，當兩邊交換的是內部資料結構：緊密耦合的兩個行程可能仍被視為一個程式；而且無論如何，被散佈的那個 GPL 程式本身的義務不會消失。
  • 不要假設 LGPL 一定沒事，當你靜態連結、修改了函式庫或發佈到限制替換的平台：靜態連結需要提供可重新連結的材料；修改要公開；某些應用程式商店的條款與 GPL 系授權的衝突曾經讓 VLC 在 2011 年被移出 iOS App Store。
  • 不要假設 AGPL 與你無關，當你的產品是服務：修改過的 AGPL 程式碼即使從未散佈副本，只要使用者透過網路使用它，就有提供原始碼的義務。
  • 不要假設授權固定不變，當你升級依賴：專案會改授權；新版本可能不再是寬鬆授權。記錄你依賴的版本與當時的授權。
  • 不要假設這些結論適用於你，當你不發佈任何東西：純內部使用的工具，多數授權（AGPL 的網路條款除外）都不要求任何事。反過來，一旦開始對外發佈，前面的義務就全部回來。
  • 不要假設授權回答了專利問題：MIT 沒有明文專利授權；FFmpeg 的 LGPL 不包含編解碼器的專利授權。專利要另外評估。

帶走的判斷問題

  1. 這段程式碼會不會進入我發佈或對外提供的產品？如果只是學想法，我能不能依公開規格或文件自己寫，並記錄依據？
  2. 我要用的「那個檔案或套件」本身是什麼授權、哪個版本？不是 repo 首頁寫的那個。
  3. 觸發義務的動作是什麼：散佈、修改、還是網路使用？我的產品會做哪一個？
  4. copyleft 的範圍是檔案、函式庫還是整個程式？我的架構（連結方式、模組切分）落在範圍內還是外？
  5. 我的專案對下游承諾了什麼授權？引入這段程式碼會不會讓這個承諾變得不正確？
  6. 如果不能用，替代方案的代價是什麼：換套件、自己寫、買授權，還是讓這個功能離開核心路徑？
  7. 發佈物中是否帶齊所有授權聲明，包括間接依賴與執行環境？有沒有工具在 CI 中檢查？
