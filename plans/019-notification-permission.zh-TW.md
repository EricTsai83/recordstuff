# 019 — 通知權限引導

[English](019-notification-permission.md) | [繁體中文](019-notification-permission.zh-TW.md)

狀態：待執行。優先順序：下一項。建立：2026-09-21。

## 問題與目標

使用者回報下載的 release 沒有顯示通知，也沒有提示開啟通知權限。目前[通知發送](../src/main/tray.ts)直接呼叫 Electron `Notification.show()`，不支援或失敗時只寫 log；沒有 App 自己的通知授權查詢、請求流程與補救介面。現有[權限監看](../src/main/permission.ts)只處理螢幕錄製。尚未重現該 release 與 macOS 環境的確切原因。

提供可見的雙語引導，讓使用者能啟用存檔與錯誤通知，也涵蓋從舊版升級的人。拒絕或無法取得通知權限時，仍可錄影。範圍是目前支援的 macOS App；維持其他平台既有行為，不宣稱已完成其他平台驗收。

## 預期體驗

| 狀態 | 引導與操作 |
| --- | --- |
| 尚未決定 | 首次安全的閒置時機顯示 App 說明，提供「啟用通知」與「稍後再說」。啟用會請求系統授權；略過仍可錄影。 |
| 已拒絕 | 顯示一次說明，提供「開啟通知設定」與「稍後再說」，不重複請求系統授權。 |
| 已授權 | 不跳首次引導；設定顯示權限狀態與開啟系統通知設定的入口。 |
| 已授權但關閉提示，或其他受限傳送狀態 | 原生 API 能辨識時，在設定中說明具體限制並提供系統設定入口；不要把所有不顯示橫幅的設定都當成拒絕授權。 |
| 未知／查詢或請求失敗 | 設定如實顯示無法取得狀態，提供重試與手動設定步驟；記錄診斷，不假設已授權，也不循環跳提示。 |

- 在「設定 → 一般」加入通知區塊，包含目前狀態、適當的啟用／設定／重試操作，以及授權後由使用者主動發送的測試通知。說明已授權不保證一定顯示橫幅。
- 將引導版本／已處理記錄持久化，與 OS 權限分開。既有安裝也適用，不沿用 Windows 的 `tray-hint-shown`。略過後，重新啟動或更新 App 都不自動重複提示，但保留設定入口。只有實際顯示／處理引導後才記錄；延後或顯示失敗不能視為已完成。
- 啟動錄影、錄影中、存檔中，以及螢幕權限／重新啟動復原期間，延後自動引導。避免權限視窗重疊與存檔完成時搶焦點；等閒置且既有復原介面結束後再顯示，顯示前重新確認狀態。
- 啟動、開啟設定、授權請求完成、從系統設定返回時重新查詢。選單列 App 不能只依賴 activate；設定面板可見期間也使用有界限的更新機制。
- 日後撤銷權限時更新設定狀態，不重新開始自動引導。通知失敗不得反覆彈窗、阻擋存檔或改變錄影狀態。
- 引導使用不依賴通知權限的 App 對話框／設定介面，不能用通知提醒使用者缺少通知權限。

## 執行順序

### 1. 確認實際授權行為

- [ ] 能取得時，記錄受影響的 release 版本、macOS 版本、安裝路徑、bundle ID、簽署身分、通知設定與相關 log；區分使用者回報與自行重現的證據。
- [ ] 檢查專案實際解析的 Electron 版本及其 macOS 通知實作。在已簽署封裝 App 上確認首次 `Notification.show()` 是否請求授權，以及尚未決定／已拒絕的行為。`Notification.isSupported()` 只代表能力支援；failed/show 事件不能當可靠的權限查詢或橫幅可見證據。
- [ ] 驗證能以 **RecordStuff 本身的 App 身分**查詢原生通知設定與主動請求授權的方法。若使用中的 Electron 有支援的 API，優先採用；否則實作最小的行程內 macOS UserNotifications 原生橋接。不使用權限歸屬另一 App 的獨立 helper，不以 renderer 網頁通知權限代替，也不為本機通知註冊 APNs。
- [ ] 若需要橋接，涵蓋原生編譯、Electron ABI／架構、封裝、簽署與 CI release 建置。先驗證封裝 App 能載入原生模組，再整合介面。只請求需要的通知選項，維持既有靜音通知。
- [ ] 驗證支援的 macOS 上的通知設定入口。若無法直接導向或只能開啟總覽，提供「系統設定 → 通知 → RecordStuff」手動步驟，不把未驗證的私有 deep link 當作唯一復原方式。

### 2. 實作權限狀態與引導

- [ ] 新增 main process 權限 adapter／controller，明確處理尚未決定、拒絕、授權、受限與未知狀態；非同步操作要有時限、請求要去重，結束時清理資源。與螢幕權限及錄影狀態分開。
- [ ] 實作上述引導持久化／舊版遷移與閒置排程。協調授權請求與一般通知發送，避免第一則通知與主動授權流程競爭；授權後不補送過時通知佇列。
- [ ] 透過現有設定 model／preload 傳遞狀態與白名單操作，加入英文與繁中翻譯。處理查詢、請求、開啟設定與原生載入失敗，不崩潰也不誤報成功。
- [ ] 保留現有存檔通知延遲／取消、通知物件生命週期、Finder 顯示與診斷。補上權限轉換與請求 log，不記錄無關的私人資料。

### 3. 驗證行為

- [ ] 增加針對狀態映射、首次／升級引導、持久化略過、未知／錯誤／逾時、併發請求、設定更新與結束清理的測試。測試錄影／復原時延後提示，確保通知失敗不影響檔案完成寫入。
- [ ] 修改 App 後執行 `pnpm check` 與 `git diff --check`。
- [ ] 依[原生 computer-use 驗收 skill](../.agents/skills/astra-acceptance-with-computer-use/SKILL.md)，以 `pnpm start:app` 執行下表並留下雙語證據。只停止／儲存測試者自己開始的錄影；重建或結束前確認是否有使用者錄影。

| 原生情境 | 必要證據 |
| --- | --- |
| 全新通知授權狀態 | 引導可見；啟用會出現屬於 RecordStuff 的真正系統授權流程；允許後能看見測試／存檔通知。使用全新測試帳號或受控環境，不能只靠重裝就宣稱權限是全新狀態。 |
| 拒絕、略過、重新啟動 | 仍可錄影／存檔／播放；不重複自動引導；設定仍可復原。 |
| 既有安裝沒有權限 | 即使已有 App 偏好設定，升級仍會收到一次引導。 |
| 開啟設定、允許、返回 | 正確頁面或可用的替代步驟；狀態更新；後續通知出現，不要求不必要的重啟。 |
| 原已授權／撤銷權限 | 已授權不多跳提示；撤銷後狀態正確且仍可錄影。 |
| 錄影與螢幕權限復原 | 不重疊彈窗、不打斷存檔，也不因自動延後的提示搶焦點。 |
| 專注模式或關閉橫幅 | 不誤報「拒絕權限」；分開記錄測試發送請求與實際可見結果。 |
| 技術失敗 | 查詢／請求／原生載入／開啟設定失敗時有可用替代方式與 log，不重複提示或卡住。 |

- [ ] 回歸開始／停止／存檔／播放，確認螢幕與系統音訊、存檔通知點擊／Finder 顯示，以及等待存檔通知期間開始下一次錄影。記錄實際測過的行為與未測範圍。
- [ ] 透過 release 封裝路徑與正式 bundle 身分，驗收安裝後的 release 形式簽署套件。記錄版本／commit、簽署事實、OS、權限狀態與證據。僅本機開發簽署版本不足以證明下載版行為。另行授權發布後，再驗證公開下載產物並補證據，不能事先宣稱已完成。

## 完成條件與範圍

本計畫不授權 commit、push、tag 或發布。不包含 APNs 服務、自動更新、螢幕權限重設計或平台擴充。不要為建立測試環境而重設使用者既有的通知偏好。

完成實作及本機 release 形式驗收，將失敗與未測範圍保留在雙語[驗證紀錄](../docs/zh-TW/verification/README.md)，更新[桌面設計](../docs/zh-TW/system-design/desktop.md)與相關 Help／安裝指引及翻譯，再依[計畫完成流程](README.zh-TW.md#完成計畫)收尾。尚未發布時，明確保留公開下載驗收為 release 後續事項。
