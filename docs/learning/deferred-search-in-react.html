打字不卡、清單跟得上：在 React 裡篩選本機清單時，該用 useDeferredValue 還是 debounce

搜尋框邊打字邊篩選清單，是最常見的互動之一，也是最容易在資料變多後開始卡頓的地方。本文說明這個問題真正的成本在哪裡，比較「每個按鍵都立刻篩選」、debounce 與 React 的 useDeferredValue 三種做法，說明為什麼在「清單已經在記憶體裡、成本主要是重畫」的前提下，useDeferredValue 是較好的預設，以及它在什麼情況下會讓你踩到坑。範例來自一個選單列錄影 App 的錄影檔搜尋。

這篇文章要回答的問題

一個介面上有一個輸入框和一份清單，輸入框的內容決定清單顯示哪些項目。使用者連續打字時，我們希望兩件事同時成立：

  1. 輸入框永遠立即回應。每個按鍵都馬上出現在框裡，游標不會頓住，中文輸入法的選字視窗不會延遲。
  2. 清單盡快反映最新的搜尋字。不需要和輸入框同步到同一毫秒，但不應該明顯落後，也不應該顯示錯的結果太久。

資料少時，兩者自然同時成立。問題出在清單變長、每張卡片變複雜之後：每打一個字都要重畫整份清單，重畫的時間開始和打字的速度搶同一條主執行緒。於是可遷移的問題是：當「依輸入重畫清單」變貴時，怎麼讓輸入保持優先，又不讓清單無謂地延遲？

先確認前提：成本到底在哪裡

選做法之前，先看清楚每個按鍵到底觸發了什麼工作。以本文的範例來說，情境如下：

  • 資料已經在記憶體裡。App 的 main process 一次把所有錄影的清單（標題、時間、大小、縮圖網址）送到頁面；搜尋只是在頁面上比對標題，不會為了搜尋去打 API、讀檔或做行程間通訊。
  • 比對本身很便宜。每個按鍵對每支錄影做一次「標題轉小寫、找子字串」。幾千次這種字串操作，在現代電腦上通常遠低於一毫秒。
  • 真正貴的是重畫。每張卡片有縮圖、時間、長度、選單按鈕。搜尋字從「很多結果」變成「很少結果」再變回來時，React 要把幾百、幾千張卡片卸載再掛回 DOM，這比比對貴上好幾個數量級。

這三點就是後面所有判斷的前提。注意第二點：常見的「把每個標題預先轉成小寫存起來」這種優化，在這裡幾乎沒有效果，因為它優化的是本來就不貴的那一段。先找出成本在哪，再決定要優化什麼，比任何單一技巧都重要。

天真做法：每個按鍵都同步篩選並重畫

最直接的寫法，是讓清單直接讀輸入框的值：

TypeScriptfunction Library({ items }: { items: Recording[] }) {
  const [query, setQuery] = useState("");
  const shown = items.filter((item) => matches(item, query));
  return (
    <>
      <input value={query} onChange={(event) => setQuery(event.target.value)} />
      <CardList items={shown} />
    </>
  );
}

每個按鍵都是一次「緊急」更新：React 必須在同一次 render 裡把新的字畫進輸入框，同時把整份清單重算、重畫完，才能把控制權還給瀏覽器。清單一旦重畫要花 50 毫秒，使用者每打一個字就會感覺輸入框卡 50 毫秒；連續打字時，按鍵會排隊，最後一口氣出現。這個症狀很好辨認：輸入框「跟不上手」，而不是清單慢。

常見解法一：debounce

debounce 的意思是「停止打字 N 毫秒之後，才用最後的值做一次工作」。套在搜尋上，就是讓清單讀一個延遲更新的值：

TypeScriptconst [query, setQuery] = useState("");
const [listQuery, setListQuery] = useState("");
useEffect(() => {
  const timer = setTimeout(() => setListQuery(query), 250);
  return () => clearTimeout(timer);
}, [query]);
const shown = items.filter((item) => matches(item, listQuery));

它確實讓輸入框在打字途中不卡，但付出三個代價：

  • 固定延遲，跟機器快慢無關。就算只有二十支錄影、重畫只要兩毫秒，清單也一律晚 250 毫秒才更新。快的電腦和小的清單，都被迫承受為慢的情況設計的延遲。
  • 計時器到期後，重畫照樣會卡。debounce 只是把重畫往後挪，並沒有讓重畫變得可中斷。使用者停頓 250 毫秒後又繼續打字，剛好撞上那次重畫，輸入框一樣會頓一下。
  • 多了要自己管理的狀態。計時器、清理、兩份狀態的同步，都是額外的程式碼與錯誤來源。

debounce 真正擅長的，是讓「每次觸發都有固定外部成本」的工作少做幾次，例如每次搜尋都要打一次 API。它減少的是呼叫次數，不是每次重畫的阻塞。

另一個模型：把更新分成緊急與不緊急

React 18 之後的並行渲染（concurrent rendering）提供了另一種思路：同一個輸入，可以觸發兩種優先順序不同的更新。輸入框顯示新字是緊急的，必須立即完成；清單反映新字是不緊急的，可以在背景做，而且被更新的輸入打斷時可以放棄重來。

useDeferredValue 就是把一個值變成「不緊急版本」的 hook：

TypeScriptconst [query, setQuery] = useState("");
const listQuery = useDeferredValue(query);
const shown = useMemo(
  () => items.filter((item) => matches(item, listQuery)),
  [items, listQuery],
);

使用者打一個字時，實際發生的是兩次 render：

  1. 緊急 render。query 是新的字，但 listQuery 仍然回傳上一次的值。因為清單的輸入沒變（useMemo 直接回傳上次的結果，卡片元件也因為 props 沒變而略過），這次 render 幾乎只更新輸入框，很快就完成。
  2. 背景 render。React 接著以低優先順序、用新的 listQuery 重畫清單。這次 render 可以被中斷：如果使用者在途中又打了一個字，React 會放棄算到一半的結果，先處理新的緊急更新，再用最新的字重新開始背景 render。
壓力debounce 怎麼回應useDeferredValue 怎麼回應
輸入框要立即回應打字途中不重畫，但計時器到期那次重畫仍會阻塞緊急 render 不碰清單；背景 render 可被打斷，輸入永遠優先
清單不要無謂地延遲固定晚 N 毫秒，連小清單也一樣沒有固定延遲：機器快、清單小時幾乎同步，慢時才落後
連續打字時不要做白工只在停頓後算一次（這是它的強項）過時的背景 render 會被丟棄，只完成最後那次
程式碼與狀態要簡單計時器、清理、兩份狀態一行 hook，加上把清單計算 memo 起來

這正是 React 官方文件對兩者的區分：deferred value 和 React 的排程深度整合，延遲多久由裝置的實際速度決定，背景工作可以中斷；debounce 和 throttle 仍然適合用來減少網路請求這類「每次都有外部成本」的工作。

前提：慢的那一段必須能被略過。useDeferredValue 本身不會讓重畫變快，它只是把重畫移到背景。如果清單元件在緊急 render 裡也照樣整個重畫（沒有 memo、或每次都產生新的陣列與函式 props），緊急 render 一樣慢，輸入框一樣卡。把清單的計算放進以 deferred 值為依賴的 useMemo，並讓卡片元件在 props 不變時略過 render，是這個模式能生效的前提。

為什麼在這個前提下它是較好的預設

把論證收斂成五句話：

  • 前提：資料已在記憶體中，每個按鍵沒有網路或磁碟成本，主要成本是 React 重畫清單，而且執行在支援並行渲染的 React 上。
  • 問題：同步篩選讓輸入與重畫搶同一條主執行緒，清單變長時輸入框跟不上手。
  • 對應：useDeferredValue 把重畫移到可中斷的背景 render，輸入的緊急 render 只做很少的事。
  • 選擇：相較於 debounce，它沒有固定延遲、不會在計時器到期時整段阻塞、也不需要自己管理計時器。
  • 界線：一旦每個按鍵都會觸發外部成本，或慢的不是 React 重畫，這個結論就會反轉（見下一節）。

什麼時候不該用它

  • 每個按鍵都會打 API 或讀檔。useDeferredValue 不會減少請求次數：背景 render 被丟棄之前，可能已經觸發了請求。這時應該用 debounce（或 throttle）減少呼叫次數，並用 AbortController 取消過時的請求；兩者可以並用，debounce 管請求，deferred 管畫面。
  • 慢的是 JavaScript 計算，不是 render。例如每次都要對上萬筆資料做模糊比對或排序。背景 render 雖然可中斷，但單一次同步計算本身不可中斷。這時應該先降低計算成本（建索引），或移到 Web Worker。
  • DOM 節點本身就太多。上萬張卡片同時存在時，就算沒有搜尋，捲動和版面計算也會慢。這時需要虛擬化清單（只畫看得到的部分）。在這種規模下，延後顯示解決不了根本問題。
  • 你自己擁有觸發更新的那一行。如果篩選結果是你用 setState 寫入的另一份狀態，直接把那次 setState 包進 startTransition 通常更直接。useDeferredValue 適合「你只拿到一個值，管不到它是怎麼被設定的」的情況，例如從外部 store 或父元件 props 來的值。
  • 清單小而簡單。二十個純文字項目，同步篩選就夠了。加上 deferred value 不會壞事，但也沒有可見的好處；這不是必須優化的地方。

它帶來的新規則：清單會短暫落後於輸入

採用 useDeferredValue 之後，畫面上會同時存在兩個「現在」：輸入框顯示最新的字，清單可能還停在上一個字。對使用者來說這通常無害，但對程式碼來說，任何「設定搜尋字之後，立刻假設清單已經更新」的邏輯都會出錯。

範例 App 就踩到了這個坑。錄影存檔後的通知被點擊時，App 要打開錄影檔分頁、清除搜尋，然後把焦點移到那段錄影的卡片上並捲到它。流程是：清除搜尋字、重畫、立刻對那張卡片呼叫 focus()。問題是：

  • 這個 App 的頁面以外部 store 搭配 flushSync 同步重畫。同步（最高優先）的更新正是緊急更新，所以 useDeferredValue 在這次 render 回傳的仍是舊的搜尋字。
  • 如果那段錄影剛好被舊搜尋字篩掉，這次 render 之後，DOM 裡根本還沒有那張卡片，focus() 安靜地什麼也沒做。
  • 背景 render 稍後把卡片畫出來，但沒有人重新聚焦或捲動。使用者點了通知，看到的卻是沒有目標的清單。

修正的原則是：使用者在打字時，延後是好的；程式主動改變搜尋並馬上要用到結果時，就不要延後。做法是讓這種程式化的重設，在那一次 render 直接使用即時的值：

TypeScript// 由程式清除搜尋、要立刻聚焦結果時設為 true；使用者再打字時設回 false。
const deferredQuery = useDeferredValue(store.query);
const listQuery = store.queryNow ? store.query : deferredQuery;
const shown = useMemo(() => filter(items, listQuery), [items, listQuery]);

這次重畫會是同步的，清單很長時可能稍慢一點；但它只發生在少見的「從通知跳到某段錄影」路徑上，正確地跳到目標比那幾十毫秒重要。其他同類情況也適用同一條規則：鍵盤在搜尋結果間移動的選取、搜尋後自動選取第一筆、測試裡「輸入後立刻檢查清單」的斷言，都需要意識到清單可能還沒跟上。

用真正的瀏覽器驗證時序。這個問題在以 happy-dom 執行的頁面測試裡重現不出來：那個環境的排程和真正的瀏覽器不同，拿掉修正後測試照樣通過。最後是在 Chromium 裡用 Playwright 寫測試：先搜尋一個不存在的字讓清單變空，再模擬通知進入，斷言焦點落在那張卡片上。只有這個測試在拿掉修正時會失敗。和渲染排程有關的修正，要在真正的渲染引擎裡證明。

回到範例：這個 App 實際的選擇

錄影檔分頁的情況完全符合前提：清單由 main process 一次送到頁面，搜尋只比對標題，沒有任何 I/O；卡片元件以 memo 比較 props，清單計算以 deferred 搜尋字為依賴放在 useMemo 裡。所以搜尋改用 useDeferredValue，而不是 debounce。另外兩個常被提起的優化則刻意沒做：

  • 預先算好小寫標題：比對不是成本所在，省下的時間量測不到。
  • 虛擬化清單：目前的規模（幾十到幾百支錄影）還不需要；每天一組的區塊已用 content-visibility: auto 讓畫面外的部分不參與排版。真的出現上千支錄影、而且量測顯示捲動或清空搜尋時明顯卡頓，才值得引入。

帶走的判斷問題

下次遇到「輸入驅動清單」的介面，可以依序問自己：

  1. 每個按鍵會不會觸發網路、磁碟或行程間通訊？會的話，先用 debounce／throttle 減少次數，並取消過時的請求。
  2. 不會的話，慢的是什麼？是 React 重畫、純計算，還是 DOM 節點太多？分別對應 useDeferredValue、降低計算成本或 Web Worker、虛擬化。
  3. 採用 useDeferredValue 時，清單的計算和子元件能不能在緊急 render 裡被略過？不能的話，它不會有效果。
  4. 有沒有程式碼在改變搜尋之後，立刻假設清單已經更新？那些路徑需要即時的值，或在結果出現後再行動。
  5. 驗證時序相關的行為時，測試環境的排程是否和真正的瀏覽器一致？不一致時，用真正的瀏覽器測。
