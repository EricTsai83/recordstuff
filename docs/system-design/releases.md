# GitHub release automation

[English](releases.md) | [繁體中文](../zh-TW/system-design/releases.md)

Updated: 2026-10-03. Pushing a version tag is the only release action, and the tag is the version: CI stamps it into the build, signs, verifies, publishes, re-verifies the public download and records the facts back on main in one run. The draft/promote flow with an in-pipeline manual acceptance gate was used for [0.1.1](../verification/releases/0.1.1.md) and retired the same day 0.1.2 was prepared; manual checks now happen before tagging. [0.1.2](../verification/releases/0.1.2.md) was the first release on this flow: tag push to public release in under three minutes.

By the maintainer's decision of 2026-10-03 ([design decisions](decisions.md)), the same tag also builds and publishes an unsigned Windows x64 installer for every version after 1.1.1 (`LAST_MACOS_ONLY_VERSION` in `scripts/lib/release-manifest.mts`), with the same flow as the Mac: built, gated, published, downloaded anonymously and gated again. Its gates run on GitHub's Windows runners; no Windows hardware is involved, so nothing about Windows capture, system audio, notifications or the tray is verified by a release. As of this update no two-platform release has been published; the first, a pre-release rehearsal and then a stable version, waits for the maintainer's explicit tag request.

See [delivery diagrams](delivery.md) for the website/App split, deployment ownership, and update-feed flow.

For stable releases, `record` and the website share the verifier in `scripts/lib/release-manifest*.mts` to fetch and cross-check the GitHub release, `release.json`, SHA256SUMS, `release-win32-x64.json` for a version after 1.1.1, and the download assets once. The website manifest has a `windows` block exactly for those versions; the `release.json` asset and the website's `/release.json` feed keep their darwin-arm64 shape, because installed macOS apps parse them. That snapshot generates `website/release-manifest.json`, both README download blocks and any missing verification records. README and verification Markdown are outputs, never parsed back as release data. Offline tests read the committed JSON manifest to check the READMEs independently of the candidate version stamped into `package.json`; this verifies committed consistency, not whether GitHub has a newer release. Pre-releases create historical verification records only and do not change the stable manifest, READMEs or package.json.

The committed `website/release-manifest.json` is the stable download pointer, and `record` validates it before fetching the release. A verified stable version newer than it is **promoted**: the manifest and both README blocks are written from the same snapshot. The same version is **unchanged** when its release identity and asset facts match the committed ones (source commit, publication time, DMG name, size and SHA-256, the Windows installer's name, size, SHA-256 and URLs when the version carries one, and the asset and release URLs, as `pnpm site:manifest verify` compares them): the committed manifest keeps its bytes, including `verifiedAt`, and the README blocks are rendered from the identical facts; any difference fails before a write and lists the fields. An older version is **historical only**: it adds its missing verification records and leaves the manifest and READMEs alone, so an older tag recorded late or rerun cannot move the download pointers backward. package.json is not the pointer authority, because it can hold an unrelated development or candidate version; it keeps its own rule of advancing to a newer recorded stable version and never moving back. A missing, unreadable or malformed committed manifest stops the record with its remedy (restore it from main, or regenerate it for the current stable release with `pnpm site:manifest generate vX.Y.Z`); `record` never chooses a pointer without one, and there is no implicit bootstrap. The output names the outcome and the files written; a retry that changes nothing writes nothing. A historical-only stable record still runs `deploy-website`, which redeploys the unchanged pointer.

The release tool and website share root-level `scripts/lib/release-manifest.mts` (schema and validation) and `release-manifest-client.mts` (published-data transport). The website CLI owns only its paths and commands. Recording prepares every output in memory after reading and validating all inputs, then writes the files. This prevents malformed inputs or missing markers from causing partial updates; it is not a cross-file power-loss transaction. `scripts/release-record.test.ts` runs the real CLI in disposable checkouts with fixed network and gh responses, covering promotion, an older stable version recorded after a newer one, equal-version retries and conflicting source commit, digest or size, prerelease recording, package.json ahead of and behind the manifest, a missing, non-JSON, malformed or pre-release baseline, preserved manual evidence, candidate versions, commit mismatches and invalid README markers; every failure leaves all outputs unchanged.

Vercel retains Root Directory `website` and must enable **Include source files outside of the Root Directory in the Build Step** so builds can read the shared modules. The deployment workflow checks that setting and also triggers on `scripts/lib/release-manifest*.mts` changes.

## Release contract

[release.yml](../../.github/workflows/release.yml) builds and publishes only on `v*` tag pushes. There is no branch or pull-request trigger for App publication. A manual dispatch with an existing tag runs only the post-publish verification job, never an App build, publication or website deployment. Website delivery runs independently through [website.yml](../../.github/workflows/website.yml): pushes to main affecting `website/**`, shared release manifest modules, the shared version grammar (`src/shared/version.ts`), or that workflow automatically deploy the website; `workflow_dispatch` on main retries website delivery without a release tag or App job. The workflow is named Release. The macOS `build`, `publish` and `verify-published` jobs use `macos-15`, the build with an arm64 runtime assertion; `build-windows` and `verify-published-windows` use `windows-2025`, the build with an x64 assertion; `record` uses `ubuntu-24.04`. Every job uses Node 24.21.0, and the builds pnpm 10.33.4 and frozen lockfile installation. Actions are pinned to full commit SHAs; recheck upstream when updating.

Sequence in one workflow run: two builds run in parallel. `build` (macOS): tag/source checks → code checks (`pnpm check`) → import fixed identity → `pnpm dist:mac` → mounted verification → candidate artifact. `build-windows`: the same tag/source checks and version stamp, refusing a version that carries no Windows build → `pnpm check` → `pnpm dist:win` → `release.mts candidate-windows`, which installs, inspects and uninstalls the installer on the runner and writes `release-win32-x64.json` → a build-provenance attestation of the installer (`actions/attest-build-provenance`) → its own candidate artifact. Then → independent publish job that needs both builds, reverifies without private keys (the Windows installer by its bytes, record and checksum line, since it cannot run on macOS), writes SHA256SUMS with one line per binary asset and creates one public release → `verify-published` job that downloads the version's assets (`release.mts assets`) anonymously from the public release URL, checks SHA256SUMS, reruns the mounted/signature/metadata gates and compares GitHub's own asset digests (`release.mts published`), and alongside it `verify-published-windows` on `windows-2025`, which downloads the same assets, compares `Get-FileHash` with the installer's SHA256SUMS line, runs `gh attestation verify` and installs, inspects and uninstalls the published installer, requiring the `app.asar` hash recorded at build time (`release.mts published-windows`; a macOS-only tag has nothing to check there) → `record` job, which needs both verification jobs, that writes the release facts into main: package.json version, the marked README download block in both languages, a bilingual verification record skeleton and, for stable tags only, the website's `website/release-manifest.json` (generated from the same verified snapshot by `release.mts record`, which moves the manifest and README blocks only to a newer stable version; pre-release tags keep their record commit but never reach the website), committed as `github-actions[bot]` → `deploy-website` job (stable tags only) that calls the reusable `website.yml` workflow, which checks out main, validates project access and submits source with the pinned Vercel CLI (`deploy --archive=tgz --prod`). Vercel installs `website/` dependencies and runs `pnpm test && pnpm check` before publishing the site, including online manifest verification and generated feed/link checks. It is skipped with a notice when `VERCEL_TOKEN`, `VERCEL_ORG_ID` or `VERCEL_PROJECT_ID` is not configured, has `contents: read` only and never touches the release; a website failure leaves the release public and the previous site live. The build jobs have contents:read, and `build-windows` also id-token and attestations write for its attestation; the publish and record jobs have contents:write; the verification jobs need neither secrets nor write access. Signing secrets are supplied only to the macOS build signing step; the Windows build has none, because its installer is unsigned by decision. A failure in either build or in reverifying either candidate fails the whole tag before publication: a version after 1.1.1 is published for both platforms or not at all. The release environment permits `v*` tags, controlled by trusted repository maintainers. One concurrency group, `recordstuff-delivery` (named `recordstuff-macos-delivery` before Windows was added), serializes tag releases without cancelling running releases; manual re-verification runs use a group of their own. GitHub keeps only one pending run per group and cancels it when another queues, so push one tag at a time behind a running release; a tag cancelled that way has no release and no record, and `gh run rerun <run-id>` starts it again. A separate website production concurrency group serializes all website entry points without cancelling active deployments. Each website job checks out the latest main after acquiring the lock, so an older queued trigger cannot restore an older checkout. The release job calls the reusable workflow explicitly because manifest commits pushed with `GITHUB_TOKEN` do not trigger push workflows.

Gates that stop a release, in order: the tagged commit is not an ancestor of `origin/main`; the tag is malformed or older than the last version recorded in package.json; the tree is not clean; a release for that tag already exists (drafts included); code checks fail; secrets are missing or the imported identity fingerprint is not `01B373511530BBF287CA35E54C10A5F017AAD637`; bundle signatures, identifiers, hardened runtime or designated requirement fail; the DMG root is not exactly `Applications` and `RecordStuff.app` plus permitted hidden Finder layout files; packaged version or architecture mismatch; candidate metadata or SHA256SUMS differ on reverification; the tag no longer points to the verified commit. For a version after 1.1.1 the Windows build also stops the release when the runner is not x64; the installer or the installed `RecordStuff.exe` is not Authenticode `NotSigned`; the silent per-user install fails or registers a machine-wide (HKLM) uninstall entry; there is not exactly one HKCU uninstall entry whose DisplayVersion is the version; `RecordStuff.exe` is not PE machine x64 or its ProductVersion differs; a tray ICO or the Start-menu shortcut is missing; the silent uninstall fails or leaves the app, the shortcut or the registration; or the installer's size or SHA-256 differs from `release-win32-x64.json` on reverification. No macOS fallback without the fixed identity, no partially verified fallback and no single-platform fallback exists.

Version semantics: the tag is the single source of the version. The build job writes the tag's version into package.json in its working tree (`release.mts version`) before `pnpm dist:mac` and `pnpm dist:win`, so the Apps, installers and records carry it; the repository's package.json records the newest recorded stable version for `preflight`: the record job advances it and never moves it back, while the download pointers follow the committed manifest. `vX.Y.Z` publishes as the latest release, unless a newer stable release is already public: then it stays historical (`--latest=false`), so the latest release, the app's update fallback, never moves back. `vX.Y.Z-suffix` (for example `v0.2.0-rc.1`) publishes flagged as a pre-release, is never marked latest, and does not update package.json or the README. Both use the same builds and gates. The asset set follows the version: 1.1.1 and earlier keep the three-asset contract (DMG, `release.json`, SHA256SUMS), so main can still verify those tags; every later version, pre-releases included, carries five, those three plus `RecordStuff-<version>-x64-unsigned-setup.exe` and `release-win32-x64.json`.

The certificate fingerprint is pinned. Each build imports encrypted PKCS#12 into a temporary keychain, configures codesign key access and certificate-specific Code Signing trust. A trap and always-cleanup remove certificate files, keychain, and trust. This supports disposable GitHub-hosted runners, not persistent runners without adaptation.

Since 0.1.2 the DMG contains only the App and the Applications link over a generated drag-arrow background; no help documents are bundled in any format. Installation, manual update and removal guidance lives in the [website Help](https://record.ericts.com/help), release notes and the commit-pinned [installation guide](../../resources/INSTALL.md). Future English release notes should link the website Help alongside the commit-pinned guide. The Windows installer is a per-user one-click NSIS installer; its guidance (SmartScreen, manual update by running the new installer, uninstall from Settings → Apps, where data stays) is in the same guide, Help and the release notes' Windows section.

## Operation

Verification is a development activity, done before the tag exists. Releasing is two commands on a pushed main:

1. Run `pnpm start:app` (build, sign, verify and open the same App bundle CI will package) and then `pnpm acceptance`: it starts and stops a recording with the global shortcut, verifies the file's integrity tier and writes its report under `docs/verification/measurements/` (local, gitignored). Optionally let an agent follow the [native acceptance skill](../../.agents/skills/native-acceptance/SKILL.md) to read that report and check playback with `pnpm acceptance:playback`. If `pnpm acceptance` cannot run (shortcut refused, no Accessibility access for the terminal, no Chrome), fall back to the manual check: make a short recording and play it back. Either way this is the whole functional check; the DMG adds nothing for App behavior, and CI verifies DMG structure on every tag. Only when packaging configuration changed (electron-builder files, icons, background, DMG layout) also run `pnpm dist:mac`, open the DMG from `dist/` and confirm the Finder window shows the App, the arrow and Applications with nothing else. There is no Windows step: without a Windows machine no manual Windows smoke precedes a tag. For a Windows packaging change, dispatch [check.yml](../../.github/workflows/check.yml) on the branch before merging; its `check-windows` job builds the installer and runs the same install/uninstall gates. Every release's record must therefore list Windows capture, system audio, notifications and the tray as not verified on hardware.
2. Tag the pushed commit with the next unused version and push the tag. Nothing in the repository names the version beforehand.

```bash
git tag v0.1.3
git push origin v0.1.3
gh run watch --exit-status "$(gh run list --workflow=release.yml --limit 1 --json databaseId --jq '.[0].databaseId')"
```

When the run finishes, `gh release view v0.1.3` shows the public release with its assets (three for 1.1.1 and earlier, five for a later version), and main carries a `docs(release): record published v0.1.3` commit from the record job with package.json at 0.1.3, the README download block in both languages, and `docs/verification/releases/0.1.3.md` plus its translation. Pull main, then complete the record's "Local acceptance before tagging" and "Not recorded" sections with what was actually done in step 1 (the acceptance skill writes its summary there; a manual fallback is written by hand); the generated skeleton never claims a check that was not performed. The `verify-published` and `verify-published-windows` jobs are the download check: they fetch what an anonymous user gets and rerun every artifact gate on GitHub's network, so no local re-download is needed. If it fails, the release stays public and the maintainer decides between a fix-forward version and leaving it; the job never unpublishes. To re-verify an existing release later, dispatch the workflow with its tag; both verification jobs run, each by that version's own asset set:

```bash
gh workflow run release.yml --ref main -f tag=v0.1.2
```

Rollback is a new version: never overwrite, delete or re-tag a published release. If the workflow fails before publishing, fix the source, bump the version, and tag again; a tag on a failed run may be left in place or deleted, but its version must not be reused for a release once any release object (even a partial one) exists for it. If a run fails after the release object was created, treat that version as consumed and handle the partial release by hand. Do not remove verification gates to unblock delivery.

## Website delivery

Configure repository Actions secrets `VERCEL_TOKEN`, `VERCEL_ORG_ID`, and `VERCEL_PROJECT_ID`; the Vercel project Root Directory remains `website/`. Vercel Git deployments stay disabled to avoid duplicate deployments. A missing secret skips deployment with a notice. Website pushes and stable App releases share the same online manifest verification, website tests, Astro diagnostics, generated feed comparison and built-link checks inside the Vercel build before its output goes live. Non-website commits do not trigger standalone website deployment; pre-release tags do not call it. To retry after configuring secrets or fixing a deployment failure:

```bash
gh workflow run website.yml --ref main
```

This workflow never builds, signs or publishes the App. After deployment, verify the public feed and actual App transport before treating update delivery as accepted.

## Tool boundaries and failures

`node scripts/release.mts preflight|version|candidate|candidate-windows|verify|publish|published|published-windows|record|assets vX.Y.Z [directory]`, or `windows-smoke [directory]`, shares local and CI validation. `preflight` requires a clean tree, a tag not older than the last recorded package.json version, and an unused release. `version` stamps the tag's version into the working-tree package.json for the build. `record` reads the committed stable manifest and the public release, then writes missing verification records and, for a stable tag, advances package.json and writes the stable website manifest and the marked README blocks (`<!-- release-download:start/end -->`) only as the promoted, unchanged or historical-only outcome above allows; it never overwrites an existing record. `candidate` computes SHA256SUMS and release.json from final DMG bytes, recording version, source commit, repository, platform, filename, size, SHA-256, certificate fingerprint, app.asar hash, Node and pnpm. `verify` rechecks a candidate directory against those files. `published` does the same on files downloaded from the public URL, taking the version from the tag and the source commit from what the tag points to (so the current tooling can verify any older release from a main checkout), and additionally requires the GitHub release to be non-draft with exactly the version's asset set, matching by name, size and GitHub-computed SHA-256 digest; for a version after 1.1.1 it also checks the Windows installer against `release-win32-x64.json` and SHA256SUMS. `assets` prints a tag's asset names for the workflow's downloads. The Windows modes need a Windows x64 host and run in CI: `candidate-windows` installs the installer silently, checks it (the gates above) and uninstalls it, then writes `release-win32-x64.json` with version, source commit, repository, platform, filename, size, SHA-256, the installed `app.asar` hash, signature state `unsigned`, Node and pnpm; `published-windows` checks the downloaded installer against its record, SHA256SUMS and GitHub's digest, then repeats the install gates and requires the same `app.asar` hash; `windows-smoke` runs the install gates for the installer `pnpm dist:win` just built, without a tag, and refuses a machine where RecordStuff is already installed. The two `app.asar` hashes of a release are recorded in its two records; their equality is not enforced. `publish` rechecks, confirms the tag points at the verified commit, writes the English notes (with macOS, Windows and Verify sections for a version after 1.1.1) and creates the public release with `gh release create --verify-tag` (`--latest`, `--latest=false` for a stable version older than a published one, or `--prerelease`).

`start-app.mjs --verify-app APP_PATH` uses only the public `RECORDSTUFF_SIGN_IDENTITY` SHA-1 and reuses existing deep signature, certificate, identifier, runtime and designated requirement checks. It requires no private key, build or app launch. `assertDmgContents` requires the root to contain exactly `Applications` and `RecordStuff.app` plus, at most, the hidden regular files `.DS_Store`, `.VolumeIcon.icns` and `.background.png`/`.background.tiff`; any other entry, any hidden directory or symlink, or a guide hidden with a leading dot fails the release.

CI cannot prove screen or system-audio capture: runners have no TCC grants. That is why recording is checked locally before tagging, on macOS only. What CI proves is that the committed source builds, signs with the pinned identity, packages to the expected layout, and that the published bytes are the verified bytes; for Windows, that the unsigned installer installs per user, registers, matches its record and attestation and uninstalls cleanly. The Windows app is never started, so nothing it does at run time is proven.

Apple notarization, Windows code signing, automatic App updates, Intel Mac and Windows on Arm delivery, Windows hardware verification and warning-free installation remain outside scope. See [signing design](signing.md) for T3 Code comparisons.

After frozen installation, CI explicitly runs Electron 44 install.js because the package has no postinstall. cleanup-release-keychain.py bounds each OS cleanup operation to 15 seconds, warns on failure, and removes temporary files. Disposable runner teardown removes any remaining OS state.

For local `verify` or `publish`, check out the source commit recorded in release.json; later documentation commits on main do not change candidate bytes. A local `publish` of a version after 1.1.1 also needs the CI-built Windows candidate and its record in the directory.
