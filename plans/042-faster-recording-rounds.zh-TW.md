# 042 — 更快的錄影回合

[English](042-faster-recording-rounds.md) | [繁體中文](042-faster-recording-rounds.zh-TW.md)

狀態：已規劃，尚未實作。建立日期：2026-09-26。來源：[plan 041](../docs/zh-TW/verification/history-2026-09.md#plan-041-結案--2026-09-26) 回合的耗時分析與維護者要求。排在 040 與 037 之前，讓它們的錄影回合受益；沒有硬性相依。執行順序見[佇列](README.zh-TW.md#順序與狀態)。

## 問題與證據

plan 041 回合佔用桌面約 50 分鐘，其中約 20 分鐘重複了已經存在的證據。流程規則的部分已經修正：2026-09-26 [測試指南](../docs/zh-TW/testing.md#縮短錄影回合)新增了沿用基準、只錄在該環境下有差別的案例、候選方案只篩選一次、改動後每個量只量一次、有疑慮才重複等規則。剩下的是 runner 的固定成本：

| 041 回合的指令 | 錄影 | 實際耗時 |
| --- | --- | --- |
| `pnpm matrix -- fps` | 2 × 30 秒 | 103 秒 |
| `pnpm matrix -- quick` | 3 × 30 秒 | 144 秒 |
| `pnpm matrix -- long` | 180 秒 | 218 秒 |

每個案例還要付出：App 啟動、autorecord 的 1.5 秒開始延遲、停止與存檔、結束 App、以 ffprobe 讀兩次與 ffmpeg 讀三次的驗證（完整 `-count_frames` 解碼、逐格時間戳、blackdetect、silencedetect 與 astats），以及固定 10 秒的休息。每次執行指令還會重新建置 `out/`，並開啟測試素材、等待 5 秒。要重複就得再執行一次，所以 `fps` 跑兩次就付了兩次建置與兩次素材啟動。以上各部分的成本是從指令總耗時推估的；步驟 1 會在任何修改之前先量測。matrix 也沒有中斷時的清理：按 Ctrl-C 後素材瀏覽器仍開著，autorecord 的 App 會繼續錄到計時結束。

## 範圍

範圍內：`pnpm matrix` 的編排（一次執行多個 matrix 與重複、中斷清理、各階段計時）、案例之間的休息、短案例的長度，以及驗證的解碼次數。範圍外：門檻與必要證據、測試素材、App 的 autorecord 行為與每個案例各啟動一次 App（這讓案例彼此隔離）、`pnpm acceptance` 以及通知、設定、更新 runner、音質診斷、Windows。

## 步驟 1 — 量出時間花在哪裡

- [ ] 每次 matrix 執行都印出並記錄各階段耗時：建置、開啟素材，以及每個案例的啟動到開始錄影、錄影、停止到存檔、結束 App、每個驗證工具、休息。在維護者電腦上至少收集一次 `fps`、一次 `quick` 與一次 `long`。用這張表而不是上面的推估，決定要實作步驟 2 的哪些項目。

## 步驟 2 — 只在量到成本的地方移除固定成本

- [ ] 一次執行多個 matrix 與重複，例如 `pnpm matrix -- fps,long --repeat 2`：只建置一次、開一次素材、一個 desktop round；重複的案例像節奏診斷的幀率那樣交替執行，讓沒有哪個案例總是最先或在機器最熱時執行。摘要保留每一次執行，並依案例整理重複結果的最小值、median 與最大值；任何一次 fail、blocked 或 incomplete 都讓該案例不能通過，exit code 維持不變。
- [ ] 案例之間的休息：在相同案例上比較現行的 10 秒與較短的休息，或把驗證時間當作休息。只有 CPU、平均幀率、間隔 median 與掉格都落在步驟 1 觀察到的跑與跑之間差異內，才採用較短的休息。
- [ ] 短案例：比較 15 秒與 30 秒的 `fps` 與 `quick` 案例。`all` matrix 已經使用 15 秒；以每秒一次閃光計算，15 秒的案例仍有約 14 組閃光／短音配對，遠高於至少 3 組的要求。只有每個判定的指標都落在觀察到的差異內，才採用 15 秒；`long` 維持 180 秒。
- [ ] 驗證：若步驟 1 顯示解碼佔了可觀的比例，改由一次 ffmpeg 執行取得同步標記與聲道能量，而不是三次。用受控產生的媒體檢查，必須得到與分開執行相同的閃光、短音與各聲道 RMS；工具失敗時該項檢查仍須判定失敗並丟棄部分輸出（plan 030 的規則）。
- [ ] 中斷：收到 SIGINT 或 SIGTERM 時關閉素材瀏覽器，讓進行中的 autorecord 案例存完檔或把它停止，結束 desktop round，確認本輪的程序都已結束，再以 130 或 143 結束，做法比照節奏診斷。清理時不得結束其他 RecordStuff。

## Go criteria

- 同一組證據（例如 `fps` 兩次加 `long` 一次）的實際耗時，比分開執行時至少少 25%。
- 在相同程式碼下，沒有任何判定的指標變動超過跑與跑之間的差異；判定、必要證據與 exit code 不變；重複結果的摘要不會掩蓋失敗的那一次。
- 量到的節省很小或比較未通過的項目，就放棄並記錄原因，不要照樣實作。

## 驗證與排除

- [ ] `pnpm check`，並補上單元測試：參數解析（多個 matrix 名稱、`--repeat` 的範圍、未知名稱）、交替順序、保留失敗的重複摘要，以及（若有實作）單次解碼與分開執行的解析結果一致。
- [ ] 實際執行修改後的 runner：在維護者電腦上跑一次多 matrix 加 `--repeat` 的回合，以及一次中斷的回合並確認沒有殘留的 Electron 或素材程序。記錄改動前後的實際耗時與各階段表。
- [ ] 排除：App 錄影 smoke 與原生驗收，因為 App 沒有改動；levels matrix、十分鐘錄影與音質診斷，除非修改碰到它們。

- [ ] 更新雙語[工具指南](../docs/zh-TW/system-design/tooling.md)的 matrix 章節與指令，在雙語驗證歷史與索引記錄耗時、採用與放棄的項目及其證據，然後刪除本計畫與其翻譯。沒有另外要求時不 commit、push 或發布。
