設定頁怎麼儲存才不會卡：每項設定各自儲存、單一寫入者排序、畫面樂觀顯示

當設定的真實值住在另一個 process（Electron 的主程序、後端伺服器、作業系統服務），畫面每改一個值都要來回一趟。這篇說明一個可遷移的做法：每項設定各自送出、由擁有資料的一方單一寫入並替結果編號、畫面先顯示使用者的選擇並在失敗時退回，以及它在什麼條件下才是最好的預設、什麼時候不該用。

情境：值不在畫面這邊

許多桌面 App 和網頁的設定頁都長這樣：畫面（renderer、瀏覽器）只負責顯示與收集輸入，真正的設定值由另一方保管。以 Electron 為例，設定頁跑在 renderer process，主程序（main process）擁有設定檔、驗證值是否合法、在錄影中鎖住不能改的項目，也會因為別的入口（選單列圖示、快捷鍵）改動設定而主動推送新的畫面資料。

這個模式成立需要幾個前提，後面的論證都建立在它們上面：

  • 擁有者在另一邊。畫面送出「我想把 X 改成 v」，擁有者決定接不接受，並回傳整份最新的畫面資料（以下稱 view）。
  • 一次只改一個值，而且改動很頻繁。開關、分段按鈕、滑桿、拖曳位置，使用者常在幾百毫秒內連續操作好幾項。
  • 往返很快但不是零。同機 IPC 加上寫檔通常是幾毫秒到幾十毫秒；偶爾會失敗（磁碟錯誤、值被拒絕、正在錄影而被鎖）。
  • 擁有者也會主動推送。畫面收到的 view 可能來自自己的請求，也可能來自別的入口，抵達順序不保證等於產生順序。

本文的範例是一個螢幕錄影 App 的「錄影工作室」：使用者調整相機泡泡的寬、高、圓角，切換鏡像，拖曳泡泡位置，也調整系統聲音的音量。每一個動作都是一次「改一個值」。

天真的做法會怎麼壞

做法一：同一時間只存一個，其他控制項鎖住

最直覺的保護是全頁一個「正在儲存」旗標：存檔期間，其他設定的變更直接丟掉，為了不讓使用者點了沒反應，乾脆把其他控制項 disable。它確實避免了並行，但使用者看到的是：改寬度時，高度、圓角、音量滑桿全部閃一下變灰；手快一點，第二個點擊就消失了。保護的是程式，犧牲的是操作。

做法二：畫面這邊排隊

把「丟掉」改成「先記著，等前一個存完再送」，閃爍消失了，但帶來三個新問題：無關的設定互相等待（延遲串成一條鏈）；排隊中的變更只存在畫面記憶體裡，視窗在那幾十毫秒內關掉就遺失；而且為了讓排隊中的值看起來已生效，需要另一套顯示來源，和滑桿、數字欄位自己記住的拖曳中值並存，兩套規則難以維護。

做法三：全部直接並行送出，不做任何排序

反方向走到底也會壞。兩個請求同時抵達擁有者，如果各自「讀出目前設定、改一個欄位、寫回檔案」，後寫的會蓋掉先寫的改動（lost update）；回應抵達畫面的順序也不固定，較早產生的 view 晚到時，會把畫面倒回舊狀態。

這三種失敗指出了要同時滿足的力量：

  • 使用者的每個選擇都要被送出，不能被丟掉，也不該被無關的存檔擋住。
  • 寫入必須有確定的順序，每次都從最新的已存值出發。
  • 畫面不能被較舊的資料蓋回去。
  • 失敗要能被看見，而且歸屬清楚：是哪一項、要不要重試。
  • 控制項不該閃，也不該在使用者手上突然變灰。

模式：把三種責任分開

關鍵觀察是：「寫入順序」、「畫面新舊」和「單一設定的進行中狀態」是三件不同的事，做法一用一個全域旗標同時處理三件，所以只好把全頁鎖住。把它們分給最適合的一方：

  1. 寫入順序交給擁有者的單一寫入者。擁有者用一條佇列依序處理所有寫入，每次都從上一次成功寫入後的值套用變更。不管畫面同時送來幾個請求，檔案上都不會有 lost update。
  2. 畫面新舊交給遞增的版本號。擁有者每產生一份 view 就給它一個遞增的 revision。畫面只套用比手上更新的 view，較舊的直接丟棄。抵達順序因此不再重要。
  3. 進行中狀態改成每項設定各一份。畫面替每項設定記住「正在存哪個值、是哪一次請求」和「上一次為什麼失敗」。一項設定的存檔只影響它自己：同一項設定的新選擇取代舊的，其他設定照常送出。

在這三個基礎上，畫面可以安全地做第四件事：樂觀顯示。使用者一選，控制項立刻顯示新值；擁有者確認後換成它回傳的值（通常相同）；失敗時退回擁有者的值，並在那一列說明原因。

每個機制解決哪個問題

機制解決的失敗放在哪一方
單一寫入佇列，每次從最新已存值套用並行寫入互相覆蓋（lost update）、暫存檔競爭擁有者
每份 view 帶遞增 revision，畫面丟棄舊的晚到的舊回應或舊推送把畫面倒回去擁有者編號、畫面比較
每項設定各自的進行中狀態與最新請求編號無關設定互相等待或被丟掉、全頁鎖住造成閃爍畫面
同一項設定只聽最新那次請求快速連點時，較早的結果把較新的意圖顯示成失敗或舊值畫面
樂觀顯示，失敗時退回擁有者的值點了之後要等一個往返才看到變化；失敗後畫面停在錯的值畫面
每項設定各自的錯誤與重試基準一個錯誤蓋掉另一個、重試在值已被別處改動後仍出現畫面

值與動作要分開對待

不是每次送出都是「改一個值」。「開啟系統通知設定」、「檢查更新」、「選擇資料夾」是動作：它們沒有可以先顯示的結果，重複觸發還可能開兩個對話框。所以：

  • 值做樂觀顯示，同一項設定的新選擇取代舊的。
  • 動作不做樂觀顯示；同一項設定的動作在執行中時，再按一次會被忽略。但它只等自己，不等其他設定。
  • 連續輸入（拖曳滑桿、拖曳位置、打字）由控制項自己保留草稿值，放開或送出時才算一次選擇。打字的內容尤其不該被樂觀值覆蓋：如果擁有者拒絕了這個檔名，使用者需要原本打的字來修改，而不是看到它被換回舊值。
  • 少數真正需要獨佔的操作才等所有存檔完成，例如結束 App（不該在存檔途中離開）、會攔截所有按鍵的快捷鍵編輯器。這是例外清單，不是預設。

程式碼長什麼樣

以下是範例 App 實際採用的形狀，刪去了焦點管理與報讀等細節。先看擁有者端的單一寫入者：每次寫入都排在前一次之後，並從最新的已存值計算新值，前一次失敗也不會卡住後面的寫入。

TypeScript// 主程序：設定檔的唯一寫入者
private save(update: (current: Settings) => Settings): Promise<void> {
  const run = this.queue.then(async () => {
    const next = update(this.settings); // 從最新已存值出發
    await this.write(next);
    this.settings = next;
  });
  this.queue = run.catch(() => undefined); // 失敗只拒絕自己的呼叫者
  return run;
}

擁有者每產生一份 view 就遞增 revision，畫面只接受更新的版本。這一行讓「哪個回應先到」不再影響正確性：

TypeScript// 畫面：較舊的 view 一律丟棄
export function render(next: SettingsView): void {
  if (next.revision !== undefined && view?.revision !== undefined && next.revision < view.revision) return;
  view = next;
  // …重新繪製
}

畫面端每項設定有自己的進行中狀態與錯誤。送出時只登記自己那一項；回應回來時，只有「這項設定最新的那次請求」能決定它成功或失敗，但任何回應帶回的 view 都照 revision 套用：

TypeScriptconst saves = new Map<string, { choice: string; request: number }>();
const failures = new Map<string, Failure>();

export async function choose(group: string, choice: string): Promise<void> {
  const id = ++requestId;
  saves.set(group, { choice, request: id }); // 同一項設定的新選擇取代舊的
  failures.delete(group);
  draw();
  const newest = () => saves.get(group)?.request === id;
  try {
    const result = await window.settings.choose(group, choice);
    render(result.view); // 由 revision 決定要不要套用
    if (newest() && !result.applied) failures.set(group, failureFrom(result, group));
  } finally {
    if (newest()) saves.delete(group);
    draw();
  }
}

樂觀顯示只需要一個讀值函式：這項設定正在存的值若是它自己的選項之一，就顯示它；否則顯示擁有者確認的值。存檔結束（不論成敗）後，進行中的紀錄被移除，畫面自然回到擁有者的值。

TypeScriptexport const confirmed = (group: SettingsGroup) =>
  group.choices.find((c) => c.checked)?.id ?? "";

export const committed = (group: SettingsGroup) => {
  const save = saves.get(group.id);
  const isValue = save && group.choices.some((c) => c.id === save.choice) && !isAction(group, save.choice);
  return isValue ? save.choice : confirmed(group);
};

注意失敗時記錄的「重試基準」要用 confirmed，不能用 committed：失敗那一刻進行中的紀錄還在，用樂觀值當基準會讓重試判斷錯誤。

為什麼它是這些前提下最好的預設

和最簡單的可行替代方案「全頁一個存檔鎖」相比：鎖確實正確，但它把三種不同的保證綁在一起，代價由使用者承擔（閃爍、被吞掉的點擊、無關設定互相等待）。拆開之後，每一種保證由最有資格的一方提供：擁有者本來就是唯一能決定寫入順序與版本的人；畫面本來就是唯一知道使用者剛剛選了什麼的人。和「畫面端排隊」相比，它不需要第二套顯示來源，也沒有「已顯示但尚未送出」的空窗。

它接受的代價是：畫面上會短暫出現擁有者還沒確認的值；失敗時控制項會跳回去。因為往返只有幾十毫秒，失敗也少見，這個代價在前提成立時很小，換到的是每次操作都立即回應。

這個模式依賴擁有者端的兩個保證。如果擁有者沒有單一寫入者（每個請求各自讀寫檔案），或 view 沒有單調遞增的版本號，就不能讓畫面並行送出；應先在擁有者端補上這兩點，再拆掉畫面的鎖。

什麼時候不該用

  • 值之間有必須一起成立的約束。例如「最小值不能大於最大值」、多欄位組成一個帳號設定。逐欄各自儲存會產生暫時不合法的組合。這時改用表單：使用者填完按「儲存」，一次送出、一次驗證、一次寫入。
  • 往返很慢或常常失敗。跨網路、會被伺服器大幅改寫的值，樂觀顯示會頻繁跳回去，反而更混亂。應顯示「儲存中」並在完成前保持原值，或先在本地驗證。
  • 動作不可逆或昂貴。刪除、付款、送出訊息不該樂觀地假設成功；它們是動作，不是值。
  • 只有一兩個欄位、幾乎不會連續操作。全頁鎖雖然不優雅，但如果使用者永遠碰不到並行，拆開的複雜度不值得。
  • 寫入彼此依賴順序以外的語意。例如「切換語言」會改變其他所有設定的顯示文字。這仍然可以並行，因為整份 view 會由最新 revision 決定；但若某項改動會使另一項的值失效，擁有者必須在寫入佇列中檢查，而不是假設畫面送來的值都還合法。

套用在本專案

RecordStuff 是一個 Electron 螢幕錄影 App，設定頁與錄影工作室跑在 renderer，主程序擁有設定。擁有者端的兩個保證原本就存在：設定儲存（SettingsStore.save）是單一佇列，主程序產生的每份 view 都帶遞增的 revision，畫面也早就會丟棄舊的 view。真正卡住的是畫面端：choose() 用一個全域的 saving、一個全域的請求編號與一個全域的 failure，任何設定存檔時，其他設定的選擇都被丟掉，於是每個控制項都得在別人存檔時暫時 disable。在錄影工作室裡，這就是改寬度時其他欄位一起閃的原因。

改動因此集中在畫面端：

  • saving 換成每項設定一份的 savingOf(group)，failure 換成 failureOf(group)，全域請求編號只用來產生唯一 id，每項設定只聽自己最新的請求。
  • committed() 對值類設定做樂觀顯示，confirmed() 保留擁有者的值作為失敗後的重試基準。
  • 開關、分段按鈕、下拉選單、滑桿、文字欄位、螢幕排列與錄影工作室的所有欄位，不再因為別的設定存檔而 disable。
  • 動作按鈕只等自己那項設定；只有隱藏介面、結束與快捷鍵編輯器使用 anySaving() 等待所有存檔。

測試鎖住的是行為，不是實作：一個 UI 測試讓第一項設定的存檔卡住，確認第二項設定仍可操作、立刻顯示、立刻送出，並在兩者都回應後保持正確的值；一個頁面測試確認同一項設定的動作重複按會被忽略，另一項設定的動作則照常送出；另有測試確認失敗後控制項退回擁有者的值。

開發過程中曾先做過「畫面端排隊」的版本，它解決了閃爍，但留下串接延遲、關窗遺失與兩套顯示來源三個問題，最後被這個版本取代；這段歷程正好對應前面的做法二。

在別的程式碼庫判斷是否適用

  1. 設定值是否由另一方擁有，而畫面每次只改一個值？
  2. 擁有者是否有單一寫入者，讓每次寫入都從最新已存值出發？沒有就先補。
  3. 擁有者送出的每份資料是否有單調遞增的版本，畫面能否據此丟棄舊資料？沒有就先補。
  4. 值之間是否有必須一起成立的約束？有的話，那一組改用表單一次送出。
  5. 往返是否夠快、失敗是否少見，讓樂觀顯示偶爾跳回去可以接受？
  6. 哪些送出是動作而不是值？它們不做樂觀顯示，只防同一項的重複觸發。
  7. 哪些操作真的需要等所有存檔完成？把它們列成明確的例外，其餘一律各自儲存。
