編解碼器、容器與不怕當機的錄影：每一個選擇的取捨

錄影工具最容易被低估的風險不是畫質，而是「還沒按停止就當機了，檔案還在不在」。本文從 codec 和容器的分工講起，拆開 MP4 的索引與資料，說明 muxer 為什麼總要在最後回頭補寫，再逐一比較幾個架構選擇：硬體或軟體編碼器、自己寫 muxer 或連結 FFmpeg、一般／fragmented／hybrid MP4、由誰寫檔、多久 sync 一次，以及收尾失敗時怎麼辦。每個選擇都會講清楚它依賴的條件、替代方案的代價、其他產品怎麼選，以及哪些情況會讓結論翻轉。貫穿範例是 RecordStuff 在 2026 年 10 月換上的 Rust 原生錄影引擎。

問題：錄影檔什麼時候才算「存在」

想像使用者錄了一場一小時的會議，第 59 分鐘時，錄影程式當掉了。原因可能是程式本身的 bug、作業系統把它殺掉、筆電沒電，或是磁碟滿了。使用者的期待很單純：至少留下當機前那 59 分鐘。

最直覺的寫法是這樣：編碼器每產生一段壓縮好的畫面和聲音，就追加到檔案尾端；按下停止時，再寫一份「目錄」，記錄每一格在哪裡、多大、什麼時間播放。這正是一般 MP4 的寫法。正常停止時，它的結果最好：檔案精簡、相容性最高，任何播放器都能直接打開。

問題出在沒有正常停止的時候。磁碟上已經有 59 分鐘、可能好幾 GB 的壓縮資料，但目錄還沒寫。播放器不知道一格從哪裡開始、在哪裡結束，也不知道它屬於畫面還是聲音，多數播放器會直接說「檔案已損毀」。資料都在，檔案卻等於壞了。更天真的做法是把整段錄影留在記憶體、停止時一次寫出，那連資料都不會留下。

這件事牽動好幾股互相拉扯的力量：

  • 當機時保留多少。理想是保留到中斷前一兩秒。
  • 正常存檔後的相容性與開檔速度。QuickTime、瀏覽器、剪輯軟體都要能打開，而且要立刻打開。
  • 從停止到可用的時間。收尾時間不應該隨錄影長度增加；一小時的錄影不能讓使用者等一分鐘。
  • 程式大小與授權。多帶一套媒體函式庫，就多一份體積和授權義務。
  • 可擴充性。今天輸出 H.264 MP4，明天可能要 MOV、HEVC 或 MKV。
  • 實作與驗證的成本。每多一種檔案形式，就多一組要測的失敗情境。

所以本文要回答的是：寫檔管線要怎麼設計，才能讓任何時刻中斷都留下可播放的檔案，正常結束時又得到相容性最好的檔案，而且收尾時間不隨錄影長度增加？要回答這個問題，得先把「檔案」拆開來看。

心智模型：codec、容器、索引與資料

影音檔牽涉兩件常被混為一談的事：

  • Codec（編解碼格式）決定「一格畫面或一段聲音怎麼壓縮成位元組」。影像有 H.264、HEVC（H.265）、AV1；聲音有 AAC、Opus。Encoder（編碼器）則是某個 codec 的實作：H.264 可以由 Apple 的 VideoToolbox、Microsoft 的 Media Foundation、開源的 x264 產生，三者輸出的都是合法的 H.264。
  • Container（容器）決定「這些壓縮好的片段怎麼放進一個檔案」：有幾條 track（影像軌、音訊軌）、每個片段屬於哪條 track、什麼時候播放、用什麼 codec 參數解碼。MP4、MOV、MKV、WebM 都是容器。寫容器的程式叫 muxer，讀容器的叫 demuxer。

兩者互相獨立：同一段 H.264 可以放進 MP4，也可以放進 MKV。只換容器、不碰壓縮資料的轉換叫 remux，速度大致等於複製檔案；要換 codec 才需要解碼再重新編碼（transcode），又慢又會損失畫質。這個區分很重要，因為「當機後救檔」幾乎都是容器層的問題，不是 codec 的問題。

容器裡又有兩種性質完全不同的資料：

  • Payload（資料本體）：壓縮後的樣本本身，佔檔案的 99% 以上。它在編碼器交出來的那一刻就定了，寫下去之後不必再改。
  • Index（索引）與 metadata：每個樣本的位置、大小、時長，哪些是關鍵影格，codec 參數，總長度。它很小，但要等到最後一個樣本出現，才寫得完整。

不怕當機的錄影，本質上就是在處理一個問題：在 payload 持續寫入的同時，讓索引隨時都處於「可讀」的狀態。

後文會反覆用到以下名詞：

名詞白話解釋
樣本（sample）容器裡的最小單位：一格壓縮後的畫面，或一個 AAC 封包（1024 個聲音 frame）。
關鍵影格（key frame、sync sample）不依賴其他影格就能解碼的畫面。播放器只能從關鍵影格開始播，所以跳轉、截斷後的恢復都以它為起點。
timescale、tick容器用整數記時間：timescale 是「一秒有幾個 tick」。影像常用 90,000，聲音常用取樣率（48,000）。
解碼時間與顯示時間有 B-frame（雙向預測影格）時，解碼順序和顯示順序不同，容器要另外記差值（ctts）。沒有 B-frame 時兩者相同。
Priming（編碼延遲）AAC 編碼器輸出的開頭一小段不是真正的聲音，而是編碼器自己的延遲。播放時必須跳過，否則聲音會比畫面晚。
sync／fsync要求作業系統把已寫入、但還在記憶體快取裡的資料真正落到磁碟上。

MP4 的內部：ISO BMFF 的 box

MP4 和 MOV 都屬於 ISO Base Media File Format（ISO BMFF，ISO/IEC 14496-12）這個家族，源頭是 Apple 的 QuickTime 檔案格式。它的基本單位叫 box（QuickTime 稱為 atom）：開頭 4 bytes 是大小，接著 4 bytes 是類型（例如 moov），然後是內容。box 可以層層巢狀。大小欄位寫 1 時，後面會多出 8 bytes 的 64 位元大小，檔案超過 4 GiB 時就需要它。

  trak            每條 track 一個
    tkhd          track 編號、長度、畫面大小

    mdia

      hdlr        vide（影像）或 soun（聲音）

        stsd      codec 參數（avc1 + avcC、mp4a + esds）

        stsz      每個樣本的大小

播放器要找到第 n 格畫面，先用 stts 算出時間，再用 stsc、stco、stsz 算出它在檔案裡的位置與長度。注意：這些表格的每一列都要等對應的樣本寫下去之後才知道，而 stco 記的是從檔案開頭算起的絕對位置。所以完整的 moov 只能在最後寫。

Fragmented MP4 換了一種組織方式。開頭的 moov 只描述 track 與 codec 參數，sample table 全部是空的，另外放一個 mvex 宣告「後面還有 fragment」。接著每隔一段時間寫一個 fragment，也就是一個 moof（這一段的小索引）加上一個 mdat（這一段的樣本）：

Textftyp
moov              track 與 codec 參數；sample table 全空
  mvex / trex     宣告這是 fragmented 檔
moof              第 1 段的索引
  mfhd            序號
  traf            一條 track 在這一段的內容
    tfhd          哪條 track；位置從這個 moof 的第一個 byte 起算
    tfdt          這一段第一個樣本的解碼時間

mdat              第 1 段的樣本
moof / mdat       第 2 段……

關鍵在於：每個 fragment 都是自我描述的。它的位置是相對於自己的 moof 計算，時間由 tfdt 直接給出，所以 fragment 寫下去之後，再也不需要修改。讀取端一段一段往下讀，讀到不完整的最後一段就停下來。

Edit list 與 AAC 的 priming

索引不只記錄「樣本在哪裡」，也記錄「從哪裡開始播」。AAC 編碼器輸出的前幾個封包，包含編碼器自身的延遲。Apple 的 QuickTime 檔案格式文件以 2112 個 frame 作為 Apple AAC 編碼器的典型 priming 值，在 48 kHz 下約 44 ms。如果直接從第一個樣本開始播，聲音就會比畫面晚 44 ms。

這些 priming 樣本不能直接丟掉，因為解碼器需要它們來「暖機」。正確做法是保留樣本，再用 elst（edit list）告訴播放器：「這條 track 從媒體時間 2112 開始播」。最後一個 AAC 封包也會補滿 1024 個 frame，多出來的尾巴同樣由 edit 的長度排除。這是容器層的修正，不需要動到任何壓縮資料。

為什麼 muxer 要回頭寫

有了上面的結構，就能理解一個普遍現象：多數容器在結束時，都必須回到檔案前面改寫某些欄位，或在尾端補寫某些東西。原因是容器的某些欄位記錄的是「總量」或「絕對位置」，而這些值要到最後才知道。

  • 一般 MP4：mdat 開頭的大小欄位，要等所有樣本寫完才知道，muxer 通常先寫一個佔位的標頭，最後再回頭補上。完整的 moov 則追加在尾端。如果要求 moov 放在檔案前面（俗稱 faststart，方便網路邊下載邊播），就得把整個檔案重寫一遍。FFmpeg 的 -movflags +faststart 就是在收尾時多跑一輪，把資料往後搬。另一種做法是先預留空間（FFmpeg 的 moov_size 選項），但預留不夠時，寫檔就會失敗。
  • MKV（Matroska）：以 EBML 元素組成，每個元素都有大小欄位。Segment 的總大小、影片長度、用來跳轉的索引 Cues，以及開頭指向 Cues 的 SeekHead，都要在結束時補寫或回頭改寫。不過 Matroska 允許「未知大小」的元素，所以一個寫到一半就中斷的 MKV，仍然能從頭依序播放，只是長度未知、跳轉比較差。這也是 OBS 長期建議「先錄 MKV，需要時再 remux 成 MP4」的原因。
  • WebM（Matroska 的子集）：瀏覽器的 MediaRecorder 是邊錄邊把資料片段交給網頁，自己沒辦法回頭改寫已經交出去的片段。因此一種常見的情況是：錄出來的 WebM 缺少長度與 Cues，播放器的進度條無法正常跳轉，必須事後再處理。

由此可以歸納出一條通則：只要容器的索引參照了絕對位置或總量，muxer 就只有三條路：回頭改寫、整檔重寫，或事先預留空間。Fragmented 的設計則換了一個思路：讓每一段都自我描述，從根本上避開回頭改寫。這條通則，也決定了後面「由誰寫檔」的答案：如果寫檔的一方只拿得到一串只能往後追加的片段，它就無法回頭改寫，除非它自己也懂這個格式。

三種寫 MP4 的方式：一般、fragmented、hybrid

Hybrid 的技巧值得多看一眼。錄影時，檔案就是一個標準的 fragmented MP4。存檔時只做兩件事：

  1. 在檔案尾端追加一個完整的 moov。它的 sample table 列出所有樣本，stco 直接指向它們在各個 fragment 裡的現有位置。
  2. 把開頭那個舊 moov 的前 16 bytes，改寫成一個 64 位元的 mdat 標頭。這個 mdat 從舊 moov 的位置一路涵蓋到新 moov 之前，於是舊的 moov 和所有 moof 都變成 mdat 裡的「不透明資料」，播放器會直接略過。

結果檔案從頭讀起是 ftyp、mdat、moov，就是一個一般 MP4。整個過程沒有複製或搬動任何樣本，所以收尾時間只和索引大小有關，與影片長度無關。

Fragmented 的「播放器要讀每一段」不只是理論。RecordStuff 舊的錄影路徑曾經直接存 fragmented MP4。2026-10-10 量測一段 36 分鐘、2.7 GB、2,106 個 fragment 的錄影：Chromium 要先讀約 358 MB、花約 1.1 秒，才顯示第一格；同樣的資料轉成一般 MP4 後，只需要 27 到 41 ms。AVFoundation（QuickTime、Quick Look）則完全打不開那個 fragmented 檔（錯誤 -11832），轉成一般 MP4 後就能開。

還有第四條路：錄成本來就耐中斷的格式，存檔後再複製成新檔。OBS 的「錄 MKV、自動 remux 成 MP4」選項，以及 Cap 把錄影寫成一段段 DASH segment、停止後在背景 remux 成新 MP4 的做法，都屬於這一類。它的代價是收尾時要把整個檔案複製一遍，時間和需要的磁碟空間都與長度成正比，換來的好處是錄影時的格式可以自由選擇。

當機之後能救回什麼

「當機」其實包含幾種不同的情況，能保住的東西也不一樣：

  • 錄影程序當掉或被殺。程式已經呼叫 write 寫出的資料，就算還沒落盤，也已經在作業系統的 page cache 裡，作業系統會照常把它寫到磁碟。會遺失的，只有程式自己還沒交出去的部分：編碼器裡的影格，以及 muxer 還沒寫出的 fragment。
  • 作業系統當機或斷電。只有 sync 過的資料有機會留下，而且前提是檔案系統與磁碟確實照 sync 的要求寫入；沒有 sync 的資料則沒有任何保障。這是定期 sync 真正在防的情況。
  • 磁碟滿或寫入錯誤。檔案可能停在某個 box 的中間。讀取端必須能辨認「最後一個 box 不完整」，然後在那裡停下。

不同檔案形式的救援難度天差地遠。一般 MP4 少了 moov，只能用工具（例如 untrunc 一類的程式）拿同一台機器、同一種設定錄出的完好檔案當參考，逐格猜出樣本邊界來重建，結果沒有保證。Fragmented 檔則不需要救，播放器本來就能播到最後完整的一段。如果需要一般 MP4（例如要給 QuickTime 開），用 FFmpeg remux 一次即可：

Shell# 只換容器、不重新編碼：讀 fragmented 檔，寫成一般 MP4，並把 moov 放到前面
ffmpeg -i partial.recording.mp4 -c copy -movflags +faststart recovered.mp4

這行指令也說明了 FFmpeg 適合待的位置：它是很好用的事後工具，但這一步需要把整個檔案讀寫一遍。

RecordStuff 的做法是不自動修復。每次錄影開始前，主程序會先寫一個 sentinel 檔，記錄這次錄影的暫存檔路徑；正常結束後再刪掉。下次啟動時，如果發現殘留的 sentinel，就在歷史紀錄中加一筆「RecordStuff 沒有正常結束」，並附上 partial 檔的位置，不掃描、也不改寫任何檔案。實測在錄影中途直接殺掉錄影程序，留下一個可以播放 8.0 秒的 partial 檔。兩條 track 的長度差了 147 ms，因為影像和聲音各自大約每秒寫一次 fragment，中斷時各自停在不同的位置。

「可播放」要說清楚是被誰播放。前面提到，AVFoundation 打不開舊路徑產生的 fragmented 檔。新引擎中斷後留下的 fragmented 檔，在 QuickTime 能不能開，目前沒有驗證過。所以「中斷後的檔案可以播放」這個保證，目前只對 Chromium、ffprobe 這類讀得懂 fragment 的工具成立；對其他播放器，最穩當的說法是「資料都在，remux 一次就能用」。

六個選擇與它們的取捨

以下每個選擇都用同一個框架來看：它依賴哪些條件、替代方案要付出什麼代價、其他產品怎麼選、RecordStuff 怎麼選，以及什麼情況會讓結論翻轉。其他產品的做法只寫有公開資料可查的部分，不確定的地方會明白標出。

1. 硬體編碼器或軟體編碼器

選項。硬體編碼器由專用晶片處理，例如 Apple 晶片的 media engine（透過 VideoToolbox 使用），以及 GPU 廠商的編碼器（在 Windows 上透過 Media Foundation 的 encoder transform 使用）。軟體編碼器則在 CPU 上執行，代表是 x264；Microsoft 也提供 Media Foundation 的軟體 H.264 編碼器。

硬體適合的條件。錄影時，使用者正在用電腦做別的事，CPU 預算要留給他；要即時編碼；位元率設得夠寬裕，讓不同編碼器之間的壓縮效率差距不那麼重要；輸出是本機檔案，而不是低頻寬的直播。

硬體的代價。同樣的位元率下，畫質通常比不上 x264 的慢速 preset；可調的參數少；行為會隨 GPU、驅動程式和作業系統版本改變，所以在一台機器上的驗證，能推廣的範圍比較小；而且未必存在。虛擬機器常常沒有 GPU。Windows 的 N 版本沒有安裝 Media Feature Pack 時，連 Media Foundation 的編碼器都沒有。

軟體的代價。1080p60 即時編碼會吃掉可觀的 CPU。x264 採 GPL 授權（另有商業授權），打包進非 GPL 的 App 會產生授權問題。

其他產品。OBS 兩種都提供，讓使用者選 x264 或各平台的硬體編碼器。QuickTime 透過 AVFoundation 使用系統編碼器。Chromium 的 MediaRecorder 在平台提供硬體編碼器時會使用它，在 Mac 上就是 VideoToolbox。

RecordStuff。macOS 用 VideoToolbox（影像）和 AudioToolbox（AAC）。Windows 依設計是「GPU 提供時用硬體，否則用 Microsoft 的軟體編碼器」；不過目前的程式碼還在用軟體 H.264 encoder transform，硬體編碼器（非同步的 encoder transform）仍是待辦。編碼器的設定是為錄影、而不是串流調整的：關閉 frame reordering（不產生 B-frame），讓解碼順序等於顯示順序，容器就不需要 ctts，每一格的時長也能直接由下一格的時間推出來；並且至少每秒一個關鍵影格，讓每個 fragment 都從關鍵影格開始。代價是少了 B-frame，壓縮效率略低一些。

什麼會翻轉結論。需要在很低的位元率下保住畫質，例如有上傳大小限制；需要跨機器產生可重現的輸出，例如做測試基準；某個 GPU 系列的硬體編碼器有 bug；或目標平台根本沒有硬體編碼器。最後一種情況一定要有軟體備援。

2. 自己寫 muxer，或連結 FFmpeg／libav

FFmpeg 是什麼。FFmpeg 是一個開源專案，主要包含幾個函式庫：libavcodec（編解碼器）、libavformat（容器的 mux／demux）、libavfilter（濾鏡）、libswscale（縮放與色彩轉換），以及大家熟悉的 ffmpeg、ffprobe 命令列工具。libav 通常指這組函式庫，也是曾經從 FFmpeg 分出去、後來停止維護的專案名稱。

連結 FFmpeg 的好處。幾百種容器與 codec，經年累月磨出來的邊界情況處理，以及現成的 faststart、fragment 等選項。如果產品要在錄影時讓使用者自選 MKV、WebM、MOV，這是最省事的路。

連結 FFmpeg 的代價。

  • 體積與建置。依編譯選項不同，大小可以從數 MB 到數十 MB。每個平台都要建置、簽章，並跟上版本更新與 API 變動。
  • 授權。FFmpeg 預設以 LGPL 2.1 以上版本授權；啟用 GPL 元件（例如 x264、x265）後，整個建置就變成 GPL。以 LGPL 發佈時，常見做法是動態連結：保留授權聲明、提供（或承諾提供）該函式庫的原始碼，並讓使用者可以換上自己修改過的版本。靜態連結則還需要提供讓使用者重新連結的目的檔。對一個以 MIT 授權、發佈已簽章 App 的專案，這些都做得到，但每次發佈都多了一份要持續遵守的義務。這裡只是工程上的概要，不是法律意見。
  • 控制權。不怕當機的檔案配置、收尾的 sync 順序、失敗時退回哪一種形式，這些正是錄影工具最在意的細節，卻得透過別人的抽象層去控制。

自己寫的代價。每多一種容器，就是一份新工作；要自己讀規格，處理 edit list、64 位元大小、colr、esds 這類細節；還要自己驗證各家播放器的相容性。好消息是，只寫一種容器家族的範圍不大：RecordStuff 的 MP4 writer 連同測試大約 750 行。

FFmpeg 適合放在哪裡。可以分成三個位置來看：

  • 錄影路徑：這裡最在意即時性、耐中斷和小體積，可以不放 FFmpeg。
  • 匯出與轉檔：例如 GIF、WebM、MKV。這時速度不必即時，格式種類才是重點，正是 FFmpeg 擅長的。
  • 開發工具：用 ffprobe、ffmpeg 解碼成品、量測指標，不隨 App 發佈，也就沒有發佈上的授權義務。

其他產品。OBS 本身採 GPL，也大量使用 FFmpeg，但它的 Hybrid MP4 是 OBS 自己寫的 muxer（plugins/obs-outputs/mp4-mux.c）。Cap 的錄影管線用到 FFmpeg，包括停止後的 remux；它的這部分程式碼採 AGPLv3。

RecordStuff。錄影路徑用自己寫的 ISO BMFF muxer，涵蓋 MP4 和 MOV；這次只輸出 H.264 + AAC 的 MP4。其他格式留給未來的匯出功能，到時可以只為轉檔引入 FFmpeg。

什麼會翻轉結論。錄影時就必須提供多種容器；團隊沒有人能維護格式細節；產品已經為了其他功能（例如剪輯器）帶上 FFmpeg；或者專案本身就是 GPL。

3. 一般、fragmented 還是 hybrid

三者的比較在前一節的表格裡。這裡把它們依賴的條件說清楚：

  • 一般 MP4：只有在中斷的代價很低時才合理，例如很短的片段、可以重錄，或者有可靠的外部救援流程。
  • 只用 fragmented：適合讀取端本來就吃 fragment 的情況，例如瀏覽器的 MSE、DASH／HLS（CMAF）串流；或者輸出目標根本不能回頭寫，例如 pipe、上傳串流。
  • Hybrid：適合輸出是本機檔案、存檔後要給 QuickTime 和剪輯軟體開，同時又要耐中斷的情況。前提是能在檔案任意位置寫入，而且錄影期間在記憶體保存整份 sample table。RecordStuff 每個樣本保存大小與時長各 4 bytes，60 fps 錄一小時約 216,000 格，影像部分不到 2 MB。

Hybrid 多出來的代價是：要測兩種形式，收尾的每一步都要有失敗處理，而且「最後的檔案一定是一般 MP4」這件事不保證成立（見第 6 個選擇）。

什麼會翻轉結論。輸出改成不能回頭寫的目標，就只剩 fragmented；檔案本來就要再經過剪輯器處理，像 Cap 那樣錄 segment、事後 remux 就更自然；如果目標播放器全都讀得懂 fragment，hybrid 的收尾就沒有必要。

4. 由誰寫檔：擷取引擎自己寫，或把 chunk 串給另一個程序

背景。Electron 這類桌面 App 有一個主程序（main process），負責視窗、選單和檔案，它的 JavaScript 跑在單一的 event loop 上。RecordStuff 舊的錄影路徑是這樣分工的：一個隱藏的 Chromium renderer 用 MediaRecorder 編碼，每秒把一段 fragmented MP4 透過 IPC 交給主程序；主程序的 FileWriter 依序追加寫入、每 5 秒 sync 一次；存檔時，再由 TypeScript 寫的 mp4-finalize.ts 解析這些不是自己寫出的 fragment，建立索引，把檔案變成一般 MP4。

RecordStuff 的決定（plan 076 的 D3）。改由原生引擎自己完成擷取、編碼、mux 與寫檔，並定期 sync。錄影時寫成可以從中斷恢復的 fragmented 形式，存檔時變成一般 MP4。主程序保留檔案的生命週期：檔名與資料夾、開始前的剩餘空間檢查、sentinel、歷史紀錄、通知，以及包含結束與睡眠處理的狀態機。引擎則以事件回報寫了多少 bytes，以及寫入錯誤（磁碟滿、寫入失敗）。理由有三個：

  1. 多數容器要回頭寫才能收尾。MP4 的 moov、MKV 的大小欄位與 Cues 都是如此。一串只能往後追加的 chunk，接收端無法乾淨地回頭改寫，除非它也懂這個格式。只有一種格式時，這還勉強可行，舊路徑就是讓主程序去解析 MP4；可是一旦輸出格式可以選擇，muxer 的邏輯就會被拆到兩個程序、兩種語言裡。
  2. 主程序的 event loop 卡住時，不再拖延寫檔。主程序的 event loop 可能因為 UI、IPC、GC 或某個同步呼叫而停頓。原生引擎的寫檔執行緒不受它影響：擷取和編碼器的 callback 把樣本丟進 channel 就返回，從不等待磁碟。
  3. 媒體相關的程式碼集中在同一種語言。

代價。引擎必須自己處理磁碟錯誤，例如把 ENOSPC 歸類成 disk_full；也要限制等待寫入的資料量，RecordStuff 設在 64 MB，超過就讓錄影以 output_write_failed 失敗，而不是一直佔用記憶體到程序被殺。主程序也失去直接觀察寫檔的能力，只能依靠進度事件判斷寫檔是否停滯。

被否決的替代方案。

  • 沿用「chunk 交給主程序既有的 writer」：今天改動最少，但會擋住其他容器。
  • 把原生模組直接載入主程序：最簡單，但原生程式碼一當掉，整個 App 就跟著結束。
  • 做成獨立的執行檔：隔離最徹底，但必須先證明 macOS 的螢幕錄製權限也套用在它身上。

最後的選擇是放在 Electron 的 utilityProcess：它當掉時只結束那個子程序，已經寫出的資料留在磁碟上。

其他產品。以 MediaRecorder 為基礎的網頁錄影工具，本質上就是 chunk 串流模型：瀏覽器把 Blob 片段交給頁面，由頁面處理後續。OBS 是單一原生程序，由它的輸出模組自己寫檔。

什麼會翻轉結論。擷取程序被沙盒限制、不能寫檔；輸出只能是網路串流；或者確定永遠只輸出一種只需要往後追加的格式。在這些情況下，chunk 串流反而更簡單。

5. 多久 sync 一次，fragment 多長

Sync。前面提過，sync 防的是作業系統當機和斷電，不是程序當機。RecordStuff 的目標是每 5 秒 sync 一次，讓斷電時通常只失去最後幾秒和一個 fragment；但這是預定的檢查點間隔，不是保證：sync 能保住多少要看檔案系統與磁碟是否如實把資料寫下，一次卡住的寫入或 sync 也會讓之後的檢查點延後。代價是 sync 在慢速磁碟上（網路磁碟、USB 硬碟）可能要等很久。由於 sync 發生在寫檔執行緒上，等待只會讓資料在 channel 裡排隊，不會卡住擷取；排隊的上限就是前面的 64 MB。

Fragment 長度。RecordStuff 的影像 fragment 在滿一秒後的第一個關鍵影格結束，聲音每一秒結束一段，兩條 track 各自分段，以免晚到的聲音拖住影像。Fragment 越短，中斷時遺失越少，但每段都有 moof 的額外開銷：trun 每個樣本佔 12 bytes，fragment 越多，播放器開檔時要掃的 box 也越多。Fragment 越長，額外開銷越小，但中斷時遺失越多。

什麼會翻轉結論。常常斷電的環境，sync 要更頻繁；很慢的網路磁碟，可能要降低頻率並提示使用者；直播類輸出則需要更短的 fragment。

6. 收尾失敗怎麼辦

Hybrid 的收尾會寫檔兩次，每一次都可能失敗。設計原則只有一條：每一步之前與之後，檔案都必須是某一種播放器讀得懂的形式。RecordStuff 的順序是：

  1. sync，確認所有 fragment 都已落盤。
  2. 在尾端追加完整的 moov，然後 sync。如果失敗，就把檔案截回追加之前的長度，退回原本的 fragmented 檔。
  3. 把舊 moov 的前 16 bytes 改寫成 mdat 標頭，然後 sync。如果寫入失敗，標頭可能只寫了一半，這時兩種形式都讀不懂，所以要把原本的 16 bytes 寫回去。如果是 sync 失敗，程式碼假設 16 bytes 落在同一個磁區內，要嘛整個寫進去、要嘛完全沒寫進去，因此不論哪種結果，檔案都還讀得懂。

只要沒有變成一般 MP4，引擎就在回報中寫明原因（例如 index not written: …），並照常發佈這個 fragmented 檔，而不是把它當成錄影失敗。如果在步驟 2 和 3 之間中斷，檔案就是「fragmented 檔，後面多了一份沒人用的索引」，讀得懂 fragment 的播放器仍然照常播放。

另一半的問題是時間。在 RecordStuff 的第一版原型裡，引擎要等檔案收尾完成，才回報 stopped；而 Recorder 對停止設了 10 秒的期限。在很慢的磁碟上，收尾可能超過 10 秒，錄影就會被當成 stop_timeout 結束，偏偏這時檔案正在收尾。後來的修正把兩件事分開：

現在引擎的 stop 在擷取與編碼器都停止後就回報 stopped，另一個 finish 則在檔案變成一般 MP4，或確定變不成、且知道原因之後，才回報 finished（或寫入錯誤）。在一台 Mac 上實測，Recorder 在 stopped 之後 0 到 1 ms 回到閒置，檔案在其後 19 到 22 ms 收尾完成。慢到足以超過舊期限的磁碟，這次沒有找到可以重現的環境，所以「慢速磁碟不再觸發 stop_timeout」目前是由事件順序與單元測試證明，沒有實際在慢速磁碟上驗證過。

其他產品。Cap 同樣先結束錄影狀態，再交給另一個登錄表處理收尾。根據 RecordStuff 對 OBS 原始碼的靜態檢視，OBS 的 Hybrid MP4 收尾在步驟之間沒有加上 sync 屏障，而且 OBS 和 Cap 都沒有限制收尾的時間。

什麼會翻轉結論。如果收尾變成與長度成正比的工作（例如 remux 複製），就需要顯示進度，可能也要讓使用者取消。如果某個流程要求「存檔完成」之前什麼都不能做，例如自動上傳，那就必須等 finished，而不是 stopped。

實例：RecordStuff 的一次錄影

RecordStuff 是一個常駐 macOS 與 Windows 選單列的錄影 App，以 Electron 和 TypeScript 寫成。在 plan 076 中，它把擷取、編碼、mux 與寫檔，從 Chromium 移到一個用 Rust 寫的原生模組（native/capture/），在 Electron 的 utilityProcess 裡執行。下面依序走過一次錄影，看前面那些選擇如何落實。

一個時鐘

每次錄影只用一個單調遞增的時鐘：macOS 用 mach absolute time，Windows 用 QueryPerformanceCounter。影像樣本保留擷取時的時間戳。聲音則依累計的樣本數放進 track，不採信每個 buffer 自帶的時間戳：只要時間戳與計數的差距在容忍範圍（10 ms）以內，buffer 就接在上一個後面。時間戳跑在前面時（裝置有一段時間沒送資料），中間補上靜音；落在後面時（聲音時鐘跑太快），就丟掉多出來的樣本。所以不管錄多久，聲音相對畫面的漂移都不會超過容忍值。這個「對齊器」叫 AudioAligner，在 timing.rs。實測 10 分鐘錄影的漂移是 0 ms：600 組閃光與嗶聲全部對上。

編碼器與寫檔執行緒

VideoToolbox 的設定如前所述：即時模式、不重排影格、至少每秒一個關鍵影格。AudioToolbox 的 AAC 編碼器在建立時，會透過 kAudioConverterPrimeInfo 回報它的 priming frame 數。Windows 的 Media Foundation AAC 編碼器不公開這個值，所以引擎建立編碼器時，先餵一段靜音來實際量測。

編碼好的樣本經由 channel，送到一個專門的寫檔執行緒。這條執行緒擁有檔案與 muxer：收到 H.264 的參數（avcC）後，才寫出開頭的 ftyp 與空表 moov；在那之前到達的 AAC 封包會先暫存起來。之後，影像在滿一秒後的第一個關鍵影格切段，聲音每秒切段，每段用一次寫入追加到檔尾；每 5 秒 sync 一次，每秒回報一次寫了多少 bytes。

Edit list：讓 priming 消失在播放時間裡

Muxer 的 track 設定裡有一個 skip 欄位，就是編碼器回報的 priming。寫 trak 時，它變成一個 edit：

Rust// 節錄自 native/capture/src/mux/mp4.rs 的 write_trak，註解為本文所加
if track.config.skip > 0 || track.presented.is_some() {
    // 一個 edit：從媒體時間 skip（AAC 的 priming）開始播。
    // fragmented 時還不知道總長，segment duration 寫 0，表示「播到最後」。
    let edts = w.open(b"edts");
    let elst = w.open_full(b"elst", 1, 0);
    w.u32(1)
        .u64(if plain { track.duration_in(movie_timescale) } else { 0 })
        .u64(u64::from(track.config.skip));
    w.u16(1).u16(0);
    w.close(elst);
    w.close(edts);
}

單元測試用 2112 個 frame 的 priming 檢查這段：50 個 AAC 封包，包含 priming、一秒的聲音和尾端補齊的部分。fragmented 階段，edit 是 (0, 2112)，也就是「長度未知，從 2112 開始」；收尾後，edit 變成 (48_128, 2112)，track 長度也是 48,128，尾端補齊的部分被排除在外。有一個細節值得注意：有 edit 的影片，會把整部影片的 timescale 設成聲音的取樣率，這樣 edit 才能剛好停在最後一個樣本上，不會被捨入成整數毫秒。

收尾

停止時，引擎先清空影像與聲音編碼器，把剩下的樣本送進 channel，接著回報 stopped，再請寫檔執行緒收尾。收尾的核心就是前一節的三步：

Rust// 節錄自 HybridMp4::finish，省略部分分支，註解為本文所加
self.out.sync()?;                               // 1. 所有 fragment 先落盤
let end = self.end;
let mut w = BoxWriter::new();
write_moov(&mut w, &self.tracks, true);          // 完整索引，stco 指向各段樣本的原位置
if let Err(cause) = self.out.write_at(&w.bytes, end).and_then(|_| self.out.sync()) {
    // 2. 索引寫不進去：截回原長度，仍是 fragmented 檔
    let _ = self.out.truncate(end).and_then(|_| self.out.sync());
    return Ok((FinishReport { bytes: end, fragmented: Some(format!("index not written: {cause}")) }, self.out));
}
let total = end + w.len() as u64;
if let Err(cause) = self.out.write_at(&mdat_header_64(end - self.moov_at), self.moov_at) {
    // 3. 標頭可能只寫了一半：把舊 moov 的前 16 bytes 寫回去
    return match self.out.write_at(&self.moov_head, self.moov_at).and_then(|_| self.out.sync()) {
        Ok(()) => Ok((FinishReport { bytes: total, fragmented: Some(format!("header not written: {cause}")) }, self.out)),
        Err(restore) => Err(io::Error::new(cause.kind(), format!("header not written ({cause}) nor restored ({restore})"))),
    };
}

注意索引的內容是在每個 fragment 確實寫入之後才更新的。這樣索引描述的永遠是磁碟上真正存在的東西，而不是「原本打算寫進去的東西」。測試會檢查幾件事：

  • 截在 fragment 中間的檔案，仍然讀得出所有完整的 fragment。
  • 索引寫入失敗時，檔案會退回 fragmented。
  • 標頭只寫了一半時，原本的 16 bytes 會被寫回去。
  • 收尾後的檔案頂層依序是 ftyp、mdat、moov，每個樣本的位元組與時間都和寫入時相同。

和舊路徑對照

舊路徑的檔案配置一樣是 hybrid，差別在於誰懂這個格式。MediaRecorder 寫出 fragmented MP4，主程序的 TypeScript 再一路跟著解析它寫出的每個 fragment，記錄每個樣本的大小、時長和位置，存檔時用同樣的「追加 moov、改寫 16 bytes」完成收尾。當年為 36 分鐘錄影建索引只花了 16 ms，索引大小 1.5 MB。

但它必須理解一個別人寫的檔案。遇到它看不懂的結構，例如 track 不從 0 開始，需要它不會寫的 edit list，就只能放棄，維持 fragmented。新引擎自己寫檔，priming 就能直接用 edit list 處理，不必去理解別人的檔案。另外，在同一台 Mac 上量測整體結果：每個檔案的音訊與畫面長度差，從 +13 到 +15 ms 變成 0 ms；錄影時的 CPU 從 15.3%／23.3% 降到 10.4%／14.0%（30／60 fps，單核百分比）。兩條路徑在 Mac 上都使用 VideoToolbox 硬體編碼，所以 CPU 的差異來自整條管線，而不是硬體與軟體編碼器的差別。

編碼器平台編碼器：VideoToolbox／AudioToolbox；Media Foundation（目前用軟體 H.264）即時錄影、CPU 要留給使用者、位元率寬裕每位元畫質略低、行為因機器而異、要處理沒有編碼器的環境低位元率要求畫質、需要可重現輸出、沒有硬體
Muxer自己寫 ISO BMFF（MP4／MOV）錄影時只輸出一種容器家族；在意耐中斷的細節與體積新容器都是新工作；相容性要自己驗證錄影時就要多種容器；已經帶著 FFmpeg；GPL 專案
FFmpeg 的位置不在錄影路徑；只在開發量測，未來的匯出可用匯出與錄影的需求不同匯出時才付授權與體積成本錄影時就需要轉檔
檔案形式Hybrid MP4本機檔案、可任意位置寫入、要給 QuickTime 開兩種形式、收尾的失敗處理、記憶體中的 sample table不能回頭寫的輸出；事後本來就要 remux
誰寫檔擷取引擎（utilityProcess 裡的寫檔執行緒）格式要可擴充；主程序 event loop 可能停頓引擎自己處理磁碟錯誤與排隊上限沙盒不能寫檔；永遠只用只追加的格式
Sync 與分段每 5 秒 sync；約每秒一個 fragment能接受斷電時遺失數秒慢速磁碟上的 sync 等待；每段的額外開銷常斷電；慢速網路磁碟；直播
收尾失敗停止與收尾分開；失敗就保留 fragmented 檔並說明原因收尾時間短且固定「存檔後一定是一般 MP4」不再保證收尾變成複製；後續流程需要完整檔案

不要這樣做的情況

  • 不要在輸出不能回頭寫時用 hybrid。寫到 pipe、socket 或上傳串流時，收尾的第二步根本做不到。這時直接用 fragmented，並讓讀取端去處理 fragment。
  • 不要在錄的是短片、而且可以重錄時，為耐中斷付出這麼多複雜度。錄 5 秒 GIF 素材的工具，用一般 MP4 加上「失敗就重錄」就夠了。
  • 不要為了「以後可能要很多格式」，就把 FFmpeg 放進錄影路徑。格式需求真的出現時，通常是匯出功能，而匯出不需要即時、也不需要耐中斷。
  • 不要自己寫 muxer，如果錄影當下就必須支援多種容器，或者團隊沒有人能維護格式規格。這時 libavformat 的成熟度，比自己掌控細節更值錢。
  • 不要讓接收 chunk 的一方去解析它沒寫過的格式，除非你能接受「看不懂就放棄」。RecordStuff 的舊路徑正是這樣，它確實能在看不懂時安全地退回 fragmented，但也因此無法正確處理需要 edit list 的情況。
  • 不要把 sync 當成防程序當機的手段，也不要把它放在擷取執行緒上。程序當機不需要 sync；把 sync 放在擷取執行緒上，慢速磁碟就會讓錄影掉格。
  • 不要把收尾放在停止的期限裡。只要收尾可能碰到慢速磁碟，就要把「停止擷取」和「檔案完成」分成兩個事件。

可以帶走的判斷準則

  • 你的容器的索引參照了什麼？參照絕對位置或總量的索引，一定要回頭寫。先確定寫檔的一方做得到。
  • 中斷有哪幾種，各自能保住什麼？程序當機、斷電、磁碟滿，要分開回答。sync 只回答其中一種。
  • 每一個寫檔步驟之前與之後，檔案是哪一種讀得懂的形式？如果答不出來，那一步就需要回復機制，或者要換個順序。
  • 收尾時間和錄影長度有關嗎？有關的話（remux、faststart），就要有進度顯示、空間檢查，以及不受停止期限限制的生命週期。
  • 「可播放」是指被誰播放？列出目標播放器，並分別驗證中斷檔和正常檔。
  • FFmpeg 解決的是哪一個位置的問題？錄影、匯出、開發量測，三者的授權、體積與即時性要求都不同。
  • 編碼器的設定是否在幫 muxer 的忙？不重排影格、固定的關鍵影格間隔，會讓 fragment 切段、時長計算和收尾都簡單很多。
  • 什麼證據能翻轉你的選擇？先寫下來：需要的新格式、新的輸出目標、新的播放器、測到的失敗。下次遇到時，就知道該重新評估哪一個決定。
